# Математика материалов полигонов: `none/reflective/translucent/varadd/add/shade` (M4.2.4)

Что здесь: точная математика всех шести материалов полигонов мира — по
инструкциям `gundx.exe` 1.36 (ImageBase `0x400000`), а не по догадке
вьювера. Инструмент: `tools/re/material_blend.py` (`--json`, `--stats`,
`--xrefs`, `--self-test`; stdlib + `gm/sbw.py`, всё только чтение).

**Главный вывод, который меняет прежнюю картину:** per-kind математика в
движке **есть** — это четыре LUT-билдера, которые стартуют вместе с
материальной таблицей (`0x41f618`/`0x41f8d1`/`0x41fbe3`/`0x41ff6f`). Но в
**поставочной 3dfx-сборке эти LUT не читает никто**: кадровый проход берёт из
записи материала только `+0x10` (общий `lighttable`) и рисует **все** полигоны
одним Glide-стейтом `grAlphaBlendFunction(ONE, ONE_MINUS_SRC_ALPHA, ZERO, ZERO)`,
т.е. прозрачность берётся из альфы текстуры. Поэтому:

* «точная математика режимов» — это формулы LUT (§3), они доказаны;
* «как движок рисует материал» — никак: бит 0 поля `mode` (и только он)
  используется в **трассировке/выборе** (`0x437fba`, `0x439e75`, `0x43d568`), и
  выставлен он **только у `reflective`** (mode = 1); у остальных mode = 2 и
  бит 0 = 0. Прежнее утверждение «движок делит полигоны на два прохода по
  биту 0» — неверно: `2 & 1 == 0` (см. §2.3).

## 1. Метод и инструмент

* **Таблица не берётся из констант**: `tools/re/material_blend.py` читает
  байты конструктора `0x420c03` (опкоды `C7 /0`, `A1`/`89`) и строки имён прямо
  из `.data`, затем проверяет, что они совпадают с моделью (эти же проверки
  гоняет `--self-test`). Ошибиться в «переписанной руками» таблице нельзя.
* **Формулы** сняты с листинга (`objdump -D -M intel`), кэш
  `~/.cache/gunmetal-re/gundx.asm`, через `tools/re/disrange.py`. Каждая
  формула в коде инструмента снабжена адресами инструкций.
* **Потребители** — байтовый скан образа на little-endian `e0 70 56 00`
  (`--xrefs`): 183 вхождения, 7 кластеров, «прочих» — 0. Плюс отдельный скан
  `mov reg,[reg+0xb4]` / `mov [reg+0xb4],reg` — кэш таблицы в контексте рендера
  (запись `0x4223ce`, чтение `0x4409c5`).
* **Данные** — 36 поставочных `.sbw` через `gm/sbw.py` (`--stats`).

Ghidra не запускалась (MCP выключен); декомпилятор не использовался, только
инструкции.

(в поставке используется только стиль 0), но `materials.py --map` и
`docs/WORLD_MATERIALS.md` §2.1 стоит поправить.

### 2.3 Что `mode` значит на самом деле

* `0x437fc3` (луч/выбор, `0x437d05`), `0x439e7e`, `0x43d571`: `mode & 1` —
  полигон допускается в выбор/трассу **даже без текстуры** (ветка `0x437fba`).
  Это единственные читатели бита 0.
* `0x42453f` (валидатор `0x423edb`): `mode & 2`, затем `mode & 1`; при
  «транспарентной» текстуре (ниббл `[0x76ed44+0x10*(tex-1)] == 1`) и
  `mode & 1 == 0` печатает `"Warning: transparent texture %s found at
  sector[%ld].object[%ld].poly[%ld]"` (`0x4a8ea8`). То есть биты режима
  связаны с прозрачностью, но **рендер их не читает вообще**.
* `2 & 1 == 0` ⇒ у `translucent/varadd/add/shade` бит 0 **снят**. Утверждение
  «движок отправляет полигон во второй проход, если бит 0 выставлен, а значит
  varadd/add/shade идут во второй проход» (NOTES.md, docs/FORMATS.md,
  docs/WORLD_MATERIALS.md) — неверно: под гейт попадает ровно 300 полигонов
  `reflective` из 235 069.

## 3. Математика шести видов (доказано по инструкциям)

Обозначения: `texel_c` — канал цвета текселя, `shade_c` — канал цвета
освещения (палитровый индекс лайтмапа/света), оба в **6-битном** виде `0..63`
(палитра игры — 256×3 байт в `0x83d320`, заполняется в рантайме).
Все LUT — `0x10000 = 256×256` байт, индексация `LUT[row*0x100 + col]`.

| материал | формула (по каждому из r,g,b, в этом порядке) | clamp | билдер | LUT |
|---|---|---|---|---|
| `none` | `out = texel` (LUT нет, `+0x08 = NULL`) | — | — | — |
| `reflective` | `out = (texel + shade + 1) >> 1` | нет (≤63 by construction) | `0x41ff6f` | trantable |
| `translucent` | `out = (texel + shade + 1) >> 1` | нет | `0x41ff6f` | trantable |
| `varadd` | `m = max(shade)`; `m < 16` → `w=63, k=16`, иначе `w = 63−(m+m/2)`, `k = m+m/2+16`; `w = max(w,0)`, `k = min(k,63)`; `out = min(63, (shade*k + texel*w) / 63)` | сверху | `0x41fbe3` | varaddtable |
| `add` | `out = min(63, texel + shade)` | сверху | `0x41f618` | addtable |
| `shade` | `out = clamp(texel * (63 − shade) / 63, 0, 63)` | с двух сторон | `0x41f8d1` | shadetable |

`>>` — арифметический сдвиг (`SAR`), `/` — `IDIV` (усечение к нулю), т.е.
порядок операций важен: сначала сумма/произведение, потом деление, потом
clamp (кроме `tran`, где clamp не нужен).

Инструкции-якоря:

* **tran** `0x41ff6f`: `LEA EAX,[EAX+EDX+1]` (`0x42000e`) + `SAR EAX,1`
  (`0x420012`) на канал; остальные каналы — `0x420033/0x420037` и
  `0x420058/0x42005c`; сохранение в LUT — `0x42007c`.
* **shade** `0x41f8d1`: `MOV ECX,0x3f; SUB ECX,[shade]` (`0x41f9ad`),
  `IMUL` (`0x41f9b8`), `IDIV 0x3f` (`0x41f9c1`); clamp снизу `0x41f9f8`,
  сверху `0x41fa1f`.
* **add** `0x41f618`: суммы `0x41f6f4`..`0x41f70c`; насыщение `0x41f70f`..
  `0x41f736` (только сверху).
* **varadd** `0x41fbe3`: `max` трёх каналов `0x41fcbf`..`0x41fd04`;
  ветка `m < 16` — `0x41fd07`; `w/k` — `0x41fd1d`..`0x41fd3d`; clamp весов —
  `0x41fd40`..`0x41fd53`; сумма-деление `0x41fd5a`..`0x41fdb1`.
* **`col == 0` — тождество**: у всех четырёх билдеров внутренний цикл имеет
  спец-ветку «если столбец 0, положить номер строки»: add `0x41f672`,
  shade `0x41f92b`, varadd `0x41fc3d`, tran `0x41ffd6`. Отсюда два вывода:
  (а) `LUT[row][0] = row` — «нулевой shade = не смешивать», даже если
  палитровая запись 0 не чёрная; (б) **строка — это тексель**, столбец — shade
  (у `shade`/`varadd` это видно ещё и по асимметрии формулы).
* **Квантизация** (общая для всех билдеров): `idx18 = r<<12 | g<<6 | b`
  (`0x41f736` для add), затем байт из `[0x567128 + idx18]`, а при
  `flag[src_index] != 0` (таблица `0x530fb8`) — ещё из `[0x56712c + idx18]` и
  выбор ближнего по сумме квадратов (`0x41fa88`).

Три визуально разных режима из этого следуют так:

* `translucent`/`reflective` — «полупрозрачный»: цвет = среднее текстуры и
  света (50/50, с округлением вверх). `reflective` отличается от
  `translucent` **только** полем `mode = 1` (и именем): та же LUT, та же
  интенсивность 64. Это важный факт для вьювера (§7).
* `add` — аддитивный: `texel + shade` с насыщением.
* `varadd` — «переменный add»: вес зависит от **максимального** канала света.
  Тёмный свет (`m < 16`) почти не меняет тексель (слабая добавка), средний —
  осветляет (веса в сумме 79/63, т.е. ярче единицы), яркий (`m = 63`) —
  полностью заменяет тексель цветом света. Из-за смены ветки на `m = 16`
  функция **немонотонна** (проверяется в `--self-test`: 23 → 22).
* `shade` — затемнение: умножение на `(63 − shade)/63` с усечением.

## 4. Что делает с этим поставочный рендер (доказательство «нет»)

1. `tools/re/material_blend.py --xrefs`: 183 обращения к базе `0x5670e0`,
   кластеры — free `0x420bd3`, конструктор `0x420c03` (170), `ctx+0xb4 =
   table` `0x4223ca`, валидатор `0x424538/0x424554`, экспорт `.sow`
   `0x426df0/0x426ef8`, имена `0x42eb2c/0x42eb7a`, гейт выбора
   `0x437fbc/0x439e77/0x43d56a`. **Ни одного** чтения в кадровом проходе,
   кроме одного (`ctx+0xb4`).
2. Кадровый проход `0x4409b8`: `MOV ECX,[EAX+0xb4]` (`0x4409c5`) →
   `MOV EDX,[ECX+0x10]` (`0x4409cb`, байты `8B 51 10`) = `table[0]+0x10` =
   `lighttable`, у всех 30 записей одинаковый. Других полей записи функция не
   читает (единственное использование — `0x441b41`/`0x441b59`).
3. Указатели LUT (`0x567104/108/118/11c/120/124`) читаются **только** в
   аллокаторе/фри (`0x41e3d8`..`0x41e7ff`), в билдерах (`0x41f600`..
   `0x41ffff`) и в конструкторе (`0x421240`..`0x42223d`) — проверяется
   ассертом в `--self-test`.
4. `lighttable` в рендере — это **фог по глубине**, а не материал:
   `level = 0x3f − ftol(z)` (`0x44194d`), clamp `4..0x3f` (`0x441963`,
   `0x441976`), затем `fbuf[i] = lighttable[level*0x100 + fbuf[i]]` на
   заблокированном LFB (`0x441b27`..`0x441b59`). Сама таблица (`0x4201fe`)
   устроена как «тянуть цвет к белому»: при `level < 0x40`
   `c' = (pal*(0x40−level) + level*0x40) >> 6`, clamp 63; при `level ≥ 0x40`
   — белый; строки `0x80..0xff` — тождество.
5. Кадр целиком: `grColorCombine(1,0,1,2,0)` (`0x440a74`),
   `grAlphaCombine(1,0,0,2,0)` (`0x440a84`),
   `grAlphaBlendFunction(ONE, ONE_MINUS_SRC_ALPHA, ZERO, ZERO)` (`0x440abe`).
   Один стейт на весь кадр; прозрачность — из альфы текстуры.

**Вывод:** в этой сборке материал не влияет на смешение вообще. Per-kind
математика исполняется (LUT-ы строятся) и остаётся мёртвым грузом — вероятно,
наследие программного рендера DOS-версии (`gun.exe`), где кадр был 8-битным и
смешивался именно такими таблицами. Это гипотеза (§6), но сами формулы — нет.

## 5.1. Поправка к области §4: `0x4409b8` — трасса рёбер, а не заливка

Проверено позже (`docs/FOG.md`): проход `0x4409b8` идёт по major-оси DDA и
пишет **один пиксель на шаг** — это отрисовка рёбер, а не заполнение
полигонов (`grAADrawLine` в 3dfx-режиме). Поэтому вывод §4 «кадровый проход
читает `material[0]+0x10` и рисует» верен только для этой рёберной трассы:
она берёт `lighttable` (фог по глубине), а LUT материалов не читает **нигде**.
Прозрачности из альфы текстуры тоже нет — альфы в `.sbm` нет вообще, есть
бинарный хрома-кей по индексу 0 (`docs/ALPHA.md`). Итог для рендера: ни LUT,
ни материал в кадровый цвет не входят; входят палитра текселя и свет
(лайтмап/яркость), что и делает `gm/render.py`.

## 6. Что осталось гипотезой (и почему)

| утверждение | статус | почему |
|---|---|---|
| `row = texel`, `col = shade` | **сильная гипотеза** (код билдеров + `LUT[row][0] = row`) | потребителя LUT в exe нет, так что порядок индексации при вызове не проверить |
| что именно подаётся в `texel`/`shade` (индекс текстуры и индекс лайтмапа?) | гипотеза | читателей нет; `texel` — очевидно текстура, `shade` — свет (лайтмап/vertex light) по смыслу таблицы |
| `reflective` = зеркало/окружение | гипотеза | запись идентична `translucent` кроме `mode=1` и имени; env-map кода в этой сборке не найдено |
| смысл `mode = 1` vs `2` | частично | бит 0 читают только выбор/трасса (`0x437fba`, `0x439e75`, `0x43d568`) и валидатор (`0x423edb`, текст «transparent texture»); бит 1 — только валидатор |
| `+0x2c` (0/64/64/100/127/−128) | **не веса** | запись есть (`0x4214d8`..), читателей нет ⇒ трактовать как коэффициент смешения нельзя |
| точная финальная квантизация LUT | не воспроизводима из exe | палитра `0x83d320`, dither-таблицы `0x8c8000`/`0x908000`, флаги `0x530fb8` — BSS, заполняются в рантайме |
| «LUT-ы — наследие DOS-рендера» | гипотеза | косвенно: они строятся, но не читаются; в DOS-версии кадр 8-битный |
| побочный эффект: второй проход | **опровергнуто** | `2 & 1 == 0`; в рендере гейта нет вовсе |

## 7. Расхождение с текущим `gm/render.py::face_blend`

Сейчас (`face_blend`, строки ~557–579):

```python
w = MATERIAL_INTENSITY[idx] / 127.0
if MATERIALS[idx] == "translucent":
    return ("mix", 0.5)
return ("add", w)
```

| материал | сейчас во вьювере | что доказано | расхождение |
|---|---|---|---|
| `none` | нет прохода | нет прохода | ок |
| `reflective` | `add` с весом 64/127 = 0.504 | LUT `trantable` = **среднее 50/50** текселя и света | режим неверный: это не аддитив, а смешение |
| `translucent` | `mix` 0.5 | `trantable`: `(texel+shade+1)>>1` | число 0.5 верное, но смешивается с **фоном/чёрным**, а не с цветом света; и без `+1`-округления |
| `varadd` | `add` с весом 100/127 = 0.787 | переменный вес от `max(shade)`, ветка `m<16`, сумма весов 79/63 | не константа; при ярком свете замещение, при тёмном — почти ничего |
| `add` | `add` с весом 127/127 = 1.0 | `min(63, texel+shade)` по каналам | вес 1.0 случайно совпал; нет насыщения по каналам и нет «shade = цвет света» (сейчас добавляется чёрный/константа) |
| `shade` | `add` с весом −128/127 = −1.008 | `texel*(63−shade)/63`, clamp 0..63 | знак/смысл неверны: это умножение-затемнение, а не вычитание |
| гейт «второй проход» | по `bit 0` ⇒ `reflective + все прочие` | бит 0 только у `reflective`; рендер его не использует | вьювер рисует «вторым проходом» 5 материалов, движок — ни одного |

Итого: из шести режимов случайно угадан ровно один (`translucent` ≈ 0.5) и
один вес (`add` = 1.0). Остальное — приближение, которое теперь можно
заменить точными формулами.

## 8. Рекомендация: как переносить

### 8.1 Что выбрать

Есть два разных «правильно», их надо развести явно:

* **A. Паритет с поставочным движком** (`materials="engine"`): никакого
  per-material смешения — один бленд `ONE, ONE_MINUS_SRC_ALPHA` (альфа
  текстуры), плюс `lighttable` как фог по глубине. Материал влияет только на
  то, попадает ли полигон в выбор/трассу.
* **B. Математика режимов** (`materials="lut"`): точные LUT-формулы из §3,
  texel = цвет текстуры, shade = цвет лайтмапа (в вьювере — цвет освещения
  полигона). Это то, что «задумано» таблицей и что видно в данных как
  смешиваемые полигоны.

Рекомендую: **оставить текущее поведение дефолтом** (регресс бит-в-бит не
трогаем) и добавить opt-in режим `B`, а `A` описать в `docs/RENDER.md` как
«паритет». `face_blend` при этом заменяется на «какая LUT у вида» + точная
формула, а `MATERIAL_INTENSITY` перестаёт быть весом (оставить как справку
`+0x2c`).

### 8.2 Python (`gm/render.py`)

```python
C6 = 63.0                      # каналы движка — 6-битные

MAT_BLEND = {                  # kind -> (lut, formula-tag)
    "none":         (None,          "opaque"),
    "reflective":   ("trantable",   "avg"),
    "translucent":  ("trantable",   "avg"),
    "varadd":       ("varaddtable", "varadd"),
    "add":          ("addtable",    "add"),
    "shade":        ("shadetable",  "shade"),
}

def _c6(v):                    # float 0..1 -> int 0..63, как палитра движка
    return max(0, min(63, int(round(v * 63.0))))

def blend_rgb(kind, texel, shade, shade_is_zero=False):
    """RGB 0..255 (texel) + RGB 0..255 (shade/light) -> RGB 0..255.

    Точная математика LUT (§3): всё считается в 6-битных целых.
    """
    if kind == "none":
        return texel
    if shade_is_zero and kind != "none":
        return texel                       # LUT[row][0] = row
    t = [_c6(c / 255.0) for c in texel]
    s = [_c6(c / 255.0) for c in shade]
    if kind in ("reflective", "translucent"):
        out = [(a + b + 1) >> 1 for a, b in zip(t, s)]
    elif kind == "add":
        out = [min(63, a + b) for a, b in zip(t, s)]
    elif kind == "shade":
        out = [max(0, min(63, a * (63 - b) // 63)) for a, b in zip(t, s)]
    else:                                   # varadd
        m = max(s)
        if m < 16:
            w, k = 63, 16
        else:
            w, k = 63 - (m + (m >> 1)), m + (m >> 1) + 16
        w, k = max(w, 0), min(k, 63)
        out = [min(63, (b * k + a * w) // 63) for a, b in zip(t, s)]
    return tuple(int(round(c * 255.0 / 63.0)) for c in out)
```

`face_blend` тогда возвращает не «вес», а `(kind, lut)`, а второй проход
вьювера (сортировка дальние→ближние, без записи z) остаётся — но рисует
**все** полигоны с LUT, а не «по биту 0».

### 8.3 C++ (`engine/src/render/render.cpp`)

```cpp
// 6-bit integer maths of the engine's palette LUTs (docs/MATERIAL_BLEND.md).
static inline int c6(float v) noexcept {
    int i = (int)std::lround(v * 63.0f);
    return i < 0 ? 0 : (i > 63 ? 63 : i);
}
static inline int idiv63(int num) noexcept {          // IDIV: trunc toward 0
    return num / 63;                                  // num >= 0 here
}
Rgb blend_material(MaterialKind k, Rgb texel, Rgb shade, bool shade_zero) {
    if (k == MaterialKind::None || shade_zero) return texel;  // LUT[row][0]=row
    int t[3] = {c6(texel.r), c6(texel.g), c6(texel.b)};
    int s[3] = {c6(shade.r), c6(shade.g), c6(shade.b)};
    int o[3];
    switch (k) {
    case MaterialKind::Reflective:
    case MaterialKind::Translucent:
        for (int i = 0; i < 3; ++i) o[i] = (t[i] + s[i] + 1) >> 1;
        break;
    case MaterialKind::Add:
        for (int i = 0; i < 3; ++i) o[i] = std::min(63, t[i] + s[i]);
        break;
    case MaterialKind::Shade:
        for (int i = 0; i < 3; ++i)
            o[i] = std::clamp(idiv63(t[i] * (63 - s[i])), 0, 63);
        break;
    case MaterialKind::VarAdd: {
        int m = std::max({s[0], s[1], s[2]});
        int w = 63, kk = 16;
        if (m >= 16) { w = 63 - (m + (m >> 1)); kk = m + (m >> 1) + 16; }
        w = std::max(w, 0); kk = std::min(kk, 63);
        for (int i = 0; i < 3; ++i)
            o[i] = std::min(63, idiv63(s[i] * kk + t[i] * w));
        break;
    }
    default: return texel;
    }
    return Rgb{o[0] * 255.0f / 63.0f, o[1] * 255.0f / 63.0f,
               o[2] * 255.0f / 63.0f};
}
```

Замечания для переноса:

* считать **строго в целых 0..63** и только на выходе переводить в float —
  иначе `+1>>1`, `idiv63` и clamp перестанут совпадать с движком;
* `shade_zero` — это «индекс света 0», а не «чёрный цвет» (см. §3);
* для `reflective` не изобретать env-map: в exe его нет;
* `MATERIAL_INTENSITY` (`+0x2c`) в формулы **не** входит;
* финальную квантизацию (dither-таблицы) для вьювера можно не повторять —
  это палитровый артефакт 8-битного кадра; в float-RGB вьювере она не нужна и
  только добавит шум. Если нужен пиксель-в-пиксель с игрой — это отдельная
  задача (палитра + dither, недоступны из exe).
