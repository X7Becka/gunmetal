# Gunmetal — спецификация форматов данных

Всё ниже проверено на реальной установке `D:\games\Gunmetal 3dfx` (v1.36) и
реализовано в пакете `gm/`. Где формат разобран не до конца — это отмечено
явно («статус»), без догадок «под видом факта».

Термины: `u8/u16/u32` — little-endian целые, если не сказано иное.
Все размеры даны в байтах.

---

## 1. Архивы BIGFILE (`.idx` + `.dat`)

Пара файлов: индекс `*.IDX`/`*.idx` и данные `*.DAT`/`*.dat`.

```
IDX:
    char  magic[7];        // "BIGFILE"
    u8    0x1A;            // разделитель
    u32   count;
    count * {
        char name[8];      // NUL-дополненные, virtual-имена
        u32  offset;       // смещение блоба в .dat
    };

DAT:
    сырая конкатенация блобов: размер блоба = offset[i+1] - offset[i],
    последний — до конца файла.
```

`name` — не имя файла на диске, а «виртуальное» имя ресурса: движок обращается
к нему как `PICS\<name>.sbm`, `sounds\<name>.sou` и т.п.

Проверенные архивы установки:

| Индекс | Записей | Размер `.dat` | Полезная нагрузка |
|---|---:|---:|---|
| `PICS/SBM.IDX` | 1648 | 45 442 175 | `.sbm` (текстуры, с mip-цепочкой) |
| `sprites/SBM.IDX` | 179 | 1 083 044 | `.sbm` (спрайты, 1 уровень) |
| `sounds/SOU.IDX` | 999 | 26 738 998 | `.sou` (звуки/музыка) |
| `FRONTEND/BMP.IDX` | 143 | 2 845 582 | Windows BMP |

Между блобами нет паддинга (смещения строго непрерывны), а имена — NUL-дополненные
8-байтные поля. Поэтому архив **пересобирается побайтово точно**: пересборка всех
пяти архивов из их же блобов даёт идентичные `.idx` и `.dat` (проверено).

Реализация: `gm/bigfile.py` (`BigFile`, `Entry`, `build_index`, `pack`,
`replace_entry`).
CLI: `gm.py list <idx>` — таблица; `gm.py extract <idx> <out>` — сырые блобы;
`gm.py pack <out.idx> <dir> [--ext .EXT]` — собрать архив из каталога;
`gm.py set <idx> <name> <file> <out.idx>` — заменить/добавить одну запись.

## 2. Текстуры и спрайты `.sbm`

8-битные палитровые блобы; палитра в блобе **не хранится** (см. §6).

```
struct Sbm {
    u32 zero;               // в поставке всегда 0
    u8  log2_width;         // width  = 1 << log2_width
    u8  log2_height;        // height = 1 << log2_height
    u8  levels_minus_one;   // число уровней mip = levels_minus_one + 1
    u8  zero;
    u32 flags;              // в поставке 0 или 1
    u8  pixels[];           // mip-цепочка, уровень 0 первым, индексы палитры
};
```

Уровень `k` имеет размер `(w >> k) x (h >> k)`; цепочка идёт до уровня,
заданного `levels_minus_one`. Полный размер пиксельных данных:

```
sum( max(1, 1<<(log2w-k)) * max(1, 1<<(log2h-k))  for k in 0..levels_minus_one )
```

Это тождество выполняется **побайтово для всех 1648 записей `PICS` и 179
записей `sprites`** — так формат и был подтверждён.

**Писатель / repack.** `Sbm.to_bytes()` пересобирает блоб ровно как прочитан
(побайтово для всех 1827 блобов). `sbm.encode(w, h, pixels, levels, flags, mip)`
строит новый блоб из 8-битных индексов (стороны — степени двойки; `mip` =
`box`/`nearest` для нижних уровней). `flags` значим: у текстур в поставке
0/1/2/16, у спрайтов 256/257 — при пересборке спрайта значение нужно сохранять.

Реализация: `gm/sbm.py` (`parse`, `Sbm.to_png`, `Sbm.to_bytes`, `encode`,
`expected_size`).
CLI: `gm.py textures <game> <out>` и `gm.py sprites <game> <out>`
(у спрайтов по умолчанию индекс 0 делается прозрачным: `--transparent 0`);
обратный путь — `gm.py sbm <image.png|.bmp> <out.sbm> [--palette BMP]
[--game DIR] [--mips N] [--flags N] [--filter box|nearest]` (при совпадении
палитры индексы сохраняются точно, иначе — ближайший цвет). Новый блоб кладётся
в архив через `gm.py set`.

## 3. Модели `.sob`

Текст, но **переводы строк не значимы**: это плоский поток токенов,
разделённых пробелами (в ~половине файлов имя текстуры оказывается в конце
«строки плоскости» — построчный парсер на этом ломается).

```
<vertex_count> <face_count>

vertex_count * ( x y z )                    // float, мировые единицы

face_count * {
    8 токенов-имён                          // [0] — диффузная текстура,
                                            // [1..7] — флаги материала
                                            //   ("none", "translucent", "add")
    flags nverts i0 .. i(nverts-1)          // целые
    [ -1 ]                                  // необязательный одиночный -1
    15 чисел                                // origin(3) U(3) V(3) N(3) spare(3)
}
```

Целочисленная строка может сопровождаться одиночным `-1` в новых файлах;
локально решить, есть ли он, нельзя, поэтому парсер **откатывается назад**
(backtracking с мемоизацией по позиции токена — остаётся линейным).

Векторы `U/V/N` — единичные оси, умноженные на 65536 (16.16-проекция):
`UV = dot(p - origin, axis) / 65536` как первое приближение.

Проверено: **все 672 модели из `SOBS/` разбираются**, поток токенов
расходуется точно. Реализация: `gm/sob.py`; CLI `gm.py sob <src> <out>` пишет
OBJ + MTL.

`.soe` (шаблоны «thing») — тоже поток токенов, но форма иная и разобрана
частично: `parse_soe()` возвращает сырые токены.

## 4. Уровневые `.sbc`

Небольшие блоки маленьких 8-битных карт.

```
struct Sbc {
    char magic[4];          // "SBC0" (5 файлов) или "SBC1" (46 файлов)
    u32  count;

    count * {
        u32 desc;           // w_log = desc & 0xffff, h_log = desc >> 16
        u8  pixels[];       // (1<<w_log) * (1<<h_log) байт
    };
};
```

Записи хранятся вплотную; `8 + sum(4 + 2**w * 2**h)` равно размеру файла
**точно для всех 51 файла** (34 в корне игры + 17 в `SOBS/`). Лишних
«хвостовых» байтов нигде нет.

> Ранняя гипотеза о другой раскладке (заголовок `u32, u16, u16` + «сетка
> байтов, кратных 4») **опровергнута** и заменена раскладкой выше.

Что это за данные: каждая запись — небольшая (от 4×4 до десятков пикселей)
8-битная карта, значения гладкие и в основном в нижней части диапазона. Это
согласуется с атласами лайтмапов, которые логирует движок (`Lightmap mem:
N bytes`). Визуально — маленькие в основном тёмные серые карты; семантика
(лайтмап/что именно) остаётся **гипотезой**.

Поэтому в коде их называют «lightmap-подобные», и работают с ними
честно — как с безымянными 8-битными картами, а не как с доказанными
лайтмапами.

Реализация: `gm/sbc.py` (`parse`, `Record.to_png`, `Sbc.to_bytes`, `encode`).
CLI: `gm.py sbc <пути...> <out>` — на каждый файл каталог с PNG
`NNNN_<w>x<h>.png` и сводный `_sheet.png` (первые 256 записей сеткой);
`--rebuild DIR` — запись обратно (структура сохраняется по подкаталогам,
`to_bytes` побайтово точен для всех 51 файла).

## 5. Звук `.sou`

### 5.1 Контейнер (разобран полностью, все 999 записей)

```
SOU0 / SOU1                          SOU2
------------------------------       ------------------------------
char magic[4]  "SOU0"/"SOU1"         char magic[4]  "SOU2"
u32  sample_rate                     u32  sample_rate
u32  flags      0 или 1              u32  meta1
u32  length     байт payload         u32  meta2
u8   payload[length]                 u32  units
                                     u8   payload[units*4]   // с offset 20
```

* Для `SOU0/SOU1`: payload = `data[16 : 16+length]`. `length` совпадает с
  остатком файла у моно-записей; у трёх стерео-записей `length == payload + 1`.
  Загрузчик требует `(flags & 0xff) <= 1`; `flags == 1` ⇒ стерео
  (6 записей: CUT-EMP, CUT-PAM, CUT-PREZ, INTRO, VRCHAMBR, VRCHAMHQ).
* Для `SOU2`: payload = `data[20:]`, и `units * 4` равно остатку размера файла
  (проверено на FINALE/OVERTURE/WINNER; **FINALE и WINNER побайтово совпадают**).

### 5.2 Кодеки

Диспетчеризация в загрузчике сэмплов `gundx.exe` (VMA `0x40af30`) по цифре
магии:

| Магия | Формат драйвера | Payload |
|---|---|---|
| `SOU0` | 0 | **сырой беззнаковый 8-битный PCM** |
| `SOU1` | 3/2/1 при `rate < 10000 / < 18000 / иначе` | сжатый поток 8-битных кодов, выход 16 бит |
| `SOU2` | 4 | сжатые музыкальные треки |

Из поставки: `SOU0` — 13 записей (лупы: DRONE, ECMLOOP, FFLOOP, THUMH/K/L/M,
F-DFIELD/F-DISL/F-MRLL/F-PCL, C-PC, MAGDEF), `SOU1` — 983, `SOU2` — 3.

**`SOU1`/`SOU2` — это кодек драйвера, а не PCM.** Звуковая система —
Miles Sound System (AIL): в `gundx.exe` есть секции `adpcmseg`, `mixasmda`,
`mixasmse`, `putseg`, `putsegda`, `tempscrs` и строки проб карт («SB 16 sound
card found», …), ключи `/sb`, `/sbpro`, `/sb16`, `/sb32`, `/sb64`. Эти секции —
runtime-буферы; таблицы шагов ADPCM грузились из **отсутствующих** AIL-segment
файлов, поэтому сжатый payload **из самой установки не декодируется**.

Доказательство, что payload сжат, а не PCM: запись `SILENCE` (SOU1, 8000 Гц,
400 байт) — точный 3-байтовый цикл `4b 0c 20` (дельта-кодек держит константу);
как сырой 8-битный PCM это был бы громкий гул. Гистограммы байтов SOU1/2 близки
к равномерным (MAD1/MAD0 ≈ 1.2), тогда как у SOU0 (THUMK, C-PC) — гладкие
(≈ 0.1/0.33).

Поэтому `gm/sou.py` намеренно **отказывается** писать WAV для `SOU1/2`
(`Sou.to_wav()` бросает исключение) — чтобы не выдать мусор за звук.
CLI: `gm.py sounds <game> <out>` пишет 13 WAV (`SOU0`) и 986 сырых дампов вида
`{NAME}.sou{1,2}.{rate}.{mono|stereo}.bin`.

**Статус: контейнер — да; кодек `SOU1`/`SOU2` — открыт** (нужен либо дизасм
драйвера, либо битые AIL-таблицы).

## 6. Палитра и `.bmp`

8-битная графика игры не несёт палитру в блобе. Вместо этого установка
содержит **общую VGA-палитру из 256 цветов**, повторённую (побайтово
идентично) почти во всех `.bmp` файлах. `gm/palette.py` достаёт её из любого
такого BMP:

* `load_from_bmp(path)` — прочитать палитру из файла;
* `installed(game_dir)` — взять из известных носителей
  (`FLAG/naUSA.BMP`, `FLAG/aanataka.bmp`, `PICS/oaktabl1.bmp`, `PICS/mine-1c.bmp`).

`.bmp` — обычные Windows BMP (8 бит, палитровые). `gm/bmp.py` читает их и
нормализует палитру в порядок `R,G,B,X` (в файле хранится `B,G,R,X`) — из-за
этого раньше всё декодированное искусство было синеватым, баг исправлен.

CLI: `gm.py frontend <game> <out>` выгружает `FRONTEND/BMP.DAT`.

### 6.1 Таблицы поиска `LOOK16.TAB` и `LOOK162.TAB`

Оба файла — ровно **262144 Б = 64³**: куб «6-6-6 RGB → байт», т.е.
`data[(r<<12)|(g<<6)|b]`, где `r,g,b ∈ 0..63`. Движок генерирует их при
отсутствии (`gundx.exe` `0x41e771` — таблица 1, `0x41e8ec` — таблица 2; вложенные
циклы по 0x40 значений, на каждый цвет пишется один байт) и иначе просто читает
с диска.

Значение куба — **индекс цвета палитры**: для цвета `(r,g,b)` это ближайший
цвет палитры, найденный взвешенной метрикой ядра `0x4228e0`
(`(sr+0x100)·dr² + 512·dg² + (0x17f−sr)·db²`, где `sr = r + palette[i].r`).
Палитры разные:

* **`LOOK16.TAB`** — палитра игры по умолчанию (рабочая копия `0x5309b8`,
  строится из мастер-палитры `0x83d320`; ремап слотов `0x5620c0`). В поставке:
  234 разных значения, диапазон 1..239 (слоты палитры).
* **`LOOK162.TAB`** — палитра, выбранная `NEONS.PIN` (рабочая копия `0x530cb8`,
  ремап `0x5641c0`). `NEONS.PIN` — текстовый список: число `count`, затем
  `count` индексов палитры. В поставке 20 индексов
  `{173,174,175,191,240..255}` — **ровно** множество значений `LOOK162.TAB`
  (проверено).

Сообщение движка «Generating 16-bit table N...» относится именно к этой
регенерации: при первом запуске таблицы считаются (с прогрессом `%03d`), потом
пишутся и на следующих запусках только читаются. Прикладной смысл — перевод
цвета в индекс 8-битного палитрового кадра. Проверено также, что `LOOK16.TAB`
корректен как разбиение Вороного: 230 из 234 меток односвязны (4 — с двумя
компонентами из-за усечения на границе куба).

Реализация: `gm/look.py` (`load`, `parse_neons`, `stats`, `apply8`, `to_png`);
CLI `gm.py look FILE [--png OUT] [--palette BMP] [--neons NEONS.PIN] [--scale N]`
(экспортирует куб как монтаж 8×8 из 64 срезов, 512×512).

## 7. PNG-вывод

Внешних зависимостей нет (`pip`/`PIL`/`numpy` недоступны), поэтому PNG
пишется и читается вручную поверх стандартного `zlib`: `gm/png.py` —
`from_indexed` (разворот в RGB), `indexed` (8-битный PLTE-индексный PNG,
round-trip без потерь), `gray`, `rgb`, `rgba` и читатель `decode` (8 бит,
без интерлейса, типы 0/2/3/4/6). Индексный вывод используется для `.sbm`, чтобы
правка текстуры не теряла индексы при дубликатах цвета в палитре.

## 8. Анимации `.soa`

Обычный DOS-текст (CRLF). Первая строка — 4 числа, далее имена кадров:

```
<mode> <period> <frames> <loop>
<имя кадра>
...
```

* `frames` — сколько имён читает движок; в нескольких файлах есть лишние
  хвостовые строки (парсер сохраняет все).
* `loop` = 1 (цикл) или 0 (один раз; у `dclock*`, `FILM`).
* `mode` = 0/1; `period` — шаг кадра (24…600).

Проверено: все 77 файлов `anims/` разбираются. Реализация: `gm/soa.py`
(`parse`, `to_bytes`, `from_names`), CLI `gm.py soa <файлы|каталоги>
[--rebuild DIR]`.

**Запись.** Формат строчный: достаточно сохранить точные строки. `Soa.to_bytes()`
собирает файл с CRLF **побайтово точно для всех 104 `.soa`** (включая
`spritani/`, `Sobanim/`); `render_lines()`/`from_names()` дают канонический текст
для новых файлов (без «хвостовых» пробелов и лишних пустых строк оригинала).

## 9. Музыка `.sog` и архив `MUSIC/SOU.DAT`

`.sog` — **это просто текстовый плейлист**: по одному имени сэмпла на строку.
Имена ссылаются не на `sounds/SOU.DAT`, а на **второй BIGFILE-архив**
`MUSIC/SOU.DAT` + `MUSIC/SOU.IDX` (3092 записи, **все `SOU2`**, ~75 МБ).

```
.sog  : line 1..N — имя сэмпла (совпадает с именем записи MUSIC/SOU.IDX)
```

Проверено: все 651 файл `.sog` разбираются; 25 песен ссылаются на 95 имён,
которых нет ни в `MUSIC/SOU.IDX`, ни в `sounds/SOU.IDX` (вырезанный контент —
движок бы выдал «Unable to load sample…»). Реализация: `gm/sog.py`
(`parse`, `to_bytes`, `from_names`),
CLI `gm.py sog <файл|каталог> [--music MUSIC/SOU.IDX] [--rebuild DIR]`
(`to_bytes` побайтово точен для всех 651 файла, включая верхнерегистровые
`.SOG`; `--rebuild` пишет по подкаталогам).

## 10. Мир `.sbw`

Полностью разобран побайтово: **все 36 файлов парсятся ровно до EOF**. Файл —
один последовательный поток, который читает загрузчик `gundx.exe` VMA `0x42aa63`
(таблицы), `0x422f03`/`0x422d55` (аллокаторы), цикл стадии 1 на `0x42ad65` и цикл
стадии 2 `0x425f4c` → `0x422b88`/`0x422a51`:

```
u32 count1;                                    // таблица текстур
count1 * { char name[]; u16 flag; u32 value; };   // name — ASCII с NUL

u32 count2;                                    // таблица эффектов/анимаций
count2 * {
    char name[];          // имя эффекта/анимации
    u32  kind;            // класс анимации (0/1/101/102)
    u32  start;           // первый id сэмпла/кадра
    u32  n;
    u16  ids[n];          // id по порядку
};

u32 count3;                                    // секторы (по 0x18 Б в памяти)
count3 * {                                     // стадия 1: шапки объектов
    u32 objects;          // объектов в секторе
    u16 kind;             // вид/флаг сектора
    u8  sub;              // доп. флаг
    objects * {
        u32 id;           // id объекта
        u8  header[96];   // 4 точки по 3 компоненты; каждая компонента
                          // записана как пара (u32 pad=0, f32) => origin +
                          // 3 масштабированных базисных вектора
                          // (во всех файлах базис = diag 1.875)
    }
}

count3 * objects * {                           // стадия 2: геометрия
    u16 n_verts; u16 n_polys;
    f32 verts[n_verts][3];    // локальные координаты
    f32 radius;               // 0x60 — радиус описанной сферы (= |bounds|)
    u8  f75; u8 f74;          // 0x75/0x74 — не используются (0; f75=1 у 7 объектов)
    u32 f7c; u32 f78;         // 0x7c/0x78 — не используются (0)
    f32 bounds[3];            // 0x84 — полуразмеры AABB (целые в данных)
    u8  reserved[24];         // 0x90 — 24 нулевых байта
    n_polys * { /* см. таблицу полей полигона ниже */ }
}
```

Стадия 1 даёт секторы и объекты с их трансформом, стадия 2 — вершины и
полигоны в том же порядке (сектор × объект). Каждая запись полигона — это
**0x80 байт в памяти** (`resolve_poly` @ `0x434463` возвращает
`object+0x6c + i*0x80`), а на диске поля идут в другом порядке и без указателя
на список индексов, поэтому парсер раскладывает их по смещениям движка.

Что уже точно понятно:

- `verts` + `idx` — это сетка; индексы всегда в диапазоне `0..n_verts-1`
  (проверено на всех 36 файлах). Полигоны в основном четырёхугольники
  (202 097 квадов, 13 628 треугольников, встречаются n-угольники до 12 вершин).
- Заголовок объекта (96 Б) = origin + 3 базисных вектора; каждая компонента
  записана 8 байтами `(u32 pad=0, f32)`. Во **всех** 28 192 объектах pad=0, а
  базис — строго диагональный `diag(1.875, 1.875, 1.875)`; origin лежит в
  пределах примерно ±8.
- Объект (стадия 2): `radius` = |`bounds`| (радиус описанной сферы, проверено:
  21 125 из 28 192 совпадают точно, остальные — из-за округления `bounds` до
  целых); `bounds` — полуразмеры AABB по вершинам (`bounds ≈ (max−min)/2`);
  `f74`/`f78`/`f7c` всегда 0, `reserved` (24 Б) всегда 0.

### 10.1 Поля полигона

Смещения — в 0x80-байтовой записи движка. «Точно» = подтверждено кодом
движка/командой языка; «вероятно» = устойчивая эмпирика.

| Смещ. | Тип | Поле | Смысл |
|------:|-----|------|-------|
| 0x00 | u16 | `texture` | индекс текстуры (знаковый): **>0** — 1-based запись таблицы текстур, **<0** — запись таблицы эффектов (шаг 0x5c), **0** — без текстуры. SET_POLY_TEXTURE (id 0x0f) |
| 0x02 | u16 | `material` | индекс материала 0..5 = none/reflective/translucent/varadd/add/shade; индексирует таблицу материала (ds:0x5670e0, шаг 0x40, имя на +0x34) |
| 0x04 | u16 | `lightmap` | индекс лайтмапа (знаковый), 0 = нет; при загрузке пересчитывается через базу лайтмапов уровня; учитывается в массиве использования лайтмапов |
| 0x06 | u16 | `u_scale` | (вероятно) масштаб текстурных координат |
| 0x08 | 3×f32 | `centre` | центр полигона в локальных координатах (для осевых граней = центроид вершин) |

| 0x54 | u32 | `uv_u_fp` | u32-спутник 0x50 |
| 0x58 | u32 | `uv_v_fp` | u32-спутник 0x52 |

| 0x5e | u16 | `anim0` | анимируемый UV-скаляр |
| 0x60 | u16 | `scroll_v` | скролл по V (SET_POLY_SCROLL) |
| 0x62 | u16 | `anim1` | анимируемый UV-скаляр |
| 0x64 | u16 | `v_scale` | (вероятно) масштаб текстурных координат |
| 0x66 | u16 | `anim2` | анимируемый UV-скаляр |
| 0x68 | u32 | `reserved` | всегда 0 |
| 0x6c | u16[] | `indices` | индексы вершин объекта (`n_idx` штук) |

| 0x72 | u16 | `handle` | слот-id; текстовый загрузчик отображает ввод 1→0x7ff8, 2→0x7ff9, иначе 0 |

Назначение `centre`/`corner_a`/`corner_b` — кэш кадра отрисовки: для осевых
граней они совпадают с вершинами полигона, для наклонных — это проекция на
плоскость лайтмапа. Пять полей `0x5c/0x5e/0x60/0x62/0x66` движок
интерполирует вместе (`0x4342f0`) — так анимируется скролл текстуры.

Реализация: `gm/sbw.py` (полный парсер + экспорт в OBJ + `Sbw.to_bytes`),
CLI `gm.py sbw <файлы> [-v] [--obj DIR] [--transform] [--rebuild DIR]`.

**Запись.** `Sbw.to_bytes()` собирает файл обратно из распарсенных таблиц,
секторов, вершин, 50-байтного хвоста объекта и 112-байтного хвоста полигона —
**побайтово точно для всех 36 файлов**. Это основа для правки геометрии: изменить
вершины/поля и записать (`--rebuild DIR`).


## 11. Видео `.sbv`

**Контейнер.** Заголовок и таблица кадров разобраны по дизассемблеру загрузчика
`gundx.exe` VMA `0x49e1e8` (ширина > 0x140=320 отклоняется):

```
char magic[4];      // "SBV0"
u32  width;         // <= 320
u32  height;
u32  frame_count;
frame_count * { u32 timestamp_ms; u32 end_offset };  // end_offset от data_start
```

`data_start = 16 + 8*frame_count`. Кадр *i* занимает
`[data_start+prev, data_start+end[i])`, где `prev = end[i-1]` (0 для i=0);
последний `end` ровно на EOF (проверено на `Intro` 320×160×500,
`orient` 4523 кадра, `winner` 1820 кадров).

**Кодек — разобран полностью.** Это собственный (не Bink/Smacker/Indeo)
чисто внутрикадровый **пирамидальный** кодек: кадр = 3 плоскости (яркость
`W×H` и две цветности `W/2×H/2`, сэмплы — знаковые 16-битные), каждая
реконструируется «снизу вверх». Декодер транслитерирован 1:1 в `gm/sbv.py`
и сверен с эмуляцией `gundx.exe` **побайтово** на 27 кадрах всех трёх файлов
(включая первый и последний кадр каждого).

Плоскость (дизасм `0x49ee8c`):

1. из потока читаются знаковые `i32 min` и `i32 max`, затем по одному байту на
   сэмпл самой грубой сетки (яркость `(W/4)×(H/4)`, цветность `(W/8)×(H/8)`).
   Значение сэмпла `(int)(byte*(max-min)/256.0 + min)` — деление на вещественную
   константу **256.0** (`0x4a2ac0`), усечение к нулю;
2. остальные сэмплы дочитывает **битовый энтропийный поток**: он заполняет сетку
   блоками `factor×factor` (`0x49f4db`, `factor` 4 → 8), а оставшиеся «щели»
   закрывают инверсный лифтинг `0xa1d940` + фиксация краёв `0x49f1e3` и
   раздвижка `0x49f43a`.
   Последовательность вызовов для яркости:
   `0x49f4db(W/4,H/4,4)`, `0x49f1e3(W/4,H/4)`, `0x49f43a(W/4,H/4)`,
   `0x49f4db(W/2,H/2,8)`, `0x49f1e3(W/2,H/2)`, `0x49f43a(W/2,H/2)`,
   `0x49f4db(W,H,8)`, `0x49f1e3(W,H)`;
   для цветности — `0x49f4db(W/8,H/8,4)`, `0x49f1e3/0x49f43a(W/8,H/8)`,
   `0x49f4db(W/4,H/4,8)`, далее как у яркости без последних трёх вызовов.

Энтропийный декодер (`0xa1d000`): биты читаются **начиная со старшего**.
Состояние (`0x6c08e0`): указатель источника, счётчик бит, аккумулятор и три
предиктора (класс, шаг, знак). На блок:

- унарный код класса + бит знака, DPCM относительно предиктора. Класс `0` —
  весь блок нулей (биты больше не читаются); класс `>= 0x11` — конец плоскости;
- унарный код шага (тоже DPCM) + бит знака блока: `step = 1 << (e & 31)`;
- далее один из 17 статических обработчиков (таблица в `.data` по `0xa1c400`).
  **В реальных файлах встречаются только классы 0, 1 и 3**: полный прогон всех
  6843 кадров трёх файлов (12.3 млн блоков) даёт гистограмму
  `{0: 6526044, 1: 3001203, 3: 2790153}`, счётчик `FAMILY_BLOCKS` = 0;
- **класс 1**: если курсор выровнен на 16 байт и следующий бит `0` — четыре нуля и
  `cursor += 16`; иначе бит «нулевой?», и при `1` бит знака даёт `±step`;
- **класс 3**: так же, но значение `(1 + число подряд идущих единиц) * step`,
  причём бит знака читается **до** серии;
- классы 2 и 4..16 («семейные», `0xa1d170 + 0x80k`) читают N «сырых» бит; в
  реальных данных не встречаются, а сами обработчики внутренне
  несогласованны (читают биты из аккумулятора, не сдвигая его), поэтому в
  `gm/sbv.py` они реализованы «по мере разумения» и считается счётчик
  `FAMILY_BLOCKS`.

Конверсия YUV→RGB (`0x49e33b`), сэмплы знаковые 16-битные, `C0`/`C1` берутся из
цветностных плоскостей в позиции `(x>>1, y>>1)`:

```
r = clamp((Y + C0      + 8) >> 4)   // арифметические сдвиги, clamp 0..255
g = clamp((Y - C0 - C1 + 8) >> 4)
b = clamp((Y + C1      + 8) >> 4)
```

Движок затем прогоняет эти байты через три таблицы по 256 dword
(`0x4a6a40`/`0x4a6e40`/`0x4a7240`) с фиксированной точкой и кладёт результат в
32-битную поверхность DirectDraw; таблицы, судя по всему, гамма-рампа режима
вывода, и в toolkit не воспроизводятся — отдаётся естественный 8-битный RGB.

Модуль `gm/sbv.py` (контейнер + полный декодер),
CLI `gm.py sbv <файл> [out] [--png DIR] [--frames SPEC] [--scale N] [--no-raw]`;
`--frames` принимает `0`, `1,5,9-12` или `all`.


## 12. Мир/уровни `.sbt`

Файл мира — **скомпилированная «World Things file»**. В движке есть два
загрузчика: текстовый (`sbt_load`, `0x454b8d`; писатель — `0x454d20`, режим
`"wt"`) и бинарный, читающий поставленные `*.sbt` («BINARY SAVE»). Бинарный файл
— это тот же текстовый, только скомпилированный, и 1-байтовый *тип* записи —
это числовой id текстового ключевого слова (текстовый загрузчик буквально
сравнивает строки `POLY_HANDLE`/`OBJECT_HANDLE`/`SECTOR_HANDLE`/`SCRIPT`/
`END_OF_FILE` и читает по одной строке чисел — см. строки форматов около
`0x4b9600`). Все 36 поставленных `*.sbt` (`level*`, `dm*`, `secrt*`, `temple`)
разбираются ровно до EOF.

Заголовок (84 байта):

    char magic[80];   // b"BINARY SAVE\0" + нули
    u32  version;     // должен быть 0

Далее — записи. Каждая начинается с 1 байта *типа*; полезная нагрузка следует
сразу за ним и полностью вычитывается обработчиком этого типа. Тип `255`
(`END_OF_FILE`) — конец потока, без нагрузки (последний байт файла). Типы 10 и
13 диспетчеризуются в заглушку, возвращающую -1 (не поддерживаются).

| # | Имя (текстовое) | Полезная нагрузка |
|---|---|---|
| 1 | `SWITCH` | `u32 n <= 0x200`; `n * 32` байт |
| 2 | `DOOR` | `u32 n <= 100`; `n * 184` байт |
| 3 | `THING` | `u8 exists`; если ≠0 — `0x528` байт |
| 4 | `THING_TYPES` | `u32 n <= 0x80`; `n` типов по `936`: `char name[16]` + `double params[49]` + `528` байт целочисленных полей |
| 5 | `NAMED_ITEMS` | `u32 n <= 0x31`; `n` по `52`: `char name[16]` + 9 `u32` (источник — текстовый `item\<name>.soi`) |
| 6 | `SPRITES` | `u32 n <= 0x1f3`; `n * 44` байт |
| 7 | `SOUND_SOURCES` | `u32 n <= 0x7f`; `5*n*4 + n*8` байт |
| 8 | `SECTOR_STUFF` | `0x5800` байт |
| 9 | `PLAYER_STATUS` | `u8 exists`; если ≠0 — `0x3510` байт |
| 11 | `SCRIPT` | `u32 c <= 0xc8` (`c*40`) + `u32 n <= 0x400` (`n*4` ×3) + `u32 m <= 0x30000` (`m` байт) + `u8 flag` (если ≠0 — `9*0x400` байт) |
| 12 | `SOUND_SAMPLE_TABLE` | `300 * u32` + `300` имён по 9 байт (`0x4b0 + 0xa8c`) |
| 15 | `POLY_HANDLE` | `u32 n < 0x1f4`; четыре **параллельных** колонки `u32[n]`: `tag, sector, object, poly` |
| 16 | `OBJECT_HANDLE` | `u32 n < 0x12c`; три колонки: `tag, sector, object` |
| 17 | `SECTOR_HANDLE` | `u32 n < 0x100`; две колонки: `tag, sector` |
| 18 | `LIFT` | `u32 n <= 0x1e` (`n*168`) + `u32 k <= 0xc8` (`k*12`) |
| 19 | `ITEM` | `0x7080` байт |
| 20 | `SOB_TABLE` | `u32 n <= 0xc8`; `n` по `{char name[12]; u32 amount; u32 ptr}` |
| 255 | `END_OF_FILE` | — |

Все поставленные уровни имеют одну и ту же последовательность записей:
`12, 20, [15, 16,] 17, 5, 4, 11, 255`.

### 12.1 Таблицы handle (15/16/17) — координаты полигонов

Записи хранятся **по колонкам**, а не как массив структур: сначала `n` значений
первой колонки, потом `n` значений второй и т. д. Загрузчики читают каждую
колонку в свой глобальный массив (полигоны: `0x5b21f8`, `0x618b88`, `0x5e5680`,
`0x6183b8`), поэтому побайтная раскладка не совпадает с наивным `{u32 ×4}`.

Колонки:

    POLY_HANDLE    tag, sector, object, poly
    OBJECT_HANDLE  tag, sector, object
    SECTOR_HANDLE  tag, sector

`(sector, object, poly)` — это **канонический адрес полигона** в движке: его
принимает `resolve_poly` (`0x434463`) и его же печатает отладочный оверлей
редактора как `SECTOR:%d OBJECT:%d POLY:%d` (глобалы `0x62cae0/e4/e8`).
Проверено: **все 4277 poly-handle, 207 object-handle и 900 sector-handle** из 36
уровней указывают на существующие полигоны/объекты/секторы соответствующего
`.sbw` (`gm.py sbt --resolve`).

Ведущий `tag` — непрозрачный id, присвоенный редактором: по нему адресуют
сущность команды скрипта `SET_HANDLEPOLY_*`/`SET_HANDLESECTOR_*`, тогда как
семейство `SET_POLY_*` адресует полигон прямо тройкой `(sector, object, poly)`
(сигнатуры `LLLL` и `LLLLL` в таблице команд, напр. `SET_HANDLEPOLY_TEXTURE`).
`tag` не уникален и не является функцией данных полигона между уровнями —
поэтому хранится как есть.

### 12.2 Прочие записи

* **`THING_TYPES` (4)** — определения «things» (напр. `bgchunk1`, `CRATE`); 936
  байт = `name[16]` + 49 `double` (значения вида `0.01`, `0.1`, `6000.0`) + 528
  байт целочисленных полей (консольный обработчик «add thing type», `0x47cb6c`,
  читает `u32` по `+0x198/+0x19c/+0x1a8/+0x1ac`). В движке тип загружается из
  *текстового* файла `thing\<name>.soe` (строка `0x4bbb90`, `fopen(...,"rt")`) и
  компилируется в этот бинарный блок — связка с `.soe` (см. §13).
* **`SOUND_SAMPLE_TABLE` (12)** — 300 счётчиков ссылок + 300 имён по 9 байт. Все
  непустые имена (5800 ссылок по всем уровням) находятся в `sounds/SOU.IDX`.
* **`SOB_TABLE` (20)** — `name[12]` → `SOBS/<name>.sob` **или** `Sobanim/<name>.soo`
  (загрузчик логирует «Unable to load SOB or SOO %s»), второе `u32` (`amount`,
  загрузчиком не читается — вероятно счётчик из редактора), и третье `u32` —
  устаревший адрес кучи, который загрузчик перезаписывает указателем на
  разобранную модель (`0x47c845`, шаг записи `0x14`). У четырёх уровней
  встречается имя-заглушка `default`, файла для которого нет.
* **`NAMED_ITEMS` (5)** — `char name[16]` + 9 `u32` (52 байта). Загрузчик
  `0x4689f0` читает запись из текстового `item\<name>.soi` форматом
  `%ld %ld %s %ld %s %ld %s %ld %ld` (три `%s` резолвятся функцией `0x45fb90`)
  и пишет числа по `+0x10..+0x30`; отсюда и граница имени — 16 байт (strncpy
  в `0x468a53` копирует 15 байт). **`SCRIPT` (11)** — скомпилированный
  скрипт-блок; полностью разобран, см. §12.3.

Реализация: `gm/sbt.py`, `gm/sbtvm.py`, CLI
`gm.py sbt <пути...> [-v] [--resolve] [--json DIR] [--rebuild DIR]`
`[--script] [--script-out DIR]` (флаг `--resolve` сверяет таблицы handle с
соседним `.sbw`; `--script` декомпилирует скриптовый блок, см. §12.3).

**Запись.** `Sbt.to_bytes()` собирает файл из 84-байтной шапки и сырых payload'ов
записей — **побайтово точно для всех 36 файлов** (`--rebuild DIR`). Для
полностью разобранных записей есть и структурный кодировщик
`encode_payload(type, payload)`: таблицы handle (15/16/17), `NAMED_ITEMS` (5),
`THING_TYPES` (4), `SOB_TABLE` (20) пересобираются из полей точно (205/205 записей
в поставке); у имён сохраняется полный слот (`name_raw` — в `THING_TYPES` после
NUL встречаются «хвостовые» байты). Правка записи — через `sbt.set_payload`.

## 12.3 Скриптовая ВМ `SCRIPT` (11)

Запись `SCRIPT` — это `count*40` «things» + три параллельные колонки handle
(`n*4` каждая) + `m`-байтный **блок кода** + `flag` (+`9*0x400` таблиц).
Загрузчик записи — `0x462a80`: он читает именно в таком порядке, что и даёт
раскладку выше (прежнее `n*12` — те же байты, три колонки подряд).

Блок кода — поток **инструкций** `[u8 опкод][операнды…]`, где опкод = id
команды; `0xFF` — конец под-скрипта. Размер операндов задаёт *сигнатура*
команды (движковая функция `0x457170`, таблица букв `0x457204`):

| буквы | размер |
|---|---|
| `A` `B` `D` | 8 байт (`double`) |
| `Y` | 1 байт |
| `S` | строка с NUL |
| остальные (`E G I L M N O P R T V Z`) | 4 байта |

В exe две таблицы команд, обе восстановлены и вшиты в `gm/sbtvm.py`:

* **`COMMANDS`** (`0x4b53e8`, 192 шт.) — именованные команды редактора
  (`ADD_DOOR`, `SET_POLY_TEXTURE`, `LOAD_MUSIC`…). Диспетчер — `0x45c500`
  по `id-1`; все 202 id имеют уникальный обработчик.
* **`CONDITIONS`** (`0x4b62ec`, 59 шт.) — команды *второй ВМ* условий и
  выражений (`ADD_THING`, `FIRE_SOURCEPLAYER_LASER`,
  `SOURCEPLAYER_AMMO_AT_LEAST`, `RANDOM`…), обработчик `0x45f490`
  (диспетч `0x45f8e0`).

Несколько id **не имеют имени** в таблице `COMMANDS`, потому что это
*структурные* операторы. Их имена и раскладку дал **текстовый загрузчик
`0x460eca`**: он сравнивает текущий токен с пулированными строками
(`DEFINE_WEAPONS`, `DEFINE_AMMO`, `DEFINE_EQUIPMENT`, `DEFINE_PLAYER_TYPES`,
`DEFINE_LEVEL_OBJECTIVES`, `ADD_LIFT`, `SOURCEPLAYER_PATH`, `IF`, `ELSE`,
`END`) и компилирует их, эмитя байт опкода, затем счётчик, затем операнды
записи тем же обходчиком `0x461bc0`:

| id | имя | раскладка (сигнатура) | метка счётчика |
|---|---|---|---|
| 103 | `DEFINE_LEVEL_OBJECTIVES` | `u32 n (≤30)` + `n` строк (`S`) | `Objectives count` |
| 158 | `SOURCEPLAYER_PATH` | `u32 n (≤32)` + `n*{4}` (`E`) | `Path points` |
| 170 | `DEFINE_WEAPONS` | `u32 n (≤31)` + `n × (3×S + LLLLEEEEELLLLDBBDL)` = 0x54 | `Weapon count` |
| 171 | `DEFINE_AMMO` | `u32 n (≤31)` + `n × (1×S + LEOLLLLLLL)` = 0x28 | `Ammo count` |
| 172 | `DEFINE_PLAYER_TYPES` | `u32 n` + `n × (3×S + LDLLDODDDDLNVNVEED…EE)` = 0x17c | `Number of player types` |
| 175 | `DEFINE_EQUIPMENT` | `u32 n (≤31)` + `n × (1×S + LEEEEEELLLLL)` = 0x30 | `Equipment count` |
| 188 | `ADD_LIFT` | `0x94` байт + `u32 n (≤31)` + `n*0xc` | `Lift stops` |
| 199 | `IF` | `u8 cond-id` + операнды `CONDITIONS[cond]` + `u32 size` + тело(`size`) | — |
| 200 | `ELSE` | `u32 rel` — относительный прыжок *мимо* else-ветки | — |
| 201 (`0xC9`) | `EVAL` | `u8 cond-id` + операнды `CONDITIONS[cond]` | — |
| `0xFF` | `END` | конец под-скрипта | — |

Размеры записей (0x54/0x28/0x17c/0x30/0x94/0xc/4) **побайтово совпадают**
с пулированными сигнатурами (`0x4b8fa8`, `0x4b900c`, `0x4b9024`, `0x4b8fe8`,
`0x4b8f7c`, `0x4b8f78`, `0x4b7ba4`) и проверяются в генераторе.

`ELSE` компилируется как безусловный относительный переход: компилятор
патчит `size` у `IF` так, чтобы при ложном условии прыгнуть на начало
else-ветки, а сама ветка завершается `200` (прыжок за конец ветки). `END` на
нулевой глубине вложенности эмитит `0xFF` (конец под-скрипта). Декодер
разворачивает `IF`/`ELSE` рекурсивно (else-ветка читается линейно до цели
перехода).

**семантика полей таблиц.** Имена таблиц — из ошибок-строк exe
(`Maximum number of ammo/weapon/equipment types exceeded`). Потребители:

| таблица | счётчик (глобал) | массив в памяти | запись |
|---|---|---|---|
| `DEFINE_AMMO` (171) | `0x818958` (≤31) | `0x818960` | 56 байт: имя `char[16]` в `+0x28`, 10 полей |
| `DEFINE_WEAPONS` (170) | `0x819028` (≤31) | `0x80fa00` | **0x2a8 = 680** байт: имя `char[16]` в `+0x298` |
| `DEFINE_EQUIPMENT` (175) | `0x815420` (≤31) | `0x814c8c` | 64 байта: имя `char[16]` в `+0x0f` |

Потребитель ammo `0x450b10` раскладывает переданные поля по
`+0x00,04,08,0c,10,14,18,1c,20,24` (поле `+0x20` клампится снизу в `1`);
в файле запись = имя + 10 слов, порядок слов не совпадает с порядком в
памяти. Значения слова 1 — сквозные id (`4000100+i` = `0x3d0964+i`).

### поля `DEFINE_WEAPONS` (потребитель `0x450be0`, вызывающий `0x45cac0`)

Вызывающий читает запись (после 3 строк) как 21 dword и пушит их
`arg3..arg23`; потребитель сохраняет их в запись по 0x2a8 байт. Строки:
`arg0` = имя (strncpy 15 байт в `+0x298`), `arg1` → `0x40b9c0` (разбор
запросного имени, хендл в `+0x290`), `arg2` = имя иконки → грузится из
каталога `frontend` в `+0x50` (или запись зануляется, если `none`).

Соответствие «операнд сигнатуры → смещение в памяти» (у потребителя
`0x450be0` окно аргументов меняется на `pop ebx` в `0x450d29`, отсюда
«сдвиг на dword» во второй половине полей):

| операнд | offset | смысл | статус |
|---|---|---|---|
| `L1` | `+0x24` | режим огня (switch в `0x445ac0`, кейсы 0/1/4/5; в dm1 — 1, 2, 4) | код |
| `L2` | `+0x2c` | период перезарядки: пишется в `0x81c358` при выстреле (`0x445f08`), `>0` блокирует выстрел (`0x445aa8`) | код |
| `L3` | `+0x3c` | индекс типа боеприпаса (в `DEFINE_AMMO`; `-1` = неизвестен) | код |
| `L4` | `+0x40` | расход боеприпаса на выстрел | код |
| `E1` | `+0x30` | id снаряда/эффекта (arg0 спавнера `0x4795b0`, `0x445ee2`) | код |
| `E2` | `+0x34` | id второго снаряда (спавнится, когда `0x81c35c == 0`) | код |
| `E3` | `+0x38` | значение состояния → `0x81c35c` (`0x445f7b`) | код |
| `E4` | `+0x4c` | id (в dm1 — константа `0xffff8ab5`) | значения |
| `L5` | `+0x44` | цена, в единицах «наличных» `0x81c36c` (столбец `COST`) | код |
| `L6` | `+0x48` | очки: суммируется в счёт игрока `0x81c374` (`0x4524d0`) | код |
| `L7` | `+0x28` | битовые флаги (тесты бит `0x01`/`0x40`/`0x80`) | код |
| `L8` | `+0x294` | индекс класса/семейства (0..8) | значения |
| `D1` | `+0x00` | `double × 0.91`; `≠0` только у баллистических (гранаты 0.015, плазма 0.007) → фактор баллистики | значения |
| `B1` | `+0x08` | разброс (тангенс: 0.0875 = tan5° … 1.732 = tan60°) | значения |
| `B2` | `+0x10` | разброс, вторая ось (тангенс) | значения |
| `D2` | `+0x18` | `double` 500..9999; читается вместе с разбросом при выстреле (`0x445992`) → дальность или скорость снаряда | значения |
| `L9` | `+0x20` | индекс точки вылета: проверяется `0 ≤ x < 8` (`0x4458c4`), индексирует таблицу матриц узлов (`0x81bf38`) | код |

Доказательства. `L3` проверяется на `< [0x818958]` (иначе
`Unknown ammo type for weapon (%s)`), значения сходятся с именами
(`MACHINE GUN`→`BULLETS`, `CANNON`/`AUTOCANNON`→`CANNON SHELLS`,
`FLAMETHROWER`→`NAPALM`, `TAC NUKE`→`TAC NUKE`, `MRL`→`MICRO-ROCKETS`,
лазеры→`POWER CELLS`); `L4` вычитается из запаса игрока
`[0x81c2dc + ammo*4]` при выстреле (`0x445e98`); `L5` читается в
покупке/продаже (`0x47c365` вычитает из `0x81c36c`, `0x47c2a7` возвращает
при продаже); `L2` пишется в счётчик `0x81c358`, который проверяется в
начале обработки выстрела; `L9` ограничен восемью точками вылета. Столбцы
экрана покупки (`0x4be67c` `COST`, `0x4be694` `AMMO TYPE`) независимо
подтверждают `L5`/`L3`. Поля со статусом «значения» доказаны лишь
диапазонами значений и согласованностью с поведением (баллистические
стволы, короткие дистанции у EMP/огнемёта).

Пример из `dm1.sbt`: ammo (15: `BULLETS`…`DECOY`), weapons (19:
`MACHINE GUN`…`MESON GUN`), equipment (12), затем `IF
LEVEL_OBJECTIVES_COMPLETE { DEFINE_PLAYER_TYPES … }` и далее.

**Декодер** `gm.sbtvm.decode(code) -> [Insn]` (тела `IF` — рекурсивно) и
`gm.sbtvm.render(code) -> str`. **Все 36 файлов декодируются до побайтового
конца** (36/36, проверяется в `regress.py`). CLI:
`gm.py sbt <путь> --script [--script-out DIR] [--script-lines N]`.

## 13. Сущности `.soe`

**Разобран** по загрузчику движка (`gundx.exe` VMA `0x47cb6c`), а не по образцу
(в поставке лишь один файл — `SOBS/railrock.soe`). Движок открывает
`thing\<name>.soe` текстом (`fopen(..,"rt")`, строка `0x4bbb90`) и
компилирует в запись `THING_TYPES` из `.sbt` (§12) — бинарный
`char name[16]` + 49 `double` + 528 Б целых.

Файл — поток токенов через пробелы. Первый токен — **версия** (0..13); часть
блоков включается по ней. Порядок чтения (движковые `fscanf`, строка формата →
смысл):

| # | Условие | Формат | Блок |
|---|---------|--------|------|
| 1 | всегда | `%ld` | `version` (0..13) |
| 2 | всегда | `%ld %ld %s %ld %ld` | id-блок (`0x19c`,`0x198`,`class_name`,`0x1a8`,`0x1ac`) |
| 3 | v ≥ 9 | `%ld` | `0x1b0` |
| 4 | всегда | `%s %lf×6 %s` | `collision_type`, 6 `double` (`0x10/0x20/0x28/0x90/0x98/0xa0`), форма |
| 5 | форма `ellipsoid` | `%lf %lf %lf` | радиусы (у railrock `115 115 80`) |
| 5 | форма `sphere` | `%lf` | радиус |
| 6 | всегда | `%lf %lf %lf %lf` | `0x50/0x58/0x60/0x68` |
| 7 | v ≥ 7 | `%s %ld` | `event_a`, `0x1d4` |
| 7 | v < 7 | `%s %s %ld` | то же + второй event |
| 8 | v ≥ 8 | `%ld`×4 | `0x1d8..0x1e4` (max shield values) |
| 8 | v < 8 | `%ld` | одно значение на все 4 |
| 9 | всегда | `%s %s` | texture info |
| 10 | всегда | `%ld` | expire value (`0x1e8`) |
| 11 | v ≥ 3 | `%s` | expire event |
| 12 | всегда | `%s %lf %lf %lf %ld %s %s %ld %ld %ld` | блок из 10 полей (`0xc8`-буфер, `0x78/0x80/0x88`, `0x1c8`, два `%s`, `0x200/0x210/0x214`) |
| 13 | v ≥ 4 | `%lf` | falling fear (`0xc8`) |
| 14 | v ≥ 5 | `%s` | create event |
| 15 | v ≥ 6 | `%s` ×3 | morale failure / time out / damaged event |
| 16 | v ≥ 7 | `%ld %ld` | `0x1cc / 0x1d0` |
| 17 | v ≥ 10 | `%lf %lf` | `0xa8 / 0xb0` |
| 18 | v ≥ 11 | `%lf %lf` | `0xb8 / 0xc0` |
| 19 | v ≥ 12 | `%lf %lf` | `0x18 / 0x70` |
| 20 | v ≥ 13 | `%s %lf` | leash location (`0xd0`) |
| 21 | v ≥ 2 | `%ld`, затем `count × %s` | path points |
| 22 | всегда | `%ld`, затем `count × (%s %ld×6)` | weapon list (не более 8) |
| 23 | v ≥ 1 | `%ld`, затем `count × (%s %lf×6 %ld)` | children (не более 4) |

Проверка: файл `railrock.soe` (61 строка) содержит ровно **67 токенов**, и
парсер потребляет все до последнего (без остатка). Значения вроде «`none`»,
`NONE` и `0`-строки — легальные токены (`%s`), а не числа. Реализация:
`gm/soe.py` (`parse_text`/`parse_file`, `to_bytes`, `render_lines`);
CLI `gm.py soe <пути...> [-v] [--rebuild DIR]` (`to_bytes` побайтово точен,
`render_lines()` — канонические значения по строкам для новых файлов).

Роли многих полей неизвестны (движок копирует их в структуру почти без
интерпретации), поэтому в коде они названы по смещениям (`fXX`); названы
семантически те, что подписаны в сообщениях самого загрузчика (collision,
shields, events, weapons, children, path points).
