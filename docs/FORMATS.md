# Gunmetal — спецификация форматов данных

Всё ниже проверено на реальной установке `D:\games\Gunmetal 3dfx` (v1.36) и
реализовано в пакете `gm/`. Где формат разобран не до конца — это отмечено
явно («статус»), без догадок «под видом факта».

Термины: `u8/u16/u32` — little-endian целые, если не сказано иное.
Все размеры даны в байтах.

---

## 1. Архивы BIGFILE (`.idx` + `.dat`)

Пара файлов: индекс `*.IDX`/`*.idx` и данные `*.DAT`/`*.dat`.

```
IDX:
    char  magic[7];        // "BIGFILE"
    u8    0x1A;            // разделитель
    u32   count;
    count * {
        char name[8];      // NUL-дополненные, virtual-имена
        u32  offset;       // смещение блоба в .dat
    };

DAT:
    сырая конкатенация блобов: размер блоба = offset[i+1] - offset[i],
    последний — до конца файла.
```

`name` — не имя файла на диске, а «виртуальное» имя ресурса: движок обращается
к нему как `PICS\<name>.sbm`, `sounds\<name>.sou` и т.п.

Проверенные архивы установки:

| Индекс | Записей | Размер `.dat` | Полезная нагрузка |
|---|---:|---:|---|
| `PICS/SBM.IDX` | 1648 | 45 442 175 | `.sbm` (текстуры, с mip-цепочкой) |
| `sprites/SBM.IDX` | 179 | 1 083 044 | `.sbm` (спрайты, 1 уровень) |
| `sounds/SOU.IDX` | 999 | 26 738 998 | `.sou` (звуки/музыка) |
| `FRONTEND/BMP.IDX` | 143 | 2 845 582 | Windows BMP |

Между блобами нет паддинга (смещения строго непрерывны), а имена — NUL-дополненные
8-байтные поля. Поэтому архив **пересобирается побайтово точно**: пересборка всех
пяти архивов из их же блобов даёт идентичные `.idx` и `.dat` (проверено).

Реализация: `gm/bigfile.py` (`BigFile`, `Entry`, `build_index`, `pack`,
`replace_entry`).
CLI: `gm.py list <idx>` — таблица; `gm.py extract <idx> <out>` — сырые блобы;
`gm.py pack <out.idx> <dir> [--ext .EXT]` — собрать архив из каталога;
`gm.py set <idx> <name> <file> <out.idx>` — заменить/добавить одну запись.

## 2. Текстуры и спрайты `.sbm`

8-битные палитровые блобы; палитра в блобе **не хранится** (см. §6).

```
struct Sbm {
    u32 zero;               // в поставке всегда 0
    u8  log2_width;         // width  = 1 << log2_width
    u8  log2_height;        // height = 1 << log2_height
    u8  levels_minus_one;   // число уровней mip = levels_minus_one + 1
    u8  zero;
    u32 flags;              // в поставке 0 или 1
    u8  pixels[];           // mip-цепочка, уровень 0 первым, индексы палитры
};
```

Уровень `k` имеет размер `(w >> k) x (h >> k)`; цепочка идёт до уровня,
заданного `levels_minus_one`. Полный размер пиксельных данных:

```
sum( max(1, 1<<(log2w-k)) * max(1, 1<<(log2h-k))  for k in 0..levels_minus_one )
```

Это тождество выполняется **побайтово для всех 1648 записей `PICS` и 179
записей `sprites`** — так формат и был подтверждён.

**Писатель / repack.** `Sbm.to_bytes()` пересобирает блоб ровно как прочитан
(побайтово для всех 1827 блобов). `sbm.encode(w, h, pixels, levels, flags, mip)`
строит новый блоб из 8-битных индексов (стороны — степени двойки; `mip` =
`box`/`nearest` для нижних уровней). `flags` значим: у текстур в поставке
0/1/2/16, у спрайтов 256/257 — при пересборке спрайта значение нужно сохранять.

Реализация: `gm/sbm.py` (`parse`, `Sbm.to_png`, `Sbm.to_bytes`, `encode`,
`expected_size`).
CLI: `gm.py textures <game> <out>` и `gm.py sprites <game> <out>`
(у спрайтов по умолчанию индекс 0 делается прозрачным: `--transparent 0`);
обратный путь — `gm.py sbm <image.png|.bmp> <out.sbm> [--palette BMP]
[--game DIR] [--mips N] [--flags N] [--filter box|nearest]` (при совпадении
палитры индексы сохраняются точно, иначе — ближайший цвет). Новый блоб кладётся
в архив через `gm.py set`.

## 3. Модели `.sob`

Текст, но **переводы строк не значимы**: это плоский поток токенов,
разделённых пробелами (в ~половине файлов имя текстуры оказывается в конце
«строки плоскости» — построчный парсер на этом ломается).

```
<vertex_count> <face_count>

vertex_count * ( x y z )                    // float, мировые единицы

face_count * {
    8 токенов-имён                          // [0] — диффузная текстура,
                                            // [1..7] — флаги материала
                                            //   ("none", "translucent", "add")
    flags nverts i0 .. i(nverts-1)          // целые
    [ -1 ]                                  // необязательный одиночный -1
    15 чисел                                // origin(3) U(3) V(3) N(3) spare(3)
}
```

Целочисленная строка может сопровождаться одиночным `-1` в новых файлах;
локально решить, есть ли он, нельзя, поэтому парсер **откатывается назад**
(backtracking с мемоизацией по позиции токена — остаётся линейным).

Векторы `U/V/N` — единичные оси, умноженные на 65536 (16.16-проекция):
`UV = dot(p - origin, axis) / 65536` как первое приближение.

Проверено: **все 672 модели из `SOBS/` разбираются**, поток токенов
расходуется точно. Реализация: `gm/sob.py`; CLI `gm.py sob <src> <out>` пишет
OBJ + MTL.

**Рендер** — `gm/render.py` + CLI `gm.py view`: перспективная камера с
автоподгонкой по габаритам, z-буфер, триангуляция веером, планарные UV из
поля записи (`Sob.uv`), текстуры по имени из `PICS/SBM.IDX` (затем
`sprites/SBM.IDX`) — из 526 имён текстур моделей находится 448. По умолчанию
UV-размах грани растягивается на всю текстуру (`--uv fit`), ключ `--uv tile`
повторяет её на мировую единицу. Фоны — вертикальный градиент, свет —
одно направление + ambient; `--wire`, `--cull`, `--flat`, `--no-textures`,
`--angle front|back|left|right|top|iso`, `--ascii` (ASCII-превью для
терминала/тестов), `--sheet` (контактный лист iso/front/left/top в одном
PNG, `render.contact_sheet`). Тот же рендерер рисует и уровни `.sbw` (см. ниже).

`.soe` (шаблоны «thing») — тоже поток токенов, но форма иная и разобрана
частично: `parse_soe()` возвращает сырые токены.

## 4. Уровневые `.sbc`

Небольшие блоки маленьких 8-битных карт.

```
struct Sbc {
    char magic[4];          // "SBC0" (5 файлов) или "SBC1" (46 файлов)
    u32  count;

    count * {
        u32 desc;           // w_log = desc & 0xffff, h_log = desc >> 16
        u8  pixels[];       // (1<<w_log) * (1<<h_log) байт
    };
};
```

Записи хранятся вплотную; `8 + sum(4 + 2**w * 2**h)` равно размеру файла
**точно для всех 51 файла** (34 в корне игры + 17 в `SOBS/`). Лишних
«хвостовых» байтов нигде нет.

> Ранняя гипотеза о другой раскладке (заголовок `u32, u16, u16` + «сетка
> байтов, кратных 4») **опровергнута** и заменена раскладкой выше.

Что это за данные: **лайтмапы уровня**. Загрузчик уровня собирает путь
`«<уровень>.SBC»` рядом с `.sbw` и, если файла нет, печатает
`Warning, unable to load level lightmaps (SBC file missing).` (`0x442482`);
записи складываются в один глобальный массив (`[0x5a45cc]`, по 8 байт:
указатель на пиксели + `(w-1) | ((h-1) << 8)`, счётчик в `0x5a45c8`), который
контекст рендера отдаёт растеризатору (`0x4223b9`). Все 36 `.sbc` попарно
соответствуют 36 `.sbw` по имени (`level0.sbc` ↔ `level0.sbw`).

Загрузчик (`0x429a2a`) нормирует форматы: `SBC1` читается как есть, а в
`SBC0` каждый байт сдвигается влево на 2 (2-битные уровни) — на выходе
значения в шкале `0..127`, в которой движок и считает свет. В памяти строки
идут с шагом **256 байт** (на диске — вплотную, `w` байт на строку).

Как полигон ссылается на лайтмап: поле `+0x04` — **1-based** индекс внутри
`.sbc` уровня; при загрузке движок прибавляет базу уже загруженных лайтмапов
(`0x428064`), а если индекс выходит за число записей файла — печатает
`Warning: unable to load lightmap %ld of sob %s` и обнуляет поле.

Выборка (доказано по коду `0x43ca5a`…`0x43cc9c`):

```
u = (dot(u_axis, вершина − centre) * 64 + (int)uv_u_fp) / 2 ; texel = ftol(u) >> 10
v = (dot(v_axis, вершина − centre) * 64 + (int)uv_v_fp) / 2 ; texel = ftol(v) >> 10
свет = clamp(brightness + object[0x74] + level[0x16]
             + pixels[(v & (h−1)) * 256 + (u & (w−1))], −128, 127)
```

То есть лайтмап проецируется **теми же осями `u_axis`/`v_axis`**, что и
текстура, но со своим смещением `uv_u_fp`/`uv_v_fp` (+0x54/+0x58, знаковые,
16.16) и плотностью 32 мировые единицы на тексель (`×64/2/1024`).
Проверено на `level0`/`dm1`: **99.4%** из 10 070 вершинных выборок попадают
внутрь своей страницы (остальные — перехлёст на тексель, движок маскирует по
`w-1`/`h-1`). `corner_a`/`corner_b` (+0x38/+0x44) — не углы, а **min/max AABB**
вершин относительно центра (движок считает их при загрузке,
`0x43529f`/`0x4353d0`); для выборки лайтмапа они не нужны.

Прочие два слагаемых: `object[0x74]` — знаковый байт объекта, во **всех**
28 192 объектах 0 (загрузчик пишет 0, `0x42ae55`); байт `+0x16` принадлежит
**сектору** (см. таблицу структуры сектора в §10) — загрузчик тоже пишет 0,
а скрипт может задать его командой с таблицей `0x4b6784` (`0x4578f8`).
В просмотрщике оба заменены ключом `--ambient` (по умолчанию 0).

Реализация: `gm/sbc.py` (`parse`, `Record.to_png`, `Sbc.to_bytes`, `encode`).
CLI: `gm.py sbc <пути...> <out>` — на каждый файл каталог с PNG
`NNNN_<w>x<h>.png` и сводный `_sheet.png` (первые 256 записей сеткой);
`--rebuild DIR` — запись обратно (структура сохраняется по подкаталогам,
`to_bytes` побайтово точен для всех 51 файла). Просмотрщик: `gm.py view
<level.sbw>` рисует уровень с лайтмапами (`--no-lightmap`, `--ambient N`).

## 5. Звук `.sou`

### 5.1 Контейнер (разобран полностью, все 999 записей)

```
SOU0 / SOU1                          SOU2
------------------------------       ------------------------------
char magic[4]  "SOU0"/"SOU1"         char magic[4]  "SOU2"
u32  sample_rate                     u32  sample_rate
u32  flags      0 или 1              u32  meta1
u32  length     байт payload         u32  meta2
u8   payload[length]                 u32  units
                                     u8   payload[units*4]   // с offset 20
```

* Для `SOU0/SOU1`: payload = `data[16 : 16+length]`. `length` совпадает с
  остатком файла у моно-записей; у трёх стерео-записей `length == payload + 1`.
  Загрузчик требует `(flags & 0xff) <= 1`; `flags == 1` ⇒ стерео
  (6 записей: CUT-EMP, CUT-PAM, CUT-PREZ, INTRO, VRCHAMBR, VRCHAMHQ).
* Для `SOU2`: payload = `data[20:]`, и `units * 4` равно остатку размера файла
  (проверено на FINALE/OVERTURE/WINNER; **FINALE и WINNER побайтово совпадают**).

### 5.2 Кодеки

Диспетчеризация в загрузчике сэмплов `gundx.exe` (VMA `0x40af30`) по цифре
магии:

| Магия | Формат драйвера | Payload |
|---|---|---|
| `SOU0` | 0 | **сырой беззнаковый 8-битный PCM** |
| `SOU1` | 3/2/1 при `rate < 10000 / < 18000 / иначе` | сжатый поток 8-битных кодов, выход 16 бит |
| `SOU2` | 4 | сжатые музыкальные треки |

Из поставки: `SOU0` — 13 записей (лупы: DRONE, ECMLOOP, FFLOOP, THUMH/K/L/M,
F-DFIELD/F-DISL/F-MRLL/F-PCL, C-PC, MAGDEF), `SOU1` — 983, `SOU2` — 3.

**`SOU1`/`SOU2` — это кодек драйвера, а не PCM.** Звуковая система —
Miles Sound System (AIL): в `gundx.exe` есть секции `adpcmseg`, `mixasmda`,
`mixasmse`, `putseg`, `putsegda`, `tempscrs` и строки проб карт («SB 16 sound
card found», …), ключи `/sb`, `/sbpro`, `/sb16`, `/sb32`, `/sb64`. Эти секции —
runtime-буферы; таблицы шагов ADPCM грузились из **отсутствующих** AIL-segment
файлов, поэтому сжатый payload **из самой установки не декодируется**.

Доказательство, что payload сжат, а не PCM: запись `SILENCE` (SOU1, 8000 Гц,
400 байт) — точный 3-байтовый цикл `4b 0c 20` (дельта-кодек держит константу);
как сырой 8-битный PCM это был бы громкий гул. Гистограммы байтов SOU1/2 близки
к равномерным (MAD1/MAD0 ≈ 1.2), тогда как у SOU0 (THUMK, C-PC) — гладкие
(≈ 0.1/0.33).

Поэтому `gm/sou.py` намеренно **отказывается** писать WAV для `SOU1/2`
(`Sou.to_wav()` бросает исключение) — чтобы не выдать мусор за звук.
CLI: `gm.py sounds <game> <out>` пишет 13 WAV (`SOU0`) и 986 сырых дампов вида
`{NAME}.sou{1,2}.{rate}.{mono|stereo}.bin`.

**Статус: контейнер — да; кодек `SOU1`/`SOU2` — открыт** (нужен либо дизасм
драйвера, либо битые AIL-таблицы).

## 6. Палитра и `.bmp`

8-битная графика игры не несёт палитру в блобе. Вместо этого установка
содержит **общую VGA-палитру из 256 цветов**, повторённую (побайтово
идентично) почти во всех `.bmp` файлах. `gm/palette.py` достаёт её из любого
такого BMP:

* `load_from_bmp(path)` — прочитать палитру из файла;
* `installed(game_dir)` — взять из известных носителей
  (`FLAG/naUSA.BMP`, `FLAG/aanataka.bmp`, `PICS/oaktabl1.bmp`, `PICS/mine-1c.bmp`).

`.bmp` — обычные Windows BMP (8 бит, палитровые). `gm/bmp.py` читает их и
нормализует палитру в порядок `R,G,B,X` (в файле хранится `B,G,R,X`) — из-за
этого раньше всё декодированное искусство было синеватым, баг исправлен.

CLI: `gm.py frontend <game> <out>` выгружает `FRONTEND/BMP.DAT`.

### 6.1 Таблицы поиска `LOOK16.TAB` и `LOOK162.TAB`

Оба файла — ровно **262144 Б = 64³**: куб «6-6-6 RGB → байт», т.е.
`data[(r<<12)|(g<<6)|b]`, где `r,g,b ∈ 0..63`. Движок генерирует их при
отсутствии (`gundx.exe` `0x41e771` — таблица 1, `0x41e8ec` — таблица 2; вложенные
циклы по 0x40 значений, на каждый цвет пишется один байт) и иначе просто читает
с диска.

Значение куба — **индекс цвета палитры**: для цвета `(r,g,b)` это ближайший
цвет палитры, найденный взвешенной метрикой ядра `0x4228e0`
(`(sr+0x100)·dr² + 512·dg² + (0x17f−sr)·db²`, где `sr = r + palette[i].r`).
Палитры разные:

* **`LOOK16.TAB`** — палитра игры по умолчанию (рабочая копия `0x5309b8`,
  строится из мастер-палитры `0x83d320`; ремап слотов `0x5620c0`). В поставке:
  234 разных значения, диапазон 1..239 (слоты палитры).
* **`LOOK162.TAB`** — палитра, выбранная `NEONS.PIN` (рабочая копия `0x530cb8`,
  ремап `0x5641c0`). `NEONS.PIN` — текстовый список: число `count`, затем
  `count` индексов палитры. В поставке 20 индексов
  `{173,174,175,191,240..255}` — **ровно** множество значений `LOOK162.TAB`
  (проверено).

Сообщение движка «Generating 16-bit table N...» относится именно к этой
регенерации: при первом запуске таблицы считаются (с прогрессом `%03d`), потом
пишутся и на следующих запусках только читаются. Прикладной смысл — перевод
цвета в индекс 8-битного палитрового кадра. Проверено также, что `LOOK16.TAB`
корректен как разбиение Вороного: 230 из 234 меток односвязны (4 — с двумя
компонентами из-за усечения на границе куба).

Реализация: `gm/look.py` (`load`, `parse_neons`, `stats`, `apply8`, `to_png`);
CLI `gm.py look FILE [--png OUT] [--palette BMP] [--neons NEONS.PIN] [--scale N]`
(экспортирует куб как монтаж 8×8 из 64 срезов, 512×512).

## 7. PNG-вывод

Внешних зависимостей нет (`pip`/`PIL`/`numpy` недоступны), поэтому PNG
пишется и читается вручную поверх стандартного `zlib`: `gm/png.py` —
`from_indexed` (разворот в RGB), `indexed` (8-битный PLTE-индексный PNG,
round-trip без потерь), `gray`, `rgb`, `rgba` и читатель `decode` (8 бит,
без интерлейса, типы 0/2/3/4/6). Индексный вывод используется для `.sbm`, чтобы
правка текстуры не теряла индексы при дубликатах цвета в палитре.

## 8. Анимации `.soa`

Обычный DOS-текст (CRLF). Первая строка — 4 числа, далее имена кадров:

```
<mode> <period> <frames> <loop>
<имя кадра>
...
```

* `frames` — сколько имён читает движок; в нескольких файлах есть лишние
  хвостовые строки (парсер сохраняет все).
* `loop` = 1 (цикл) или 0 (один раз; у `dclock*`, `FILM`).
* `mode` = 0/1; `period` — шаг кадра (24…600).

Проверено: все 77 файлов `anims/` разбираются. Реализация: `gm/soa.py`
(`parse`, `to_bytes`, `from_names`), CLI `gm.py soa <файлы|каталоги>
[--rebuild DIR]`.

**Запись.** Формат строчный: достаточно сохранить точные строки. `Soa.to_bytes()`
собирает файл с CRLF **побайтово точно для всех 104 `.soa`** (включая
`spritani/`, `Sobanim/`); `render_lines()`/`from_names()` дают канонический текст
для новых файлов (без «хвостовых» пробелов и лишних пустых строк оригинала).

## 9. Музыка `.sog` и архив `MUSIC/SOU.DAT`

`.sog` — **это просто текстовый плейлист**: по одному имени сэмпла на строку.
Имена ссылаются не на `sounds/SOU.DAT`, а на **второй BIGFILE-архив**
`MUSIC/SOU.DAT` + `MUSIC/SOU.IDX` (3092 записи, **все `SOU2`**, ~75 МБ).

```
.sog  : line 1..N — имя сэмпла (совпадает с именем записи MUSIC/SOU.IDX)
```

Проверено: все 651 файл `.sog` разбираются; 25 песен ссылаются на 95 имён,
которых нет ни в `MUSIC/SOU.IDX`, ни в `sounds/SOU.IDX` (вырезанный контент —
движок бы выдал «Unable to load sample…»). Реализация: `gm/sog.py`
(`parse`, `to_bytes`, `from_names`),
CLI `gm.py sog <файл|каталог> [--music MUSIC/SOU.IDX] [--rebuild DIR]`
(`to_bytes` побайтово точен для всех 651 файла, включая верхнерегистровые
`.SOG`; `--rebuild` пишет по подкаталогам).

## 10. Мир `.sbw`

Полностью разобран побайтово: **все 36 файлов парсятся ровно до EOF**. Файл —
один последовательный поток, который читает загрузчик `gundx.exe` VMA `0x42aa63`
(таблицы), `0x422f03`/`0x422d55` (аллокаторы), цикл стадии 1 на `0x42ad65` и цикл
стадии 2 `0x425f4c` → `0x422b88`/`0x422a51`:

```
u32 count1;                                    // таблица текстур
count1 * {
    char name[];          // имя текстуры, ASCII с NUL
    u16  flag;            // в поставке 0/1; загрузчик кладёт байты в +6/+5
                          // записи 0x76ed40 (шаг 0x10), имя — в +7
    u32  value;           // «вес» текстуры **на уровне**: загрузчик (`0x42aba9`)
                          // кладёт его в массив счётчиков ссылок `0x5310c0[i]`,
                          // который код `0x424eab`/`0x424e50` инкрементирует/
                          // декрементирует при загрузке/выгрузке текстуры.
                          // Это НЕ индекс в `PICS/SBM.IDX`: одно и то же имя
                          // в разных уровнях несёт разные значения (1936 имён,
                          // 928 расходятся), и с размером текстуры значение не
                          // связано (у 64×64 встречаются 301/37/24/39)
};

u32 count2;                                    // таблица эффектов/анимаций
count2 * {
    char name[];          // имя эффекта/анимации
    u32  kind;            // класс анимации (0/1/101/102)
    u32  start;           // первый id сэмпла/кадра
    u32  n;
    u16  ids[n];          // id по порядку
};

u32 count3;                                    // секторы (по 0x18 Б в памяти)
count3 * {                                     // стадия 1: шапки объектов
    u32 objects;          // объектов в секторе
    u16 kind;             // «тип сектора» × 6: SET_SECTOR_TYPE (id 10) пишет
                          // тип×6 (сеттер 0x42d9d5), геттер 0x42d9a0 делит на 6.
                          // В поставке только {0,6,12,18,24}; рендер поле не
                          // читает (в коде — лишь +0x16 и +0x17)
    u8  sub;              // доп. флаг
    objects * {
        u32 flags;        // не «id», а битовое поле: во всех 36 уровнях всего
                          // 9 значений (0 у 26 664 объектов, 8, 32, 0x10000,
                          // 0x10010, 0x100000, …) — степени двойки и их суммы
        u8  header[96];   // 4 точки по 3 компоненты; каждая компонента
                          // записана как пара (u32 pad=0, f32) => origin +
                          // 3 масштабированных базисных вектора
                          // (во всех файлах базис = diag 1.875)
    }
}

count3 * objects * {                           // стадия 2: геометрия
    u16 n_verts; u16 n_polys;
    f32 verts[n_verts][3];    // локальные координаты
    f32 radius;               // 0x60 — радиус описанной сферы (= |bounds|)
    u8  f75; u8 f74;          // 0x75/0x74 — не используются (0; f75=1 у 7 объектов)
    u32 f7c; u32 f78;         // 0x7c/0x78 — не используются (0)
    f32 bounds[3];            // 0x84 — полуразмеры AABB (целые в данных)
    u8  reserved[24];         // 0x90 — 24 нулевых байта
    n_polys * { /* см. таблицу полей полигона ниже */ }
}
```

Стадия 1 даёт секторы и объекты с их трансформом, стадия 2 — вершины и
полигоны в том же порядке (сектор × объект). Каждая запись полигона — это
**0x80 байт в памяти** (`resolve_poly` @ `0x434463` возвращает
`object+0x6c + i*0x80`), а на диске поля идут в другом порядке и без указателя
на список индексов, поэтому парсер раскладывает их по смещениям движка.

Что уже точно понятно:

- `verts` + `idx` — это сетка; индексы всегда в диапазоне `0..n_verts-1`
  (проверено на всех 36 файлах). Полигоны в основном четырёхугольники
  (202 097 квадов, 13 628 треугольников, встречаются n-угольники до 12 вершин).
- Заголовок объекта (96 Б) = origin + 3 базисных вектора; каждая компонента
  записана 8 байтами `(u32 pad=0, f32)`. Во **всех** 28 192 объектах pad=0, а
  базис — строго диагональный `diag(1.875, 1.875, 1.875)`; origin лежит в
  пределах примерно ±8.
- Объект (стадия 2): `radius` = |`bounds`| (радиус описанной сферы, проверено:
  21 125 из 28 192 совпадают точно, остальные — из-за округления `bounds` до
  целых); `bounds` — полуразмеры AABB по вершинам (`bounds ≈ (max−min)/2`);
  `f74`/`f78`/`f7c` всегда 0, `reserved` (24 Б) всегда 0.

### 10.1 Поля полигона

Смещения — в 0x80-байтовой записи движка. «Точно» = подтверждено кодом
движка/командой языка; «вероятно» = устойчивая эмпирика.

| Смещ. | Тип | Поле | Смысл |
|------:|-----|------|-------|
| 0x00 | u16 | `texture` | индекс текстуры (знаковый): **>0** — 1-based запись таблицы текстур, **<0** — запись таблицы эффектов (шаг 0x5c), **0** — без текстуры. SET_POLY_TEXTURE (id 0x0f) |
| 0x02 | u16 | `material` | индекс материала 0..5 = none/reflective/translucent/varadd/add/shade; индексирует таблицу материала (ds:0x5670e0, шаг 0x40, имя на +0x34). Параметр `+0x2c` (заполняет загрузчик `0x4214d8`…`0x421549`): `0 / 64 / 64 / 100 / 127 / -128`; первый dword записи, бит 0 — «особый проход»: при нём движок отправляет полигон во второй (смешиваемый) проход (`0x437fba`, `0x439e75`, `0x43d568`) |
| 0x04 | u16 | `lightmap` | индекс лайтмапа (знаковый), 0 = нет; при загрузке пересчитывается через базу лайтмапов уровня; учитывается в массиве использования лайтмапов |
| 0x06 | u16 | `u_scale` | **производное**: `uv_u_fp >> 7` (текстовый загрузчик `0x425db4`); в поставке верно для 235 057 из 235 069 полигонов, т.е. авторским полем не является |
| 0x08 | 3×f32 | `centre` | центр полигона в локальных координатах (для осевых граней = центроид вершин) |
| 0x14 | 3×f32 | `normal` | нормаль грани, единичная (движок проверяет: `Invalid poly ...`) |
| 0x20 | 3×f32 | `u_axis` | ось U текстуры, единичная (`Invalid poly U vector`) |
| 0x2c | 3×f32 | `v_axis` | ось V текстуры, единичная (`Invalid poly V vector`) |
| 0x38 | 3×f32 | `corner_a` | **min** AABB вершин полигона относительно центра (движок пересчитывает при загрузке, `0x43529f`; инициализируется ±inf) |
| 0x44 | 3×f32 | `corner_b` | **max** AABB вершин |
| 0x50 | u16 | `uv_u` | текстурная координата; авто-UV прибавляет `dot(u_axis, v−centre)×256` (константа `0x4a2258` = 256.0), т.е. вчетверо быстрее, чем `0x54` |
| 0x52 | u16 | `uv_v` | то же по V |
| 0x54 | u32 | `uv_u_fp` | смещение U проекции (знаковое, читается как `int`): `texel = ftol((dot(u_axis, v−centre)×64 + 0x54)/2) >> 10` (константы `0x4a2298` = 64.0, `0x4a2280` = 2.0), см. §4 |
| 0x58 | u32 | `uv_v_fp` | то же по V |
| 0x5c | u16 | `scroll_u` | вес скролла текстуры по U: хелпер `0x434c80` читает его как **s16** и строит мировое смещение `t·(s16[0x5c]·u_axis + s16[0x60]·v_axis)/256.0` (`0x4a2258`); родственная команда — SET_POLY_SCROLL (id 0x11) |
| 0x5e | u16 | `anim0` | анимируемый s16: `0x4342f0` интерполирует 16-битные половины по отдельности между двумя полигонами-ключами |
| 0x60 | u16 | `scroll_v` | см. 0x5c |
| 0x62 | u16 | `anim1` | см. 0x5e |
| 0x64 | u16 | `v_scale` | **производное**: `uv_v_fp >> 7` (`0x425ddc`; верно для 235 059 из 235 069) |
| 0x66 | u16 | `anim2` | см. 0x5e |
| 0x68 | u32 | `reserved` | всегда 0 |
| 0x6c | u16[] | `indices` | индексы вершин объекта (`n_idx` штук) |
| 0x70 | u8 | `brightness` | яркость (SET_POLY_BRIGHTNESS, id 0x10) |
| 0x71 | u8 | `n_idx` | число индексов (3..12) |
| 0x72 | u16 | `handle` | слот-id; текстовый загрузчик отображает ввод 1→0x7ff8, 2→0x7ff9, иначе 0 |
| 0x74 | u16 | `f74` | вспомогательное времени выполнения: текстовый загрузчик обнуляет (`0x425df2`); в поставке ненулевое лишь у ~5 % полигонов |
| 0x76 | u16 | `f76` | то же (`0x425de6`) |
| 0x78 | u16 | `overlay` | индекс текстуры оверлея (та же кодировка, что и 0x00) |
| 0x7a | u16 | `f7a` | вспомогательное (0..2) |
| 0x7c | u32 | `flags` | битовое поле: **0x8000** = «UV/кадр полигона посчитаны» (есть у всех поставочных полигонов; при сброшенном бите `0x43e02d` пересчитывает UV из геометрии), **0x2** = «прозрачная» (текстура из sprites/прозрачная), **0x4** = переключается командой (`xor [poly+0x7c],4`, `0x46adbc`/`0x46aefa`) |

Назначение `centre`/`corner_a`/`corner_b` — кэш кадра отрисовки: `centre` —
центр полигона, `corner_a`/`corner_b` — min/max AABB вершин относительно
центра (нужны генератору лайтмапов, при загрузке пересчитываются, `0x43529f`).
Поля `0x5c/0x5e/0x60/0x62/0x66` движок интерполирует **по 16-битным половинам**
(`0x4342f0` — между двумя полигонами-ключами), а `0x434c80` берёт `s16[0x5c]` и
`s16[0x60]` как веса осей `u_axis`/`v_axis` — похоже, так строится мировое
смещение скролла текстуры (сама формула доказана, назначение — «значения»).

Эмпирическая (но движком **не используемая**) закономерность: пары
`(0x5c,0x5e)` и `(0x60,0x62)` в поставке — бит-в-бит корректные `f32` (все
470 138 значений конечны и не нули; 72 % из них лежат в пределах 5 % от
степени двойки, а самое частое — ровно `2^k·(1+1/128)`; связь с `u_scale`
лишь статистическая (медиана `u_scale·f` = 0.77) — похоже на артефакт
экспорта: float-значения попали в два s16-слота. Движок
читает эти слоты только как `s16`, поэтому опираться на float-чтение нельзя.

Авто-UV (`0x43e02d`, работает лишь при сброшенном бите `0x8000`): по последней
вершине полигона считается проекция, затем `0x50 += ftol(dot(u_axis, v−centre)×256)`,
`0x54 += ftol(dot(u_axis, v−centre)×64)`, та же пара для V (`0x52`/`0x58`), после чего
текстовый загрузчик выводит `0x06 = 0x54>>7` и `0x64 = 0x58>>7`.

Константы `±inf`-образных защёлок и множителей (секция `.rdata`): `0x4a2250` = 1.0,
`0x4a2254` = f32 1.875 (базис!), `0x4a2258` = 256.0, `0x4a225c` = f32 3.75,
`0x4a2260` = 4.0, `0x4a2268` = 1e38 (плюс float-сентинелы ±107761.65 =
`0x47d2ced3`/`0xc7d2ced3` в `0x43e02d`), `0x4a2280` = 2.0, `0x4a2298` = 64.0.

Реализация: `gm/sbw.py` (полный парсер + экспорт в OBJ + `Sbw.to_bytes`),
CLI `gm.py sbw <файлы> [-v] [--obj DIR] [--transform] [--rebuild DIR]`.

**Запись.** `Sbw.to_bytes()` собирает файл обратно из распарсенных таблиц,
секторов, вершин, 50-байтного хвоста объекта и 112-байтного хвоста полигона —
**побайтово точно для всех 36 файлов**. Это основа для правки геометрии: изменить
вершины/поля и записать (`--rebuild DIR`).

**Рендер уровня.** Тот же `gm/render.py` рисует и мир: `render.level_meshes(w)`
оборачивает каждый объект (вершины + полигоны + имя текстуры из таблицы
`w.tex`) в меш с планарным UV `uv = (dot(p-centre, u_axis), dot(p-centre,
v_axis))` (оси `u_axis`/`v_axis` — уже единичные, в отличие от `.sob`), после
чего работает обычный `render.render(...)`. Пример:

```sh
python3 gm.py view "…/Gunmetal 3dfx/level0.sbw" --out out/view --size 640 --el 40 --ascii
```

`level0.sbw`: 58 секторов, 192 объекта, 1449 полигонов, 57 текстур; рендер
480² занимает ~0.5 с. Заметка: `--transform` (трансформ объекта из заголовка)
не нужен — вершины объектов уже в крупных мировых координатах (габарит
`level0` — ±576 по X/Y и ±680 по Z), а origin в заголовке — микро-смещение.

**Вид «изнутри».** Автоподгонка ставит камеру снаружи; для интерьера задаются
позиция и цель (`--pos x,y,z --look x,y,z`), а лишнюю дальнюю геометрию
отсекает `--clip DIST` (полигон отбрасывается, если его центр дальше DIST от
глаза): `render(..., pos=..., look=..., clip=...)`. Дополнительно:

- **материалы** (`--no-materials` выключает) — второй проход, как в движке:
  непрозрачные пишут z-буфер, смешиваемые рисуются после них «от дальних к
  ближним», z только проверяют. Вес берётся из `material+0x2c`
  (`translucent` — смешение 0.5, `add`/`varadd` — аддитивно, `shade` —
  вычитание); точная математика смешения в растеризаторе движка не
  прослежена, поэтому это документированное приближение. В моделях та же
  логика по меткам `SobFace.material_flags` (`add`, `translucent`, `varadd`);
  напр. `rays10.sob` — все 78 граней аддитивные.
- **яркость полигона** `+0x70` (0..127) — аддитивная добавка к освещению
  (коэффициент 0.5; тоже приближение).
- **лайтмапы `.sbc`** (`--no-lightmap` выключает) — полигон ссылается на
  запись sibling-файла `<уровень>.sbc` полем `+0x04` (1-based); проекция и
  формула света — в §4. Свет (`brightness + выборка лайтмапа`, 0..127)
  заменяет нормальное затенение и переводится в множитель `свет/127`
  (линейно; таблица «свет → палитра» движка не прослежена, поэтому это
  приближение, как и для материалов). Полигоны **без** лайтмапа (в `level0`
  их 860 из 1449) остаются на нормальном затенении. Ключ `--ambient N`
  добавляет постоянный уровень света (заменяет байт сектора `+0x16`, см. ниже).
- **отсечка по пирамиде видимости** (`--no-sectors` выключает) — на каждый
  объект считается AABB, переводится в пространство вида и проверяется на
  пересечение с пирамидой (`Camera.aabb_visible`). Отсечка **консервативна**:
  картинка совпадает бит-в-бит, но граней считается меньше (пример: вид из
  dm1 — 238 граней → 25 при полном совпадении пикселей). Движок делает то же
  самое — пропускает объекты по флагам `obj+0x70 & 0x10010` и радиусу
  `obj+0x60` (`0x437d86`…`0x437db0`).
  Ключ `--sector N` оставляет только один сектор — удобно рассматривать
  группу геометрии в изоляции. Замечание: секторы `.sbw` — это **группы
  объектов**, а не изолированные комнаты: их AABB сильно перекрываются и
  часто центрированы в начале координат (уровни скомпонованы вокруг центра,
  `level0` — арена с башней), а `kind` встречается только как 0 и кратные 6.
- **отсечка полигона по ближней плоскости** — полигон не отбрасывается, если
  какая-то вершина за ближней плоскостью, а обрезается по `z >= near`
  (Сазерленд—Ходжман в пространстве вида) с интерполяцией UV и координат
  лайтмапа; размах текстурной UV-подгонки (`--uv fit`) при этом считается до
  отсечки, чтобы текстура не «прыгала». Это убирает дырки, когда камера
  стоит вплотную к стене.

Структура сектора в памяти движка (0x18 Б, массив `[0x5670d8]`, счётчик
`[0x5670dc]`, загрузчик `0x42ad34`…`0x42ae15`):

| Смещ. | Поле |
|------:|------|
| 0x00 | число объектов (u32) |
| 0x04 | указатель на массив указателей объектов |
| 0x14 | `kind` сектора (u16; в данных 0 и кратные 6) |
| 0x16 | **байт света сектора** (знаковый; загрузчик пишет 0, скрипт может задать — команда с таблицей `0x4b6784`, обработчик `0x4578f8`) |
| 0x17 | `sub` (u8) |

```sh
# группа геометрии в изоляции (уровень целиком — арена с башней вокруг центра)
python3 gm.py view "…/Gunmetal 3dfx/level0.sbw" --out out/view --size 640 --sector 5 --el 40
# камера внутри dm1 (там светлый проём): --pos/--look/--clip/--cull
python3 gm.py view "…/Gunmetal 3dfx/dm1.sbw" --out out/view --size 640 \
    --pos 0,0,20 --look 60,60,20 --clip 200 --cull
```


## 11. Видео `.sbv`

**Контейнер.** Заголовок и таблица кадров разобраны по дизассемблеру загрузчика
`gundx.exe` VMA `0x49e1e8` (ширина > 0x140=320 отклоняется):

```
char magic[4];      // "SBV0"
u32  width;         // <= 320
u32  height;
u32  frame_count;
frame_count * { u32 timestamp_ms; u32 end_offset };  // end_offset от data_start
```

`data_start = 16 + 8*frame_count`. Кадр *i* занимает
`[data_start+prev, data_start+end[i])`, где `prev = end[i-1]` (0 для i=0);
последний `end` ровно на EOF (проверено на `Intro` 320×160×500,
`orient` 4523 кадра, `winner` 1820 кадров).

**Кодек — разобран полностью.** Это собственный (не Bink/Smacker/Indeo)
чисто внутрикадровый **пирамидальный** кодек: кадр = 3 плоскости (яркость
`W×H` и две цветности `W/2×H/2`, сэмплы — знаковые 16-битные), каждая
реконструируется «снизу вверх». Декодер транслитерирован 1:1 в `gm/sbv.py`
и сверен с эмуляцией `gundx.exe` **побайтово** на 27 кадрах всех трёх файлов
(включая первый и последний кадр каждого).

Плоскость (дизасм `0x49ee8c`):

1. из потока читаются знаковые `i32 min` и `i32 max`, затем по одному байту на
   сэмпл самой грубой сетки (яркость `(W/4)×(H/4)`, цветность `(W/8)×(H/8)`).
   Значение сэмпла `(int)(byte*(max-min)/256.0 + min)` — деление на вещественную
   константу **256.0** (`0x4a2ac0`), усечение к нулю;
2. остальные сэмплы дочитывает **битовый энтропийный поток**: он заполняет сетку
   блоками `factor×factor` (`0x49f4db`, `factor` 4 → 8), а оставшиеся «щели»
   закрывают инверсный лифтинг `0xa1d940` + фиксация краёв `0x49f1e3` и
   раздвижка `0x49f43a`.
   Последовательность вызовов для яркости:
   `0x49f4db(W/4,H/4,4)`, `0x49f1e3(W/4,H/4)`, `0x49f43a(W/4,H/4)`,
   `0x49f4db(W/2,H/2,8)`, `0x49f1e3(W/2,H/2)`, `0x49f43a(W/2,H/2)`,
   `0x49f4db(W,H,8)`, `0x49f1e3(W,H)`;
   для цветности — `0x49f4db(W/8,H/8,4)`, `0x49f1e3/0x49f43a(W/8,H/8)`,
   `0x49f4db(W/4,H/4,8)`, далее как у яркости без последних трёх вызовов.

Энтропийный декодер (`0xa1d000`): биты читаются **начиная со старшего**.
Состояние (`0x6c08e0`): указатель источника, счётчик бит, аккумулятор и три
предиктора (класс, шаг, знак). На блок:

- унарный код класса + бит знака, DPCM относительно предиктора. Класс `0` —
  весь блок нулей (биты больше не читаются); класс `>= 0x11` — конец плоскости;
- унарный код шага (тоже DPCM) + бит знака блока: `step = 1 << (e & 31)`;
- далее один из 17 статических обработчиков (таблица в `.data` по `0xa1c400`).
  **В реальных файлах встречаются только классы 0, 1 и 3**: полный прогон всех
  6843 кадров трёх файлов (12.3 млн блоков) даёт гистограмму
  `{0: 6526044, 1: 3001203, 3: 2790153}`, счётчик `FAMILY_BLOCKS` = 0;
- **класс 1**: если курсор выровнен на 16 байт и следующий бит `0` — четыре нуля и
  `cursor += 16`; иначе бит «нулевой?», и при `1` бит знака даёт `±step`;
- **класс 3**: так же, но значение `(1 + число подряд идущих единиц) * step`,
  причём бит знака читается **до** серии;
- классы 2 и 4..16 («семейные», `0xa1d170 + 0x80k`) читают N «сырых» бит; в
  реальных данных не встречаются, а сами обработчики внутренне
  несогласованны (читают биты из аккумулятора, не сдвигая его), поэтому в
  `gm/sbv.py` они реализованы «по мере разумения» и считается счётчик
  `FAMILY_BLOCKS`.

Конверсия YUV→RGB (`0x49e33b`), сэмплы знаковые 16-битные, `C0`/`C1` берутся из
цветностных плоскостей в позиции `(x>>1, y>>1)`:

```
r = clamp((Y + C0      + 8) >> 4)   // арифметические сдвиги, clamp 0..255
g = clamp((Y - C0 - C1 + 8) >> 4)
b = clamp((Y + C1      + 8) >> 4)
```

Движок затем прогоняет эти байты через три таблицы по 256 dword
(`0x4a6a40`/`0x4a6e40`/`0x4a7240`) с фиксированной точкой и кладёт результат в
32-битную поверхность DirectDraw; таблицы, судя по всему, гамма-рампа режима
вывода, и в toolkit не воспроизводятся — отдаётся естественный 8-битный RGB.

Модуль `gm/sbv.py` (контейнер + полный декодер + **писатель контейнера**),
CLI `gm.py sbv <файл> [out] [--png DIR] [--frames SPEC] [--scale N] [--no-raw]
[--rebuild DIR]`;
`--frames` принимает `0`, `1,5,9-12` или `all`.

**Запись.** Блок кадра внутрикадровый и не требует контекста, поэтому таблицу
кадров можно пересобрать из размеров блоков: `gm/sbv.py:build` пишет
`magic + width/height/count + {timestamp_ms; end_offset} + блоки`, а
`Sbv.to_bytes(blob)` — обратная операция к `parse`. Все три поставочных клипа
(`Intro`, `orient`, `winner`, 53.2 МБ) собираются **побайтово точно**
(`--rebuild DIR`, проверка `sbv / rebuild round-trip`). Кадры можно также
разложить на `frames.txt` (первая строка — `# sbv width=W height=H frames=N`)
и `NNNNN.sbvf`, а затем собрать обратно: если `FILE` — каталог, `OUT` задаёт
целевой клип (`sbv / raw blocks -> clip`). Это *контейнерный* писатель — он
переставляет/перетаймирует существующие блоки, но **не сжимает пиксели**:
референсного энкодера в `gundx.exe` нет, а выбор класса/экспоненты в битовом
потоке из декодированных плоскостей однозначно не восстанавливается.


## 12. Мир/уровни `.sbt`

Файл мира — **скомпилированная «World Things file»**. В движке есть два
загрузчика: текстовый (`sbt_load`, `0x454b8d`; писатель — `0x454d20`, режим
`"wt"`) и бинарный, читающий поставленные `*.sbt` («BINARY SAVE»). Бинарный файл
— это тот же текстовый, только скомпилированный, и 1-байтовый *тип* записи —
это числовой id текстового ключевого слова (текстовый загрузчик буквально
сравнивает строки `POLY_HANDLE`/`OBJECT_HANDLE`/`SECTOR_HANDLE`/`SCRIPT`/
`END_OF_FILE` и читает по одной строке чисел — см. строки форматов около
`0x4b9600`). Все 36 поставленных `*.sbt` (`level*`, `dm*`, `secrt*`, `temple`)
разбираются ровно до EOF.

Заголовок (84 байта):

    char magic[80];   // b"BINARY SAVE\0" + нули
    u32  version;     // должен быть 0

Далее — записи. Каждая начинается с 1 байта *типа*; полезная нагрузка следует
сразу за ним и полностью вычитывается обработчиком этого типа. Тип `255`
(`END_OF_FILE`) — конец потока, без нагрузки (последний байт файла). Типы 10 и
13 диспетчеризуются в заглушку, возвращающую -1 (не поддерживаются).

| # | Имя (текстовое) | Полезная нагрузка |
|---|---|---|
| 1 | `SWITCH` | `u32 n <= 0x200`; `n * 32` байт |
| 2 | `DOOR` | `u32 n <= 100`; `n * 184` байт |
| 3 | `THING` | `u8 exists`; если ≠0 — `0x528` байт |
| 4 | `THING_TYPES` | `u32 n <= 0x80`; `n` типов по `936`: `char name[16]` + `double params[49]` + `528` байт целочисленных полей |
| 5 | `NAMED_ITEMS` | `u32 n <= 0x31`; `n` по `52`: `char name[16]` + 9 `u32` (источник — текстовый `item\<name>.soi`) |
| 6 | `SPRITES` | `u32 n <= 0x1f3`; `n * 44` байт |
| 7 | `SOUND_SOURCES` | `u32 n <= 0x7f`; `5*n*4 + n*8` байт |
| 8 | `SECTOR_STUFF` | `0x5800` байт |
| 9 | `PLAYER_STATUS` | `u8 exists`; если ≠0 — `0x3510` байт |
| 11 | `SCRIPT` | `u32 c <= 0xc8` (`c*40`) + `u32 n <= 0x400` (`n*4` ×3) + `u32 m <= 0x30000` (`m` байт) + `u8 flag` (если ≠0 — `9*0x400` байт) |
| 12 | `SOUND_SAMPLE_TABLE` | `300 * u32` + `300` имён по 9 байт (`0x4b0 + 0xa8c`) |
| 15 | `POLY_HANDLE` | `u32 n < 0x1f4`; четыре **параллельных** колонки `u32[n]`: `tag, sector, object, poly` |
| 16 | `OBJECT_HANDLE` | `u32 n < 0x12c`; три колонки: `tag, sector, object` |
| 17 | `SECTOR_HANDLE` | `u32 n < 0x100`; две колонки: `tag, sector` |
| 18 | `LIFT` | `u32 n <= 0x1e` (`n*168`) + `u32 k <= 0xc8` (`k*12`) |
| 19 | `ITEM` | `0x7080` байт |
| 20 | `SOB_TABLE` | `u32 n <= 0xc8`; `n` по `{char name[12]; u32 amount; u32 ptr}` |
| 255 | `END_OF_FILE` | — |

Все поставленные уровни имеют одну и ту же последовательность записей:
`12, 20, [15, 16,] 17, 5, 4, 11, 255`.

### 12.1 Таблицы handle (15/16/17) — координаты полигонов

Записи хранятся **по колонкам**, а не как массив структур: сначала `n` значений
первой колонки, потом `n` значений второй и т. д. Загрузчики читают каждую
колонку в свой глобальный массив (полигоны: `0x5b21f8`, `0x618b88`, `0x5e5680`,
`0x6183b8`), поэтому побайтная раскладка не совпадает с наивным `{u32 ×4}`.

Колонки:

    POLY_HANDLE    tag, sector, object, poly
    OBJECT_HANDLE  tag, sector, object
    SECTOR_HANDLE  tag, sector

`(sector, object, poly)` — это **канонический адрес полигона** в движке: его
принимает `resolve_poly` (`0x434463`) и его же печатает отладочный оверлей
редактора как `SECTOR:%d OBJECT:%d POLY:%d` (глобалы `0x62cae0/e4/e8`).
Проверено: **все 4277 poly-handle, 207 object-handle и 900 sector-handle** из 36
уровней указывают на существующие полигоны/объекты/секторы соответствующего
`.sbw` (`gm.py sbt --resolve`).

Ведущий `tag` — непрозрачный id, присвоенный редактором: по нему адресуют
сущность команды скрипта `SET_HANDLEPOLY_*`/`SET_HANDLESECTOR_*`, тогда как
семейство `SET_POLY_*` адресует полигон прямо тройкой `(sector, object, poly)`
(сигнатуры `LLLL` и `LLLLL` в таблице команд, напр. `SET_HANDLEPOLY_TEXTURE`).
`tag` не уникален и не является функцией данных полигона между уровнями —
поэтому хранится как есть.

### 12.2 Прочие записи

* **`THING_TYPES` (4)** — определения «things» (напр. `bgchunk1`, `CRATE`); 936
  байт = `name[16]` + 49 `double` (значения вида `0.01`, `0.1`, `6000.0`) + 528
  байт целочисленных полей (консольный обработчик «add thing type», `0x47cb6c`,
  читает `u32` по `+0x198/+0x19c/+0x1a8/+0x1ac`). В движке тип загружается из
  *текстового* файла `thing\<name>.soe` (строка `0x4bbb90`, `fopen(...,"rt")`) и
  компилируется в этот бинарный блок — связка с `.soe` (см. §13).
* **`SOUND_SAMPLE_TABLE` (12)** — 300 счётчиков ссылок + 300 имён по 9 байт. Все
  непустые имена (5800 ссылок по всем уровням) находятся в `sounds/SOU.IDX`.
* **`SOB_TABLE` (20)** — `name[12]` → `SOBS/<name>.sob` **или** `Sobanim/<name>.soo`
  (загрузчик логирует «Unable to load SOB or SOO %s»), второе `u32` (`amount`,
  загрузчиком не читается — вероятно счётчик из редактора), и третье `u32` —
  устаревший адрес кучи, который загрузчик перезаписывает указателем на
  разобранную модель (`0x47c845`, шаг записи `0x14`). У четырёх уровней
  встречается имя-заглушка `default`, файла для которого нет.
* **`NAMED_ITEMS` (5)** — `char name[16]` + 9 `u32` (52 байта). Загрузчик
  `0x4689f0` читает запись из текстового `item\<name>.soi` форматом
  `%ld %ld %s %ld %s %ld %s %ld %ld` (три `%s` резолвятся функцией `0x45fb90`)
  и пишет числа по `+0x10..+0x30`; отсюда и граница имени — 16 байт (strncpy
  в `0x468a53` копирует 15 байт). **`SCRIPT` (11)** — скомпилированный
  скрипт-блок; полностью разобран, см. §12.3.

Реализация: `gm/sbt.py`, `gm/sbtvm.py`, CLI
`gm.py sbt <пути...> [-v] [--resolve] [--json DIR] [--rebuild DIR]`
`[--script] [--script-out DIR]` (флаг `--resolve` сверяет таблицы handle с
соседним `.sbw`; `--script` декомпилирует скриптовый блок, см. §12.3).

**Запись.** `Sbt.to_bytes()` собирает файл из 84-байтной шапки и сырых payload'ов
записей — **побайтово точно для всех 36 файлов** (`--rebuild DIR`). Для
полностью разобранных записей есть и структурный кодировщик
`encode_payload(type, payload)`: таблицы handle (15/16/17), `NAMED_ITEMS` (5),
`THING_TYPES` (4), `SOB_TABLE` (20) пересобираются из полей точно (205/205 записей
в поставке); у имён сохраняется полный слот (`name_raw` — в `THING_TYPES` после
NUL встречаются «хвостовые» байты). Правка записи — через `sbt.set_payload`.

## 12.3 Скриптовая ВМ `SCRIPT` (11)

Запись `SCRIPT` — это `count*40` «things» + три параллельные колонки handle
(`n*4` каждая) + `m`-байтный **блок кода** + `flag` (+`9*0x400` таблиц).
Загрузчик записи — `0x462a80`: он читает именно в таком порядке, что и даёт
раскладку выше (прежнее `n*12` — те же байты, три колонки подряд).

Блок кода — поток **инструкций** `[u8 опкод][операнды…]`, где опкод = id
команды; `0xFF` — конец под-скрипта. Размер операндов задаёт *сигнатура*
команды (движковая функция `0x457170`, таблица букв `0x457204`):

| буквы | размер |
|---|---|
| `A` `B` `D` | 8 байт (`double`) |
| `Y` | 1 байт |
| `S` | строка с NUL |
| остальные (`E G I L M N O P R T V Z`) | 4 байта |

В exe две таблицы команд, обе восстановлены и вшиты в `gm/sbtvm.py`:

* **`COMMANDS`** (`0x4b53e8`, 192 шт.) — именованные команды редактора
  (`ADD_DOOR`, `SET_POLY_TEXTURE`, `LOAD_MUSIC`…). Диспетчер — `0x45c500`
  по `id-1`; все 202 id имеют уникальный обработчик.
* **`CONDITIONS`** (`0x4b62ec`, 59 шт.) — команды *второй ВМ* условий и
  выражений (`ADD_THING`, `FIRE_SOURCEPLAYER_LASER`,
  `SOURCEPLAYER_AMMO_AT_LEAST`, `RANDOM`…), обработчик `0x45f490`
  (диспетч `0x45f8e0`).

Несколько id **не имеют имени** в таблице `COMMANDS`, потому что это
*структурные* операторы. Их имена и раскладку дал **текстовый загрузчик
`0x460eca`**: он сравнивает текущий токен с пулированными строками
(`DEFINE_WEAPONS`, `DEFINE_AMMO`, `DEFINE_EQUIPMENT`, `DEFINE_PLAYER_TYPES`,
`DEFINE_LEVEL_OBJECTIVES`, `ADD_LIFT`, `SOURCEPLAYER_PATH`, `IF`, `ELSE`,
`END`) и компилирует их, эмитя байт опкода, затем счётчик, затем операнды
записи тем же обходчиком `0x461bc0`:

| id | имя | раскладка (сигнатура) | метка счётчика |
|---|---|---|---|
| 103 | `DEFINE_LEVEL_OBJECTIVES` | `u32 n (≤30)` + `n` строк (`S`) | `Objectives count` |
| 158 | `SOURCEPLAYER_PATH` | `u32 n (≤32)` + `n*{4}` (`E`) | `Path points` |
| 170 | `DEFINE_WEAPONS` | `u32 n (≤31)` + `n × (3×S + LLLLEEEEELLLLDBBDL)` = 0x54 | `Weapon count` |
| 171 | `DEFINE_AMMO` | `u32 n (≤31)` + `n × (1×S + LEOLLLLLLL)` = 0x28 | `Ammo count` |
| 172 | `DEFINE_PLAYER_TYPES` | `u32 n` + `n × (3×S + LDLLDODDDDLNVNVEED…EE)` = 0x17c | `Number of player types` |
| 175 | `DEFINE_EQUIPMENT` | `u32 n (≤31)` + `n × (1×S + LEEEEEELLLLL)` = 0x30 | `Equipment count` |
| 188 | `ADD_LIFT` | `0x94` байт + `u32 n (≤31)` + `n*0xc` | `Lift stops` |
| 199 | `IF` | `u8 cond-id` + операнды `CONDITIONS[cond]` + `u32 size` + тело(`size`) | — |
| 200 | `ELSE` | `u32 rel` — относительный прыжок *мимо* else-ветки | — |
| 201 (`0xC9`) | `EVAL` | `u8 cond-id` + операнды `CONDITIONS[cond]` | — |
| `0xFF` | `END` | конец под-скрипта | — |

Размеры записей (0x54/0x28/0x17c/0x30/0x94/0xc/4) **побайтово совпадают**
с пулированными сигнатурами (`0x4b8fa8`, `0x4b900c`, `0x4b9024`, `0x4b8fe8`,
`0x4b8f7c`, `0x4b8f78`, `0x4b7ba4`) и проверяются в генераторе.

`ELSE` компилируется как безусловный относительный переход: компилятор
патчит `size` у `IF` так, чтобы при ложном условии прыгнуть на начало
else-ветки, а сама ветка завершается `200` (прыжок за конец ветки). `END` на
нулевой глубине вложенности эмитит `0xFF` (конец под-скрипта). Декодер
разворачивает `IF`/`ELSE` рекурсивно (else-ветка читается линейно до цели
перехода).

**семантика полей таблиц.** Имена таблиц — из ошибок-строк exe
(`Maximum number of ammo/weapon/equipment types exceeded`). Потребители:

| таблица | счётчик (глобал) | массив в памяти | запись |
|---|---|---|---|
| `DEFINE_AMMO` (171) | `0x818958` (≤31) | `0x818960`, шаг `0x38` | 56 байт: имя `char[16]` в `+0x28`, 10 полей |
| `DEFINE_WEAPONS` (170) | `0x819028` (≤31) | `0x80fa00`, шаг `0x2a8` | **0x2a8 = 680** байт: имя `char[16]` в `+0x298` |
| `DEFINE_EQUIPMENT` (175) | `0x815420` (≤31) | `0x814c60`, шаг `0x40` | 64 байта: имя `char[16]` в `+0x2c` |
| `DEFINE_PLAYER_TYPES` (172) | `0x7941bc` (≤32) | `0x7995e0`, шаг `0x1cc` | 460 байт (см. ниже) |

### поля `DEFINE_AMMO` (потребитель `0x450b10`, вызывающий `0x45cc40`)

Вызывающий пушит запись как `arg1..arg10` (порядок: `[eax+0x24]`…`[eax+0x00]`),
`arg0` = строка-имя (копируется `strncpy` 15 байт). Потребитель раскладывает
аргументы по памяти **перестановкой** (поле `+0x20` клампится снизу в `1`):

| операнд | offset | смысл | статус |
|---|---|---|---|
| `L0` | `+0x04` | максимальный запас: при покупке запас клампится к нему (`0x47b642`) | код |
| `E1` | `+0x18` | id объекта подбора (аргумент спавнера `0x4686a0`, `0x450af4`) | код |
| `O2` | `+0x14` | id объекта подбора (тот же спавн) | код |
| `L3` | `+0x1c` | id объекта подбора | код |
| `L4` | `+0x08` | размер партии: продажа `запас -= +0x08` (`0x47b4ee`), покупка `запас += +0x08` (`0x47b613`) | код |
| `L5` | `+0x0c` | цена: `наличные -= +0x0c` при покупке (`0x47b5f2`), `+= +0x0c` при продаже (`0x47b512`) | код |
| `L6` | `+0x10` | вес единицы боеприпаса: `вес += запас[i] × +0x10` (`0x4525c1`) | код |
| `L7` | `+0x00` | флаги (байт): `0x01` — можно купить (`0x47b5bd`), `0x02` — можно продать (`0x47b4db`, «LEFT TO SELL» `0x49539b`), `0x08` — скрыть из списка покупки (`0x47b425`, `0x49569e`) | код |
| `L8` | `+0x20` | патронов в «единице» (обойме): делитель для колонки units (`0x4929d5`, `0x4957b2`) | код |
| `L9` | `+0x24` | вес случайного выбора типа при подборе: `0x4509b4` суммирует по доступным типам, `random % сумма` (`0x450a54`) | код |

`L9` в `dm1.sbt` = 0..6, `L8` = 1 (кроме `POWER CELLS` = 100), `L0` =
5000/180/100/…/60000, `L5` = 500/4000/…/100000. `E1` — сквозные id
(`4000100+i`), `O2` = индекс самого типа (`0..14`), `L3` = 64. Флаги
непокупаемых типов (`TAC NUKE`, `FOAMED ALUMINUM`, `AUTO SENTRY`, `DECOY`)
= `0x88` (`0x08` скрыть + `0x80`, смысл старшего бита не установлен).

### поля `DEFINE_EQUIPMENT` (потребитель `0x450e60`, вызывающий `0x45cbe0`)

Вызывающий пушит 12 dword'ов как `arg1..arg12` (порядок: `[eax+0x2c]`…`[eax+0x00]`),
`arg0` = строка-имя. Потребитель кладёт их **по порядку** `+0x00…+0x28` и
`+0x3c` (имя — в `+0x2c`, `char[16]`, обнуляется `+0x3b`):

| операнд | offset | смысл | статус |
|---|---|---|---|
| `L0` | `+0x00` | флаги (байт): `0x01` купить (`0x47b8ba`), `0x02` продать (`0x47b7d0`), `0x04` не участвует в цикле выбора оборудования (`0x4460f5`), `0x08` скрыть из списка покупки (`0x47b6fc`, `0x47b798`) | код |
| `E1` | `+0x04` | id объекта: аргумент спавнера `0x4795b0` при покупке (`0x47b940`) | код |
| `E2` | `+0x08` | id объекта: аргумент спавнера `0x4795b0` при активации (`0x446099`) | код |
| `E3` | `+0x0c` | читается кодом эффектов оборудования (`0x446228`, `0x446574`) | значения |
| `E4` | `+0x10` | читается там же (`0x44621d`, `0x446521`) | значения |
| `E5` | `+0x14` | — | — |
| `E6` | `+0x18` | — | — |
| `L7` | `+0x1c` | — | — |
| `L8` | `+0x20` | индекс типа боеприпаса (обязан быть `< 0x818958`, иначе ошибка `0x4ac6a4`; `-1` = без боеприпаса) | код |
| `L9` | `+0x24` | цена (`наличные -= +0x24`, `0x47b8cd`; `+= +0x24`, `0x47b879`) | код |
| `L10` | `+0x28` | вес: суммируется в общий вес (`0x45258c`, база `0x814c88` = `+0x28`) | код |
| `L11` | `+0x3c` | — | — |

Проверка `L8` по данным `dm1.sbt`: `FORCE SHIELD` → 10 (`POWER CELLS`),
`MINE LAYER` → 11 (`MINES`), `COMBAT BLOCK` → 12, `AUTO SENTRY` → 13,
`DECOY` → 14, пассивные (`RADAR`, `TARGETING`, `WARP DEVICE`…) → `-1`.
Слова `E*` в файле — уже разрешённые хендлы объектов (в `dm1.sbt` отрицательные
вида `0xfffff8xx`).

### общая функция характеристик `0x4524d0`

Считает **общий вес** (`[player+0x81c374]`, печатается как `WEIGHT: %ld`) и
**максимальную скорость** (`[player+0x81bd88]`, `TOP SPEED: %ld`):

```
вес = Σ (стат[i]/100 × [0x818950])            ; i = 0..3, [player+0x81c2a0+4i]
    + Σ по купленным стволам   weapon+0x48     ; битовая маска [player+0x81c2d8]
    + Σ по купленному оборуд.  equip+0x28      ; битовая маска [player+0x81c364]
    + Σ по типам боеприпасов   запас[i]×ammo+0x10   ; запас [player+0x81c2dc+4i]
```

### поля `DEFINE_WEAPONS` (потребитель `0x450be0`, вызывающий `0x45cac0`)

Вызывающий читает запись (после 3 строк) как 21 dword и пушит их
`arg3..arg23`; потребитель сохраняет их в запись по 0x2a8 байт. Строки:
`arg0` = имя (strncpy 15 байт в `+0x298`), `arg1` → `0x40b9c0` (разбор
запросного имени, хендл в `+0x290`), `arg2` = имя иконки → грузится из
каталога `frontend` в `+0x50` (или запись зануляется, если `none`).

Соответствие «операнд сигнатуры → смещение в памяти» (у потребителя
`0x450be0` окно аргументов меняется на `pop ebx` в `0x450d29`, отсюда
«сдвиг на dword» во второй половине полей):

| операнд | offset | смысл | статус |
|---|---|---|---|
| `L1` | `+0x24` | режим огня (switch в `0x445ac0`, кейсы 0/1/4/5; в dm1 — 1, 2, 4) | код |
| `L2` | `+0x2c` | период перезарядки: пишется в `0x81c358` при выстреле (`0x445f08`), `>0` блокирует выстрел (`0x445aa8`) | код |
| `L3` | `+0x3c` | индекс типа боеприпаса (в `DEFINE_AMMO`; `-1` = неизвестен) | код |
| `L4` | `+0x40` | расход боеприпаса на выстрел | код |
| `E1` | `+0x30` | id снаряда/эффекта (arg0 спавнера `0x4795b0`, `0x445ee2`) | код |
| `E2` | `+0x34` | id второго снаряда (спавнится, когда `0x81c35c == 0`) | код |
| `E3` | `+0x38` | значение состояния → `0x81c35c` (`0x445f7b`) | код |
| `E4` | `+0x4c` | id (в dm1 — константа `0xffff8ab5`) | значения |
| `L5` | `+0x44` | цена, в единицах «наличных» `0x81c36c` (столбец `COST`) | код |
| `L6` | `+0x48` | вес: суммируется в общий вес машины `0x81c374` (`0x4524d0`), который экран печатает как `WEIGHT: %ld` (`0x4952c3`) | код |
| `L7` | `+0x28` | битовые флаги (тесты бит `0x01`/`0x40`/`0x80`) | код |
| `L8` | `+0x294` | индекс класса/семейства (0..8) | значения |
| `D1` | `+0x00` | скорость накопления заряда (`0x81bfe8 += delta × D1`, счётчик 0..1 сравнивается с `1.0`) | код |
| `B1` | `+0x08` | тангенс конуса разброса, ось 1 (0.0875 = tan5° … 1.732 = tan60°) | код |
| `B2` | `+0x10` | тангенс конуса разброса, ось 2 | код |
| `D2` | `+0x18` | дальность цели: верхняя граница в поиске попадания `0x477f90` | код |
| `L9` | `+0x20` | индекс точки вылета: проверяется `0 ≤ x < 8` (`0x4458c4`), индексирует таблицу матриц узлов (`0x81bf38`) | код |

Доказательства. `L3` проверяется на `< [0x818958]` (иначе
`Unknown ammo type for weapon (%s)`), значения сходятся с именами
(`MACHINE GUN`→`BULLETS`, `CANNON`/`AUTOCANNON`→`CANNON SHELLS`,
`FLAMETHROWER`→`NAPALM`, `TAC NUKE`→`TAC NUKE`, `MRL`→`MICRO-ROCKETS`,
лазеры→`POWER CELLS`); `L4` вычитается из запаса игрока
`[0x81c2dc + ammo*4]` при выстреле (`0x445e98`); `L5` читается в
покупке/продаже (`0x47c365` вычитает из `0x81c36c`, `0x47c2a7` возвращает
при продаже); `L2` пишется в счётчик `0x81c358`, который проверяется в
начале обработки выстрела; `L9` ограничен восемью точками вылета; `D1`
накапливается в счётчик заряда `0x81bfe8` (`0x445c5b`:
`fild delta; fmul [weapon+0x00]; fadd [0x81bfe8]`), который сравнивается
с `1.0` (константа `0x4a22d8`), а при отпускании гашетки обнуляется
(`0x445d43`); `B1`/`B2`/`D2` передаются в запрос попадания `0x477f90`,
где `D2` служит верхней границей дистанции (`0x4784fb`:
`fcomp [esp+0x20]`, `esp+0x20` = `fild` от `D2`), а `B1`/`B2` задают
конус: кандидат принимается только при
`|смещение по оси 1| < масштаб × B1` и `|смещение по оси 2| < масштаб ×
B2` (`0x4781d9`-`0x47821b`). Столбцы экрана покупки (`0x4be67c` `COST`,
`0x4be694` `AMMO TYPE`) независимо подтверждают `L5`/`L3`. Поля со
статусом «значения» (`E4`, `L8`) доказаны лишь диапазонами значений
(`L8` ∈ 0..8 — группировка стволов по семействам).

Пример из `dm1.sbt`: ammo (15: `BULLETS`…`DECOY`), weapons (19:
`MACHINE GUN`…`MESON GUN`), equipment (12), затем `IF
LEVEL_OBJECTIVES_COMPLETE { DEFINE_PLAYER_TYPES … }` и далее.

### поля `DEFINE_PLAYER_TYPES` (шасси; потребитель `0x47a170`)

Таблица — это **шасси** (в `dm1.sbt` 4 записи: `LIGHT`/`MEDIUM`/`STEALTH`/
`HEAVY CHASSIS`). Три строки: имя, ресурсное имя (`tick`), имя иконки
(`tickx`). Обработчик 172 — `0x45ccc0`: читает 3 строки и передаёт запись
как список аргументов в `0x47a170`.

| | значение |
|---|---|
| запись в файле | `3×S + 0x17c` (95 dword) |
| массив в памяти | база `0x7995e0`, **шаг `0x1cc`** (460 Б) |
| счётчик | `0x7941bc`, предел `0x20` (32), ошибка `0x4bb1a0` |
| пост-обработка | `0x47a720` (вызывается из `0x45d042`) |

Раскладка памяти — **перестановка** 95 полей (не совпадает с файловым
порядком); воспроизводится инструментом:

```sh
python3 tools/re/table_layout.py 0x47a170 0x7995e0 --end 0x47a730 --stride 0x1cc
```

Первые поля записи — указатели/хендлы: `+0x00`/`+0x04` берутся из хвоста
файловой записи (dword 88/89), `+0x08`…`+0x14` — из дополнительных
аргументов (строки/хендлы). Пример (важные смещения):

| память | источник |
|---|---|
| `+0x00` | файловый dword 88 |
| `+0x04` | файловый dword 89 |
| `+0x08`…`+0x14` | доп. аргументы (имена/хендлы) |
| `+0x18`/`+0x1c` | dword 1 / 2 (double `op1`) |
| `+0x20`/`+0x24` | dword 5 / 6 (double `op4`) |
| `+0x28`/`+0x2c`/`+0x30`/`+0x34`/`+0x38` | dword 7 / 11 / 9 / 10 / 11 |
| `+0x148`/`+0x14c`/`+0x150`/`+0x154` | dword 0 / 3 / 4 / 7 |
| `+0x1c4`/`+0x1c8` | dword 98 / 99 (доп. аргументы) |

**Поля ходовых характеристик** (`op0`…`op4`) найдены по коду применения шасси
к игроку — ветка «шасси выбрано» функции пост-обработки, `0x47ac1a`…`0x47ad90`
(для индекса `i` адрес записи `edx = i × 0x1cc`):

| операнд | память | смысл | приёмник в игроке |
|---|---|---|---|
| `op0` (`L`, файл dword 0) | `+0x148` | **предельная масса** (вес) | `[player+0x81c378]` (`0x47ac8f`), по умолчанию 1000 |
| `op1` (`D`, dword 1-2) | `+0x18`/`+0x1c` | **штраф скорости на единицу массы сверх предела** | `[player+0x81bd80]`/`[+4]` (`0x47ac9b`), 0 по умолчанию |
| `op2` (`L`, dword 3) | `+0x14c` | **броня × 100** | `[player+0x81c28c]` = `op2×100` (`0x47acc5`), 5000 по умолчанию |
| `op3` (`L`, dword 4) | `+0x150` | **предел брони × 100** | `[player+0x81c284]` = `op3×100` (`0x47ace0`), 10000 по умолчанию |
| `op4` (`D`, dword 5-6) | `+0x20`/`+0x24` | **базовая максимальная скорость** | `[player+0x81bd70]`/`[+4]` (`0x47ac77`), 2.0 по умолчанию |

Код применения (`0x47a7xx`…`0x47afxx`) копирует дальше всю «физику» шасси в
блок игрока `0x81bdb0`…`0x81bdc8`, `0x81bf90`…, `0x81c420`… (там же `rep movs`
двух строк: из `+0x16c` и `+0x17c`), поэтому остальные ~85 полей записи — это
физические параметры шасси (масса, инерция, тяга, геометрия), а не игровая
логика. Их роль можно дочитывать по коду `0x47ac1a`…`0x47af3e`.

**Проверка значений `dm1.sbt`** (расшифровка через sig-операнды, а не «сырые
dword»): `LIGHT` предел 500 / броня 80 / скорость 1.70, `MEDIUM` 1000 / 130 /
1.00, `STEALTH` 500 / 90 / 1.00, `HEAVY` 1600 / 200 / 0.60 — ровно то, что
ожидается от лёгкого/тяжёлого шасси.

Скорость и вес **на экране** берутся не из записи шасси напрямую, а из
структуры игрока: `TOP SPEED: %ld` печатает `[player+0x81bd88]` (`0x4952fd`),
`WEIGHT: %ld` — `[player+0x81c374]` (`0x4952c3`); оба считает `0x4524d0`:
скорость = `[player+0x81bd70]` − `(вес − предел) × [player+0x81bd80]` с
клампом снизу (`0x4525d5`…`0x452603`), вес = Σ(стат/100 × `[0x818950]`) +
Σ стволы`+0x48` + Σ оборудование`+0x28` + Σ запас×боеприпас`+0x10`.
Последовательность `+0x48`…`+0xbc` и парные блоки `0xc8`… в раскладке выше —
вероятно, бронеплиты (броня/масса), но это остаётся гипотезой.

### «физика» шасси: блок копирования `0x47ac1a`…`0x47af3e`

Помимо ходовых полей та же ветка копирует в структуру игрока (`[player+…]`,
база записи игрока 0 `0x81bd00`, шаг `0x3510`) остальные параметры шасси.
Полная карта снимается инструментом:

```sh
python3 tools/re/copy_trace.py 0x47ac1a 0x47af3e --src 0x7995e0 --stride 0x1cc \
    --dst 0x81bd00 --map "0x47a170 0x7995e0 0x47a730 0x1cc"
```

| приёмник игрока | источник (память шасси) | что используется | статус |
|---|---|---|---|
| `+0x070` (0x81bd70) | `+0x020` | макс. скорость (D, операнд `op4`) | код |
| `+0x080` (0x81bd80) | `+0x018` | штраф скорости (D, `op1`) | код |
| `+0x58c` (0x81c28c) | `+0x14c` ×100 | броня (`op2`) | код |
| `+0x584` (0x81c284) | `+0x150` ×100 | предел брони (`op3`) | код |
| `+0x678` (0x81c378) | `+0x148` | предел массы (`op0`) | код |
| `+0x0b0`…`+0x0c8` | `+0x028`, `+0x030`, `+0x034`, `+0x038`, `+0x03c`, `+0x000` | `+0x0b0`/`+0x0b8`/`+0x0c0` — **габариты (радиус) модели шасси**: `0x4522ad` конвертирует три `double` во `float` и вызывает `setobjectradius` `0x41df24` (тексты ошибок `0x4a88c4` «setobjectradius NULL», `0x4a88dc` «!inuse»); `+0x0c8` — ходовой параметр (`fmul` в `0x44392e`, `fld` в `0x444225`); вся группа из шести dword'ов (`+0x0b0`…`+0x0c4`) передаётся в `0x43c51f` (`0x44fe74`) | код / значения |
| `+0x238` (0x81bf38) | `mem +0x100`… | 8-элементная таблица узлов | код |
| `+0x19c`…`+0x230` (0x81bfa0…0x81bfdc) | `mem +0x48`…`+0x84` (8 `double`) | восемь `double`: `0x81bfa0` — предел отклонения, `0x81bfa8` — жёсткость, `0x81bfb0` — демпфирование (модель подвески: `|z| fcom [0x81bfa0]`, `fsub`, ×`[0x81bfa8]`/`[0x81bfb0]` в `0x44481c`…`0x44484d`), `0x81bfb8` — коэффициент в интеграторе скорости (`0x44447e`: `v += v×[0x81bfb8] + ускорение`); `0x81bfc0`/`+0x81bfc8` и `0x81bfd0`/`+0x81bfd8` — две пары значений, которые выбирает бит `0x4` в `[player+0x81c240]` (`0x447d7c`) и отдаёт в **настройку состояния рендера** `0x446590` (аргументы 25…28); что кодирует пара — не установлено, в этой сборке бит `0x4` вообще не выставляется (см. ниже) | значения |

Значения этих восьми полей (нумерация = порядок в памяти):
`0x81bfa0` — **порог проникновения**: при `|0x81bda0| ≥ порога` срабатывает
удар, объект `-11`/`-21` через спавнер `0x4795b0` (`0x4448c2`, `0x444db3`), а
само проникновение `0x81bda0` обнуляется;
`0x81bfa8` и `0x81bfb0` — **два числа урона** за единицу проникновения:
из них (×`d` × `[0x4a2310]`) конвертируются два целых (`ftol` `0x40e0e0`) и
уходят в функцию попадания `0x453b50` (`arg8` — вычитается из суммарной брони
`[player+0x81c288]`, `arg9` — накопитель «расплёска» при пробитии плиты).
Внутри `0x453b50` по направлению удара (`arg2`…`arg7` — точка/вектор) выбирается
одна из **четырёх бронеплит** `[player+0x81c290]`…`[+0x81c29c]` (индекс 0…3 по
знакам компонент), урон вычитается из плиты, а её переполнение — из суммарной
брони; при нуле брони вызывается `0x4536e0` (гибель). Предел брони —
`[player+0x81c284]` (из `op3`), текущая броня — `[player+0x81c288]`;
`0x81bfb8` — коэффициент интегратора скорости (`0x44447e`);
`0x81bfc0`+`0x81bfc8` и `0x81bfd0`+`0x81bfd8` — по два `double` на режим: какие
из них брать, решает бит `0x4` регистра `[player+0x81c240]` (`0x447d7c`).
Выбранная пара (4 dword'а = 2 `double`) уходит **не** в видео-слой, а в
`0x446590` — настройку состояния рендера: у функции 33 dword-аргумента
(позиция/ориентация игрока `0x819040`…`0x81906c`, глобалы `0x5a45**`, пара,
константы `0x4aa398`/`0x4aa39c`), а внутри пара становится `float`'ами
`ds:0x83d26c` (пара №1) и `ds:0x83d270` (пара №2) рядом с `float(0x81bda8)` →
`ds:0x83d278`; `ds:0x83d230`/`0x83d234` получают масштабы проекции от размера
экрана (`0x83d944` × `[0x4a23d8]` = 0.003125, `0x80d7e0`). Тот же вызов есть в
`0x448b39` и `0x44937e` (там те же 4 dword'а пушатся в обратном порядке).
Ранее тут значился «HUD-помощник `0x497080`» — это **ошибка**: `0x497080` —
диспетчер предъявления кадра (present/блит), он принимает 7 аргументов
(`arg2` = буфер `0x6c3160`, `arg3`/`arg4`/`arg5` = `0x83d944`/`0x83d630`/
`0x5a4618`, `arg1` = `0x5a45ec`, `arg6` ∈ {`0x10`, `0x8`, иначе} выбирает
видео-слой `0xa1b940`/`0xa1b1f0`/`0xa1b420`, `arg7` ≠ 0 — высота `0xc8` (200),
иначе `0x60` (96), ширина всегда `0x140` = 320). Пары он не получает вообще.
**Бит `0x4` в поставке не выставляется**: `test BYTE [player+0x81c240],4`
встречается в exe ровно один раз (`0x447d7c`), а все записи в этот регистр —
это `xor`/`and`/`or` с масками `0x11d400` (`0x44d684`), `0xfffffcf0`
(`0x452fe0` — сбрасывает в т.ч. биты 4/5/6/7/10/11) и точечные биты
`0x1/0x2/0x8/0x10/0x20/0x40/0x80/0x2000`; бит `0x4` не ставит ни один код.
Значит, из двух пар всегда берётся `0x81bfc0`/`0x81bfc8`, а
`0x81bfd0`/`0x81bfd8` — «мёртвые» данные этой сборки. Что именно кодирует
пара (координаты/уровень шкалы) — не установлено.
Отдельно: `0x81bf90` — смещение, на которое временно сдвигают точку для
запроса/спавна (`0x444dce`: `pos += 0x81bf90; call 0x4360f1; pos -= 0x81bf90`),
а `0x81bda0` — текущее проникновение (в шасси не хранится).
Ветка «шасси не выбрано» (`0x47ab40`…) кладёт свои значения по умолчанию:
`0x81bfa0` = `10.0`, `0x81bfb8` = `0.92` (`0x3fed70a3d70a3d71`),
`0x81bfc0`/`c8`/`d0`/`d8` = `0.25` — они пишутся как младшее слово (`bfa0`) +
старшее (`bfa4`), т.е. обычные little-endian `double`.
Значения этих полей в `dm1.sbt` (по 8 `double`, распознаны по «красивым»
числам; LIGHT … HEAVY): `1600 0.9/0.92/0.92/0.96 64 1 80 0.2 0/0/0/-5
63/69/69/57`. Ту же таблицу несут все `level*.sbt`/`dm*.sbt`. По **сырым
байтам** записи (проверено на `dm1.sbt`, смещение сразу после трёх строк)
`double`-ы лежат так: dword 1–2 = `0.003` (штраф скорости), 3 = `80` (броня),
4 = `100` (предел брони), 5–6 = `1.7` (макс. скорость), 8–9 = `30`, 10–11 =
`65`, 12–13 = `20`, 14–15 = `10`, 23–24 = `13/12.5/12.5/12`, 25–26 =
`400/500/500/600`, 27–28 = `1600`, 29–30 = `0.9…0.96`, 31–32 = `64`,
33–34 = `1`, 35–36 = `80`, 37–38 = `0.2`, 39–40 = `0/-5`, 41–42 =
`63/69/69/57` (дальше — 8-элементная таблица узлов).
| `+0x1b8`/`+0x1f8`/`+0x238` (0x81beb8/0x81bef8/0x81bf38) | три массива по 8 dword (`mem +0x84`, `+0xc0`, `+0x100`) | **координаты 8 узлов крепления** (цикл на 8 итераций в `0x47af08`): читаются как `fmul QWORD` в коде точки вылета `0x4458fb`/`0x445903`/`0x44590b` — это и есть таблица, которую индексирует `L9` оружия | код |
| `+0x720`, `+0x724`, `+0x738`, `+0x74c`, `+0x750`, `+0x764`, `+0x778`, `+0x7a8` | `+0x168`, `+0x17c`, `+0x190`…`+0x1c0` | dword'ы и **строки** (`rep movs` из `mem +0x16c`, `+0x180`, `+0x19c`, `+0x1b0`) | — |

Замечание: струкура памяти шасси хранит **строки внутри записи** (`+0x16c`,
`+0x180`, `+0x19c`, `+0x1b0`), которые копирование переносит в игрока через
`strlen`+`rep movs`; в файле им соответствуют дополнительные «строковые»
аргументы хранилища (`tools/re/table_layout.py` печатает их как
`extra arg 96…100 (string/handle)`).

Имена восьми `double` по `0x81bfa0`… уточнены по потребителям движения: это
параметры **подвески/сопротивления** (`0x44447e`, `0x44481c`…`0x44484d`) и две
пары значений, выбираемые битом `0x4` признака `[player+0x81c240]`
(`0x447d7c` → `0x446590`, аргументы 25…28). Статус — «значения»: имена выведены
из вида вычислений, не из текстовых меток движка.

**Открытый вопрос — точная укладка.** Обработчик `DEFINE_PLAYER_TYPES`
(`0x45ccc0`) читает запись сплошным «свипом» (смещения `[esi+0x178]` вниз до
`[esi]`) и в середине подменяет четыре поля хендлами (резолвер имён `0x42b81b`,
локальные указатели на строки записи), а функция-хранилище `0x47a170`
раскладывает 101 аргумент в память фиксированной перестановкой. Её карта
«аргумент → смещение» воспроизводится инструментом (`tools/re/table_layout.py`,
`tools/re/sbt_fields.py`), и на семи якорях (`op0` → `+0x148`, `op1` → `+0x18`,
`op2` → `+0x14c`, `op3` → `+0x150`, `op4` → `+0x20`…`+0x24`, файловые dword
0…6) она сходится; но `double`-ы записи начинаются с **нечётных** dword'ов
(см. выше), а перестановка кладёт их в восьмибайтово выровненные слоты
`+0x48`…, из-за чего «в лоб» совместить файл и память для блока
`0x81bfa0`…`0x81bfdc` не удаётся — по-видимому, записи шасси в поставке
собраны другим тулчейном (та же болезнь, что у `brief/level17.sme`, §14).
Поэтому **какие именно из восьми `double` попадают на `0x81bfa0`…`0x81bfdc`**
(и, значит, чему равны «пара» `0x81bfc0`/`c8` и порог/урон/демпфер) —
не установлено; достоверны только состав и значения восьми `double`.

## 12.4 Сцена: расстановка объектов кодом `SCRIPT`

**Статической расстановки в `.sbt` нет**: массив `things` записи `SCRIPT` пуст
во **всех 36** уровнях (`count = 0`), и ни один скрипт не выполняет
`ADD_THING*`. Сцена строится в рантайме кодом `SCRIPT`, поэтому единственный
статический источник — сам байткод. Разбор — `gm/scene.py`
(`gm.py scene <уровень.sbt> [--json]`).

Диспетчер команд `0x45c500` индексируется по **`op - 1`** (`jmp
[edx*4+0x45c500]`, `0x4574d4`), что даёт адреса обработчиков ниже. Соглашение
вызова — cdecl: операнды кладутся на стек в обратном порядке, поэтому
`[esp+4]` — **первый** операнд записи.

| команда | id | обработчик | что доказано кодом |
|---|---|---|---|
| `ADD_SKY_LIGHT_SOURCE` | 88 | `0x47e130` | `pos = (double)a0, a1, a2` (`fild`), затем `a3` (слово) и **байты** `a4/a5/a6` → R,G,B. Массив небесных источников `0x638130`, шаг `0x20`, не больше `0x10` (16), счётчик `0x64bbb0` |
| `ADD_LIGHT_SOURCE` | 87 | `0x47e1b0` | те же `fild a0,a1,a2` + цвет из байтов `a4/a5/a6`; массив `0x638330`, шаг `0x50`, до `0x3e8` (1000), счётчик `0x64bbb4`; далее вектор направления (`a7..a9`), размеры/радиусы (`a12`, `a15`) |
| `ADD_LOCATION` | 196 | `0x45bea6` | десять операндов кладутся **дословно** в запись «thing» (массив `0x80d8e0`, шаг `0x28`, счётчик `0x80d87c`, максимум 200). Потребитель `0x476008` читает `fild +0x04 / +0x08 / +0x0c` → x, y, z, т.е. это операнды 2..4; три `double` (`+0x10/+0x18/+0x20`) — ориентация (`level1` хранит yaw = π) |
| `ADD_ITEM` / `ADD_ITEM_FIXED` | 53 / 55 | `0x4598e7` → `0x4686a0` | слот в массиве предметов `0x806398` (шаг `0x60`, 300 слотов); позиция — `fild [esp+0x18]/[0x1c]/[0x20]`, т.е. **операнды 5, 6, 7** |
| `ADD_SOUND_SOURCE` | 187 | `0x459c6e` → `0x46b210` | семь операндов в параллельные массивы на 128 элементов: `a0 → 0x800340`, `a1 → 0x800540`, `a2 → 0x800140`, `a3 → …`, последний `double → 0x800760`. Какая из трёх колонок x/y/z — кодом **не доказано**; первые три приняты позицией («значения») |

Три `A`-double — **угол** (`0`, `π/2`, `−π/2` в данных), не позиция; пять `E` — **id сущностей** (см. ниже) либо 0; хвост `VNVNVN` — параметры (тип/направление/скорость: `700`, `120`, `99999`, `1500`) |

### Таблица сущностей в записи `SCRIPT`

Блок «трёх параллельных колонок handle» — это **таблица сущностей уровня**:
`n` записей по 12 байт, хранятся по колонкам (загрузчик `0x462b03`…`0x462bb0`:
счётчик → `0x5b1df0`, колонки → `0x5b0df0`, `0x5e4680`, `0x616658`).

| колонка | глобал | значения | смысл |
|---|---|---|---|
| 0 | `0x5b0df0` | `0`, `511` (`0x1ff`), `1023` (`0x3ff`) | **битовая маска** состояния сущности: компилятор пишет `0x3ff` (`0x460843`), команды правят биты, найдя запись линейным поиском по id (`0x457c49`: `\|= 0x1ff`, `0x457c52`: `&= 0xfffffe00`, `0x457cde`: `&= ~(1<<a)`) |
| 1 | `0x5e4680` | `-30231`, `-30067`, `4000303`, … | **id сущности** — то, чем команды `ADD_*` адресуют объект (поиск: `cmp [eax*4+0x5e4680], edx`) |
| 2 | `0x616658` | `0`, `13767`, `13773`, `13807`, … | **смещение** записи сущности в буфере скомпилированного мира: шаги между соседними записями (`6, 11, 34, 122, 994, 3, …`) **совпадают от уровня к уровню** (`dm1` и `level13` идентичны) — записи переменной длины, шаблоны редактора одни и те же |

**Происхождение id — интернированные имена.** Компилятор `SCRIPT`
(`0x46082f`…`0x4608a8`) кладёт в маску `0x3ff`, затем читает *токен имени*
лексером (`0x45fb90` — разбор токена до `'`/пробела, `0x45fea0` — собственно
интернирование), записывает полученный id в колонку 1, а в колонку 2 —
вычисленное смещение. Часть id — не имена, а «сквозные» id ресурсов
(`4000303` и подобные, как у `NAMED_ITEMS`, §12.2).

**Связь id → геометрия в поставке не восстанавливается** (отрицательный
результат): таблицы имён в файлах нет (в `.sbt` лежат только id), а поле «id»
объекта `.sbw` — на самом деле битовое поле (§10: во всех 36 уровнях всего 9
значений), поэтому `ADD_DOOR`/`ADD_SWITCH`, у которых вместо координат стоят
id сущностей, по данным уровня разместить нельзя. Доступен только сам список
сущностей — `gm.py scene --json` → `entities` (`id`, маска, смещение).

При этом `ADD_LOCATION` получает явные x,y,z (потребитель `0x476008`), а
`ADD_SPRITE` — явную позицию, так что «места» и спрайты размещаются
статически; двери и переключатели — нет.

### Кадр координат: 1.875 (подтверждён односторонним аргументом)

Скриптовые координаты — **мировые** координаты движка. Вершины `.sbw` движок
масштабирует базисом заголовка объекта (`diag(1.875)`, `object.points[1..3]`),
то есть `world = origin + 1.875 × v`, а просмотрщик и вся проекция лайтмапов
работают в «файловом» кадре — поэтому `gm.scene.SCALE = 1/1.875`.

Решающий (и не смещённый) аргумент — **односторонний**: спрайты (`ADD_SPRITE`,
позиция доказана кодом) стоят *внутри* уровня, значит размах их координат **не
может превышать** размах самой геометрии того же уровня. Измерено по 23
уровням (где ≥4 спрайтов): медиана отношения размахов = **1.52** (1.88, если
учитывать уровни с 3 спрайтами). Значение > 1 несовместимо с «тем же кадром» и
как раз соответствует базису 1.875.

Что оказалось **тупиками** (записано, чтобы не повторять):

* «доля позиций внутри AABB уровня» — критерий смещён: при уменьшении
  масштаба точки сходятся к центру и доля растёт монотонно (38% → 75% на шкале
  1.0→3.0), «лучший» масштаб получается произвольным;
* «расстояние до ближайшей вершины геометрии» — то же смещение (медиана
  `расст/диагональ` падает 0.78 → 0.29 → 0.15 → 0.08 при масштабах 1, 1.875,
  2.5, 3.5, минимума на 1.875 нет);
* корреляция **запечённых лайтмапов** с моделями света (`ламберт ×
  1/(1+d²/R²)`) нулевая при любом масштабе: `|r| < 0.18` на
  `level0`/`dm1`/`level1`/`level5`, знак меняется от уровня к уровню;
* медиана `|pos|` «мест»/света/звука превышает медиану `|v|` геометрии в
  6.5…250 раз — но это как раз ожидаемо для фоновых объектов и светильников
  (ср. `bgchunk*` в `THING_TYPES`), а не опровержение кадра.

Позиции **источников света** и **звуков** в этот кадр не укладываются (их
размах ≈ 5× размаха уровня), поэтому их кадр считать неустановленным:
использовать как маркеры или подбирать `--scene-scale` вручную. Позиции
`ADD_SPRITE` (и, вероятно, `ADD_LOCATION`) — в кадре 1.875.

## 13. Сущности `.soe`

**Разобран** по загрузчику движка (`gundx.exe` VMA `0x47cb6c`), а не по образцу
(в поставке лишь один файл — `SOBS/railrock.soe`). Движок открывает
`thing\<name>.soe` текстом (`fopen(..,"rt")`, строка `0x4bbb90`) и
компилирует в запись `THING_TYPES` из `.sbt` (§12) — бинарный
`char name[16]` + 49 `double` + 528 Б целых.

Файл — поток токенов через пробелы. Первый токен — **версия** (0..13); часть
блоков включается по ней. Порядок чтения (движковые `fscanf`, строка формата →
смысл):

| # | Условие | Формат | Блок |
|---|---------|--------|------|
| 1 | всегда | `%ld` | `version` (0..13) |
| 2 | всегда | `%ld %ld %s %ld %ld` | id-блок (`0x19c`,`0x198`,`class_name`,`0x1a8`,`0x1ac`) |
| 3 | v ≥ 9 | `%ld` | `0x1b0` |
| 4 | всегда | `%s %lf×6 %s` | `collision_type`, 6 `double` (`0x10/0x20/0x28/0x90/0x98/0xa0`), форма |
| 5 | форма `ellipsoid` | `%lf %lf %lf` | радиусы (у railrock `115 115 80`) |
| 5 | форма `sphere` | `%lf` | радиус |
| 6 | всегда | `%lf %lf %lf %lf` | `0x50/0x58/0x60/0x68` |
| 7 | v ≥ 7 | `%s %ld` | `event_a`, `0x1d4` |
| 7 | v < 7 | `%s %s %ld` | то же + второй event |
| 8 | v ≥ 8 | `%ld`×4 | `0x1d8..0x1e4` (max shield values) |
| 8 | v < 8 | `%ld` | одно значение на все 4 |
| 9 | всегда | `%s %s` | texture info |
| 10 | всегда | `%ld` | expire value (`0x1e8`) |
| 11 | v ≥ 3 | `%s` | expire event |
| 12 | всегда | `%s %lf %lf %lf %ld %s %s %ld %ld %ld` | блок из 10 полей (`0xc8`-буфер, `0x78/0x80/0x88`, `0x1c8`, два `%s`, `0x200/0x210/0x214`) |
| 13 | v ≥ 4 | `%lf` | falling fear (`0xc8`) |
| 14 | v ≥ 5 | `%s` | create event |
| 15 | v ≥ 6 | `%s` ×3 | morale failure / time out / damaged event |
| 16 | v ≥ 7 | `%ld %ld` | `0x1cc / 0x1d0` |
| 17 | v ≥ 10 | `%lf %lf` | `0xa8 / 0xb0` |
| 18 | v ≥ 11 | `%lf %lf` | `0xb8 / 0xc0` |
| 19 | v ≥ 12 | `%lf %lf` | `0x18 / 0x70` |
| 20 | v ≥ 13 | `%s %lf` | leash location (`0xd0`) |
| 21 | v ≥ 2 | `%ld`, затем `count × %s` | path points |
| 22 | всегда | `%ld`, затем `count × (%s %ld×6)` | weapon list (не более 8) |
| 23 | v ≥ 1 | `%ld`, затем `count × (%s %lf×6 %ld)` | children (не более 4) |

Проверка: файл `railrock.soe` (61 строка) содержит ровно **67 токенов**, и
парсер потребляет все до последнего (без остатка). Значения вроде «`none`»,
`NONE` и `0`-строки — легальные токены (`%s`), а не числа. Реализация:
`gm/soe.py` (`parse_text`/`parse_file`, `to_bytes`, `render_lines`);
CLI `gm.py soe <пути...> [-v] [--rebuild DIR]` (`to_bytes` побайтово точен,
`render_lines()` — канонические значения по строкам для новых файлов).

Роли многих полей неизвестны (движок копирует их в структуру почти без
интерпретации), поэтому в коде они названы по смещениям (`fXX`); названы
семантически те, что подписаны в сообщениях самого загрузчика (collision,
shields, events, weapons, children, path points).

## 14. Разметка интерфейса `.sml` / кодированные `.sme`

Каталог `SML/` (`brief/`, `prelevel/`, `design/`, `help.sml`, `credits.sml`)
— плоская **разметка интерфейса** в стиле XML: поток тегов без дерева
(`<p>` не закрывается, а тянется до следующего блочного тега). Теги:
`<I x="64" y="64" f="ltmills" a="l">` — картинка, `<F S="3">`/`<f s="2">` —
шрифт/набор, `<M B= S=>` — музыка, `<k>` — позывной игрока, а
`<f s="2">dmills=niacdispatch</f>` — пары «имя=значение».

**Разметка разобрана по загрузчику** `0x497650`: он индексирует позиции `<` и
`>` в массивы `0x68de40`/`0x68e668` (до 512 тегов), сдвигает буквы (см. ниже) и
заменяет `\n` на пробел (`0x497784`). Диспетчер тегов — `0x497d30`: байт после
`<` идёт в таблицу классов `0x498448` и jump-таблицу `0x4983f8`, т.е. движок
понимает **ровно девять** букв:

| Тег | Роль (доказано кодом) |
|---|---|
| `r`/`R` | новая строка (`row`) |
| `p`/`P` | абзац: сдвигает ширину строки на половину длины текста |
| `c`/`C` | одна **центрируемая колонка** строки (текст — следующий сегмент) |
| `f`/`F` | шрифт: атрибут `s`/`S` задаёт номер (общий парсер `0x498580`) |
| `x`/`X` | позиция по X в процентах от ширины (`значение*ширина/100`) |
| `k`/`K` | **позывной игрока**: вставляется строка `Soldier` (`ds:0x4bc2b8`) |
| `s`/`S` | вставляется строка `" "` (`ds:0x4ab74c`) |
| `m`/`M` | музыка: атрибут `B` → `ds:0x68cc8c` (трек), `S` → `ds:0x68cc88` (смещение) |
| `i`/`I` | картинка: атрибуты `x`/`y` — позиция, `f` — имя спрайта, `a` — клавиша действия |
| `/` | закрывающий тег (восстанавливает состояние разметки) |
| всё прочее, вкл. `d`/`D` | обработчика нет — **игнорируется** |

Разобрана и кодировка:

часть файлов лежит в **закодированном** виде (расширение `.sme`, 151 файл) —
это позиционный шифр Цезаря:

    encoded[i] = буква ? сдвиг(plain[i], +(i % 10)) : plain[i]

то есть каждая буква сдвигается вперёд на `индекс_байта % 10` внутри своего
алфавита (регистр сохраняется), все прочие байты копируются без изменений;
декодирование — тот же сдвиг со знаком минус. Сдвиг зависит только от позиции,
поэтому `encode(decode(x)) == x` для любого файла.

**Доказательство.** Из 147 пар `.sme`/`.sml` **131** раскодировались побайтово
в свой `.sml` (например `decode(LEVEL1.SME) == level1.sml`), остальные 16 —
разные редакции (в 9 из них `.sme` длиннее, в 3 короче, в 4 той же длины);
по крайней мере в одной паре видно, что правили именно `.sme`: `help.sme`
даёт исправленное «Toggle Player ID» (в `.sml` опечатка «PLayer») и строку
«P - Pause», которой в `.sml` нет. Все 151 `.sme` раскодировались в
корректную разметку, т.е. закодирован весь набор, а не отдельные файлы.

Содержимое: брифинги (`brief/level*`), «газеты» перед уровнем (`prelevel/`),
описания предметов (`design/`), помощь и титры.

Реализация: `gm/sml.py` (`decode`, `encode`, `tags`, `plain`, `stats`).
CLI `gm.py sml <SML или файлы> <out>` пишет в `<out>/sml/` раскодированную
разметку и в `<out>/txt/` текст без тегов (блочные теги → переводы строк,
`<k>` и теги с атрибутами сохраняются); `--rebuild DIR` собирает `.sme`
обратно — побайтово для 150 файлов из 151 (см. ниже).

**Аномалия поставки.** В `brief/level17.sme` на смещении 70 стоит лишний
`\r\n`. И движок (`0x497650` считает **каждый** байт), и `gm/sml.py` сдвигают
букву на `индекс % 10`, поэтому этот разрыв сбивает фазу и весь хвост брифинга
читается мусором (хотя в `brief/dir.txt` он есть). Замена разрыва на один
пробел — правило самого движка (`\n` → пробел, `0x497784`) — восстанавливает
текст целиком. `gm.py sml` делает такую починку автоматически (и только если
декодирование «как есть» даёт неизвестные буквы тегов), а `--rebuild` пишет
исправленный файл: 150 `.sme` из 151 собираются побайтово, `level17.sme` —
исправленным (на 1 байт короче).


## 15. Секретные уровни, DM5 и таблица имён `LVLNAMES.SLU`

Единственный служебный файл вне BIGFILE-архивов — `LVLNAMES.SLU` (ASCII,
CRLF, 595 байт): строки `СТВОЛ Отображаемое имя`, где ствол = имя файлов уровня.
Загрузчик — `0x48b3f0`: имя файла берётся из `ds:0x4bc270` (там лежит указатель
на строку `LVLNAMES.SLU`, `0x4bca9c`), файл открывается (`0x40dae0`), под
недостаток памяти/ошибку печатаются `0x4bdcf0`/`0x4bdcdc`, строки разбираются в
два буфера — имя уровня (2049 Б, `ds:0x68cc90`) и ствол (31 Б, `ds:0x68cc94`).
В поставке 33 строки: `LEVEL1`…`LEVEL24`, `SECRT1 Foundry`, `SECRT2 Processor`,
`DM1 Trailer Park`…`DM4 Deathmatch Till Dawn`. **Строки `DM5`/`TEMPLE` в файле
нет** (файл от 31.08.1998), хотя `GPatch.log` показывает, что патч правил
`lvlnames.slu` в том же прогоне, что и писал `temple.sbw`; имя `DM5 - TEMPLE`
в итоге берётся из самого уровня (`SET_LEVEL_NAME` в `temple.sbt`).

`NEW_LEVEL` из скрипта уровня — обычный переход, поэтому секретные уровни и
«новый» DM-уровень описаны целиком скриптами соседей (проверено декодером
`gm.py sbt`):

| Уровень | Имя (`SET_LEVEL_NAME`) | Лучшее время / секретов | .sbw | Куда ведёт `NEW_LEVEL` |
|---|---|---|---|---|
| `secrt1` | `SECRET LEVEL - FOUNDRY` | 147 / 4 | 116 секторов, 432 объекта, 3622 полигона, 444 текстуры | `level5`, `level00` |
| `secrt2` | `SECRET LEVEL - PROCESSOR` | 238 / — | 101 сектор, 490 объектов, 4233 полигона, 466 текстур | `level19`, `level000` |
| `temple` | `DM5 - TEMPLE` | — | 55 секторов, 517 объектов, 3751 полигон, 406 текстур | `level5`, `level00` |

**Как попадают в секретные уровни.** В скрипте `level4.sbt` (OIL RIG) есть
отдельный под-скрипт `SOURCEPLAYER_FOCAL_ADJUST 0.8; NEW_LEVEL "Secrt1"`
(смещение `0xde21`, закрыт байтом `0xFF`/`END`), в `level16.sbt` (CULT MOON) —
такой же `NEW_LEVEL "secrt2"` (`0xe44d`); обоих прямо никто не адресует прыжком,
т.е. вызов идёт по триггеру вещи-«прыжковых ворот». Оба уровня объявляют
`SET_LEVEL_SECRETS 5`, а «найденные секреты» внутри уровня отмечают под-скрипты
`ADD_SOURCESCREEN_TEXT 1 "FOUND A SECRET"` + `INCREMENT_SOURCEPLAYER_SECRET_TALLY`.

Карточки между уровнями это подтверждают текстом: `SML/prelevel/s1.sml` (=
`secrt1.sme`, файлы побайтово совпадают по тексту) — «YOU FOUND A SECRET LEVEL!
… That wasn't a Nataka jumpgate … a Network 53 foundry … It should be about
fifteen meters from your arrival point. Just go through the gate and get back to
headquarters.»; `s2.sml` (= `secrt2.sme`) — «… one of Keller's jumpgates …
a Kyodai ore processor …». То есть в `level4` есть ворота «Натака», ведущие в
Foundry, в `level16` — ворота «Келлера», ведущие в Processor, а внутри
секретного уровня стоит ворота обратно в штаб (`level00`/`level000`) или дальше
по кампании (`level5`/`level19`).

**`temple` (DM5).** Новый уровень патча 1.36 (`patch136.txt` — «This patch also
includes a new deathmatch level, the TEMPLE», `GPatch.log` — `writing temple.sb`,
плюс `patching secrt1.sb`/`secrt2.sb`; даты файлов `secrt*.sbw`/`temple.sbw` —
28.11.1998, день выхода патча). Это чисто DM-уровень: `NEW_LEVEL` ведёт в
`level5`/`level00`, т.е. в DM-классик-цепочку. Его спрайты/анимации лежат в
`dm2.sbt` (таблица имён `DM5A`…`DM5O`), музыка — банк `dm5` в `MUSIC/SOU.IDX`.
DM-цепочка задана скриптами: `dm1 TRAILER PARK` → `DM2` → `DM3` → `dm4` →
`level1`.

Контекст `level00`/`level000`/`level0a`: это **три варианта штаба** (HQ) — в них
ведут концовки почти всех уровней (`NEW_LEVEL "level00"` / `"level000"`).
`level00.sbw` и `level000.sbw` — одна и та же карта (совпадают все разобранные
поля, `.sbc` побайтово одинаков), а `level0a` — третий её вариант; различается
только поле `value` в таблице текстур (139 записей из 383, у 120 из них
отношение ровно `8/7`), т.е. это разные сборки одной карты. Своих строк в
`lvlnames.slu` у них нет (там только `LEVEL1`…`LEVEL24`, `SECRT1/2` и `DM1..DM4`)
— в меню паузы игрок видит особые пункты для `LEVEL20`/`SECRT1`/`SECRT2`
(`0x4888e4`…: сравнение имени уровня из `0x5a48b8` с этими тремя строками
запрещает «Restart level from HQ»).

Реализация: отдельного кодека не нужно — `lvlnames.slu` читается как текст
(CRLF), а всё остальное уже покрыто `.sbt`/`.sbw`/`.sml`.
