# Запись `.key` (KEYCFG): побайтовый round-trip и правка одного слота (`M11.5`, срез 13)

* **Статус:** срез готов. Round-trip **3/3** файлов побайтово, оракул
  `gm/small.py` — **3/3**; правка слота меняет **ровно 8-байтовый регистр**
  (в демо — 1 фактически изменённый байт), правка имени — только `name[16]`;
  хвост 112 Б не меняется никогда. Правку видят и Python (`gm/small.py`,
  `gm.py misc`), и C++ (`engine/src/input/controls.cpp`). Self-test **49/49**.
* **Ветка:** `feat/keywrite`, база `master` `a776e9b`, дата 2026-10-24.
* **Файлы:** `tools/editor/keywrite.py` (новый), `docs/KEY_WRITE.md` (этот
  документ). Больше ничего не менялось.
* **Игра:** только чтение, `/mnt/d/games/Gunmetal 3dfx` (зеркало
  `~/.cache/gunmetal-re/game`). Результаты команд — в
  `/tmp/opencode/keywrite` (в git не попадают).
* **Оракул:** `gm/small.py` (`parse_key`, `to_bytes`), раскладка —
  `docs/FORMATS.md` §8.2, `docs/CONTROLS_CPP.md` §1.1, `docs/CONFIG.md` §6,

## 1. Что лежит в поставке

Файлы **есть**, синтетика не понадобилась:

```sh
find "/mnt/d/games/Gunmetal 3dfx" -iname '*.key'
# /mnt/d/games/Gunmetal 3dfx/KEYCFG/PERFECT.key   376
# /mnt/d/games/Gunmetal 3dfx/KEYCFG/SPLIT1.KEY    376
# /mnt/d/games/Gunmetal 3dfx/KEYCFG/SPLIT2.KEY    376
```

Итого **3 файла, 1128 Б**, ровно по `0x178`; регистр расширения разный
(`.key` и `.KEY`) — перечисление игры (`KEYCFG\*.KEY`, `0x48534a`) регистр не
различает, инструмент тоже.

> `KEYCFG/*.KEY` — **пользовательские данные**: игра перезаписывает их при
> смене раскладки, `tools/re/install_audit.py` держит их в списке `volatile`
> (`docs/BASELINE.md` §«Внешние расхождения установки»). Поэтому «эталонных»
> байтов набора в репозитории нет и быть не должно; проверяются инварианты
> формата, а не конкретные коды. В каталог игры инструмент не пишет никогда.

## 2. Раскладка

```
+0x000  char name[16]              имя набора, NUL-дополненное
+0x010  31 * { u32 code; u32 b }  действия 0..30 (248 Б)
+0x108  14 * { u32 x;    u32 y }  непонятый хвост 112 Б
        ------------------------
        0x178 = 376 Б
```

* Загрузчик `0x4852e7`…`0x4853e6` делает `fread(buf, 0x178, 1, f)`, копирует
  имя `strncpy(...,16)` и распаковывает **31** пару в рабочую запись
  `name[16]` + `31*8` = `0x108` (`0x6c2058 + i*0x108 + 0xF8`), писатель
  `0x485440` сбрасывает те же `0x178` байт (`docs/CONFIG.md` §6, §9;
  `docs/CONTROLS_CPP.md` §1.1).
* `code` — не DirectInput DIK, а индекс собственной таблицы имён игры
  (123 записи × 6 Б по RVA `0x4A5B88`): `0x11` = W, `0x39` = SPACE,
  `0x6D` = UP; `0` = «не назначено».
* `b` — второй u32; **во всех 93 используемых парах поставки он 0**, смысл не
  доказан. Раскладку «код + модификаторы» данные **не подтверждают**, поэтому
  инструмент печатает `b` как есть, предупреждает о ненулевом и никогда не
  трактует его как модификаторы.
* Пары 31..44 — не «действия 31+»: это хвост писателя (см. §4).

Модель инструмента — ровно эта: `name[16]` + 45 пар, `parse -> to_bytes`
биективен для любого содержимого.

## 3. Доказано round-trip'ом

```sh
python3 tools/editor/keywrite.py --roundtrip
```

```
roundtrip: /mnt/d/games/Gunmetal 3dfx/KEYCFG
  3 files, 1128 bytes
  identical=3/3  differs=0  errors=0
  tail preserved=3/3  non-canonical names=0
  oracle gm/small.py: to_bytes identical=3/3

```

То есть **все** доступные файлы читаются и собираются обратно побайтово; хвост
сохраняется как есть; независимый оракул `gm/small.py` даёт те же байты.
`--roundtrip FILE` делает то же для одного файла.

## 4. `--audit`: числа корпуса и что такое хвост

```sh
python3 tools/editor/keywrite.py --audit
```

```
files: 3, 1128 bytes; names: PERFECT(7), SPLIT1(6), SPLIT2(6) (lengths {6: 2, 7: 1}, unique 3)
actions: 31 used slots (pairs 0..30 of 45 in the file); bound 67/93 (72%), per file 29/19/19
codes: distinct 53, range 0x0f..0x72, outside the 123-entry name table: 0
second u32 (modifiers?): nonzero 0/93 -> 'code + modifiers' is NOT confirmed
tail (pairs 31..44, 112 bytes): identical in 1/3 pattern(s); zero 39, nonzero 73, distinct byte values 40
tail top bytes: 00 x39, 8c x6, e1 x5, ff x4, 99 x4, 1b x3
tail status: HYPOTHESIS - the writer's uninitialised stack; preserved verbatim, never edited
```

Что из этого следует.

* Наборы: 3 имени длиной 6–7 Б, все уникальны, имя внутри файла = имя файла
  без расширения. Свободных действий: у `PERFECT` 2, у `SPLIT1`/`SPLIT2` по 12;
  всего назначено **67 из 93** слотов.
* Коды: 53 разных, все в диапазоне `0x0F..0x72` и все внутри таблицы 123 имён.
  Внутри одного набора повторов нет.
* Второй u32 = 0 **93/93** — значит пара это «код + что-то, что игра не
  заполняет», а не подтверждённые модификаторы.
* **Хвост 112 Б**: у всех трёх файлов он **побайтово одинаков** (1 паттерн на
  3 файла), но **не нулевой**: 39 нулей и 73 ненулевых байта, 40 разных
  значений, повторы (`8c` ×6, `e1` ×5, `ff` ×4, `99` ×4). В
  `docs/CONFIG.md` §6 записан другой хвост (`f3 78 51 6d` по `0x108`), то есть
  между сохранениями игры он **меняется**, оставаясь одинаковым у всех наборов.
  Это согласуется с разбором `docs/CONTROLS_CPP.md` §1.1 и `docs/CONFIG.md`:
  писатель сбрасывает `0x178` байт, а осмысленных в его записи только `0x108`,
  остальные 112 — остаток стека того же пути записи. **Статус: гипотеза**,
  подкреплённая данными (одинаковость у трёх файлов + дрейф между снимками), но
  не кодом. Смысл байтов не разобран, инструмент их не трогает и отказывается
  править слоты 31..44.

## 5. `--list` и `--check`

```sh
python3 tools/editor/keywrite.py --list KEYCFG/PERFECT.key      # [--json]
```

31 строка: `idx`, действие (имена из `kActionNames`, таблица указателей
`0x4BC558`), код, символ из 123-имён, второй u32, 8 байт в hex. Символ — только
отображение: `NONE` для 0, `KEY_<n>` для кодов вне таблицы. `--json` отдаёт те
же поля плюс смещение пары.

```sh
python3 tools/editor/keywrite.py --check FILE [--against FILE]
```

`--check` проверяет размер, каноничность имени, коды (бит 31 — ошибка, как в C++
читателе; коды ≥123 — предупреждение, они сохраняются), ненулевой второй u32
(предупреждение) и печатает `sha256`. С `--against` печатает **число
изменённых байт**, первый отличившийся offset и разбивку: сколько байт в имени,
какие слоты, сколько в хвосте.

## 6. Правка: ровно один 8-байтовый слот

```sh
python3 tools/editor/keywrite.py --file KEYCFG/PERFECT.key \
        --set-slot 29 --bytes 6600000000000000 --out /tmp/opencode/keywrite/PERFECT_slot29.key
```

```
edit: …/PERFECT.key -> …/PERFECT_slot29.key
  slot 29 (linear_left): bytes 248..255 -> 6600000000000000
  bytes: 376 -> 376 (+0); changed 1 byte(s), first at offset 248
  tail (112 opaque bytes): untouched
  sha256: 55c4d63c12322177 -> 8c4c14d41e3c6a1a
  gm/small.py sees 'PERFECT'; --check: ok
```

Слот 29 был `0`, стал `0x66` (NENTR по таблице имён): пара занимает ровно 8 Б
(`248..255`), из них реально изменился 1 байт — нули остались нулями. Это и
есть «правка 8-байтового регистра»: инструмент не имеет пути изменить 7 или 9
байт слота.

Контроль: `--check OUT --against IN` → `changed: 1 byte(s), first at offset
248; name 0, slots [29], tail 0`.

Если нужны все 8 байт, это тоже ровно 8:

```sh
python3 tools/editor/keywrite.py --file KEYCFG/SPLIT1.KEY \
        --set-slot 0 --bytes 0403020108070605 --out /tmp/opencode/keywrite/SPLIT1_8B.key
# bytes: 376 -> 376 (+0); changed 8 byte(s), first at offset 16
# warning: code 16909060 (0x1020304) is outside the 123-entry name table
# warning: second u32 is 0x05060708 … (preserved)
```

**Оба читателя видят правку.**

* Python (`gm/small.py`): `entries[29] == (102, 0)`, `to_bytes() == файл`;
  `gm.py misc OUT --json` печатает `"codes": […, 102, 0, …]`. Для 8-байтового
  демо — `(16909060, 84281096)`.
* C++: одноразовый harness, собранный из `engine/src/input/controls.cpp`
  (в git не входит):
  `zigcxx -std=c++20 -I engine/src kharness.cpp engine/src/input/controls.cpp`.
  На исходном `PERFECT.key` — `29 a=0 b=0 NONE`; на правленом —
  `29 a=102 b=0 NENTR`, остальные 30 строк совпадают. На 8-байтовом демо —
  `0 a=16909060 b=84281096`, `pairs[0]` читается как записано.

Имя:

```sh
python3 tools/editor/keywrite.py --file KEYCFG/SPLIT2.KEY \
        --set-name MYKEYS --out /tmp/opencode/keywrite/SPLIT2_name.key
# changed 6 byte(s), first at offset 0; name 6, slots none, tail 0
```

C++ видит `name=MYKEYS`, оракул — `MYKEYS`, `to_bytes` совпадает, `--check` ok.
`name[16]` вмещает ≤15 байт + NUL; игра при записи обрезает **имя файла** до 8
символов (`KEYCFG\%.8s.key`, `0x485440`), но внутреннее имя читает 16 байт —
поэтому длинное имя формат не ломает, хотя на диске получит укороченный файл.

## 7. Отказы (код 2)

* файл не 376 Б (`375`/`377` — отказ, а не «дочитаем/обрежем»);
* имя длиной 16 Б без NUL или с ненулевыми байтами после NUL;
* пустая правка, `--set-name` без `--file`/`--out`;
* `--set-slot` вне `0..44`, и отдельно `31..44` — «непонятый хвост»;
* `--bytes` не 16 hex-цифр (ровно 8 Б) или не hex;
* `--set-name` не latin1, с NUL или >15 Б;
* слот с битом 31 в коде (C++ читатель считает такой файл битым);
* `--out` внутри установки игры, её зеркала или репозитория; `--out` равен
  входу.

Коды выхода: `0` успех, `1` проверка не прошла (`--roundtrip`/`--check`/
`--self-test`), `2` отказ/плохой вход, `3` внутренняя ошибка.

## 8. Self-test и регрессия

```sh
python3 tools/editor/keywrite.py --self-test          # 49/49
python3 tools/editor/keywrite.py --self-test --json   # то же одной JSON-строкой
```

Проверки без игры: модель и оракул, размеры, имя (16 Б, NUL внутри, контрольные
символы, пустое, latin1), hex-пара, смещения `16+8n`, отказ на хвосте и
диапазоне, «один слот = 1 изменённый байт» и «8 байт = 8», правка имени,
комбинированная правка, guard'ы (игра/зеркало/репозиторий/тот же файл),
`--check` с `--against`, битый/неизвестный код, ненулевой второй u32, 31 строка
`--list`, символы из `controls.cpp`, синтетические `--audit`/`--roundtrip`.

`python3 regress.py --mirror --json` — см. отчёт коммита: C++/Python не
менялись, поэтому ожидания прежние; новые файлы в регрессию не входят.

## 9. Ограничения

* **Не проверяет валидность скан-кода.** Любой `u32` без бита 31 принимается;
  коды вне таблицы 123 имён — предупреждение, а не отказ (C++ читатель их тоже
  сохраняет). Дубликаты кодов между действиями и конфликты «клавиша занята»
  инструмент не ловит — это делает редактор игры (`%s has been used twice`,
  `0x4BD790`), а не файл.
* **Второй u32 не интерпретируется.** Раскладка «модификаторы» не подтверждена
  (0/93 в поставке); записывать туда осмысленное значение можно только сырыми
  8 байтами и с предупреждением в `--check`.
* **Хвост 112 Б — гипотеза.** Инструмент его сохраняет и отказывается править;
  «правильный» хвост не восстановить, пока не разобран смысл. При правке хвост
  берётся из входного файла, поэтому правленый файл наследует именно его.
* **Наборы — пользовательские данные.** В поставке они уже отличаются от
  манифеста (`volatile`), поэтому `--audit`/`--roundtrip` показывают *текущее*
  состояние установки. Инструмент не пишет в игру: результат всегда в `--out`.
* Имя — latin1 (как `char[16]`); UTF-8 не поддерживается намеренно.
* `--list`/`--check`/правка требуют каноничного имени; `--roundtrip` считает
  неканоничное имя предупреждением и всё равно проверяет байты.

## 10. Доказано / гипотеза / осталось

**Доказано:** раскладка `name[16] + 45*8` и размер 376 Б (round-trip 3/3 и
оракул 3/3); 31 используемая пара, смещения `16+8n`; правка слота меняет ровно
свой 8-байтовый регистр; имя — только первые 16 Б; хвост при правке
побайтово сохраняется; Python и C++ читатели видят правку.

**Гипотеза:** хвост 112 Б — остаток стека писателя (одинаков у трёх файлов,
дрейфует между сохранениями, в документации зафиксирован другой снимок);
`b` — не модификаторы.

**Осталось:** разобрать смысл хвоста (нужен разбор писателя `0x485440` и его
стека) — до этого правка 31..44 запрещена; при желании — валидация конфликтов
и «занятости» клавиш на уровне редактора.
