# Подводное состояние, экранный эффект и звук (`M7.7`)

Статус: **состояние и палитра прослежены до конца; фильтра в звуке нет** —
доказано кодом, данными и отрицанием. Всё снято с `gundx.exe` v1.36
(sha256 `929ffa72…acd17`, база `0x400000`), игру инструмент только читает.
Инструмент: `tools/re/underwater.py` (`--self-test`, `--fields`, `--scripts`,
`--anchors`, `--json`), Ghidra не нужна.

Смежные документы: `docs/SCREEN_FX.md` (§1.6 фейд, §3.2 палитры),
`docs/AUDIO_3D.md` (§7 «чего в тракте нет»), `docs/SOUND_FIELDS.md` (§3 запись
голоса), `docs/RECORDS.md` §2.2 (`SECTOR_STUFF`, флаги `+0x50`),
`docs/PLAYER_FIELDS.md` (`+0x3200`), `docs/VM_EXEC.md` (условия 47/48),
`docs/WORLD_FIELDS.md` §2.1 (запись сектора мира), `docs/FORMATS.md` §10.1.

## 1. Флаг «под водой»

### 1.1. Где живёт

Поле — `u32` `player+0x3200` (бит `0x8`), слот 0 — `0x81c240`
(`docs/PLAYER_FIELDS.md` §10). Массив игроков: `0x819040 + i*0x3510`, 8 слотов.

**Смещение «текущего сектора» — `+0x323c`, а не `+0x327c`.** Для слота 0 это
`0x81c27c`, и именно этот абсолютный адрес фигурирует в `docs/SECTOR_STUFF.md`
§1.3 / `docs/WORLD_FIELDS.md` §2.6. Проверка:

```
0x81c27c - 0x819040 = 0x323c
```

Код использует его как индекс сектора: диапазон `0..0xff`, индекс в
`SECTOR_STUFF` (`0x800b60 + sector*0x58`, `0x451160`: `0x800b60 + param_2*0x16`
двордов) и подстановка в слот «сектор» у `event_post` (`0x4448b5`).
`docs/PLAYER_FIELDS.md` §10 называет `+0x323c` «`model_id`» — это ошибка
документа (правка — за владельцем `PLAYER_FIELDS.md`; здесь фиксируется
расхождение). `docs/AUDIO_3D.md` §7 уже пишет правильно: `idx = player+0x323c`.

### 1.2. Кто ставит и снимает

Обе записи — в физике игрока `FUN_00443690`:

```
444F4A  test BYTE PTR [ebx+0x81c240],0x8     ; уже в воде?
444F53  mov  edx,[ebx+0x81c27c]              ; текущий сектор
444F5A  call 0x42d99f                        ; тип = kind/6
444F62  cmp  eax,1
444F65  je   0x44501c                        ; ещё в воде -> ничего
444F6B  mov  ecx,[ebx+0x81c240]              ; ВЫХОД из воды
444F71  and  ecx,0xfffffff7
444F74  mov  [ebx+0x81c240],ecx              ; бит 0x8 снят
444F7A  mov  ecx,[ebx+0x81c450]              ; player+0x3410 (P22 шасси)
...
444FB8  mov  eax,[ebx+0x81c27c]              ; ветка «не в воде»
444FBF  call 0x42d99f
444FC7  cmp  eax,1
444FCA  jne  0x44501c
444FCC  mov  edx,[ebx+0x81c240]              ; ВХОД в воду
444FD2  or   edx,0x8
444FD5  mov  [ebx+0x81c240],edx
444FDB  mov  eax,[ebx+0x81c44c]              ; player+0x340c (P21 шасси)
```

Полный список писателей бита `0x8` — **ровно два места** (скан листинга по
`0x81c240`/`0x81c241`, 161 строка): `0x444FD2` (ставить) и `0x444F74`
(снимать). Загрузка сейва бит не восстанавливает:

```
464C25  and edi,0x11d400        ; маска сохранённых битов, бита 0x8 в ней нет
464C2D  mov [eax+0x81c240],edi
```

`0x11d400 & 0x8 == 0`, поэтому вода после загрузки пересчитывается из сектора,
а не берётся из сейва.

### 1.3. Когда срабатывает

Раз в тик физики, **по сектору**, без проверки глубины и объёма: как только
текущий сектор игрока имеет тип 1 (`kind == 6`), бит ставится; как только тип
другой — снимается. Дополнительно на переходе:

* **вход** (`бит был 0`, `тип == 1`): если `player+0x340c != 0`, зовётся
  `event_post(id = player+0x340c, sector, 0, 0, x, y, z, player-0x10000)`
  (`0x444FDB`…`0x445014`);
* **выход** (`бит был 1`, `тип != 1`): то же с `player+0x3410`
  (`0x444F7A`…`0x444FB5`).

В поставочных данных эти поля шасси — константы `-30062` (P21) и `901010`
(P22) (`docs/WEAPON_FIELDS.md` §P21/P22), т.е. событие уходит всегда, а что
именно оно запустит — решает таблица скриптов уровня (§4.3).

### 1.4. Что бит меняет в физике

```
444122  test BYTE PTR [ebx+0x81c240],0x8     ; в воде?
444141  fmul QWORD PTR ds:0x4a2330           ; скорость * 0.75
444807  test BYTE PTR [ebx+0x81c240],0x8     ; удар: вода или земля
444847  fmul QWORD PTR ds:0x4a2310           ; порог воды * 0.5
4448C0  event_post(-11) SYSTEM_PLAYER_HIT_WATER
444EAE  event_post(-10) SYSTEM_PLAYER_HIT_GROUND
444928  mov [ebx+0x81bda0],0x33333333        ; вертикальная составляющая
444932  mov [ebx+0x81bda4],0xc0033333        ;   = -2.4 (тонет)
```

То есть вода: горизонтальная скорость ×0.75, вертикальная составляющая
фиксируется на −2.4, удар о поверхность даёт событие `-11` и
`damage_player(type 4)`. Удар считается по `|вертикальная составляющая|`
(`player+0x2d60`) против порога шасси `player+0x2f60`; в воде порог
умножается на `0.5` (`0x444847`), на земле — полный (`0x44483f`…), и тогда
постится `-10`.

### 1.5. Условия ВМ 47 и 48 (закрыты)

**47 `SOURCEPLAYER_UNDERWATER`** (`0x45e8dc`, сигнатура пустая):

```
45E8DC  mov eax,[esp+0x94]     ; адрес слота arg9
45E8E3  mov eax,[eax]
45E8E5  and eax,0xffff         ; индекс игрока (младшее слово)
45E8EA  jl  ...                ; < 0 -> false
45E8F0  cmp eax,8
45E8F3  jge ...                ; >= 8 -> false
45E8F9  lea ecx,[eax+eax*2]    ; \  ecx = i*0x3510
45E8FC  lea ecx,[ecx+ecx*8]    ;  |
45E8FF  shl ecx,1              ;  |
45E901  sub ecx,eax            ;  |
45E903  shl ecx,4              ;  |
45E906  add ecx,eax            ;  |
45E908  shl ecx,4              ; /
45E90B  mov eax,[ecx+0x81c240] ; player+0x3200
45E911  and eax,0x8
```

Возврат — `flags & 8` (8 или 0; ВМ считает истиной ненулевое). Аргумент — тот
же слот arg9, что и у `SOURCE_IS_PLAYER` (`0x45d15b`).

**48 `SOURCE_UNDERWATER`** (`0x45e91c`, сигнатура пустая):

```
45E91C  mov eax,[esp+0x7c]     ; сектор источника (поле кадра ВМ)
45E920  test eax,eax
45E922  jl  ...                ; < 0 -> false
45E928  push eax
45E929  call 0x42d99f          ; тип = kind/6
45E931  dec eax
45E932  neg eax
45E934  sbb eax,eax
45E936  inc eax                ; 1, если тип == 1, иначе 0
```

`[esp+0x7c]` — именно сектор источника: тем же полем пользуется
`SOURCESECTOR_FLAGS` (`0x45ecd1`: `mov eax,[esp+0x7c]`, проверка `0..0x100`,
индекс в `0x800b60 + sector*0x58`). Геттер:

```
42D99F  cmp [ebp+8],0 / jl -> -1
        cmp eax,[0x5670dc] / jl -> -1
        ecx = i*0x18;  ax = word [0x5670d8+ecx+0x14]
        cdq; idiv 6
```

Сеттер `0x42d9d5`: `mov word [0x5670d8+i*0x18+0x14], type*6`, поэтому
«тип 1» в скриптах = `kind = 6`.

Обе функции — без Ghidra, по листингу; в `tools/re/underwater.py` есть
байтовые якоря `0x45E8DC/0x45E8F9/0x45E90B/0x45E91C/0x45E931/0x42D99F/0x42D9F1`.

## 2. Экранный эффект

### 2.1. Палитры

| что | адрес |
|---|---|
| `GAMEPAL` (768 Б, 6 бит/канал) | `0x83d320` |
| `WATERPAL` (768 Б) | `0x83d640` |
| текущая палитра (указатель) | `[0x83d2c4]`, старт `0x44afb3` = `0x83d320` |
| загрузчик BMP-палитры | `0x44af78` (gamepal), `0x44afa3` (waterpal) → `0x47efe0` |
| предупреждение | `0x4abb5c` `"Unable to load underwater palette (FRONTEND\\WATERPAL.BMP), auto generating it."` |
| автогенерация | `0x41edd3` |

Загрузчик `0x47efe0(subdir, name, dest)` берёт палитру BMP и сжимает каждый
канал в 6 бит:

```
47F0B4  shr dl,2
47F0BD  shr dl,2
47F0C6  shr dl,2
```

**Файл в поставке есть.** `FRONTEND\WATERPAL.BMP` лежит внутри бигфайла
`FRONTEND/BMP.IDX`/`.DAT` (`gm/bigfile.py`): записи `GAMEPAL` и `WATERPAL`, обе
по 1142 байта, 8 bpp, 256 цветов. `WATERPAL` — настоящая сине-зелёная
таблица: средние `R/G/B = 82.7/151.1/127.9`, отличается от `GAMEPAL` во всех
256 слотах (например слот 2: `GAMEPAL (23,23,23)` → `WATERPAL (41,81,72)`).
Поэтому ветка автогенерации `0x41edd3` в рознице **мёртвая** (сработает
только при отсутствии записи).

Автогенератор (на случай отсутствия файла), доказан кодом:

```
out.r = in.r >> 2          ; 0x41EE00  sar eax,2
out.g = in.g/2 + 0x10      ; 0x41EE20  sar edx,1; add edx,0x10
out.b = in.b/2 + 0x0a      ; 0x41EE41  sar ecx,1; add ecx,0xa
```

### 2.2. Как переключается

Переключение — **не смешивание**, а подмена указателя `[0x83d2c4]`, и
происходит в двух местах кадра:

```
447950  cmp DWORD PTR [esi+0x81c250],7   ; action_state == 7 ?
44795A  ...
447962  test BYTE PTR [esi+0x81c240],8   ; игрок под водой?
44796B  mov ecx,[0x83d2c4]
447971  mov eax,0x83d640                 ; WATERPAL
447976  cmp ecx,eax / je -> готово
44797A  jmp 44798B
44798B  mov [0x83d2c4],eax               ; подмена
447990  mov [esp+0x10],1                 ; «палитра менялась»
```

и мировой проход: `0x449f4d` (первый вид) и `0x449fa3` (второй вид) с тем же
тестом бита `0x8` и теми же записями `[0x83d2c4] = 0x83d640` / `0x83d320`
(проверка `action_state` там тоже есть — `0x449f45`/`0x449f9d`, шаблон как у
`0x44795a`).

В конце кадра флаг «менялась» проверяется и палитра ставится через яркость:

```
449EBA  cmp DWORD PTR [esp+0x10],edi(0)
449EBE  je  ...
449EC0  call 0x4847b0      ; -> 0x40c7d0([0x83d2c4], p) -> 0x407220 SetEntries
```

То есть подводная палитра **не** идёт напрямую в DirectDraw: она проходит
через общий путь яркости (0..3, подмешивание белого), как и обычная.

### 2.3. Чего в эффекте нет

* **Нет затухания/перехода**: `[0x83d2c4]` меняется на `WATERPAL` одним
  присваиванием, обратной интерполяции палитр в кадре нет (единственный
  модулятор — `0x4847b0` по уровню яркости).
* **Нет тумана/глубины**: `SET_CAMERA_HAZE` — отдельный белый оверлей
  (`docs/SCREEN_FX.md` §1), к воде не привязан; в кадре `haze = 0`.
  Единственные `SET_CAMERA_HAZE` под `IF SOURCE_UNDERWATER` — это **не**
  всплеск при входе, а ветка взрыва/смерти (см. §4.4).
* **Нет учёта глубины**: палитра включается по факту «сектор типа 1».

Гипотеза (не проверено): при split-screen палитра глобальная, поэтому при
разном состоянии двух видов итог зависит от порядка обхода
(`0x449f4d`/`0x449fa3`); кто «побеждает» — не трассировано.

## 3. Звук: фильтра нет

### 3.1. Что есть вместо фильтра

Единственная «водоподобная» механизма в звуке — сдвиг громкости по флагам
**сектора**, а не игрока. Три цикла разбора 3D-очереди считают его одинаково:

```
46BCC6  mov esi,[esi+0x81c27c]      ; сектор слушателя
46BCE5  test al,0x2 / je +3 / inc [ebp+0x10]
46BCEC  test al,0x4 / je +3 / inc [ebp+0x10]
```

`n = база + бит2 + бит4`; база — аргумент вызывающего (в кадре `0x447935`
пушится `ebp = 0`, поэтому `n ∈ {0,1,2}`). Далее:

```
46BDA4  fld [esi-0x1c]        ; atten
46BDA9  fmul [esp+0x20]       ;   * 2^n
46BDBB  fsubp                 ; volume - atten*dist
46BDC2  mov ecx,[ebp+0x10]
46BDCB  add ecx,ecx           ; cl = 2n
46BDCD  sar edi,cl            ; gain >>= 2n
```

Итого: бит `0x2` или `0x4` → `atten *= 2` и `gain >>= 2` (÷4 по громкости);
оба бита → `atten *= 4`, `gain >>= 4` (÷16). Это **только громкость**, без
изменения спектра. Те же три места: `0x46bce5`, `0x46c193`, `0x46c422`
(`docs/RECORDS.md` §2.2). Отдельно бит `0x8` флагов сектора вообще исключает
сектор из выбора ambient-сэмпла (`0x46c652`, `test [esi+4],0x8`).

### 3.2. Почему это не «подводное» в поставке

Прогон по всем 36 `.sbt`: команда `SET_SECTOR_FLAGS` (опкод 14) — 115 сайтов,
из них со значением, у которого есть бит `0x2`/`0x4`, — **95**, и **ни один**
не адресует сектор типа «вода» (`kind == 6`): все — `kind 0`
(`level16`: 78 сайтов со значением `6`, `level12`/`level13`: `10/14/31`).
Скрипты вообще не читают эти биты: `SOURCEPLAYER_SECTOR_FLAGS` встречается
165 раз и **всегда с маской `2`** (бит «сектор наносит урон»), не `4/8`.
Значит, в розничных уровнях сдвиг громкости по воде не включается; он
включается в «глухих/повреждающих» зонах (`level16` и т.п.) — назначение
битов `0x2/0x4` остаётся гипотезой (в `docs/AUDIO_3D.md` §10 она и помечена
гипотезой).

### 3.3. Отрицание: где фильтра нет (перечень проверенного)

1. **Запись голоса** `0x84e068 + i*0x50` (i = 0…8) — 20 двордов, все
   именованы: `remaining, sample_id, step_hi, step_lo, cursor, right_offset,
   loop_start, loop_len, format, prev_vol_l, prev_vol_r, vol_l, vol_r,
   music_a/b/c, acc_l, level_l, acc_r, level_r`
   (`docs/SOUND_FIELDS.md` §3). Слота коэффициента/среза/состояния фильтра в
   записи нет: `20*4 == 0x50` — вся запись занята.
2. **Микшер** `0x409330` и декодеры: SOU0 — таблица `0x858000`
   (`volume*256 + byte`), SOU1 — дублирование слотов (`0x852b40/0x852c00/
   0x852cc0`), SOU2 — бит-поток `0x852d80` + polyphase `0x8534c0`. Ни одного
   рекурсивного/биквадратного звена, ни истории сэмплов — фильтровать нечем.
3. **Чтения состояния игрока в звуковом коде** (`0x409000..0x40f000` и
   `0x46a000..0x46f000`), ровно 9 адресов:
   `0x46a64e, 0x46a799, 0x46afb4` (сектор → ambient/секторный звук),
   `0x46bb0e` (`action_state`), `0x46bcc6` (сектор → биты 2/4),
   `0x46bef6` (`action_state`), `0x46c174`, `0x46c404` (сектор → биты 2/4),
   `0x46ee4d` (флаг `0x1000`). **Ни один** не тестирует бит `0x8`; в
   `0x46bb27` тест — `0x40` (`f6 06 40`), это флаг столкновения, не вода.
   `--self-test` проверяет и множество адресов, и отсутствие теста `0x8`.
4. **Запрос звука** `0x4cabd8` (8 полей: `queued, class, sample_id, volume,
   pan, rate, priority, flags`) и очередь `0x62ce18` (10 полей) не содержат
   ни «underwater», ни множителя: громкость приходит из скрипта/формулы
   `0x46bdc2`. Глобального «подводного» множителя нет.
5. **Скрипты**: ни одной команды с `WATER` в имени
   (`gm/sbtvm.COMMANDS`), кроме условий 47/48; «водяные» сэмплы — обычные
   `PLAY_*` с другими id/громкостями (§4.5).

### 3.4. Что реально звучит в воде

* **Вход/выход** — событие шасси (§1.3): `event_post(-30062)` на входе и
  `event_post(901010)` на выходе. Обработчик ищется по таблице событий уровня
  (`0x479960` → `0x45fa00`, таблица id `0x5e4680` / offset `0x616658`), т.е.
  звук задаётся данными уровня, а не движком.
* **Всплеск** — сэмплы `splash` (вход) и `splash3` (выход), обычный
  `PLAY_SAMPLE_AT_SOURCE(sample, volume, rate, priority)`: например `level0`
  вход `[81, 64, 22050, 10000]` (0x81bb), выход `[82, 51, 16000, 3000]`
  (0x85a1). Раскладка по уровням — `--scripts`.
* **Секторный ambient** — у воды может быть свой `SET_SECTOR_SOUND(L, sample,
  count, param)`; в поставке таких секторов 8: `level11` 16/17 (`thumoil`),
  161 (`c-pc`), 189 (`doorf1st`); `level15` 93 (`selectm`); `level4` 33 и 169
  (`selectm`), 166 (`exp1s`, `count 85`, `param 0.9`).
* Сэмпл `amunderw` (`AM UNDERW…`) — это **музыкальный трек** уровня
  (`PLAY_MUSIC(8)` под `SOURCE_IS_LOCAL_PLAYER_ONE`), а не звук воды; как
  секторный ambient он стоит лишь в `level1` (сектор 22) и `level7`
  (16/17/21/22), причём эти секторы не типа «вода».

## 4. Корпус

Прогон `python3 tools/re/underwater.py --scripts` (36 `.sbt` + 36 `.sbw`,
только чтение). Итоговые числа закреплены в `--self-test`.

### 4.1. Условия

| что | число |
|---|---:|
| уровней `.sbt` | 36 |
| `SOURCE_UNDERWATER` (IF/EVAL) | **690** (17…23 на уровень) |
| `SOURCEPLAYER_UNDERWATER` | **72** (ровно 2 на уровень) |

Условие 48 стоит в каждом уровне (код общий), даже там, где статической воды
нет: скрипт один и тот же шаблон, вода появляется только на 17 уровнях.

### 4.2. Где вода в геометрии

| что | число |
|---|---:|
| уровней со статической водой (`kind == 6`) | **17** |
| секторов типа «вода» | **133** |
| всего секторов | 5104 |

Уровни: `dm1, dm3, dm4, level2, level3, level4, level5, level8, level10,
level11, level14, level15, level17, level18, level19, level20, level21`
(больше всего — `level11` 25, `level4` 24, `level14` 14, `level21` 12).
`.sbw` не хранит отдельного «water bit»: вода — это `Sector.kind == 6`
(`gm/sbw.py`), т.е. тип 1 в записи мира.

Вода бывает и **динамической**: `SET_HANDLESECTOR_TYPE` меняет тип на 1 и
обратно. В `level4` тег `33` → секторы `[31, 32, 34]` (`0xf56d` → тип 1;
`0xf5a4` → 0), тег `44` → `[136, 138, 140]` (`0xf64a` → 1; `0xf68a`,
`0xf6cb` → 0); все шесть в `.sbw` статически `kind 0`. Между командами стоят
`SLEEP`/`GENERATE`, т.е. это сценарий затопления/осушения. Другие уровни
меняют тип на 2/3/4 (`level11:270,271` — 63 сектора, `level12:2`,
`level15:5`, `level23:102`) — это не вода.

### 4.3. Вода в скриптах: зачем условие 48

`IF SOURCE_UNDERWATER` в поставочных данных — это «мой (источника) сектор —
вода». Типичные ветки (по `level0`):

| off | что делает ветка |
|---|---|
| `0x3a4f` | другой спрайт всплеска + `PLAY_SAMPLE_AT_SOURCE(13,…)` + `GENERATE` |
| `0x4e1f`, `0x4ff5`, `0x5361`, `0x5540`, `0x56f5`, `0x58dd` | подводные варианты выстрелов (`FIRE_SOURCEPLAYER_*`, другие id/углы) |
| `0x522d` | другой спрайт у WeaponPoint + `PLAY_SAMPLE_AT_SOURCE(29,…)` |
| `0x6880`, `0x6a30`, `0x6d47`, `0x6e96`, `0x7761`, `0x79cb` | взрывы под водой (свои спрайты/сэмплы/урон) |
| `0x6f92` | ветка **взрыва/смерти**: `SET_CAMERA_HAZE(1.0, 0.005)` + выпадение предметов |

То есть 48 — не «состояние игрока», а «сектор источника», поэтому она
работает и для снарядов/мин/бочек, а не только для машины игрока.

### 4.4. `SET_CAMERA_HAZE` под водой: 36 сайтов, но это не вход в воду

`--scripts` находит ровно **36** сайтов `SET_CAMERA_HAZE` с объемлющим
`SOURCE_UNDERWATER` — по одному на уровень, все со значениями `(1.0, 0.005)`.
Но контекст — блок взрыва/смерти: в `level0` (0x6f92) внутри стоят
`ADD_ITEM_AT_SOURCE_FIXED` (выпадение предметов), `PLAY_SAMPLE_AT_SOURCE(66…)`
= `exp4n`, `CAUSE_BLAST_RADIUS_DAMAGE`, а непосредственно перед блоком —
`GENERATE` трупа и `SOURCEPLAYER_DELETE` (0x6f8b/0x6f90). Значит это
«игрок погиб в воде → белая вспышка + всплеск», а не эффект входа.

**Поправка к `docs/SCREEN_FX.md` §1.6**: строка «`IF SOURCE_UNDERWATER` →
`1.0, 0.005` — всплеск при входе в воду» описывает смерть/взрыв под водой.
Входа в воду в скриптах нет: вход обрабатывает движок (§1.3) и он не ставит
haze.

### 4.5. Звук в данных

| что | число |
|---|---:|
| `SET_SECTOR_SOUND` на статических водных секторах | 8 |
| `SET_SECTOR_FLAGS` с битом `0x2/0x4` | 95 сайтов, на воде — **0** |
| `SOURCEPLAYER_SECTOR_FLAGS` | 165, маска всегда `2` |

Вход/выход воды по таблице уровня: `-30062` → первый `PLAY_*` — `splash` в
**33/36** уровней; исключения `dm2`, `level15`, `level2`, где тот же id
указывает на блок «HEADLIGHT OFF»/«FLIGHT PACKS ON» (т.е. всплеска на входе
там нет — данные так связали id). `901010` → `splash3` в **36/36**.

> Статус этой связи: id и вызов `event_post` — код (0x444FDB/0x444F7A);
> сопоставление id → блок взято из таблицы хэндлов записи 11 уровня
> (колонки: id, offset). Цикл загрузки этой таблицы в рантайм
> (`0x5e4680`/`0x616658`) до байта не прослежен — поэтому «33/36 splash»
> помечаем как **данные**, а не как доказанный рантайм.

## 6. Что нужно нашему движку

### `vm`

* `SOURCEPLAYER_UNDERWATER` (47) — `player.flags & 0x8`;
  `SOURCE_UNDERWATER` (48) — `world.sector(source_sector).type == 1`
  (`kind == 6`). Оба уже выразимы через `VmState`/`world_sectors`
  (`docs/RECORDS.md` §2.2): нужен только геттер типа сектора.
* Писатели флага — в тик физики игрока: `sector = player.sector`,
  `in_water = (sector_type(sector) == 1)`; на переходе — событие
  `player.chassis.events[water_enter/exit]` (поля P21/P22), если не 0.
* `SOURCEPLAYER_SECTOR_FLAGS` (49) — `(sector_stuff[player.sector].flags & mask)
  == mask` (маска в данных всегда 2). Закрывает одно из «open» условий.

### `render`

* Хранить `GAMEPAL` и `WATERPAL` как **6-битные** таблицы (`>>2` при загрузке,
  `<<2` при выводе) и указатель «текущая»; переключать в конце кадра.
* Наш рендер сейчас разворачивает индексированные текстуры в RGBA при
  загрузке (`sbm_to_rgba(level, palette_)`, `engine/src/render/render.cpp`).
  Для подмены палитры нужен либо счётчик поколения палитры, сбрасывающий
  кэш текстур, либо хранение индексов и выборка цвета на блите. Второе
  ближе к оригиналу и дешевле по памяти.
* Яркость 0..3 применять тем же проходом, что и сейчас (подмешивание белого,
  пивот 63), до `SetEntries`/вывода.
* Никакого фейда и haze на входе в воду не добавлять — в оригинале их нет.

### `audio`

* Ничего «подводного» не добавлять: low-pass/фильтр/питч в оригинале
  отсутствуют (см. §3.3). Если понадобится паритет по громкости — реализовать
  ровно сдвиг `atten *= 2^n`, `gain >>= 2n` по битам `0x2/0x4` флагов
  **сектора слушателя** (сейчас у нас этого нет; в поставке на воде не
  встречается, но код общий).
* События воды — не звук движка: это `event_post(id шасси)`; наш `vm` должен
  уметь запускать скрипт по id, а звук возьмётся из `PLAY_SAMPLE*`.

## 7. Доказано / гипотеза / осталось

### Доказано (код)

* флаг: `+0x3200` бит `0x8`; писатели `0x444FD2`/`0x444F74`, других нет
  (скан 161 обращения к `0x81c240`); загрузка сейва бит не восстанавливает
  (`0x464C25`, маска `0x11d400`);
* источник — `player+0x323c` (слот 0 `0x81c27c`), тип сектора `kind/6`
  (`0x42d99f`), сеттер `type*6` (`0x42d9d5`);
* условия 47/48 — байты и арифметика (§1.5); 48 читает сектор источника;
* вода в физике: скорость ×0.75, вертикальная −2.4, порог удара ×0.5,
  события `-11`/`-10`, `damage_player(type 4)`;
* переходы: `event_post(player+0x340c)` / `event_post(player+0x3410)`;
* палитра: загрузчики `0x44af78/0x44afa3` → `0x47efe0` (6 бит),
  переключатели `0x447962/0x449f4d/0x449fa3`, применение в конце кадра
  `0x449ec0` → `0x4847b0`; автогенерация `0x41edd3`
  (`R>>2, G/2+16, B/2+10`);
* звук: сдвиг по битам `0x2/0x4` (`0x46bce5/0x46c193/0x46c422`,
  `atten*=2^n`, `gain>>=2n`); бит `0x8` — исключение из ambient (`0x46c652`);
  в звуковом коде нет чтения бита `0x8`, в записи голоса нет фильтра.

### Доказано (данные)

* 36 уровней, 690 `SOURCE_UNDERWATER`, 72 `SOURCEPLAYER_UNDERWATER`;
* 17 уровней и 133 сектора статической воды; динамическая вода — `level4`
  теги 33/44 (секторы 31/32/34 и 136/138/140, статически `kind 0`);
* 36 сайтов `SET_CAMERA_HAZE(1.0, 0.005)` под водой — блок смерти/взрыва;
* 95 сайтов `SET_SECTOR_FLAGS` с битом `0x2/0x4`, на воде — 0;
* `WATERPAL` есть в `FRONTEND/BMP.IDX` (1142 Б, 8 bpp), сине-зелёная,
  отличается от `GAMEPAL` во всех 256 слотах.

### Гипотеза

* смысл битов `0x2/0x4` флагов сектора («глухая зона»/урон) — назначение не
  доказано, доказана только формула громкости;
* split-screen и подводная палитра: глобальный указатель, порядок видов не
  трассирован;
* соответствие id `-30062` → блок `splash` (33/36) — из таблицы хэндлов
  уровня, рантайм-регистрация не прослежена;
* «вода как объём»: тип сектора помечает весь сектор, отдельного уровня
  жидкости/глубины в `.sbw` нет (совпадает с `docs/FORMATS.md` §10.1).

### Осталось

* трассировать загрузчик таблицы событий `0x5e4680`/`0x616658` (какая запись
  `.sbt` её наполняет) — тогда «33/36 splash» станет кодом;
* проверить в оригинале, меняется ли палитра при `action_state == 7`
  (код говорит «нет», наблюдения нет);
* уточнить, что делают биты `0x2/0x4` в `level16` (78 секторов) — возможно,
  это и есть «подводный тоннель» без типа воды.

## 8. Расхождения с master-доками (для интегратора)

1. `docs/PLAYER_FIELDS.md` §10: `+0x323c` назван `model_id`; по коду это
   **индекс текущего сектора** (диапазон `0..0xff`, индекс `SECTOR_STUFF`,
   слот сектора у `event_post`). Абсолютный адрес `0x81c27c` в
   `SECTOR_STUFF.md`/`WORLD_FIELDS.md` — верный.
2. `docs/SCREEN_FX.md` §1.6: 36 сайтов `SET_CAMERA_HAZE(1.0, 0.005)` под
   `SOURCE_UNDERWATER` — это смерть/взрыв под водой, а не всплеск при входе.
3. `docs/VM_EXEC.md`: условия 47/48 можно перевести из `open` в `value`
   (47 — `flags & 8`, 48 — `type(source sector) == 1`); 49 —
   `(sector_flags & mask) == mask`.
4. `docs/PLAYER_FIELDS.md` §10: бит `0x8` поля `+0x3200` подписан
   «бездорожье / в воздухе»; у бита ровно два писателя (`0x444FD2`/`0x444F74`),
   и оба срабатывают только по `тип(сектор игрока) == 1`, поэтому бит —
   «в воде», а «в воздухе» его поставить некому. Эффекты (скорость ×0.75,
   пропуск демпфирования подвески) — это сопротивление воды.
5. Подсказка «строка `0x4aab6b`» — опечатка: `0x4aab6b` лежит в области
   `0xff`-заполнения (не строка); строка —
   `0x4abb5c` (`"Unable to load underwater palette …"`).
6. Подсказка «коллизия с водой `0x4ac27b`/`0x4ac2b0`» — это `.rdata`:
   `0x4ac27b` внутри `"door_loadbin(): Error loading door info."`,
   `0x4ac2b0` внутри `"…number of switches reached (%d)."`; к воде отношения
   нет. Коллизия воды — обычный путь `FUN_00443690` (§1.4), отдельной функции
   нет.
