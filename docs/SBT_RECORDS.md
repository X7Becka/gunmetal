# Все типы записей `.sbt`: раскладка, писатели, побайтовая проверка

Документ закрывает **весь** поток записей `.sbt` (не только `SECTOR_STUFF`/
`ITEM`/`LIFT`, см. `docs/RECORDS.md`): диспетчер типов, полевое устройство
каждого типа, структурные писатели в `gm/sbt.py` и проверку
`parse -> rebuild` на поставке.

* **Код:** `gundx.exe`, ImageBase `0x400000` (дизассемблер —
  `tools/re/disrange.py`, xref — `tools/re/xref.py`, PE — `tools/re/exelib.py`).
* **Данные:** 36 уровневых `*.sbt` + `SAVEGAME/saved0.sbt`, `saved1.sbt`
  (только чтение, `/mnt/d/games/Gunmetal 3dfx`).
* **Инструмент:** `tools/re/records.py --check`.
* **Статус:** `parse -> rebuild` **38/38 файлов побайтово**, **289/289
  записей** (уровни + цепочка состояния сейвов).

## 1. Диспетчер: где доказан номер типа

Бинарный загрузчик читает один байт типа и прыгает через две таблицы:

```
0x455162  mov edx,[esp+0x10]      ; прочитанный байт
0x455166  and edx,0xff
0x45516c  lea eax,[edx-1]
0x45516f  cmp eax,0xfe            ; 0 и >255 отсекаются
0x45517c  mov cl,[eax+0x455658]   ; байтовая таблица индексом типа-1
0x455182  jmp [ecx*4+0x455604]    ; таблица обработчиков
```

Следовательно, `type -> handler` — не догадка, а данные самого бинарника.
Таблица ниже снята `tools/re/savegame.py`-совместимым разбором
`0x455604`/`0x455658`; адрес — первая инструкция обработчика.

| тип | имя | обработчик | предел/формат | писатель |
|---|---|---|---|---|
| 1 | `SWITCH` | `0x44f000` | `u32 n ≤ 0x200`, `n × 0x20` | `0x44f0a0` (save-цепочка) |
| 2 | `DOOR` | `0x44e540` | `u32 n ≤ 100`, `n × 0xB8` | `0x44e250` создатель `ADD_DOOR` |
| 3 | `THING` | `0x46fd90` | `u8 exists`, если ≠0 — `0x528` | — (в уровне не пишется) |
| 4 | `THING_TYPES` | `0x47e000` | `u32 n ≤ 0x80`, `n × 936` | `0x47cb6c` (из `.soe`) |
| 5 | `NAMED_ITEMS` | `0x468ef0` | `u32 n ≤ 0x31`, `n × 52` | `0x4689f0` (из `.soi`) |
| 6 | `SPRITES` | `0x4564b0` | `u32 n < 0x1F4`, `n × 44` | — |
| 7 | `SOUND_SOURCES` | `0x46b280` | `u32 n < 0x80`, 5 колонок `u32` + колонка `f64` | `0x46b41b` (save-цепочка) |
| 8 | `SECTOR_STUFF` | `0x46b7b0` | ровно `0x5800` (256 × 0x58) | `0x46b7f0` |
| 9 | `PLAYER_STATUS` | `0x451c20` | `u8 exists`, если ≠0 — `0x3510` | `0x452020` (save-цепочка) |
| 10 | — | `0x4971b0` (`or eax,-1; ret`) | **заглушка, payload не читается** | — |
| 11 | `SCRIPT` | `0x462a80` | `u32 c` (`c×40`) + `u32 n` (`3×n×4`) + `u32 m` (`m`) + `u8 flag` (+`9×0x400`) | — |
| 12 | `SOUND_SAMPLE_TABLE` | `0x40b670` | `300×u32` + `300×9` имён (`0x4B0+0xA8C`) | — |
| 13 | — | `0x4971b0` | **та же заглушка, что 10** | — |
| 14 | — | `0x4555ae` | ошибка `World Things file (%s) corrupt` `0x4acac8` | — |
| 15 | `POLY_HANDLE` | `0x4633a0` | `u32 n < 0x1F4`, 4 колонки `u32` | — |
| 16 | `OBJECT_HANDLE` | `0x463680` | `u32 n < 0x12C`, 3 колонки `u32` | — |
| 17 | `SECTOR_HANDLE` | `0x463900` | `u32 n < 0x100`, 2 колонки `u32` | — |
| 18 | `LIFT` | `0x44ec20` | `u32 n ≤ 0x1E` (`n×0xA8`) + `u32 k ≤ 0xC8` (3 колонки `u32`) | `0x44eed0` |
| 19 | `ITEM` | `0x468df0` | ровно `0x7080` (300 × 0x60) | `0x468ea0` |
| 20 | `SOB_TABLE` | `0x47c7c0` | `u32 n ≤ 0xC8`, `n × 20` | — |
| 255 | `END_OF_FILE` | `0x455189` | конец потока, payload нет | — |

«Писатель» в таблице — только те адреса, которые удалось подтвердить
дизассемблером (создатель записи или save-писатель). Прочерк означает, что
поля записи читаются/проверяются, но отдельная функция-писатель в этом
билде не локализована (файл уровня собирается редактором-компилятором, а не
движком).

Типы **10 и 13** диспетчер принимает, но обработчик `0x4971b0` — это
`mov eax,-1; ret`: полезной нагрузки у них нет. В поставке они не
встречаются; `gm/sbt.py` считает их неподдерживаемыми и падает с ошибкой, а
не «съедает» байты. Тип **14** — явная ошибка «corrupt», не запись.

## 2. Полевое устройство

### 2.1. `SWITCH` (1) — 32 байта, 8 × i32

`ADD_SWITCH` (опкод 183, `0x45b6ff` → `0x44e5f0`) копирует восемь операндов
**дословно** в массив `0x5a4af0` (шаг `0x20`, счётчик `0x5a945c`):

| +0x | поле | смысл | доказательство |
|---|---|---|---|
| 0x00 | `kind` | 0 обычный, `0x101` transformed, `0x102..0x104` source | `0x44f960` |
| 0x04 | `id` | id сущности для `GENERATE` (`0x479960`/`0x479810`) | код |
| 0x08 | `radius` | радиус триггера kind `0x102..0x104` | `0x44fb9e` |
| 0x0C..0x14 | `pos.x/y/z` | позиция триггера (мировая система движка) | `0x44f960` → `0x479960` |
| 0x18 | `aux` | вспомогательный звуковой аргумент | гипотеза |
| 0x1C | `sound` | индекс сэмпла, `-1` = тишина | `0x44f...` |

В уровнях типа 1 нет: переключатели создаются скриптом; в сейвах — блок 1
(в поставке `saved0/1` блока 1 нет, как и дверей).

### 2.2. `DOOR` (2) — 184 байта

`ADD_DOOR` (опкод 184, `0x459b5b` → `0x44e250`) **переставляет** операнды в
массив `0x8381a0` (шаг `0xB8`, счётчик `0x5a9450`, ≤100).

| +0x | поле | тип | смысл |
|---|---|---|---|
| 0x00 | `box[0..8]` | 9 × f64 | закрытый угол, открытый угол, размер |
| 0x48 | `delta[0..2]` | 3 × f64 | дельта движения бокса за тик (`0x450054`) |
| 0x60 | `const` | f64 | `0.03`, писатель `0x44e460`, читателя нет |
| 0x68 | `flags` | i32 | младший ниббл 1..3, бит `0x40` — used (`0x45068d`) |
| 0x6C..0x7C | `ids[0..4]` | 5 × i32 | id сущностей; `GENERATE` `0x44f6c0`, `0x44fc78` |
| 0x80 | `state` | i32 | `-1` закрывается, `0` закрыта, `+1` открывается |
| 0x84/0x88 | `sector`/`object` | i32 | адрес створки в `.sbw` (`0x434419`) |
| 0x8C/0x90 | `phase_prev/next` | u32 | фаза анимации до/после тика |
| 0x94 | `step` | i32 | приращение фазы за тик |
| 0x98/0x9C | `param5/6` | i32 | операнды L6/L7, читателей нет |
| 0xA0 | `v[0..2]` | 3 × i32 | операнды V хвоста `VNVNVN` — гипотеза |
| 0xAC | `n[0..2]` | 3 × i32 | операнды N хвоста `VNVNVN` — гипотеза |

### 2.3. `THING` (3) — `u8 exists` + `0x528`

В **уровневой** записи загрузчик `0x46fd90` читает один флаг и, если он
ненулевой, ровно одну запись `0x528` в массив `0x7ac080` (шаг `0x528`,
инициализация 260 слотов). Это «прикреплённый спрайт игрока»; внутренние
поля `0x528` — runtime-состояние, в карту не входят.

⚠️ **Блок 3 сейва — другой формат:** 260 × (`u8 present` +
`[0x528]`), см. `docs/SAVE_FIELDS.md` §10. `records.py --check` разбирает его
отдельной функцией `decode_things`, а не как запись типа 3.

### 2.4. `THING_TYPES` (4) — 936 байт

```
char name[16];      // +0x000
double params[49];  // +0x010 .. +0x198
u32 tail[132];      // +0x198 .. +0x3A8
```

* `+0x1A4` (`tail[3]`) — индекс в `SOB_TABLE`: доказано загрузчиком
  `thing\<name>.soe` (`0x47cb6c` → `0x47c9b0` → `[936·i+0x776f04]`) и
  проверено на 2896/2896 типах (`tools/re/thing_models.py`).
* Остальной `tail` — флаги/id, opaque; сохраняется байтами.
* Потребитель модели — `0x46d0a0` → `0x46d8b0` → `0x47c990`/`0x4277cd`.
* Имя хранится полным 16-байтным слотом (`name_raw`): после NUL в поставке
  встречаются байты, поэтому `encode_payload` их не нормализует.

### 2.5. `NAMED_ITEMS` (5) — 52 байта

`char name[16]` + 9 × u32. Загрузчик `0x4689f0` читает текстовый
`item\<name>.soi` форматом `%ld %ld %s %ld %s %ld %s %ld %ld`; три `%s`
резолвятся `0x45fb90`, числа ложатся в `+0x10..+0x30`.
`ADD_NAMED_ITEM[_EX]` (`0x459a78`/`0x459ac0` → `0x468d40`) передаёт
`f2→ITEM+0x38, f3→+0x3C, f4→+0x40, f5→+0x44, f6→+0x48, f7→+0x4C,
f8→+0x50/+0x54`.

### 2.6. `SPRITES` (6) — 44 байта

| +0x | поле | тип | смысл | xref |
|---|---|---|---|---|
| 0x00/0x04 | `scale_x/y` | f32 | масштаб | `0x456164`/`0x456173` |
| 0x08 | `runtime_object` | u32 | устаревший указатель, пересоздаётся `0x436685` | `0x456556` |
| 0x0C..0x14 | `x/y/z` | i32 | мировая позиция | `0x456136/40/4a` |
| 0x18 | `param` | u8 | байтовый render-параметр (α/яркость?) | `0x45615e` — гипотеза |
| 0x19..0x1B | pad | 3 B | выравнивание, в сейвах 0 | данные |
| 0x1C | `flags` | u32 | render-флаги (0/2/4) | `0x456001` — гипотеза |
| 0x20 | `effect_id` | i32 | id модели/эффекта | `0x456130` → `0x4360f1` |
| 0x24 | `param16` | u16 | 16-битный render-параметр | `0x456179` |
| 0x26..0x27 | pad | 2 B | нули в поставке | данные |
| 0x28 | `spawn_time` | u32 | часы уровня на момент создания | `0x456185` |

### 2.7. `SOUND_SOURCES` (7) — 5 × u32 + 1 × f64

Колонки (не массив структур!), порядок доказан `ADD_SOUND_SOURCE`
(`0x459c6e` → `0x46b210`) и писателем сейва `0x46b41b`:

```
x[0x800340] y[0x800540] z[0x800140] volume[0x7ffd40] sample[0x7fff40]
pitch[0x800760, f64]
```

| колонка | смысл | создатель | потребитель |
|---|---|---|---|
| 1 | `x` | `0x46b23e` | позиция |
| 2 | `y` | `0x46b250` | позиция |
| 3 | `z` | `0x46b25b` | позиция |
| 4 | `volume` | `0x46b26d` | громкость |
| 5 | `sample` | `0x46b266` | индекс `SOUND_SAMPLE_TABLE`, читает `0x46b602` |
| 6 (f64) | `atten` (бывш. «pitch») | `0x46b249` | **затухание на единицу расстояния**; читает `0x46b616` (`docs/AUDIO_3D.md` §2.2) |

**Поправка 2026-10-23** (`docs/AUDIO_3D.md` §2): шестая колонка — это
`atten` на единицу, а не питч: у скриптовых источников она зашита
`0x3f9eb851eb851eb8` = `0.03` (`0x46b8ad`/`0x46b8b7`), а `0x46b616` кладёт её
в поле затухания запроса. Порядок **операндов** опкода `ADD_SOUND_SOURCE`
(`0x459c6e`) — `x, y, z, sample, volume, atten`; порядок **колонок в памяти**
— `x, y, z, volume, sample, atten` (базы выше). У
`PLAY_FRAME_LOOP_SAMPLE_AT_SOURCE` сигнатура `LENVL` =
`(event_hi, event_lo, sample, volume, priority)`, rate фиксирован 11025.

### 2.8. `SECTOR_STUFF` (8) — 256 × 0x58

Полевая карта и потребители — `docs/RECORDS.md` §2. В `gm/sbt.py` добавлен
`SectorSlot` (все 0x58 байт, включая паддинги `+0x42/+0x46`), поэтому блок
пересобирается из полей, а не из сырых байт.

### 2.9. `PLAYER_STATUS` (9) — `u8 exists` + `0x3510`

Загрузчик `0x451c20` читает флаг, затем структуру
`0x81c240..0x81f750`; поля структуры (позиция, углы, история 240×3,
броня/щиты, оружие/патроны) доказаны в `docs/SAVE_FIELDS.md` §9.2.
В `gm/sbt.py` запись хранится как `exists + raw 0x3510`: поля читаются
`records.py`/`savefile.py`, но контейнер не «нормализует» runtime-массив.

### 2.10. `SCRIPT` (11), `SOUND_SAMPLE_TABLE` (12)

* **11**: `u32 c` + `c×40` things + `u32 n` + три колонки `n×4` + `u32 m`
  + `m` байт кода + `u8 flag` (+ `9×0x400`). Полностью разобран в
  `gm/sbtvm.py`; `Script.encode()` пишет те же сегменты.
* **12**: `300×u32` счётчиков + `300` имён по 9 байт. `SampleTable.name_slots`
  хранит точные `0xA8C` байт (после NUL бывают хвосты); `names` — удобное
  представление. Все 5800 непустых имён резолвятся в `sounds/SOU.IDX`.

### 2.11. `POLY_HANDLE` (15), `OBJECT_HANDLE` (16), `SECTOR_HANDLE` (17)

Колонки, не массив структур:

```
15: tag, sector, object, poly   (4 колонки, n < 0x1F4)
16: tag, sector, object         (3 колонки, n < 0x12C)
17: tag, sector                 (2 колонки, n < 0x100)
```

Загрузчики `0x4633a0`/`0x463680`/`0x463900` читают каждую колонку в свой
глобал (`0x5b21f8`, `0x618b88`, `0x5e5680`, `0x6183b8` и т. д.).
`(sector, object, poly)` — адрес для `resolve_poly` `0x434463`; `tag` —
редакторский id для `SET_HANDLEPOLY_*`/`SET_HANDLESECTOR_*`, не уникален.
Проверка по `.sbw`: 4277/207/900 попаданий (см. `docs/FORMATS.md` §12.1).

### 2.12. `LIFT` (18) — `n×0xA8` + 3 колонки остановок

Загрузчик/писатель `0x44ec20`/`0x44eed0`: `u32 n ≤ 30`, `n` записей по
`0xA8` в `0x836de0`, `u32 k ≤ 200`, затем три **параллельные** колонки
`u32[k]` (`0x5a9130` floor/button id, `0x5a8e10` высота с клампом `0xffff`,
`0x5a8af0` звук/эффект). Поля записи — `docs/RECORDS.md` §4. В поставке
записей типа 18 нет; проверка только кодовая + синтетическая.

### 2.13. `ITEM` (19) — 300 × 0x60

Полевая карта — `docs/RECORDS.md` §3. `ItemSlot` в `gm/sbt.py` покрывает все
0x60 байт (`basis`, `position`, `runtime_object`, `kind`, `state`, операнды,
`sob_index`, `flags`, паддинг `+0x59..+0x5B`, sentinel `0xFFFF`).
Создатели — четыре `ADD_ITEM*` + `ADD_NAMED_ITEM*` → `0x4686a0`; потребитель
состояния — `0x468e41` (значения `-2/-1/0/-3/-4/>0`).

### 2.14. `SOB_TABLE` (20) — 20 байт

`char name[12]` + `u32 amount` + `u32 ptr`. Загрузчик `0x47c7c0` резолвит
`SOBS/<name>.sob` или `Sobanim/<name>.soo` через `0x47c990` и **перезаписывает
`ptr`** указателем модели (`0x47c845`); `amount` обратно не читается.
`name_raw` сохраняет полный 12-байтный слот.

## 3. Что пишет `gm/sbt.py`

`Sbt.rebuild()` (`gm/sbt.py`) собирает файл из 84-байтной шапки и **полей**
записей; `Sbt.to_bytes()` остаётся побайтовым round-trip из `record.raw`.
`encode_payload(type, payload)` теперь умеет все поддерживаемые типы:

| режим | типы | что структурно |
|---|---|---|
| `fields` | 4, 5, 7, 8, 11, 12, 15, 16, 17, 19, 20 | все байты из именованных полей |
| `fields (stops)` | 18 | счётчики и три колонки остановок; 168-байтные записи — raw (поля не доказаны данными) |
| `framed` | 1, 2, 6 | счётчик + точные байты записей (поля записи доказаны кодом, но не типизированы в контейнере) |
| `opaque` | 3, 9 | `exists` + неизменённые байты runtime-структуры |

`parse -> rebuild` уровней проверяется целиком (`rebuild(verify=True)`),
сейвов — по цепочке блоков `6, 19, 8, 7, 3, 9` (префикс сейва и хвост после
цепочки сохраняются дословно).

## 5. Что осталось

1. **1/2/6**: поля записи доказаны кодом, но в `gm/sbt.py` контейнер хранит
   их как точные байты; типизация `SwitchRecord`/`DoorRecord`/`SpriteRecord`
   даст «fields» вместо «framed» (данных в поставке нет, кроме 4 спрайтов в
   сейвах — они уже декодируются `decode_sprite`).
2. **3**: внутренние поля `0x528` (runtime things) не разобраны; в уровне
   запись одиночная, в сейве — 260 слотов. Границы и флаги проверяются.
3. **9**: `0x3510` хранится raw; карта полей есть в `docs/SAVE_FIELDS.md`,
   но контейнер намеренно не нормализует runtime-массив (история 240×3,
   привязки объектов).
4. **18**: ни одного поставочного экземпляра; 168-байтные записи остаются
   raw, три колонки остановок типизированы. Нужен сейв с лифтом для
   проверки полей данными.
5. **10/13**: заглушки `0x4971b0`; если появится файл с ними, это
   заведомо неполная/чужая версия — парсер обязан ругаться, а не угадывать.
6. Семантика `SWITCH +0x18`, `SPRITE +0x18/+0x1C`, `DOOR +0x98..+0x9C` —
   гипотезы (потребителей в этом билде нет).
