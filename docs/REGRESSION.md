# Регрессия: ворота, бюджет времени и практики

Как устроена защита от регрессий в `gunmetal-re`, что запускать и когда, и
какие правила нельзя нарушать, чтобы «зелёный» прогон что-то значил.
Числа — замеры на 32-ядерной машине (зеркало в `~/.cache/gunmetal-re/game`).

## 1. Слои проверок (снизу вверх)

| слой | команда | бюджет | что ловит |
|---|---|---:|---|
| self-test инструмента | `python3 tools/re/<tool>.py --self-test` | <1 с | сломанный парсер/писатель до интеграции |
| CTest quick | `ctest --preset quick` (8 потоков) | ~34 с (50 тестов) | C++: форматы, рендер, VM, сейвы |
| регресс быстрый | `python3 regress.py --mirror --json` | ~46 с | сквозной Python-оракул: 113 проверок |
| регресс полный | `python3 regress.py --full --mirror --json` | ~78–88 с, тёплый кэш ~60 с | + извлечение, писатели, VM-корпус, фильмы (121) |
| паритет | `tools/parity_*.py`, `sob_writer.py --check` | минуты | Python ↔ C++ и Python ↔ оригинал |
| fuzz/trust | входит в `regress.py` (545 кейсов) | ~2 с | границы доверия: битые входы, `--force`, выход за каталог |
| CTest всё | `ctest -j 8 --output-on-failure` | ~235 с (61 тест) | quick + тяжёлые C++-свипы SBV/паритета |

Правило: **внутренний цикл — quick, перед интеграцией — full**. `--full` без
необходимости не гонять: он в 3 раза дольше, а 90 % правок ловит quick.

## 2. Как читать результат

* Быстрый прогон печатает по строке на проверку (`[ok  ]`/`[FAIL]`) и итог.
* Для агента/CI: `--json` печатает **одну** строку
  `{"passed":113,"total":113,"seconds":45.7,"failed":[]}` — это дешевле, чем
  121 строка в контексте; при падении в `failed` лежат точные имена.
* Ненулевой exit code — единственный сигнал для CI; «почти зелёный» не
  считается.

## 3. Практики, которые уже в коде

* **Один источник данных — установка или её зеркало.** `--mirror` кэширует
  проверку свежести на 15 минут и сам пересинхронизирует при расхождении;
  результаты на установке и зеркале обязаны совпадать (проверено: 113/113 и
  121/121 в обоих режимах).
* **Файлы игры адресуются по содержимому.** `engine/tests/game_content.h`
  (генерируется `tools/re/game_content.py --write`) хранит FNV-1a64
  канонического содержимого `.sbt`/`.sbw` по манифесту установки, а
  `gmtest::resolve_game_file()` находит файл по хэшу. Переименование или
  перестановка файлов в установке больше не меняет смысл голденов;
  `game_content.py --check` печатает такие аномалии (на этой установке —
  `level1`↔`level2` и `.sbt`, и `.sbw`).
* **Регистронезависимые пути** (`gp()`): drvfs не различает регистр, ext4 —
  различает. Любая проверка, читающая файл игры, идёт через `gp()`.
* **Параллельность там, где она измерима.** `check_many` (извлечение),
  ProcessPool в `gm.py sbc` (25,7 → 4,4 с), `gm.py sounds` (28,6 → 9,6 с;
  деревья WAV побайтово совпали), `tools/re/vm_exec.py --corpus` (38,7 →
  4,0 с), `parity_film --quick` (19,3 → 1,8 с), `sou1_model.py --verify`
  (983 записи: ~10 мин последовательно → ~2 мин на 16 потоках, JSON сверен
  с `docs/manifests/sou1-fnv.json` — 0 расхождений). Потолок — 16 воркеров:
  дальше растёт RSS, выигрыш <15 %.
* **Никаких записей в игру.** Все выходы — `--out`/`build/`/`~/.cache`;
  `--force` требуется для перезаписи; проверки на это есть в `trust`.
* **Кэш результатов (только с `--mirror`).** Четыре самые дорогие «чистые»
  проверки (`sob_writer --check`, `sou_container --check`, `vm_exec --corpus`,
  `film parity`) кэшируются по ключу = SHA-256 Python-исходников (`gm.py`,
  `gm/*`, `tools/*`, `regress.py`) + digest зеркала + argv. Кэшируются только
  успешные прогоны: падение всегда перезапускается, а любая правка кода или
  данных меняет ключ, поэтому устаревшая запись ничего не скрывает. Попадания
  видны в `--json.cached`. Сброс: `--no-cache`, `GM_REGRESS_CACHE=0` или
  `rm -rf ~/.cache/gunmetal-re/regress-cache`.
* **Таймаут на проверку.** `run_raw()` ограничен 900 с
  (`GM_CHECK_TIMEOUT`): зависший парсер становится обычным падением с именем
  проверки, а не вечным зависанием CI.
* **Детерминизм.** Сортированные `glob`, фиксированные seed
  (`--seed 0x12345678` в VM), побитовые сравнения вместо «похоже», x87
  допускает 1 ulp (замкнутая форма против трассы).
* **Golden-файлы обновляет только автор изменения поведения**, в том же
  коммите, с доказательством (N/N, побайтово), иначе тест перестаёт быть
  тестом.

## 4. Чего пока нет (честный список)

* **Покрытие Python** собирается `tools/qa/coverage.py` (stdlib `trace`,
  без зависимостей): курированный набор команд, слияние по номерам строк,
  `--json`, `--min PCT`, `--full` (с извлечением). Быстрый набор даёт
  **40,4 %** (3653/9033 строк, 26 файлов); самые тёмные — `render` 13 %,
  `png` 14 %, `sou2` 14 %, `sbv` 15 %, `sob` 17 %. C++ coverage
  (`llvm-cov`) не собирается.
* **Фазз-корпус не сохраняется**: `fuzz_formats.py` генерирует кейсы в
  temp-каталоге; для ночного fuzz нужен persistent corpus + seed.
* **Единый отчёт CTest+regress** (JUnit XML) не формируется; CI-матрицы нет.
* **FNV-1a64 в `sou_container --check`** — 11 из 12,5 с чистого Python
  (последовательная свёртка). Параллелится только вместе с форматом хэша;
  цена осознанно принята.

## 5. Known failures и «внешние» падения

* Внешнее падение (подменённые в установке `level1.sbt`/`level2.sbt`) — не
  повод править код. Оно фиксируется в `docs/BASELINE.md` с точными именами
  проверок и причиной; `--json.failed` даёт тот же список машинно.
* Актуальный срез (2026-10-22): Python-регресс **113/113** (quick) и
  **121/121** (`--full`); CTest **50/50** (quick, ~34 с) и **61/61**
  (все, `-j 8`, ~235 с). Четыре прежних падения (`core`, `camera_rig`,
  `sbtvm`, `vm`) имели одну причину: в установке `level1.sbt`/`level2.sbt`
  (и `.sbw`) поменяны местами относительно манифеста (`2aa7…`/`7e6d…` ровно
  наоборот). Вылечено **адресацией по содержимому**
  (`game_content.h` + `resolve_game_file`), а не правкой голденов; `things`/
  `things_full` — тем же резолвом плюс параллельной доработкой автоматов
  движения. `tools/re/game_content.py --check` по-прежнему показывает
  4 аномалии в установке — это факт о данных, а не ошибка тестов.
* Нельзя «чинить» тест ослаблением ожидания без записи, почему ожидание было
  неверным. Ослабление допустимо только с новым доказательством (N/N,
  побайтово, эмулятор).
* Пропущенные проверки не маскируются: `--category extract` включает
  `--full` автоматически, а не молча выкидывает тяжёлое.

## 6. Быстрые команды

```sh
# внутренний цикл
python3 regress.py --category save,vm --mirror
python3 regress.py --mirror --json
ctest --preset quick --output-on-failure

# перед интеграцией
python3 regress.py --full --mirror --json
ctest --preset full --output-on-failure
python3 tools/re/gmcache.py selftest
python3 tools/re/sou_container.py --check
python3 tools/re/sob_writer.py --check
```

## 7. Что улучшать дальше (по приоритету)

1. Поднять покрытие Python по карте `tools/qa/coverage.py` (render/sbv/sob —
   через `--full`) и добавить `--min` в ночной прогон; C++ coverage.
2. Persistent fuzz-корпус + ночной прогон с новым seed.
3. Разнести `core_full` (один монолитный C++-тест) на независимые тесты,
   чтобы CTest параллелился глубже; голдены CTest привязать к содержимому
   файлов (сейчас 4 падения из-за переставленных `level1/level2.sbt`).
4. JUnit/JSON-артефакты для CI и сравнение времени по коммитам (ловить
   замедление раньше, чем оно станет привычкой).
