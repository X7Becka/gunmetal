# Рендер экрана 5 `ERROR` (`engine/src/ui/error_render.h`)

Срез 16 пункта `M8.8`: один кадр экрана **5** фронтенда (`gundx.exe`, ImageBase
`0x400000`) в RGBA-буфер 320×200. Модуль без состояния — рисует то, что ему
передали в `ErrorRenderOptions`, и отдаёт числа (`rows`, `lines`, `ink_pixels`,
`missing_glyphs`, `arrows`). Шрифты и метрики — из `render/text_layout`
(`FONTS4` в `FRONTEND/BMP.IDX`), точный fade — из `render/hud_lut`. Ничего не
измеряется заново.

Код: `engine/src/ui/error_render.h/.cpp`; тест —
`engine/tests/test_error_render.cpp` (CTest `error_render`, label `quick`).
Соседние срезы — `KEY_JAMMING_RENDER.md` (16, тоже `step 0`, но `rows 1`),
`LAY_BUCKS_RENDER.md` (20, четыре фиксированные строки), `MENU_RENDER.md`
(общая механика `0x485dd0`, палитра и клип).

Главный вывод среза: экран **показывает готовый текст из общего буфера ошибки**
`0x4aa2f8` и переносит его по словам; форматирования (`%s`/`%d`) в обработчике
нет — буфер заполняют чужие процедуры ошибок **до** перехода в состояние 5.
`rows = 0`, пунктов, курсора и стрелок нет; единственный ввод — `Esc`, который
возвращает в главное меню (состояние 1).

## 1. API

```cpp
#include "ui/error_render.h"

gm::ErrorRenderOptions options;       // чёрный холст, message = "No Error."
options.background = "PLATE";         // "" = чёрный холст
options.message = "Unable to load world file (savegame).";

std::vector<std::uint32_t> rgba;      // 0xRRGGBBAA
int width = 0, height = 0;
gm::ErrorRenderStats stats;
std::string error;
if (!gm::render_error(game, options, rgba, width, height, &stats, &error)) {
    // error: текст с префиксом "error_render: "
}
// width=320 height=200, rgba.size()==64000
// stats: rows=0 lines=4 ink_pixels=489 missing_glyphs=0 arrows=0
```

| Поле `ErrorRenderOptions` | По умолчанию | Смысл |
|---|---|---|
| `std::string background` | `""` | запись `FRONTEND/BMP.IDX` в (0,0); `"PLATE"` — панель экрана; пусто — чёрный холст |
| `std::string message` | `"No Error."` | готовый текст буфера `0x4aa2f8`, рисуется по словам (шрифт 0). Не формат: `%s`/`%d` уже подставлены до экрана (§2.4). Значение по умолчанию — образ `.data` в exe. Пустая строка = ветка `0x48ad16` (только заголовок и подсказка) |
| `bool fade_lut` | `false` | точный fade `0x682f90` по палитровым индексам |
| `int fade_lut_level` | `11` | 0..15; 11 — тождество, 12..15 светлеют |
| `std::string fade_lut_dump` | `""` | дамп 4096 Б (`load_hud_lut`) |
| `const HudLut* fade_lut_table` | `nullptr` | готовая таблица, приоритетнее дампа |

Публичный помощник (нужен тесту и будущему CLI):
`std::vector<std::string> error_words(std::string_view message)` — ровно те
слова, которые перебирает цикл `0x48ad1a`..`0x48ad85`, включая пустые слова из
ведущего/двойного/хвостового пробела (§2.3).

`ErrorRenderStats`:

* `rows` — **всегда 0** (запись `0x67f10c`, не длина списка);
* `lines` — число текстовых прогонов кадра, т.е. число вызовов `0x485dd0`:
  1 (`ERROR`) + по одному на слово (пустые слова тоже считаются, они реально
  вызывают отрисовщик) + 1 (`ESC TO RETURN TO MENU`); для `"No Error."` — 4;
* `ink_pixels` — уникальные пиксели глифов (фоновая плата не считается — как в
  `menu_render`/`key_jamming_render`);
* `missing_glyphs` — байты без глифа в атласе (пропускаются, не фатальны);
* `arrows` — спрайтов `MENUARRW` на экране нет (в `0x48acd0` нет вызова), всегда
  0, тест пинует 0.

Константы: `kErrorCanvasWidth/Height` (320/200), `kErrorBackground`
(`0x000000FF`), `kErrorTitle` (`"ERROR"`), `kErrorPrompt`
(`"ESC TO RETURN TO MENU"`), `kErrorDefaultMessage` (`"No Error."`),
`kErrorPanelName` (`"PLATE"`), `kErrorPanelWidth/Height` (196/131),
`kErrorTitleFont` (5), `kErrorTextFont` (0), `kErrorRows` (0),
`kErrorItemStep` (0), `kErrorTitleX/Y` (38/14), `kErrorMessageX` (10),
`kErrorMessageY` (34), `kErrorMessageLinePitch` (10),
`kErrorMessageWrapWidth` (180), `kErrorWordGap` (6), `kErrorPromptX/Y` (100/91).

## 2. Доказано (листинг + данные)

### 2.1. Диспетчер и пролог обработчика

`0x48acd0`..`0x48ada5` — 0xd5 байт кода, `ret` в `0x48ada5`, дальше 10 `nop`.
Диспетчер `0x487e71` считает `eax = [0x4bc440] - 5` и прыгает через таблицу
`0x4883d8` (33 входа, id 5..37); вход для id 5 — первый dword таблицы
`0x487f01`:

```
4883d8: 01 7f 48 00            ; [0x4883d8] = 0x487f01
487f01: call 0x48acd0
487f06: jmp  0x487f64          ; общий эпилог
```

Пролог и константы:

```
48acd4: xor eax,eax
48acd7: mov DWORD PTR ds:0x67f10c,eax   ; rows = 0
48acdc: mov DWORD PTR ds:0x662d58,eax   ; step = 0
48ace1: call 0x486050                   ; PLATE -> 0x6865f8 (196x131)
```

В `docs/UI_SCREENS.md` §2 у экрана 5 в колонках `rows`/`step` стоит «—»: оракул
`ui_screens.py` ищет только `mov ds:<global>,imm` (`immediate_writes`), а здесь
ноль приходит через `eax`, поэтому карта его не печатает. Код пишет **0 в оба
глобала** — это доказано листингом, а не моделью.

### 2.2. Все вызовы `0x485dd0`

Порядок аргументов (стек): `font, text, centered, x, row, item`; `y` считается
внутри: для `row >= 0` — `y = row + step*item` (`0x485e4b`..`0x485e5c`), для
`row < 0` — `y = -row` (`0x485e2b`..`0x485e38`). `centered != 0` заменяет `x`
на `(196 − width)/2` (`0x485de2`..`0x485dfa`, `width` — `0x47fa50`), а
`item = -1` срезает и `item*step`, и проверку подсветки (`0x485e04`).

| # | текст | VA | font | centered | x | row | item | y | сайт `push`/`call` |
|---|---|---|---|---:|---:|---:|---:|---:|---|
| 0 | `ERROR` | `0x4bdc50` | 5 | да | 38 (игнор.) | 14 | −1 | 14 | `0x48ace6`..`0x48acf5` |
| 1 | каждое слово `0x4aa2f8` | буфер | 0 | нет | 10 + … | y из цикла | −1 | 34 + 10·строка | `0x48ad66`..`0x48ad6f` |
| 2 | `ESC TO RETURN TO MENU` | `0x4bdc38` | 0 | да | 100 (игнор.) | 91 | −1 | 91 | `0x48ad89`..`0x48ad98` |

Независимое подтверждение — оракул `tools/re/ui_screens.py --json`: для id 5 он
отдаёт `handler 0x48acd0`, `title 0x4bdc50`, `assets plate, fonts`, пункт
`ESC TO RETURN TO MENU` с `item = -1`, `x = 0x64`, `row = 0x5b` и примечание
«message lines from 0x4aa2f8, wrapped at 0xb4 px».

`item = -1` во **всех** вызовах, поэтому шрифт 4 (`0x485e19`) недостижим:
подсветки, курсора и пунктов у экрана нет.

### 2.3. Цикл слов: `0x48ad1a`..`0x48ad85`

```
48acfa: mov al,ds:0x4aa2f8      ; первый байт буфера ошибки
48ad02: test al,al
48ad04: mov DWORD PTR [esp+0x8],0x22   ; y = 34 (внутри цикла это [esp+0x10])
48ad0c: mov edi,0xa                    ; x = 10
48ad11: mov esi,0x4aa2f8
48ad16: je 0x48ad89                    ; пустой буфер -> сразу подсказка
48ad18: push ebp / push ebx            ; из-за этого y съезжает на +8 в [esp]
48ad1a: ...                            ; скан слова до 0x20 или NUL
```

Скан (`0x48ad1e`..`0x48ad30`) идёт от `esi` вперёд до `0x20` или `0x00`; байт
в конце слова временно заменяется нулём (`0x48ad37`), ширина считается
`0x47fa50(0, слово)` (`0x48ad3a`), байт восстанавливается (`0x48ad7d`) и один
пробел пропускается (`0x48ad81`).

Перенос (`0x48ad44`..`0x48ad5a`): если `x + width > 0xb4 = 180` (строго
больше; ровно 180 ещё влезает), то `x = 10`, `y += 10` — **до** отрисовки
слова. Затем вызов `0x485dd0` (font 0, `centered = 0`, `item = -1`) и
`x += width + 6` (`0x48ad77`).

Следствия, которые модуль воспроизводит буквально:

* 6 px — это и есть пробел; **второй** пробел подряд становится пустым словом:
  отрисовщик вызывается, ничего не рисует, но `x += 6`. Ведущий пробел — тоже
  пустое слово; **одинарный хвостовой** пробел съедается на `0x48ad81` и
  пустого слова не даёт, а второй хвостовой — даёт;
* слово шире 170 px переносится даже в начале строки (первое слово тогда
  рисуется на `y = 44`), а дальше обрезается 196-пиксельной полосой, не 180;
* у `y` в обработчике нет верхней границы: длинный текст уходит ниже 131-й
  строки буфера.

Проверено тестом на 9 строках (`error_words`): `""` → `{}`, `"No Error."` →
`{No, Error.}`, `" A"` → `{"", A}`, `"A "` → `{A}`, `"A  B"` → `{A, "", B}`,
`"A   B"` → `{A, "", "", B}`, `"A  "` → `{A, ""}`.

### 2.4. Буфер сообщения и «подстановка»

`0x4aa2f8` — общий буфер ошибки в `.data`; в образе exe там лежит `"No Error."`
(это и есть значение по умолчанию `options.message`). Следующий
адресуемый dword — `0x4aa348`, т.е. под буфер отведено `0x50` = 80 байт, но
`sprintf` (`0x40d8e0`) пишет без ограничения длины, и никакой проверки размера
нет.

Форматирование выполняют **чужие** процедуры, а не экран:

| сайт | что пишет в `0x4aa2f8` | формат (VA) | затем |
|---|---|---|---|
| `0x4424e5` | `Unable to load world file (%s).` | `0x4ab5e4` | `0x4424fa: mov [0x4bc440],0x5` |
| `0x466b78` | `Network client program version (%ld.%02ld) is different ...` | `0x4b9fc8` | `0x466b98: mov [0x4bc440],0x5` |
| `0x466ce7` | `Network client level version (%ld.%02ld) is different ...` | `0x4b9f64` | `0x466cf9: mov [0x4bc440],0x5` |
| `0x44255b` | `Unable to engine_initall().` | `0x4ab5a4` | `0x442571: sprintf`, затем state 5 |

То есть подстановка `%s`/`%d` **есть**, но она происходит до экрана: обработчик
`0x48acd0` читает готовую строку и переносит её по словам. Поэтому в API одно
поле `message` (готовая строка), а не формат с аргументами — это честная модель,
а не упрощение.

### 2.5. Ввод, переход и достижимость

Состояние 5 пишется из процедур ошибок (таблица §2.4) — экран **достижим**, в
отличие от экрана 20. Ввод — единственная ветка во фронтенд-обработчике ввода
`0x48b56c`:

```
48b56c: cmp ebp,0x5
48b56f: jne 0x48b58c
48b571: cmp bl,0x1b            ; Esc?
48b574: jne 0x48e659           ; любая другая клавиша -> общий ret, без звука
48b57a: mov DWORD PTR ds:0x4bc440,0x1   ; -> главное меню
48b581: pop edi/esi/ebp/ebx; add esp,8; ret
```

Стрелок, `Enter`, кликов и звуков интерфейса у экрана нет.

### 2.6. Ассеты, цвета, палитра

* `FRONTEND/BMP.IDX`: `PLATE` (196×131) + `FONTS4` (грани 5 и 0).
  `MENUARRW`, `CHECK`/`NOCHECK`, `SLIDE`/`KNOB`, `NUMFONTS` не читаются.
* `PLATE` грузится и проверяется **всегда**: `0x48ace1` вызывает `0x486050`,
  который копирует `0x1913` dword (196×131) из `0x6d2b60` в `0x6865f8`
  (`docs/UI_SCREENS.md` §9).
* Палитра атласа `FONTS4`: шрифт 5 → `(155,15,15)` = `0x9b0f0f`, шрифт 0 →
  `(19,15,15)` = `0x130f0f` (`docs/MENU_RENDER.md` §3). Индекс 0 прозрачен;
  белого (шрифт 4) на кадре нет — тест это проверяет.
* `PLATE` использует собственную палитру BMP.

## 3. Модель

1. **Холст** 320×200, непрозрачный `#000`; опционально `background`
   (`FRONTEND/BMP.IDX`) в (0,0), клип по холсту.
2. **Плата.** `PLATE` (196×131) загружается и проверяется всегда. Куда движок
   блитит буфер `0x6865f8` на 320×200, не задокументировано
   (`docs/MENU_RENDER.md` §2), поэтому панель не рисуется неявно:
   `background = "PLATE"` кладёт её в (0,0), пусто — чёрный холст.
3. **Клип текста** — 196×131 (плоский буфер `0x6865f8`, а не построчный).
4. **Заголовок** `ERROR` (шрифт 5) центрируется в полосе 196 px:
   `x = (196 − width)/2`, `y = 14`. Отрицательный `x` (текст шире полосы)
   ограничен нулём — это модельная поправка, в оригинале был бы
   отрицательный offset в буфер.
5. **Сообщение** — слова `options.message` шрифтом 0 от `x = 10`, `y = 34`,
   перенос при `x + width > 180`, шаг строки 10, разнос слов 6; `centered = 0`,
   `item = -1`. Пустая строка — только заголовок и подсказка.
6. **Подсказка** `ESC TO RETURN TO MENU` (шрифт 0) центрируется, `y = 91`.
7. **Курсора, подсветки, чекбоксов, слайдеров, стрелок нет** — все вызовы
   статические; `stats.arrows = 0`, `stats.rows = 0`.
8. **Точный fade** `0x682f90`: индекс палитры каждого нарисованного пикселя
   проходит через `render/hud_lut.h::map(level, index)` **до** выборки цвета;
   уровень 11 — тождество, 12..15 — реальные таблицы. Нужна таблица
   (`fade_lut_table`) или дамп 4096 Б (`fade_lut_dump`, `docs/HUD_LUT.md` §2).
   Без обоих — отказ, а не «тихо без fade».
9. **Отказы** (префикс `error_render: `, буфер очищен, `width`/`height` = 0,
   `*stats` обнулён): пустой каталог игры; нет/битый `FRONTEND/BMP.IDX`; нет
   грани 5 или 0 (`FONTS4`); нет/битая/не 196×131 `PLATE`; неизвестная/битая/
   не-8-bpp запись `background`; `fade_lut` без таблицы и дампа; нечитаемый
   дамп. `message` отказать не может: любой байт рисуется или учитывается в
   `missing_glyphs`.

## 5. Ограничения

* **Нет ввода**: единственная клавиша — `Esc` → состояние 1 (`0x48b57a`);
  стрелок/`Enter`/кликов и звуков интерфейса нет.
* **Экран не генерирует ошибку**: текст приходит из буфера `0x4aa2f8`, который
  заполняют процедуры загрузки/сети; модуль рисует только переданную строку.
  Форматирование `%s`/`%d` — в этих процедурах, не в обработчике.
* **CLI — есть (срез 17).** `--error [--error-message TEXT] [--no-plate]
  [--png OUT] [--fade-lut N]`: по умолчанию
  `error_screen: rows=0 lines=4 ink=489 missing=0 arrows=0`; длинное сообщение
  `Unable to load world file (savegame).` — `lines=8 ink=803`. CTest
  `cli_error_screen`, `_long`; `cli_fade_lut` (11 = без fade). Модуль
  подключён к `main.cpp`; ниже — прежнее ограничение среза.
* Куда движок блитит буфер 196×131 на 320×200 — по-прежнему не
  задокументировано; модуль рисует панель и текст от (0,0), как соседние
  рендереры (`KEY_JAMMING_RENDER.md` §3, `LAY_BUCKS_RENDER.md` §3).
* Отрицательный `x` центрированного текста ограничен нулём (модель, §3.4);
  в оригинале смещение ушло бы в буфер.
* Границы буфера 80 Б (`0x4aa2f8`..`0x4aa347`) — наблюдение по соседним
