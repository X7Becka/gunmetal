# Мир / сектор / объект / полигон: карта рантайма (M2.3.2)

Что здесь: точная карта **рантайм-представления мира** Gunmetal — таблицы
секторов (`0x5670d8`), AABB секторов (`0x567138`), записи объекта (`0xa8`) и
полигона (`0x80`), таблицы материалов (`0x5670e0`), а также `SECTOR_STUFF`
(`0x800b60`, `256 × 0x58`). Для каждого поля — смещение, тип, смысл, адреса
читателей/писателей и статус **доказано / гипотеза**. Отдельно — соответствие
полей C++ (`CollisionWorld` / `SbwLevel` / `WorldState`), сверка с поставочными
`.sbw` и список того, что **не** перенесено.

Смежное, не дублируется: `docs/WORLD_MATERIALS.md` — потребители полей
материалов, overlay/scroll/anim, флаги объекта и вопрос `f32`/`f64`;
`docs/FORMATS.md` §10 — формат `.sbw` (диск),
`docs/COLLIDE.md` — треугольники/пол/лучи C++ (`CollisionWorld`),
`docs/DOORS_CPP.md` — `WorldState` и привязка дверей к `(sector, object)`,
`docs/RECORDS.md` §2 — `SECTOR_STUFF` (тип 8 сейва),
`docs/THING_FIELDS.md` — почему `0x800bb0` — это `SECTOR_STUFF+0x50`, а не
таблица типов.

Инструмент: `tools/re/world_fields.py` (`--map`, `--verify`, `--self-test`;
только stdlib; `gm/sbw.py` — необязательный оракул) и
`tools/re/materials.py` (`--map`, `--verify`, `--self-test` — таблица
материалов и её использование).

Все адреса — VA `gundx.exe` 1.36 (`ImageBase 0x400000`).

## 1. Метод

1. `tools/ghidra/mcp.py decompile|disasm|xrefs|bytes|batch` (headless Ghidra
   12.1.4, `docs/GHIDRA.md` §4.1). Декомпилятор — источник гипотез; x87-код
   перепроверялся по `disasm`.
2. Загрузчик `.sbw` — `0x422a63` (стадия 1: `0x42ad34`…`0x42ae15`, стадия 2:
   `0x425f4c` → `0x422b88`/`0x422a51`), **писатель** `.sbw` — `0x42afbb`,
   загрузчик текстового `.sow` — `0x42a33d` (он же показывает, как те же поля
   выглядят в «нормальных» `double`).
3. Потребители: `0x434419` (объект по `(sector, object)`), `0x434463` (полигон
   по `(sector, object, poly)`), `0x434fed` (AABB сектора), `0x4360f1`
   (точка → сектор), `0x437d05` (луч по миру для освещения), `0x43529f`
   (пересчёт AABB объекта и полигонов), `0x420c03` (таблица материалов),
   `0x42f183` (ссылки полигонов/«порталы»).
4. Числа — прогон всех 36 поставочных `.sbw` (только чтение) независимым
   парсером `world_fields.py`; для `level0`/`dm1` — сверка с `gm/sbw.py`.

## 2. Таблицы рантайма

### 2.1 Сектор (`0x5670d8`, шаг `0x18`)

| смещ. | тип | поле | кто читает/пишет | статус |
|---:|---|---|---|---|
| `0x00` | `u32` | `n_objects` | загрузчик `0x42ad9c`; `0x422d55`; `0x434419`, `0x434463`; add `0x4358c9`, del `0x435995` | доказано |
| `0x04` | `u32*` | `objects[n]` → записи `0xa8` | `0x422d55` (n·4 + n·0xa8), `0x434419` | доказано |
| `0x08` | `u16` | резерв | обнуляется `0x42adf3`; читателей/писателей не найдено (39 функций с xref на `0x5670d8`) | гипотеза |
| `0x0a` | `u16` | `n_sprites` | обнуляется `0x42adfc`; `+1` — `0x43659f`, `-1` — `0x4363de` | доказано |
| `0x0c` | `u32` | резерв | обнуляется `memset` в `0x422f03`; потребителей нет | гипотеза |
| `0x10` | `u32*` | `sprites[n]` (второй список, запись спрайта) | рост `0x43659f`, удаление `0x4363de`, чтение `0x428215` | доказано |
| `0x14` | `u16` | `kind` = тип×6 | загрузчик `0x42adbd`; геттер `0x42d99f` (÷6), сеттер `0x42d9d5` (×6) | доказано |
| `0x16` | `u8` | `light` (байт света сектора) | обнуляется `0x42ae05`; `SET_SECTOR_BRIGHTNESS` пишет `[sector+0x16]` в `0x4578f8` (геттер `0x42d8a5`) | доказано |
| `0x17` | `u8` | `sub` | загрузчик `0x42adde`; писатель `.sow` `0x42906c` | доказано |

Итого `0x18`; `0x08`/`0x0c` — выравнивание/резерв, в загрузчике только
обнуляются.

### 2.2 AABB секторов (`0x567138`, шаг `0x30`)

| смещ. | тип | поле |
|---:|---|---|
| `0x00/08/10` | `f64` | `min_x/min_y/min_z` |
| `0x18/20/28` | `f64` | `max_x/max_y/max_z` |

Пишет только `0x434fed`, и только для **объекта 0** сектора
(`0x43529f` вызывает её при `object == 0`). Формула (asm `0x4350a5`…):

```
min = origin - bounds + min(0, extent)      // origin/bounds/extent — объекта 0
max = origin + bounds + max(0, extent)
```

где `origin` — `obj+0x00` (`f64`), `bounds` — `obj+0x84` (`f32`),
`extent` — `obj+0x90` (`f64`, в поставке всегда 0): дополнительный полуразмер
по оси, знак выбирает сторону расширения (для куллинга берётся `|extent|`). Инициализация — `±1e38`
(`0x2a16a1b1/0x47d2ced3`); слот сектора **0** так и остаётся `±1e38`
(`0x434fed` при `sector == 0` только переинициализирует его), поэтому
`0x4360f1` и `0x437d05` начинают перебор с сектора 1. Читает `0x4360f1`
(точка → сектор) и `0x437d05` (луч по миру для освещения).

**Это не AABB всей геометрии сектора.** В мировом кадре
(`origin + basis·local`) внутри такого бокса лежит **27 519 из 28 192**
объектов (97.6 %; `tools/re/world_fields.py --self-test`), в старом
`f32`-кадре было **13 186 из 28 192** — ещё один независимый признак того,
что `origin` — это `f64`-сдвиг, а не мусор. Для `level0` — 190 из 192. Сектор
— группа геометрии, а бокс — дешёвый broad-phase по объекту 0 (обычно крупная
«коробка» сектора: у 5068/5104 секторов флаги объекта 0 равны 0; 21% его
полигонов без текстуры, остальные — обычная геометрия).

### 2.3 Объект (`0xa8`)

| смещ. | тип | поле | кто | статус |
|---:|---|---|---|---|

| `0x18` | 9 × `f64` (3 строки) | `basis`, `world = origin + B·local` | загрузка `0x42aea7/0x42aec8/0x42aee9`; `0x437af8` | доказано |
| `0x60` | `f32` | `radius` (`|bounds|`) | загрузка `0x425f4c`; cull `0x437d8c`, `0x437d05`; сфера сектора `0x4360f1` | доказано |

| `0x75` | `u8` | `f75` | загрузка `0x425f4c` (в 7 объектах = 1) | доказано |
| `0x76` | `u16` | выравнивание | не читается/не пишется | гипотеза |
| `0x78` | `u32` | `f78` | загрузка; в поставке всегда 0 | доказано (не используется) |
| `0x7c` | `u32` | `f7c` | загрузка; в поставке всегда 0 | доказано (не используется) |
| `0x80` | `u32*` | владелец: `0` = объект уровня, иначе указатель на **экземпляр вещи** (пул `0x71cd40`, шаг `0x148`, `+0x128` — «in use»); не «модель» | `0x435995` (правит списки сектора/полигона у владельца); ветвления `0x429e3b`, `0x42d045`, `0x42f183`, `0x437c4e`; рендер-цикл `0x4409b8` | доказано |
| `0x84` | 3 × `f32` | `bounds` (полуразмеры AABB) | загрузка; **пересчёт** `0x43529f`; AABB сектора `0x434fed` | доказано |
| `0x90` | 3 × `f64` | `extent` (доп. полуразмер AABB по осям) | загрузка из «reserved» файла; чтение `f64`: `0x434fed` (расширяет бокс сектора), `0x437d05` (`|extent|` в радиус), `0x440867` (флаг «сектор с extent»); писателей в коде мира нет, в поставке 0. См. `docs/WORLD_MATERIALS.md` §4.3 | доказано (в данных всегда 0) |
| `0xa8` | — | конец записи | шаг `n*0xa8` в `0x422d55` | доказано |

`bounds` — не `(max−min)/2` по вершинам, а `max(|x|), max(|y|), max(|z|)`
после применения базиса (`0x43529f`: `FABS` компонент, вершина минус origin).
В поставке оба определения совпадают для **28 192/28 192** объектов (допуск
2 ед.), `radius == |bounds|` точно — для **20 736/28 192** (остальное —
округление `bounds` до целых).

Полигон полигона: `corner_a/corner_b` (`0x38/0x44`) пересчитываются
`0x43529f` как min/max компонент вершин **относительно origin объекта** (не
центра полигона; `centre` остаётся авторским), стартовые значения `±1e38`
(`0x7e967699`/`0xfe967699`).

Замечание о **сдвиге имён**: на диске три `u16` идут в порядке
`0x72/0x74/0x76`, поэтому `gm/sbw.py` (`Poly.f74/f76/handle`) и
`engine/src/res/sbw.h::SbwPoly` называют их `f74, f76, handle` — это имена
**дисковых слотов**, а не смещений. Семантика движка: `sector+1`, `object`,
`poly+1`. Проверено по asm `0x42f2a5`…`0x42f2d2` (sector — `0x72−1`,
object — `0x74`, poly — `0x76−1`).

Ссылки/«порталы» в поставке почти не используются: `0x42f183` обрабатывает
только полигоны с `texture != 0`, таких со ссылкой всего **2** на все 36
уровней (обе резолвятся, нормали целевых граней противоположны). Остальные
11 356 полигонов с ненулевыми `0x72/0x74` не имеют текстуры и движком не
разрешаются — это остаток экспорта.

### 2.5 Таблица материалов (`0x5670e0`, `0x1e` = 30 × `0x40`)

Строится `0x420c03` при загрузке уровня: `DAT_005670e0 = malloc(0x1e << 6)`,
`DAT_005670e4 = 0x1e`. Пять групп («стилей света») × шесть видов; имя на
`+0x34`, для группы 0 — `none/reflective/translucent/varadd/add/shade`,
для групп 1..4 — `_ld_none_2 … _ld_shade_5`. Индекс полигона
`material = style*6 + kind`; в поставке используются только `0..4`
(`style = 0`: none/reflective/translucent/varadd/add; вид `shade` = 5 не
встречается, стили > 0 не используются).

| смещ. | тип | поле | статус |
|---:|---|---|---|
| `0x00` | `u32` | режим: `0` непрозрачный, `1` отражающий, `2` смешиваемый; **бит 0 = второй (смешиваемый) проход** — читают `0x437fc3`, `0x439e7e`, `0x43d571`, `0x423edb` | доказано |
| `0x04` | `u32*` | палитра стиля: styles 0/1 → `paltable`, 2 → `redtable`, 3 → `goldtable`, 4 → `bluetable` (`0x41e3d8`, 0x20100/0x2100 Б) | доказано (запись), читателей нет |
| `0x08` | `u32*` | blend-LUT вида: kind1/2 → `trantable`, 3 → `varaddtable`, 4 → `addtable`, 5 → `shadetable` (256×256 Б) | доказано (запись), читателей нет |

### 2.6 `SECTOR_STUFF` (`0x800b60`, 256 × `0x58`)

### 2.8 Как движок использует карту

* **Точка → сектор** (`0x4360f1`): перебор секторов **с 1** (сектор 0
  исключён) → AABB `0x567138` → сфера `|p − obj0.origin| < obj0.radius`
  (с защёлкой `1e38`) → для всех полигонов объекта 0
  `dot(normal, p − centre) ≥ 0`; выбирается ближайший по радиусу. Результат
  пишется в `inst+0x3c8` (`0x46d8b0`, `0x46e0b7`).
* **Луч по миру** (`0x437d05`, вызывается из `0x43e69d` — запекание
  освещения/лайтмапов: `0x47e2d0`/`0x47e370` обходят все полигоны и
  источники `0x638130`/`0x638330`): перебор секторов с 1, cull по
  `obj+0x70 & 0x10010`, сфера `obj+0x60` + `|extent|` (`0x4804b0` = `fabs`),
  затем полигоны: **нетекстурированные полигоны (`texture == 0`) не
  тестируются** (47 291 из 235 069), кроме случаев `material+0x00 & 1`
  (второй/смешиваемый проход) или `overlay != 0`; пересечение — плоскость
  `normal`/`centre` + тест точки. То есть «проходимость» геометрии для луча
  задаётся текстурой и битом 0 материала, а не отдельным collision-флагом.
* **Пересчёт** после загрузки объекта (`0x43529f`): AABB всех полигонов и
  `bounds`/`radius` объекта; для объекта 0 — ещё AABB сектора (`0x434fed`).
* **Двери**: `(sector, object)` → `0x434419`; объект-створка получает
  трансформ от `0x434887` (bbox `corner … corner+size`), см. `docs/DOORS_CPP.md`.

## 3. Диск → память

| диск (`.sbw`) | память | примечание |
|---|---|---|
| `u32 objects`, `u16 kind`, `u8 sub` | `sector+0x00`, `+0x14`, `+0x17` | `+0x0a/+0x10` — спрайты, в файле их нет |
| `u32 id`, `u8 header[96]` | `obj+0x70`, `obj+0x00/+0x18/+0x30/+0x48` | 96 Б = 3 + 9 «слов» по 8 Б |
| `u16 n_verts, n_polys` | `obj+0x68`, `obj+0x6a` | |
| `f32 verts[][3]` | буфер `obj+0x64` | |
| `f32 radius`, `f75`, `f74`, `f7c`, `f78`, `f32 bounds[3]`, 24 Б | `obj+0x60`, `+0x75`, `+0x74`, `+0x7c`, `+0x78`, `+0x84`, `+0x90` | 50 дисковых байт → 72 байта памяти (дыры) |
| полигон: `5H, bright, n_idx, idx[], 112 Б` | `poly+0x00…+0x7f` | порядок полей в хвосте — §2.4 |

**Кодировка трансформа.** 96-байтовый заголовок — это **12 `f64`**:
`origin[3]` + `basis[3][3]` (little-endian), `world = origin + basis·local`,
базис единичный (поворот). Доказательства:

* загрузчик читает 96 байт **без преобразования** прямо в
  `obj+0x00/+0x18/+0x30/+0x48` (`0x42ae86`, `0x42aea7`, `0x42aec8`, `0x42aee9`);
* трансформ `0x437af8` — `FLD double ptr [ECX+0x18]`, `FMUL`/`FADD double`
  (вершины при этом `FLD float ptr [EAX]`);
* младший dword каждого слова = 0 у **338 304/338 304** слов (28 192 объекта
  × 12) — ровно то, что даёт `f64` из `f32`;
* норма каждой строки `basis` в `f64`-чтении ровно `1.0`
  (**84 576/84 576** строк);
* AABB сектора (`origin ± bounds`, строится `0x434fed` из `origin` в `f64`)
  содержит все вершины у **4716/5104** секторов; в `f32`-кадре — **0/5104**.

Поэтому «`origin + 1.875·local`» — артефакт чтения старшего dword как `f32`:
`f32`-биты `1.0` (`0x3FF00000`) равны `1.875`. Конверсии `f32` → `f64` в
цепочке загрузки нет и не требуется.

**Исправлено** (ветка `feat/sbw-transform`): `gm/sbw.py::_points`,
`engine/src/render/collide.cpp::decode_transform` и
`engine/src/render/render.cpp::header_points` читают 12 `f64`, множителя
`1.875` больше нет нигде в коде. Тест — `engine/tests/test_sbw_transform.cpp`
(36 уровней: младший dword 0 у 338 304/338 304 слов, базис — единичный у
28 192/28 192 объектов; плюс синтетический повёрнутый/масштабированный базис,
сверенный с `gm/sbw.py` до `1e-12`). Паритет C++ ↔ Python проверяют голдены
`collide` (пересняты, `tools/re/collide_goldens.py`) и `core` (кадр 320×200
совпадает с `gm/render.py` байт в байт).

### 3.1. Согласованность с `.sbt`: что подтверждает новый кадр

Главный критерий — позиции из скрипта должны попадать на свою геометрию.
Прогон 36 уровней (`tools/re/spawn.py`, `gm/scene.py`, `gm/sbw.py`) в двух
кадрах — старом (`origin32 + 1.875·local`, т.е. прежний код) и новом
(`origin + basis·local`):

| источник точек | старая система | новая система |
|---|---|---|
| спавны (36 шт., слот 0): внутри AABB мира | 21/36 | **36/36** |
| спавны: сколько AABB объектов содержат точку (мин/макс) | 0…211 | **1…3** |
| спавны: расстояние до пола под точкой (n=36) | 14 «нет пола», остальные 0.0 … 15 862 (медиана 570) | **13.7 … 258.1** (медиана 56) |
| сохранённый игрок `saved0.sbt` (1 116.17, 798.21, 48) | вне AABB мира | **внутри, 1 объект, стена в 46.2** |
| `ADD_SPRITE` (547 точек): ближе 5 единиц к мешу | 15 (2.7 %) | **303 (55.4 %)**, на 5 уровнях 96–100 % |
| `ADD_THING` (76–154 точки на уровень): медиана до поверхности | 255 … 1 558 | **31 … 56** |
| `ADD_LOCATION` / `ADD_ITEM` | — | в основном интерьеры из `.sob`, обе системы далеки |
| `ADD_SWITCH` (3 321): ближе 5 единиц | **2 843 (85.6 %)** | 351 (10.6 %) |

Строки 1–6 закрывают вопрос: новый кадр — тот, в котором живёт рантайм.
Строка `ADD_SWITCH` — **открытый вопрос по данным** (не по трансформу):
операнды 3..5 `ADD_SWITCH` (позиция триггера) численно совпадают с
`1.875·local`, то есть с *файловым* кадром без `origin`, хотя движок сравнивает
их с позицией игрока напрямую (`0x44fc30`: `dist(player − rec[3..5]) < radius`,
для kind `0x101` — со сдвигом на `origin` двери). Числа совпадают на 85.6 %
против 10.6 % для мирового кадра, и это не эффект плотности (контроль:
случайные точки в том же боксе дают 0.2 %). Гипотезы, которые надо проверить
отдельно: (а) экспортёр уровня писал триггеры в пред-разбитом кадре
(до вычитания `origin` объектов); (б) для kind `0x101..0x104` позиция вообще
относительна. До выяснения `gm/scene.py::SCALE = 1/1.875` сохранён **только**
для проверок дверей/переключателей (`tools/re/doors.py`, `regress.py`), а
позиции мира (`markers`, `render_lights`, `--scene-scale`, `ADD_THING`)
масштабируются на `VOLUME_SCALE = 1.0`.

Проверка рантайма, не зависящая от `.sbt`: сохранённый мир
`SAVEGAME/saved0.sbw` (написан движком, `0x42afbb`) побайтово равен
`level0.sbw` — кроме одного `-0.0` в базисе объекта 48/6, то есть загрузчик и
писатель держат эти 12 `f64` как есть. Позиция игрока из `saved0.sbt`
(1 116.17, 798.21, 48) лежит внутри ровно одного AABB объекта нового кадра;
в старом кадре она вообще вне AABB мира.

## 6. Что не перенесено (приоритет)

1. **`SECTOR_STUFF` целиком** (P1): движение объектов сектора, урон, звук,

   зоны урона).
2. **Семантика материала** (P1): 30 записей, `+0x00` бит 0 (второй проход),
   `+0x20..+0x28` (множители), `+0x2c` (параметр). Сейчас C++ берёт только
   `material<6` и приближённо смешивает; для коллизий «проходимость»
   смешиваемых полигонов (`material&1`) не учтена, для рендера — нет
   таблиц стилей; в движке этот бит ещё и «включает» полигон в луч даже без
   текстуры.
3. **Полигональные ссылки/порталы** (P2): `0x72/0x74/0x76` + рантайм-маркеры
   `0x7ff8/0x7ff9` (`0x42f183`, `0x42d045`). В поставке всего 2 текстурных
   полигона со ссылкой, поэтому приоритет низкий, но без этого нет зеркал.
4. **Оверлей/скролл/анимация UV** (P2): `0x78`, `0x5c/0x60`, `0x5e/0x62/0x66`,
   `0x434c80`, `0x4342f0`; 156 полигонов с оверлеем.
5. **Флаги объекта** (P2): `0x70` (`0x10010`, `0x40000/0x80000`, `0x100000`),
   `0x80` (владелец), `0x90` (extent) — culling/owning/AABB.
6. **Текстуры/эффекты/лайтмапы как таблицы** (P3): `flag`, `value`,
   refcount `0x5310c0`, `kind/start/ids` эффектов; сейчас используются только
   имена и 1-based индексы.
