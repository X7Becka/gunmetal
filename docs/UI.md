# UI и меню: `.sml` / `.sme`, экраны, ассеты

Документ описывает **семантику интерфейсной разметки** Gunmetal: язык
`.sml`, его закодированную форму `.sme`, элементы UI, экранный автомат
фронтенда и связь с бинарными ассетами (`FRONTEND/BMP.IDX`,
`sprites/SBM.IDX`, `Film/*.sof`). Всё проверено на эталонной установке
`/mnt/d/games/Gunmetal 3dfx` (v1.36) и на дизассемблере `gundx.exe`
(ImageBase `0x400000`).

Инструмент: `python3 tools/re/ui_semantics.py --check` (и `--json`, `--dump`,
`--screens`, `--assets`, `--self-test`). Читатель формата — `gm/sml.py`
(`decode_best`, `describe`, `elements`).

**Экранный автомат по коду** (обработчики, переходы, порядок пунктов меню,
слоты сейвов, KEYCFG) — отдельный документ `docs/UI_SCREENS.md` и инструмент
`tools/re/ui_screens.py`; там же §12 перечисляет поправки к этой странице
(31 биндинг, id 20/30/33, порядок пунктов options/controls).

## 1. Корпус

`SML/` содержит 300 файлов:

| каталог | `.sme` | `.sml` | всего |
|---|---:|---:|---:|
| `brief/` | 25 | 24 | 49 |
| `prelevel/` | 77 | 76 | 153 |
| `design/` | 47 | 47 | 94 |
| корень (`help`, `credits`) | 2 | 2 | 4 |
| **итого** | **151** | **149** | **300** |

Пар «ствол + `.sme`/`.sml`» — **147**. Четыре `.sme` идут без `.sml`
(`brief/LEVEL0A.SME`, `prelevel/rand25.sme`, `prelevel/secrt1.sme`,
`prelevel/secrt2.sme`), два `.sml` — без `.sme` (`prelevel/s1.sml`,
`prelevel/s2.sml`). Это нормальная поставка, а не ошибка извлечения.

После декодирования **131 пара побайтово совпадает**. Остальные 16:

* **14 редакций** — текст/разметка отличаются (например `help.sme`
  исправляет `PLayer` → `Player`, добавляет `P - Pause`; `dm4.sml` вообще
  без закрывающего `</d>`, а `DM4.SME` — корректный);
* **2 пары** (`prelevel/LEVEL20`, `prelevel/LEVEL4`) — текст совпадает с
  `.sml`, но `.sme` закодирован из LF-текста и потом переведён в CRLF;
* `brief/level17.sme` — редакция **и** транспортная аномалия: лишний CRLF
  внутри файла (см. §4).

`python3 gm.py sml ... --rebuild` по-прежнему собирает **150/151** `.sme`
побайтово; `level17.sme` — на 1 байт короче (починка). Это не изменилось:
новый `decode_best` не трогает API `decode`/`encode`, а используется
инструментом и документацией.

## 2. Язык `.sml`

Плоский поток тегов, не дерево. Документ обязан иметь вид

```
<d> ... </d>
```

`<d>`/`</d>` — единственная обязательная оболочка. Теги не обязаны
закрываться (`<p>` действует до следующего блочного тега), но количество
`<` и `>` должно совпадать, а последний тег — быть `</d>`/`</D>`.

### 2.1. Теги, которые понимает движок

Диспетчер `0x497d30` берёт байт после `<`, индексирует таблицу классов
`0x498448` и jump-таблицу `0x4983f8`. Понимаются ровно девять букв
(регистр не важен) плюс `/`; всё остальное, включая `d`/`D`, — no-op
(`0x4983eb`).

| Тег | Обработчик | Семантика |
|---|---|---|
| `R`/`r` | `0x497d7c` | новая строка (row) |
| `P`/`p` | `0x497da0` | абзац: добавляет полвысоты строки и начинает новую строку |
| `C`/`c` | `0x497ec2` | центрируемая колонка: измеряет следующий текстовый сегмент и сдвигает его в остатке ширины |
| `F`/`f` | `0x497e9f` | шрифт: атрибут `s`/`S` — номер шрифта; пишется в `0x68e650` |
| `X`/`x` | `0x497f38` | позиция по X в процентах: `value * width / 100` |
| `K`/`k` | `0x497e2c` | вставляет позывной `Soldier` (`ds:0x4bc2b8`) |
| `S`/`s` | `0x497de8` | вставляет строку `" "` (`ds:0x4ab74c`) |
| `M`/`m` | `0x497f92` | музыка: `B` → `ds:0x68cc8c`, `S` → `ds:0x68cc88` |
| `I`/`i` | `0x498012` | картинка: `x`/`y` — позиция, `f` — имя BMP, `a` — выравнивание `l`/`r` |
| `/` | `0x49838e` | закрывающий тег (снимает состояние) |

Важно: **`d`/`D` не обрабатываются диспетчером**. Это оболочка документа,
которую проверяет загрузчик, а не элемент UI.

### 2.2. Атрибуты

Парсер значения — `0x498580` (число через `atoi`, строки в кавычках).
Фактические атрибуты поставки:

| Атрибут | Встречается | Значение |
|---|---:|---|
| `f s` / `F S` | 268 | номер шрифта; в поставке только `2` (174) и `3` (94) |
| `i x`, `i y`, `i f`, `i a` | по 72 | позиция, имя BMP, выравнивание (`l`/`r`, регистр не важен) |
| `m B`, `m S` | по 56 | трек и смещение/громкость; значения `B` 0/1/60, `S` 0..170 |

Есть 268 `<f>`/`<F>` **без** `s` (шрифт не меняется) — это допустимо.
`<I>` без `a` тоже допустим, но в поставке всегда есть `a`.

### 2.3. Текст

* Байт `\n` (и `\r`) при загрузке заменяется пробелом (`0x497784`).
* `<r>`/`<p>` — перевод строки, `<c>` — разделитель колонок.
* `<k>` → `Soldier`, `<s>` → `" "`. Это единственные подстановки.
* Теги с атрибутами (`<I ...>`, `<M ...>`, `<f s=...>`) сохраняются в
  «сыром» тексте; `plain()` оставляет их, `describe()["body"]` — уже без
  тегов.

### 2.4. Пределы

Загрузчик `0x497650` пишет смещения `<` и `>` в массивы
`0x68e668`/`0x68de40` и **отказывается** от документа при
`count >= 0x200`, т.е. максимум **511 тегов**. Также проверяются:

* первый тег — `<d>` (иначе `SML file has no tags`);
* последний — `</d>` (иначе `SML file doesn't end with </D>`);
* число `<` равно числу `>` (иначе `SML bracket imbalance`).

## 3. `.sme`: кодировка и загрузчик

`.sme` — та же разметка, закодированная позиционным шифром Цезаря:

```
encoded[i] = letter ? shift(plain[i], +(i % 10)) : plain[i]
```

Буква сдвигается внутри своего алфавита (регистр сохраняется), остальные
байты копируются. Декодирование — `-(i % 10)`. Сдвиг зависит от **байтового
индекса**, поэтому вставка/удаление любого байта ломает весь хвост.

Загрузчик `0x497310`:

1. получает путь вида `SML\BRIEF\LEVEL%ld.SML` (`0x4bde48`/`0x4bde64`);
2. дописывает `E` и пытается открыть `.SME` (буква `E` —
   `mov BYTE PTR [esp+edx+0x13],0x45`);
3. если `.SME` открылся — ставит флаг декодирования `0x68f19c=1`;
4. иначе открывает исходный `.SML` и ставит `0x68f1a0=1` (режим
   «закодировать в scratch-буфер», фактически plain-текст читается как есть);
5. `0x497650` декодирует и индексирует теги.

Отсюда практическое правило: **на диске `.sme` — основная форма, `.sml` —
резервная/редакторская**. Это объясняет, почему `help.sme` и `DM4.SME`
содержат исправленный текст, а `.sml` — старый/битый.

## 4. Транспортные аномалии (негативные кейсы)

### 4.1. `brief/level17.sme` — лишний CRLF

В файл после кодирования вставлен `\r\n` на смещении 70. Позиционный ключ
сбивается, хвост читается мусором. Движок заменяет `\n` пробелом
(`0x497784`), поэтому починка — свернуть `\r\n` в один пробел. Это делает
`gm/sml.py:decode_auto` и новый `decode_best` (note `newline-repair`).

### 4.2. `prelevel/LEVEL20.sme`, `prelevel/LEVEL4.sme` — LF → CRLF

Файлы закодированы из текста с **LF**, а поставлены с **CRLF**. Каждый `\r`
сдвигает фазу на 1, поэтому вторая и следующие строки декодируются в
бессмыслицу, а последний тег превращается в `</B>`/`</C>`. Починка — убрать
`\r` перед декодированием (`decode_best`, note `crlf-strip`); после неё текст
совпадает с `.sml` с точностью до переводов строк.

Это не было видно старому `decode_auto`: буквы тегов оставались «похожими»,
и эвристика по `SHIPPED_TAGS` не срабатывала. `ui_semantics.py --check`
проверяет оболочку `</d>` и поэтому ловит оба файла. `gm.py sml` на старом
декодере печатает 16 различных букв тегов (артефакт `B`), корректный корпус
даёт 15.

### 4.3. `prelevel/dm4.sml` — нет `</d>`

Единственный `.sml` без закрывающего тега. `.SME`-брат корректен и
заканчивается `</d>`, поэтому игра (она предпочитает `.sme`) не страдает.
`--check` считает это известной аномалией (`KNOWN_ANOMALIES`), а не провалом
всего корпуса.

### 4.4. `help.sme` — исправленная редакция

`help.sme` декодируется в 90 тегов против 63 в `help.sml`, содержит
`Toggle Player ID` (в `.sml` опечатка `PLayer`) и строку `P - Pause`.
Это доказывает, что `.sme` — не просто «сжатая копия», а самостоятельная
редакция.

## 5. Элементы UI, координаты, шрифты

### 5.1. Модель элемента

`gm/sml.py:elements()` возвращает упорядоченный список `Element`:

```python
Element(kind, tag, pos, attrs, value, x, y, align,
        track, offset, line, text)
```

`kind`: `doc`, `row`, `paragraph`, `column`, `image`, `font`, `music`,
`placeholder`, `text`, `close`, `unknown`. `pos` — байтовое смещение,
`line` — 1-based строка. Это готовый вход для HUD/UI: текст, картинки,
шрифты и музыка идут в одном потоке, как их видит движок.

`gm/sml.py:describe()` даёт сводку: количества тегов/атрибутов, оболочку
`<d>`, неизвестные теги, картинки, шрифты, музыку, текст без тегов,
превышение лимита тегов.

### 5.2. Картинки `<I>`

Обработчик `0x498012`:

* `x`, `y` — целые координаты; `y` добавляется к текущей строке; `a`
  выбирает левый/правый край, поэтому в поставке самостоятельный вклад `x`
  не виден (это остаётся гипотезой, см. §10);
* `a=l` — картинка у левого края, `a=r` — у правого (в поставке 50 `l`,
  22 `r`/`R`);
* `f` — имя loose-BMP в `SML/` (без расширения); грузится загрузчиком
  `0x47efe0` с префиксом `sml`;
* в поставке все 72 `<I>` имеют `x="64" y="64"`, а все 15 уникальных имён —
  это BMP **64×64** (16-й файл `OILBOAT.bmp` не используется). Для экрана
  320×200 пара `64,64` читается как пиксели (картинка 64×64 на строке 64),
  а не как проценты; процентная позиция в языке — отдельный тег `<X>`.
  Выравнивание `a` прижимает картинку влево/вправо, поэтому `x` при
  заданном `a` — резервная величина.

`<I>` не требует закрывающего тега. В рантайме обработчик переписывает
атрибут `f` в 2-значный индекс хэндла (`0x4980db` + `atoi` `0x414dd0`),
чтобы при повторной отрисовке брать уже загруженный BMP из таблицы
`0x68f010`; это деталь реализации, на диске имя остаётся именем.

### 5.3. Шрифты `<F>/<f>`

* Номер шрифта — `s`/`S`; движок хранит его в `0x68e650`.
* Высота строки: `font < 3` → 10 px, иначе 18 px (код `0x4983c3`:
  `sub eax,3; neg; sbb; and 0xf8; add 0x12`).
* Метрики/отрисовка — `0x47fa50` (ширина строки) и `0x47faf0` (вывод);
  таблица шрифтов — 31 запись по `0x1c` байт от `0x65ddd0`.
* Атласы в `FRONTEND/BMP.IDX`: `FONTS1` 512×168, `FONTS2` 1024×80,
  `FONTS3` 520×56, `FONTS4` 512×168, `NEWFONTS` 512×168, `NUMFONTS` 180×48.
  Инициализация — `0x48fa28`..`0x4902xx`; точное сопоставление «номер шрифта →
  атлас» ещё не добито (см. §10).
* В `.sml` используются только `s=2` и `s=3`; меню для подсветки выбранного
  пункта берёт шрифт `4` (см. §6).

### 5.4. Музыка `<M>`

`B` пишется в `ds:0x68cc8c`, `S` — в `ds:0x68cc88`. В поставке 56 тегов:
`B` = 0/1/60, `S` = 0/40/50/70/80/100/170. `B` — номер трека; смысл `S`
(смещение/громкость) в коде не подписан, это гипотеза.

### 5.5. Раскладка

Глобальные переменные рендера:

| Адрес | Роль |
|---|---|
| `0x68e648` | текущая Y-строка |
| `0x68e658` | левый край/отступ |
| `0x68e64c` | остаток ширины |
| `0x68e65c` | высота строки (10/18) |
| `0x68e654` | нижняя граница страницы |
| `0x68f008` | X внутри строки |
| `0x4be8b8` / `0x4be8bc` | ширина/высота, задаются `0x4972f0(w,h)` |
| `0x68ee74` | начало колонки/абзаца |
| `0x68ee70` | номер страницы |

`0x497880` — цикл раскладки/отрисовки: режет текст на сегменты, измеряет
`0x497c20`, рисует `0x497b60`, обрабатывает теги через `0x497d30`.
`0x498600`/`0x4986b0`/`0x498750` — первая/следующая/предыдущая страница
(массивы `0x68ee78` — стартовые теги страниц, `0x68ee7c` — их состояние).
Конкретные extents задаёт вызывающий код (например, брифинг-пагер в
`0x487c40` вызывает `0x4972f0(0x10b,0xa7)` = 267×167).

## 6. Экраны и меню

### 6.1. Экранный автомат

Состояние фронтенда — dword `0x4bc440`. Диспетчер `0x487e71`:

```
eax = [0x4bc440] - 5
if eax <= 0x20: jmp [eax*4 + 0x4883d8]
```

То есть таблица `0x4883d8` — **экранная таблица** (33 входа, id 5..37).
`id 0..4` — драйверные состояния (title loop, основной цикл, SML-пагер

### 6.2. Как выбирается элемент

Единой data-driven таблицы «экран → список пунктов» нет: каждый обработчик
рисует свой список, часто через массив строк. Общий механизм выбора:

* текущий выбранный пункт — dword `0x68ccf4`;
* отрисовщик пункта `0x485dd0(text, font, centered, x?, row, item_id, ...)`;
* если `item_id == [0x68ccf4]` и текст не пуст, шрифт принудительно
  становится `4` (`0x485e19`) — это подсветка;
* текст центрируется в полосе шириной 196 px (ширина `PLATE`) и
  компонуется в копию `PLATE`: `0x486050` копирует 196×131 байт из
  `0x6d2b60` в `0x6865f8`, отрисовщик пишет в эту копию;
* шаг строки — `0x662d58` (обычно 15, у некоторых экранов 8/16), число
  строк — `0x67f10c`.

Примеры таблиц пунктов:

* `0x4bc558` — 30 названий биндингов (`Move Forward` … `Linear Right`);
* `0x4bc4d4` — пары «действие/обратное действие» (`Speed +/- Slide` …);
* `0x4bc6d8` — значения графических опций (`No`, `Little`, `Some`, `Max`);
* `0x4bc6e8` — режимы deathmatch (`Deathmatch Classic`, `Scavenger Hunt
  Deathmatch`, `Normal Deathmatch`);
* `0x4bc308` — имена zoom-оверлеев (`zooma`…`zoomg`);
* `0x4bc288` — имена HUD-панелей: `""`, `""`, затем восемь раз `PANEL`
  (индекс — `0x4bc1c8`).

Фон экрана тоже выбирается по состоянию: имя `0x4bc1b8` — это `DISBAND`
или `DEMOTION` (две 8-символьные константы `0x4be8a0`/`0x4be8a8`);
переключатель `0x497210` выбирает одну из них, затем `0x47efe0` грузит
320×200 BMP.

### 6.3. Брифинги и SML-пагер

Состояние `id=2` — пагер SML. Он:

* при необходимости грузит `SML\HELP.SML` (`0x4bd250`) в буфер
  `0x6d8fc0` 320×200 и рисует `HELPSCRN`;
* вызывает `0x497310` для `SML\BRIEF\LEVEL%ld.SML` / `LEVEL%ld%c.SML`
  (`0x4bde48`/`0x4bde64`), `SML\CREDITS.SML` (`0x4bd228`);
* инициализирует страницу `0x4972f0`, рисует первую/следующую/предыдущую
  через `0x498600`/`0x4986b0`/`0x498750`;
* листает состояние `0x4bc3a8` и номер страницы `0x4bc43c`.

Именно здесь `.sml`/`.sme` становятся «экранами»: брифинги, prelevel-
«газеты», design-описания, help и credits.

## 7. Связь с ассетами

### 7.1. `FRONTEND/BMP.IDX` (143 записи)

`BIGFILE`-архив обычных Windows BMP (8 бит). Это **атлас интерфейса**, а не
источник картинок SML:

* полные экраны 320×200: `BRIEFBG2`, `CLOUDLO`, `CUSSBG`, `DEMOTION`,
  `DISBAND`, `HELPSCRN`, `LEVELEN2`, `LOADPAGE`, `MADLO`, `SHARE0..3`,
  `STATSBG`;
* шрифты: `FONTS1..4`, `NEWFONTS`, `NEWFONT2`, `NUMFONTS`;
* панели/рамки: `PANEL`, `PANELMID`, `PANELTOP`, `PANELTWO`, `HUMPAN`,
  `PANNEW`, `SCROLL`, `PLATE` (196×131), `F_M_TITL` (232×52);
* иконки: `EQUIP0..12` (24×24), `WCON*`/`WICON*` (24×24), `RPVICONS`,
  `KEYICONS`, `KEYICNS2`, `RADAR` (64×75), `TARGET` (24×16),
  `DETECTOR` (16×16), `ZOOM` (128×128), `ZOOMA..G` (64×64);
* элементы управления: `CHECK` (8×16), `NOCHECK` (8×8), `KNOB` (8×8),
  `SLIDE` (72×8), `FILESLOT` (124×10), `MENUARRW` (16×8),
  `MENULIT` (16×16);
* портреты/плитки: `BRAIN01..10` (80×125), `KILLTILE` (80×16),
  `PLAY` (112×25).

Размеры в загрузчике `0x48fa..0x49019f` совпадают с заголовками BMP; это
позволяет использовать `FRONTEND/BMP.IDX` как готовый атлас для HUD.

### 7.2. `SML/*.bmp` (16 файлов, 64×64)

Картинки `<I f=...>` — **отдельные loose-BMP рядом с `.sml`**, не записи
архива. Все 15 используемых имён находятся в `SML/` (регистр не важен):

`drilhed`, `hotcargo`, `jmpshld`, `ltmills`, `ltstrong`, `lv1swtch`,
`lv6idol`, `oilfile`, `pamelal`, `prnguyen`, `sensaray`, `sparnuke`,
`virsampl`, `viruscor`, `vpishii`. Все — 64×64, 8 бит. `OILBOAT.bmp` лежит
рядом, но в разметке не встречается.

Ни одно из этих имён **не** встречается в `FRONTEND/BMP.IDX`,
`sprites/SBM.IDX` или `PICS/SBM.IDX` — это доказывает разделение
«UI-атлас / loose-иллюстрации / мировые спрайты».

### 7.3. `sprites/SBM.IDX` (179) и `PICS/SBM.IDX` (1648)

`sprites/` — мировые эффекты (взрывы, дым, вспышки, планеты), `PICS/` —
текстуры мира. Формат `.sbm` — 8-битные mip-цепочки (`gm/sbm.py`). SML их
не использует; для HUD они не нужны, кроме случаев, когда HUD-эффект
рисуется мировым спрайтом (в текущем UI такого нет).

### 7.4. `Film/*.sof` — HUD-фильмы

48 файлов `.sof` — безголовые последовательности тайлов 8192 байт
(128×64, хранятся транспонированными). `gm/sof.py` декодирует их. Это
**анимированный HUD-слой**: `AMMO*`, `WEAPON*`, `TANK*`, `SHIELD*`,
`EQUIP*`, `DEFAULT`; загрузчик HUD `0x4958d0` рисует фильм на строке 125,
`.fdx`/`.idx` задаёт `count,fps` (парсер `0x498e20`). SML-разметка и `.sof`
не ссылаются друг на друга: SML — статические экраны/брифинги, `.sof` —
боевой HUD.

## 8. Инструмент и проверки

```sh
python3 tools/re/ui_semantics.py --check
# files 300 (.sme 151, .sml 149), pairs 147: identical 131,
# revisions 14, line-endings 2; newline-repair .sme 1
# images 72 (15 unique), fonts [2, 3], music 56
# known malformed: 1 file(s) (prelevel/dm4.sml)
# check: OK
```

Что проверяет `--check`:

* все `.sme` декодируются в `<d>...</d>` (с учётом трёх вариантов ремонта);
* оболочка, баланс `<`/`>`, отсутствие неизвестных тегов, лимит 511 тегов;
* у каждой картинки есть `SML/<name>.bmp`, корректный `a` и `x`/`y`;
* шрифты — целые 0..30, музыка — целые `B`/`S`;
* пары `.sme`/`.sml`: identical / revision / line-endings;
* негативные self-тесты: неизвестный тег, отсутствие `<d>`/`</d>`, лимит
  тегов, LF→CRLF и вставка CRLF, `decode_auto` на пустом вводе.

`--json` выдаёт полный отчёт: `engine`, `screens`, `counts`, `files`
(элементы, ассеты, предупреждения), `pairs`, `assets` (FRONTEND, sprites,
PICS, SML BMP, films). `--dump` печатает элементы по файлам, `--screens` —
таблицу экранов, `--assets` — инвентарь.

## 10. Гипотезы и что осталось

Доказано:

* язык тегов, девять обработчиков, атрибуты, подстановки, оболочка `<d>`;
* `.sme` = позиционный шифр, предпочтение `.sme` загрузчиком;
* 131/147 пар идентичны; аномалии LEVEL17/LEVEL20/LEVEL4 и `dm4.sml`;
* все 15 картинок SML — loose BMP 64×64; UI-атлас — `FRONTEND/BMP.IDX`;
* экранная таблица `0x4883d8` и выбор пункта через `0x68ccf4`.

Гипотезы/не добито:

1. **Точный смысл `M S`** (смещение, громкость или номер стиля) — в коде
   только запись в `ds:0x68cc88`; значения 0..170.
2. **`<I x>` vs `a`**: в поставке `x=64` при `a=l/r`, поэтому вклад `x`
   в позицию не виден. Нужен эксперимент с `x` без `a`.
3. **Сопоставление номера шрифта и атласа** `FONTS1..4/NEWFONTS` —
   инициализация в `0x49010b`.. ещё не разобрана до конца; известно только
   `font<3` → высота 10, `>=3` → 18 и что SML использует 2/3.
4. **Разбиение на страницы**: массив `0x68ee78`/`0x68ee7c` и порог
   `0x4be8bc`; алгоритм переноса с учётом `<p>`/`<r>` и высоты строки
   частично восстановлен, но не проверен на всех брифингах.
5. **Цвет/палитра текста** и точные координаты экранного origin для
   SML-пагера (267×167) — нужна сверка с кадром игры.
6. **Пункты меню**: списки часто инлайновые; полная карта «экран → массив
   пунктов → item id» не составлена (в docs есть примеры). Для HUD это не
   критично, для точного воспроизведения меню — следующий шаг.
7. **`<I>` runtime-перезапись `f` в 2-значный handle** (`0x4980db`) —
   поведение описано, но точная схема имён/хэндлов не проверена на всех
   72 картинках.
8. **`B` в старом декодере** — артефакт LEVEL20; после `decode_best` его нет.
   Это подтверждает, что корпус содержит 15 настоящих букв тегов, а не 16.

Следующие шаги для HUD/UI:

* перенести `Element`/`describe` в C++ как модель `UiDocument`;
* реализовать загрузку `.sme` с тремя вариантами ремонта (или предпочитать
  `.sme`, как игра);
* собрать HUD из `FRONTEND/BMP.IDX` (панели, иконки, шрифты) и `.sof`
  (анимации), а SML-экраны рисовать отдельным пагером;
* для меню использовать таблицу состояний `0x4883d8` и `0x68ccf4`, а не
  парсить `.sml` (меню в игре не на SML).
