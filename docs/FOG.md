# Туман по глубине: формула, таблица `lighttable`, Glide (M4.1.6)

Что здесь: точная формула тумана по глубине в `gundx.exe` 1.36 (ImageBase
`0x400000`) — что такое `z`, как из него получается `level`, как устроена
таблица `lighttable` (`ds:0x567104`) и какие параметры уходят в Glide. Это
закрывает вопрос из `docs/MATERIAL_BLEND.md` §4 («`lighttable` в рендере —
это фог по глубине») и `docs/RE_AUDIT.md` §M4.1.6.

Инструмент: `tools/re/fog.py` (`--json`, `--table`, `--glide`, `--anchors`,
`--self-test`; stdlib + `gm/palette.py`, только чтение). Ghidra не
использовалась, только инструкции (`tools/re/disrange.py`) и байты образа.

**Главное, что меняет прежнюю запись:** `0x4804b0` — это **`fabs`**, а не
`sqrt`. В нём нет ни одного `fsqrt`, он обнуляет бит знака и возвращает
аргумент (`0x48056e`: `and ecx,0x7fffffff`). Следовательно `z` — **не
корень** и не квадрат: это камерная глубина, умноженная на `64/a0`. Второе
уточнение: `0x40e0e0` (`ftol`) — это `fistp` с **RC=11 (усечение)**, а не
округление к ближайшему: `0x40e0ef` делает `or ah,0x0c`.

## 1. Метод

* Формулы — по инструкциям. Кэш листинга `~/.cache/gunmetal-re/gundx.asm`
  через `tools/re/disrange.py`.
* Каждая цифра в `tools/re/fog.py` привязана к адресу и проверяется
  `--self-test`: 21 «якорь» (последовательность байт) — если бинарь другой,
  тест падает, а не врёт.
* `lighttable` **строится** инструментом из палитры `FRONTEND/GAMEPAL`
  (`gm/palette.py`) по формуле билдера, а не берётся готовой (она в BSS).
* Имена Glide-функций и слоты IAT не захардкожены: инструмент разбирает блок
  `GetProcAddress` `0x416900`..`0x416e30` (там лежат строки `_grFogMode@4` и
  т.п. в `.data` возле `0x4a85b4`) и сам строит карту «имя → слот», затем
  ищет `call DWORD PTR ds:<слот>`.

## 2. Что такое `z` (`0x4409b8`)

Цепочка (все адреса — в проходе `0x4409b8`):

1. **Вершина в мир**: `0x437af8(out, vertex, obj)` = `M_obj · v_local + t`
   (3×4 double-матрица объекта `obj+0x00`..`obj+0x50`, шаг вершин 12 байт,
   `obj+0x64`).
2. **В камеру**: `0x440e3a`..`0x440e5a` вычитает `eye = ctx+0x00/+0x08/+0x10`.
3. **Скалярное произведение с осью взгляда**: `0x440c98` берёт `ctx+0x48`
   (`e2`), `0x440caa` — `ctx+0x50`, `0x440cbc` — `ctx+0x58`; каждый элемент
   умножен на `64/a0` (`0x440c05`: `fld [ctx+0xa0]`, `0x440c0b`:
   `fdivr QWORD ds:0x4a2298` = `64.0 / a0`) и сложен с остальными
   (`0x440ea7`..`0x440ec1`). Для сравнения: ряд `x` — `0x440e5d`..`0x440e7c`
   (`ctx+0x30` → `[ebp-0x188]`), ряд `y` — `0x440e82`..`0x440e9f`
   (`ctx+0x60` → `[ebp-0x1b0]`).
4. **Модуль**: `0x440ec9` `call 0x4804b0`; результат — `[ebp-0x1d0]`
   (`0x440ed1`). Это и есть `z`.

`e2` — третья ось камеры, направление взгляда (`docs/CAMERA.md` §4: экранные
оси — `+0x30` = X, `+0x60` = −Y, `+0x48` = глубина; там же доказано, что
`0x440c1d`..`0x440c8f` умножают именно эти строки).

`a0 = ctx+0xa0` пишется в `0x4466b2`/`0x4466da`:

```
a0 = ((W << 8) * 0.4 >> 7) * [0x80d8a0] * k(level)
   = 0.8 · W · [0x80d8a0] · k(level)      # 256 при W=320, k=1
```

(арифметика `0x44667a`..`0x44669b`: `W<<8`, `imul 0x66666667` = ·0.4,
`sar edx,7`, итого `0.8·W`; `[0x80d8a0] = 1.0`; `k(level)` — double из таблицы
уровня `0x81bf98 + 0x190·index`, умножение `0x4466d8`.)

**Почему `fabs`, а не `sqrt`.** `0x4804b0` — тонкая обёртка: при конечном
аргументе она делает `and ecx,0x7fffffff` над старшим словом (`0x48056e`),
кладёт обратно и возвращает (спецветки — только Inf/NaN). Никакой FPU-операции
в теле нет, `fsqrt` (`D9 FA`) не встречается ни в теле функции, ни во всём
проходе `0x4409b8`..`0x4420d0`. Старая догадка «похоже на CRT `sqrt`»
опровергнута; `docs/WORLD_FIELDS.md` §2.6 уже называет `0x4804b0` — `fabs`,
это подтверждается здесь байтами.

**Интерполяция.** Значение глубины в вершинах интерполируется **линейно по
major-оси экрана**, а не как `1/z`: `0x4417bc`..`0x4418b7` считают
`dv/di = (d2−d1)/(i2−i1)` и далее `d += (i − i0)·dv/di`. Поэтому `level`
постоянен поперёк трассы (по minor-оси) и меняется вдоль major-оси — типичный
DDA, а не попиксельная перспективная коррекция.
`fabs` применяется к уже интерполированному значению (`0x441940`,
`0x441aa9`, `0x441e46`, `0x441fb9`).

## 3. `level` и clamp

```
0x441921  fld  [ebp-0x170]          ; minor-координата (y)
0x441927  call 0x40e0e0             ; ftol
0x441932  push [ebp-0x1e8]          ; старшее слово double z
0x441939  push [ebp-0x1ec]          ; младшее слово
0x441940  call 0x4804b0             ; fabs(z)
0x441948  call 0x40e0e0             ; ftol
0x44194d  mov  ecx,0x3f
0x441952  sub  ecx,eax              ; level = 63 - ftol(z)
0x441963  level = max(level, 4)
0x441976  level = min(level, 0x3f)
```

`0x40e0e0` — `fstcw` / `or ah,0x0c` / `fldcw` / `fistp` / `fldcw`: RC = 11,
то есть **усечение к нулю**. `ftol(0.99) = 0`, `ftol(−2.7) = −2`.
Практического различия с «к ближайшему» тут ±1 уровень (шаг 4 юнита), но
формула должна быть точной.

Копии той же пятёрки инструкций: `0x441ab6` (ветка «нет 3dfx» — второй
вариант DDA), `0x441e53`, `0x441fc6`. `--self-test` проверяет все четыре.

Диапазон `level` — `4..63`, поэтому реально используются строки таблицы
4..63: `63` = «белый», `4` = «почти исходный цвет» (см. §5).

## 4. `lighttable` (`ds:0x567104`, builder `0x4201fe`)

Таблица 256×256 байт, индекс `row*0x100 + col`, где `col` — индекс пикселя
(цвет из палитры), `row` — `level`.

```
row < 0x40:   c' = min(63, (pal6[col][c]·(0x40 − row) + row·0x40) >> 6)
0x40..0x7f:   c' = 63  (белый)
row >= 0x80:  table[row][col] = col   (байтовое тождество)
```

Инструкции: `0x42024c` (`cmp row,0x40`), `0x420264` (`mov edx,0x40`),
`0x420272` (`shl eax,6`), `0x420277` (`sar ecx,6`), clamp по каналам
`0x4202cb`/`0x4202d8`/`0x4202e5`; ветка «белый» — `0x4202f4`; тождество с
`row = 0x80` — `0x4204e2`..`0x420538` (счётчик байта = `col`).

Смысл: **линейная тяга цвета палитры к белому** с весом `row/64`; `row = 0` —
палитра как есть, `row = 0x3f` — чистый белый.

Палитра — 6-битная `0x83d320`: загрузчик `FRONTEND/GAMEPAL` пишет по 3 байта
со сдвигом `>>2` (`0x47f0b4`, `0x47f0bd`, `0x47f0c6`). Это важно: при 8-битных
значениях формула сразу упиралась бы в clamp 63 и строка 0 перестала бы быть
тождеством (а она обязана — это точка «без тумана»).

Финальная квантизация (`0x42031a`..`0x4204d5`): 18-битный цвет
`r<<12|g<<6|b` → байт из `[0x567128 + idx]`, а при `flag[col] != 0`
(`0x530fb8`) — ещё из `[0x56712c + idx]` и выбор ближнего по сумме квадратов.
Обе таблицы — BSS (строятся в рантайме), поэтому `fog.py` подменяет этот шаг
«ближайшим цветом палитры»; в `--self-test` проверяется, что строка 0
попадает в цвет палитры **точно** (расстояние 0).

Проверка формы таблицы (`--self-test`): строка 0 = палитра, строка 0x3f =
белый, 0x40..0x7f = белый, ≥0x80 = байтовое тождество, по каждому каналу
значения не убывают с ростом `row`.

Пример (реальная палитра `GAMEPAL`, 6 бит):

| индекс | цвет | row 0 | 8 | 16 | 24 | 32 | 40 | 48 | 56 | 63 |
|---:|---|---|---|---|---|---|---|---|---|---|
| 16 | 6,2,2 | 6,2,2 | 13,9,9 | 20,17,17 | 27,25,25 | 35,33,33 | 42,40,40 | 49,48,48 | 56,56,56 | 63,63,63 |
| 20 | 30,20,20 | 30,20,20 | 34,25,25 | 38,31,31 | 42,36,36 | 47,42,42 | 51,47,47 | 55,53,53 | 59,58,58 | 63,63,63 |
| 176 | 0,4,12 | 0,4,12 | 8,11,18 | 16,19,25 | 24,26,31 | 32,34,38 | 40,41,44 | 48,49,51 | 56,56,57 | 63,63,63 |
| 255 | 63,63,63 | 63,63,63 | … | … | … | … | … | … | … | 63,63,63 |

Чистый белый в палитре — индексы 96 и 255, поэтому «белые» строки при
квантизации дают 96 (первый подходящий).

## 5. Глубина → `level` → цвет (серая палитра)

`a0 = 256` (320×200, `k = 1`), значит `z = 0.25·d` и шаг — 4 юнита на уровень:

```
level = clamp(63 - trunc(0.25·d), 4, 63)
```

| глубина `d` | `z` | `level` | чёрный (0,0,0) | серый (32,32,32) | белый |
|---:|---:|---:|---|---|---|
| 0 | 0 | 63 | 63,63,63 | 63,63,63 | 63,63,63 |
| 24 | 6 | 57 | 57,57,57 | 60,60,60 | 63,63,63 |
| 48 | 12 | 51 | 51,51,51 | 57,57,57 | 63,63,63 |
| 72 | 18 | 45 | 45,45,45 | 54,54,54 | 63,63,63 |
| 96 | 24 | 39 | 39,39,39 | 51,51,51 | 63,63,63 |
| 120 | 30 | 33 | 33,33,33 | 48,48,48 | 63,63,63 |
| 144 | 36 | 27 | 27,27,27 | 45,45,45 | 63,63,63 |
| 168 | 42 | 21 | 21,21,21 | 42,42,42 | 63,63,63 |
| 192 | 48 | 15 | 15,15,15 | 39,39,39 | 63,63,63 |
| 216 | 54 | 9 | 9,9,9 | 36,36,36 | 63,63,63 |
| 240 | 60 | 4 | 4,4,4 | 34,34,34 | 63,63,63 |
| ≥ 236·k | ≥ 59 | 4 | 4,4,4 | 34,34,34 | 63,63,63 |

`--table` печатает то же самое для любого `--a0`.

Проверка на реальном кадре (`out/oracle/win2.json`: камера
(259.1, 658.4, −70.0), yaw 6.0146, level0): из 1217 вершин перед камерой
медиана глубины 626 юнитов, **1055 вершин попадают в `level = 4`** (тумана
нет), и только 162 — ближе 236 юнитов, где `level > 4`. То есть при `k = 1`
эффект — узкая «дымка у камеры» в пределах комнаты, а не дымка на горизонте.

## 6. Glide-фог (3dfx-путь той же функции)

В начале `0x4409b8`, если `ctx+0xec` (глобальный конфиг рендера `0x4c05d0`,
копия в `0x4465b2`) имеет бит `0x800`, движок настраивает Glide-фог
(`0x440a57`: `cmp [ebp-0x1f4],0` → `je 0x440c02`):

| адрес | вызов | аргумент |
|---|---|---|
| `0x440a64` | `grDisableAllEffects` (слот `0x4d744c`) | — |
| `0x440a8c` | `grFogMode` (`0x4d7470`) | **2** = `GR_FOG_WITH_TABLE` |
| `0x440a97` | `grFogColorValue` (`0x4d746c`) | **`0xffffff`** (белый) |
| `0x440aa6` | `guFogGenerateExp` (`0x4d74c0`) | таблица `[ebp-0x4c]` (ровно 64 байта), плотность **0.9f** (`0x3f666666`) |
| `0x440ab0` | `grFogTable` (`0x4d7474`) | та же таблица |

Слоты найдены разбором `GetProcAddress`-блока `0x416a00`..: строки в `.data`
`_grFogColorValue@4` = `0x4a8674`, `_grFogMode@4` = `0x4a8688`,
`_grFogTable@4` = `0x4a8698`, `_guFogGenerateExp@8` = `0x4a8828`,
`_guFogGenerateLinear@12` = `0x4a8854` (см. `--glide`).
64-байтный буфер `[ebp-0x4c]`..`[ebp-0x0c]` — это и есть
`GR_FOG_TABLE_SIZE = 64`.

`guFogGenerateExp` — код Glide, не exe; по исходникам Glide 2.x
`t[i] = 255·(1 − exp(−density·i/63))`, при `density = 0.9`:
`0, 3, 7, 10, 14, …, 149, 151` (дальний край — 151/255 = 59 % белого).
`fog.py --self-test` проверяет 64 записи, `t[0] = 0`, максимум 151,
монотонность.

Кроме кадрового пути есть уровневые настройки:

| адрес | что |
|---|---|
| `0x41713a` | `grFogMode(0x202)` = `GR_FOG_WITH_TABLE │ 0x200 (ADD2)`, цвет из данных уровня `level+0x30` |
| `0x4171b5` | `grFogMode(2)` |
| `0x4171d7`..`0x41735b` | сборка таблицы из `[0x9e8cf4]` и трёх `float` уровня (`+0x20/+0x24/+0x28`, умножаются на 255.0) |
| `0x417c7f`, `0x417faa`, `0x4184ac` | `grFogMode(0)` — выключение фога на время прохода |
| `0x4184a4` | `grFogColorValue(0x404040)` — «нейтральный» цвет при выключении |
| `0x41889c` | `guFogGenerateLinear(tbl, 0.25·[ctx+0xc4], [ctx+0xc4])` |
| `0x4188a6` | `grFogTable(tbl)` |

`0x417c99` — `grFogMode(0x102)` = table + `MULT2`.

Итог: в 3dfx-сборке туман — **белый, экспоненциальный, плотность 0.9**, и
дальний край даёт лишь 59 % белого. Это согласуется с эталонным кадром
(`out/oracle/win2.png`): заметной белой дымки на горизонте нет, сцена тёмная.

## 7. Что передавать в `gm/render.py` (рендер не меняется)

Точная копия движка (программный путь):

```
color_fog   = (63, 63, 63)              # белый, 6-битные каналы
a0          = 0.8 * W * k               # 256 при 320x200, k=1
level(d)    = clamp(63 - trunc(d * 64 / a0), 4, 63)
c'          = min(63, (c*(64 - level) + 63*level) >> 6)   # == LUT-формула
```

Для вьювера это удобно выразить через «начало/конец»:

* `near = 0`, `far = 59·a0/64 = 236` юнитов (при `a0 = 256`): на `near` —
  100 % белого, на `far` — 6 % (`level = 4`), дальше не меняется;
* шаг дискретизации — 4 юнита (`64/a0 = 0.25`) и 1 уровень;
* предлагаемые ключи: `--fog` (по умолчанию выключен), цвет `#ffffff`,
  `--fog-near 0 --fog-far 236`. При `zoom`/разрешении `far` масштабируется как
  `236·W/320`.

Важно: у движка **инверсия привычного тумана** — белеет ближний план, а не
дальний (§8). Если вьюверу нужен «обычный» туман, это будет *другая*
функция, и её нельзя выдавать за движок.

## 8. Что доказано, что гипотеза, что осталось

| утверждение | статус | почему |
|---|---|---|
| `z = \|(64/a0)·(e2·(p−eye))\|` | **доказано** | `0x440c98`..`0x440ed1`, `0x4804b0` = `fabs` |
| `level = clamp(63−trunc(z), 4, 63)` | **доказано** | `0x44194d`..`0x44197d`, `0x40e0ef` (RC=11) |
| `fbuf[i] = lt[level*0x100 + i]` | **доказано** | `0x441b2d`..`0x441b5c`; второй вход `0x44203d` |
| формула и границы `lighttable` | **доказано** | builder `0x4201fe`, проверяется в `--self-test` |
| палитра LUT — 6-битная | **доказано** | `>>2` при загрузке `0x47f0b4`; иначе строка 0 не тождество |
| Glide: белый, `guFogGenerateExp(0.9)`, mode 2 | **доказано** (вызовы/константы) | `0x440a8c`..`0x440ab0` |
| тело `guFogGenerateExp` | **гипотеза** (исходники Glide 2.x) | в exe только `push 0.9` |
| «туман белеет к камере» | **факт кода, семантика неясна** | `level = 63 − z`, строка 63 = белый; в 3dfx-сборке этот путь не рисует кадр (см. ниже) |
| чем именно является проход `0x4409b8` | **открыто** | он идёт по объектам/полигонам и рисует **по одному пикселю на шаг** (DDA по major-оси, `0x441b83`: `i += 1`), т.е. это попиксельная трасса рёбер, а не заливка; в 3dfx-режиме те же рёбра идут через `grAADrawLine` (`0x441666`). Заливка полигонов в этом проходе не найдена; в поставочной сборке кадр рисует Glide (`0x417843` и далее — `guDrawPolygonVertexListWithClip`) |
| почему программный путь не виден в игре | **сильная гипотеза** | кадр `out/oracle/win2.png` — из Glide-пути; программный включается только при `ctx+0xec & 0x800 == 0` |
| `k(level)` в `a0` | **не расшифрован** | таблица уровня `0x81bf98 + 0x190·idx` заполняется в рантайме (`docs/CAMERA.md` §7); от неё зависит `far` |
| небо/скайбокс | **не проверялось** | отдельного фога для неба в этом проходе нет: таблица одна, глобальная |
| под водой / в лаве | **не проверялось** | скриптовых команд, меняющих `lighttable` или `grFogColorValue`, не искали; уровневый цвет `level+0x30` (`0x417152`) — первый кандидат |
| второй путь (`0x4419a2`, таблица `0x4a6a40`, шаг 0x10) | **открыто** | пишет 4 байта на пиксель через `0xa1a1c0` (упакованный аккумулятор), уровень считается тем же кодом; таблица — статический рамп в `.data`; в 8-битном LFB не используется |
