# `.soo` — модельные анимации Gunmetal

**Статус:** M1.1 закрыт (2026-10-20). Разобраны загрузчик `0x42b4e1` и плеер
`0x433e00`, семантика `mode`/`count` доказана дизассемблером, проверены все 40
файлов поставки, добавлены `Soo.timeline()` / `Soo.frame_at(ms)` и инструмент
`tools/re/soo_semantics.py`.

**Коротко:**

| что | результат |
|---|---|
| файлов | 40 (`Sobanim/`, в т.ч. 3 с расширением `.SOO`) |
| строк-кадров | 264, движок читает **261** |
| суммарная длительность (движок) | 19 987 тиков (219.6 с) |
| `mode` | 26 × one-shot (`0`), 14 × loop (`1`) |
| загрузятся в движке | **33 из 40** |
| не загрузятся | 7 (4 из-за отсутствующих `.sob`, 3 из-за разной топологии) |
| round-trip | 40/40 побайтово (`gm/soo.py`) |

---

## 1. Формат

`Sobanim/<name>.soo` — обычный текст (CRLF), без бинарного заголовка:

```
0                 mode
3                 count
BigGate1 200      имя позы (SOBS/BigGate1.sob) и длительность
BigGate2 6000
BigGate3 10
```

* В трёх файлах (`bamfin`, `bamfrays`, `icebamf`) первые два числа стоят в
  одной строке (`0 3`).
* Разделители — любые пробельные символы; регистр имён на Windows не важен,
  загрузчик строит путь `Sobanim\<name>.soo` и `SOBS\<name>.sob`.
* `count` — **не комментарий и не «подсказка»**: движок читает ровно `count`
  строк `%s %ld` и закрывает файл. Всё, что дальше, не читается вообще.
* Раскладка (CRLF, комбинированный заголовок, отсутствие финального перевода
  строки, хвостовые пустые строки) сохраняется в `Soo.to_bytes()`.

## 2. Загрузчик `0x42b4e1` (доказано)

Это функция «SOB **или** SOO по имени»; её вызывают оба загрузчика
`SOB_TABLE` — текстовый (`0x47c845`) и бинарный (`0x47c9ea`), — а
скриптовый компилятор приходит сюда через `0x47c9b0` (`0x461e71`; ошибка
`0x4b9128`, «Unable to load SOB or SOO»).

Порядок действий (адреса — VMA):

1. Пустое имя → `NULL`; имя `none` (`0x4a99e0`) → `NULL`
   (`0x42b50f`).
2. **Сначала `.sob`**: `0x427a05` собирает `sobs` (`0x4a9550`) +
   имя + `sob` (`0x4a954c`) и грузит модель. Если получилось — возврат
   (`0x42b52f`).
3. Иначе — `.soo`: `0x40d1a0("sobanim", name, "soo")`
   (`0x42b57c`; строки `0x4a99ec`, `0x4a99e8`).
4. `fscanf(f, "%ld %ld", &mode, &count)` (`0x42b5c2`, формат `0x4a99f4`).
   Ровно два числа, иначе — ошибка.
5. `mode` → `soo+0x00`, `count` → `soo+0x04` (`0x42b5d4`).
6. Проверка `1 <= count <= 0x20` (`0x42b5f1`); записей `.soo` не больше
   `0x200` (`0x42b551`, глобал `0x5a45d0`).
7. Цикл `i = 0..count-1`: `fscanf(f, "%s %ld", name, &duration)`
   (`0x42b657`, формат `0x4a99fc`), длительность → `soo+0x88+4i`
   (`0x42b687`), поза → `soo+0x08+4i` (`0x42b6d5`). Любая поза не
   загрузилась — ошибка **всей** анимации (`0x42b6ec`).
8. Совместимость поз: у всех кадров `+0x68` (число вершин) и `+0x6a`
   (число граней) должны совпадать с кадром 0 (`0x42b71b`…`0x42b79e`) —
   иначе ошибка. Это необходимо для морфинга (см. §3.3).
9. Радиус `+0x60` берётся у кадра 0 и записывается во все кадры
   (`0x42b6f1`…`0x42b7b8`; сравнение с нулём — защита от отрицательного
   значения, а не максимум по кадрам).
10. Первой позе ставится id анимации: `sob0+0x7c = -1 - n_soo`
    (`0x42b7bd`), затем `n_soo++` (`0x42b7d5`).

Структура в памяти: база `0x6fbd40`, шаг `0x108`:

| смещение | поле |
|---|---|
| `+0x00` | `mode` (i32) |
| `+0x04` | `count` (i32, 1..32) |
| `+0x08 + 4i` | указатель на `.sob`-позу `i` (32 слота) |
| `+0x88 + 4i` | длительность кадра `i`, тики 91 Гц (32 слота) |

`0x108 = 0x88 + 32*4` — сходится с шагом таблицы.

Фрагмент:

```asm
42b57c: 68 e8 99 4a 00   push 0x4a99e8        ; "soo"
42b581: 8b 55 08         mov  edx,[ebp+8]    ; name
42b585: 68 ec 99 4a 00   push 0x4a99ec        ; "sobanim"
42b58a: e8 11 1c fe ff   call 0x40d1a0
...
42b5b6: 68 f4 99 4a 00   push 0x4a99f4        ; "%ld %ld"
42b5c2: e8 f9 25 fe ff   call 0x40dbc0        ; fscanf
...
42b687: 89 94 81 88 00 00 00  mov [ecx+eax*4+0x88],edx   ; duration
...
42b7bd: 83 ca ff         or   edx,-1
42b7c0: 2b 15 d0 45 5a 00 sub  edx,[0x5a45d0]
42b7cc: 89 50 7c         mov  [eax+0x7c],edx  ; anim id on pose 0
```

**Важно:** id вешается только на **первую** позу. Если `SOB_TABLE` ссылается
на `BigGate2`, анимация не включится — это обычная статическая модель.

### 2.1. Связь с `SOB_TABLE` и `.sob`

* `SOB_TABLE` (тип 20 `.sbt`) — записи по 20 байт: `char name[12]`, `u32
  amount`, `u32 ptr`. Загрузчик (`0x47c7c0`, `0x47c9b0`) читает имя и
  вызывает `0x42b4e1`; указатель на модель кладётся в `entry+0x10`
  (`0x47c84e`, `0x47c9fd`). `0x47c990(index)` возвращает `entry+0x10`.
* `amount` анимационным кодом не читается; это не число кадров.
* Имена кадров — это **отдельные файлы** `SOBS/<name>.sob`, а не кадры
  внутри одного `.sob`. Внутри `.sob` кадров нет.
* 28 базовых имён `.soo` встречаются в `SOB_TABLE` уровней; 28-е имя
  `fire` — нет, но его кадры `fire1a`/`fire1b` встречаются как
  самостоятельные модели. 11 файлов не упомянуты ни как имя, ни как кадр
  (вероятно, cut-content/тестовые): `BigGate`, `Cultist2`, `Dev1`, `Nuke1`,
  `Nuke2`, `bamfin`, `keldorc`, `keldoro`, `kntpod`, `patfly`, `tester`.
* Не путать с `.soa` (`0x42b81b`, строки `soa`/`flaganim`/`anims`): это
  другой формат (UI/флаги), у него целочисленный счётчик кадров и шаг
  структуры `0x5c`.

## 3. Плеер `0x433e00` — семантика `mode`/`count` (доказано)

Вызов: рендер объекта (`0x41a9b1`)

```asm
41a9b1: 83 7a 7c 00      cmp dword [edx+0x7c],0
41a9b5: 74 12            je  0x41a9c9
41a9b7: a1 d8 82 9e 00   mov eax,[0x9e82d8]   ; текущее время
41a9c1: e8 3a 94 01 00   call 0x433e00        ; play(obj, now)
```

Псевдокод точно по инструкциям:

```c
play(obj, now):
    if (obj->anim >= 0) return;                 // 0x433e13
    rec = &soo_table[-1 - obj->anim];           // база 0x6fbd40, шаг 0x108
    total = sum(rec->dur[0..count-1]);          // 0x433e35
    if (total <= 0) return;                     // 0x433e67
    t = now - obj->start;  if (t < 0) t = 0;    // obj+0x78, 0x433e72/84
    if (mode == 0) { if (t >= total) t = total-1; }   // 0x433e8b..b2
    else if (mode == 1) { t %= total; }               // 0x433eb4..bb
    // для mode > 1 нормализации НЕТ (в поставке таких нет)
    acc = 0; i = 0;
    while (i < count && t >= acc + dur[i]) { acc += dur[i]; i++; }
    cur = rec->frame[i];
    nxt = (i == count-1) ? (mode == 0 ? cur : rec->frame[0])
                         : rec->frame[i+1];     // 0x433f37..6b
    alpha = (t - acc) / dur[i];                 // 0x433f24..34
    for (v = 0; v < obj->nverts; v++)           // +0x68, массив +0x64, шаг 12
        obj->vert[v] = lerp(cur->vert[v], nxt->vert[v], alpha);
    for (f = 0; f < obj->nfaces; f++)           // +0x6a, массив +0x6c, шаг 0x80
        obj->face[f] = lerp(cur->face[f], nxt->face[f], alpha);
```

### 3.1. `mode` — доказано

| `mode` | поведение | адрес |
|---|---|---|
| `0` | **one-shot**: при `t >= total` время прижимается к `total-1`; последний кадр интерполируется сам в себя → поза удерживается навсегда | `0x433e8b`…`0x433eb2`, `0x433f48`…`0x433f5e` |
| `1` | **loop**: `t %= total`; на последнем кадре `next = frame[0]`, то есть плавный переход последней позы в первую | `0x433eb4`…`0x433ebb`, `0x433f55`…`0x433f5b` |
| другое | нормализации нет; цикл выбора кадра выйдет за `count` — неопределённое поведение. В поставке только 0/1 | — |

Именно это раньше было «не доказано»: теперь видно и ветку зажима, и выбор
`next` в конце.

### 3.2. `count` — доказано

`count` — авторитетное число кадров. Загрузчик читает ровно `count` строк
(`0x42b637`, условие `i < count`), а не «до EOF». Следствия:

| файл | `count` | строк | движок играет | что теряется |
|---|---|---|---|---|
| `nblast.soo` | 8 | 9 | 8 кадров, 215 тиков (2.36 с) | `nblast_k 10` |
| `nbloom.soo` | 8 | 9 | 8 кадров, 215 тиков (2.36 с) | `nbloom_k 10` |
| `ruinbeam.soo` | 5 | 6 | 5 кадров, 1700 тиков (18.7 с) | второй `ruinbm0 100` |

`len(frames) < count` — ошибка загрузки (объявлено больше, чем есть); в
поставке таких файлов нет.

### 3.3. Длительности — тики 91 Гц, не миллисекунды

В плеере нет ни одного умножения/деления на частоту: `dur[i]` — сырые
единицы того же таймера, что пришёл в `now`. Этот таймер — **счётчик кадров
главного цикла**, 91 тик в секунду:

* `0x4074e0` спит ~11 мс на кадр (`Sleep(elapsed+11)`), `0x44bdc0`
  инкрементирует `[0x5a4a74]` ровно раз за итерацию;
* `0x44d4c0`: `delta = [0x5a4a74] - [0x5a46e8]`, затем
  `[0x5a46e4] += min(delta, 45)` — то есть часы уровня копят **кадры**;
* `0x44db80`: каждые `91` единица (`0x44db8d: cmp ecx,0x5b`) — одна
  секунда; значит `1 тик = 1000/91 ≈ 10.99 мс`;
* тот же `0x5a46e4` сохраняется в сейв как поле `F1`; при завершении уровня
  оно делится на 91 (`0x45c057`) — независимое подтверждение частоты;
* `.soa`-загрузчик `0x42badf` переводит `period` (сотые секунды) в тики
  ровно как `period*91/100`;
* `0x9e82d8` — текущее время для рендера в тех же тиках; `obj+0x78`
  задаётся при создании из `[0x5a46e4]` (конструктор `0x43ad40` пишет
  аргумент `[ebp+0x18]`, вызывающий `0x47796b` передаёт часы уровня).

Человеко-масштабная проверка: `BigGate2 6000` = 66 с удержания,
`Cultist` 50/150/100/100 = 4.4 с цикла, `Fire 50/40` ≈ 1 с, `NUKEring`
4×30 = 1.3 с. Версия «мс» дала бы 90 мс на цикл огня и 120 мс на взрыв —
неправдоподобно. **Доказано: тики 91 Гц.**

`obj+0x78` как «время старта/спавна»: вычитание `now - obj+0x78` доказано,
а то, что туда кладётся именно время спавна, следует из конструктора и
вызова; отдельной проверки «пауза/смена базы» нет.

### 3.4. Интерполяция, а не смена модели

Движок **не подменяет модель** на каждом кадре. Он держит один объект
(первую позу) и на каждом рендере пересчитывает его вершины и
per-face-записи линейной интерполяцией между текущей и следующей позой
(`0x433f6d`…`0x434415`). Поэтому:

* все позы обязаны иметь одинаковые `+0x68` и `+0x6a` (число вершин и
  граней) — это проверяет загрузчик;
* «смена модели» — это морфинг вершин, а не swap;
* интерполируются не только позиции (массив `+0x64`, шаг 12), но и
  per-face/vertex-записи (массив `+0x6c`, шаг `0x80`: поля `+0x08`…`+0x2c`
  и дальше).

## 5. Разбор конкретных анимаций

### `BigGate` — one-shot на 6.2 с, ломается о последний кадр

`mode 0`, кадры `BigGate1 200`, `BigGate2 6000`, `BigGate3 10`.
Задумано: 200 тиков (~2.2 с) открытие → 6000 тиков (~66 с) удержание → 10 тиков (~0.11 с) финальный щелчок, затем
поза `BigGate3` удерживается. Но `SOBS/BigGate3.sob` в поставке нет, а
загрузчик требует **все** кадры (`0x42b6ec`), поэтому `BigGate.soo` не
загружается целиком: ни `BigGate1`, ни `BigGate2` не получают `+0x7c`.
Статические `BigGate1/2` при этом грузятся как обычные `.sob`. Имени
`BigGate` нет ни в одном `SOB_TABLE` — вероятно, вырезанный контент.

### `Cloud` — one-shot «пуф» 640 тиков (~7 с)

`mode 0`, 9 кадров: `Cloud1d 50`, затем семь интервалов
`Cloud1a/Cloud1b` по 80 тиков (~0.88 с), финал `Cloud1c 30` (~0.33 с). Все позы 18v/14f, загрузка
успешна. Играет один раз и замирает на `Cloud1c`. Ссылка есть во всех 36
уровнях (общая модель).

### `Cultist` — цикл 400 тиков (~4.4 с) с «удержаниями»

`mode 1`: `cult1a 50/150`, `cult1b 50/150`. Внутри каждого кадра длительность
задаёт не смену позы, а скорость морфинга: 50 тиков переход, 150 тиков почти
статичное удержание (alpha растёт, но позы соседние). На 400 тиках
`cult1b` плавно morph-ится обратно в `cult1a`. Используется в
`level13/14/16`.

### `Dev1` / `tester` — loop, который не загрузится

`mode 1`, `dev1b 100`, `dev1a 400` (500 тиков, ~5.5 с). Обеих моделей
(`SOBS/dev1a.sob`, `SOBS/dev1b.sob`) нет → загрузка всей анимации
обрывается. `tester.soo` — побайтовый дубликат `Dev1.soo` (тестовый
остаток). Ни один из файлов не упомянут в `SOB_TABLE`.

### `Fire` — loop 90 тиков (~1 с), но позы несовместимы

`mode 1`, `fire1a 50` (16 вершин / 7 граней), `fire1b 40`
(12 вершин / 6 граней). Загрузчик сравнивает `+0x68/+0x6a` и отвергает
файл (`0x42b780`/`0x42b7a0`). При этом `fire1a` и `fire1b` сами по себе
являются записями `SOB_TABLE` (во всех уровнях и в `level5/22`
соответственно), поэтому статически огонь рисуется, а морфинга нет.
Это доказывает, что `+0x68/+0x6a` — именно размеры топологии, а не
произвольные поля.

### `NUKEring` — one-shot 120 тиков (~1.3 с)

`mode 0`, `shock2a..d` по 30 тиков (~0.33 с), все 18v/18f, загрузка успешна. Играет
4 кадра и удерживает `shock2d`. Ссылка — во всех 36 уровнях. Верхний
регистр расширения (`.SOO`) не мешает: Windows ищет без учёта регистра.

## 6. Инструменты

### `tools/re/soo_semantics.py`

Только stdlib (+ чистый `gm`), игру не пишет:


Масштаб общий на лист, поэтому видно и относительный размер поз (например,
у `Fire` вторая поза заметно крупнее).

### `gm/soo.py`

Старый API (`parse`, `parse_file`, `to_bytes`, `duration`, `Frame`, `Soo`)
не изменён. Добавлено:

```python
a = soo.parse_file(path)
a.loop                 # mode == 1
a.engine_frames        # первые count кадров (то, что читает движок)
a.dropped_frames       # хвост после count (мёртвые строки)
a.short / a.truncated  # строк меньше/больше count
a.engine_duration      # сумма длительностей движковых кадров, тики
a.timeline()           # [Timing(index, name, duration, start, end, next_index)] — тики
a.frame_at(ms, start=0)# Pose(..., duration/elapsed/phase/total — тики)
a.frame_at_tick(t)     # то же без пересчёта мс -> тики
```

`frame_at` переводит мс в тики (91/1000) и повторяет `0x433e00`:
отрицательное время → 0; mode 0 —
зажим на `total-1`; mode 1 — `% total`; `alpha` — доля текущего кадра.

## 8. Опровергнутые гипотезы

1. **«`count` — просто количество строк, авторитетен список кадров»** —
   опровергнуто. Загрузчик читает ровно `count` (`0x42b637`) и не смотрит
   на остаток. `nblast/nbloom` теряют 9-й кадр, `ruinbeam` — 6-й.
2. **«`mode` — это номер варианта/чего-то неясного; 0/1 = loop/one-shot
   не доказано»** — доказано: `0` = зажим и удержание, `1` = остаток по
   модулю и переход последнего кадра в первый (`0x433e8b`…`0x433f5b`).
3. **«Имена кадров — кадры внутри `.sob`»** — нет. Это отдельные файлы
   `SOBS/<name>.sob`; внутри `.sob` кадров нет.
4. **«Длительности в миллисекундах»** — опровергнуто. Часы движка —
   счётчик кадров 91 Гц (`0x44d4c0`, `0x44db8d`, сейв `F1/91`), поэтому
   `6000` = 66 с, а не 6 с; версия «мс» была ошибкой.
5. **«На каждом кадре подменяется модель»** — нет. Один объект, линейный
   морфинг вершин и per-face-данных между соседними позами.
6. **«Лишние строки всё равно проигрываются»** — нет, они мёртвые.
7. **«`keldorc`/`keldoro` — рабочие анимации смены модели»** — нет:
   топология кадров разная, загрузчик отвергает файл целиком.
8. **«`BigGate` играет первые два кадра, пока нет третьего»** — нет:
   загрузка атомарная, при отсутствии любого `.sob` анимация не создаётся.
9. **«`amount` в `SOB_TABLE` — число кадров анимации»** — не подтверждено:
   загрузчик и плеер его не читают; в записи он есть, но для `.soo`
   бесполезен.

## 9. Что осталось

* **База `obj+0x78`.** Вычитание `now - obj+0x78` доказано; то, что это
  именно время спавна (и как ведёт себя пауза/перезапуск), — сильная
  гипотеза, отдельного теста нет.
* **`mode > 1`.** В поставке нет; код не нормализует время и выходит за
  массив кадров — поведение не моделируется (`frame_at` бросает
  `ValueError`).
* **Точная семантика per-face-записей `+0x6c` (шаг `0x80`).** Видно, что
  они интерполируются (поля `+0x08`…`+0x2c` и далее), но полная карта
  полей не снята; для таймлайна это не нужно.
* **События по концу анимации.** Ни в загрузчике, ни в плеере нет вызова
  «animation finished»; mode 0 просто удерживает позу. Если скрипты
  рассчитывают на событие, его обработчик не найден.
* **Почему в поставке битые данные** (`BigGate3`, `dev1*`, `bamf*`,
  `Fire`, `keldor*`). Похоже на cut-content/старую версию формата; текущий
  загрузчик такие файлы не принимает.
* **`.soa`** (`0x42b81b`) — отдельный формат, здесь не разбирался.

## Viewer

`gm.py view Sobanim/Cultist.soo --at 1000 --size 480 --out cultist.png` parses
the animation, calls `frame_at(1000)` (tick 91) and linearly morphs the two
pose `.sob` models (`gm.render.morph_models`: vertices plus face origin/u/v/normal/spare).  The engine requires equal topology, so mismatched
poses raise instead of guessing.  At tick 91 Cultist is in frame 1
(`cult1a`→`cult1b`); time 0 and 1000 ms produce different images, pinned by
regress.

C++ has the same path:

```sh
gunmetal --anim Cultist --at 1000 --width 240 --height 240 --render pose.png
```

`anim.cpp:soo_pose_at` and `sob.cpp:morph_sob` mirror the Python timeline and
interpolator; the 240×240 frame is bit-identical (FNV-1a64 RGB
`3adbef60432bc3dd`, pinned in `gm_tests`).
