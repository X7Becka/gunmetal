# Текстурные UV кадрового прохода и полигоны без текстуры (M4.1.8)

Что здесь: два узких вопроса из `docs/ORACLE.md` («Текстуры: масштаб UV и
полигоны без текстуры»), снятые с инструкций `gundx.exe` 1.36 (ImageBase
`0x400000`). Инструмент — `tools/re/texuv.py` (`--json`, `--self-test`,
`--anchors`, `--stats <level>`; stdlib + `tools/re/exelib.py`, игра только
на чтение). Ghidra не запускалась: только листинг `objdump -D -M intel`
через `tools/re/disrange.py` и байты образа.

**Коротко.**

| вопрос | ответ | статус |
|---|---|---|
| делитель текстурных UV | **64**: `texel = (dot(axis, v−centre)·64 + uv_fp) >> 6` | доказано (`0x43e11c`/`0x43e122`, `0x41be68`) |
| единица `uv_u_fp` (`+0x54`) | **1/64 текселя** | доказано (там же) |
| единица `uv_u` (`+0x50`) | **1/256 текселя** | доказано (`0x43e0ff`/`0x43e10f`) |
| масштаб | **1 тексель на единицу мира** | доказано кодом + данными (все 1088 текстурных полигонов `level0`) |
| `poly+0x00 == 0` | **полигон пропускается**: setup `0x9fde50` → `-1` → drawer возвращается | доказано (`0x9fdf24`..`0x9fdf3e`, `0x9fe4cb`, `0x41b6e9`) |
| рисуется ли «последней привязанной» или белым | нет: это `return`, не fallback | доказано (`0x41b6e9` → `0x41c710`) |

Делитель `2048` — это **лайтмап** (`docs/FORMATS.md` §4), а не текстура. Оба
прохода берут один и тот же числитель `N`, но лайтмап сдвигает его на 11, а
текстура на 6, то есть страница лайтмапа в **32 раза грубее** текстуры
(1 тексель лайтмапа на 32 единицы мира против 1 текселя текстуры на 1
единицу). Отсюда и «огромные блоки» при `uv="fit"`/`/2048`.

---

## 1. Формула (доказано)

```
N       = dot(u_axis, vertex − centre) · 64 + uv_u_fp        # единицы 1/64 текселя
texel_u = N >> 6        # кадровый проход, текстура
texel_v = (dot(v_axis, vertex − centre) · 64 + uv_v_fp) >> 6
texel_lm= N >> 11       # лайтмап (docs/FORMATS.md §4)
```

Якоря (байты сверяет `texuv.py --self-test`/`--anchors`; смещение — точное
начало инструкции):

| адрес | байты | смысл | статус |
|---|---|---|---|
| `0x43e0cd` | `8b 45 0c d9 40 20` | авто-UV: начало `dot(u_axis, centre−v)` | доказано |
| `0x43e0ff` | `dc 0d 58 22 4a 00` | `fmul 256.0` (`0x4a2258`) — `uv_u += d·256` | доказано |
| `0x43e10f` | `66 89 42 50` | `mov [poly+0x50], ax` → `uv_u` в 1/256 текселя | доказано |
| `0x43e11c` | `dc 0d 58 22 4a 00` | `fmul 256.0` — тот же `d` для `uv_u_fp` | доказано |
| `0x43e122` | `dc 35 60 22 4a 00` | `fdiv 4.0` (`0x4a2260`) → `uv_u_fp` в 1/64 текселя | доказано |
| `0x43e132` | `89 41 54` | `mov [poly+0x54], eax` | доказано |
| `0x41bdb1` | `0f bf 51 50` | кадровый проход читает `uv_u` (`+0x50`) | доказано |
| `0x41bdcd` | `c1 e2 08` | `shl 8` → тексель в 16.16 (8.8 → 16.16) | доказано |
| `0x41be65` | `8b 51 54` | кадровый проход читает `uv_u_fp` (`+0x54`) | доказано |
| `0x41be68` | `c1 e2 0a` | `shl 10` → тексель в 16.16 (1/64 → 16.16) | доказано |
| `0x43cb79` | `dc 0d 98 22 4a 00` | лайтмап: `·64.0` — **тот же числитель** | доказано |
| `0x43cbc7` | `dc 35 80 22 4a 00` | лайтмап: `/2.0` | доказано |
| `0x43cc0d` | `c1 fa 0a` | лайтмап: `sar 10` = `N >> 11` | доказано |

### 1.1 Три независимых доказательства

1. **Писатель авто-UV** `0x43e02d` (его вызывает загрузчик для полигонов со
   сброшенным `poly+0x7c & 0x8000`: `0x425e07`, `0x432fc5`). Одна и та же
   геометрическая величина `d = dot(u_axis, centre−v)` (мировые единицы)
   пишется в оба поля, во второе — делённой на 4. Значит `uv_u_fp` ровно в
   4 раза грубее `uv_u`, а так как делитель в `uv_u` — 256, масштаб
   **1 тексель на единицу мира**. Дополнительный смысл: запись
   `uv_u += dot(centre−v)·256` ставит тексель 0 в выбранную вершину
   (обнуление UV «от угла»), что согласуется только со знаком
   `+dot(u_axis, v−centre)` в формуле выборки.
2. **Оба растеризатора** кадрового прохода переводят поле в 16.16 именно
   сдвигом `<<10`: `uv_u_fp · 2¹⁰ = uv_u_fp/64 · 2¹⁶`. Сдвиг `<<8` для
   `uv_u` даёт то же самое, если `uv_u` в 1/256. Любая другая единица
   (1/2048 и т. п.) сделала бы эти сдвиги бессмысленными; более того, сразу
   за ними идёт `sub` двух 16.16-координат (`0x41be6b`) — «свёртка» пары
   `uv_u`/`uv_u_fp` по ширине текстуры.
3. **Данные** (`texuv.py --stats`, всё на поставочных уровнях):

   * `(uv_u − 4·uv_u_fp) mod 64 == 0` для **всех** полигонов: `level0`
     1449/1449, `dm1` 5786/5786, `dm2` 12472/12472 — поля кодируют одно и то
     же с точностью до округления;
   * протяжённость текселя вдоль `u_axis` равна мировой протяжённости
     **бит в бит** у всех текстурных полигонов: `level0` 1088/1088,
     `dm1` 5053/5053, `dm2` 11543/11543 (отношение ровно 1.000, не медиана —
     `p10`/`p90` тоже 1.0).

Опровергнутые варианты: `/2048` даёт 1/32 текселя на единицу (в 32 раза
крупнее — «блоки»), `/32` — 2 текселя на единицу (вдвое мельче движка),
`uv="fit"` вообще игнорирует поля полигона.

### 1.2 Точность и округление — гипотеза

Движок ведёт расчёт в `double` (`0x43e0cd`.., `fild`/`fadd`) и лишь затем
переводит в целое (`ftol` `0x40e0e0`), а кадровый проход — через `float` и
16.16. Поэтому в `texuv.py` формула реализована как
`int(dot·64 + uv_fp) >> 6` (арифметический сдвиг, floor) и **может
отличаться от оригинала на ±1 тексель** на вершинах ровно на границе.
Для паритета картинки это шум; для побайтового сравнения — нет.

Отдельная странность данных: сдвиг `uv_u` относительно `4·uv_u_fp` всегда
кратен 64 единицам (1/4 текселя), а «осмысленные» величины кратны 4096
(16 текселей) — похоже на артефакт компилятора уровней. На формулу не
влияет: кадровый проход берёт базу из `uv_u_fp`, а `uv_u` — только для
свёртки (`0x41be6b`).

## 2. Полигоны без текстуры (доказано: пропускаются)

### 2.1 В цикле кадра проверки текстуры нет

Цикл видимых полигонов — `0x41ac99`..`0x41add0` (шаг записи полигона `0x80`,
`0x41aca3`). На каждый полигон он делает **две** проверки и затем зовёт
drawer:

| адрес | что |
|---|---|
| `0x41acb4` | `cmp [ebp-0x20], 0` — условие «оверлей/скан» (поля объекта, не текстура) |
| `0x41ad37` | `dot(normal, eye−centre)` — отсечение задних граней |
| `0x41adc8` | `call 0x41b6cb` — отрисовка; вызывается для **каждого** выжившего полигона |

Побайтовый скан всего диапазона на `movsx/movzx word [reg+0]`: **ноль
вхождений**. То есть индекс `poly+0x00` в цикле не читается вообще.

### 2.2 Проверка живёт в setup текстур

`0x41b6cb` (drawer) первой же инструкцией зовёт setup `0x9fde50`/`0x9fde70`
(`0x41b6dd`) и уважает код возврата: `0` — рисовать, `-1` — выйти, ничего не
нарисовав (`0x41b6e5`, `0x41b6e9` → `0x41c710`).

Внутри setup индекс берётся «объединением» полей (`0x9fde8e`..`0x9fdefc`):

```
ecx = (handle < 1) ? −0x78 : 0        # 0x9fde8e / 0x9fde91 / 0x9fde9d
tex = movsx word [poly + ecx + 0x78]  # 0x9fdefc: poly+0x00 либо poly+0x78
[0x9e8cac] = tex                      # 0x9fdf1f: «текущая текстура»
```

и затем (`0x9fdf24`..`0x9fdf3e`):

```
if (tex != 0)                    → рисовать
if ([0x9e8cd0] != 0)             → рисовать       # handle (poly+0x72)
if ([0x9e8d0c] != 0)             → рисовать       # object+0x70 & 0x10
if ([0x9e8c9c] != 0)             → рисовать       # class-dword от f7a
return −1                                        # 0x9fe4cb → ПРОПУСК
```

Якоря: `0x9fdf24` `85 c0`, `0x9fdf3e` `0f 84 87 05 00 00` (`je 0x9fe4cb`),
`0x9fe4cb` `b8 ff ff ff ff c3` (`mov eax,−1; ret`), `0x41b6e9`
`e9 22 10 00 00` (`jmp 0x41c710` — выход из drawer без геометрии).
Дополнительно setup отбрасывает `n_idx <= 2` (`0x9fde93` `80 7b 71 02`) и
полигоны за пределом арены (`0x9fde7c`).

**Вердикт: полигон с `poly+0x00 == 0` не рисуется вовсе.** Ни белым, ни
плоским цветом, ни «последней привязанной текстурой» — это `return`, а не
fallback.

### 2.3 Лазейки (рантайм, в данных не встречаются)

Полигон всё же проходит, если сработала любая из трёх проверок:

* `poly+0x72` (handle) `!= 0` — тогда индекс берётся из `poly+0x78`
  (оверлей), а не из `+0x00` (`0x9fdefc`);
* `object+0x70 & 0x10` — флаг объекта, ставится в рантайме;
* class-dword `[0x9e82c4 + (f7a + word[ctx+0x14])·0x40] != 0` — таблица
  классов текстур, статически не проверялась (см. §3).

Если полигон прошёл, а индекс остался 0, софт-маппер индексирует
`texture_table[−1]` (`0x41be0a`..`0x41be0e`) — «запись перед таблицей»,
величина неопределённая. Это не «белый цвет» и не «плоский цвет».

### 2.4 Данные

| уровень | всего | `texture == 0` | handle ≠ 0 | overlay ≠ 0 | f7a ≠ 0 | пропуск | прошли |
|---|---:|---:|---:|---:|---:|---:|---:|
| `level0` | 1449 | 361 (25 %) | 4 | 0 | 0 | 357 | 4 |
| `dm1` | 5786 | 733 (13 %) | 10 | 9 | 0 | 723 | 10 |
| `dm2` | 12472 | 929 (7 %) | 21 | 0 | 0 | 908 | 21 |

То есть в поставочных уровнях подавляющее большинство полигонов без текстуры
действительно пропускается; «прошедших» единицы процентов, и у них индекс
читается из оверлея.

**Важная поправка к `docs/ORACLE.md`.** Там сказано «429 из 1449 (30 %) имеют
`poly+0x00 == 0`». Фактически в `level0`: **361** полигон с `texture == 0` и
**68** с отрицательным индексом (`65534` = −2 — 53 шт., `65533` = −3 — 9,
`65532` = −4 — 2, `65535` = −1 — 1), всего 429. Отрицательный индекс — это
**таблица эффектов** (шаг `0x5c`, резолвер `0x41de7d`, вызывается из
`0x9fdf17`), такие полигоны движок **не** пропускает: они рисуются
эффектом. Смешивать их с «без текстуры» нельзя — это два разных пути.

## 3. Что осталось (гипотезы)

1. **`[0x9e82c4]`** — таблица классов текстур (шаг `0x40`), читается в setup
   (`0x9fdf01`). Статически не разобрана: заполняется в рантайме после
   загрузки уровня, ненулевое значение снимает пропуск. По данным `f7a == 0`
   у всех полигонов, так что индекс = `word[ctx+0x14]` (база уровня).
2. **`object+0x70 & 0x10`** — флаг объекта; в `.sbw` его нет (заголовок
   96 байт), значение рантайм-зависимое. Похоже на «рисовать даже пустое»
   (ср. `0x20000` — force-render владельца, `0x440d74`).
3. **`uv_u` против `uv_u_fp`.** Движок берёт базу из `uv_u_fp` (`0x41be65`), а
   `uv_u` использует для свёртки. Какое из двух полей «первично» в
   компиляторе уровней — не установлено (см. §1.2 про кратность 64).
4. **Скролл/анимация.** `uv_u += Δt·s16[0x5c]` (`0x41bdc4`..`0x41bdcb`) —
   уже описано в `docs/FORMATS.md`; в формулу выше входит как постоянная
   добавка к `uv_u` (и через свёртку влияет и на `uv_u_fp`-координату).
5. **Точное соответствие шага 16.16 ↔ пиксель** (какой LOD и какая
   фильтрация) — вне этой задачи, см. `docs/MIPMAPS.md`.

## 4. Формула → что видно на `win2`

Метрики из `docs/ORACLE.md` (world-полоса, `focal 160/133.33`, fitted
`pitch +8`) приведены как есть; последние две строки — **предсказание** по
доказанной формуле (кадры не перегонялись в этой задаче).

| вариант | формула | ожидание на `win2` | `win1` corr/edges | `win2` | `win3` |
|---|---|---|---|---|---|
| `uv="fit"` | одна копия на полигон | крупные «растянутые» пятна, решётки нет | +0.021 / 0.431 | +0.204 / 0.341 | +0.226 / 0.289 |
| `/2048` | лайтмап-делитель | блоки 32×32 единицы мира — «плитка» | +0.016 / 0.356 | +0.217 / 0.308 | +0.251 / 0.227 |
| `/32` | 2 текселя на единицу | решётка вдвое мельче движка | — | — | — |
| **`/64` (движок)** | `N >> 6` | настоящая решётка: 1 тексель = 1 единица | — | — | — |
| `/64` + пропуск без текстуры | + `skip_untextured` | решётка без бирюзовой «крупы» | **+0.127 / 0.496** | +0.110 / 0.360 | +0.133 / 0.264 |
| `/64` (измерено как `/64`) | | | +0.039 / 0.445 | +0.198 / 0.350 | +0.212 / 0.282 |

Что это значит для метрик: строка «`/64` + пропуск» — единственная, где
`win1` резко улучшается, и она же совпадает с тем, что делает движок.
Падение `corr` на `win2/win3` при пропуске объясняется тем, что эталонные
кадры содержат и то, чего наш рендер ещё не делает (небо/туман/эффекты,
`docs/SKY.md`, `docs/FOG.md`) — «крупа» там случайно коррелировала с
яркостью эталона. Поэтому ориентироваться надо на `win1` + визуальную
решётку, а не на сумму корреляций.

## 5. Что делать в `gm/render.py` (в этой задаче **не менялось**)

1. Режим `uv="texel"` с точной константой. В `LevelMesh` уже есть
   `face.uv_fp` и `face.u/v` (оси), поэтому формула — одна строка:

   ```python
   def uv(self, face, vertex):                    # uv="texel"
       d = _sub(vertex, face.origin)
       return (int((_dot(d, face.u) * 64.0 + face.uv_fp[0])) >> 6,
               int((_dot(d, face.v) * 64.0 + face.uv_fp[1])) >> 6)
   ```

   Не путать с `LevelMesh.uv()` (сырой `dot` в мировых единицах) и с
   `Lightmaps.uv()` (тот же числитель `>> 11`). Для справки: `gm/render.py`
   уже содержит точную лайтмап-формулу — текстурная отличается **одним
   сдвигом** (6 вместо 11).
2. Флаг `skip_untextured` (по умолчанию выключен, пока не сверены кадры):
   пропускать `face.texture == 0`. Отдельно и независимо: отрицательный
   `face.texture` — это эффект, а не «нет текстуры»; сейчас `LevelMesh`
   отдаёт для него `"none"` и рисует плоским цветом, что неверно (§2.4) —
   но это вопрос таблицы эффектов, а не флага.
3. Ожидаемые числа после включения: доля пропущенных полигонов 25 % на
   `level0`, 13 % на `dm1`, 7 % на `dm2`; тексель-решётка 1:1 с миром.
4. Режимы `/2048`, `/32` оставить только для сравнения — они не движковые.

```

python3 tools/re/texuv.py --self-test      # якоря + формула + данные (27 проверок)
```

константы `.rdata` (`256.0/4.0/64.0/2.0`), формулу на синтетическом
полигоне (тексель в центре, 1 единица = 1 тексель, дробные шаги,

детерминизм), согласованность таблицы режимов (`/2048` ровно в 32 раза
грубее `/64`, `/32` — вдвое мельче) и инварианты по трём поставочным
уровням.
