# Рендер экрана выбора уровня (`engine/src/ui/level_select_render.h`)

Срез 3 пункта `M8.4`: [`LevelSelect`](LEVEL_SELECT.md) знает 36 строк, курсор
и доступность, этот модуль **рисует экран 17** — `SELECT LEVEL FOR NEW GAME`
— в RGBA-буфер 320×200: плату `PLATE` (196×131), заголовок, до 10 строк с
курсором, стрелки прокрутки `MENUARRW` и `ESC TO CANCEL`. Ничего не измеряется
заново: атласы и метрики — из `render/text_layout` (`FONTS4` в
`FRONTEND/BMP.IDX`), имена — из `LVLNAMES.SLU`, координаты — из обработчика
`0x48a3c0`.

Код: `engine/src/ui/level_select_render.h/.cpp`; тест —
`engine/tests/test_level_select_render.cpp` (CTest `level_select_render`,
label `quick`). Канон поведения — `docs/LEVEL_SELECT.md`, `docs/UI_SCREENS.md`
§2/§3/§3.8/§9, `docs/MENU_RENDER.md` (те же шрифты и та же полоса платы).

Проверка:

```sh
cmake --build build --target gm_level_select_render_tests -j 4
./build/engine/tests/gm_level_select_render_tests
ctest --test-dir build -R '^level_select_render$' --output-on-failure
python3 regress.py --mirror --json
```

## 1. Что доказано (дизассемблер `0x48a3c0` и байты поставки)

Обработчик экрана — 90 инструкций, снятых `tools/re/disrange.py` в этой
сессии; всё, что ниже, взято из них, а не из картинки.

| факт | значение | источник |

| число строк | runtime-счётчик `ds:0x68ddb0` -> `[0x67f10c]` | `0x48a3c0`/`0x48a3c9` |
| шаг строки | 8 | `mov dword [0x662d58], 8` на `0x48a3ce` |

| стрелка вниз | `MENUARRW` при `scroll + 10 < count`, блиттер `0x485cc0`, те же 128 байт **вперёд** | сайт `0x48a438`..`0x48a44d` (`push 0xc4`, `push 0x68c33b`), `0x485cc0` |

| `ESC TO CANCEL` | `0x4bd9d8`, font 0, `centered=0`, `x=38`, `row=111` | `0x48a4a1`..`0x48a4b0` |

## 2. Модель (не доказано кодом)

* **Ориентация платы.** `PLATE` рисуется в порядке `parse_bmp` (top-down), как
  в `ui/menu_render`; на самой плате нет текста, поэтому в отличие от
  `HELPSCRN` (там `flipV` проверен по надписям) ориентацию нечем проверить.
  Обе ориентации выглядят правдоподобно; выбрана та же, что у соседнего
  рендера меню.
* **Экранный origin платы.** Не документирован (`UI.md` §8), поэтому полоса
  рисуется в (0,0) — та же условность, что у `ui/menu_render` и
  `ui/pager_render`.
* **Цвета** — палитра атласа: font 0 -> `130f0f` (тёмно-серый) с тенью
  `4b4b4b`, font 4 -> `efefef` (белый) с тенью `afafaf`, font 5 -> `9b0f0f`
  (тёмно-красный) с тенью `6b473b`. Это цвета `FONTS4` (те же, что в
  `docs/MENU_RENDER.md` §3); «какой номер шрифта какому ассету» в бинарнике не
  привязан (`UI_SCREENS.md` §11), здесь используется раскладка `text_layout`
  (`font_table_spec`), проверенная на кадре HUD.
* **Порядок строк** — кампанийный порядок `LevelSelect` (см.
  `docs/LEVEL_SELECT.md` §2): в оригинале это скан каталога с сортировкой
  `0x48b350`, а не таблица.
* **`\r` в имени** не рисуется: рендерер пропускает `CR`/`LF` (как
  `ui/menu_render`). В оригинале байт уходит в блиттер, но глифа у него нет,
  так что картинка та же; счётчик `missing_glyphs` его не считает.
* **Заголовок центрируется по полосе 196 px**, а не по 320: `0x485dd0`
  считает `(196 - width)/2` независимо от `x=38`.
* **Состояние `unlocked` не рисуется.** В оригинале блокировок нет
  (`LEVEL_SELECT.md` §2), маркера для них не документировано, поэтому
  заблокированные строки выглядят как доступные: кадры при счётчике 1 и 25
  побайтово одинаковы (тест, 0 отличающихся пикселей).
* **Порядок байтов стрелки.** Блиттер `0x485cc0` копирует 128 байт файла
  вперёд (16 в строке, 8 строк), `0x485d00` — те же байты назад, поэтому
  «вниз» — это файловый порядок строк, «вверх» — поворот на 180°. В рендере
  спрайт читается в файловом порядке (через `parse_bmp` с обратным индексом
  строки, потому что `parse_bmp` отдаёт BMP снизу вверх), а не в порядке
  «как нарисовано в редакторе»; сама плата по-прежнему рисуется в порядке
  `parse_bmp` (§2) — расхождение ориентации платы и стрелок унаследовано от
  той же недоказанной ориентации платы.
* **Палитра стрелки** берётся из `MENUARRW`; она побайтово совпадает с
  палитрой `PLATE` (256/256), так что на кадре это неразличимо, но привязка
  «индекс → цвет» остаётся на ассете, как у шрифтов и фона.
* **Пиксели стрелок не входят в `ink_pixels`**: счётчик остаётся «чернилами
  глифов» (см. §4), а стрелки тест считает отдельно по своим прямоугольникам.

## 3. Имена: что видно на этой установке

`0x48a4c0` сравнивает байты, без складывания регистра, и требует пробел после
ствола. В поставке 3dfx-версии файлы уровней — `level1.sbw` (нижний регистр),
а `LVLNAMES.SLU` — `LEVEL1 Testing Range` (верхний). Поэтому на **этой**
установке ни один из 36 стволов не находит строку, и экран показывает
`level1`, `level2`, … — ровно как игра. Печатные названия появляются на
установке с верхним регистром имён (`LEVEL1.SBW`, CD-раскладка); правило
реализовано, регистр не складывается.

Тест проверяет обе ветки: настоящий файл (`matched=0/24`, `LEVEL1` ->
`LEVEL1 - Testing Range\r`) и синтетический `LVLNAMES.SLU` нижним регистром во
временном каталоге (`FRONTEND` — симлинк на поставку, только чтение):
`level1` -> `level1 - Title 00`, чернила растут, все 10 полос сверяются
побайтово с независимым блитом. Отсутствие файла — не ошибка: стволы, кадр
побайтово равен кадру с настоящим файлом (на этой установке).

## 4. API

```cpp
#include "ui/level_select.h"
#include "ui/level_select_render.h"

gm::CampaignState campaign;
campaign.load(1);                     // 7 доступных уровней

gm::LevelSelect select;
select.build(campaign, nullptr);      // 36 строк кампанийного порядка

gm::LevelSelectRenderOptions options;
options.background = "PLATE";         // пусто = чёрный холст
// options.title / options.cancel — по умолчанию true

std::vector<std::uint32_t> rgba;      // 0xRRGGBBAA
int width = 0, height = 0;
gm::LevelSelectRenderStats stats;
std::string error;
if (!gm::render_level_select("/mnt/d/games/Gunmetal 3dfx", select, options, rgba,
                             width, height, &stats, &error)) {
    // текст причины: пустой список, нет каталога игры, нет BMP.IDX,
    // нет/битый/не 8bpp background
}
// width=320 height=200 rgba.size()==64000
```

`LevelSelectRenderStats`: `rows` — сколько строк нарисовано
(`min(размер списка, 10)`), `selected_row` — индекс курсора в
`LevelSelect::levels()` (то есть на какой видимой полосе подсветка),
`ink_pixels` — пиксели холста, закрытые хотя бы одним пикселем глифа
(уникальные, не зависят от фона), `missing_glyphs` — символы без глифа
(пропускаются, не фатальны), `arrows` — сколько спрайтов `MENUARRW`
нарисовано (0..2: вверх при `scroll > 0`, вниз при `scroll + 10 < count`).
Пиксели стрелок в `ink_pixels` не входят.

Контракт ошибок: на отказе `rgba` очищается, `width`/`height` = 0, `stats`
обнуляется — устаревшей или полунарисованной картинки не бывает. Если
стрелка нужна, а `MENUARRW` в `FRONTEND/BMP.IDX` нет или он не 16×8, кадр
отказывает текстом `level_select_render: arrow MENUARRW: ...`; кадр без
стрелок (окно в начале и в конце списка) такой ассет не читает.

Утилиты с доказанной семантикой (ими же пользуется тест):

* `int level_select_scroll(int count, int selected)` — начало окна по
  `0x48a3f1`..`0x48a416`: 7 строк -> 0; 36 строк и курсор 0/5/6/19/24/35 ->
  0/0/1/14/19/26;
* `std::string level_select_name(std::string_view stem, std::string_view lvlnames)` —
  текст строки по `0x48a4c0` (побайтовое `<stem> `, `"<stem> - "` + остаток,
  максимум 30 символов, иначе ствол).

Контракт ошибок: на отказе `rgba` очищается, `width`/`height` = 0, `stats`
обнуляется — устаревшей или полунарисованной картинки не бывает.

## 4b. Точный fade (`fade_lut`, срез 8)

`HudLut` — таблица **индекс → индекс**, поэтому к готовому RGBA-кадру она
честно не прикладывается. Этот рендерер и так берёт цвет из палитры источника
(`PLATE`, `MENUARRW`, атлас глифа), поэтому минимальный индексный слой сделан
внутри него: перед `palette_colour` индекс каждого пикселя идёт через
`render/hud_lut.h::map(levels, index)`. Пиксели без индекса (чёрный холст без
`background`) не трогаются — как в движке, где буфер всегда 8 bpp.

```cpp
gm::HudLut lut;
gm::build_hud_lut(*gm::installed_palette(game, err), lut, &err);  // без файла

options.background = "PLATE";
options.fade_lut = true;
options.fade_lut_level = 0;      // 0..15: 11 — тождество, 12..15 светлее
options.fade_lut_table = &lut;   // приоритетнее дампа
// или: options.fade_lut_dump = "/home/<user>/.cache/gunmetal-re/hud_lut.bin";
```

* `fade_lut_table` (указатель, владелец — вызывающий) приоритетнее
  `fade_lut_dump`; дамп читается `load_hud_lut` (ровно 4096 Б). Нет ни
  таблицы, ни дампа — `level_select_render: fade LUT needs a table
  (fade_lut_table) or a dump (fade_lut_dump)`; нет файла — `...
  fade LUT: hud_lut: cannot read '...'`. На отказе `rgba` очищается, как у
  остальных ошибок.
* Таблица строится из `FRONTEND/GAMEPAL` в памяти (`build_hud_lut`), файл не
  нужен; на этой поставке она побайтово равна дампу (4096/4096,
  [HUD_LUT.md](HUD_LUT.md) §2b). Путь с дампом — вторая проверка того же
  результата.
* RGBA-модели (`fade`/`fade_level`) в этом модуле нет, так что `fade_lut` —
  единственный путь затемнения и ни с чем не конкурирует; уровни 12..15 не
  клампятся к 11 (в движке это реальные таблицы, они осветляют).
* Индекс, который таблица выводит за пределы палитры источника, — отказ
  (`... fade LUT level L maps index I to M, outside the K-entry palette`).
  Дамп пишет 0..255, поэтому на 256-записной палитре это недостижимо, но
  укороченный атлас ловится вместо тихой подмены цвета.

Что стоит за числами:

* **окно** — правило `0x48a3f1`..`0x48a416` как числа: список из 7 строк
  всегда с 0; 36 строк и курсор 0/5/6/19/24/35 -> 0/0/1/14/19/26; крайние
  случаи (пустой и отрицательный список, курсор вне списка) дают 0/кламп;
* **имена** — в настоящем файле **30** непустых строк (плюс пустая строка
  `\r` в конце), совпадений с 36 стволами **0** из-за регистра; `LEVEL1`
  даёт `LEVEL1 - Testing Range\r` (CR попадает в буфер, как в `0x48a4c0`),
  `LEVEL10` не путается с `LEVEL1`, ствол без пробела не совпадает, текст
  обрезается до 30 символов;
* **counter=1** — список всё равно 36 строк (кампанийный корпус), доступно
  **7**, нарисовано `rows=10` (окно с 0, `level1`..`level10`), `ink=1305`.
  Заголовок: bbox (26,14), ширина 142 = `measure - 1` (последний advance
  несёт `+1` трекинга), x = `(196 - 143)/2` = 26; первая строка (14,27),
  ширина 22; `ESC TO CANCEL` (38,111), ширина 72; alpha 255 во всех 64 000
  пикселях; `missing_glyphs=0`; все 11 полос побайтово равны независимому
  блиту из `load_font`; сумма чернил полос равна `ink_pixels`; цвета:
  заголовок `6b473b`+`9b0f0f` (font 5), строка курсора `afafaf`+`efefef`
  (font 4);
* **состояние разблокировки на кадр не влияет**: counter 1 и counter 25 дают
  побайтово одинаковый кадр (0 отличающихся пикселей) — в оригинале
  блокировок нет, и маркера для них не документировано;
* **`PLATE`** как фон: 25 676 пикселей полосы 196×131 независимо
  декодируются тестом (`BigFile` + `parse_bmp`), 38 324 вне полосы остаются
  чёрными, текст не меняется (`ink=1305`), расхождений 0;
  `menu_panel_asset(Screen::LevelSelect) == "PLATE"` — та же плата, что у
  меню;
* **точный fade** (срез 8): на `counter=1` с `PLATE` уровень **11** даёт
  **0** отличий от кадра без fade (чернила, строки и стрелки те же); уровень
  **0** — **63 981** чёрный пиксель из 64 000 (19 нечёрных — это слоты вне
  рамп, которые таблица не трогает; без fade 38 324) и **25 657** отличий от кадра без fade; уровни 12/13/14/15 — четыре разных кадра
  (соседние 17 702 / 23 103 / 20 877, против 11 — 16 495 / 24 620 / 24 854 /
  25 565). Таблица строится из `GAMEPAL` в памяти (`build_hud_lut`), без
  файла; дамп, когда он есть, даёт те же байты. Отказы без таблицы/дампа и с
  несуществующим дампом проверяются текстом (`fade LUT`, `hud_lut`) и
  очисткой буфера;
* **counter=25** — 36 записей, `rows=10`; курсор 0 -> строки 0..9; выбор
  20-й строки (`level20`, индекс 19) -> `scroll=14`, видимы
  `level15`..`level24`, курсор на полосе 5; индекс 24 -> `scroll=19`
  (окно 19..28); индекс 35 (`dm4`) -> `scroll=26` (окно 26..35, курсор на
  полосе 9); кадры 0 и 19 отличаются на **478** пикселей: 437 — полосы строк,
  41 — появившаяся стрелка вверх (кадр 0 её не имеет), других отличий вне
  полос строк нет; все 10 полос каждого окна сверены с независимым блитом;
* **выключатели и курсор** — `title=false` снимает 364 пикселя (чернила
  полосы заголовка), `cancel=false` — 185, оба — 756 остаётся (только
  строки); ничего вне своей полосы не меняется; ход курсора 0 -> 1 меняет
  **141** пиксель, все — в полосах 0/1, у выбранной строки появляется
  `efefef`;
* **стрелки** — `MENUARRW` (16×8, 41 ненулевой байт) декодируется тестом
  прямо из BMP (`bfOffBits`, файловый порядок строк) и сравнивается
  попиксельно: при `scroll=0` (курсор 0) верхнего прямоугольника нет вовсе, а
  нижний — ровно **41** пиксель с bbox **(160,123)-(173,127)**; в середине
  списка (курсор 19, `scroll=14`) есть оба: нижний тот же, верхний — **41**
  пиксель с bbox **(160,3)-(173,7)**, и это единственное отличие от кадра 0
  вне полос строк (**41** пиксель); в последнем окне (`scroll=26`,
  `26 + 10 = 36`) нижней стрелки нет, верхняя на месте. Чернила кадра целиком:
  1346 (низ), 1514 (середина), 1313 (верх) — против 1305 «только текст»;
  `stats.arrows` = 1/2/1;
* **негативы** — пустой список, пустой путь игры, каталог без
  `FRONTEND/BMP.IDX`, `background="NOSUCH"`: у каждого текст с префиксом
  `level_select_render:`, буфер очищен, `stats` нули. Без `LVLNAMES.SLU`
  кадр собирается (стволы) и на этой установке побайтово равен кадру с
  настоящим файлом (`ink=1305`); синтетический файл нижним регистром
  (временный каталог, `FRONTEND` — симлинк) даёт `ink=2213` (+908) и
  `level1 - Title 00` в первой полосе.

## 6. Ограничения

* **Стрелки нарисованы (срез 5)**: обе — из `MENUARRW`, якоря и условия
  доказаны адресами (§1) и закреплены тестом (41 пиксель, bbox
  (160,123)-(173,127) и (160,3)-(173,7)). Сверка — с листингом и ассетом;
  живой кадр оригинала в этой среде не снимался, поэтому «так же, как на
  экране» проверено по коду и данным, а не по скриншоту.
* **Ориентация платы** остаётся моделью (§2): стрелки рисуются в файловом
  порядке спрайта, плата — в порядке `parse_bmp`; если ориентация платы
  когда-нибудь подтвердится обратной, стрелки надо будет перевернуть вместе
  с ней (одна константа на спрайт).
* **Нет звука** `updown` и кликов (`ui/ui_sounds.*`), нет курсора мыши.
* **Нет миниатюр/превью уровней** и нет рамки: у экрана 17 их и нет в
  поставке (`UI_SCREENS.md` §9 — только `plate` и `menuarrw`).
* **CLI — есть (срез 4)**: `--level-select [--level-select-counter N]
  [--level-select-row N] [--no-plate] [--png OUT] [--png-scale N]`.
  `show_level_select` печатает `level_select: counter=1 rows=36 unlocked=7
  selected=0 (level1)`, затем `render: rows=10 selected=0 320x200 ink=1305
  missing=0` и PNG 256 283 Б; CTest `cli_level_select`, `_png`, `_scroll`,
  `_scale`. Плата `PLATE` рисуется по умолчанию, `--no-plate` оставляет
  чёрный холст. К фронтенду и `GameRuntime` не подключено.
* **Порядок, разблокировка и `selected`** — из модели `LevelSelect`
  (`LEVEL_SELECT.md` §2), не из скана каталога.
* **CLI точного fade — есть**: `--level-select --fade-lut N` (общий флаг с
  `--pager`), уровень 11 = кадр без fade, 12..15 различаются
  (`cli_fade_lut`). Было: `--fade-lut N` для
  `--level-select` в этом срезе не выведен (флаг только в API), `main.cpp` и
  `config.*` не менялись.
* **Имена** на этой установке — стволы (§3); печатные названия требуют
  установки с верхним регистром имён, регистр намеренно не складывается.
* **Ориентация платы и origin** — модель (§2).
