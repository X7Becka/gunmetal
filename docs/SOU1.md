# `SOU1`: 4-битный ADPCM Miles — разобран

Статус: **блокер закрыт**. Независимая модель (`tools/re/sou1_model.py`)
побайтово совпадает с эмулятором реальных инструкций `gundx.exe` на всех
**983** записях `SOU1` из `sounds/SOU.IDX` (67 939 382 слота, 2123.1 с
звука). FNV и длительности зафиксированы в
`docs/manifests/sou1-fnv.json`.

Прежнее утверждение «на длинных треках сигнал расходится, модель начального
состояния/адаптации не полная» **опровергнуто**: расходился стенд
`tools/re/sou_decode.py`, а не кодек (см. §5).

## 1. Контейнер и каналы

`SOU1` — 16-байтный заголовок (`magic`, `u32 rate`, `u32 flags`, `u32 length`)
и payload `data[16:16+length]` (§5.1). В поставке 983 записи:

| rate | flags | записей | режим | слотов на байт |
|---|---|---|---|---|
| 8000 | 0 | 361 | моно, 4 копии | 8 |
| 16000 | 0 | 607 | моно, 2 копии | 4 |
| 32000 | 0 | 9 | моно, 1 копия | 2 |
| 32000 | 1 | 6 | стерео, 1 копия | 2 на канал |

Для чётности используется `length & ~1` (загрузчик `0x40b0dd` делает
`and al,0xfe`); хвостовой байт при нечётной длине игнорируется.

Стерео-записи (CUT-EMP, CUT-PAM, CUT-PREZ, INTRO, VRCHAMBR, VRCHAMHQ) лежат в
payload **чересперепутанными по нибблам**. Загрузчик (`0x40b2d8..0x40b313`)
раскладывает каждую пару байт `A B` в два байта:

```
left  = (A & 0xf0) | (B >> 4)
right = ((A << 4) & 0xf0) | (B & 0x0f)
```

Размер каждого канала — `length/2` (`0x83d974`, запись в `0x40b0e8`), каналы
декодируются независимо, у каждого своё состояние. Это же значение лежит в
поле `+0x14` структуры сэмпла (`0x83d974`), откуда оно попадает в `voice+0x14`
и используется микшером как смещение второй половины (`0x409ee5`).

## 2. Алгоритм

Три функции отличаются только числом копий:

* `0x852b40` — 1 копия (`rate >= 18000`);
* `0x852c00` — 2 копии (`10000 <= rate < 18000`);
* `0x852cc0` — 4 копии (`rate < 10000`).

Выбор — в загрузчике `0x40b246`: `cmp rate,0x2710` → `cmp rate,0x4650`; там же
`length << 3 / << 2 / << 1` даёт число выходных слотов (`0x40b258`,
`0x40b27d`, `0x40b295`).

Цикл (`0x852ba0` для `0x852b40`, аналогично в двух других):

```
code  = byte >> 4                  ; затем byte & 15
delta = [table_ptr + level + code*4]   ; 32-битная знаковая
acc   = (acc + delta) & 0xffffffff
level = (level + [0x850500 + code*4]) & 0xffffffff
emit acc                            ; copies раз
```

В реальном коде это `add ebx,[ecx+eax+disp]` (`0x852ba0`/`0x852bbc`),
`add ecx,[eax+0x850500]` (`0x852ba7`/`0x852bc3`), вывод —
`add [edi],ebx` (`0x852bb2`) и `add [edi-4],ebx` (`0x852bce`). Важно: вывод
**прибавляется** к буферу, а не записывается; для автономного декода буфер
должен быть нулевым.

`step[16]` при `0x850500`:

```
-64 -64 -64 -64   128 256 384 512
-64 -64 -64 -64   128 256 384 512
```

## 3. Таблицы дельт: одна общая кривая

Массив указателей `0x850480[32]` (`vol & 31`) даёт стартовые адреса
`0x850540, 0x850640, 0x850700, … 0x850c80`. Это **не 32 отдельные таблицы по
16 дельт**, а одна непрерывная кривая `0x850540..0x8522c0` (0x1d80 байт,
118 строк по 16 dword'ов). `level` — байтовое смещение *внутри* кривой, и
адаптация свободно ходит по ней. Сразу за `0x8522c0` лежит step-таблица
`SOU2` (`-4 ×16`, затем `8,16,…,128`), поэтому выход за конец кривой было бы
видно как мусор.

Измерено на всём корпусе (volume 31):

* максимум `level` = **0x1600** (запись `ADON`);
* максимум читаемого адреса = **0x8522ac**, до конца кривой 0x13 байт;
* максимум `|acc|` = 0x100000 (2^20), 32-битного переполнения нет; даже если
  бы было, x86-сложение всё равно считается mod 2^32, и модель это повторяет.

Зажима `level` в коде нет — и не нужно: валидные потоки держатся внутри
кривой. Указатель выбирается байтом `[0x84a6a8] = volume - 1`, где
`volume` 1..32 вычисляется из громкости и панорамы в `0x40a4b0`/`0x40a690`;
максимум даёт индекс 31.

## 4. Начальное состояние и микшер

Состояние — 8 байт `{acc, level}` на канал. Голос — структура из 0x50 байт,
база `0x84e068`, 8 голосов (`0x409dcc`: `lea ecx,[edx+edx*4]; shl 4`).
Микшер передаёт декодеру указатели `voice+0x40` (левый) и `voice+0x48`
(правый): `0x409ea4`/`0x409ec9` для 4 копий, `0x409f49`/`0x409f69` для 2,
`0x40a007`/`0x40a026` для 1.

Старт голоса — `0x40a5e0`. Он обнуляет **все четыре** dword'а состояния:

```
0x40a64d  mov [eax+0x84e0ac],ecx   ; voice+0x44 (level L)
0x40a653  mov [eax+0x84e0a8],ecx   ; voice+0x40 (acc L)
0x40a659  mov [eax+0x84e0b4],ecx   ; voice+0x4c (level R)
0x40a65f  mov [eax+0x84e0b0],ecx   ; voice+0x48 (acc R), ecx = 0
```

Значит новый сэмпл всегда начинается с `acc = level = 0`; отдельного
«начального состояния из потока» нет — в заголовке `SOU1` только rate/flags/
length.

Микшер работает кадрами: `0x409dd8` выбирает голос, `0x409dde` берёт
`count = min(voice[0], 0x400)` (не больше 1024 слотов), декодирует в два
буфера и в конце прибавляет к источнику `count >> 3 / >> 2 / >> 1` байт
(`0x409eff`, `0x409f9c`, `0x40a05c`). Состояние между кадрами **не
сбрасывается**, поэтому один вызов на весь payload эквивалентен покадровому
(при условии, что границы вызова кратны числу слотов на байт).

Второй канал (`flags == 1`) декодируется из `voice[0x10] + voice[0x14]`
(`0x409ee5..0x409ee8`), где `voice[0x14]` — смещение второй половины
деинтерливированного буфера.

## 5. Почему раньше «расходились длинные треки»

Старый `tools/re/sou_decode.py` использовал плоскую память так:

```
payload @ 0x200000, output @ 0x300000, state @ 0x400000
count = len(payload) * factor
```

Декодер пишет `4*count` байт выхода. Слот с номером `0x40000` (262144)
попадает по адресу `0x300000 + 0x40000*4 = 0x400000`, то есть **ровно в
`{acc, level}`**. С этого места эмулятор декодирует уже с затёртым
состоянием — отсюда «расхождение на длинных треках».

Проверено на реальных записях старым стендом:

| запись | rate | payload | слотов | первый неверный слот | адрес |
|---|---|---|---|---|---|
| PRAM | 16000 | 248864 | 995456 | 262144 = 0x40000 | 0x400000 |
| SOYBOY | 32000 | 263500 | 527000 | 262144 = 0x40000 | 0x400000 |
| INTRO (канал 0) | 32000 | 288000 | 576000 | 262144 = 0x40000 | 0x400000 |

Второй нюанс — буфер не обнулялся. Пока выход лежал ниже образа (`0x300000`),
там были нули, и это не мешало; но если output перекрывает загруженный образ
(например, `0x401000` — начало `.text`), `add [edi],ebx` прибавляет сигнал к
байтам exe. Поэтому исправленный стенд:

* держит состояние в `0x0E0000`, payload в `0x100000`, выход в `0x300000`;
* обнуляет выходной участок перед каждым куском;
* декодирует кусками по `0x10000` слотов (кратно 2/4/8) с сохранением
  состояния — как микшер.

## 6. Проверка

Модель (чистый Python, без x86) — `tools/re/sou1_model.py`; эталон —
`decode_stream_emu`, исполняющий байты `0x852b40/0x852c00/0x852cc0` через
`tools/re/x86mini.py`.

```sh
python3 tools/re/sou1_model.py --verify --json /tmp/opencode/sou1_manifest.json
python3 tools/re/sou1_model.py --check docs/manifests/sou1-fnv.json  # ~40 с
python3 tools/re/sou1_model.py --verify --limit 40
python3 tools/re/sou1_model.py INTRO out/intro.wav
python3 tools/re/sou_decode.py INTRO out/intro.wav   # тот же результат, эмулятор
```

Результат полного прогона: **983/983 записей bit-exact**, 0 расхождений,
67 939 382 слота (2123.1 с при 32 кГц). Для каждой записи в манифесте
зафиксированы: `rate`, число каналов, `payload_bytes`,
`slots_per_channel`, `seconds`, FNV-1a64 32-битного PCM (`fnv1a64`), FNV-1a64
16-битного PCM после `>>5` с клипом (`fnv1a64_pcm16`) и FNV по каналам.

`SILENCE` (400 байт, 8000 Гц) — 3200 слотов ровно, суммы дельт по циклу
`4b 0c 20` сбалансированы, аккумулятор колеблется около нуля; это по-прежнему
удобный smoke-тест.

## 7. Опровергнутые гипотезы

* **«Начальное состояние не ноль / грузится из потока»** — нет: `0x40a5e0`
  обнуляет `voice+0x40..0x4c`, в заголовке состояния нет. Модель с нулём
  сходится на всех записях.
* **«32-битное переполнение/сдвиги»** — аккумулятор и `level` действительно
  32-битные и складываются mod 2^32, но на корпусе `|acc| <= 0x100000`, а
  `level <= 0x1600`; расхождения из-за переполнения нет. Модель повторяет
  арифметику x86 один в один.
* **«`level` уходит за таблицу»** — таблица не 16 элементов: это кривая
  0x1d80 байт, `level` — смещение в ней; максимальный адрес корпуса
  `0x8522ac` на 0x13 байт ниже конца. Зажима нет и не требуется.
* **«Таблицы грузились из отсутствующих AIL-сегментов»** — для `SOU1`
  неверно: указатели, шаги и кривая лежат в `adpcmseg` (`0x850480`,
  `0x850500`, `0x850540..0x8522c0`).
* **«Длинные треки расходятся из-за модели адаптации»** — нет: расходился
  стенд (перекрытие выхода и состояния на слоте 0x40000).

## 8. Что осталось (вне кодека)

* Python-оракул `gm/sou.py` и C++-движок пока не декодируют `SOU1` — это
  отдельная задача интеграции; исследовательский декодер готов.
* Точная формула громкости/панорамы (`0x40a4b0`, `0x40a690`) в модель не
  переносилась: кодек принимает готовый индекс таблицы 0..31; сверка идёт на
  индексе 31 (полная громкость).
* Точное преобразование 32-битного аккумулятора в 16-битный PCM на выходе
  микшера не трассировалось. В WAV используется `acc >> 5` (наблюдаемая полная
  шкала аккумулятора ≈ 2^20), но гейн микшера игры может отличаться; эталон в
  тесте — сырые 32-битные слоты.
