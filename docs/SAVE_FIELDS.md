# Поля сейва Gunmetal: карта «поле → смещение → смысл → доказательство»

* **Статус:** карта заполнена для всех групп, которые читает/пишет сейвер;
  **83 поля доказано**, **31 гипотеза**, **14 полей неизвестны**.
* **Инструмент:** `tools/re/save_fields.py` (stdlib-only, без импорта `gm.sbt`).
* **Проверки:** `--check` — 2/2 файла, `--self-test` — 13/13 негативных
  случаев, `--diff saved0.sbt saved1.sbt` — см. §11.
* **Игра:** только чтение (`/mnt/d/games/Gunmetal 3dfx`).
* **Дата:** 2026-10-20, ветка `feat/save-fields`, база `master` `78e93d5`.

Обозначения доказательств:

* **код** — адрес в `gundx.exe` (ImageBase `0x400000`) доказывает раскладку,
  писателя или потребителя;
* **данные** — значение проверено на обоих поставочных сейвах (2/2) или на
  всех записях блока (25/25 дверей, 24/24 переключателя и т. д.);
* **гипотеза** — раскладка и писатель известны, смысл потребителя — нет;
* **неизвестно** — нет ни читателя, ни внятного смысла.

Карта снимается самим инструментом:

```
python3 tools/re/save_fields.py --map            # карта
python3 tools/re/save_fields.py --map --verbose  # карта + xref/доказательства
python3 tools/re/save_fields.py --json           # карта + разобранные сейвы
python3 tools/re/save_fields.py --check          # валидация файлов
python3 tools/re/save_fields.py --self-test      # негативные кейсы
python3 tools/re/save_fields.py --diff A B       # сравнение по полям
```

`--check` возвращает 0 при успехе и 2 при найденных проблемах; ошибка
разбора (битый контейнер) — код 1. Пути по умолчанию берутся из
`SAVEGAME/*.sbt` установки, можно передать свои файлы позиционными
аргументами.

## 1. Контейнер и блоки

Заголовок — ровно `0x13c` байт, дальше поток `[u8 id][payload]`, последний
байт — `0xff` (EOF). Выравнивания, контрольной суммы и хвоста нет.
Подробности контейнера — `docs/SAVE.md`; ниже только то, что нужно для
адресации полей. Размер блока в таблице включает байт типа.

| id | блок | раскладка payload | размер в saved0 |
|---|---|---|---|
| 12 | sound table | `300 × u32` counts + `300 × 9` имён | 3901 |
| 20 | SOB table | `u32 n` + `n × 20` | 1345 |
| 15 | poly handles | `u32 n` + 4 колонки | 1669 |
| 17 | sector handles | `u32 n` + 2 колонки | 213 |
| 5 | named items | `u32 n` + `n × 52` | 57 |
| 4 | thing types | `u32 n` + `n × 936` | 53357 |
| 11 | script | runtime-форма things/named/code/tables | 76345 |
| 2 | doors | `u32 n` + `n × 0xB8` | 4605 (n=25) |
| 1 | switches | `u32 n` + `n × 0x20` | 773 (n=24) |
| 6 | sprites | `u32 n` + `n × 0x2c` | 181 (n=4) |
| 19 | ITEM | ровно `0x7080` = 300 × `0x60` | 28801 |
| 8 | SECTOR_STUFF | ровно `0x5800` = 256 × `0x58` | 22529 |
| 7 | sound sources | `u32 n` + `n × 28` | 173 (n=6) |
| 3 | things | 260 × (`u8 present` + `[0x528]`) | 8181 (6/260) |
| 9 | player | 8 слотов + две пары `0x50 + 0x3510` | 40921 |
| 255 | EOF | — | 1 |

Блоки 1, 2, 6, 7, 18 при `count <= 0` не пишутся вовсе (в сейвах LEVEL0
блок 18 отсутствует). Блоки 4, 5, 11, 12, 15, 17, 20 — уже разобранные
кодеки `gm.sbt`; их поля в эту карту не входят.

## 9. Игрок: блок 9, структура `0x3510`

### 9.1. Раскладка блока

```
повторить 8 раз:
    u8 present                     # 0/1, флаг и структура чередуются
    если 1:
        0x3510 байт структуры
        для k = 0..15:
            если u32(struct + 0x317c + 4*k) != 0:
                16 байт вложенной записи
затем 2 × (char[0x50] header + 0x3510 struct)
```

Это **не** «8 флагов подряд»: первая версия парсера читала их подряд и
получала мусорный флаг из первого байта позиции. Проверка `present ∈ {0,1}`
теперь ловит такую ошибку (см. §12).

В `saved0`/`saved1`: флаги `1,0,0,0,0,0,0,0`, вложенных записей нет;
у первой пары header — `LEVEL0`, у второй — пустая строка. Payload блока —
40920 байт: `8 + 0x3510 + 2*(0x50 + 0x3510)`.

## 10. Блок things (3)

Блок 3 — не таблица фиксированных записей: 260 × (`u8 present` +
`[0x528]`). В сейвах присутствует 6 слотов; размер 8181 =
`1 (тип) + 260 (флаги) + 6*0x528`. Поля внутри `0x528`-записи в эту карту
не входят (это runtime-состояние «вещей»); инструмент проверяет только
флаги и границы. Единственное различие saved0/saved1 в блоке — слот 0
(86 байт), см. §11.

## 13. Опровергнутые гипотезы

1. **«8 флагов игроков идут подряд».** Нет: флаг и `0x3510`-структура
   чередуются. При чтении подряд первый «флаг» получается из байта позиции.
2. **«F1 — миллисекунды».** Код завершения делит F1 на 91, а формат
   `0x483f00` трактует результат как секунды (делит на 60 и 10). Значит,
   игровые часы считают 91 единицу в секунду. Это уточняет
   `docs/SOO.md` §3.3: «мс» относится к шкале анимаций (`0x9e82d8`), а не к
   сейвовым часам `0x5a46e4`. Само деление на 91 — доказано; вывод о
   91 Гц — прямое следствие.
3. **«F0 — флаг состояния».** Это число слотов игрока; F0 и F16 пишутся
   вместе в `0x44d196`.
4. **«Дверь +0x48 — углы».** Это дельта движения бокса; в покое 0 во всех
   25 записях.
5. **«Спрайт +0x1c — амплитуда jitter».** Это render-флаги (аргумент 11,
   биты 1/2/4). Разброс позиции делает отдельный код `0x4592c2`, и в
   LEVEL0 он вернул 0.
6. **«ITEM +0x54 — самостоятельное поле».** Это старшая половина op6,
   записываемая тем же обработчиком `0x4686a0`.
7. **«SECTOR_STUFF +0x40 — один u32 урона».** Нет: два u16
   (`+0x40`/`+0x44`) с padding между ними; writer пишет половины раздельно.
8. **«SECTOR_STUFF +0x18 — движение».** Писатель известен, читателя нет:
   статус гипотезы.
9. **«Броня 0..100».** Единицы — сотые: 10000 = 100.00, щит 8000 = 80.00.
10. **«history_index — число записей».** Это следующий слот кольца по
    модулю 240 (`0xf0`), 194 → 130.
