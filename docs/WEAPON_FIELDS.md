# Карта записей «оружие / боеприпасы / оборудование / шасси» (M2.3.5)

**Статус:** карты восстановлены по коду игры (только чтение), проверены на
`level0.sbt` и `dm1.sbt`; инструмент — `tools/re/weapon_fields.py`
(`--map`, `--file`, `--verify`, `--self-test`).
Таблицы SBT — `docs/FORMATS.md` §12.3, рантайм оружия — `docs/WEAPONS_CPP.md`,
шасси — `docs/PLAYER_GHIDRA.md` §1, `docs/PLAYER.md` §5.

## 1. Метод

Запись таблицы в памяти — не копия файла: обработчик опкода читает операнды из
скриптового буфера и передаёт их как список аргументов **store-функции**, а та
раскладывает их по фиксированным смещениям. Поэтому карта снимается в два шага:

1. **store-функция → «параметр → смещение».** Декомпилятор даёт
   `(…&DAT_00BASE + i*stride) = param_N`, т.е. точный адрес записи каждого
   аргумента. Это доказательство: адрес памяти виден в инструкции
   (`mov [eax+0x80fa24],ecx`, где `eax = i*0x2a8`).
2. **обработчик → «dword файла → параметр».** Обработчик читает dword'ы
   записи и пушит их в обратном порядке (последний push = `arg0`), вклинивая
   между ними строки и хендлы. Индекс аргумента = позиция в push-стеке
   (`esp + 4*i` на момент `call`).

Обе половины сходятся: `param_k` ↔ `arg_{k-1}` ↔ dword'у файла. Для
оружия/патронов/оборудования порядок dword→параметр линейный (лишние строки
стоят в начале), у шасси строки и хендлы вклиниваются в середину, из-за чего
«наивная» нумерация `arg-1` даёт сдвиг — именно эту ошибку содержала первая
версия таблиц в `FORMATS.md` §12.3 (см. §10).

Команды воспроизведения:

```sh
# store-функции (параметр -> смещение)
python3 tools/ghidra/mcp.py decompile 0x450be0 0x450b10 0x450e60 0x47a170

# обработчики (порядок пушей; строки/хендлы вклиниваются)
python3 tools/ghidra/mcp.py disasm 0x45cac0 --count 80   # оружие
python3 tools/ghidra/mcp.py disasm 0x45cbe0 --count 80   # оборудование
python3 tools/ghidra/mcp.py disasm 0x45cc40 --count 60   # патроны
python3 tools/ghidra/mcp.py disasm 0x45ccc0 --count 400  # шасси

# независимая проверка раскладки шасси по store-функции
python3 tools/re/table_layout.py 0x47a170 0x7995e0 --end 0x47a730 --stride 0x1cc

# карты, данные и проверки
python3 tools/re/weapon_fields.py --map
python3 tools/re/weapon_fields.py --file "/mnt/d/games/Gunmetal 3dfx/dm1.sbt"
python3 tools/re/weapon_fields.py --verify
python3 tools/re/weapon_fields.py --self-test
```

## 2. Теги

`W0..W20`, `A0..A9`, `E0..E11`, `P0..P94` — **номер dword'а в файловой
записи** (то же, что `dN` в `tools/re/sbt_fields.py`). Буквенный тег
(`L3`, `E1`, `D2`, …) — буква операнда сигнатуры и её номер по порядку
(с 1). Соответствие задаётся сигнатурой таблицы:

| таблица | опкод | сигнатура (после счётчика) | dword'ов | запись в памяти | шаг | счётчик |
|---|---|---|---|---|---|---|
| `DEFINE_WEAPONS` | 170 | `SSS LLLL EEEE LLLL D BB D L` | 21 | `0x80fa00` | `0x2a8` | `0x819028` (≤31) |
| `DEFINE_AMMO` | 171 | `S L E O LLLLLLL` | 10 | `0x818960` | `0x38` | `0x818958` (≤31) |
| `DEFINE_EQUIPMENT` | 175 | `S L EEEEEE LLLLL` | 12 | `0x814c60` | `0x40` | `0x815420` (≤31) |
| `DEFINE_PLAYER_TYPES` | 172 | `SSS L D LL D O DDD L N V N V EE` + 35×`D` + `EE` | 95 | `0x7995e0` | `0x1cc` | `0x7941bc` (≤32) |

### 2.1 Буквенные теги (как в `FORMATS.md`)

| таблица | соответствие |
|---|---|
| `DEFINE_WEAPONS` | `L1..L4` = W0..W3, `E1..E4` = W4..W7, `L5..L8` = W8..W11, `D1` = W12/13, `B1` = W14/15, `B2` = W16/17, `D2` = W18/19, `L9` = W20 |
| `DEFINE_AMMO` | `L1` = A0, `E1` = A1, `O1` = A2, `L2..L8` = A3..A9 |
| `DEFINE_EQUIPMENT` | `L1` = E0, `E1..E6` = E1..E6, `L2..L6` = E7..E11 |
| `DEFINE_PLAYER_TYPES` | `L1` = P0, `D1` = P1/2, `L2` = P3, `L3` = P4, `D2` = P5/6, `O1` = P7, `D3..D6` = P8..P15, `L4` = P16, `N1` = P17, `V1` = P18, `N2` = P19, `V2` = P20, `E1..E2` = P21..P22, `D7..D41` = P23..P92, `E3..E4` = P93..P94 |

Store-функции: `0x450be0`, `0x450b10`, `0x450e60`, `0x47a170`;
обработчики: `0x45cac0`, `0x45cc40`, `0x45cbe0`, `0x45ccc0`.

В файле запись = строки + блок dword'ов (`0x54`, `0x28`, `0x30`, `0x17c`
байт); строки лежат **перед** блоком и в dword'ы не входят, поэтому
`tag → dword` относится только к числовой части. Шаг в памяти (`0x2a8` и др.)
включает имена и хендлы, поэтому он больше файлового блока.

Неоперандная часть записи:

| смещение | размер | что | кто |
|---|---|---|---|
| `+0x50` | `0x240` (загружается `0x18`) | структура иконки (`0x47efe0`, каталог `frontend`) | UI армори; при строке `none` (`0x4a6968`) весь блок зануляется `rep stos` `0x450dee` (`0x90` dword'ов) |
| `+0x290` | 4 | хендл `FUN_0040b9c0`(2-я строка записи) | только стор `0x450e24/0x450e34` |
| `+0x298` | 16 | имя `char[16]` (`strncpy` 15) | `0x49291e`, `0x496f43` |

Доказанные детали, которых нет в `FORMATS.md` §12.3:

* **`charge_rate` масштабируется**: `0x450d34`: `fld [esp+0x48]; fmul
  QWORD PTR [0x4a2488]` — константа `0.91`. В памяти лежит
  `файловое_значение × 0.91`, а не оно само (у `PLASMA CANNON` в
  `level0.sbt` файловый `0.007` → в памяти `0.00637`).
* `muzzle = -1` — легальное значение («без узла вылета»), проверка
  `test eax,eax; jl` (`0x4458cc`) перед `cmp eax,8` (`0x4458d2`). У `MRL` в
  `level0.sbt`/`dm1.sbt` именно `-1`.
* биты `flags`: `0x01` — «RIGHT TO BUY» (`0x496c53`, `0x47c34d`), `0x02` —
  «LEFT TO SELL» (`0x47c21a`, `0x47c29b`, строки `0x4be6c8`/`0x4be6d8`),
  `0x08` — пропуск в цикле выбора (`0x47c1bc`, `0x47c260`). Биты `0x04`,
  `0x40`, `0x80` в exe **не тестируются** (в данных встречаются: `0x43`,
  `0xc8`, `0xcc`) — редакторские пометки, роль не установлена.
* `class_index` (`+0x294`) — не «просто значение»: `0x44577e`/`0x4457bc`
  собирают маску стволов, у которых `class == [player+0x81c404]`, т.е. это
  семейство оружия.

### 6.2 Тело (P23..P86): 8 «плит» × 3 `double`

* `P23+2k` / `P24+2k` (`k=0..7`) — `body[k]`: `double` по `+0x48+8k`,
  копируется в `player+0x81bfa0+8k` (`0x47ae26..0x47aefc`). Значения
  `LIGHT`: `13.0, 400.0, 1600.0, 0.9, 64.0, 1.0, 80.0, 0.2`. Четвёртое
  (`+0x60`, `0.9`) — коэффициент `k` интегратора скорости (`0x44447e`);
  остальные — порог/жёсткость/демпфирование подвески и т.п.
  (`docs/FORMATS.md` §12.3).
* `P39..P86` — плиты: `plate[p][c]`, `p=0..7`, `c=0..2`.
  В файле — по строкам (`dword = 39 + 6p + 2c`), в памяти — по столбцам:
  `+0x88 + 0x40c + 8p`. Копируются блоком `0x47af08..0x47af32` в
  `player+0x81beb8 / +0x81bef8 / +0x81bf38` (по 8 штук).
  `LIGHT`: `plate[0] = (0.0, 63.0, 4.0)`, `plate[1] = (0.0, 63.0, 4.0)`,
  `plate[3] = (-8.0, 63.0, -6.0)`, `plate[7] = (0.0, -80.0, 0.0)`; у
  `HEAVY` `plate[0] = (-5.0, 57.0, 10.0)`.
  Похоже на 8 точек/секторов брони — статус **значения**.

**Расхождение, найденное при сверке:** `Weapons::load` берёт

ненулевым `charge_rate` в поставе) это завышает скорость накопления заряда
на ~10 %.

не читает `DEFINE_*`: он берёт `Weapon::projectile_speed`/`thing_type`, т.е.
слой гипотез, заполняемый из `THING_TYPES` и FIRE-подскрипта.

## 9. Аномалии и расхождения с `FORMATS.md` §12.3

1. **`+0xf8`/`+0xfc` шасси читаются вне записи.** Обработчик `0x45ccc0`
   берёт два dword'а не из записи, а из `[record+0xa84]` / `[record+0xa88]`
   (`0x45ce11`, `0x45ce18`) — это на 0xa84 байта вперёд, т.е. байты соседних
   секций SBT. Соответственно файловые dword'ы `P77`/`P78` (плита 6, столбец 1)
   **не читаются вовсе**, а `plate[6][1]` в памяти — мусор. В поставочных
   данных это байты следующей записи (`0x4014…`), т.е. значение не определено.
   Скорее всего ошибка оригинала (или потерянный блок данных), но она
   воспроизводится одинаково на всех уровнях.
2. **`+0x28` шасси — не «индекс модели», а первый `double` тройки.**
   В `FORMATS.md` §12.3 `op5 (O)` приписан `+0x28`; на самом деле `dword 7`
   (`O`, значения 15/16/17/18) идёт в `+0x154` (`model_index`, доказывается
   `0x47af34` → `FUN_00452240`), а `+0x28` — начало `double` `body_x`.
3. **`k` интегратора — `+0x60`, а не `+0x58`.** `LIGHT` даёт `0.9` именно по
   `+0x60` (`dword 29/30`), копируется в `player+0x81bfb8` (`0x47ae90`).
4. **`+0x17c` шасси берётся из `V`-операнда (`dword 18`), а не из `N`**:
   `N` (`dword 17`, значения 9/10/−1/11) не читается, `V` (28/35/22/41) —
   индекс звука. «−1 у STEALTH» из §12.3 относится к неиспользуемому `N`.
5. **`+0x00` шасси — три `double` (`0.001/0.01/0.05`), а не хендлы.**
   `dword 87..92` — это три `double`, а не шесть указателей.
6. `muzzle = -1` — легальное значение (см. §3), `FORMATS.md` ограничивал
   диапазон `0..8`.
