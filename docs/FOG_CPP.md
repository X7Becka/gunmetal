## 1. Доказано кодом (перенесено без изменений)

Все пункты — `docs/FOG.md` §2–§4; статус «доказано» там, здесь — то, что
именно реализовано и чем проверено.

| что | реализация | доказательство |
|---|---|---|
| `z = \|(64/a0)·(e2·(p−eye))\|` | `fog_z()` | `0x440c98`..`0x440ed1`, `0x4804b0` = `fabs` (не `sqrt`); `fog_z` в `tools/re/fog.py` |
| `level = clamp(63 − trunc(z), 4, 63)` | `fog_level()` | `0x441921`..`0x44197d`, `ftol` = `fistp` RC=11 (`0x40e0ef`) |
| применение: `fbuf[i] = table[level*0x100 + fbuf[i]]` | `fog_pixel()`, `fog_frame()` | `0x441b2d`..`0x441b5c` (вторая копия `0x44203d`) |
| `row < 0x40`: `min(63, (pal6[c]·(0x40−row) + row·0x40) >> 6)` | `build_fog_table()` | `0x42024c`..`0x4202f2` |
| `0x40..0x7f` — белый, `>= 0x80` — байтовое тождество | `build_fog_table()` | `0x4202f4`, `0x4204e2`..`0x420538` |
| палитра LUT — **6-битная** (0..63) | `pal6[256][3]`, отказ при байте > 63 | `0x47f0b4` (`shr dl,2` при загрузке BMP) |

Порядок операций повторяет `tools/re/fog.py`: сначала скалярное произведение,
потом умножение на `64/a0`, затем `fabs`; `level` считается в `double` и только
потом приводится к `int`, чтобы `|z| > 2^63` не попадал в преобразование
(сначала кламп, потом каст). `-ffp-contract=off` уже стоит на `gm_engine`,
поэтому FMA не сдвигает ни `z`, ни таблицу.

Дополнительно зафиксировано тестом: уровень 4 наступает при `z >= 59`
(то есть при `a0 = 256` — с глубины 236 юнитов), уровень 5 — при 235.
Это та самая «дымка у камеры», о которой говорит `docs/FOG.md` §5/§7.

## 2. Модель (не выдаётся за движок)

1. **Квантование цвета обратно в индекс палитры.** Билдер `0x4201fe` кончает
   18-битным `r<<12|g<<6|b` и ищет байт в dither-таблицах `0x567128`/`0x56712c`,
   которые строятся в рантайме (BSS) и потому не воспроизводимы. Как и
   `tools/re/fog.py`, модуль заменяет этот шаг правилом: **первое точное
   совпадение цвета в палитре, иначе ближайший по сумме квадратов 6-битных
   расстояний, при равенстве — меньший индекс**. Числа таблицы поэтому
   совпадают с Python-оракулом, но не с оригинальным экраном, где dither
   может выбрать другой (соседний) индекс того же цвета.
2. **`a0` — вход, а не константа.** `a0 = 0.8·W·k(level)`, `k(level)` читается
   из рантайм-таблицы `0x81bf98 + 0x190·index` и не расшифрован
   (`docs/FOG.md` §2, «k(level) не расшифрован»). `FogParams::a0` по умолчанию
   256 — значение для 320×200 и `k = 1`.
3. **Glide-путь не моделируется.** `grFogMode(2)`, `grFogColorValue(0xffffff)`,
   `guFogGenerateExp(table, 0.9f)`, `grFogTable` — это состояние Glide
   (`docs/FOG.md` §6), а не формула, которую исполняет этот движок. Тело
   `guFogGenerateExp` в exe отсутствует, поэтому и «таблица 64 байта» здесь не
   строится.
4. **Строки `>= 0x80`** (тождество) в кадровом проходе недостижимы: `level`
   клампится в 4..63. Они реализованы, потому что это часть билдера и
   материальных LUT, и проверены тестом.
5. **Не подключено**: `render.cpp` рисует RGB, а не 8-битный палитровый кадр,
   поэтому `fog_frame` пока никем не вызывается; CLI `--fog` не добавлялся
   (это общий файл и отдельный срез).

## 3. API (`engine/src/render/fog.h`)

`namespace gm`, зависимости — только stdlib и `render/render.h` (`Vec3d`).

| функция | смысл |
|---|---|
| `struct FogParams { double a0 = 256.0; }` | `ctx+0xa0 = 0.8·W·k` |
| `double fog_z(const FogParams&, Vec3d eye, Vec3d e2, Vec3d p)` | формула `z`; `NaN` при `a0 <= 0`/не конечных входах/переполнении |
| `bool fog_z(..., double& z, std::string* error)` | проверенный вариант, отказ с текстом |
| `int fog_level(double z)` | `clamp(63 − trunc(z), 4, 63)`; не конечный `z` → 4 (безопасный «нет тумана» край, никогда не индекс вне таблицы) |
| `bool fog_level(double z, int& level, std::string* error)` | проверенный вариант (NaN/inf — отказ) |
| `struct FogTable { std::array<uint8_t, 256*256> data; }` | `ds:0x567104`, `data[level*256+col]` |
| `bool build_fog_table(const uint8_t pal6[256][3], FogTable&, std::string* error)` | весь LUT по формуле `0x4201fe` + модель квантования §2.1 |
| `uint8_t fog_pixel(const FogTable&, int level, uint8_t index)` | одна выборка; уровень вне 0..255 — no-op (возвращает `index`) |
| `bool fog_pixel(..., uint8_t& out, std::string* error)` | проверенный вариант |
| `void fog_frame(const FogTable&, int level, std::span<uint8_t> fbuf)` | in-place кадр; плохой уровень — кадр не тронут |
| `bool fog_frame(..., std::string* error)` | проверенный вариант, отказ с текстом |

Константы: `kFogLevelMin = 4`, `kFogLevelMax = 63`, `kFogRows =
kFogColumns = 256`, `kFogRowWhite = 0x40`, `kFogRowIdentity = 0x80`.

Контракт ошибок: `false` + текст в `*error`; на успехе `*error` очищается;
вход/выход при отказе не меняются (`z`, `level`, `out`, кадр). Исключений нет,
аллокаций нет, состояние не хранится — детерминизм проверяется побайтово
(две сборки таблицы равны, FNV совпадает).

## 4. Числа теста (`ctest -R '^fog$'`, 99 проверок, 0.65 с)

```
fog_level (clamp(63-trunc(z),4,63)): z=0->63 z=0.5->63 z=1->62 z=1.999->62
  z=2->61 z=10->53 z=58.999->5 z=59->4 z=60->4 z=100->4 z=-1->63
fog_z (a0=256, 64/a0=0.25, eye=(0,0,0), e2=(1,0,0)):
  p=(4,0,0)->1 p=(0,4,0)->0 p=(-4,0,0)->1 p=(-4,-3,-2)->1
palette: fnv1a64=12941b858f0f2949 (shipped 1.36 GAMEPAL)
lighttable: mismatches_vs_formula=0/65536
lighttable: fnv1a64=ea757b2e157e2905 entries=65536
lighttable: white_index=96 white_rows=66 (rows 62..127), row0_byte_identity=253/256
fog_frame 256 level=0: fnv1a64=3652cec8557d1358 changed=3/256
fog_frame 256 level=63: fnv1a64=f11b05f4478ab725 changed=255/256
fog_frame 64000 level=0: fnv1a64=dd9a27420d92a0c5 changed=750/64000
fog_frame 64000 level=4: fnv1a64=800c97fe8c5af3e1 changed=20000/64000
fog_frame 64000 level=63: fnv1a64=2ca8fedaa4d2ab25 changed=63750/64000
fog: 99 checks, ok
```

Что это значит:

* **`z`/`level`.** `z = 0.5` даёт **63**, а не 62: `ftol` — усечение к нулю
  (`fistp`, RC=11, `0x40e0ef`), значит `63 − trunc(0.5) = 63`; полоса 62
  начинается с `z = 1`. Это расходится с формулировкой задания («0.5→62»),
  которая предполагала округление к ближайшему; канон `docs/FOG.md` §3 и
  `tools/re/fog.py --self-test` (`ftol(0.5) == 0`) говорят 63. Тест
  закрепляет доказанное значение. Остальные якоря задания совпадают
  (0→63, 1→62, 10→53, 59→4, 60→4, 100→4, −1→63).
* **Таблица.** Полный FNV-1a64 всех 65 536 байт совпадает с независимым
  Python-оракулом. **Все 65 536 записей** равны второй реализации формулы
  внутри `test_fog.cpp` (`reference_index`).
* **Палитра.** `FRONTEND/GAMEPAL` (1024 байта, 256×BGRA на диске) читается
  **C++** загрузчиком `gm::installed_palette` (`res/bmp.h`, нормализует в RGBX)
  и сдвигается на 2 бита; FNV-1a64 всех 768 байт `pal6` (RGB-порядок) —
  `12941b858f0f2949`. Первые 8 значений: `(0,0,0) (0,0,0) (5,5,5) (8,8,8)
  (12,12,12) (15,15,15) (18,18,18) (21,21,21)`, запись 255 — белая.
  **Найдено расхождение в оракуле:** `gm/palette.py`/`gm/bmp.py` отдают RGBX,
  а `tools/re/fog.py::load_palette6` перечитывает их как B,G,R, поэтому
  печатает тройки с переставленными R и B (индекс 16 у него «6,2,2», в
  действительности **(2,2,6)**). На таблицу это не влияет: квантователь
  сравнивает квадраты расстояний, а формула и обе полосы симметричны по
  каналам, поэтому глобальная перестановка каналов даёт те же 65 536 байт.
  Тест проверяет это явно («таблица инвариантна к обмену R↔B»). Цветовые
  примеры в `docs/FOG.md` §4 поэтому тоже читаются с обменом R↔B; сам LUT
  и все индексы верны.
* **Row 0.** В пространстве цветов строка 0 — палитра целиком; побайтово
  тождество только **253/256**, потому что палитра повторяет три цвета:
  `(0,0,0)` в 0/1, `(8,0,0)` в 48/65, белый в 96/255, а квантователь берёт
  первый индекс (`1→0`, `65→48`, `255→96`). Это свойство оракула, а не
  ошибка: «тождество» в движке — цветовое.
* **Белая полоса.** Строки `0x40..0x7f` белые; строка 63 (последний
  достижимый уровень) — тоже белая. После квантования плоских белых строк
  **66**: строка 62 даёт цвета `(62,62,62)..(63,63,63)`, ближайший к которым в
  этой палитре — белый, поэтому диапазон `62..127`, а не 65 строк.
  Первый белый индекс — **96**, не 255 (первое точное совпадение).
* **Строки `>= 0x80`** — байтовое тождество (128 и 255 проверены).
* **Кадры.** `fog_frame` побайтово равен прямому обходу `fog_pixel`; FNV
  кадров совпадают с Python. Level 0 меняет 3 байта из 256 (те же слоты
  дубликатов), level 63 — 255 из 256 (индекс 96 остаётся 96). На кадре
  320×200 (64 000 байт, `i mod 256`) level 0 меняет 750 байт, level 4 —
  20 000, level 63 — 63 750.

Если палитра в установке не совпадает с поставочной (проверяется FNV 768
байт `pal6`), тест печатает это и проверяет только палитро-независимые
инварианты (строка 0 в цветовом пространстве, строки `>= 0x80`, полное
совпадение с формулой, детерминизм); точные goldens поставочной палитры
пропускаются с текстом. Это защищает от ложного падения на установке без
`FRONTEND/BMP.IDX`, где `installed_palette` берёт loose BMP с magenta-слотами.

Отдельные записи таблицы (goldens Python), они же в тесте: `row 1 col 0 = 64`,
`row 8 col 16 = 18`, `row 16 col 16 = 6`, `row 32 col 0/16/20/176 =
10/11/108/12`. Они же показывают модель §2.1 (цвета в RGB): формула даёт
`(9,9,13)`, `(17,17,20)`, `(42,42,47)`, а ближайшие записи палитры —
`(8,8,16)`, `(18,18,18)`, `(43,43,43)`; dither оригинала мог выбрать иначе.

Негативы (все — `false` + текст, без изменения выхода): `a0 = 0`, `a0 = −1`,
`a0 = inf`, NaN/±inf в `eye`/`e2`/`p`, `level = −1` и `256` у `fog_pixel` и
`fog_frame`, байт палитры 64 и 200, `pal6 == nullptr`, NaN/inf в `fog_level`.

## 5. Как получены goldens

Независимый оракул — Python-модуль `tools/re/fog.py` (тот же, что даёт 21
якорь инструкций) плюс `gm/palette.py`; в C++ они не вызываются.

```sh
cd /home/nooverload/gunmetal-re
python3 - <<'EOF'
import sys; sys.path[:0] = ['.', 'tools/re']
import fog
from gm import palette as pm

raw = pm.installed('/mnt/d/games/Gunmetal 3dfx')     # RGBX (gm/bmp.py normalises)
pal6 = [(raw[i*4] >> 2, raw[i*4+1] >> 2, raw[i*4+2] >> 2) for i in range(256)]
rows = fog.build_lighttable(pal6, rows=range(256))    # та же формула + квантование

def fnv(bs):
    h = 0xcbf29ce484222325
    for b in bs:
        h = ((h ^ b) * 0x100000001b3) & 0xFFFFFFFFFFFFFFFF
    return h

print('palette', hex(fnv(bytes(v for c in pal6 for v in c))))
print('table  ', hex(fnv(bytes(rows[r][c] for r in range(256) for c in range(256)))))
print('white rows', [r for r in range(256)
                     if all(rows[r][c] == 96 for c in range(256))])
for n in (256, 320 * 200):
    frame = bytes(i % 256 for i in range(n))
    for lvl in (0, 4, 63):
        out = bytes(rows[lvl][b] for b in frame)
        print(n, lvl, hex(fnv(out)), sum(a != b for a, b in zip(frame, out)))
EOF
```

Одной `fog.load_palette6()` здесь недостаточно: она отдаёт тройки в порядке,
переставленном относительно RGB (см. §4, «Палитра»); хеши от этого не
меняются (таблица инвариантна), но цветовые примеры — да. Поэтому палитра
строится явно из `gm.palette.installed` (RGBX → `>>2`).

Проверка инструмента перед работой: `python3 tools/re/fog.py --self-test`
(21/21 якорь). `--table` печатает «глубина → level → цвет», а не дамп
таблицы, поэтому золотые значения выше сняты прямым вызовом
`build_lighttable`, как и записано в шапке теста.

## 6. Ограничения и что осталось

* **18-битная квантизация/dither** (`0x567128`/`0x56712c`, `0x530fb8`) не
  воспроизводимы: таблицы BSS и строятся в рантайме. Модуль использует
  «точный/ближайший» индекс — модель, совпадающая с оракулом, но не с
  экранным dither.
* **`k(level)`** в `a0` не расшифрован, поэтому `a0` — параметр, а не
  константа; поведение при смене уровня (дальность тумана) не проверено.
* **Не подключено**: `render.cpp` (RGB-кадр), палитровый буфер, CLI `--fog`,
  `--fog-near/--fog-far`; срез 2 — только математика + LUT + тест.
* **Glide-путь** (`guFogGenerateExp(0.9)`, `grFogMode(2)`, белый
  `0xffffff`) не моделируется; уровневые настройки `0x41711f`.. и
  `guFogGenerateLinear` (`0x41889c`) — тоже.
* **Семантика «ближе ⇒ белее»** остаётся необъяснённой (`docs/FOG.md` §8):
  модуль повторяет код, а не намерение автора.
* **Порядок каналов в оракуле.** `tools/re/fog.py::load_palette6` читает
  `gm/palette.py` (RGBX) как B,G,R, поэтому его цветовые тройки — с
  переставленными R и B (примеры в `docs/FOG.md` §4 тоже). LUT, индексы,
  `level` и все FNV от этого не зависят (таблица инвариантна к глобальной
  перестановке каналов — проверено тестом), но `fog.py` и примеры `FOG.md`
  стоит поправить отдельным срезом: оба файла вне списка этого.
* Второй путь (`0x4419a2`, таблица `0x4a6a40`, 4 байта/пиксель) не
  реализован: он не используется 8-битным LFB.
* `fog_z` возвращает `NaN` для нефизичных входов, а не бросает исключение —
  вызывающий обязан проверить (или использовать проверенную перегрузку).
