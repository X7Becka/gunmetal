# Gunmetal — спавн игрока и первое лицо

Что здесь: откуда движок берёт точку старта игрока на каждом уровне, как
считается позиция камеры первого лица, какой высоты глаз у каждого шасси и
какие углы лежат в структуре игрока. Всё проверено на `gundx.exe` v1.36 из
`D:\games\Gunmetal 3dfx` (дизассемблер — `tools/re/xref`, листинг
`gundx.asm`, адреса — виртуальные адреса образа; база `0x400000`).

Статус: **механизм спавна разобран полностью** (36/36 уровней, 143 точки
кампании и 248 DM-точек). Открытые вопросы перечислены в §9 и явно отделены от
доказанного. Инструмент: `tools/re/spawn.py` (stdlib, ничего не пишет в игру).

## 0. Коротко

| что | значение | доказательство |
|---|---|---|
| точка старта кампании | `SET_PLAYER_START` (op **169**), слот игрока (0 в одиночной игре) | §1, §2 |
| точка старта DM | `SET_DEATHMATCH_START` (op **168**), на старте — слот игрока | §1, §2 |
| позиция | три `s32` из операндов 1–3, мир в тех же единицах, что `.sbw` | §3 |
| углы | три `f64` из операндов 4–6 | §3, §6 |
| камера | `camera_z = pos_z + player[0x2F50]` | §4 |
| `player[0x2F50]` | LIGHT 10.0, MEDIUM/STEALTH 11.0, HEAVY 12.0, 57 CHEVY 14.0; без шасси 16.0 | §5 |
| DM на респавне | движок сам выбирает слот, самый далёкий от других игроков | §2 |
| yaw | третья угловая величина (`player+0x28`), сырое значение, не нормализовано | §6 |
| высота «ног» | `z` спавна — опорная точка; камера выше неё на высоту глаза | §4 |

Однострочно для рендера:

```
eye_z  = spawn_z + eye_height(chassis)      # 10.0 для LIGHT
camera = (spawn_x, spawn_y, eye_z)
yaw    = третий f64; forward = (sin yaw·cos pitch, cos yaw·cos pitch, -sin pitch) (§6)
```

## 1. Команды и раскладка операндов

`gm/sbtvm.py` уже знает обе команды (таблица `COMMANDS`, строки 222–223):

```
168  SET_DEATHMATCH_START   LLLLAAA
169  SET_PLAYER_START       LLLLAAA
```

`L` — 4-байтовый операнд, `A` — 8-байтовый double. Итого запись занимает
`4*4 + 3*8 = 40` байт:

```
u32 slot          ; номер слота 0..7
s32 x, y, z       ; мировые координаты
f64 a0, a1, a2    ; три угла (см. §6)
```

Проверка по обработчикам. Байт-код диспетчеризуется в `0x4574d4`
(`dec edx; cmp edx,0xc9; jmp DWORD PTR [edx*4+0x45c500]`), то есть номер
операции `N` берёт запись `0x45c500 + (N-1)*4`. Для наших команд:

| op | запись таблицы | хранилище | int-массивы | double-массивы |
|---|---|---|---|---|
| 169 | `0x45c7a0` → `0x45c270` | `0x450880` | `0x5a9460/80/a0` | `0x5a94c0/95a8/96a8` |
| 168 | `0x45c79c` → `0x45c2bc` | `0x4508d0` | `0x5a9540/60/80` | `0x5a9500/9668/96e8` |

Обработчик читает 10 dword'ов операндов (`push` ×10, `add esp,0x28` после
`call`) и передаёт их в хранилище. Хранилище проверяет `0 <= slot < 8`
(`0x450884`..`0x45088b`, `0x4508d4`..`0x4508db`) и раскладывает:

```asm
; 0x450880 (SET_PLAYER_START), фрагмент
45088d  fld   QWORD PTR [esp+0x14]       ; a0
450899  fstp  QWORD PTR [eax*8+0x5a94c0]
4508a4  mov   DWORD PTR [eax*4+0x5a9460],ecx   ; x
4508ba  mov   DWORD PTR [eax*4+0x5a9480],edx   ; y
4508c1  mov   DWORD PTR [eax*4+0x5a94a0],ecx   ; z
4508cf  ret
```

(в листинге `eax` — слот, `ecx/edx` — очередные операнды; для 168 то же самое
с адресами `0x5a9500/9540/9560/9580/9668/96e8`).

Ограничение «8 слотов» — единственное ограничение формата; уровень может
объявить меньше точек. Неиспользованные слоты обнуляются при сбросе уровня:
`0x451b20`..`0x451bb7` делает `rep stos` по каждому массиву (16 dword'ов на
double-массив = 8 значений, 8 dword'ов на int-массив).

## 2. Какой слот выбирается

Единая точка входа — `0x452730(player_index, arg2, arg3)`, структура игрока
`i` лежит по `0x819040 + i*0x3510` (шаг `0x3510` виден в `0x452a1c` и в обходе
игроков `0x45299a`).

| ситуация | arg3 | ветка | что берётся |
|---|---|---|---|
| старт уровня | 0 | `0x452af1` | при `0x4421c0() == 0` — `SET_PLAYER_START[slot]`, иначе `SET_DEATHMATCH_START[slot]` |
| респавн | 1 | `0x452953` → `0x452b8f` / цикл `0x452969` | кампания — `SET_PLAYER_START[slot]`; DM — перебор слотов |

`0x4421c0` — это `return *(u32*)0x83d2c8 != 0;` (`setne`), то есть проверка
флага DM/сетевого режима. Вызовы:

* старт: `0x453211`..`0x453215` — `push 0` (arg3), `push arg2`, `push slot`;
* респавн: `0x452677`..`0x452698` — `push 1`, `push 0`, `push player`.

Выбор слота при старте — **прямо индекс игрока**: `0x452b1b` (`SET_DEATHMATCH_START`)
и `0x452b8f` (`SET_PLAYER_START`) делают `mov eax,[ebp+0x8]` и индексируют
массивы через `eax`. Для одиночной кампании это слот 0.

При респавне в DM (`0x452969`..`0x452a79`) движок перебирает слоты 0..7
(`[esp+0x18]` от `0x5a9540` до `0x5a9560`), для каждого считает расстояние до
каждого активного игрока (`fild` координат слота, вычитание позиции игрока,
`call 0x4344df`), оставляет максимум по игрокам и побеждает слот с наибольшим
таким максимумом. `0x4344df` — не евклидова длина, а приближение: модули
`|dx|,|dy|,|dz|` сортируются, результат = `max + (mid + min)/2`
(`0x434528`..`0x43459b`). Игроки с состоянием `0` или `7` пропускаются
(`0x4529a5`..`0x4529ae`). Начальное «лучшее» расстояние — `0.0`;
если других игроков нет, останется слот 0.

## 3. Копирование в структуру игрока

`0x452b8f`..`0x452bfb` (кампания; при DM-старте то же самое в
`0x452b1b`..`0x452b87`) и `0x452a7d`..`0x452ae6` (DM, слот, выбранный
перебором) — одна и та же последовательность:

```asm
452b8f  mov  eax,[ebp+8]                 ; slot
452b92  fild DWORD PTR [eax*4+0x5a9460]  ; x как int
452ba7  fstp QWORD PTR [ebx+0x819040]    ; -> double player+0x00
452bad  fild DWORD PTR [eax*4+0x5a9480]  ; y
452bb4  fstp QWORD PTR [ebx+0x819048]    ; -> player+0x08
452bba  fild DWORD PTR [eax*4+0x5a94a0]  ; z
452bc1  fstp QWORD PTR [ebx+0x819050]    ; -> player+0x10
452bc7  mov  [ebx+0x819058],ecx          ; a0 (double)
452be1  mov  [ebx+0x819060],ecx          ; a1 (double)
452bf4  mov  [ebx+0x819068],edx          ; a2 (double)
```

Итоговая структура (смещения от базы игрока `0x819040`):

| смещение | тип | смысл |
|---|---|---|
| `+0x00`, `+0x08`, `+0x10` | `f64` | x, y, z (из `s32`, через `fild`) |
| `+0x18`, `+0x20`, `+0x28` | `f64` | три угла из операндов 4–6 |

Важно: позиции в структуре — **double**, хотя в скрипте это `s32`. Это видно
по `fstp QWORD PTR` (8 байт), а не `fst`.

## 4. Камера первого лица

Точка камеры собирается из `player+0x00/0x08/0x10` (`0x819040/48/50`) и поля
`player+0x2F50` (адрес `0x81bf90`):

```asm
448d2b  fld   QWORD PTR [esi+0x81bf90]   ; eye height
448d31  fadd  QWORD PTR [esi+0x819050]   ; + pos_z
448d3a  fstp  QWORD PTR [esp]            ; z камеры -> аргумент 0x446590
```

В режиме `camera mode == 1` (`0x448d86`..`0x448ddf`) x/y/z и та же сумма
публикуются в глобальные поля (`0x448d8b`..`0x448ddf`):

```
0x5a4708  x (double)
0x5a4710  y (double)
0x5a4718  z + eye (double)
```

(в этой ветке `fld [esi+0x81bf90]` / `fadd [esi+0x819050]` повторены в
`0x448da2` и `0x448db4`, `fstp` — в `0x448ddf`).

Для «мёртвой» камеры/других режимов используются другие ветки, но формула
`z + player[0x2F50]` — общая для первого лица. Поле `+0x2F48` (`0x81bf88`,
значение `0.5`, пишется в `0x452db0`) — **другое** поле, к высоте камеры
отношения не имеет (это видно и по сейву: там одновременно `+0x2F48 = 0.5` и
`+0x2F50 = 10.0`).

Ориентация: в той же ветке `0x448dd1` берёт `player+0x28` (`0x819068/6c`) и
передаёт в построение видовой матрицы `0x44a020` (вызов — `0x448e3c`). То есть
**третья угловая величина из скрипта — это угол камеры** (см. §6).

## 5. Высота глаза по шасси

`player+0x2F50` — не константа, а копия double'а `0x799620` из записи шасси:

```asm
47ad2b  mov  eax,[edx+0x799620]   ; младший dword
47ad37  mov  ecx,[edx+0x799624]   ; старший dword
47ad3d  mov  [ebx+0x81bf90],eax   ; player+0x2F50
47ad43  mov  [ebx+0x81bf94],ecx
```

Запись шасси создаётся командой `DEFINE_PLAYER_TYPES` (op **172**);
`0x47a2b7`/`0x47a2c1` кладут в `0x799620/24` очередной double. В разобранной
структуре `gm/sbtvm.py` это `vals[9]`; эмпирически все 36 уровней дают одну и
ту же таблицу:

| шасси | `player+0x2F50` |
|---|---|
| `LIGHT CHASSIS` | **10.0** |
| `MEDIUM CHASSIS` | 11.0 |
| `STEALTH CHASSIS` | 11.0 |
| `HEAVY CHASSIS` | 12.0 |
| `57 CHEVY` | 14.0 |
| нет шасси (fallback `0x47aa87`) | 16.0 |

В сейве `LEVEL0` у игрока `player+0x2F50 = 10.0`, что совпадает с LIGHT
CHASSIS. Что кампания всегда стартует именно с LIGHT, по данным не проверено:
высота зависит от выбранного шасси, а сейв фиксирует только один случай.

### Оракул сейва

`/mnt/d/games/Gunmetal 3dfx/SAVEGAME/saved0.sbt`, файловое смещение
`0x34C37` — копия структуры игрока (позиция `(24, -208, 48)` совпадает с
`SET_PLAYER_START[0]` из `level0.sbt`):

```
+0x00..0x10  (24.0, -208.0, 48.0)
+0x18..0x28  (0.0, 0.0, 0.0)
+0x2F48      0.5
+0x2F50      10.0        <- LIGHT CHASSIS
+0x2F58      1.0
+0x2F60      13.0
```

Проверить:

```sh
python3 -c "import struct;b=open('/mnt/d/games/Gunmetal 3dfx/SAVEGAME/saved0.sbt','rb').read();o=0x34C37;print(struct.unpack_from('<3d',b,o),struct.unpack_from('<3d',b,o+0x18),struct.unpack_from('<d',b,o+0x2F50))"
# (24.0, -208.0, 48.0) (0.0, 0.0, 0.0) 10.0
```

Тот же сейв показывает, что `z` в скрипте — опорная точка («ноги»/центр
шасси), а не глаз: камера выше неё ровно на `10.0`.

## 6. Углы и yaw

Три `f64` из операндов 4–6 попадают в `+0x18/+0x20/+0x28` в том же порядке.
Во **всех 391** записях спавна (143 кампанийных + 248 DM) первые две величины
равны `0.0`, ненулевая только третья. Поэтому для спавна важен ровно один
угол — `a2`, поле `player+0x28`.

Что доказано:

* третья величина уходит в камеру (`0x448dd1` грузит `player+0x28`, вызов
  видовой матрицы — `0x448e3c`), значит это угол поворота камеры;
* значения в данных — «человеческие»: все кратны 5° и лежат в диапазоне
  от -135° до 280° (например `0`, `±90°`, `180°`, `270°`); это сырые радианы,
  без нормализации: `4.7124` = 270°.

**Доказано** (`docs/CAMERA.md`): базис `0x41e025` даёт при roll = 0

```
forward = ( sin(yaw)·cos(pitch),  cos(yaw)·cos(pitch), -sin(pitch) )
right   = ( cos(yaw),            -sin(yaw),             0            )
up      = ( sin(yaw)·sin(pitch),  cos(yaw)·sin(pitch),  cos(pitch)  )
```

Оси мира: X вправо, Y вперёд, Z вверх; при `yaw = 0` взгляд вдоль **+Y**,
положительный yaw ведёт к +X, `pitch > 0` — взгляд вниз. Первые две величины
в спавнах всегда 0, но в общем случае `a0` — pitch, `a1` — roll.
`gm.scene.first_person`, `gm.py spawn` и C++ `--spawn-camera` используют эту
формулу; кадр level0 200x200 побитово совпадает в Python и C++
(FNV `4bb462b101263118`).

Названия первых двух величин (`pitch`/`roll`) — только позиционные: они
всегда нули, проверить их семантику на данных нельзя.

## 7. Проверка по геометрии `.sbw`

`tools/re/spawn.py` строит мировые треугольники `.sbw`
(`sbw.SbwLevel` → `world_vertices()`), затем для каждой точки считает:

* `inside_world_aabb` — попала ли точка в AABB всех вершин мира;
* `nearest_wall` — расстояние до ближайшего **вертикального** треугольника
  (`|n_z| < 0.8`; пол и потолок стеной не считаются), `in_wall` при `< 1.0`;
* `floor_z` / `floor_gap` — пересечение луча вниз с треугольниками;
* `nearest_scene_object` — ближайший объект, поставленный скриптом
  (`LOCATION`, `ADD_THING*`, item, switch, door).

Результаты по 143 кампанийным точкам:

| показатель | значение |
|---|---|
| внутри AABB `.sbw` | 75 |
| вне AABB `.sbw` | 68 |
| формально «в стене» (`< 1.0`) | 6 |
| расстояние до ближайшего объекта сцены: медиана | 221.5 |
| … меньше 50 | 37 из 143 |

«Вне AABB» — не ошибка: это интерьеры, собранные из `.sob`-моделей, которые
скрипт ставит через `ADD_THING*` (например `level1`: спавн `(84,4180,-3064)`,
ближайший объект сцены — `LOCATION` `(88,4132,-3064)` на расстоянии 48.2).
Для таких уровней проверка по `.sbw` бессмысленна, поэтому инструмент печатает
ещё и ближайший объект сцены.

Шесть точек ближе 1.0 к вертикальной плоскости: `level2` слоты 1, 2, 5, 6,
`level4` слот 0, `level12` слот 0. Это не сбой разбора: `level2` — кластер из
8 стартов в тесном помещении (зазоры 0.2–0.7), `level12` стоит ровно на
границе сектора (0.0), `level4` — в 0.6 от стены при зазоре до пола 0.9.
Порог `1.0` выбран условно; трактовать `in_wall` надо как «точка вплотную к
стене», а не «точка внутри стены».

## 9. Покрытие, границы, остаток

**Доказано:**

* раскладка операндов, адреса массивов, проверка слота 0..7;
* копирование int→double в `+0x00/+0x08/+0x10` и трёх double в
  `+0x18/+0x20/+0x28`;
* выбор слота: старт — индекс игрока; респавн в DM — перебор «самого
  далёкого» слота;
* формула камеры `z + player[0x2F50]` и таблица высот по шасси;
* значения высоты подтверждены сейвом `LEVEL0`;
* 143/248 точек вытащены из всех 36 `.sbt`; вокруг них скрипт ставит
  объекты сцены (медиана расстояния 221.5 ед.), что подтверждает кадр.

**Не доказано / остаток:**

1. ~~Конвенция yaw.~~ Закрыто: базис и формулы — `docs/CAMERA.md`;
   камера от спавна реализована (`gm.py view --spawn`, C++ `--spawn-camera`).
2. **Семантика `a0`/`a1`.** В спавнах всегда 0; называть их pitch/roll —
   догадка по позиции в тройке.
3. **DM на HQ-уровнях.** Массивы DM там не заполнены; при попытке DM движок
   возьмёт нули. Доступны ли эти уровни в DM — не проверено.
4. **Точный смысл `arg2`** у `0x452730` (второй аргумент) не разобран: на
   старте/респавне он равен 0, на что ещё влияет — неизвестно.
5. **`in_wall`** — эвристика с порогом 1.0, не приговор геометрии.

### 10.5 C++: новый `engine/src/res/spawn.h`

```cpp
#pragma once

#include <array>
#include <cstdint>
#include <optional>
#include <string_view>

#include "res/scene.h"

namespace gm {

/// Камера первого лица: точка спавна + высота глаза шасси (player+0x2F50).
struct PlayerStart {
    int slot = 0;
    std::array<std::int32_t, 3> pos{};  // опорная точка («ноги»)
    std::array<double, 3> angles{};     // [2] — yaw камеры (сырой, см. docs/PLAYER.md §6)
    double eye_height = 10.0;           // LIGHT CHASSIS

    std::array<double, 3> camera() const {
        return {static_cast<double>(pos[0]), static_cast<double>(pos[1]),
                static_cast<double>(pos[2]) + eye_height};
    }
};

/// Высота глаза по имени шасси из DEFINE_PLAYER_TYPES (op 172).
double chassis_eye_height(std::string_view chassis, double fallback = 16.0);

/// Слот *slot* из SET_PLAYER_START (или SET_DEATHMATCH_START при *deathmatch*).
std::optional<PlayerStart> player_start(const Scene& scene, int slot = 0,
                                        bool deathmatch = false);

} // namespace gm
```

Реализация `player_start` — линейный поиск по `scene.spawns` с фильтром
`deathmatch == deathmatch && slot == slot`; `chassis_eye_height` — таблица из
§5 (`"LIGHT CHASSIS"` → 10.0, `"MEDIUM CHASSIS"`/`"STEALTH CHASSIS"` → 11.0,
`"HEAVY CHASSIS"` → 12.0, `"57 CHEVY"` → 14.0, иначе `fallback`).

Замечание: C++-слой пока не декодирует `DEFINE_PLAYER_TYPES`; чтобы высота
бралась из уровня, нужен ещё разбор op 172 в `sbtvm` (Python-версия уже
делает это в `gm/sbtvm.py`).

## 11. Воспроизведение

```sh
cd /path/to/gunmetal-re

# все 36 уровней, таблица (~4 c)
python3 tools/re/spawn.py

# только выбранные уровни + JSON
python3 tools/re/spawn.py level0 level1 dm3 --json

# без чтения .sbw (быстро, без геометрии)
python3 tools/re/spawn.py level0 --no-geom

# другая высота глаза: шасси или произвольное значение
python3 tools/re/spawn.py --chassis "HEAVY CHASSIS"
python3 tools/re/spawn.py --eye 12.5

# сводка
python3 tools/re/spawn.py | tail -1
# итог: уровней 36, точек кампании 143, точек DM 248, вне AABB .sbw 68/143
```

JSON (`--json`) — объект `{game, levels: [...]}`; в каждом уровне есть
`level`, `sbt`, `sbw`, `chassis_eye` (таблица шасси→высота), `chassis`,
`eye_default`, `campaign` и `deathmatch` (списки точек) и `counts`. Точка:
`index`, `pos`, `yaw` (рад), `yaw_deg`, `angles`, `camera`, `eye_height`,
`gravity`, `source`, `nearest_scene_object`.
