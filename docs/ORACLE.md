# Эталонный оракул (M4.4.2)

«Оракул» — запущенная оригинальная игра, с которой снимаются эталонные кадры
для сравнения с новым рендером.

## Что уже есть в установке

Проверено в `D:\games\Gunmetal 3dfx`:

| компонент | файлы | статус |
|---|---|---|
| игра | `gundx.exe` (v1.36), `gun.exe`, `gunmetal.cfg`, `gunmetal.hi` | есть |
| dgVoodoo | `dgVoodooCpl.exe`, `dgVoodoo.conf` (Version `0x273` = 2.7.3), `DDraw.dll`, `D3DImm.dll` | есть |
| DXWnd | каталог `DXWnd\` (`dxwnd.exe`, `dxwnd.ini`, `tweaks.ini`, …) | есть |
| сохранения | `SAVEGAME\saved0.sbt/.sbw`, `saved1.sbt/.sbw` | есть |

То есть **оракул доступен**: игра запускается на стороне Windows; dgVoodoo
подменяет DirectDraw/D3DImm. DXWnd не обязателен — он нужен только для окна
320×200 с точными пикселями (см. «Без DXWnd» ниже).

## Как снять кадр

1. На Windows запустить игру через профиль DXWnd (windowed, без рамки,
   `DXWnd/dxwnd.ini` уже содержит 320×200), **или** напрямую `gundx.exe` в
   полноэкранном режиме (см. «Без DXWnd»).
2. Загрузить нужное сохранение (`SAVEGAME\saved0.sbt`) и встать в
   фиксированную точку (например, старт `level0`, 3 секунды без ввода).
3. В PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File capture.ps1 -ProcessName gundx `
    -Out '\\wsl.localhost\Ubuntu\home\nooverload\gunmetal-re\out\oracle\level0.png'
```

Скрипт `tools/win/capture.ps1` находит окно процесса, поднимает его,
захватывает прямоугольник окна и пишет PNG. Он **не работает из WSL** (нет
доступа к рабочему столу Windows); скрипт нужно скопировать на Windows-сторону,
например:

```sh
cp tools/win/capture.ps1 /mnt/c/Users/nooverload/capture.ps1
powershell.exe -ExecutionPolicy Bypass -File 'C:\Users\nooverload\capture.ps1' \
    -ProcessName gundx -Out 'C:\Users\nooverload\level0.png'
```

## Кадр и состояние — одним запуском (`-State`)

`capture.ps1 -State` снимает PNG и **сразу** пишет sidecar из того же процесса:

```powershell
powershell -ExecutionPolicy Bypass -File capture.ps1 -State `
    -GameDir 'D:\games\Gunmetal 3dfx' -EyeHeight 10 `
    -Out '\\wsl.localhost\Ubuntu\home\nooverload\gunmetal-re\out\oracle\win4.png'
# -> win4.png + win4.json (sidecar), одна строка JSON в stdout
```

Что делает:

* открывает процесс с `PROCESS_VM_READ`, читает блок игрока
  `0x819040 + slot*0x3510` и имя уровня `0x5a4868` **до** и **после**
  `CopyFromScreen` (два сэмпла вокруг кадра);
* пишет sidecar в формате ниже плюс `state_stable`, `state_before` и
  `state_source`; если камера сдвинулась между сэмплами
  (`Δpos > 0.5` или `Δугла > 1e-3`), ставит `state_stable: false` и просит
  не использовать кадр для попиксельного сравнения;
* хэши `<level>.sbt/.sbw` считает сам (`-GameDir`), `render.width/height` —
  из `-RenderWidth/-RenderHeight` (по умолчанию 320×200).

Почему это важно: до сих пор кадр снимал `capture.ps1`, а состояние читал
отдельный `state.ps1` — между ними проходили секунды. На `win2` такой sidecar
не воспроизводит кадр: лучшее объяснение — наклон камеры ≈6° вниз
(`corr` 0.087 → 0.279, см. ниже), то есть пружина `+0x18` уже была в другом
положении.

Проверено: скрипт парсится PowerShell 5.1 (`Parser::ParseFile` — 0 ошибок) и
доходит до проверки процесса; полный прогон требует запущенной игры.

## Что фиксировать вместе с кадром

* `level` (имя `.sbt`), координаты/угол камеры (из сохранения или скрипта);
* хэш пары сохранений (`sha256sum saved0.sbt saved0.sbw`);
* разрешение и режим вывода (dgVoodoo: `OutputAPI`, `ImageScaleFactor`);
* время/кадр от старта уровня.

Без этого кадр нельзя сравнивать: HUD, оружие и анимации зависят от состояния.

## Ограничения

* dgVoodoo — это Glide/D3D-обёртка: цвета и фильтрация могут отличаться от
  оригинального 3dfx-рендера. Для сравнения «наш рендер ↔ оригинал» нужно
  либо отключить пост-обработку dgVoodoo, либо сравнивать структурно
  (геометрия, HUD-элементы), а не побитово.
* Полноэкранный захват зависит от DPI и темы Windows; скрипт берёт **прямоугольник
  окна**, поэтому масштаб 100 % обязателен.
* Запуск игры из WSL (`cmd.exe /c start …`) технически возможен, но забирает
  экран пользователя — для CI и регрессии это не автоматизируется; кадры
  снимаются вручную/по запросу и складываются в `out/oracle/` (без ассетов
  игры — только PNG-кадры, если пользователь разрешит их хранить).

## Сравнение кадра с нашим рендером

Инструмент: `tools/re/oracle_compare.py` (stdlib + `gm/png.py`). Побитовое
сравнение с dgVoodoo некорректно, поэтому считаются структурные метрики на
сетке 320×200 (кадр DXWnd в `DXWnd/dxwnd.ini` — 320×200, как и наш рендер):

| метрика | смысл | хорошо |
|---|---|---|
| `corr` | корреляция яркости (Пирсон) | ≥ 0,90 в полосе world |
| `mad` | средняя абсолютная разница, 0..1 | чем меньше, тем лучше |
| `edges` | Jaccard пересечения Sobel-краёв | ≥ 0,50 |
| `hist` | L1/2 гистограммы RGB 4×4×4 | чем меньше, тем лучше |

Метрики считаются отдельно для всего кадра, `world` (верхние 70 %) и `hud`
(нижние 30 %): HUD и оружие зависят от состояния и не должны маскировать
расхождение геометрии.

```sh
# 1. снять кадр (Windows, игра запущена через DXWnd)
powershell -ExecutionPolicy Bypass -File capture.ps1 -ProcessName gundx `
    -Out '\\wsl.localhost\Ubuntu\home\nooverload\gunmetal-re\out\oracle\level0.png'

# 2. отрендерить тот же уровень/позу нашим движком (пример для level0)
./build/release/engine/gunmetal --level level0 --render out/level0.png --width 320 --height 200

# 3. сравнить (crop — если в кадр попала рамка окна)
python3 tools/re/oracle_compare.py --oracle level0.png --ours out/level0.png
python3 tools/re/oracle_compare.py --oracle level0.png --ours out/level0.png \
    --crop 0,0,320,200 --json
```

Проверка самого инструмента: `python3 tools/re/oracle_compare.py --selftest`
(6/6; одинаковые кадры дают `corr=1, mad=0, edges=1`).

`heuristic: match` — это **не доказательство**: сначала сверь состояние
(уровень, поза/угол, хэш сейва, разрешение), иначе совпадение может быть
случайным. Результат и метрики складывай рядом с кадром в `out/oracle/`
(схема sidecar — ниже).

## Без DXWnd (полноэкранный запуск)

`gundx.exe` запускается напрямую и работает: dgVoodoo в этой установке
настроен как `FullScreenMode = true`, `ScalingMode = stretched_ar`,
`KeepWindowAspectRatio = true` (`dgVoodoo.conf`). На экране 1920×1080 кадр
320×200 растягивается с сохранением пропорций до 1728×1080 и центрируется —
по 96 px чёрных полей слева и справа. Снимать окно в этом режиме нельзя
(GDI вернёт чёрный кадр), снимается весь экран:

```powershell
powershell -ExecutionPolicy Bypass -File capture_screen.ps1 `
    -Out '\\wsl.localhost\Ubuntu\home\nooverload\gunmetal-re\out\oracle\level0.png'
# -> JSON: {"out": "...", "screen": {...,"w":1920,"h":1080}, "captured": {...}}
```

```sh
python3 tools/re/oracle_compare.py --oracle level0.png --ours out/level0.png --auto-crop
```

`--auto-crop` находит прямоугольник не-чёрных пикселей (в тесте на
синтетическом кадре 2000×1000 вернул ровно вставленные `160,40,1280,720`).
Если сцена сама содержит чёрные края, задай прямоугольник явно:
`--crop 96,0,1728,1080`.

Цена полноэкранного пути: изображение растянуто билинейно, поэтому `edges`
мягче, чем при оконном захвате 1:1. Для геометрии и цвета этого достаточно;
для побитового паритета лучше окно 320×200 (DXWnd или копия игры с
`FullScreenMode = false` — **установку не менять**, копия в проекте).

В sidecar пиши режим: `"capture": {"mode": "fullscreen", "screen": [1920,1080],
"rect": [96,0,1728,1080]}`.

## Состояние из живой игры: `tools/win/state.ps1`

Кадр без состояния бесполезен, поэтому рядом с ним читается рантайм:
`player[0]` — массив 8 записей по `0x3510` от `0x819040`
(`docs/PLAYER_FIELDS.md`), позиция `+0x00/+0x08/+0x10`, углы
(тангаж/крен/рыск) `+0x18/+0x20/+0x28`, всё `f64`. Имя текущего уровня —
буфер `0x5a4868` (`"LEVEL0"` для level0, `docs/LEVEL_LOAD.md` S17).

```powershell
powershell -ExecutionPolicy Bypass -File state.ps1
# {"level":"LEVEL0","position":[1116.17,803.83,48],
#  "angles":{"pitch":0,"yaw":4.8201,"roll":0}, ...}
```

Скрипт только читает (`PROCESS_VM_READ`), ничего не пишет. Глаз камеры —
`position.z + 10` для шасси LIGHT (`docs/PLAYER.md` §2).

## Захват окна: `capture.ps1`

Снимает **клиентскую область** окна (`-Mode window` — всё окно), обрезает её
по экрану: развёрнутое окно игры шире дисплея (1940×1123 при экране
1920×1080), и без обрезки `CopyFromScreen` даёт чёрные поля. Печатает JSON с
окном, снятым прямоугольником и экраном.

Исправлено 2026-10-22: `Join-Path` с абсолютным `-Out` давал неверный путь,
`Resolve-Path` для ещё не созданного файла — `$null`, и `$bmp.Save($null, …)`
падал с `ArgumentNullException` («Имя параметра: stream»). Теперь
`[IO.Path]::GetFullPath`, каталог создаётся.

## После правки палитры и индексов текстур (2026-10-22)

Обе найденные ошибки рендера исправлены (`docs/PALETTE.md`): палитра берётся
из `FRONTEND/GAMEPAL.BMP`, имя текстуры полигона — `tex_names[i-1]`. Кадры
`win1..win3` пересчитаны заново (`tools/re/oracle_render.py`, `focal=160,133.33`,
area-даунсэмпл эталона с обрезкой 1 px рамки):

| кадр | полоса | corr | edges | что видно |
|---|---|---|---|---|
| `win1` | world | +0.021 | **0.431** | контуры совпадают (ванная/коридор), яркость — нет |
| `win2` | world | +0.088 | 0.296 | арка и вывеска угадываются, света меньше |
| `win3` | world | −0.050 | 0.183 | два танка/дверь не воспроизводятся |

Вывод изменился: **magenta больше нет** (`HAZFLR` даёт жёлто-чёрные полосы,
`docs/TEXTURE_AUDIT.md`), геометрия `win1` согласуется по контурам (0.43), а
остаток расхождения — **освещение**: лайтмапы тусклые (среднее 30/127,
`docs/LIGHTMAP_AUDIT.md`), у 59 % граней без лайтмапа `brightness` 8–16, и
наша кривая `0..127 → RGB` не совпадает с движковой (у оригинала цвета проходят
через 6-6-6-куб `LOOK16.TAB`, `docs/FORMATS.md` §6.1). Это следующий пункт
`M4.2.5`.

Отдельно к вопросу о проекции: `docs/CAMERA.md` §7 даёт `+0x90 = 1.0`,
`+0x94 = 4H/(3W) = 0.8333` при 320×200, но не фиксирует, к какой половине
экрана нормируется `y`. Оба варианта (`focal=(160, 83.33)` — движковая
формула, анаморфная; `(160, 133.33)` — квадратный пиксель 4:3) проверены на
трёх кадрах: разница в `corr` ±0.03, геометрия не решается. Нужен кадр с
известной 3D-точкой (например, углы `TRANSIT GATE`), а не перебор.

### Почему остаётся расхождение `win2`: кадр и состояние сняты не в один момент

Проверено на `win2` (масштаб `focal=(160,133.33)`, лайтмапы/мипы/alpha как выше):

| гипотеза | что делали | лучший `corr` (world) |
|---|---|---|
| исходное состояние из sidecar | `pitch=0`, `pos` из sidecar | 0.087 |
| вертикальный сдвиг картинки | перебор `dx/dy` (шаг 6/3 px) | 0.282 при `dy = -15` |
| наклон камеры | `pitch` −24…+12° | **0.279 при +6°** (смотрение вниз) |
| высота глаза | `eye.z` −50…0 | 0.178 при −30 |

То есть кадр лучше всего объясняется **наклоном камеры на ~6° вниз**, которого
в sidecar нет (`pitch = 0`), и вертикальным сдвигом ~15 px — это одно и то же
явление для дальней геометрии. Ни `yaw`, ни позиция вдоль луча, ни знак
`focal` такого выигрыша не дают (`yaw` ±180°: max 0.089; смещение вдоль луча
±400: max 0.23 при +300 на старом рендере).

Вывод: **sidecar не воспроизводит кадр**, потому что состояние читается
отдельным запуском `state.ps1`; крен/тангаж камеры к этому моменту уже другой
(пружина `+0x18` живая, `docs/PLAYER_FIELDS.md`). Пока кадры снимаются двумя
скриптами, побитовое сравнение невозможно — это ограничение методики, а не
рендера.

Практический вывод для будущих кадров: `capture.ps1` и `state.ps1` — два
разных запуска Windows-скриптов, и nobody не гарантирует, что состояние снято
в тот же момент, что и кадр. Следующий кадр должен сниматься одним скриптом:
`capture.ps1 -State` пишет PNG и sidecar из одного процесса (позиция игрока
читается сразу после `CopyFromScreen`).

## Куда складывать кадры

Кадры и sidecar'ы живут в **`out/oracle/`** (каталог в `.gitignore`, в git не
попадает; ассеты игры туда не копируются). Windows-путь для скриптов:

```
\\wsl.localhost\Ubuntu\home\nooverload\gunmetal-re\out\oracle\<имя>.png
```

`capture.ps1` и `capture_screen.ps1` пишут PNG через `MemoryStream` +
`File.WriteAllBytes`: прямой `Bitmap.Save()` на `\\wsl.localhost` ненадёжен.
Проверено: запись в `out/oracle` с Windows-стороны проходит.

Sidecar (рядом с кадром, обязателен):

```json
{
  "level": "LEVEL0",
  "sbt_sha256": "…", "sbw_sha256": "…",
  "save": null,
  "camera": {"pos": [x, y, z], "player_pos": [x, y, z],

```

## Верхняя полоса кадра (измерено 2026-10-23)

**Первая версия этого раздела была неверной, исправлено.** Я измерил средний
RGB верхних 2 % высоты (21 строка из 1080) и сначала решил, что это чистый
фон. Проверка опровергла: если отрендерить те же кадры с `bg=False`
(градиент выключен), **ни один пиксель не меняется** — 0 из 64 000, во всех
трёх кадрах. Значит в `win1..win3` фон полностью закрыт геометрией (это
внутренние сцены, неба не видно), а верхняя полоса — **освещённый потолок**.

| кадр | эталон | наш рендер | что видно |
|---|---|---|---|
| `win1` | 40.3, 39.6, 33.8 | 47.1, 60.4, 61.8 | у нас потолок синеватый и светлее |
| `win2` | 26.4, 26.6, 21.7 | 25.2, 25.1, 25.0 | совпало (у `win2` лучший `corr`) |
| `win3` | 37.6, 37.6, 31.6 | 24.5, 24.0, 23.6 | у нас темнее на ~13 уровней |

Вывод: это не аргумент про фон, а ещё одно указание на **рассинхрон состояния
камеры** (win2 совпал, win1/win3 — нет) либо на разные поверхности в кадре.
Фон (`BG_TOP`/`BG_BOTTOM`) в этих кадрах не виден вообще, поэтому его замена —
низкий приоритет; приоритет — новый атомарный кадр.
