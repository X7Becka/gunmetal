# Строитель LUT `0x682f90`: 16×256 таблиц воспроизведены из кода (`M8.5`, срез 6)

Статус: **срез 6** (2026-10-24). Инструмент — `tools/re/lut_build.py`, этот
документ. До среза единственным точным источником таблиц был дамп с живой игры
(`~/.cache/gunmetal-re/hud_lut.bin`, `tools/win/dump_lut.lua`); теперь те же
4096 байт строятся кодом **побайтово**:

```
identical bytes=4096/4096
dump  FNV-1a64 0x6330406254771f3d
built FNV-1a64 0x6330406254771f3d
```

C++ не менялся: `engine/src/render/hud_lut.*` по-прежнему читает дамп,
`build_model_lut` остаётся канальной моделью `(v*k + max/2)/max`;
`docs/HUD_LUT.md` и `ROADMAP.md` в этом срезе не правились.

## 1. Цепочка вызовов и адреса

| адрес | что делает |
|---|---|
| `0x491f10`..`0x491f2d` | блит полосы: `push &DAT_00682f90 + k*0x100` — таблица `k` подаётся как палитра источника в `0xa1b510`; `k = (field + 0x80) >> 4`, кламп 15 (и 7 при `0x6e89c0`) |
| `0x44b22b` | инициализация вызывает строитель `0x48f970` |
| `0x48f890` | вызывается первым; настраивает UI-рампы/цвета (`0x6c1f60`, `0x6c1fdc`, `0x6c2058`, `0x66459c`), таблиц `0x682f90` **не касается** |
| `0x48f9e2` | `counter = 0`, `esi = 0x682f90` |
| `0x48f9ef` | тело цикла: `fild k` → `fmul qword [0x4a2978]` → `fstp qword [esp]` → `push 1` → `call 0x483290(dst, factor, 1)` |
| `0x48fa0e`..`0x48fa1f` | `esi += 0x100`, `k++`, пока `esi < 0x683f90` → 16 таблиц подряд |
| `0x4a2978` | double `1/11` = `0x3FB745D1745D1746` |
| `0x483290` | строит одну таблицу: 256 слотов → 256 индексов |
| `0x483250` | предикат «слот не трогать» |
| `0x4228e0` | взвешенный поиск ближайшего цвета по слотам `1..254` |
| `0x40e0e0` | `__ftol`: ставит в управляющее слово x87 RC=11 и делает `fistp`, т.е. **усечение** |
| `0x83d320` | палитра **6 бит** на компоненту (R,G,B), 256×3 байта |
| `0x44af88` | загрузка палитры: `0x47efe0("frontend", "gamepal", 0x83d320, …)` |
| `0x47f0b4` | конверсия палитры при загрузке: `shr dl,2` на каждый компонент (BMP → 6 бит, порядок R,G,B) |
| `0x418769` | потребитель: `cmp edx,0x3f` (кламп 6 бит), затем `0x41878b: shl edx,2` при разворачивании в 8 бит |
| `0x682f90` | сами таблицы в RAM: `0x682f90`..`0x683f8f` |

Аргументы `0x483290`: `(uint8_t *dst, double factor, int use_skip_list)`.
Третий аргумент равен 1 при старте; при 0 предикат `0x483250` не вызывается
(этот вариант измерен в §4 строкой «no skip list»).

## 2. Формула

```
0x483290(dst, factor = k/11, use_skip = 1):
  for i = 0..255:                       # esi = 0x83d321, шаг 3, 256 итераций
    if use_skip and 0x483250(i):
        dst[i] = i                      # 0x4832b4: mov [ebx+edi], bl
        continue
    (pr,pg,pb) = palette6[0x83d320 + 3*i]        # 6-битные компоненты
    r = trunc(pr * factor); g = trunc(pg * factor); b = trunc(pb * factor)
    dst[i] = argmin over j in 1..254 of d(j)
```

`d(j)` — метрика `0x4228e0` (те же константы, что в `LOOK16.TAB`,
`docs/LOOK16.md` §1, там она проверена на 262144 ячейках):

```
d(j) = (pj.r + r + 0x100) * (pj.r - r)^2
     + 512                * (pj.g - g)^2
     + (0x17f - pj.r - r) * (pj.b - b)^2
```

Три детали, без которых совпадения нет (числа — §4):

* **Палитра именно 6-битная.** Константы `0x100` и `0x17f` имеют смысл только
  для `0..63`: при 8-битных входах коэффициент `0x17f - (pr+r)` уходит в
  минус и «расстояние» перестаёт быть расстоянием (совпадает 2834/4096).
  В рантайме `0x83d320` действительно 6-битная — это видно по загрузчику
  (`shr dl,2`) и по потребителю (кламп `0x3f`, затем `shl 2`); в самом
  `0x483290` сдвига нет, он читает байты как есть.
* **Усечение, а не округление** (`RC=11` в `0x40e0e0`; `round()` даёт 3388/4096).
* **Строгое `<`** при поиске минимума: при равных расстояниях остаётся
  **меньший** индекс (`<=` теряет 147 байт из 4096).

Диапазон поиска задаёт вызывающий: `push 1` и `push 0xff`, граница
исключающая → кандидаты `1..254`. Поэтому индекс `0` не выдаётся никогда
(`min == 1` во всех таблицах), а `255` не выдаётся поиском — он и так в списке
исключений.

## 3. «Рампы»: откуда 20 нетронутых слотов

Строитель **не** ходит по списку рамп: он перебирает все 256 слотов палитры и
пропускает ровно 20 индексов, зашитых в `0x483250`:

```
173, 174, 175, 191, 240..255
```

Это в точности набор `NEONS.PIN` — слоты вне игровых рамп (`docs/LOOK16.md`
§1, `docs/UPSCALE.md` §3.2). Поэтому уровень 0 оставляет 20 записей как есть
(236/256 уходят в чёрный слот 1), а не 256/256. Тем самым гипотеза из
`docs/HUD_LUT.md` §4 («таблица строится по списку рамп») уточняется: списка
рамп в строителе нет, есть жёсткий список исключений; рампы — свойство самой
палитры, и исключения выбраны как «слоты вне рамп». Сам список — код,
причина выбора — по-прежнему вывод.

```sh
python3 tools/re/lut_build.py --dump
python3 tools/re/lut_build.py --build
```


Проверка независима от C++-теста `hud_lut` и от чисел `docs/HUD_LUT.md` §2:
те же 16 строк (`identity` / `colour-identity` / `white` / `min` / `max` /
`distinct`) печатает `--explain`, они совпадают с таблицей §2 до числа
(например, уровень 0 — `21 22 1 1 255 21`, уровень 11 — `254 256 …`).

Что ломается, если деталь модели заменить (`--ablate`):

| вариант | совпало |
|---|---:|
| **код как есть** | **4096/4096** |
| палитра 8 бит (без `shr dl,2`) | 2834/4096 |
| `round()` вместо усечения | 3388/4096 |
| `<=` вместо `<` (последний минимум) | 3949/4096 |
| кандидаты `0..255` (оба конца) | 3729/4096 |
| без списка исключений (`0x483250` игнорируется) | 3848/4096 |
| фактор `k/15` | 1095/4096 |
| фактор `k/16` | 979/4096 |

`--self-test` — 59 проверок свойств (45 без палитры/игры, дамп не нужен):
форма 16×256, слот 255 → 255 во всех уровнях, 20 исключений, уровень 0 →
чёрный слот 1, уровень 11 — тождество на `1..254` (и `0 → 1`, `65 → 48` на
реальной палитре), 12..15 не алиасы 11, разрешение ничьих в меньший индекс,
симметрия и формула метрики, `1/11` = `0x3FB745D1745D1746`,
`trunc(63*15/11) = 85` (а не 86), отказы `read_dump` на 0/4095/4097 Б, отказы
`--emit` в репозиторий и игру.

`--emit` пишет построенные 4096 Б и отказывает (код 2) в репозиторий (включая
основной чекаут, если работа идёт в worktree) и в каталог игры:

```sh
python3 tools/re/lut_build.py --emit /tmp/opencode/hud_lut_rebuilt.bin
cmp /tmp/opencode/hud_lut_rebuilt.bin ~/.cache/gunmetal-re/hud_lut.bin   # identical
python3 tools/re/lut_build.py --emit ./hud_lut.bin        # [error] … refusing … (rc=2)
python3 tools/re/lut_build.py --emit "/mnt/d/games/Gunmetal 3dfx/x.bin"   # rc=2
```

## 5. Уровни: что теперь объяснено

* **0** — цель `trunc(c*0) = (0,0,0)`, ближайший слот среди `1..254` — чёрный
  `1`; 20 слотов из `0x483250` остаются собой. Отсюда 236 чёрных и 20
  нетронутых.
* **11** — `factor = 11*(1/11)` в double равно `1.0000000000000002`,
  `trunc(63*1.0000000000000002) = 63`, поэтому цель — собственный цвет слота, а
  поиск возвращает сам слот. Исключения — дубли цвета: `0` и `1` оба чёрные,
  `65` и `48` оба `(8,0,0)` в 6 битах → 254/256 по индексу, 256/256 по цвету.
* **12..15** — тот же код без ветки: `k/11 > 1`, цель доходит до
  `trunc(63*15/11) = 85`, то есть **за пределы 6-битного диапазона**. Клампа в
  строителе нет, поэтому таблицы осветляют, а не совпадают с 11. Метрика при
  этом остаётся положительной: `0x17f - (85 + 63) = 235 > 0`.
* **7..10** — частичные тождества (22/23/33/68) получаются сами: чем ближе
  `k/11` к 1, тем больше слотов остаётся на месте.

## 6. Доказано / гипотеза

**Доказано кодом (дизассемблер, `tools/re/disrange.py`):**

* 16 таблиц по 256 байт в `0x682f90`, цикл `0x48f9ef`..`0x48fa1f`, вызов
  `0x483290(dst, double(k) * 1/11, 1)`; константа `1/11` — `0x4a2978`.
* компоненты усекаются (`0x40e0e0` ставит RC=11 перед `fistp`);
* палитра — 6-битная `0x83d320`: `shr dl,2` в загрузчике (`0x47f0b4`),
  кламп `0x3f` и `shl 2` у потребителя (`0x418769`, `0x41878b`);
* список исключений `0x483250` = `{173,174,175,191} ∪ {240..255}`;
* поиск — `0x4228e0` по `1..254` со строгим `<` и метрикой
  `(pr+r+0x100)d_r² + 512 d_g² + (0x17f-pr-r)d_b²`.

**Доказано данными:** все 4096 байт дампа воспроизводятся (FNV
`0x6330406254771f3d`); `--ablate` показывает, что каждая из трёх ключевых
деталей нужна (8 бит / округление / `<=` дают 2834 / 3388 / 3949).

**Гипотеза:**

* *почему* исключены именно эти 20 слотов (они `NEONS.PIN`, т.е. вне рамп) —
  список проверен кодом, намерение выведено из `docs/LOOK16.md` §1;
* x87 считает произведение в расширенной точности, Python — в double;
  на этом наборе `(level, component)` усечения совпадают, так что различить
  их данными нельзя. Утверждение «double-модель эквивалентна» — эмпирическое
  (4096/4096), не доказательство эквивалентности;
* палитра на момент построения — ровно `FRONTEND/GAMEPAL` без правок
  (совпадение дампа это подтверждает по факту, но не доказывает, что движок
  не трогает буфер до/после).

## 7. Ограничения

* Таблица — **индекс → индекс**, не цвет: чтобы получить RGB, вызывающий сам
  применяет палитру (`FRONTEND/GAMEPAL`, `res/bmp.h::installed_palette`).
* `--build`/`--emit`/`--explain` требуют установку (палитра) — игра читается
  только на чтение; без палитры `--build` отказывает с кодом 2, `--self-test`
  остаётся работоспособным (45 из 59 проверок).
* `--build` требует дамп: без него сравнение невозможно (код 2 с путём и
  фактическим размером). Сам дамп в поставку не входит — снимается
  `tools/win/dump_lut.lua`.
* Инструмент ничего не подключает к рендеру и не меняет C++: следующий срез
  может заменить чтение дампа построением (`build` в `hud_lut.cpp`), но это
  вне списка файлов этого среза.
* Проверено на одном билде (`gundx.exe` v1.36, sha256
  `929ffa72…acd17`) и одном дампе; другой билд/дамп надо проверять заново.

## 9. Где это стыкуется с остальными доками

* `docs/HUD_LUT.md` §2/§3 — числа дампа; теперь те же числа получаются из
  кода, а формула `0x483290` там помечена «не разобрана» — это устарело.
* `docs/HUD_AUDIT.md` §2.7 (цепочка блита, `k = (field+0x80)>>4`), §2.8 (дамп).
* `docs/LOOK16.md` §1 — та же метрика `0x4228e0` в 6-битном пространстве,
  проверенная на кубах; это независимое подтверждение констант.
* `docs/UPSCALE.md` §3.2/§3.3 — почему канальная модель не совпадает в
  середине: движок переквантовывает индекс по палитре, а не умножает канал.

## 9. CLI (`--hud-lut-dump OUT`, срез 4)

```bash
gunmetal --game "/mnt/d/games/Gunmetal 3dfx" --hud-lut-dump /tmp/hud_lut.bin
# hud_lut: 4096 bytes, fnv1a64=0x6330406254771f3d, /tmp/hud_lut.bin
```

Движок строит те же 16×256 таблиц из палитры поставки (`installed_palette` →
`build_hud_lut`), пишет их одним файлом 4096 Б и печатает FNV-1a 64. Файл
**побайтово совпадает** с дампом `$GM_HUD_LUT`/`~/.cache/gunmetal-re/hud_lut.bin`
(`cmp` — пусто). Запись внутрь каталога установки запрещена: путь
канонизируется (`weakly_canonical`), и если он лежит под игрой, команда
завершается с `refusing to write inside the installation` и кодом 2.
CTest `cli_hud_lut_dump`, `cli_hud_lut_dump_refuses_game`.
