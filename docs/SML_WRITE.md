## 1. Раскладка и шифр

`.sme` — та же разметка `.sml`, закодированная **позиционным шифром Цезаря**
(`docs/UI.md` §3, `gm/sml.py:1-21`):

```
encoded[i] = letter(plain[i]) ? shift(plain[i], +(i % 10)) : plain[i]
```

Буква сдвигается вперёд на `i % 10` внутри своего алфавита (регистр
сохраняется), все остальные байты копируются. Декодирование — `-(i % 10)`.
Сдвиг зависит от **байтового индекса**, поэтому:

* вставка/удаление хотя бы одного байта меняет фазу всего хвоста;
* `decode(encode(x)) == x` для любой байтовой строки, а значит побайтовый
  round-trip — это проверяемое свойство, а не «похожесть»;
* в `.sme` правка **той же длины** затрагивает только байты строки, а правка
  другой длины обязана перекодировать хвост (см. §3.3).

Переводы строк — обычные байты (`0x0D`/`0x0A`), шифр их не трогает; `--decode`
их **сохраняет**, а не нормализует. Именно поэтому «лишний» CRLF ломает
декодирование: индексы после него сдвинуты (UI.md §4.1), а `.sme`,
закодированный из LF-текста и поставленный с CRLF, — это две разные фазы
(UI.md §4.2).

## 3. Как инструмент правит текст

### 3.1. Адресация: страница и строка

`--set-text FILE --page N --line M --text "..."`:

* **`--page`** — 1-based номер `<d>...</d>`-документа в файле. В поставке он
  всегда **1**; другое значение — отказ с пояснением. Страницы пагера
  (267×167) — результат раскладки по глифовым метрикам
  (`docs/SML_PAGER.md` §2/§5), в Python-оракуле раскладчика нет, и писатель
  его не подменяет.
* **`--line`** — 1-based номер **текстового прогона**: непустого сегмента
  между тегами, ровно в том порядке, в котором его печатает `--list`
  (`text ... run=N`). Нумерация совпадает с текстовыми элементами
  `gm/sml.py:elements` (пробельные сегменты пропускаются). Пример: в
  `help.sml` прогон 1 — `GUNMETAL HELP`, 2 — `F1 - Help`, 4 — `F3 - Toggle
  PLayer ID`.

Такой выбор адреса — следствие того, что `.sml`-документы поставки
**однострочные** (`<r>`/`<p>` задают строки раскладки, а не байты файла;
внутренние `\n` есть только у двух CRLF-аномалий). «Строка исходника» как
адрес была бы бесполезна, а «строка пагера» требует движка.

### 3.2. Что проверяется до записи

1. Расширение — только `.sml`/`.sme`; иначе код 2.
2. Все байты файла (и результата) — printable ASCII `0x20..0x7e` плюс
   `TAB`/`LF`/`CR`; иначе «битая кодировка» и код 2.
3. `.sme` с транспортной аномалией (`note != "as-is"`) для правки
   **отвергается**: правильный путь — `--decode --repair …`, правка `.sml`,
   `--encode` (иначе правка чинила бы ещё и аномалию, а это уже не «только
   строка»).
4. Документ обязан быть `<d>...</d>` (`gm/sml.py`-правило), номер прогона —
   в диапазоне, новый текст непустой.
5. Новый текст: только printable ASCII, **без** `<`/`>` (иначе изменилась бы
   структура тегов) и без CR/LF (перевод строки — это `<r>`/`<p>`, а не
   байт текста).
6. После правки: оболочка и скелет элементов (`kind`/`tag` без текста)
   совпадают со старым документом; число тегов не меняется.

### 3.3. `.sml` — вырезание и вставка, `.sme` — перекодирование целиком

* **`.sml`**: результат = `raw[:start] + новый текст + raw[end:]`. Префикс и
  суффикс файла побайтово те же; длина меняется ровно на разницу длины
  текста. Инструмент это проверяет (`prefix_identical`, `suffix_identical`) и
  падает, если вне прогона изменился хоть байт.
* **`.sme`**: декодированный текст правится так же, затем **весь файл
  кодируется заново** (иначе фаза хвоста не сойдётся). Отсюда два случая:
  * длина текста та же — индексы не смещаются, меняются только буквы прогона
    (`changed_outside_run == 0`);
  * длина другая — хвост перекодирован: `changed_outside_run > 0`,
    `tail_reciphered == true`. Это не «порча», а свойство шифра; корректность
    доказывается равенством `decode(out) == edited_text`, которое инструмент
    проверяет перед записью.

### 3.4. Доказательства после правки (все обязательны)

| проверка | где |
|---|---|
| `decode(out) == edited_text` (для `.sme`) | `set_text` |
| префикс/суффикс вне прогона идентичны (`.sml`; `.sme` при той же длине) | `set_text` |
| скелет тегов/элементов не изменился | `same_structure` |
| `gm/sml.py` (`decode_best` для `.sme`, `describe` для `.sml`) видит новый текст и те же теги | `set_text` |
| `--check` нового файла — ok | `check_info` |
| sha256 файла на диске совпадает с отчётом | `set_text` |

## 4. Команды

```sh
T=tools/editor/smlwrite.py

# кодек: точное декодирование (CR/LF сохраняются) и обратное кодирование
python3 $T --decode "$GAME/SML/brief/level1.sme" --out /tmp/opencode/l1.sml
python3 $T --encode /tmp/opencode/l1.sml --out /tmp/opencode/l1.sme

# транспортные ремонты: level17 (лишний CRLF) / LF-закодированные CRLF-файлы

python3 $T --decode "$GAME/SML/prelevel/LEVEL20.SME" --repair crlf --out /tmp/opencode/l20.sml
python3 $T --decode "$GAME/SML/brief/level17.sme" --repair auto --out /tmp/opencode/l17b.sml

# проверка, список элементов (тип, строка, pos, координаты, run=N), правка
python3 $T --check "$GAME/SML/help.sme"
python3 $T --list "$GAME/SML/help.sml"
python3 $T --set-text "$GAME/SML/help.sml" --page 1 --line 4 \
        --text "F3 - Toggle Player ID" --out /tmp/opencode/help.sml
python3 $T --set-text "$GAME/SML/brief/level1.sme" --page 1 --line 5 \
        --text "TARGET LIST" --out /tmp/opencode/level1.sme

# корпус и self-test
python3 $T --roundtrip "$GAME/SML"
python3 $T --roundtrip "$GAME/SML/brief" --json
python3 $T --self-test
```

`--json` есть у всех режимов (у `--roundtrip` — `results` по файлам, у
`--set-text` — `changed_bytes`, `changed_outside_run`, `prefix_identical`,
`suffix_identical`, `check_ok`). Коды выхода: `0` успех, `1` провал проверки
(`--check`/`--roundtrip`/self-test), `2` плохой ввод/использование,
`3` внутренняя ошибка.

## 6. Ограничения (сознательно)

* **Правится только текст прогона.** Инструмент не создаёт, не удаляет и не
  переставляет теги, не меняет атрибуты (`f s=`, `I x=/y=/f=/a=`,
  `M B=/S=`), координаты, шрифты, картинки, музыку. Новый текст не может
  содержать `<`/`>`/CR/LF — это отказ (код 2).
* **`--page` — это `<d>`-документ, а не страница пагера.** Раскладка
  (267×167, переносы, страницы) требует глифовых метрик движка
  (`docs/SML_PAGER.md` §2/§5); Python-оракул её не считает, и писатель не
  выдаёт приближение за факт. В поставке страница всегда 1.
* **`--line` — текстовый прогон**, а не строка исходника и не строка
  раскладки. Нумерация — как в `--list`.
* **`.sme` при смене длины перекодирует хвост.** Это неизбежно для
  позиционного шифра; меняется не «только строка», а строка + фаза хвоста.
  Инструмент сообщает число перекодированных байт и доказывает
  `decode(out) == edited_text`.
* **Транспортные аномалии не правятся «заодно».** `.sme` с `note != as-is`
  для `--set-text` отвергается; путь — `--decode --repair …` → правка `.sml`
  → `--encode`. При этом `--encode` даёт **LF-вариант** `.sme`: в игру он
  пойдёт, но побайтово исходный CRLF-файл не воспроизведёт (это и есть
  задокументированное исключение `LEVEL20`/`LEVEL4`). Для `level17` точный
  `--decode` пишется как есть (с предупреждением), а `--repair newline` даёт
  читаемый документ на 1 байт короче — как `gm.py sml --rebuild` (150/151).
* **`prelevel/dm4.sml`** (нет `</d>`) не кодируется: `--encode` отказывает,
  `--check` помечает аномалию предупреждением (она известна, UI.md §4.3).
* **Нет записи в игру/зеркало/репозиторий** и нет перезаписи входа: `--out`
  там отвергается кодом 2.
* **Нет C++-проверки в этом срезе:** движок не менялся; паритет проверен
  Python-оракулом и `regress.py`. Чтение правленого `.sme` движком — задача
  интеграции (следующий срез), как и раскладка/рендер страниц.
