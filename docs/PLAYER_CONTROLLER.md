# Gunmetal — контроллер игрока (капсула, 91 Гц)

Что здесь: `engine/src/player/controller.{h,cpp}` — детерминированный
фиксированный тик игрока поверх примитивов `render/collide.*` (docs/COLLIDE.md):
гравитация, шаг вверх/вниз, скольжение по стенам, ограничение скорости,
субшаги при большой скорости. Это **не порт** оригинального кода движения:
константы движка не восстановлены, поэтому всё, что не доказано, помечено
гипотезой (§4). Тесты: `engine/tests/test_player_controller.cpp`, CTest
`player_controller` (метка `quick`, ~0.26 с).

Статус: API, интегратор, капсула (3 сферы), step-up/step-down, slide,
детерминизм, синтетические голдены и прогон 100 тиков по `level0.sbw`
готовы. `regress.py` проходит 113/113 на неизменённых файлах.

---

## 0. Коротко

| что | значение |
|---|---|
| единицы | мировые единицы `.sbw` (X вправо, Y вперёд, Z вверх) |
| точность | только `double`, `-ffp-contract=off` из `engine/CMakeLists.txt` |
| тик | ровно `config.dt`, по умолчанию `1.0/91.0` с |
| состояние | `pos` — **ноги** (низ капсулы), камера `pos.z + eye_height` |
| капсула | 3 сферы радиуса `r` с центрами `r`, `h/2`, `h-r` |
| субшаги | `ceil(|v|·dt / (r/2))`, не больше 32 |
| slide | до 4 итераций на субшаг; step-up — не больше одной попытки за тик |
| шаг | `step_height = 3` вверх и вниз (гипотеза) |
| пол/стена/потолок | по `n.z` с порогом `0.8`, как в `collide` |
| skin | `1e-6` — зазор, который держит depenetration |
| ошибки | NaN/inf, `dt <= 0`, `dt > 0.25`, плохая капсула → `ok=false`, состояние не меняется |

## 1. Кадр и состояние

Мир — тот же, что у `.sbw` и камеры (docs/CAMERA.md):

```
X вправо, Y вперёд, Z вверх
forward = ( sin(yaw)·cos(pitch), cos(yaw)·cos(pitch), -sin(pitch) )
right   = ( cos(yaw),            -sin(yaw),             0            )
```

Контроллер не меняет `yaw` (поворот камеры — отдельный слой); при `yaw = 0`
взгляд вдоль `+Y`, при `yaw = +90°` — вдоль `+X`.

`PlayerState::pos` — опорная точка «ног», как `z` из `SET_PLAYER_START`
(docs/PLAYER.md §3–5): камера первого лица поднимается на `eye_height`
(`player[0x2F50]`, для LIGHT CHASSIS доказано 10.0). Высота капсулы `height`
хранится в состоянии, потому что приседание её меняет.

## 2. API

```cpp
#include "player/controller.h"

gm::ControllerConfig config;                 // дефолты — LIGHT-капсула
gm::PlayerState s = gm::make_state({24, -208, 48}, 0.0, config);
gm::Input in;
in.forward = 1.0;                            // -1..1, вдоль yaw
in.strafe  = 0.0;                            // -1..1, вправо
in.jump    = false;
in.crouch  = false;

gm::StepResult r = gm::step(s, in, world, config);
if (!r.ok) { /* r.error, r.state == s */ }
s = r.state;                                 // ровно один тик
gm::Vec3d eye = gm::eye_position(s);         // pos + (0,0,eye_height)
```

| тип | поля |
|---|---|
| `PlayerState` | `pos`, `vel`, `yaw`, `height`, `eye_height`, `on_ground`, `crouching` |
| `Input` | `forward`, `strafe`, `jump`, `crouch` |
| `ControllerConfig` | `radius`, `height`, `eye_height`, `gravity`, `accel`, `friction`, `max_speed`, `step_height`, `dt`, `jump_speed`, `air_control`, `crouch_scale`, `max_dt`, `contact_skin`, `max_slides`, `max_substeps` |
| `StepResult` | `ok`, `error`, `state`, `hit_wall`, `hit_floor`, `hit_ceiling`, `stepped_up`, `stepped_down`, `jumped`, `substeps`, `slides` |

`step()` не бросает исключений, не читает время/SDL и не меняет мир. Ошибки
ввода возвращают `StepResult{ok=false, error=...}` с **исходным** состоянием.

## 3. Порядок тика и формулы

Порядок фиксирован; менять его нельзя без пересчёта голденов.

### 3.1. Валидация

Проверяются конфиг, состояние и вход: все числа конечны; `radius > 0`;
`height >= 2·radius`; `0 < crouch_scale <= 1`; `0 < dt <= max_dt`;
`dt <= 0.25 с` (жёсткий предел); `1 <= max_slides <= 16`;
`1 <= max_substeps <= 256`; `contact_skin > 0`. `forward/strafe`
зажимаются в `[-1, 1]`.

### 3.2. Приседание

```
target = crouch ? height_standing · crouch_scale : height_standing
если target < height: height = target
иначе: подъём капсулы на (target - height) проверяется sweep'ом; при препятствии
        высота не меняется
eye_height = config.eye_height · height / height_standing
```

### 3.3. Стартовая depenetration и земля

Капсула выталкивается из пересечений ещё **до** первого sweep'а (спавн
`level0` лежит на 0.546875 ниже пола). Затем:

```
grounded = sphere_cast(низ + (0,0,r), вниз, r, 0.05, только полы)
если !grounded && state.on_ground && vel.z <= 0:
    grounded = true            // только что сошёл с края: шанс на step-down
```

### 3.4. Желаемое направление, трение, ускорение

```
wish = forward·(sin yaw, cos yaw, 0) + strafe·(cos yaw, -sin yaw, 0)
если |wish| > 1: wish /= |wish|
```

Трение (только на земле):

```
speed = |vel.xy|
control = max(speed, 1.0)
next = max(0, speed - control · friction · dt)
vel.xy *= next / speed
```

Ускорение:

```
wishspeed = |wish| · max_speed
rate = grounded ? accel : accel · air_control
add = rate · wishspeed · dt
vel.xy += wish/|wish| · min(add, wishspeed - dot(vel.xy, wish/|wish|))
```

Затем жёсткий зажим `|vel.xy| <= max_speed`.

### 3.5. Прыжок и гравитация

```
если jump && grounded: vel.z = jump_speed; jumped = true; on_ground = false
vel.z -= gravity · dt
```

Порядок «прыжок → гравитация» даёт на первом тике
`vel.z = jump_speed - gravity·dt`.

### 3.6. Субшаги

```
max_step = radius / 2
n = max(1, ceil(|vel| · dt / max_step)), n <= max_substeps
h = dt / n
```

### 3.7. Collide-and-slide (на субшаг)

```
remaining = vel · h
повторить до max_slides:
    hit = ближайший sphere_cast по трём сферам (порядок: низ, середина, верх)
    если промах: pos += remaining; конец
    travel = max(0, hit.t - contact_skin)
    pos += remaining · (travel / |remaining|)
    remaining *= (|remaining| - travel) / |remaining|
    remaining -= n · dot(remaining, n)      // slide по нормали
    vel       -= n · dot(vel, n)            // только если dot < 0
    классификация: n.z >= 0.8 пол, n.z <= -0.8 потолок, иначе стена
```

`travel = hit.t - skin` — принципиально: остановка ровно в контакте даёт
`t = 0` на следующем sweep'е (начальное перекрытие) и съедает остаток
движения.

### 3.8. Step-up

Только при контакте со стеной, `grounded`, без прыжка, если `dot(wish, n) < 0`,
не больше одной попытки за тик:

```
1. headroom: sweep вверх на step_height + skin — не должно быть препятствий
2. raised = pos + (0,0,step_height)
3. вперёд по горизонтали wish на max(|wish|, radius + 0.1);
   любое препятствие -> отказ
4. floor_at(raised.xy, raised.z + skin, step_height + skin) — пол под ногами
5. принять, если floor_z > pos.z + 1e-3 и floor_z <= pos.z + step_height
   pos = (raised.xy, floor_z); vel.z = 0; remaining.xy = 0
```

Шаг вперёд на радиус нужен потому, что низ капсулы — сфера: без этого она
цепляется за верхнюю кромку ступени и остаётся висеть на ней.

### 3.9. Step-down

Если игрок был на земле, не прыгал и `vel.z <= 0`:

```
floor_z = floor_at(pos.xy, pos.z + skin, step_height + 2·skin)
если floor_z есть и 0 <= pos.z - floor_z <= step_height:
    pos.z = floor_z; vel.z = 0; on_ground = true
```

Используется луч по оси капсулы, а не sweep: на краю площадки сфера
зацепляется за кромку и «находит» её вместо нижнего пола.

### 3.10. Depenetration и финальная земля

До 8 итераций: берётся AABB капсулы (+skin), `overlap_aabb`, для каждой из
трёх сфер и каждого треугольника — `closest_point_on_triangle`; выбирается
**самое глубокое** проникновение, и вся капсула сдвигается по его нормали до
`radius + skin`. Это устойчиво в углах и не зависит от порядка «кто первый».

В конце `on_ground` пересчитывается тем же 0.05-зондом. Если после
интегрирования `pos/vel/height` перестали быть конечными (переполнение от
абсурдной входной скорости), возвращается `ok=false` с исходным состоянием.

## 4. Константы: доказано и гипотеза

### 4.1. Доказано (данные/существующие документы)

| величина | значение | источник |
|---|---|---|
| тик | `1/91` с | HUD/анимации идут на 91 Гц: `docs/HUD_PLAYER.md`, `gm/hud*` |
| `eye_height` (LIGHT) | `10.0` | `player[0x2F50]`, сейв `LEVEL0`, docs/PLAYER.md §4–5 |
| высота глаз по шасси | 10 / 11 / 12 / 14 / 16 | docs/PLAYER.md §5 |
| порог пол/стена/потолок | `0.8` | docs/COLLIDE.md §4.5 |
| `max_speed` LIGHT, база | `1.70 · 91 = 154.7` | `DEFINE_PLAYER_TYPES` op4 = 1.70 ед/тик (LIGHT), 1.00/1.00/0.60 (MEDIUM/STEALTH/HEAVY), 1.70 (CHEVY); приёмник `player+0x81bd70`; `0x443690` + `0x44db80` (91 тик = 1 с) |
| `SET_LEVEL_GRAVITY` | op 96, `D` | docs/VM_EXEC.md; в 13 уровнях значения 0.1…4.5 |

Ghidra (`docs/PLAYER_GHIDRA.md`) уточняет: `0x443690` умножает скорость на
`cos/sin(heading)` и интегрирует `param_2` шагов. `0x44d4c0` передаёт туда
`[0x5a4a74] - [0x5a46e8]`, а `0x5a4a74` — счётчик тиков отдельного потока
(`0x4074e0`, `Sleep(11)`, ~91 Гц). `0x44db80` независимо доказывает
`0x5b` (91) тик = 1 с. Поэтому `op4` — **единицы за тик**, а
`1.70 · 91 = 154.7` ед/с — доказанная конверсия, не гипотеза. Значение
`0x81bd78` уже в единицах за тик; `dt = 1/91` даёт ровно 1.70 за шаг.

`SET_LEVEL_GRAVITY` в поставочных данных — **множитель** (0.1…4.5), а не
`м/с²`; `level0` команду не содержит (множитель 1.0). Он пишется в
`0x80f840` (op 96, `0x45b7db`) и масштабирует член подвески/проникновения
(`-0.2 · multiplier · dt` в `0x443690`), а не задаёт `g`. Базовая скалярная
гравитация в оригинале не найдена; контроллер множители не применяет.

### 4.2. Гипотеза (числа выбраны по масштабу и проверены только тестами)

| величина | значение | обоснование/ограничение |
|---|---:|---|
| `radius` | 3.0 | приближение; оригинал берёт `obj+0x60` (f32 радиус SOB) в `0x452240` → `0x81bda8`, см. `docs/PLAYER_GHIDRA.md` §3 |
| `height` | 10.0 | в спавне ровно 11.0 до потолка; eye 10.0 (LIGHT) |
| `gravity` | 700.0 | синтетическая модель; оригинал использует подвеску с множителем `0x80f840` (по умолчанию 1.0), скалярная база не найдена |
| `accel` | 10.0 1/с | quake-подобная модель, разгон до max за ~9 тиков |
| `friction` | 8.0 1/с | остановка с max за ~0.13 с |
| `jump_speed` | 200.0 | высота `v²/2g ≈ 28.6` |
| `step_height` | 3.0 | = радиусу; ступени выше проверяются отдельным конфигом |
| `air_control` | 0.35 | доля `accel` в воздухе |
| `crouch_scale` | 0.7 | высота/глаз при приседании |
| `max_dt` | 0.25 с | защита от «одного длинного тика» |
| `contact_skin` | 1e-6 | зазор depenetration |
| `max_slides` / `max_substeps` | 4 / 32 | пределы работы за тик |

Оригинальные константы не искались заново: в этом checkout'е нет ни
`gundx.asm`, ни `tools/re/xref` (docs/COLLIDE.md §9, docs/PLAYER.md §11
ссылаются на листинг, которого здесь нет). Всё, что можно было взять из
существующих разборов (`op4`, op 96), взято и помечено выше.

### 5.2. `level0.sbw` (реальный файл)

Спавн `SET_PLAYER_START[0] = (24, −208, 48)`, yaw 0 (docs/PLAYER.md §8).
Пол под точкой — `48.546875` (docs/COLLIDE.md §6.2), т.е. спавн на 0.546875
ниже пола; контроллер выталкивает капсулу за один тик.

| прогон | `pos` | `on_ground` |
|---|---|---|
| 1 тик, покой | `(24, −208, 48.546876)` | да |
| +100 тиков, `forward=1`, yaw `+90°` (+X) | `(91.671874088928945, −207.99999999999997, 48.546875999999997)` | да |
| глаз после 100 тиков | `z = 58.546876` | — |

`94.671875`, значит ось капсулы останавливается на
`94.671875 − radius − skin = 91.671874`. Сам прогон (100 тиков, путь по
полу) зафиксирован как implementation-pinned golden с допуском `1e-6`.

## 6. Доверие

Доказано/проверено:

* интегратор и формулы воспроизводятся аналитически (падение, первый тик
  прыжка, апекс, зажим скорости);
* коллизии не туннелируют при `|v| = 10000` и `dt = 1/91`;
* step-up/step-down дают ожидаемые высоты на синтетической ступени;
* два одинаковых прогона побитово совпадают;
* угол не заклинивает (тест «в угол и обратно»), приседание не встаёт под
  потолком `z=8`;
* ошибки не портят состояние и не падают;
* `level0`: пол, спавн, стена `+X` и 100-тиковый путь совпадают с
  `collide`/`TEST_PLAYER_START`;
* `regress.py` — 113/113, файлы не менялись.

Не доказано:

* **все константы §4.2** — инженерные гипотезы, не числа движка;
* оригинальный алгоритм движения (`0x4344df`, `0x434887`, `0x4795b0` —
  `event_post`) не разбирался; совпадение поведения с игрой не проверено;
* капсула — **объединение трёх сфер**, а не точный цилиндр: на кромках
  поведение «круглое», отсюда skin, step-forward на радиус и луч в
  step-down;
* голдены `level0` сняты с этой реализации; независимо проверено только
  конечное `x` (стена) и пол;
* наклоны: слайд по нормали есть, но отдельного теста на sloped-floor нет
  (в `level0` такой пол встречается);
* нет пола — бесконечное падение (by design); двери/`.sob`/движущиеся
  платформы не входят в `CollisionWorld`.

## 8. Остаток

1. **Оригинальные константы.** Единица `op4` и множитель `SET_LEVEL_GRAVITY`
   уже разобраны (`docs/PLAYER_GHIDRA.md`); осталось найти радиус/высоту/
   шаг/трение и базу подвески.
2. **Точная капсула** (2 сферы + цилиндр) вместо 3 сфер: уберёт
   «зацепление» за кромки и необходимость forward-снапа на радиус.
3. **Наклоны и ступени в реальном уровне**: прогон по лестницам `level0`
   и сверка с оригиналом; сейчас есть только синтетическая ступень.
4. **Приседание под потолком**: тест на блокировку вставания.
5. **Динамические объёмы**: двери — боксы (docs/FORMATS.md §12), их нет в
   `CollisionWorld`; нужен слой AABB/OBB.
6. **`.sob`-модели**: 68/143 кампанийных спавнов вне AABB `.sbw`
   (docs/PLAYER.md §7).
7. **Камера/управление**: `yaw` в состоянии, но поворот и привязка ввода к
   камере — следующий слой; `eye_height` уже отдаётся через
   `eye_position()`.
8. **Шасси**: `max_speed`/`eye_height` сейчас константы конфига; таблица
   `DEFINE_PLAYER_TYPES` (LIGHT/MEDIUM/STEALTH/HEAVY/CHEVY) может заполнять
   конфиг по уровню. Единица `op4` закрыта: ед/тик, `×91` — проверенная
   конверсия; тест `test_speed_unit_is_per_tick` фиксирует `max_speed*dt == 1.70`
   и прохождение 154.7 ед за 91 тик.
9. **Множители гравитации уровня** (op 96) не применяются.
