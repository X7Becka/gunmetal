## 1. Поля: что читается

Полигон `.sbw` — запись `124 + 2·n_idx` на диске, `0x80` байт в памяти
(`docs/FORMATS.md` §10.1). Четыре поля среза (диск → рантайм):

| диск (`tail+`) | рантайм | тип движка | поле | кто читает |
|---:|---:|---|---|---|
| `0x00` | `0x5c` | **s16** | `scroll_u` | `0x434c11` (`0x434c80`): `float(int *(short*))` |
| `0x02` | `0x60` | **s16** | `scroll_v` | то же |
| `0x6A` | `0x5e` | **u16** | `anim0` | `0x4342f0`: `*(ushort*)` |
| `0x6C` | `0x62` | **u16** | `anim1` | то же |

Раскладка доказана `gm/sbw.py` (round-trip **36/36 побайтово**,
`docs/SBW_POLY.md` §7.2) и совпадает с C++-читателем `res/sbw.cpp:223-243`
(`poly.scroll_u = rd16(tail + 0)`, `anim0 = rd16(tail + 106)`), который
разбирает те же 36 файлов. Отсюда правило среза: **`scroll_*` — знаковые**
(`0xFFFF` = −1, а не 65535), **`anim*` — беззнаковые 0..65535**. Оба чтения
видны в декомпиляции `0x434c80` (§2) и `0x4342f0` (§3); смешивать их нельзя:
`0x8000` в `scroll_u` — это −32768, в `anim0` — 32768.

`PolyAnim` хранит именно эти четыре значения; `PolyAnim::from_raw()` делает
s16-расширение для скролла и оставляет `anim*` как `0..65535`.
`from_poly(SbwPoly)` — та же конверсия из парсера.

## 2. Скролл: доказано (`0x434c11`, вход `0x434c80`)

Декомпиляция (`tools/ghidra/fncache.py get 0x434c80`; тело — `FUN_00434c11`):

```
iVar3 = resolve_poly(sector, object, poly);            // 0 = нет полигона
fVar1 = 1 / |u_axis|^2;                                // (poly+0x20)
fVar2 = 1 / |v_axis|^2;                                // (poly+0x2c)
out.x = (s16[0x60]*v_axis.x*fVar2 + s16[0x5c]*u_axis.x*fVar1) * (float)-param_5 / 256.0
out.y = (s16[0x60]*v_axis.y*fVar2 + s16[0x5c]*u_axis.y*fVar1) * (float)-param_5 / 256.0
out.z = (s16[0x60]*v_axis.z*fVar2 + s16[0x5c]*u_axis.z*fVar1) * (float)-param_5 / 256.0
```

Что из этого **доказано**:

1. `0x5c`/`0x60` читаются как `short` (знак сохраняется);
2. результат — вектор `(-t)·(scroll_u·u_axis/|u|² + scroll_v·v_axis/|v|²)/256`,
   арифметика `float32`, возврат через три `double`;
3. деление на 256 — константа `0x4a2258` = 256.0 (`docs/FORMATS.md` §10.1);
4. `resolve_poly(0) == 0` — отказ (движок возвращает `0xffffffff`).

Что **не доказано**: смысл скаляра `param_5` и место, куда вызывающий
складывает результат. Вызовы `0x434c11` — `0x4514db` и `0x472ccf` (функция
шасси/геометрии `0x451160`), `0x46924d`, `0x472ccf`; в первом `param_5` —
это `param_4` самой функции `0x451160` (там же он индексирует локальный
слот `(param_4+5)*0x14`). `docs/WORLD_MATERIALS.md` §3.2 называет величину
«1/256 на тик», но отдельного доказательства «91 Гц» нет.

**Модель (помечена в API).** `scroll_offset(..., tick)` считает

```
offset = tick · (scroll_u · u_axis + scroll_v · v_axis) / 256.0
```

в `double`; `tick` — **тики 91 Гц** (документированное чтение), знак — как в
документе: движковый вызов соответствует `tick = -param_5`. Ноль при
`tick = 0` точен.

**Два отличия от движка, обе осознанные:**

* **Нет нормировки `1/|axis|²`.** Формула документа (`docs/FORMATS.md` §10.1,
  задание среза) записана для единичных осей; загрузчик такие и требует
  (`Invalid poly U vector`, `0x434463`), но в поставке **22 %** осей не
  единичны (`docs/SBW_POLY.md` §3.2). Для них наш вектор длиннее ровно в
  `|axis|` раз, направление то же. Пример: `dm1`, первый скролл-полигон,
  `|u_axis| = 0.400824933`, `scroll_u = 300` → наш `offset(1).x =
  0.188271306`, движковый был бы `300/256 · 0.400824933 = 0.4697…` вдоль
  единичного `u`. Если понадобится точная движковая величина — делить
  результат на `|axis|²` (или нормировать оси до вызова).
* **`double`, а не `float32`, и без насыщения.** Движок считает во `float32`
  и не переполняется на поставке (максимальный вес 15224). `scroll = 32767`
  даёт конечное `32767/256 = 127.99609375` за тик; `32768` отвергается как
  не влезающее в s16.

**Отказы** (`error` заполняется, возвращается `{0,0,0}`, исключений нет):
`tick` = NaN/±Inf; компонента оси NaN/Inf; нулевая `u_axis`/`v_axis`;
`scroll_u`/`scroll_v` вне s16; переполнение `double` при огромном `tick`
(например `1e308`) — тоже текст, а не `inf`.

## 3. `anim`: доказано (`0x4342f0`) и модель

`0x4342f0` — тело `FUN_00433e00`, интерполяционный цикл плеера `.soo`
(`param_1` — запись анимации объекта, `param_2` — текущий тик,
`docs/WORLD_MATERIALS.md` §3.3). Ключевой фрагмент (полигон `0x80` байт,
`puVar15` — `u16*`, поэтому `[0x2e]` = `+0x5c`):

```
fVar2 = (float)(local_3c - local_28) / (float)duration;   // доля кадра, float32
...
iVar11 = (int)(short)puVar15[0x2e];                            // A: s16 +0x5c
iVar18 = (int)*(short*)(iVar16 + 0x5c) - iVar11;               // s16 B - A
puVar17[0x2e] = __ftol();                                      // trunc -> +0x5c
iVar9  = (int)(short)puVar15[0x30];                            // A: s16 +0x60
iVar6  = (int)*(short*)(iVar16 + 0x60) - iVar9;
puVar17[0x30] = __ftol();
uVar10 = (uint)(ushort)puVar15[0x2f];                          // A: u16 +0x5e (anim0)
iVar8  = (uint)*(ushort*)(iVar16 + 0x5e) - uVar10;             // u16 B - A
puVar17[0x2f] = __ftol();
uVar4  = __ftol(... *(ushort*)(iVar16 + 0x62) - (uint)(ushort)puVar15[0x31] ...);
puVar17[0x31] = uVar4;                                         // anim1
```

Отсюда **доказано**:

1. интерполируется **одноимённое поле двух полигонов-ключей**: `A` — полигон
   текущего кадра клипа (запись `iVar1`), `B` — следующего (`local_24`);
   кадры и длительности — таблица клипа `0x6fbd40/0x6fbd44/0x6fbd48`, режим
   `0` — зажим на последнем кадре, `1` — закольцован (`% local_38`);
2. доля `t = (now − start − начало_кадра)/длительность_кадра`, `float32`,
   `0 ≤ t < 1` (при зажиме последнего кадра `t` доходит до `< 1`);
3. **16-битные половины по отдельности**: `0x5c`/`0x60` — **signed**
   (`(short)`), `0x5e`/`0x62`/`0x66` — **unsigned** (`(ushort)`); результат
   каждого — `trunc((B − A)·t + A)` (`__ftol`, округление к нулю) и запись
   обратно в 16-битный слот;
4. поля `0x5c/0x5e/0x60/0x62/0x66` интерполируются независимо (не как
   `f32`/`i32`-пара), и после цикла зовётся `0x434d78` (пересчёт производных
   кадра).

### 3.1 API: две формы

* **Доказанная, два ключа:** `anim_step(key_a, key_b, t)` →
  `{trunc((u16_B.anim0 − u16_A.anim0)·t + u16_A.anim0),
     trunc((u16_B.anim1 − u16_A.anim1)·t + u16_A.anim1)}` в `float32`.
  `t` обязан быть в `[0, 1]`: движок вне этого диапазона не вызывает.
* **Модель, один полигон:** `anim_step(key, t)` трактует `anim0`/`anim1`
  самого полигона как два конца и шагает половины навстречу:
  `{trunc((anim1 − anim0)·t + anim0), trunc((anim0 − anim1)·t + anim1)}`.
  При `t = 0` это ровно пара из файла, при `t = 1` — она же наоборот, при
  `t = 0.5` обе половины равны среднему. **Движок так не делает**: в его
  данных `0x5e`/`0x62` — независимые `f32`-биты экспортёра
  (`docs/FORMATS.md` §10.1), а не концы одной анимации. Форма существует
  потому, что срез просит одно-полигонный `anim_step`; для морфинга
  использовать форму с двумя ключами.

**Отказы:** `t` = NaN/±Inf или вне `[0, 1]`; `anim*` вне `0..65535` —
`{0,0}` и текст.

## 5. API

```cpp
namespace gm::texanim {

struct PolyAnim { int scroll_u, scroll_v, anim0, anim1; };
PolyAnim PolyAnim::from_raw(u16 scroll_u, u16 scroll_v, u16 anim0, u16 anim1);
PolyAnim from_poly(const SbwPoly&);          // читает 4 поля парсера

bool has_scroll(const PolyAnim&);            // scroll_u != 0 || scroll_v != 0
bool has_anim(const PolyAnim&);              // anim0 != 0 || anim1 != 0

Vec3d scroll_offset(const PolyAnim&, Vec3d u_axis, Vec3d v_axis, double tick,
                    std::string* error = nullptr);

std::pair<int,int> anim_step(const PolyAnim& key_a, const PolyAnim& key_b, double t,
                             std::string* error = nullptr);   // доказано
std::pair<int,int> anim_step(const PolyAnim& key, double t,
                             std::string* error = nullptr);   // модель
}
```

`Vec3d` — тип `render/render.h` (модуль его не меняет). `error` опционален
(`nullptr` не падает); на успехе очищается. Все функции не бросают, не
аллоцируют и детерминированы (два прогона корпуса дают идентичные строки —
проверяется тестом).

Тест находит игру сам (зеркало → `/mnt/d`); без установки печатает

## 7. Ограничения

* **Не подключено к рендеру.** `build_level_meshes`/`render_scene`/UV-сэмплер
  не читают `scroll_*`/`anim*`: `RenderFace` (`render/render.h`) этих полей
  не несёт, `render.cpp` сдвиг текстуры не применяет. Срез даёт арифметику и
  числа, а не картинку; проводка — отдельная задача (нужно решить, к чему
  прибавлять смещение: к `centre`, к UV или к обеим проекциям, — это как раз
  недоказанная часть §2).
* **Скриптовые команды уже есть, но эффекта нет.** `SET_POLY_SCROLL`
  (`0x457e7e`), `SET_SOURCEPOLY_SCROLL` (`0x45821e`) и
  `SET_HANDLEPOLY_SCROLL` (`0x4587a1`) реализованы в VM
  (`res/vm_exec.cpp`, id `0x11/0x23/0x30`) и пишут `i16` в
  `scroll_u`/`scroll_v` (`docs/VM_EXEC.md` §4), но рендер эти значения не
  читает — до этого среза запись была «в никуда». Обратной связи
  «команда → картинка» по-прежнему нет.
* **Кадры анимации не грузятся.** `anim_step` принимает два ключа снаружи;
  таблица клипов `0x6fbd40` (шаг `0x108`), выбор кадра и морфинг объекта
  остаются в `0x433e00`; модуль `.soo`-плеера (`anim/soo_player.*`) сюда не
  подключён и `anim*` не трогает.
* **Лайтмапы/кадры не переключаются.** Ни `lightmap`-анимации, ни смены
  кадров лайтмап в этом срезе нет (`docs/LIGHTMAP_*`, `docs/EFFECTS.md`).
* **`anim2` (`0x66`) вне среза**: он интерполируется тем же `0x4342f0`, но в
  `PolyAnim` не входит.
* **`t` — модель.** Масштаб (тики 91 Гц) и знак (`tick = -param_5`) взяты из
  документации, а не из трассировки вызывающего; для точной сверки с
  оригиналом нужен прогон/трасса `0x451160`/`0x472ccf`.
* **Нормировка осей не применяется** (§2): для 22 % полигонов с ненулевыми
  весами и неединичными осями модуль сдвига отличается от движкового в
  `|axis|` раз.
* **Только арифметика одного полигона.** Нет накопления фазы скролла во
  времени, нет интерполяции осей/`uv_fp` (это `0x4342f0`, доказано, но вне
  `PolyAnim`), нет проверки, что `scroll_*` вообще имеют смысл для полигона
  без текстуры (в поставке все 2917 скролл-полигонов — с эффектом/текстурой,
  отдельно не проверялось).

## 8. Воспроизведение чисел

```sh
# C++-тест: все числа §4 в stdout
./build/sandbox/engine/tests/gm_texture_anim_tests

# те же данные независимым оракулом (gm/sbw.py): разбор полигонов
python3 - <<'PY'
import glob, os, sys
sys.path.insert(0, '.')
import gm.sbw as sbw
G = os.path.expanduser('~/.cache/gunmetal-re/game')
s16 = lambda v: v - 65536 if v >= 32768 else v
polys = scroll = 0
mu = mv = 0
for f in glob.glob(G + '/*.sbw'):
    w = sbw.parse(open(f, 'rb').read())
    for sec in w.sectors:
        for obj in sec.objects:
            for p in obj.polys:
                polys += 1
                su, sv = s16(p.scroll_u), s16(p.scroll_v)
                if su or sv:
                    scroll += 1
                    mu, mv = max(mu, abs(su)), max(mv, abs(sv))
print(polys, scroll, mu, mv)   # 235069 2917 15224 10000
PY
```
