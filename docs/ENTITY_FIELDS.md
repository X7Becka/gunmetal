# Скриптовая таблица сущностей (`0x5b0df0`, `0x5e4680`, `0x616658`): карта (M2.3.6)

Что здесь: что такое три «скриптовые» массива уровня, как устроена строка
таблицы, откуда берутся `id`, флаги и offset, где лежат остальные атрибуты
сущности (тип, позиция, углы, модель, родитель/дети, сектор), полный список
потребителей, таблица «поле → C++ → тест» и проверка на поставочных `.sbt`.

Смежное (не дублируется):

* `docs/FORMATS.md` §12.4 — команды `SCRIPT` и сцена; здесь **исправлена**
  карта битов флагов (§5) и уточнён `ADD_THING_EX` (§6).
* `docs/EVENTS.md` §4.1 — имена и семантика встроенных event id (`0x4acde8`);
  здесь только правило интернирования (§4).
* `docs/THING_FIELDS.md` — типы `0x776d60`/экземпляры `0x7ac080` (модель
  `+0x1a4`, `parent +0x310`, `child_slots +0x318`, `sector +0x3c8`).
* `docs/THINGS_CPP.md`, `docs/VM_EXEC.md` — C++-модель и исполнитель.
* `gm/scene.py` — извлечение сцены; `tools/re/entities.py` — обзор сущностей.

Инструмент: `tools/re/entity_fields.py` (`--map`, `--verify`, `--self-test`,
`--json`; только stdlib, `.sbt` только читаются).

## 0. Коротко

| что | значение |
|---|---|
| запись в `.sbt` | `SCRIPT` (тип 11), хвост: `u32 n` + три колонки `n×u32` |
| счётчик | `0x5b1df0`, предел **`0x400`** (1024), в поставке 297…560 |
| колонки | `0x5b0df0` flags, `0x5e4680` id, `0x616658` offset; **шаг 4**, порядок колоночный |
| логическая строка | 12 байт = `{u32 flags; s32 id; u32 offset}`, но три отдельных массива |
| код | `m` (`0x5e2dd0`) байт по указателю `ds:0x4b6784`; `m ≤ 0x30000` |
| загрузчик | `0x462a80` (читает всё перечисленное + `u8 flag`; при `flag≠0` — ещё 9×`0x400`) |
| писатель | `0x462db0` (сохраняет ровно тот же порядок; блок 3 сейва) |
| компилятор | `0x4606d0` (`EVENT`/`ONESHOT`/`DISABLED`/`INCLUDE`) |
| сброс | `0x456f50` (`n=0`, код `m=0`, sleeping-очередь = `-1`) |
| рантайм-потребитель | `generate_runner` `0x45fa00` (+`generate_event` `0x479960`) |
| в поставке | **36 уровней, 15 061 строка, 249 дублей id**, блоки стыкуются **15 025/15 025** |
| флаги в данных | `0x1ff` × 14 173, `0x3ff` × 591, `0` × 297 — других битов нет |
| `things`-массив записи | `count = 0` во **всех 36** уровнях (сцена строится кодом) |
| `flag` (sleeping) | `0` во всех 36 уровнях; 9 таблиц живут только в сейве/рантайме |

## 1. Метод

1. `tools/ghidra/mcp.py` (headless Ghidra 12.1.4, `docs/GHIDRA.md` §4.1):
   `decompile`/`disasm`/`xrefs`/`bytes`/`batch`.
2. Потребители найдены **xref-ами** на три базы (полный список — §9); у
   каждой колонки 5–14 ссылок, все разобраны — других обращений нет.
3. Семантика битов — из **ассемблера** (`TEST AH,0x2`, `SHL EDX,CL`,
   `AND …,0xfffffe00`), не из декомпилятора: x87/`fild`-код Ghidra местами
   путает (§5, §6).
4. Числа — из поставочных `.sbt` (`--verify`), только чтение.
5. Кросс-проверка: `gm/scene.py:entities()` даёт те же строки (проверяется
   `--verify`, `checks.scene_parity 36/36`).

Все адреса — VA `gundx.exe` 1.36 (`ImageBase 0x400000`).

## 2. Запись и её рантайм-образ

`SCRIPT` (тип 11) — `docs/SBT_RECORDS.md` §2.10; загрузчик `0x462a80`
(декомпиляция, порядок чтения совпадает с `gm/sbt.py:Script`):

```c
u32 c; c*40 things;      // статическая расстановка: c = 0 во всех уровнях
u32 n;                   // -> 0x5b1df0
n*4 flags  -> 0x5b0df0
n*4 id     -> 0x5e4680
n*4 offset -> 0x616658
u32 m      -> 0x5e2dd0
m   code   -> *(u8**)0x4b6784     (0x462bfa читает m байт; m <= 0x30000)
u8  flag                          (0x462c24; 0 -> выйти)
if (flag) 9 * 0x400              // «sleeping scripts» (§8)
```

Проверки загрузчика: `n < 0 || n > 0x400` → `"Invalid script count"`,
`0x462b58`/`0x462b7e`/`0x462ba4` читают колонки ровно по `4n` байт.

**Таблица колоночная, а не массив структур.** Логически строка — 12 байт
(`flags`, `id`, `offset`), но физически это три плоских массива с шагом 4;
поэтому базы разнесены на `0x4000` (при `n = 0x400` каждая занимает ровно
`0x1000`). Кто путает — получает «id» из чужой колонки.

## 3. Карта строки

| смещение | тип | поле | смысл | статус |
|---:|---|---|---|---|
| `+0` | `u32` | `flags` | маска включения: биты 0..7 игроки, `0x100` не-игрок, `0x200` one-shot | **доказано** |
| `+4` | `s32`/`u32` | `id` | интернированное имя события (не индекс!) | **доказано** |
| `+8` | `u32` | `offset` | смещение подскрипта сущности в буфере кода | **доказано** |

Больше в строке **нет ничего**. Тип, позиция, углы, модель, родитель/дети,
сектор — не поля таблицы (§6, §7).

## 4. `id` — интернированное имя, а не индекс

`0x45fb90` (лексер, `param_5` — бит «кто объявил»):

* токен, начинающийся с цифры или `-`, — **число** (`0x45fea0`, поддержка
  `0b`/`0o`/`0x`), id = само число (`1000000`, `901013`, …);
* иначе имя приводится к верхнему регистру и линейно ищется в таблице
  `0x4acde8` (26 записей × `0x30`, счётчик `0x5e3dec`, старт `0x1a`):
  * найдено с индексом `i < 0x1a` → **`id = -i`** (`0` = `SYSTEM_LEVEL_STARTUP`,
    `-1` = `SYSTEM_LEVEL_STARTUP_RESUME`, … `-25`);
  * найдено с `i ≥ 0x1a` → **`id = -30000 - i`**;
  * не найдено → запись добавляется в конец (предел **700** имён),
    **`id = -30000 - i`**.
* `0x463a50`/`0x45f9d0` — обратное преобразование (id → имя) для лога
  `event %ld (%s)`; неизвестный id → `""`.

Отсюда: **имена сущностей невосстановимы** (в `.sbt` лежит только id), а
отрицательные id — это не «коды», а индексы в таблице имён. Проверка по
данным: 885 строк с `id ∈ [-25, 0]` (23…27 на уровень), 9702 строки с
`id < -30000`, 4474 строки с `id ≥ 0` (числовые литералы).

**Дубли id разрешены и все исполняются.** `generate_runner` (`0x45fa00`)
не прерывает цикл после совпадения: он идёт по всей колонке и запускает
**каждую** подходящую строку (счётчик `local_4` только для лога
`"event not defined"`). В поставке 249 таких «лишних» строк (dm1 — 8,
level10 — 24). Порядок исполнения = порядок строк в таблице.

Цикл по строкам разобран по байтам (`0x45fa58`…`0x45fb1c`):

| адрес | что |
|---|---|
| `0x45fa58`/`0x45fa5c` | `MOV ECX,[EDX*4+0x5e4680]` — id строки `EDX` |
| `0x45fa63`/`0x45fa65` | `CMP ECX,EAX` / `JNZ 0x45fb0d` — не тот id, следующая строка |
| `0x45fa6b`/`0x45fa70` | `local_4++` — счётчик **всех** совпадений (для warning) |
| `0x45fa74`…`0x45fa93` | `param_8 & 0xffff < 8` → `SHL EDX,CL` (`CL` = игрок), `TEST EAX,EDX`; иначе `0x45facf` `TEST AH,0x1` (`0x100`) |
| `0x45fa95`…`0x45faa3` | one-shot: `TEST AH,0x2` → `AND EAX,0xfffffe00` → запись в `0x5b0df0[i]` |
| `0x45fac6`/`0x45fb01` | `CALL 0x457390` с offset `0x616658[i]` |
| `0x45fb09`…`0x45fb1c` | `INC EDX`, `ADD EDI,4`, `JL 0x45fa58` — следующая строка |

Строки одного id запускаются **последовательно**: `0x457390` вызывается
для каждой и либо доходит до `0xff`, либо возвращается (SLEEP, §8), и только
потом берётся следующая строка. Поэтому `ENABLE`/`DISABLE` из подскрипта
первой строки влияет на проверку флагов второй (`0x45fa83` читает колонку
в момент запуска строки, а не заранее).

C++: `VmState::entities` — **вектор всех строк** в табличном порядке (не
`map`), `VmState::entity(id)` возвращает первую. `h_generate` идёт по
вектору, фильтруя по флагу источника, и запускает каждую подходящую строку;
остальные строки того же id дожидаются возврата из подскрипта
(`VmStackFrame::generate_id`/`row_cursor`, `leave_frame`).

## 5. Флаги: биты и команды (исправление `FORMATS.md` §12.4)

`docs/FORMATS.md` называет биты 0..8 «состоянием», а 9..16 — игроками. **Это
неверно**: ассемблер однозначен.

| бит | маска | смысл | доказательство |
|---:|---:|---|---|
| 0..7 | `0x001..0x080` | игрок 0..7 включён | `0x45fa8a` `SHL EDX,CL` + `0x45fa91` `TEST` (CL = индекс игрока 0..7) |
| 8 | `0x100` | включён для не-игрового источника | `0x45fad2` `TEST AH,0x1` |
| 9 | `0x200` | **one-shot**: после запуска сбросить `0x1ff` | `0x45fa95` `TEST AH,0x2` → `0x45fa9e` `AND EAX,0xfffffe00` |

Кто пишет:

| кто | что | адрес |
|---|---|---|
| компилятор, `EVENT` | `0x1ff` | `0x460744` |
| компилятор, `ONESHOT` | `0x3ff` | `0x460843` (ветка `s_ONESHOT_004b8cc0`) |
| компилятор, `DISABLED` | `0` | `0x4607c5` (`MOV […],EDI`, EDI = 0) |
| `ENABLE` (cid 5) | `flags \|= 0x1ff` | `0x457c80` |
| `DISABLE` (cid 6) | `flags &= 0xfffffe00` | `0x457c49` |
| `SOURCEPLAYER_ENABLE` (142) | `flags \|= (player < 8 ? 1<<player : 0x100)` | `0x457cef` |
| `SOURCEPLAYER_DISABLE` (141) | `flags &= ~(…)` | `0x457c9e` |
| `generate_runner` | при `0x200`: `flags &= 0xfffffe00` | `0x45fa9e` |

`ENABLE`/`DISABLE` ищут id **линейно по всей колонке** и правят **все**
совпавшие строки (цикла `break` нет). Данные согласны с компилятором:
других значений, кроме `0x1ff`, `0x3ff`, `0` (297 строк — `DISABLED`), в
поставке **нет** (проверяется в `--verify`, `checks.flags 36/36`).

### 5.1. One-shot (`0x200`): точная последовательность

Байты `0x45fa95`…`0x45fac6` (ветка игрока; ветка «не-игрок» `0x45fad4`…
`0x45fb00` идентична, только адресация `[EDX*4]` вместо `[ECX*4]`):

```
45fa95  TEST AH,0x2                  ; бит 9 загруженных флагов этой строки
45fa98  JZ   0x45faaa                ; не one-shot — просто запускаем
45fa9a  MOV  ECX,[ESP+0x10]          ; индекс строки (local_8)
45fa9e  AND  EAX,0xfffffe00          ; маска = ~0x1ff
45faa3  MOV  [ECX*4+0x5b0df0],EAX    ; записали флаги строки
45faaa  ... PUSH аргументы ...
45fac6  JMP  0x45fb01                ; CALL 0x457390(offset, 0, 6 аргументов, handle)
```

Следствия, каждое проверено тестом `vm` (`test_entity_rows`):

1. **Сброс — до вызова** `0x457390`, а не после. Подскрипт уже видит свою
   строку выключенной: `GENERATE` своего же id внутри неё ничего не запустит
   (проверка `0x45fa8a`/`0x45facf` не пройдёт) — рекурсии нет.
2. **Маска `0xfffffe00` = `~0x1ff`** очищает биты 0..8 и **сохраняет бит 9**.
   Строка `0x3ff` → `0x200`: «больше не one-shot-готова, пока её не включат».
3. **Сбрасывается только та строка, которую запускают**, и только в момент
   запуска. У дублей id свои флаги: одна строка может сброситься, вторая —
   остаться (`0x3ff`) и запуститься следом.
4. **После сброса строка не запускается повторно**, пока её не включат:
   `0x200 & (1<<player) == 0` и `0x200 & 0x100 == 0`.
5. **`ENABLE` (cid 5, `0x457c80`: `flags |= 0x1ff`) снова взводит** — `0x200 →
   0x3ff`, следующий `GENERATE` опять запустит и опять сбросит.
6. **`DISABLE` (cid 6, `0x457c49`: `flags &= 0xfffffe00`) бит 9 не трогает**:
   `0x3ff → 0x200`, а `0x200` остаётся `0x200`. То есть `DISABLE` для
   one-shot-строки — не «снять one-shot», а «выключить до `ENABLE`».
7. **`SOURCEPLAYER_ENABLE`** ставит один бит (`1<<player` или `0x100`), сброса
   не отменяет: `0x200 | 0x001 = 0x201` — строка запустится ещё раз для
   игрока 0 (и снова станет `0x200`).
8. `local_4` (счётчик совпадений) растёт **до** проверок флагов, поэтому
   warning `"event not defined"` (`0x45fb2e`) не печатается, даже если все
   строки id выключены.

## 6. Где тип, позиция, углы, модель

Всё это — в **подскрипте** строки (колонка `offset`), в записи условия
`ADD_THING*`, которую читает конструктор `0x46d000` (для `ADD_THING` —
обработчик `0x45d240`, запись 40 байт, `0x45d2a5` `ADD ESI,0x28`):

| `ADD_THING` (cid 1) | тип | поле | статус |
|---|---|---|---|
| `+0x00` | `u32` | `type` — индекс `THING_TYPES` (`0x776d60`), `0xFFFFFFFF` = «нет» | доказано |
| `+0x04` | `i32` | `x` | доказано |
| `+0x08` | `i32` | `y` | доказано |
| `+0x0c` | `i32` | `z` | доказано |
| `+0x10` | `double` | угол 0 | доказано |
| `+0x18` | `double` | угол 1 | доказано |
| `+0x20` | `double` | угол 2 | доказано |

Тип → модель: `THING_TYPES[type] + 0x1a4` (`0x776f04`) → `SOB_TABLE`
(доказано: `0x46d000` делает `iVar2 = param_1 * 0x3a8`, читает
`&DAT_00776f04 + iVar2`).

`ADD_THING_EX` (cid 2) — 56-байтовая запись; разобрана по **обходчику
условий** `0x45d120`, ветка `case 2` (он же и есть настоящий потребитель
записи; `0x45d2c0` дублирует чтение):

| `ADD_THING_EX` | тип | поле | статус |
|---|---|---|---|
| `+0x00` | `u32` | маска режима игры (фильтр `0x45c830`; та же, что у `ADD_ITEM`, `0x459adc`) | доказано |
| `+0x04` | `i32` | `level_lo` (сравнение с `DAT_0083d62c`) | доказано |
| `+0x08` | `i32` | `level_hi` | доказано |
| `+0x0c` | `u32` | `type` (`G`) | доказано (2662/2663 валидны) |
| `+0x10..0x18` | 3×`i32` | `x, y, z` | доказано (данные) |
| `+0x1c..0x33` | 3×`double` | углы (в поставке `0.0`) | гипотеза |
| `+0x34` | `i32` | `extra` (`-1`/`0`) | неизвестно |

Обходчик подтверждает и размер: `*param_1 += 0x2c` от указателя на поле
`type`, т.е. `0x0c + 0x2c = 0x38 = 56` — ровно расстояние до следующей
инструкции в данных.

`ADD_THING_AT_SOURCE` (cid 3), `..._WEAPON_POINT` (4), `ADD_THING_RELATIVE`
(5) позицию не несут: она берётся от источника/точки оружия, поэтому
абсолютная позиция есть только в записях cid 1/2. Все 7563 записи `ADD_THING*` в 36
уровнях дают **валидный** тип или `0xFFFFFFFF` (13 записей — «нет»).

## 7. Чего в таблице нет

| атрибут | где живёт | доказательство |
|---|---|---|
| **родитель/дети** | только рантайм-экземпляр `0x7ac080`: `parent +0x310`, `child_count +0x314`, `child_slots[8] +0x318` | `0x4575d3` (`GENERATE_FOR_CHILDREN`): `[EAX*8+0x7ac394]` = `+0x314`, затем `+0x318+4i`; `0x4576b1` — по `+0x310` |
| **сектор** | экземпляр `+0x3c8`, вычисляется при спавне по позиции | `0x4360f1` (поиск сектора), `0x472790` (чтение) — `docs/THING_FIELDS.md` §4 |
| **порядок спавна** | порядок строк таблицы (для одинаковых id) + порядок `ADD_THING*` внутри подскрипта | `generate_runner` идёт по строкам сверху вниз, `0x46d000` создаёт по мере исполнения |
| **имя** | не хранится: id — уже интернированное имя (§4) | `0x45fb90`/`0x463a50` |
| **модель** | `THING_TYPES[type] + 0x1a4` | `0x46d000`, `0x776f04` |

Важно не спутать: `Things::parent` в C++ — это **id сущности, чей подскрипт
создал вещь**; у движка `parent` экземпляра — слот/`handle` вещи 8..0x10b
(слоты родителя в `0x46d000` у `ADD_THING` равны `-1`, так что для
скриптовых вещей связь не заполняется). `GENERATE_FOR_CHILDREN/_PARENT`
принимают **id события** (не handle): операнд постится детям/родителю
*источника* (handle берётся из состояния ВМ). Данные: 584 таких команды,
573 (98.1%) — существующие id таблицы.

## 8. Вторая таблица записи: sleeping scripts

Если байт `flag` после кода не 0, за ним идут **девять** массивов по `0x400`
(256 × `u32`), в таком порядке (`0x462cxx`, декомпиляция загрузчика):

| # | база | поле |
|---:|---|---|
| 0 | `0x5e4278` | остаток тиков |
| 1 | `0x5e3df0` | **offset подскрипта** (продолжение); `< 0` = слот свободен |
| 2 | `0x616258` | параметр (аргумент 3 `0x457390`) |
| 3 | `0x5e5e58` | параметр (4) |
| 4 | `0x5e2dd8` | параметр (5) |
| 5 | `0x5e39d8` | параметр (6) |
| 6 | `0x5e35d8` | параметр (7) |
| 7 | `0x5e31d8` | параметр (8) |
| 8 | `0x5b29c8` | хэндл источника (аргумент 9) |

### 8.1. Что делает `SLEEP` (cid 7, `0x457390` case 7, `0x45c43b`)

Диспетчер (`0x457729`, ветка `case 7`) сначала считает задержку:

```
457729  MOV EDX,[EBX+ESI]      ; операнд (4 байта)
45772c  MOV ECX,[EBP+0xc]      ; param_2 — «уже прошло тиков»
45772f  SUB EDX,ECX            ; delay = операнд - param_2
457731  ADD EBX,0x4            ; PC += 4
457734  TEST EDX,EDX
457739  JG  0x45c43b          ; delay > 0 -> занять слот и выйти
45773f  NEG EDX               ; иначе carry = -delay
457741  MOV [EBP+0xc],EDX      ; param_2 = carry
457744  JMP 0x45c41b          ; продолжаем тут же
```

Затем `0x45c43b` ищет слот:

```
45c43b  ECX=0, ESI=0x5e3df0
45c442  CMP [ESI],0 / JL 0x45c46c   ; ищем первый слот с offset < 0
45c44b  CMP ESI,0x5e41f0 / JL      ; 256 слотов
45c453  PUSH 0x100 / "Maximum sleeping scripts (%ld reached)" ; нет места
...
45c46c  MOV [ECX*4+0x5e4278],EDX   ; остаток тиков
45c476  MOV [ECX*4+0x5e5e58],[EBP+0x14]
45c480  ... 0x5e2dd8, 0x5e39d8, 0x5e35d8
45c49e  MOV [ECX*4+0x5e3df0],EBX   ; PC продолжения (iVar9+5)
45c4a5  MOV [ECX*4+0x616258],EDI   ; аргумент 3
45c4ac  MOV [ECX*4+0x5e31d8],[EBP+0x24]
45c4b3  MOV [ECX*4+0x5b29c8],EAX   ; хэндл источника (param 9)
45c4ba  POP .../RET                ; выход из 0x457390
```

Семантика:

* **Кто спит** — не сущность и не id, а **подскрипт**: слот адресуется 0..255,
  а не id (поэтому таблица не связана с таблицей сущностей).
* **Тип условия** — таймер в тиках: `timer = операнд − param_2`, где
  `param_2` — второй аргумент `0x457390` («сколько тиков уже прошло»).
  Первый запуск всегда получает `param_2 = 0` (`0x45fac3` `PUSH 0`,
  `0x460272` тоже), пробуждение — переполнение (`0x457356` `PUSH -iVar1`).
* `timer <= 0` → **не спит**: `param_2 = -iVar19` (`0x45c4b8`) и выполнение
  продолжается тут же (переполнение переносится на следующий `SLEEP`).
* `timer > 0` → слот заполняется и **`0x457390` возвращается**; остаток этого
  (под)скрипта выполнится позже с того же PC с теми же шестью аргументами и
  тем же хэндлом источника. Для вложенного `GENERATE` это значит, что
  вызывающий скрипт продолжает работу сразу (возврат из вложенного вызова),
  а не ждёт.
* **Как просыпается** — тикер `0x457230(dt)` (он же крутит игровые таймеры):
  для каждого занятого слота `0x5e4278[i] -= dt`; при `< 1` вызывает
  `0x457390(offset, -остаток, 6 параметров, хэндл)` и освобождает слот
  (`0x5e3df0[i] = -1`, `0x45731d`). Порядок пробуждения — по номеру слота.
* **`STOP_SOURCEPLAYER_SLEEPING_SCRIPTS`** (cid 198, `0x45b93e`): освобождает
  все слоты, у которых `(0x5b29c8[i] & 0xffff)` равен хэндлу источника.
* **Переполнение**: при 256 занятых слотах печатается
  `"Maximum sleeping scripts (256 reached)"` и остаток текущего скрипта
  **отбрасывается** (обработчик делает `RET`).

В поставке `flag = 0` у всех 36 уровней, но команд `SLEEP` — **7954**
(6947 в верхнем уровне блоков + остальные внутри `IF`), максимум на уровень
276 (level23). Таблица целиком рантаймовая: в файл попадает только из сейва.

C++ (`VmState::sleeping`, 256 `VmSleepSlot`, `VmOptions::sleep_queue`):
`h_sleep` считает `delay = операнд − state.sleep_carry`, при `delay > 0`
занимает первый свободный слот (`offset = insn.next`, `ticks = delay`,
`source = source_handle`) и возвращается из подскрипта через `leave_frame`
(вызывающий продолжает), иначе обновляет carry и идёт дальше;
`vm_tick_sleepers(state, ticks)` — тикер (`0x457230`), возвращает `VmWake`
(offset, carry, хэндл); `vm_load_sleeping_scripts` читает девять массивов в
порядке выше; `vm_stop_sleeping` — cid 198.

## 12. Что не перенесено в C++ (приоритет для runtime)

1. ~~**Карта битов игроков**~~ — сделано: `source_player_bit` = `1u << player`
   (было `9 + player`), тест `test_entity_rows` (3).
2. ~~**One-shot (`0x200`)**~~ — сделано: `VmEntity::one_shot`, сброс `0x1ff`
   в `next_generate_row` **до** входа в подскрипт; тесты 1, 2, 4.
3. ~~**Дубли id**~~ — сделано: `VmState::entities` — вектор всех строк,
   `h_generate` запускает все подходящие последовательно; 249 строк поставки
   больше не теряются; тесты 4, 5.
4. ~~**Sleeping-таблица**~~ — сделано: `VmState::sleeping` (256 слотов × 9
   полей), `h_sleep`/`vm_tick_sleepers`/`vm_stop_sleeping`,
   `vm_load_sleeping_scripts`; тест `test_sleep_table`. Не подключено к
   игровому циклу (`engine/src/game/**` вне этой задачи) и по умолчанию
   выключено (`VmOptions::sleep_queue`), потому что инлайновая модель
   `clock += n` — то, на чём построены golden-тесты Python-референса.
5. **Сектор при спавне** (`0x4360f1`): нужен для `SET_SECTOR_*`/звука; в
   `Things` поля нет.
6. **Типы шести параметров SLEEP** (`0x616258`…`0x5e31d8`): сохраняются и
   возвращаются как есть, но их смысл (позиция/цель/что-то ещё) не доказан.

## 13. Доказано / гипотеза / осталось

**Доказано**

* три базы, шаг 4, колоночный порядок, счётчик `0x5b1df0` и предел `0x400`
  (`0x462a80`, `0x462b58`…`0x462d85`); писатель `0x462db0` симметричен;
* `id` — интернированное имя, формула `-i` / `-30000-i` / число
  (`0x45fb90`, `0x45fea0`, `0x463a50`);
* биты флагов 0..7/8/9 и все семь писателей (§5);
* `offset` — смещение подскрипта, исполняется `0x457390`; 15 025/15 025
  блоков стыкуются;
* `ADD_THING` (40 байт) и `ADD_THING_EX` (56 байт) — поля и адреса;
* модель = `THING_TYPES + 0x1a4` (`0x776f04`);
* `GENERATE_FOR_CHILDREN/_PARENT` ходят по рантайм-связям `+0x310`/`+0x318`;
* порядок запуска дублей и сброс one-shot до вызова (§4, §5.1):
  `0x45fa58`…`0x45fb1c`, `0x45fa95`/`0x45fa9e`;
* sleeping-таблица: девять массивов, порядок в файле, семантика `SLEEP`
  (`timer = операнд − param_2`, выход из `0x457390`), тикер `0x457230`
  (`-остаток` в `param_2`), `STOP_…` `0x45b93e`, предел 256 (§8).

**Гипотеза**

* углы `ADD_THING_EX` (`+0x1c..0x33`) — ориентация (в данных всегда `0.0`);
* поле `+0x34` (`-1`/`0`) — владелец/флаг;
* «маска режима» `+0x00` покрывает ровно те биты, что проверяет `0x45c830`
  (в данных только `1`, `31`, `33`, `63`).

**Осталось**

* имена сущностей (интернирование необратимо, если имени нет в `.sbt`);
* смысл `901013` и подобных числовых id, не встречающихся в таблице;
* связь «сущность → экземпляр» в рантайме (id события vs handle вещи) —
  частично, через `GENERATE_FOR_*`;
* шесть параметров sleeping-слота `0x616258`…`0x5e31d8` сохраняются и
  возвращаются без изменений, но их смысл (аргументы 3..8 `0x457390`) не
  доказан; хэндл источника (`0x5b29c8`) в C++ берётся из `source_player`
  (`0xffff` = «нет источника»), потому что хэндлов вещей модель не хранит.
