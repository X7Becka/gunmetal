# Отрицательные индексы текстур: кадры спрайтов/анимаций в кадровом проходе (M4.2.6)

Что здесь: закрыт вопрос из `docs/TEXUV.md` §2.4 — «отрицательный `poly+0x00`
— это, вероятно, спрайты/эффекты». Разобрана **ветка `0x9fdf07`** (что

`индекс → запись → .SOA → текстуры кадров → архив SBM`.

## 1. Ветка отрицательного индекса (код)

### 1.1 Где выбирается индекс

Setup текстуры — `0x9fde50` (обёртка) / `0x9fde70` (тело); её зовёт drawer
полигона `0x41b6cb` сразу после пролога, до любой работы с геометрией
(`0x41b6dd`), и он уважает `-1` как «не рисовать» (`0x41b6e9` → выход в
`0x41c710`).

```c
// 0x9fde78 .. 0x9fdefc
handle = word[poly + 0x72];              // = link_sector + 1 (WORLD_FIELDS §2.4)
ecx    = (handle < 1) ? -0x78 : 0;       // 0x9fde8e cmp / 0x9fde91 sbb / 0x9fde9d and
index  = (i16) word[poly + ecx + 0x78];  // 0x9fdefc: poly+0x00 либо poly+0x78
```

То есть для статического полигона индекс — `poly+0x00`, для полигона со
ссылкой на сектор (`poly+0x72 != 0`) — **оверлей** `poly+0x78`. Оба поля
знаковые; `0x41de7d` и `0x9fdefc` используют `movsx`.

### 1.2 Развилка `0x9fdf07` (доказано)

```c
// 0x9fdf07: test eax,eax ; 0x9fdf09: jns 0x9fdf1f
if (index < 0) {
    eax = resolve_frame(index,                       // 0x41de7d
                        *(u32 *)(poly + 0x68),       // 0x9fdf12: start tick
                        *(u32 *)0x9e82d8);           //          now (ticks)
}
*(u32 *)0x9e8cac = eax;                              // 0x9fdf1f: «текущая текстура»
```

Якоря (байты — в таблице `ANCHORS` инструмента):

| адрес | байты | смысл |
|---|---|---|
| `0x9fde78` | `66 8b 4b 72` | `handle = word[poly+0x72]` |
| `0x9fde8e` | `83 f9 01 19 c9` | `cmp handle,1` / `sbb ecx,ecx` → 0 или −1 |
| `0x9fde9d` | `83 e1 88` | `and ecx,0xffffff88` → `−0x78` при `handle < 1` |
| `0x9fdefc` | `0f bf 44 0b 78` | `movsx eax,word[poly+ecx+0x78]` — сам индекс |
| `0x9fdf07` | `85 c0` | `test eax,eax` |
| `0x9fdf09` | `79 14` | `jns 0x9fdf1f` — **неотрицательный индекс идёт мимо резолвера** |
| `0x9fdf12` | `8b 53 68` | второй аргумент: `poly+0x68` |
| `0x9fdf17` | `e8 61 ff a1 ff` | `call 0x41de7d` |
| `0x9fdf1f` | `a3 ac 8c 9e 00` | `[0x9e8cac] = eax` |

Резолвер (**`0x41de7d`**, аргументы `(id, t_start, t_now)`), формула уже
доказана в `docs/SOA.md` §4; здесь важны только адреса полей:

| адрес | байты | смысл |
|---|---|---|
| `0x41de83` | `83 c8 ff 2b 45 08` | `rec = 0x5642c8 + (−1 − id)·0x5c` |
| `0x41de89` | `6b c0 5c` | `imul eax,eax,0x5c` (шаг записи) |
| `0x41de8c` | `05 c8 42 56 00` | `+ 0x5642c8` (база таблицы) |
| `0x41deb2` | `8b 08` | `mode = rec+0x00` |
| `0x41decb` | `3b 42 04` | `cmp t, rec+0x04` (`period` в тиках) |
| `0x41ded9` | `0f bf 44 50 0a` | `mode 0`, `t ≥ period`: `frames[declared−1]` (`rec+0x0a+2·declared`) |
| `0x41dee7` | `f7 79 04` | `idiv period` → `rem = t % period` |
| `0x41defb` | `f7 79 04` | `idiv period` → `k = rem·declared / period` |
| `0x41df01` | `0f bf 44 42 0c` | `frames[k] = word[rec+0x0c+2k]` |
| `0x41df18` | `e8 33 fd 02 00` | иные режимы → `0x44dc50` (возвращает `frames[0]`) |

Запись `0x5c` байт (порядок полей доказан загрузчиком, §2.1):

| смещение | поле | смысл |
|---|---|---|
| `+0x00` | `i32 mode` | `0` — один раз (кладётся на последний кадр), `1` — цикл, `100/101/102` — спец (часы/фильм, `0x44dc50`) |
| `+0x04` | `i32 period` | длительность цикла **в тиках** (91 Гц); у `.soa` это `period·91/100` |
| `+0x08` | `i32 declared` | число кадров, 1..32 |
| `+0x0c + 2i` | `u16 frames[i]` | id кадров (1-based id в реестре текстур) |
| `+0x4c` | `char name[16]` | имя эффекта (`strncpy`, 0x42ac5b) |

Модель в инструменте (`effects.py`, `frame_index`) — точная копия ветки:

```python
if mode not in (0, 1):  return 0            # 0x41df18 -> 0x44dc50
if mode == 0 and t >= period:  return n-1   # 0x41decb/0x41ded9
return (t % period) * n // period           # 0x41dee7/0x41defb/0x41df01
```

Отрицательное `t` не моделируется: в отличие от `.soo` (`0x433e84` прижимает
к 0) у `0x41de7d` клампа нет, `idiv` даёт отрицательный остаток и индекс
уходит **до** массива (чтение вне записи). В поставочных данных `t ≥ 0`
(`poly+0x68 = 0`, `[0x9e82d8] ≥ 0`), так что ветка недостижима.

### 1.3 Куда попадает кадр (доказано)

Кадр — это **id текстуры**, а не отдельный объект:

* setup пишет его в `[0x9e8cac]` (`0x9fdf1f`) — то же место, куда попадает и
  положительный индекс;
* растеризатор кадрового прохода берёт `[0x9e8cac]`, вычитает 1 и сдвигает
  на 4: `0x41be0a`/`0x41be13`/`0x41be16` → `[0x9e82c8] + (id−1)·16`; запись
  `+0` — указатель на дескриптор, у него `+0x0d/+0x0e` — логарифмы ширины
  и высоты (маски координат, `0x41be1c`..`0x41be33`);
* путь спрайтовых объектов делает ровно то же: `0x41c883`/`0x41c88c`
  (`base + id·16 − 16`), только id берётся из `obj+0x20` (см. `docs/SOA.md`
  §4, «Потребитель»).

Реестр, из которого растёт `id`, — `0x76ed40`, **0x800 записей × 16 байт**,
обнуляется при загрузке мира (`0x42aab1`, `memset(0x76ed40, 0, 0x8000)`) и
заполняется таблицей текстур `.sbw` (следующий раздел). Поля записи:
`+0` указатель на изображение, `+5` `kind` (0 — `pics\`, 1 — `sprites\`),
`+6` `loop`, `+7` `char name[9]`.

### 1.4 Какие ещё поля полигона участвуют

`effects.py --self-test` сканирует все обращения `[ebx+…]` в теле setup
`0x9fde70`..`0x9fe4f0` (ebx — полигон); полный список:

| поле | где | роль в этой ветке |
|---|---|---|
| `+0x71 n_idx` | `0x9fde93` | `n_idx ≤ 2` → пропуск (`0x9fe4cb`), **до** чтения индекса; в поставке таких эффект-полигонов нет (0) |
| `+0x72 link_sector+1` | `0x9fde78` | выбирает источник индекса (`+0x00` или `+0x78`) |
| `+0x00 texture` / `+0x78 overlay` | `0x9fdefc` | сам id (знаковый, `movsx`) |
| `+0x68 start` | `0x9fdf12` | начало анимации в тиках; запись 0 в поставке, ставится при спавне объекта `0x43aff5` |
| `+0x7a f7a` | `0x9fdea6` | прибавляется к `word[ctx+0x14]` (база текстурных классов уровня) → запись класса `[0x9e82c4] + idx·0x40`, её первый dword — `[0x9e8c9c]`; в данных `f7a == 0` у всех 235 069 полигонов |
| `+0x7c flags` | `0x9fe06b` | проверяется только бит `0x4` (команда `xor`, `0x46adbc`) |
| `+0x14 normal` | `0x9fe0ee` | переводится в видовые координаты (`0x9fdde0`) |
| `+0x38/3c/40 corner_a`, `+0x44/48/4c corner_b` | `0x9fdf67`..`0x9fdff3` | экранный bbox/клип полигона |
| `+0x02 material`, `+0x04 lightmap`, `+0x70 brightness`, `+0x50/54/58 UV` | — | в setup **не читаются**: их потребляет общий растеризатор (`0x41be..`), см. `docs/WORLD_MATERIALS.md` |

Тест «пропустить или рисовать» (`0x9fdf24`..`0x9fdf3e`) идёт **после**
резолвера и проверяет уже кадр: `frame != 0` → рисовать. Кадровые id в
поставке никогда не 0 (10 762/10 762 в диапазоне `1..count1`), поэтому все
6135 эффект-полигонов проходят эту проверку; отсекаются они только общими
гейтами (видимость сектора, backface culling `0x41ad37`, клип).

## 2. Соответствие `-k` → ресурс

### 2.1 Загрузчик `.sbw` (`0x42aa63`) — доказательство порядка

```
0x42aab1  memset(0x76ed40, 0, 0x8000)          // реестр текстур
0x42aaca  fread(&count1, 4, 1, f)              // таблица текстур
0x42ab4b  strncpy(0x76ed47 + i*16, name, 9)    //   имя
0x42ab67  fread(0x76ed46 + i*16, 1, 1, f)      //   loop
0x42ab8e  fread(0x76ed45 + i*16, 1, 1, f)      //   kind
0x42abb3  fread(0x5310c0 + i*4, 4, 1, f)       //   refcount
0x42abd7  fread(&count2, 4, 1, f)  -> [0x5670cc]   // таблица эффектов
0x42ac5b  strncpy(0x564314 + j*0x5c, name, 16) //   имя  (rec+0x4c)
0x42ac77  fread(0x5642c8 + j*0x5c, 4, 1, f)    //   mode (rec+0x00)
0x42ac9e  fread(0x5642cc + j*0x5c, 4, 1, f)    //   period (rec+0x04)
0x42acc5  fread(0x5642d0 + j*0x5c, 4, 1, f)    //   declared (rec+0x08)
0x42ad13  fread(0x5642d4 + j*0x5c + 2k, 2, 1, f)  // frames (rec+0x0c)
```

`j` — **индекс в файле**, 0-based. Значит `-k` (k = 1..count2) — это
`j = k−1`, то есть `level.effects[k-1]` в `gm/sbw.py`. Никакой сортировки,
поиска по имени или зависимости от порядка загрузки: таблица читается
подряд и ровно затирает прошлую (`count2` пишется в `[0x5670cc]`).
Реестр текстур тоже пересобирается с нуля (`memset`), поэтому id кадров
всегда указывают в текстуры **этого** файла.

Писатель `.sbw` `0x42afbb` — зеркальный (`fwrite` тех же полей), имя эффекта
он берёт из `rec+0x4c` (`strlen+1`), что подтверждает: в файле лежит именно
рантайм-запись.

### 2.2 Имя → `.SOA`

Имя записи (`rec+0x4c`, до 15 символов) — это имя файла анимации без
расширения. Загрузчик спрайтов/анимаций `0x42b81b` (`docs/SOA.md` §2) ищет
`anims\<name>.soa` (для `kind 0`), `spritani\<name>.soa` (для `kind 1`),
`flaganim\<name>.soa` (для `kind 4`). Для уровневых полигонов файл не
перезагружается — запись уже прочитана из `.sbw` (§2.1), но содержимое
совпадает, и это проверено на данных:

* 262 (уровень, эффект) — 262 совпадения `mode`, `period` (в тиках),
  `declared` и **имён кадров** (48/48 разных имён, §5).

То есть `.SOA` — авторский источник, а `.sbw` хранит уже сконвертированную
запись (`period` в тиках = `period_cs·91/100`); пример: `anims/Brief.SOA` →
`1 72 3 1` → 65 тиков = `start` записи `BRIEF`.

### 2.3 Кадр → текстура → архив

`frames[i]` — 1-based id в реестре `0x76ed40`, то есть индекс в таблице
текстур того же `.sbw` (`level.tex[id-1]`). `kind` записи реестра выбирает
каталог (доказано загрузчиком изображений):

| адрес | байты | что |
|---|---|---|
| `0x423d36` | `8a 48 05` | `kind = byte[registry_entry+5]` |
| `0x423d49` | `68 b4 8d 4a 00` | `push "pics\\%s.sbm"` |
| `0x423db1` | `68 cc 8d 4a 00` | `push "sprites\\%s.sbm"` |

`kind` в `.sbw` — старший байт поля `flag` (`flag = loop \|\| kind<<8`).
Оба каталога — BIGFILE-архивы: `PICS/SBM.IDX` (1648 записей) и
`sprites/SBM.IDX` (179). Для всех кадров, **достижимых с полигонов**,
`kind == 0` → `PICS/SBM.IDX`; архив спрайтов в этой ветке не используется.

Если разрешать кадры **всех** объявленных записей (включая недостижимые
`mode 0`), находятся все **10 762/10 762** ссылки: 4242 — `kind 0`
(`PICS`), 6520 — `kind 1` (`sprites`). То есть «взрывы» рисуются спрайтами
из `sprites/SBM.IDX` (например, `blksmk_a/b/c`, `wtrb0001…`), а не
текстурами уровня; **не сопоставлено ничего** — и по достижимым, и по
объявленным кадрам.

### 3.4 Чего в поставке нет

* **`mode 0` (одноразовые) с полигонов недостижимы.** В 1333 записях
  36 уровней: `mode 0` — 542, `mode 1` — 764, `100/101/102` — 1/12/14.
  Полигоны достигают только `mode 1` (6094 полигона), `100` (3), `101` (22),
  `102` (16). То есть все «взрывы» (`expl1..4`, `smoke1`, `sparks`,
  `nuke1`, `Lightng`, `frbl`, …) объявлены в таблицах, но **на стены не
  натянуты** — их создают спавны вещей (`.sbt` `THING_TYPES`/`SPRITES`,
  `docs/SPRITE.md`), и уже там работает тот же `0x41de7d`.
* **`SPRITES` в поставочных `.sbt` нет** (тип 6: 0 записей во всех 36
  файлах), поэтому корреляцию «полигон ↔ SPRITES» измерить не на чем; поле
  `effect_id` (`+0x20`, `i32`) у спрайт-объектов — из того же id-пространства
  (`0x41c7f4` → `0x41de7d`), но данных в поставке нет.
* **`THING_TYPES`** (тип 4, 2896 записей, 397 разных имён) пересекается с
  именами эффектов только двумя: `frbl`, `lasflare` — тип вещи может
  называться так же, как анимация; это совпадение имён, а не общий ресурс.
* `.sub`-подстановки (`sprites/sprites.sub`) применяются только при
  `ram_class <= weight` (`docs/SUB.md` §2), на машине с > 24 МБ — никогда;
  для рендера эффектов их можно игнорировать.

## 4. Что рисовать и в каком порядке

### 4.1 Часы кадра (доказано)

```
t = [0x9e82d8] − poly+0x68            # тики 91 Гц
frame = frames[(t % period) * declared / period]      # mode 1
```

* `poly+0x68` у всех поставочных полигонов **0** (`docs/WORLD_FIELDS.md`
  §2.4, 235 069/235 069) — фаза равна текущему времени рендера. Значение
  ставится только при спавне экземпляра объекта: `0x43aff5` в
  `FUN_0043ad40` пишет `[ebp+0x18]` во **все** `poly+0x68` копии объекта.
* Тот же `poly+0x68` и те же часы использует скролл текстуры:
  `0x41bdb8`..`0x41bdc4` считают `(now − poly[0x68])·scroll_u` и прибавляют
  к `uv_u`; `0x41bddd`..`0x41bdf0` — то же для `scroll_v`. Это независимое
  подтверждение семантики `+0x68` («начало анимации полигона»), а не только
  эффектов.
* `[0x9e82d8]` — «время рендера» в тиках; в `gundx.exe` его никто не
  записывает (все 6 обращений — чтения, `docs/SOA.md` §3): значение
  приходит от таймера/оверлея. Отсюда **гипотеза**: это тики уровня
  (`0x5a46e4`, 91 Гц) либо близкая величина; для картинки важна только
  фаза, набор кадров от базы не зависит.
* Точное равенство `1 тик = 1000/91 мс ≈ 10.99 мс` доказано
  (`0x4074e0` `Sleep(elapsed+11)`, `0x44db80` считает 91 тик за секунду).

Готовый расчёт кадра — `effects.frame_index(mode, period_ticks, declared, t)`.

### 4.2 Порядок и глубина (доказано в объёме «нет отдельного прохода»)

* Цикл видимых полигонов `0x41ac99`..`0x41add0` (шаг полигона `0x80`) зовёт
  drawer `0x41b6cb` для каждого выжившего полигона, **не глядя на индекс**
  (`docs/TEXUV.md` §2.1). Drawer зовёт setup (`0x41b6dd`) и при `-1`
  выходит (`0x41b6e9`).
* Значит эффект-полигон рисуется **в общем потоке**: тот же порядок
  (порядок полигонов объекта/сектора), тот же клип/bbox, та же запись в
  буфер. Никакой отдельной «очереди эффектов», отдельного прохода или
  сортировки по глубине в этой ветке нет.
* Глубина для эффекта — обычная глубина полигона: setup не читает
  `poly+0x02`/`+0x04`/`+0x70`, эти поля потребляет общий растеризатор
  (`0x41be..`). Спец-обработки «эффект ближе/дальше» в коде не найдено.

### 4.3 Alpha/blend — **не доказано** (остаток)

Ветка кадра не трогает ни материал, ни блендинг: единственное, что она
меняет, — `[0x9e8cac]` (id изображения). В setup есть один «непрозрачный»
признак — байт `byte[image_entry+4]`, который кладётся в `[0x9e8ca4]`
(`0x9fdfa0`) и сравнивается с 2 (`0x9fe0cd`); что это за поле (формат?
наличие маски?) и что делает ветка `al == 2` — не разобрано. Материал
полигона в этой сборке различается только битом 0 (`docs/WORLD_MATERIALS.md`
§2.4), а сам кадр уходит в `D3DImm.dll`. Поэтому:

* **не** закладывать в рендер «эффекты = alpha-blend» без отдельного
  доказательства;
* прозрачность кадра, если она есть, приходит из SBM/палитры и материала
  полигона (`material` 0..4 в данных: у 6135 эффект-полигонов 0 — 2820,
  4 (add) — 2992, 1 — 210, 2 — 55, 3 — 58), а не из «типа эффекта».

### 4.4 Чеклист для `gm/render.py` / C++

1. Знаковый индекс: `texture = i16(word[poly+0])`; `index = link_sector < 1
   ? texture : i16(word[poly+0x78])`.
2. `index >= 0` — как сейчас (0 — пропуск, `>0` — текстура).
3. `index < 0` — `effect = effects[-1 - index]` из **этого** `.sbw`
   (не искать по имени!); `frame = frame_index(effect.mode, effect.start,
   len(effect.ids), now_ticks - poly[0x68])`.
4. `frame` — 1-based id текстуры → `level.tex[frame-1]` → SBM из
   `PICS/SBM.IDX` (kind 0) или `sprites/SBM.IDX` (kind 1).
5. Дальше — обычный путь полигона (UV `docs/TEXUV.md` §1, лайтмап,
   материал); отдельного прохода/сортировки не добавлять.
6. `mode 100/101/102` (`DCLOCK1`, `DCLOCKLG`, `FILM`) — один кадр, в
   который движок **дорисовывает** текст (часы/титры) через `0x44dc50`;
   без этого будет просто пустой/статичный кадр (`docs/SOA.md` §6).

## 6. Остатки и гипотезы

1. **`[0x9e82c8]` — инициализация вне `.text`.** Таблица дескрипторов
   изображений (шаг 16, 1-based) читается в `0x41be16`, `0x41c88c`,
   `0x41a077`, `0x9fdf85`, но записей в `gundx.exe` нет (как и у
   `0x9e82c4`/`0x9e82d0`); заполняется таймером/оверлеем (`docs/SUB.md`,
   «остатки»). Для этой задачи достаточно, что id — это id реестра
   `0x76ed40`, а не «магическое число».
2. **`[0x9e82d8]` vs тики уровня `0x5a46e4`.** Одно и то же или сдвиг — не
   доказано (`docs/SOA.md` §3); влияет на фазу.
3. **Поле `byte[image_entry+4]` → `[0x9e8ca4]` и ветка `al == 2` (0x9fe0cd).**
   Кандидат на «прозрачный/маскированный» кадр; не разобрано вместе с
   `D3DImm`.
4. **Тайл/UV для спрайтовых кадров.** У кадров-спрайтов (`ARC-2` 16×64,
   `PULSAR` 8×4) UV-формула `docs/TEXUV.md` §1 даст координаты далеко за
   пределами кадра; движок сворачивает их маской `(0x10000 << log2w) − 1`
   (`0x41be21`..`0x41be33`) и вычитает свёрнутое на `0x41be6b`, но как это
   выглядит для «плитки» на большом полигоне, на кадрах не проверялось.
5. **`mode 0` на стенах не встречается**, поэтому ветка «t ≥ period →
   последний кадр» на поставочных уровнях не наблюдаема; проверена только
   кодом и синтетикой. Для спавнов (взрывы) её нужно будет свести с
   `docs/SPRITE.md` и таблицей спавнов `0x5ab808`.
6. **`.sow` (текст) и редактор.** `0x426d28`/`0x426e7a` пишут в `.sow`
   **имя** эффекта для `index < 0` — ещё одно подтверждение, что «-k» —
   ссылка на запись таблицы, а не число.
