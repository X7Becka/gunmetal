## 1. Иконка оружия: запись `DEFINE_WEAPONS` → `WICONn`/`WCONn`

Иконка **не** выбирается по таблице «вид оружия → номер»: она лежит прямо в
записи оружия, которую строит загрузчик `DEFINE_WEAPONS`.

### 1.1. Что читает HUD

| шаг | адрес | что делает |
|---|---|---|
| слот | `0x4928eb` | `eax = [player+0x3294]` (`weapon_slot`, `docs/PLAYER_FIELDS.md` §3) |
| граница | `0x4928f1`, `0x4928f9` | `0 <= slot < [0x819028]` (счётчик оружия), иначе ветка `NO WEAPON` (`0x492b14`, строка `0x4be5cc`) |
| имя | `0x49291e` | `0x47faf0(6, 0x80fc98 + slot*0x2A8, buf, 23, 162, pitch, 0)` — `MACHINE GUN` |
| иконка | `0x49292f`..`0x492983` | копия 24×24 из записи в кадр (см. §3) |

Запись оружия: база `0x80fa00`, шаг `0x2a8` (680), счётчик `0x819028`
(максимум 31 — `cmp ecx,0x1f` в `0x450be6`).

| смещение | размер | что | доказательство |
|---|---|---|---|
| `+0x000` | 8+… | параметры (заряд, разброс, дальность…) | `docs/FORMATS.md` §12.3 |
| `+0x050` | `0x240` | **индексный растр иконки 24×24** (по 24 байта в строке) | `0x450c82..0x450c9c` |
| `+0x290` | 4 | хендл звука (`0x40b9c0`) | `0x450c68` |
| `+0x298` | 16 | имя для подписи (`strncpy` 15 + NUL) | `0x450c35`, `0x450c37` |
| `+0x2a7` | — | конец записи | шаг `0x2a8` |

### 1.2. Загрузка растра

```
0x450c82  lea eax,[edx*8+0x80fa50]      ; dest = 0x80fa50 + slot*0x2a8
0x450c97  push 0x18 / push 0x18          ; height / width = 24
0x450c8b  push 0                       ; 0
0x450c96  push esi                     ; имя иконки (третий операнд записи)
0x450c97  push 0x4abbec                ; "frontend"
0x450c9c  call 0x47efe0                ; загрузчик BMP из FRONTEND/BMP.IDX
0x450ca8  push 0x4ac650                ; "Unable to load weapon icon (%s)"
```

* `0x80fa50 = 0x80fa00 + 0x50` — ровно поле иконки (§1.1).
* Если третий операнд — строка `none` (`0x4a6968`, сравнение `0x450c68`), растр
  зануляется (`0x450dd0`: `rep stos` 0x90 dword = 0x240 байт).
* Ошибка загрузки не фатальна: печатается предупреждение, запись остаётся с
  нулями.

### 1.3. Третий операнд записи = имя ассета

`DEFINE_WEAPONS` (опкод 170) в `.sbt` — это `u32 n` и `n × (3×S + 0x54)`, три
строки: **имя оружия, имя звука, имя иконки** (`docs/FORMATS.md` §12.3).
Поставка: **36 `.sbt`**, **684 записи**, но уникальных видов оружия всего
**19** — каждый вид всегда с одной и той же иконкой (конфликтов нет):

| оружие | ассет | оружие | ассет |
|---|---|---|---|
| `MACHINE GUN` | `WICON1` | `DISINTEGRATOR` | `WCON11` |
| `CANNON` | `WICON3` | `PLASMA CANNON` | `WCON16` |
| `AUTOCANNON` | `WICON4` | `ROCKET` | `WCON18` |
| `RAILGUN` | `WICON5` | `RGM` | `WCON20` |
| `GRENADE` | `WICON6` | `MICROWAVE GUN` | `WCON22` |
| `FLAMETHROWER` | `WICON7` | `MESON GUN` | `WCON23` |
| `TAC NUKE` | `WICON8` | `EMP GUN` | `WCON24` |
| `LASER` | `WICON9` | `DISRUPTORFIELD` | `WCON25` |
| `FUSIONBEAM` | `WCON10` | `VIRAL AGENT` | `WCON41` |
| | | `MRL` | `WCON43` |

Проверка: `python3 tools/re/hud_icons.py --icons` — все 19 ассетов есть в
`FRONTEND/BMP.IDX` и все 24×24 (N/N), плюс побайтовая сверка каждой тройки в

> **Исправление к `docs/HUD_COMPOSE.md` §2, п. 3.** Утверждение «`WCON*` —

> (у `VIRAL AGENT`, `ROCKET`, `LASER-соседей` и т. п.), они лежат в том же поле
> `+0x50` записи оружия. Иконки снаряжения — отдельный атлас `equip%d` (§2).

## 2. Иконка экипировки: `DEFINE_EQUIPMENT` → `equip%d` (`EQUIPn`)

Иконки экипировки грузятся **один раз, пачкой**, а не вместе с записью:

```
0x48fa6a  mov esi,0x683ff8              ; база массива иконок
0x48fa6f  sprintf(buf, "equip%d", i)    ; строка 0x4be3a8
0x48fa86  push 0x18 / 0x18 / 0          ; height / width / flags
0x48fa8b  push esi                     ; dest
0x48fa8c  push buf                     ; "equip0".."equip11"
0x48fa8d  push 0x4abbec                ; "frontend"
0x48fa92  call 0x47efe0
0x48faa2  add esi,0x240                ; 24*24 = 576
0x48faa9  cmp esi,0x685af8             ; 12 итераций (0x1b00 / 0x240)
```

| адрес | смысл |
|---|---|
| `0x683ff8` | массив 12 × 24×24 индексных растров (шаг `0x240`) |
| `0x4be3a8` | формат имени `equip%d` |
| `0x492b32` | `eax = [player + 0x3320]` — индекс экипировки (см. §2.1) |
| `0x492cc3` | `cmp eax, 0xc` — HUD показывает только индексы 0..11 |
| `0x492b53` | имя: `0x814c8c + idx*0x40` (`%s`, формат `0x4a6874`), рисуется в `(227,169)` шрифтом 6 (`0x492b74`) |
| `0x492ce4` | источник иконки: `0x683ff8 + idx*0x240` |
| `0x492d26`–`0x492d2e` | подсветка: `test [player+0x3328], 1 << idx` → рамка-дизеринг `0xAA` |

### 2.1. Где лежит индекс (`player+0x3320`)

Индекс читается как `[player + 0x3320]` (для игрока 0 — абсолютный
`0x81c360`), маска активной экипировки — как `[player + 0x3328]` (`0x81c368`).

Доказательство — внутри самой функции. Аргументы вызывающего лежат по
`[esp+0x58]` (ret), `[esp+0x5c]` (буфер кадра, `ebp`), `[esp+0x60]` (pitch,
`esi`), `[esp+0x64]` (индекс игрока, `ebx`). В `0x4928d5..0x4928e4` код заново
считает `edi = ebx*0x3510`, а в `0x4928e7` **пишет его в слот arg2**:
`mov [esp+0x60],edi`. Поэтому все последующие чтения `[reg+0x81cXXX]` — это
`[i*0x3510 + 0x81cXXX]`, где `0x81…` уже **абсолютный адрес игрока 0**.
Pitch остаётся в `esi` (`0x492937`, `0x492cd1`, `0x492949` — шаг строки).

```
4926ac  mov ebx,[esp+0x64]        ; arg3 = индекс игрока
4926b0  mov esi,[esp+0x60]        ; arg2 = pitch = 320
4926c4..4926d6  eax = ebx*0x3510; fild [eax+0x81c288]   ; броня +0x3248
4928d5..4928e4  edi = ebx*0x3510
4928e7  mov [esp+0x60],edi        ; ← слот arg2 перезаписан смещением игрока
4928eb  mov eax,[edi+0x81c2d4]    ; слот оружия +0x3294
492b2e  mov eax,[esp+0x60]; mov eax,[eax+0x81c360]  ; экипировка +0x3320
492b9a  то же для типа патронов (число экипировки)
492cb5  то же для копирования иконки
492d2e  test [eax+0x81c368],1<<idx                  ; маска +0x3328
```

Проверка согласованности: все чтения этой формы дают ровно те смещения,
которые уже описаны в `docs/PLAYER_FIELDS.md` и `docs/HUD_AUDIT.md`:

| адрес | инструкция | `const − 0x819040` |
|---|---|---|
| `0x4926d6` | `fild [eax+0x81c288]` (броня) | `+0x3248` |
| `0x4928eb` | `mov eax,[edi+0x81c2d4]` (оружие) | `+0x3294` |
| `0x492b32` | `mov eax,[eax+0x81c360]` (экипировка) | **`+0x3320`** |
| `0x492d2e` | `test [eax+0x81c368]` (маска) | **`+0x3328`** |
| `0x492efc` | `test BYTE [eax+0x81c240],2` (форсаж) | `+0x3200` |
| `0x492f17` | `fld QWORD [eax+0x81bf88]` (тяга) | `+0x2F48` |
| `0x492ab9` | `fld QWORD [edx+0x81bfe8]` (заряд) | `+0x2FA8` |

Сдвига на `0x140` нет: ранняя рабочая запись «`pitch + 0x81c360` = `0x81c4a0`
= `+0x3460`» была ошибкой чтения (регистр `[esp+0x60]` принят за pitch).
`0x81c4a0` (`+0x3460`) — другое поле, «текущий выбранный id» панели
`WEAPON`/`AMMO` из `docs/FILM.md` §9.1; к иконке экипировки оно не относится.

Замечание: `0x492b40` (`cmp eax,[0x819028]`) проверяет индекс экипировки по
**счётчику оружия**, а не по 12 — похоже на переиспользование/исходную ошибку.
На иконку это не влияет: у копии своя граница `cmp eax,0xc` (`0x492cc3`).

Смысл поля: `docs/PLAYER_FIELDS.md` помечает `+0x3320` как «`fire_anim`,
гипотеза» (`0x445fd6`), а HUD использует его как номер экипировки 0..11.
Соседний `+0x3328` там же — `equipment_active_mask` (**доказано**: `0x47aad1`
снимает бит при снятии предмета), и подсветка HUD читает именно эту маску.
Пара «номер + маска активного» согласована, поэтому для HUD `+0x3320` — номер
экипировки; вопрос о «`fire_anim`» вынесен в §7, п. 2.

## 3. Модель «квада»: это две разные вещи

**В коде панельного слоя (2D)** иконки — не 3D-квады, а построчная копия
24×24 в буфер кадра:

| | оружие | экипировка |
|---|---|---|
| источник | `0x80fc78 + slot*0x2a8` = запись+`0x278` | `0x683ff8 + idx*0x240` |
| направление строк | **вверх**: `sub eax,0x18` (`0x49295b`), первая строка источника = последняя строка растра | **вниз**: `add eax,0x18` (`0x492cf5`) |
| приёмник | `buf + pitch*0xAA + 0x17` = **(23,170)** | `buf + pitch*0xAA + 0xC9` = **(201,170)** |
| шаг по строке | `(pitch>>2)*4` (`0x492949`) | то же (`0x492ce1`) |
| строк | `0x18` = 24 (`0x492951`) | `0x18` (`0x492cd9`) |
| ключ прозрачности | нет | нет |
| после | — | подсветка, если бит `1<<idx` в маске |

Итог по ориентации: растр в памяти лежит **снизу вверх** (как в BMP), поэтому
обратный проход даёт нормальную картинку (оружие), а прямой — зеркальную по
вертикали (экипировка). Кадр это подтверждает (см. §4 и `--compare`).

**В кадре** иконки стоят в `(23,162)` и `(201,162..163)` и совпадают с теми же
ассетами: оружие — `WICON1` в нормальной ориентации, экипировка — `EQUIP0` в
зеркальной (что побайтово равно `EQUIP12`). Разница по `y` с кодом — **−8 px**
(оружие) и −7 px (экипировка). Объяснение — §7, п. 1.

Матрицы/UV/перспективы в этом слое нет: масштаб 1:1, поворота нет. Тот факт,
что в кадре иконки выглядят «объёмнее» (по `docs/HUD_AUDIT.md` §2.4 полоса
кокпита — 3D), относится к другому слою (§7, п. 1).

## 4. Сверка с кадром `win2`

`python3 tools/re/hud_icons.py --compare` (кадр приводится к 320×200 тем же
блочным усреднением, что в `hud_audit.downscale`; метрика — Pearson по
яркости, оба направления строк):

```
frame: out/oracle/win2.png (weapon 'MACHINE GUN', equipment 0)
  weapon    WICON1   ncc=0.888 rect=[23, 162, 24, 24] top-down  (code [23, 170], d=+0,-8)
             next: WCON32 0.765 (top-down), EQUIP8 0.419 (bottom-up)
  equipment equip0   ncc=0.955 rect=[201, 163, 24, 24] bottom-up (code [201, 170], d=+0,-7)
             next: EQUIP12 0.955 (top-down), WCON11 0.848 (top-down)
```

Читать так:

* **`WICON1` — доказанная иконка `MACHINE GUN`** в кадре: NCC 0.888 при
  масштабе 1:1 и без сдвига по `x`; следующий кандидат (`WCON32`) — 0.765, это
  просто похожая «полосатая» картинка.
* **`EQUIP0` — доказанная иконка индекса 0** (`HEADLIGHTS`): NCC 0.955, причём
  именно в зеркальной ориентации, ровно как предсказывает прямой проход копии.
  `EQUIP12` даёт тот же 0.955, потому что это то же изображение (см. §2.2).
* Раньше в `docs/HUD_COMPOSE.md` §2 стояли «`WICON1` / `WICON7`»: для
  экипировки это **неверно** — `WICON7` это иконка `FLAMETHROWER`. Правильно:
  оружие — из записи `DEFINE_WEAPONS`, экипировка — `equip<idx>`.

## 5. Компас

Кадр `win2`: лента в `x 79..129`, `y 2..15`; чёрный фон, зелёные риски и
буквы. Ширина окна — **51 px**, видимая часть — `y 2..15` (14 строк).

Измерено (`--compass`, три кадра с известным `yaw` из `win*.json`):

| кадр | `yaw`, рад | длинные риски (x) | буквы (x) |
|---|---:|---|---|
| `win1` | 4.8201 | 100, 126 | 100, 125.5 |
| `win2` | 6.0146 | 81, 109 | 81, 108.5 |
| `win3` | 1.8584 | 97, 125 | 96, 124.5 |

Структура сверху вниз: короткие риски — строки `2..4` (шаг ~6..9 px, у краёв
окна гуще), длинные риски — строки `5..8` (2 px шириной, доходят до строки 7),
под каждой длинной риской — буква 5×6 px в строках `9..14`.

**Формула (подгонка по 6 рискам, rms 1.08 px):**

```
x(bearing) = 102.62 + 0.2940 * (bearing_deg - yaw_deg)      ; px
риски       через 90°  -> период 26.46 px, 360° = 105.8 px
окно        79..129    -> видно ~173.5°
yaw_deg     = degrees(player[+0x0028])
```

Подстановка: `win2` (`yaw` 344.61°): bearing 270° → 80.7 (измерено 81),
360° → 107.2 (109); `win1` (276.17°): 270° → 100.8 (100), 360° → 127.3 (126);
`win3` (106.48°): 90° → 97.8 (97), 180° → 124.3 (125). Знак: при росте `yaw`
лента едет **влево**.

**Адреса:** `yaw` — `player+0x0028` = `0x819068` (`docs/PLAYER_FIELDS.md` §4,
`fld [0x819068]` в `0x444118`). **Адрес отрисовки компаса — не найден.**
Что проверено и исключено:

* это не `0x47faf0`: во всём exe нет вызова с `y` в 0..20 и `x` в 60..140
  (перебор всех 246 площадок вызова);
* этого нет в панельной функции `0x4926a0` и в вызывающем `0x491a70`
  (единственная текстовая отрисовка вне панели — сетевой оверлей `0x491650`);
* в `FRONTEND/BMP.IDX` нет ассета ленты (`docs/HUD_AUDIT.md` §3.5);
* строк `N/E/S/W`/`COMPASS` в exe нет (поиск по всем строкам), поэтому буквы —
  либо глифы шрифта, либо растры в `.data`.

Гипотеза: лента рисуется тем же 3D-слоем кокпита, что и иконки (§7, п. 1), и
потому не находится среди 2D-отрисовок; тогда «буквы» — не текст, а часть
3D-модели/растра. Масштаб и фаза выше измерены по кадрам и от этой гипотезы не
зависят.

## 6. Источники чисел

### 6.1. Доказано (адрес чтения → формула → куда рисуется)

| элемент | адрес чтения | формула | отрисовка |
|---|---|---|---|
| урон `%` | `0x4926d6` | `100 - 100*[player+0x3248]/[player+0x3244]` (сотые) | `0x4927b5`, шрифт 9/10, `%` в `(166,190)` |
| патроны | `0x4929cd` | `[player+0x329c + 4*type] / [0x818980 + 0x38*type]`, `type = weapon[+0x3c]` | `0x492a80`, шрифт 10, `x = 72/64/56/48/40` по числу цифр (10/100/1000/10000), `y = 165` |
| число экипировки | `0x492bd0` | `[player+0x329c + 4*type] / [0x818980 + 0x38*type]`, где `type = [0x814c80 + idx*0x40]`, `idx = [player+0x3320]` (поле `+0x20` записи `DEFINE_EQUIPMENT`, `-1` = нет типа); при `type < 0` число не рисуется | `0x492be6` (`%d`) → `0x492c18`, шрифт 6, `x = 246/238/230/222/214`, `y = 175` |
| тяга | `0x492ef8` | `flags(+0x3200) & 2` → полная, иначе `ftol(engine_power(+0x2F48)*k)`, кламп 53 | заливка `0xf3`, `0x492f40` |
| заряд (полосы гексагона) | `0x492ab5` | `[player+0x2fa8] * k` | заливка `0xf3`, две строки от `(50,182)` |
| `%ld` при `[0x6e89c0] != 0` | `0x4927e0` | `[player+0x332c]` | `(261,172)`, шрифт 5; ветка включается только при ненулевом флаге `0x6e89c0` |

То есть «число экипировки» — это **остаток боеприпаса того типа, который
потребляет экипировка** (`MINES`, `POWER CELLS`…), а не отдельный счётчик: у
`HEADLIGHTS` типа боеприпаса нет (`-1`), поэтому в кадре `win2` на месте числа
стоит `0`, нарисованный другой веткой/слоем.

### 6.2. `KILL` — источник **не найден**

* Подпись доказана: `0x49289f`, строка `0x4be5e0`, `(52,186)`, шрифт 6.
* Числа рядом с подписью в этой функции **нет**: после `0x49289f` код сразу
  переходит к `DAMAGE` (`0x4928ab`), а полный перебор всех 246 площадок
  `call 0x47faf0` в exe не даёт ни одного вызова в прямоугольнике
  `x 60..90, y 165..200` (кроме отладочного оверлея `0x483d87`, `(67,170)`).
* В `docs/PLAYER_FIELDS.md` поля счётчика убийств нет; в кадре значение `0`,
  поэтому даже направление поиска по значению не проверить.
* Кандидат-гипотеза: соседние поля игрока (`+0x3320` — номер экипировки,
  `+0x3460` = `0x81c4a0` — «выбранный id» панели `WEAPON`/`AMMO`,
  `docs/FILM.md` §9.1) либо глобал матча; проверять трассировкой записи при
  убийстве.

Вывод для `hud_compose_ref.py`: `kills` остаётся параметром состояния
(`DEFAULT_STATE["kills"]`), переключать его на поле игрока пока не на что.

## 7. Что осталось гипотезой

1. **Почему иконки в кадре на 7–8 px выше кода.** 2D-слой кладёт их в
   `(23,170)`/`(201,170)`; в кадре они в `(23,162)`/`(201,162..163)`, при этом
   текстовые координаты совпадают с кодом. Правдоподобно: полоса кокпита
   рисуется 3D-проходом (`docs/HUD_AUDIT.md` §2.4: 2D-блит панели
   опровергнут, полоса зависит от камеры), и видимые иконки — из него, а
   2D-слой под ними. Ветка `0x4926a0` при этом вызывается только когда
   `[0x4bc1c8] == 1` (`0x491f57`), т.е. при конкретном выборе HUD-панели.
   Прямого xref «3D-кокпит → иконка» нет; нужно искать владельца полосы
   (следующий шаг после `0x498820`, куда передаётся колбэк `0x4919f0`).
2. **Смысл `+0x3320`.** HUD читает его как номер экипировки 0..11 и им же
   индексирует имена `DEFINE_EQUIPMENT` и иконки `equip%d`; соседняя маска
   `+0x3328` — доказанный `equipment_active_mask`. Но `docs/PLAYER_FIELDS.md`
   помечает `+0x3320` как `fire_anim` (гипотеза, `0x445fd6`): совместимы ли
   роли (объединение/переиспользование поля) — открыто.
3. **Компас.** Формула и геометрия — измерены; адрес отрисовки, источник
   букв и наличие перспективы (шаг рисок 6..9 px не равномерен) — открыты.
4. **`KILL`.** Не найден (§6.2).
5. **Шрифт видимых цифр.** В кадре `win2` цифры (`1999`, `0`) занимают ~10–11
   строк и скошены, тогда как 2D-слой использует клетки 8×10 (`NUMFONTS`
   шрифт 10). Это ещё один аргумент, что видимый слой — 3D, а не `0x4926a0`.

## 8. Проверки

```sh
python3 tools/re/hud_icons.py --self-test    # 48/48
python3 tools/re/hud_icons.py --icons        # 19 оружий + 13 записей экипировки
python3 tools/re/hud_icons.py --compare      # WICON1 0.888; EQUIP0 0.955
python3 tools/re/hud_icons.py --compass      # окно 51 px; x = 102.62 + 0.2940*(bearing-yaw)
```

`--self-test` (48 проверок, ~2.5 с) покрывает:

* арифметику раскладки: `0x80fc78 = 0x80fa00+0x50+24*23`, имя внутри записи,
  12 слотов экипировки, поля экипировки `0x81c360 = player+0x3320` и
  `0x81c368 = player+0x3328` внутри `player[0]`, и что это не `0x81c4a0`;
* NCC: тождество, инверсия, константа, несовпадение длин, инвариантность к
  усилению;
* разбор тройки `имя/звук/иконка` на синтетическом буфере (и пустом);
* геометрию окна компаса, группировку рисок, подгонку `k`/фазы на
  синтетической ленте (`k = 0.30` восстанавливается), `compass_x` внутри/вне
  окна;
* на поставке: 684 записи, 19 видов, уникальность иконки на вид, все иконки в
  `BMP.IDX` и 24×24, 13 записей экипировки, 12 иконок на месте, атлас 57
  элементов 24×24, `EQUIP12 = зеркало EQUIP0`;
* на кадрах: `WICON1` в `(23,162)` NCC 0.888 (top-down), `EQUIP0` в
  `(201,163)` NCC 0.955 (bottom-up), компас — 6 рисок, `k` в 0.2..0.4,
  rms ≤ 8°.

Границы: инструмент не запускает Ghidra (адреса — из листинга
`tools/re/disrange.py` и точечных выборок `exelib.disasm`), не пишет ни в игру,
ни в кадры; без игры `--icons`/`--compare` сообщают об этом и не падают.
