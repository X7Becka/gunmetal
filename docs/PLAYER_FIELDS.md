# PLAYER_FIELDS — поля рантайм-структуры игрока (`M2.3.1`)

Карта всех полей блока игрока `0x3510` байт: смещение, тип, смысл, чем
доказано, статус. Всё, что здесь есть, снято с трёх независимых источников
(листинг `gundx.exe`, декомпилятор Ghidra, сейвы) и воспроизводится
`tools/re/player_fields.py`.

Смежные документы: `docs/FORMATS.md` §16.15 (блок `9` в сейве, шкалы, оружие),
`docs/PLAYER.md` (спавн, камера, `+0x2F50`), `docs/CAMERA.md` (углы, лимиты,
матрица ориентации), `docs/PLAYER_CPP.md` (коэффициент `k`), `docs/WEAPONS_CPP.md`
(урон и щиты). Здесь они не пересказываются — только ссылки и уточнения.

## 0. Что исправлено относительно прежних документов

| было | на самом деле | доказательство |
|---|---|---|
| «`0x81bd00` — база записи игрока 0» | `0x81bd00 = &player[0] + 0x2cc0` — просто *внутренний* адрес блока 0: он попадает в последние 14 double трейла рыскания (`+0x25b0..+0x2d30`), а не в начало отдельной структуры. База массива — `0x819040`, конец — `0x8338c0` | код сохранения `0x452020` идёт от `&DAT_00819040` шагом `0xd44` dword и останавливается на `0x8338bf`; `0x819040 + 8*0x3510 = 0x8338c0` |
| «`+0x18` — позиция» | позиция — `+0x00/+0x08/+0x10`; `+0x18/+0x20/+0x28` — **углы** (тангаж, крен, рыскание) | `0x4437xx`: в кольцо позиций пишутся `+0x00/+0x08/+0x10`, а `+0x18/+0x20/+0x28` — в три отдельных массива «трейлов»; `FUN_0041e025` строит из них матрицу поворота (три пары cos/sin); `0x444118` `fcos/fsin` от `+0x28` |
| «`+0x2ff8/+0x3078/+0x30f8` — история X/Y/Z» | это **точки крепления навесных частей** в локальной системе корпуса, 16 слотов | `FUN_00456710` (`0x456800`): `iVar3 = (slot + player*0x6a2)*8`, запись в `0x81c038/0x81c0b8/0x81c138`, затем `world = M * local + pos` (`0x456874`) |

## 1. База, шаг, слоты

```
player[i] = 0x819040 + i * 0x3510      i = 0..7
slot 0: 0x819040 .. 0x81c54f
slot 1: 0x81c550 .. 0x81fa5f
...
slot 7: 0x8303b0 .. 0x8338bf
0x8338c0              — первый глобал после массива
```

Шаг виден в декомпиляторе тремя формами (это один и тот же `0x3510`):

| форма | пример |
|---|---|
| байтовый индекс | `*(double *)(&DAT_0081bd90 + iVar19)`, `iVar19 = param_1 * 0x3510` |
| индекс dword (`0xd44`) | `(&DAT_0081c240)[param_1 * 0xd44]` |
| индекс double (`0x6a2`) | `(double)(&DAT_0081bf80)[param_1 * 0x6a2]` |

Дополнительно в `.data` есть ещё две структуры того же размера, которые
сохраняются вместе с игроками (`0x452020`): `0x815440` (шаблон спавна: позиция
точки появления, шкалы) и `0x8338c0` (нулевой блок). Их не надо путать с
массивом игроков.

## 2. Метод

1. **Census по листингу.** `objdump -D -M intel gundx.exe` → все операнды вида
   `[reg + 0x81xxxx]` с адресом в `[0x819040, 0x8338c0)`. Так как этот диапазон
   целиком занят массивом игроков, любой такой операнд адресует поле
   `(addr - 0x819040) % 0x3510` — независимо от того, какой слот и какая
   «якорная» база использовалась в коде. Результат: **255 смещений, 2896
   обращений** (`--census`, приложение A).
2. **Декомпилятор.** `FUN_00443690` (физика, `0x444476`), `FUN_00451c20` /
   `FUN_00452020` (save/load), `FUN_00453b50` (урон), `FUN_00445300` /
   `FUN_004453d0` (оружие), `FUN_0047a980` (создание шасси), `FUN_00456710`
   (навесные части), `FUN_004524d0` (масса), `FUN_00452730` (сброс),
   `FUN_004538d0`, `FUN_00454a20/90`, `FUN_0044fc30`, `FUN_00450f50`,
   `FUN_00451160`, `FUN_00469770`, `FUN_00464400`.
3. **Сейвы** `SAVEGAME/saved*.sbt` (только чтение) — проверка значений,
   шкал, типов и раскладки хвоста.

## 3. Карта блока (все 0x3510 байт разложены)

```
+0x0000  0x0030  поза: позиция (3 double) + углы (3 double)
+0x0030  0x1680  кольцо позиций: 240 записей по 0x18 (x,y,z double)
+0x16b0  0x0780  240 double — трейл тангажа
+0x1e30  0x0780  240 double — трейл крена
+0x25b0  0x0780  240 double — трейл рыскания (внутри него лежит 0x81bd00)
+0x2d30  0x02c8  параметры шасси/подвески, скопированные из записи типа
+0x2ff8  0x0180  точки крепления навесных частей: 3 x 16 double
+0x3178  0x0004  id корпуса (объект игрока)
+0x317c  0x0040  id навесных объектов, 16 x u32
+0x31bc  0x0040  флаги навесных частей, 16 x u32
+0x31fc  0x0004  state_word (см. ниже)
+0x3200  0x0044  флаги, трейл-индекс, состояние, таймеры
+0x3244  0x0020  броня и щиты (сотые)
+0x3264  0x0030  снимок щитов при спавне + прочее
+0x3294  0x0038  оружие: слот, маска, патроны[12]
+0x32cc  0x004c  не используется (нули в сейвах, ссылок нет)
+0x3318  0x000c  таймеры стрельбы
+0x3324  0x001c  оборудование и масса
+0x3340  0x0084  ввод и счётчики действий
+0x33c4  0x001c  отложенное оружие, таймеры, id событий
+0x33e0  0x008c  строки и числа, скопированные из записи шасси
+0x346c  0x0020  массив из 8 id (сброс в -1), смысл не установлен
+0x348c  0x0084  не разобрано (единичные обращения, `0x4549xx`)
```

Раскладка проверена по сейву: `0x2ff8 + 3*0x80 = 0x3178`, `0x317c + 2*0x40 =
0x31fc`, `0x3244 + 0x20 = 0x3264`, `0x329c + 0x30 = 0x32cc` — всё стыкуется без
дыр.

## 4. Поза (`+0x0000`)

| смещение | тип | поле | статус | доказательство |
|---|---|---|---|---|
| `+0x0000` | double | `pos_x` | доказано | `0x452ba7` (спавн), `0x443f1b` (расстояние до объектов), `0x448d31` (камера) |
| `+0x0008` | double | `pos_y` | доказано | `0x452bb4`, `0x4445xx` |
| `+0x0010` | double | `pos_z` | доказано | `0x452bc1`; камера `fadd [0x819050]` (`docs/CAMERA.md`) |
| `+0x0018` | double | `pitch` (тангаж) | доказано | пружина `0x81bde8 → 0x81be08` (`0x4449d5..0x444a55`), кламп `±[0x81be18]`=30°, к `+0x18` прибавляется угол башни в `0x44fc30`, из тройки строится матрица `0x41e025` |
| `+0x0020` | double | `roll` (крен) | доказано | пружина `0x81bdf0 → 0x81be10` (`0x444af8..0x444ba5`), кламп `±[0x81be20]`=20° |
| `+0x0028` | double | `yaw` (рыскание) | доказано | `0x444118` `fld [0x819068]` → `fcos`/`fsin` (`0x444120/0x44412b`) × `[0x81bd78]` — направление движения |

Поля `+0x18/+0x20/+0x28` — **отрендеренные** углы: в физике они
интерполируются к целевым (`+0x2dc8/+0x2dd0`) со скоростью 0.005 рад/тик и
зажимаются лимитами. Сырые углы корпуса живут в блоке динамики (`+0x2da8`,
`+0x2db0`) и в целях пружины.

## 5. Трейлы (240 точек)

| смещение | тип | поле | статус | доказательство |
|---|---|---|---|---|
| `+0x0030` | `double[240][3]` | `trail_pos` | доказано | `0x443784..0x4437b5`: 6 dword из `+0x0..+0x10` в запись `0x18` байт по индексу `+0x3204` |
| `+0x16b0` | `double[240]` | `trail_pitch` | доказано | `0x44379b/0x4437a8` — копия `+0x18` |
| `+0x1e30` | `double[240]` | `trail_roll` | доказано | `0x4437bd..0x4437ca` — копия `+0x20` |
| `+0x25b0` | `double[240]` | `trail_yaw` | доказано | `0x4437df..0x4437ec` — копия `+0x28` |
| `+0x3204` | i32 | `trail_index` | доказано | `0x44376a`; инкремент и сброс при `> 0xef` (`0x4437fc`) |
| `+0x3208` | i32 | `trail_tick` | доказано | `0x44372c`: точка пишется каждые 22 тика (`0x16`) |

Трейл — это «след» машины: кольцо позиций плюс три SoA-массива углов, все по
240 записей (0xf0). Индекс общий, поэтому три массива углов синхронны кольцу.

> ⚠️ Не путать с `+0x2ff8/+0x3078/+0x30f8` — это не история, а точки крепления
> (§9).

## 6. Шасси: что и откуда копируется

`FUN_0047a980(player, type, shields*, weapons, equipment, ...)` создаёт шасси:
берёт запись типа из таблицы `0x7995e0` (шаг `0x1cc`, счётчик `DAT_007941bc`)
и раскладывает её по полям игрока. Это самая надёжная часть карты — каждой
строке соответствует конкретная пара `mov` в `0x47aa00..0x47aea0`.

| поле шасси | → поле игрока | смысл поля игрока | статус |
|---|---|---|---|
| `+0x00` | `+0x2d88` | угловое ускорение рыскания (`0x44392e/0x444225`) | доказано |
| `+0x08` | `+0x2d90` | второй источник углового ускорения (`0x4442a4`) | доказано |
| `+0x10` | `+0x2d98` | предел скорости рыскания (`0x443940`) | доказано |
| `+0x18` | `+0x2d40` | штраф скорости за единицу массы | доказано |
| `+0x20` | `+0x2d30` | базовая скорость (2.0 при неверном типе) | доказано |
| `+0x28` | `+0x2d48` | максимальная скорость | доказано |
| `+0x30..0x44` | `+0x2d70..0x2d84` | bbox min/max, **6 float** | доказано |
| `+0x48` | `+0x2f60` | порог урона | гипотеза |
| `+0x50` | `+0x2f68` | множитель урона | гипотеза |
| `+0x58` | `+0x2f70` | второй множитель | гипотеза |
| `+0x60` | `+0x2f78` | коэффициент затухания `k` | доказано |
| `+0x64..0x7c` | `+0x2f80` | 4 double, потребителя нет | неизвестно |
| `+0x40` | `+0x2f50` | высота глаза (10.0 в saved0) | доказано |
| `+0x148` | `+0x3338` | лимит массы (500) | доказано |
| `+0x168` | `+0x3468` | цена шасси (10000) | доказано |
| `+0x16c` | `+0x33e4` | строка имени шасси | доказано |
| `+0x17c` | `+0x33e0` | id иконки (28) | доказано |
| `+0x190` | `+0x33f8` | число (8) | доказано |
| `+0x194/0x198` | `+0x340c/0x3410` | числа (-30062, 901010) | доказано |

| `+0x1b8` | `+0x3424` | число (100) | доказано |
| `+0x1c0` | `+0x3438` | число (162) | доказано |

Внутри игрока первые `0x18` двойных слов блока (`+0x2d88..+0x2d9c`) —
«физические» параметры: ускорения и клампы; `+0x2da0..+0x2fe0` — уже
*состояние* пружин и столкновений (см. §7), которое сбрасывается в `0x4527e0`.


## 9. Навесные части (16 слотов)

`FUN_00456710` (`0x456800`) — единственная точка создания: на вход слот, тип,
локальные координаты, флаги.

| смещение | тип | поле | статус | доказательство |
|---|---|---|---|---|
| `+0x3178` | u32 | `body_object_id` | доказано | `0x453b50` (`== 0 → выход`), `0x4277cd` даёт объект, `0x454a20` |
| `+0x317c` | `u32[16]` | `attach_object_id` | доказано | `0x454a5b`, сериализация `0x4520b1` |
| `+0x31bc` | `u32[16]` | `attach_flags` | доказано | `0x456855` (bit0/b1/b2; bit2 — четверть размера) |
| `+0x2ff8` | `double[16]` | `attach_local_x` | доказано | `0x45683b`, `iVar3=(slot+player*0x6a2)*8` |
| `+0x3078` | `double[16]` | `attach_local_y` | доказано | `0x456845` |
| `+0x30f8` | `double[16]` | `attach_local_z` | доказано | `0x45684f` |

Мировая позиция части: `world = M(корпус) * local + pos` — ровно этот код в
`0x456874..0x4568e6` (три `fld`/`fmul` по строкам матрицы).

## 15. Сверка с сейвами (`--verify-saves`)

Реальные сейвы (`saved0`, `saved1`, `LEVEL0`) — только чтение:

```
saved0: поза (1116.17, 798.21, 48.00), углы (0.000, 0.000, 5.074)
        броня 10000/10000, щиты 8000 ×4, состояние 1, тип шасси 16,
        трейл 194/20, слот оружия 0, навесных 0, масса 1.000/500, flags 0x10400
saved1: поза (1156.36, 797.28, 48.00), углы (0.000, 0.000, 4.747)
        слот оружия 1, трейл 130/8 — остальное совпадает
```

Раскладка хвоста блока игрока (снята с сейвов и совпала с `0x452020`):

```
[09] [01] [0x3510 struct]        слот 0
     [00] × 7                    слоты 1..7 (в одиночной игре пусты)
     [0x50]  имя уровня ("LEVEL0")
     [0x3510] шаблон спавна (0x815440): поза (24, -208, 48), шкалы 100/100/80
     [0x50]  нули
     [0x3510] нулевой блок (0x8338c0)
     [ff]    терминатор
```

`7 + 0x50 + 0x3510 + 0x50 + 0x3510 + 1 = 27336` — ровно столько байт остаётся
после структуры, что и служит надёжным якорем для поиска блока (§ `find_player`
в инструменте).

Инварианты, которые проверяет `--verify-saves` (провал → exit 2):

* шкалы — целые сотые: `0 < armor_max ≤ 10^6`, `0 ≤ armor ≤ armor_max`,
  `0 ≤ shields[i] ≤ shield_max`;
* позиция конечна, `|x|,|y| ≤ 10^6`, `|z| ≤ 10^5`;
* углы: `|pitch| ≤ 30°`, `|roll| ≤ 20°` (это лимиты `+0x2dd8/+0x2de0`);
* `trail_index ∈ [0,240)`, `trail_tick ∈ [0,22]`;
* `action_state ∈ [0,7]`, тип шасси в разумном диапазоне;
* масса `> 0`, лимит массы `> 0`;
* у навесной части без id не бывает флагов; неизвестные биты флагов — только
  предупреждение;
* 8 слотов: `present` слотов 1..7 = 0 (или валидная структура), хвост 27336
  байт, терминатор `0xff`, шаблон спавна проходит те же проверки.

## 17. Что осталось

1. `+0x348c..+0x3510` — единичные обращения в `0x4549xx` с шагом `0x20`;
   похоже на массив из 4 записей, но выходит за границу блока при наивной
   экстраполяции — нужен разбор `FUN_004549xx`. (Смещения «от `0x81bd00`»
   в старых записях сюда не относятся: `0x81bd00` — это хвост `trail_yaw`,
   пересчитывать на `0x819040`.)
3. `+0x31fc` (`state_word`) — непустое в сейве (`0x3C9F2F2D`), обнуляется для
   пустого слота; кандидат — аккумулятор времени/множитель.
4. Точные границы строк `+0x343c/+0x3450` и смысл `+0x3460` (запрошенный тип
   против текущего) — нужен дамп записи шасси из `.sbt` уровня
   (`DEFINE_PLAYER_TYPES`, см. `tools/re/chassis_models.py`).
5. Группа `+0x2e10..+0x2e50` (прицеливание башни) — читается, но без
   декомпиляции `0x451160` целиком не названа.
6. Многопользовательский режим: в доступных сейвах занят только слот 0;
   инварианты для слотов 1..7 проверены структурно (7 нулевых флагов), не
   данными.
7. `+0x3228..+0x3238` (флаги рендера/вспышек) — гипотезы, нужен разбор HUD.
