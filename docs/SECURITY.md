# Границы доверия и устойчивость к битым файлам

* **Дата:** 2026-10-20.
* **Область:** Python-тулкит `gm/`, CLI `gm.py`; C++-читатели проверяются
  отдельно (golden-паритет в CTest).
* **Модель угроз:** файлы игры и всё, что пользователь подсовывает командам,
  считаются **недоверенными**. Мы не запускаем код из данных (VM только
  декодируется, x86-эмулятор — отдельный исследовательский инструмент), но
  парсер не должен падать, зависать, читать за границей буфера или молча
  перезаписывать пользовательские файлы.

## 1. Что проверяется до чтения/записи

| Формат | Проверки | Константы (`gm/…`) |
|---|---|---|
| BIGFILE `.idx/.dat` | magic + длина заголовка; `count` ≤ 1 000 000; таблица целиком в файле; смещения не убывают и не выходят за размер `.DAT`; размер записи ≥ 0; `read()` читает ровно заявленный диапазон и требует полного чтения | `bigfile.MAX_ENTRIES` |
| `.sbm` | заголовок 12 Б; `log2(w), log2(h) ≤ 12`; число мипов ≤ 13; тело содержит всю цепочку мипов; «лишние» байты сохраняются как `extra` | — |
| `.sbc` | magic; заголовок; каждая запись проверяется на попадание в файл до выделения пикселей | — |
| `.sbw` | каждая таблица/сектор/объект/полигон проверяется на границы до `struct.unpack`; счётчики ≤ 65 536; ошибки `struct.error`/`UnicodeDecodeError` нормализуются в `ValueError` с контекстом | `sbw.MAX_TABLE`, `MAX_OBJECTS` |
| `.sbt` | magic, версия 0; `Reader` не выходит за буфер; у каждого типа записи свой предел count (0xC8…); неизвестный/неподдерживаемый тип — ошибка | `sbt.py` |
| `.sob` | ≥ 2 чисел; `0 ≤ vertices ≤ 200 000`, `0 ≤ faces ≤ 5 000`; список вершин и минимальный размер потока проверяются до рекурсии; `walk()` не может уйти в бесконечную рекурсию (memo) | `sob.MAX_VERTS`, `MAX_FACES` |
| `.sbv` | контейнер: magic, `1 ≤ width ≤ 320`, `1 ≤ height ≤ 1024`, `count ≤ 200 000`, таблица целая, end-смещения не убывают и не выходят за EOF; кодек: `width ≥ 8`, чётная, `height` кратен 16; запись в plane-буфер только внутри буфера; битовый поток с жёстким лимитом переполнения | `sbv.MAX_WIDTH/HEIGHT/FRAMES`, C++ `kMaxWidth/kMaxHeight/kMaxFrames` |
| `.sou` | контейнер: magic, длина payload сверяется с остатком файла (SOU0/1), `units*4` (SOU2); WAV-заголовок строится только из проверенных полей | — |
| `.cfg` | контейнер ровно 0x2000, magic/версия, поля только в 0x190..0x8AB; `CONTROLS.CFG` — opaque | `config.py` |
| `.sog/.soa/.soe/.sml/.sme/.sub/…` | чтение по фиксированным структурам и NUL-строкам; ошибки — `ValueError` | — |

Общий принцип: **сначала границы, потом выделение памяти и циклы**. Счётчики,
которые нельзя проверить по размеру файла, ограничены константой; если формат
легально может быть больше — константа поднята с запасом и описана здесь.

## 2. Политика перезаписи

* Любая команда, пишущая **файл**, отказывается перезаписывать существующий
  путь без `--force` (`gm.py: _wopen`). Это относится к `extract`, `pack`,
  `set`, `sbm`, `textures`, `sprites`, `sounds`, `sbv`, `sbw`, `sbt`, `save
  --out` и т. д.
* `--inplace` у `save` — **явное** согласие: файл перезаписывается только по
  этому флагу (и `--out` с `--inplace` несовместимы).
* Имена записей BIGFILE санитизируются в `[A-Za-z0-9_-]` (`bigfile.safe_name`):
  сконструированный `../../X` не может выйти за каталог распаковки.
* `pack` пишет `.DAT` и `.IDX` во временные файлы и переименовывает оба только
  после успешной записи, чтобы не оставить новую пару с половиной данных.
* `extract` делает предварительную проверку всех целевых имён: при конфликте
  не пишется вообще ничего (нет частичного результата). Остальные пакетные
  команды проверяют каждый файл перед записью; уже созданные новые файлы при
  ошибке остаются — это не потеря данных, но и не транзакция.
* Запись атомарна: CLI пишет во временный файл рядом и делает `os.replace`
  только после успешного завершения блока. Ошибка/исключение удаляет temp —
  старый файл и каталог не остаются с «половиной» нового.
* `regress.py` — единственный потребитель, который передаёт `--force`
  осознанно (каталог `--out` принадлежит тесту и должен переиспользоваться).

## 3. Изоляция ошибок

* Парсеры бросают `ValueError` (или `FileNotFoundError`/`OSError` для
  ввода-вывода). CLI ловит `ValueError`, `OSError`, `struct.error` и печатает
  одну строку `gm.py: …`, возвращая код 1 — без traceback.
* Пакетные команды (`sbw`, `sbt`, `sbc`, `sob`, …) обрабатывают файлы
  независимо: один битый файл увеличивает `failed`, остальные продолжают
  обрабатываться, итоговый код 1.
* Команды не делят глобальное состояние между файлами; ошибка в одном формате
  не влияет на выходные данные другого (каждый файл пишется отдельно).
* В C++ все читатели возвращают `optional`/`bool` + `error`; исключения не
  используются как штатный путь.

## 4. Фаззинг и регрессия

`tools/fuzz_formats.py` — матрица «пустой/обрезанный/мутированный/extreme
header» для BIGFILE, `.sbv` (включая декодирование кадра), `.sbw`, `.sbt`,
`.sbm`, `.sbc`, `.sof/.fdx`, `.soo`, `.soe`, `.soa` и `SOU1`:

```bash
python3 tools/fuzz_formats.py --quick      # 545 кейсов, <2 с
python3 tools/fuzz_formats.py              # 1184 кейса, ~2 с
python3 tools/fuzz_formats.py --game … --timeout 2
```

Каждый кейс ограничен по времени (`SIGALRM`), а `MemoryError`/`RecursionError`
считаются провалом. Ожидаемый результат — `0 failure(s)`: любой исключённый
случай либо штатно отвергнут, либо успешно разобран.

C++-читатели покрыты отдельной in-process матрицей `gm_fuzz_tests`
(`engine/tests/test_fuzz.cpp`, см. `docs/FUZZ_CPP.md`): 4 396 кейсов в `--quick`
и 10 399 в `--full`; битые `.idx/.dat`, `.sbv` (включая декодирование кадра),
`.sbw`, `.sbt`, `.sbm`, `.sbc`. Она нашла и зафиксировала четыре реальных
бага: вечный цикл SBV при `width 8..15`/`height 16`, signed overflow в
`base_grid`, отрицательный сдвиг в `.sbm`, гигантский `reserve` в `.sbw`.

```bash
export PATH=$HOME/tools/cmake-4.4.4-linux-x86_64/bin:$HOME/tools/bin:$PATH
cmake --build build/sandbox -j
ctest --test-dir build/sandbox -R fuzz --output-on-failure
```

`regress.py` содержит шесть проверок границ доверия плюс паритет SOU1/SOU2, конфиги, музыку, фильмы, спавн и рендер (111/111 в быстром прогоне):
смещение за EOF в `.idx`, обрезанный `.sbw`, невозможная высота `.sbv`,
отказ от перезаписи при повторном `extract`, быстрый фазз-прогон.

## 5. Остаточные риски (осознанно приняты)

1. **Размер входного файла не ограничен.** Парсеры читают файл целиком
   (`parse_file`, `open(...).read()`); файл в несколько гигабайт займёт столько
   же памяти. Это свойство локального RE-инструмента: пользователь сам выбирает
   вход. Для автоматической обработки недоверенных каталогов запускайте с
   `ulimit -v`/контейнером.
2. **CPU-стоимость пропорциональна данным.** `.sbv` декодирует каждый кадр
   (320×160), `.sob` обходит все полигоны; ограничения сверху не дают
   квадратичных взрывов от заголовка, но честный большой файл будет считаться
   долго.
3. **Аудиокодеки.** SOU1 декодируется в Python (`gm/sou1.py`, 983/983) и
   C++ (`sou1_full`, 983/983); SOU2 — в C++ и Python (3092/3092). Лимит SOU2 — 20 000 000
   кадров на запись; SOU1 проверяет выход `level` за кривую дельт. Ошибки
   формата остаются ошибками формата, а не границей доверия.
4. **Фазз-покрытие неполное.** Python-матрица не покрывает `.soo/.sof/.sou/
   .sml/.soe/.sog`, C++ — `.sou/.sob/BMP/PNG` и VM/рендер. Golden-тесты и
   ручные лимиты (`BigFile::read`, SBW/SBT/SBV) остаются второй линией.
5. **Нет CI и sandbox.** `regress.py`/CTest — локальные; для «совсем
   недоверенных» файлов нужен внешний sandbox (seccomp/контейнер), которого в
   проекте нет.
6. **Не транзакционно.** Пакетная запись в каталог может оставить уже
   созданные новые файлы при ошибке на середине; существующие файлы при этом
   не перезаписываются.

## 6. Быстрая проверка

```bash
export PATH=$HOME/tools/cmake-4.4.4-linux-x86_64/bin:$HOME/tools/bin:$PATH
python3 tools/fuzz_formats.py
python3 regress.py                 # 111/111, включая trust-проверки
ctest --test-dir build/release -L quick
ctest --test-dir build/release -R fuzz
```
