# Фон кадра и «небо»: что рисует движок за геометрией (M4.1.6)

Что здесь: разбор того, чем в `gundx.exe` v1.36 заполняется кадр **до/вместо**
геометрии. Инструмент — `tools/re/sky.py` (`--json`, `--self-test`,
`--level`, `--game`), только чтение (exe + `.sbw`/`.sbt` через `gm/`, Ghidra не
используется). Выводы ниже проверяются его `--self-test` (43 проверки:
синтетика + утверждения по байтам exe + детерминизм).

Короткая версия: **цветовой очистки кадра в игре нет вообще**. Единственный
`grBufferClear` чистит только глубину (и альфу), а «небо» — это обычные
текстурированные полигоны с текстурами `SKY1..SKY5` из самого уровня. Поэтому
вертикальный градиент `BG_TOP`/`BG_BOTTOM` в `gm/render.py` — не упрощение
движка, а выдумка вьювера: в оригинале на его месте либо геометрия, либо
(в кадре без геометрии) содержимое буфера с прошлого кадра.

---

## 0. Коротко

| вопрос | ответ | статус |
|---|---|---|
| очистка цвета кадра | **нет**: единственный `grBufferClear` (`0x418859`) идёт с `grColorMask(0,1)`, т.е. пишет только depth/alpha | доказано |
| аргументы очистки | `color=0x000000`, `alpha=0`, `depth=0xffff`; depth mask = 1, depth mode = 2, depth func = 3 | доказано |
| как часто | раз в кадр: `0x44c230` → `0x443690` → `0x41928e` → `0x4184b6` → clear (gate `ctx+0xec & 0x800`) | доказано |
| чем заполнен фон | геометрией: полигоны с текстурами `SKY1..SKY5` (+ `FOG`/`WATFOG`) из `.sbw` | доказано (данные) |
| скайбокс-объект/флаг | **нет**: ни флага объекта, ни флага полигона, ни отдельного прохода | доказано |
| цвет фона как константа | `0x000000` (аргумент clear), но к цвету он не применяется | доказано |
| туман по глубине | белый `0xffffff`, `grFogMode(2)`, exp-таблица 0.9; линейная: `near = 0.25·far`, `far = ctx+0xc4` | доказано |

| какой из двух рендеров активен в конкретной конфигурации | софт-путь `0x4409b8` и Glide-путь `0x41928e` вызываются из одного кадра; выбор по `[0x5a4700] ∈ {1,2}` для софт-пути | **гипотеза** (на вывод о фоне не влияет) |

## 1. Очистка кадра: depth-only

### 1.1 Таблица точек входа Glide

`0x416920` — загрузчик `glide2x.dll`: строки `_grXxx@N` (`.rdata`,
`0x4a85b4..`) + `GetProcAddress` (`IAT 0x8412f4`) → указатели в BSS-таблицу
`0x4d7448 + 4·i` (33 записи). Сама таблица в файле пустая, поэтому
доказательство — **загрузчик**, а не данные. `sky.py` восстанавливает
соответствие «слот → имя → число аргументов» из кода и строк:

```
0x4d748c  grBufferClear              @12  (3 аргумента)
0x4d7480  grColorMask                @8   (2)
0x4d7450  grDepthMask                @4   (1)
0x4d7468  grConstantColorValue       @4   (1)
0x4d746c  grFogColorValue            @4   (1)
0x4d7470  grFogMode                  @4   (1)
0x4d74bc  guDrawPolygonVertexListWithClip @8
0x4d74c8  guFogGenerateLinear        @12
```

Число аргументов из декорации сверяется с числом `push` перед каждым вызовом —
это ловит ошибку «сдвига аргументов» (см. `--self-test`).

### 1.2 Сама очистка

`grBufferClear` вызывается в целом образе **ровно один раз** — `0x418859`
(внутри `0x4184b6`). Порядок push’ей (cdecl: первый push — последний аргумент):

```
418822  push 0x2                     ; grDepthBufferMode(2)
41882a  push 0x3                     ; grDepthBufferFunction(3)
418832  push 0x1                     ; grDepthMask(TRUE)   — Z-тест включён
418840  push 0,0,0                   ; grTexClampMode
418846  push 0x1 / push 0x0          ; grColorMask(FALSE, TRUE)   <-- RGB не пишем
418850  push 0xffff                  ;                         \
418855  push 0x0                     ;   grBufferClear(color=0,  ;  чистим
418857  push 0x0                     ;                  alpha=0,  ;  depth+alpha
418859  call grBufferClear           ;                  depth=0xffff)
41885f  push 0x1 / push 0x1          ; grColorMask(TRUE, TRUE)    <-- RGB снова пишем
```

То есть `color=0` в вызове есть, но **маска цвета выключена**: цветовой буфер
не очищается ни в первом кадре, ни в последующих. Чистятся только глубина
(`0xffff` = максимум) и альфа (`0`).

Вызов достижим по цепочке (все рёбра проверяются в `--self-test` поиском
`call rel32`):

```
0x44c230  кадр (docs/MAINLOOP.md)
  └─ 0x44d923  call 0x443690           — отрисовка сцены
       └─ 0x4469bc  call 0x41928e      — Glide-проход сцены
            └─ 0x4193a6  call 0x4184b6 — установка состояния Glide
                 └─ 0x418859  grBufferClear
```

Ветвление внутри `0x41928e`: `0x419392: mov edx,[ecx+0xec]; and edx,0x800` —
установка Glide выполняется только при `ctx+0xec & 0x800` (флаг «есть 3dfx»).
Тот же бит проверяет и софт-проход (`0x440a46`).

### 1.3 Единственная другая полноэкранная заливка — фейд

Кроме clear полноэкранную геометрию рисует только функция `0x4188b2` (её
вызывает сам Glide-проход `0x41928e` по флагу `[0x530968] != 0`, `0x41a2cc`):
белый четырёхугольник на весь экран, `grConstantColorValue(0xffffff)`
(`0x418cb8`), `grDepthMask(FALSE)` (`0x4188d0`), `grDepthBufferFunction(7)`
(`0x418d08`), альфа `= ftol(255 · ctx+0xe8)` (`0x418c7c`..`0x418c90`), отрисовка
`guDrawPolygonVertexListWithClip` (`0x418c71`). `ctx+0xe8` пишется из кадра
(`0x446764` → `0x83d288`) — это **переход/вспышка экрана**, а не фон. В
обычном кадре альфа = 0, и заливка невидима.

Итог по «что вообще заливает экран»: `clear` (только Z+alpha) и фейд (alpha=0 в
игре). Всё остальное — геометрия.

## 2. Небо — это геометрия, а не скайбокс

### 2.1 В коде нет ни одного «sky»-пути

* Единственные строки про небо — предупреждения загрузчика:
  `"Warning: sky texture %s found at sector[%ld].object[%ld].poly[%ld]"`
  (`0x4a8e64`, печать `0x4244e6`; условие — «тип текстуры == 2 и сектор != 0»)
  и соседнее `"Warning: transparent texture ..."` (`0x4a8ea8`). Это
  диагностика размещения, ничего не рисует.
* `ADD_SKY_LIGHT_SOURCE` (op 88) — это **источник света** (`gm/scene.py`), к
  фону отношения не имеет.
* Классификатор текстур — байт `[0x76ed44 + 0x10·(id−1)]` (таблица `0x76ed40`,
  2048 записей): nibble `2` = «sky», nibble `1` = «прозрачная». У него 9
  читателей: `0x4244b5`, `0x42451e`, `0x424680` (валидатор загрузчика) и
  `0x4398c0`, `0x43a485`, `0x43d0bb`, `0x43d7d9`, `0x43e7a9`, `0x43f203`
  (трассы/выбор/звук). **Ни одного в кадровых проходах**
  (`0x4409b8..0x4420d4` и `0x41928e..0x41a620`) — проверяется сканом образа.
* Флагов «это небо» в данных нет:
  * `obj+0x17` (из `id & 0x8000`, загрузчик `0x42a419`) — в поставке **0
    объектов** с этим битом;
  * `poly+0x7c & 0x8000` — стоит у **всех** 235 069 полигонов (234 274 не-небо
    + 795 небо), т.е. это общий признак, а не «sky»;
  * `obj+0x70 & 0x20000` — «форс-рендер владельца» (`0x440d74`), к небу не
    относится.

### 2.2 Что есть в данных

«Небо» в поставке — это полигоны, у которых в таблице имён текстур `.sbw`
стоит `SKY1..SKY5` (плюс листы `FOG`/`WATFOG`). Их характерности (36 уровней,
`sky.py --json`):

| свойство | значение |
|---|---|
| всего полигонов | 825 (`SKY*` + `FOG`/`WATFOG`) |
| уровней с ними | 30 из 36 |
| первый полигон объекта (`poly 1`) | 282 шт. — небо часто идёт «шапкой» объекта |
| на «оболочках» (extent ≥ 4000) | 331 шт. (`dm2`, `dm3`, `dm4` — дальние пейзажи) |
| типичный размер | медиана 512 × 608 юнита (квады), максимум 32 000 |
| нормаль | вертикальная (`z≈0`) у 461, вниз у 304, вверх у 30 |
| материал | `none` у 824, `reflective` у 1 |

Т.е. это не «сфера вокруг мира», а **локальные панели**: потолки/стены
открытых секций и отдельные дальние оболочки. Рисуются они тем же циклом
сектор → объект → полигон, что и стены (`0x41a9da`/`0x41acac` читают
`obj+0x6c`, шаг полигона `0x80`), поэтому в `gm/render.py` они уже
отрисовываются — специальный код для них не нужен.

### 2.3 Почему движку можно не чистить цвет

Потому что в первом лице геометрия закрывает кадр целиком. Замер нашим
рендером (level1, 320×200, точка на высоте игрока, взгляд по трём осям):

```
python3 - <<'EOF'
import sys; sys.path.insert(0,'.')
from gm import render as R, sbw
w = sbw.parse_file('/mnt/d/games/Gunmetal 3dfx/level1.sbw'); ms = R.level_meshes(w)
eye = (3599, 6809, -73)                     # первый spawn level1 (gm/scene.py)
for look in ((+1000,0,0), (0,+1000,0), (-1000,0,0)):
    img = R.render(ms, 320, 200, bg=True, pos=eye,
                   look=(eye[0]+look[0], eye[1]+look[1], eye[2]+look[2]))
    print(round(R.coverage(img), 3))         # 1.0 = градиента не видно вообще
EOF
```

Результат: `1.0 / 1.0 / 1.0` — пикселей фона нет. А вот авто-кадр вьювера
(камера снаружи, `--az 35`) даёт `coverage ≈ 0.10`: там 90 % картинки — это
и есть выдуманный градиент. Именно поэтому «фон» вьювера выглядит как
самостоятельный объект, хотя в игре его не видно.

## 3. От чего зависит уровень

Цвет фона **не зависит от уровня** (его нет), но картинка отличается:

1. **набором `SKY*`-текстур** (какая именно — `SKY1..SKY5`);
2. **`SET_LEVEL_FOG_DISTANCE`** (op 98) — значение уходит в `0x80d7f0`
   (`0x45b7cd`), затем в `ctx+0xc4` (`0x44678e`; при 0 → `0x7fffffff`,
   `0x44a127`) и в таблицу тумана `guFogGenerateLinear(table, 0.25·far, far)`
   (`0x41889c`, коэффициент `0x4a2140` = `0.25`);
3. **туманом**: цвет всегда белый `0xffffff` (`0x440a97`), режим 2

## 4. Что рисовать вместо градиента (`gm/render.py --bg`)

Ничего не меняем в этом коммите; рекомендация по фактам выше:

1. **Градиент убрать.** `BG_TOP`/`BG_BOTTOM` — не из движка: там нет ни
   цвета очистки (маска выключена), ни «неба-константы».
2. **Плоский чёрный `#000000`.** Это единственное защитимое значение:
   `grBufferClear(color=0)` — это `0x000000`, и именно такое содержимое у
   незаписанного пикселя 3dfx-буфера в первом кадре. Замена: `bg=True` →
   заливка одним цветом `(0,0,0)` (или `bg=False` и честное «не заливать»,
   если нужен «предыдущий кадр»).
3. **Не выдумывать «цвет неба уровня».** Такой константы не существует; цвет
   даёт сама текстура `SKY*` на полигоне, и вьювер её уже рисует.
4. **Туман — отдельный эффект (`--fog`), не фон.** Он белый и по глубине
   (`near = 0.25·far`), поэтому далёкая геометрия уходит в белое — но это
   именно геометрия, а не заливка. Порядок работ — задача M4.1.6 в `NEXT.md`.
5. **`coverage()` в `gm/render.py`** сравнивает пиксели с тем же градиентом
   (`line 1152`). Если заливку поменять на чёрный, метрику нужно считать от
   чёрного — иначе `coverage` станет «долей не-чёрных пикселей» случайно.
   Правку делать вместе с заменой фона, отдельным коммитом.

Что увидит пользователь: в кадре «от глаз игрока» разницы не будет вообще
(геометрия закрывает 100 % кадра, §2.3), а в авто-обзоре пропадёт синеватый
градиент — вместо него чёрный.

## 5. Что осталось (честно)

1. **Какой проход рисует кадр в конкретной конфигурации.** В exe два
   рендерера: софтверный `0x4409b8` (пишет 8-битный буфер `ctx+0x104` с шагом
   `ctx+0xd4`, затем фог-постобработка через `lighttable`
   `0x44203d..0x44206c`) и Glide-проход `0x41928e`. Оба вызываются из кадра
   `0x443690`; софтверный — при `[0x5a4700] ∈ {1,2}` (`0x448020`). Для вывода
   о фоне это не важно (правила одни), но для «что именно видит игрок»
   различие существенно. Нужен запуск с логом или кадр из игры.
2. **Первый кадр после смены режима.** Цвет не чистится вообще; что лежит в
   back buffer 3dfx на первом кадре — не проверено (нужен реальный захват,
   `docs/ORACLE.md`).
3. **Анимация неба.** У полигонов есть `scroll_u/scroll_v` (`poly+0x5c/0x60`)
   и `anim0..2`. У backdrop-полигонов скролл почти всегда нулевой (822 из 825;
   три исключения: `300`, `64336`, `65236` по U) — единицы измерения и
   потребитель не проверены. Скролл неба скриптом/сектором (`sector+0x16`)
   не доказан.
4. **`underwater`/`WATFOG`.** `level11` использует `WATFOG` (лист тумана под
   водой), отдельной подводной палитры/фильтра в кадровых проходах не
   найдено; подводный эффект не доказан.
5. **`SET_LEVEL_FOG_COLOUR` (op 97).** Команда есть в таблице VM
   (`gm/sbtvm.py`), но кадровый проход ставит **фиксированный белый**
   (`0x440a97`) и цвет из скрипта не читает. Либо команда влияет на что-то
   ещё (софт-путь/меню), либо мёртвая — не проверено.
6. **`grFogMode(2)`** — в Glide 2.x это «туман по таблице на Q»
   (перспективная глубина); имена enum’ов по заголовкам не сверялись, в
   отчёте приводятся только числа.
