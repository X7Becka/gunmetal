# Gunmetal — broad-phase сетка коллизий (`CollideGrid`)

Что здесь: `engine/src/render/collide_grid.{h,cpp}` — равномерная 3D-сетка над
**статическими** треугольниками `CollisionWorld` и обход луча по ней (3D-DDA).
Цель одна: отдать **тот же** `RayHit`, что `CollisionWorld::raycast`, проверив
меньше треугольников. Сетка ничего не меняет в `CollisionWorld`, не копирует
геометрию и не подключена к движку/LOS (см. §4).

Статус: CTest `collide_grid` (label `quick`) зелёный на `level0.sbw` и
`dm1.sbw`; паритет 0 по всем полям, ускорение по числу кандидатов и по времени
подтверждено числами (§2, §3). Изменены только новые
`collide_grid.{h,cpp}`, `engine/tests/test_collide_grid.cpp`, этот документ и
две строки в `engine/CMakeLists.txt` / `engine/tests/CMakeLists.txt`.

## 0. Коротко

| что | значение |
|---|---|
| структура | равномерная сетка по AABB мира, CSR-индекс «ячейка → индексы треугольников» |
| вставка | треугольник попадает во все ячейки своего AABB, раздутого на `1e-6` |
| обход | Amanatides–Woo 3D-DDA, отрезок луча обрезается AABB сетки; луч вне мира не посещает ячеек |
| ранний выход | обход останавливается, когда следующая граница ячейки дальше текущего лучшего `t`; граница ровно на `best` ещё проходится (иначе можно потерять равный `t`) |
| узкая фаза | те же `ray_aabb` / `ray_triangle` / эпсилоны, что в `CollisionWorld::raycast` |
| паритет | **точный (0)**: `t`, `point`, `normal`, `front_face`, `triangle`, `triangle_index`, `sector`, `dynamic` |
| tie-rule | при равном `t` побеждает **наименьший индекс** — ровно тот треугольник, который оставляет перебор по возрастанию индекса |
| фильтры | `CollideFilter` целиком: пол/потолок/стена, `backfaces`, `sectors`, список подавления |
| динамика | динамического набора в сетке нет: при `set_dynamic` запрос уходит в `CollisionWorld::raycast` (верно, без ускорения) |
| ячейка на `level0` | `72.22` (span/128), 261 888 ячеек, 27 611 ссылок, 1.1 МиБ |
| ячейка на `dm1` | `291.62` (span/128), 780 800 ячеек, 68 143 ссылки, 3.3 МиБ |
| кандидатов на луч | `level0` 25.1 из 3162 (0.79 %), `dm1` 66.5 из 11 781 (0.56 %) |
| время, Debug `-O0` | `level0` 3.0–4.0×, `dm1` 2.1–4.0× быстрее `raycast` |
| время, Release | `level0` 1.4–2.8×, `dm1` 2.2–4.3× (шумная машина, см. §3) |

## 1. Устройство

### 1.1. Построение

`build(world, cell_size, error)`:

1. Проверки (текстом в `error`, пустая сетка при отказе): пустой мир,
   `cell_size` не конечный или `<= 0`, нефинитный AABB мира, сетка больше
   потолка `kMaxCells = 2^24` ячеек или `kMaxReferences = 2^25` ссылок.
2. `dims = ceil(span / cell_size)` по каждой оси (минимум 1), начало сетки —
   `world.bounds().lo`. Сетка покрывает AABB мира ровно.
3. Два прохода: (а) посчитать ссылки на ячейку и их сумму, (б) разложить
   `cell_begin_` (CSR) и заполнить `entries_` индексами треугольников. Порядок
   треугольников — порядок `world.triangles()`, поэтому внутри ячейки индексы
   возрастают.
4. Запоминаются `owner_ = world.triangles().data()` и число треугольников —
   дешёвая проверка «мир тот же» (`matches`).

Треугольник вставляется во все ячейки своего AABB, раздутого на
`kBinSlack = 1e-6` мировых единиц. Без этого луч, идущий ровно по плоскости
ячейки, мог бы обойти ячейку, в которой треугольник зарегистрирован только с
одной стороны; `1e-6` на масштабе комнаты (сотни единиц) не добавляет ячеек,
но снимает вопрос «на какой стороне границы считать».

### 1.2. Обход

`walk_cells(origin, d, limit, visit)`:

* луч обрезается AABB сетки тем же slab-тестом (включая случаи `d == 0`),
  поэтому луч, проходящий мимо мира, не посещает ни одной ячейки;
* стартовая ячейка берётся по точке входа, далее классический DDA: для каждой
  оси — шаг `±1`, расстояние до следующей границы `t_next` и шаг `t_delta`;
* посещается ячейка, вызывается `visit(cell)`, затем шаг по оси с минимальным
  `t_next` (при равенстве — `x`, потом `y`; лишняя ячейка безвредна, пропуск —
  нет); выход при выходе за `t_exit` или за `visit`-дистанцию;
* число итераций ограничено `dim.x + dim.y + dim.z + 8`.

`visit` возвращает дистанцию, до которой обход ещё имеет смысл: для
`raycast` — текущий лучший `t`, для `candidates_for_ray` — `limit`. Проверка
`t_next <= reach` включает равенство: ячейка, начинающаяся ровно на `best`,
посещается. Это важно для tie-rule: треугольник с `t == best` может лежать в
следующей ячейке.

### 1.3. Узкая фаза и паритет

Для каждой ячейки перебираются её индексы, треугольник проходит:

1. структурный фильтр (`structural_allows`): подавление `(sector, object)`,
   `filter.allows` (пол/потолок/стена + `sectors`), опциональный
   `backfaces == false`;
2. `ray_aabb(origin, d, triangle.bounds, best)` — тот же slab-тест;
3. `ray_triangle(origin, d, triangle, best)` — та же Möller–Trumbore с теми же
   `1e-12` / `1e-9` / `t >= 1e-9`.

Порядок обхода — вдоль луча, а не по индексам, поэтому tie-rule
сформулирован явно:

```
принять, если  t < best   ИЛИ   (t == best И index < best_index)
```

Перебор `CollisionWorld::raycast` идёт по возрастанию индексов и оставляет
**первый** треугольник при точном равенстве `t`, то есть минимальный индекс.
Правило выше даёт ровно этот треугольник независимо от порядка ячеек.

Ранний выход безопасен: любой треугольник с `t <= best` пересекает свой AABB
на расстоянии `t`, значит его ячейка имеет вход не дальше `best` и будет
посещена. Треугольник может быть проверен дважды (зарегистрирован в нескольких
ячейках) — это не меняет ответ: повторный `t == best` не проходит tie-rule при
том же индексе.

Отчёт собирается теми же строками, что в `CollisionWorld::raycast`
(`point = origin + d * t`, `normal` против луча, `front_face` по
`surface_normal`), поэтому совпадает побитово.

## 2. Паритет: числа

Тест `engine/tests/test_collide_grid.cpp`, seed `0x5eedc0de1234abcd` (печатается
в выводе), 500 лучей на уровень. Половина начал — у центроидов случайных
треугольников (±4), половина — равномерно в AABB мира; направления равномерны
на сфере; `max_t` циклически: `kCollideInfinity`, `0.25·diag`, `0.5·diag`,
`diag`. Так покрыты попадания, промахи, конечные и бесконечные лимиты.

Точность — **0, не 1e-9**. Оба пути вызывают один и тот же код узкой фазы
(`ray_aabb`, `ray_triangle`) с одним и тем же `best`-порядком; расхождение
могло бы появиться только из-за другого набора треугольников или другого
tie-rule, а они исключены конструкцией (§1.3). Тест сравнивает поля `==`,
а `max_distance_delta` печатает как контроль (всегда `0.000e+00`).

Снятые числа (Debug, один прогон):

```

level0: sectors same=1856/1856          (32 луча × 58 секторов)
level0: suppressed(14,16) same=32/32

Все 16 комбинаций четырёх булевых полей `CollideFilter` (`floors`,
`ceilings`, `walls`, `backfaces`) — отдельного флага «objects» в фильтре нет;
ограничение по секторам проверено отдельно, по одному сектору за раз.

Синтетика (§2.1) закрывает края, которых нет в случайной выборке: луч идёт
ровно по двум плоскостям ячеек и попадает в треугольник, лежащий ровно в
третьей; два одинаковых треугольника дают бит-в-бит равный `t` — побеждает
индекс 2 (меньший); `max_t`, равный `t` попадания, принимается, а
`nextafter(t, 0)` — уже промах, одинаково у обоих путей.

### 2.1. Синтетический мир

Пол `z = -100` (`[-100,100]²`) и два **идентичных** треугольника стены в
`x = 0` (`y,z ∈ [-10,10]`), мировые границы `[-100,100]² × [-100,10]`.
При `cell_size = 20` плоскости сетки — `-100 + 20k`, то есть `x = 0`, `y = 0`,
`z = 0`; луч `(-50,0,0) → (1,0,0)` идёт по двум плоскостям и бьёт треугольник
в третьей. Проверяются также наклонный неединичный луч и 200 случайных лучей
при `cell_size = 20` и `5`.

## 3. Ускорение: числа

### 3.1. Кандидаты (детерминированная величина)

`candidates_for_ray` — число **уникальных** треугольников, прошедших
структурный фильтр, на всём отрезке `[0, max_t]` (верхняя оценка того, что
смотрит `raycast`: он останавливается раньше при попадании). Сумма по 500
лучам:

```

dm1:    candidates=33233  full_scan=5890500  (0.56%)  cand/ray=66.5  из 11781

Тест требует `candidates * 10 < full_scan` (не хуже 10 % от полного перебора),
фактически — 0.8 % и 0.6 %.

### 3.3. Время `raycast`: сетка против `CollisionWorld`

Те же 500 лучей, замер `std::chrono::steady_clock` в самом тесте (Debug
`-O0`, каноническая сборка):

```
level0: brute 6.8 ms  grid 1.9 ms  3.53x   hits=239
dm1:    brute 17.8 ms grid 8.5 ms  2.09x   hits=315
```

Разброс по прогонам: `level0` 3.0–4.0×, `dm1` 2.1–4.0× (Debug). Release
(`build/release`, четыре прогона): `level0` 2.66/2.78/2.64/1.35×, `dm1`
2.20/3.66/3.60/4.32×. Абсолютные времена в Release — десятые доли миллисекунды на
500 лучей, поэтому шум планировщика на общей машине иногда съедает разницу;
число кандидатов (§3.1) от нагрузки не зависит.

Важно: сетка сравнивается не с «перебором всех 11 781 треугольника», а с
`CollisionWorld::raycast`, у которого уже есть broad-phase по AABB секторов и
AABB треугольников. То есть выигрыш получен поверх существующего ускорения, а
не вместо него. Против полного перебора кандидатов в 127×/177× меньше.

Тест печатает время и попадания, но не утверждает порог по времени (на
загруженной машине это флак); жёсткое утверждение — только `candidates`.

## 4. Ограничения

* **Только статические треугольники.** Динамический набор
  (`set_dynamic`, движущиеся двери) сетка не индексирует: при
  `dynamic_triangle_count() != 0` `raycast` делегирует
  `CollisionWorld::raycast` — ответ верный, ускорения нет. Тест это фиксирует
  (`dynamic same=32/32`).
* **Мир должен быть тем же.** `matches()` сравнивает указатель
  `triangles().data()` и число треугольников. Совпало — сетка отвечает сама;
  не совпало (мир пересобран, вектор переехал) — снова делегирует. Проверка
  дешёвая, но не криптографическая: `clear()` + `build()` в тот же буфер с тем
  же числом треугольников указатель не меняет. Правило: после изменения мира
  сетку пересобрать.
* **Память.** `4·cells + 4·refs` байт в установившемся виде:
  `level0` ≈ 1.1 МиБ, `dm1` ≈ 3.3 МиБ при `span/128`. Во время `build`
  дополнительно живут `counts` и `cursor` (ещё по `4·cells`), пик ≈ 3×.
  Крупные «полы-плиты» дублируются во все ячейки своего AABB; число ссылок
  видно в `references()`, и на `dm1` это 68 143 при 11 781 треугольнике.
* **Потолки.** `kMaxCells = 2^24` ячеек и `kMaxReferences = 2^25` ссылок:
  слишком мелкая ячейка — отказ с текстом, а не OOM. `cell_size = 1e-7` на
  реальном уровне отвергается (проверено тестом).
* **Нет динамической ребалансировки.** Движущаяся геометрия — либо пересборка,
  либо отдельная сетка на позу. Это осознанно: задача — ускорить статический
  мир, не менять `CollisionWorld`.
* **Стоимость построения** — `O(треугольники + ссылки)`, один поток. Для
  `dm1` это доли миллисекунды… единицы миллисекунд (входит в тест), но
  `build` не бесплатен; строить один раз на уровень.
* **Нет `sphere_cast`/`floor_at`/`overlap_aabb`.** Ускорен только `raycast`;
  `floor_at` можно выразить через `CollideGrid::raycast`, но в API это не
  добавлено.
* **thread-local scratch.** `raycast`/`candidates_for_ray` держат буфер
  кандидатов в `thread_local` (растёт при первом вызове, потом не аллоцирует).
  Это память на поток; на запросы разных потоков друг на друга не влияет,
  объект сетки после `build` неизменяем.
* **Не подключено.** `CollisionWorld`, `game/line_of_sight.*`, `main.cpp`,
  `config.*` не тронуты; `CollideGrid` — самостоятельный слой, который вызывают
  явно. Паритет с LOS поэтому обеспечивается автоматически: LOS зовёт
  `world.raycast`, а сетка даёт тот же `RayHit` на том же мире.
* **Паритет — про этот мир и этот код.** Если `CollisionWorld::raycast`
  изменит эпсилоны/порядок/ tie-rule, сетку нужно править синхронно; тест
  поймает расхождение (он сравнивает с живым `world.raycast`, не с голденами).

## 6. Доказано / гипотеза / осталось

**Доказано (тест, числа выше):**

* паритет `CollideGrid::raycast` с `CollisionWorld::raycast` на 500 лучах
  `level0` и 500 лучах `dm1`: все поля равны, `max_distance_delta == 0`;
* паритет на всех 16 комбинациях фильтра, на каждом секторе по отдельности, со
  списком подавления и при динамическом наборе (делегирование);
* синтетические края: луч по плоскостям ячеек, треугольник на плоскости,
  точный tie → меньший индекс, `t == max_t` принимается, `nextafter` — нет;
* сетка режет узкую фазу до 0.8 % / 0.6 % полного перебора; время `raycast`
  на Debug 2.1–4.0× меньше, на Release 1.4–2.8× (`level0`) и 2.2–4.3×
  (`dm1`) — разброс от нагрузки хоста, см. §3.3;
* отказы `build`: пустой мир, `cell_size` 0/-1/NaN/inf, слишком мелкая сетка;
  `raycast` с NaN/нулевым направлением/`max_t <= 0` — промах, как у
  `CollisionWorld`;
* повторный запрос не меняет состояние сетки (`cells`, `references`,
  кандидаты те же).

**Гипотеза (не измерялось):** выигрыш на реальном кадре движка (там десятки –
сотни `raycast` за тик, часть с динамическими дверями, где сетка делегирует);
поведение при тысячах потоков (thread-local буферы); польза `sphere_cast` от
этой же сетки (её нет).

**Осталось:** подключение к `game/line_of_sight.cpp`/AI/игроку — отдельная
задача основного агента (в этом worktree запрещено править потребителей);
вариант BVH/иерархии для миров с сильно неравномерной плотностью; сетка над
динамическим набором с перестройкой по позе.
