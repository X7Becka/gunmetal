## 1. Раскладка полигона

`.sbw` — один последовательный поток (`gm/sbw.py:1-128`,
`docs/FORMATS.md` §10). Полигон — самодостаточная запись внутри стадии 2
объекта (`docs/FORMATS.md` §10, таблица полей — §10.1):

```
n_polys * {
    u16 texture;  u16 lightmap;  u16 material;  u16 overlay;  u16 f7a;
    u8  brightness;
    u8  n_idx;
    u16 indices[n_idx];
    u8  tail[112];          // кэш кадра + оси UV + uv + хвост
}                           // всего 124 + 2*n_idx байт
```

Смещения в записи (диск) и в 112-байтном хвосте:

| запись | размер | поле | смысл (`docs/FORMATS.md` §10.1) |
|---:|---:|---|---|
| `+0x00` | 2 | `texture` | знаковый: >0 — таблица текстур (1-based), <0 — эффекты, 0 — нет |
| `+0x02` | 2 | `lightmap` | 0 = нет, 1..N — запись sibling-файла `.sbc` |
| `+0x04` | 2 | `material` | 0..5 (none/reflective/translucent/varadd/add/shade) |
| `+0x06` | 2 | `overlay` | индекс оверлея (та же кодировка) |
| `+0x08` | 2 | `f7a` | вспомогательное (0..2) |
| `+0x0A` | 1 | `brightness` | u8, аддитивный свет (SET_POLY_BRIGHTNESS) |
| `+0x0B` | 1 | `n_idx` | число индексов, u8 (в поставке 3..26) |
| `+0x0C` | `2n` | `indices` | индексы вершин **объекта** |
| `tail+0x00` | 2 | `scroll_u` | вес скролла по U (движок читает s16) |
| `tail+0x02` | 2 | `scroll_v` | то же по V |
| `tail+0x04` | 2 | `u_scale` | производное `uv_u_fp >> 7`, но хранится u16 |
| `tail+0x06` | 2 | `v_scale` | то же по V |
| `tail+0x08` | 2 | `uv_u` | текстурная координата U |
| `tail+0x0A` | 2 | `uv_v` | текстурная координата V |
| `tail+0x0C` | 4 | `uv_u_fp` | знаковое смещение проекции U (лайтмап-сэмплер) |
| `tail+0x10` | 4 | `uv_v_fp` | то же по V |
| `tail+0x14` | 12 | `centre` | центр полигона (локальный кадр объекта) |
| `tail+0x20` | 12 | `normal` | авторская нормаль грани (единичная) |
| `tail+0x2C` | 12 | `u_axis` | ось U текстуры |
| `tail+0x38` | 12 | `v_axis` | ось V текстуры |
| `tail+0x44` | 12 | `corner_a` | min AABB вершин относительно `centre` (кэш загрузки, `0x43529f`) |
| `tail+0x50` | 12 | `corner_b` | max AABB |
| `tail+0x5C` | 2+2+2 | `f74`, `f76`, `handle` | вспомогательные/слот-id |
| `tail+0x62` | 4 | `reserved` | 0 |
| `tail+0x66` | 4 | `flags` | 0x8000 «кадр/UV посчитаны», 0x2 прозрачный, 0x4 переключается командой |
| `tail+0x6A` | 2+2+2 | `anim0`, `anim1`, `anim2` | анимируемые s16 |

Абсолютные смещения на примере `level0.sbw`, объект 0
(`--list level0 --object 0 --limit 1` печатает их для любого полигона):

| что | диск |
|---|---:|
| стадия 2 объекта 0 (`n_verts`/`n_polys`) | `26195` |
| вершины (8 × 12) | `26199 .. 26295` |
| хвост объекта (`radius`..`reserved`) | `26295 .. 26345` |
| полигон 0 (132 Б) | `26345 .. 26477` |
| `texture`/`lightmap`/`material`/`overlay` | `26345 / 26347 / 26349 / 26351` |
| `brightness` / `n_idx` | `26355` / `26356` |
| индексы `(0,2,4,6)` | `26357 .. 26365` |
| `uv` / `normal` / `flags` | `26373` / `26397` / `26467` |

Полигоны идут подряд: `p[k+1].off = p[k].off + 124 + 2*n_idx`; запись
объекта кончается ровно на конце последнего полигона
(`polys_end`). Это проверяет `--roundtrip` (поток полигонов покрывает
`geom_off..polys_end` без дыр и наложений) и self-test.

**Почему правка на месте безопасна.** Все общие структуры (таблицы
текстур/эффектов, заголовки стадий 1, вершины, хвост объекта) лежат
**до** полигонов; в `.sbw` нет таблицы смещений. Полигон
самодостаточен, поэтому замена его байтов не сдвигает ничего. Смена
`n_idx` меняет длину записи и сдвигает поток — это поддержано только под
`--allow-resize` (§4).

## 2. `--list`: что видно

`--list LEVEL [--object N] [--limit N] [--json]` печатает:

* глобальный индекс полигона (порядок файла: сектор → объект → полигон) и
  локальный индекс внутри объекта;
* `n_idx`, индексы вершин и диск-спан записи;
* `texture` (знаковая), `material`, `lightmap`, `overlay`, `brightness`,
  `flags`, `handle`, `f74`, `f76`;
* `normal` — авторская, её длину и признак единичности; **две**
  геометрические нормали: первое треугольное звено веера
  (`cross(b−a, c−a)`, как в C++ и `collide_goldens.py`) и
  area-weighted (Newell) нормаль всего полигона; скалярное произведение
  `normal` с Newell и слово `opposite`/`same`/`skew`;
* `u_axis`/`v_axis` с длинами, `uv` (`uv_u`,`uv_v`), `uv_fp`
  (`uv_u_fp`,`uv_v_fp`, знаковый), `u_scale`/`v_scale` (сырые u16);
* `centre`, `corner_a`, `corner_b`, сырой 112-байтный хвост (hex; в
  `--json` — целиком);
* по каждой вершине полигона — мировая позиция (`origin + basis · local`),
  сколько полигонов **объекта** и **уровня** используют эту позицию и
  сколько **объектов** делят её (точное равенство `f64`-координат).

Уровень `level0` (`--list level0 --object 0 --limit 2`):

```
sharing: 1713 distinct world positions, 431 shared by >1 object
         (max 4 objects / 11 polygons at one position)
  p[    0] obj=    0 local=  0 n_idx= 4 disk=26345+132 indices=(0, 2, 4, 6)
    fields: texture=1 material=0 lightmap=0 overlay=0 brightness=64 flags=0x00008000 handle=0
    normal=(0, 0, -1) |n|=1 geo=(0, 0, 1) newell=(0, 0, 1) dot=-1 (opposite)
    u=(0, -1, 0) |u|=1 v=(-1, 0, 0) |v|=1 uv=(18432, 47104) uv_fp=(-11776, 11776) u_scale=65444 v_scale=92
    raw[112]=00000000a4ff5c00004800b800d2ffff002e000000000000...
    verts: v0 world=(1616, 7752, 176) polys(obj/level)=3/3 objects=1 | ...
```

`u_scale = 65444` — это `0xFFA4`, сырое u16 для `uv_u_fp >> 7 = -92`:
поле производное, но хранится беззнаковым (`u_scale == (uv_u_fp>>7) & 0xFFFF`
в 235 057/235 069 полигонах, `v_scale` — в 235 059/235 069; `--audit`).

По всему корпусу (`--audit`): 298 549 различных мировых позиций, 52 134
из них используются более чем одним объектом (максимум 8 объектов и 24
полигона в одной позиции на уровне).

## 3. `--set`: поля и что зависит от них

```
--set LEVEL --object N --index I --field NAME=VALUE [--field ...] --out FILE
```

`--object N` — глобальный 0-based индекс объекта (как в `--list`),
`--index I` — 0-based индекс полигона **внутри** объекта. Поля:

| поле | значение | проверка / запись |
|---|---|---|
| `texture` | знаковое целое | 0, `1..n_tex` (текстур), `-1..-n_eff` (эффекты) |
| `lightmap` | целое | `0..N` записей sibling `.sbc` (нужен `--sbc` или файл рядом); `level0` — 405 |
| `material` | 0..5 | none/reflective/translucent/varadd/add/shade |
| `overlay` | знаковое целое | та же кодировка, что `texture` |
| `brightness` | 0..255 | u8 |
| `flags` | u32 | только документированные биты `0x8000|0x2|0x4` |
| `normal=x,y,z` | три числа | **нормализуется**; нулевой вектор и `nan/inf` отвергаются |
| `uv=u,v` | два целых 0..65535 | `uv_u`,`uv_v` |
| `u_axis=x,y,z` | три числа | пишется **как есть** (не нормализуется), нулевой и `|c| > 1e4` отвергаются |
| `v_axis=x,y,z` | три числа | то же |
| `indices=i0,i1,...` | 3..255 индексов `0..n_verts-1` | та же длина — на месте; другая — только `--allow-resize` (§4) |

Поля можно повторять (`--field a=1 --field b=2`); применяются к одной
записи, последнее значение поля побеждает. Порядок полей не важен: запись
собирается заново из головы, списка индексов и 112-байтного хвоста
(`build_record`), поэтому `indices` другой длины и `normal` в одной правке
не конфликтуют.

### 3.1 `normal` нормализуется — это следует из данных

`--audit` по всем 36 файлам (235 069 полигонов):

* длина `normal` равна `1 ± 1e-4` у **235 045** полигонов;
* ровно нулевая у **24** — и все 24 являются полигонами нулевой площади
  (первое звено веера вырождено);
* «других» (ненулевых ненормированных) **нет**.

Движок проверяет единичность (`Invalid poly ...`,
`docs/FORMATS.md` §10.1), поэтому `normal=` нормализуется в `double` и
пишется как `f32`; запрос нулевого вектора отвергается текстом и кодом 2
(искусственно создавать вырожденную нормаль инструмент не даёт).

### 3.2 `u_axis`/`v_axis` пишутся как есть

В поставке оси **не всегда единичные**: unit — 181 085 слотов `u` и
179 587 `v` (всего 360 672 из 470 138), ноль — 3 530, остальные —
ненормированные (максимум компонента 8). Нормализация изменила бы
масштаб текстуры, который рендер выводит из этих осей
(`gm/render.py:LevelMesh.uv`), поэтому редактор пишет вектор буквально;
нулевой вектор отвергается (не проецирует текстуру).

### 3.3 Что пересчитывается, а что нет

**Ничего не пересчитывается автоматически.** Инструмент меняет ровно
запрошенные поля; `centre`, `corner_a`/`corner_b`, `uv`/`uv_fp`,
`u_scale`/`v_scale`, `scroll_*`, `anim*`, `handle`, `f74/f76`, `reserved`,
а также `n_idx` (если не правится `indices`) остаются прежними — это
отдельная обязательная проверка `--check`.

Почему это корректно по данным:

* `centre` — авторское поле: совпадает со средним вершин у
  **150 423/235 069** полигонов и с серединой AABB у **204 678/235 069**;
  движок его не пересчитывает.
* `corner_a`/`corner_b` — **кэш загрузки** (`0x43529f` инициализирует их
  ±inf и считает min/max вершин относительно `centre`): в файле они
  совпадают с `min/max(vertex − centre)` лишь у **3 323/235 069**. Правка
  любого поля полигона их не трогает; после загрузки движок всё равно
  пересчитает их сам.
* `uv_u_fp`/`uv_v_fp` и `u_scale`/`v_scale` — отдельные поля; `uv=`
  меняет только `uv_u`/`uv_v`. Проекция текстуры в рендере идёт от
  `u_axis`/`v_axis`/`centre`/`uv_fp`, а не от `uv_u`.
* `normal` ни на одно поле записи не влияет: это независимая авторская
  нормаль. Её читают рендер (затенение, `shade_face`, `kLight`) и
  коллизии как `data_normal` (`docs/COLLIDE.md` §1.2); «plane»-полей,
  которые нужно было бы пересчитывать, в записи нет.
* `lightmap` при загрузке пересчитывается базой лайтмапов уровня
  (`0x428064`) — это рантайм, в файле поле остаётся тем, что записано.
* `flags=0x8000` — «UV/кадр посчитаны». Инструмент пишет слово буквально и
  **не** эмулирует `0x43e02d`: если сбросить `0x8000`, движок при
  загрузке пересчитает UV из геометрии. Это осознанно оставлено
  вызывающему.

Размер файла при любых правках §3 не меняется (все поля — фиксированной
ширины), поэтому `--check` требует «размер тот же» (§5).

## 4. Смена `n_idx` — только `--allow-resize`

`n_idx` — u8, допускается 3..255 (в поставке 3..26; 26 — доказанный
максимум, `level20.sbw`). Если новый список индексов **другой длины**:

* запись перестраивается целиком: голова с новым `n_idx`, новый список
  индексов, тот же 112-байтный хвост;
* запись вставляется в поток, поэтому все последующие байты сдвигаются на
  `2·(new − old)`; **таблицы смещений в `.sbw` нет**, так что сдвиг
  корректен;
* без `--allow-resize` правка отвергается текстом (код 2).

`--check` для resize доказывает не «те же смещения» (их нет), а **то же
содержимое**: заголовок целевого объекта, все прочие объекты (голова +
геометрия), байты целевого объекта вне целевых полигонов, маскированную
запись целевого полигона (голова/индексы/хвост), все прочие поля и
round-trip оракула. Реальный прогон: `level0`, объект 0, полигон 0,
`indices=0,2,4,6,2` (4 → 5):

```
254439 -> 254441 bytes (+2; stream shifted)
  [ok] file size changed by exactly 2 byte(s) (expected from n_idx)
  [ok] bytes outside the target object are identical
  [ok] 191 other objects (header + geometry) are identical
  [ok] poly[0]: record with the edited fields masked is byte-identical
  [ok] oracle round-trip of the edit is exact
result: OK (26 checks)
```

Движок читает результат (`--info`: `polygons=1449 vertices=2173
bytes=254441`), рендер 640×400 **побитово совпадает** с исходным
(0 пикселей): лишний индекс даёт вырожденное звено веера, геометрия та же.
Остальные объекты и их поля побайтово те же (независимая проверка через
`gm.sbw`).

Ограничение: `n_verts` и вершины не меняются — добавлять/удалять вершины
этот срез не умеет (`sbwmesh.py` двигает существующие). Список индексов
может повторять вершины и быть длиннее `n_verts` (как в поставке, где
26 индексов при меньшем числе вершин встречается).

## 5. `--reindex`: разворот обхода

```
--reindex LEVEL --object N [--index I] --out FILE
```

Без `--index` разворачивается каждый полигон объекта, с `--index` — один.
`indices` заменяется на обратный порядок, `n_idx` и размер записи те же.
Обязательные проверки (`--check ... --expect-reindex`):

* список индексов — ровно `reversed(old)`;
* **авторская `normal` не изменилась** (это `data_normal` для коллизий);
* area-weighted (Newell) нормаль изменила знак — на корпусе это верно для
  **235 045/235 045** невырожденных полигонов (`--audit`), т.е. разворот
  меняет ориентацию многоугольника как целого;
* нормаль первого треугольника веера изменила знак у плоских полигонов
  (`|dot(geo, normal)| >= 0.99`); у остальных она может отличаться не
  только знаком — см. ниже.

`normal` и `data_normal`: у поставочных полигонов обход противоположен
сохранённой нормали (`docs/COLLIDE.md` §1.2); Newell-нормаль
противоположна `normal` ровно у **235 045/235 045** невырожденных
полигонов, первое звено веера — у 234 322 («same» у 14, «skew» у 679
неплоских, вырождено у 54). После `--reindex` у `level0` объекта 187
независимая проверка через `gm.sbw` даёт:

```
obj187: 26 polys, indices reversed True, stored normal unchanged True,
        first-triangle flip 16/16, dot(geo,data_normal) -1.0 -> +1.0
```

**Важное следствие: веерная триангуляция.** Движок (и `gm/render.py`, и
`collide_goldens.py`) триангулирует полигон веером от **первого** индекса:
`(i0,i1,i2), (i0,i2,i3), …`. После разворота первым становится бывший
последний индекс, поэтому у полигона с `n_idx > 3` меняются не только
знаки, но и сами диагонали веера. Для плоских выпуклых полигонов это та
же площадь с противоположной ориентацией; для неплоских (679 в корпусе)
треугольники различаются — это не ошибка инструмента, а свойство формата.
Измерено на `level0`:

* объект 0 (6 квадов): изменены 24 байта, все `data_normal` те же,
  геометрическая нормаль каждого полигона перевёрнута, рендер 640×400 —
  **0** отличающихся пикселей;
* объект 187 (26 полигонов; у 10 из них после разворота первое звено
  веера вырождено, поэтому знак первой треугольной нормали проверен у 16
  плоских): изменены 120 байт, размер тот же, рендер — **2** пикселя
  (`x 191..193, y 151..152`) именно из-за смены диагоналей веера.

Поведение независимого оракула коллизий, который классифицирует
поверхности **по обходу** (`tools/re/collide_goldens.py`), меняется:

| файл | треугольники | пол/стена/потолок |
|---|---:|---|
| `orig` / `tex` / `norm` | 3162 | 522 / 2082 / 558 |
| `rei` (объект 187) | 3144 | **496 / 2072 / 576** |

`C++`-движок классифицирует по `data_normal` (`docs/COLLIDE.md` §1.2),
поэтому его `--info` на `rei` дословно тот же (`polygons=1449`,
`vertices=2173`, `bytes=254439`), а рендер отличается только двумя
пикселями от смены диагоналей, не от затенения. Разница в числе
треугольников у `collide_goldens` — 18 звеньев нового веера, которые его
порог площади считает вырожденными.

## 6. `--check`: что именно доказывается

```
--check FILE [--against LEVEL] [--object N
         ( --index I (--field NAME=VALUE ... | --expect-reindex)
         | --expect-reindex )] [--allow-resize]
```

Без ожидания правки файл должен быть **побайтово равен** источнику
(`--against LEVEL` или одноимённый файл рядом с `--game`). С ожиданием
выполняются (для одной правки поля — 22 проверки, `--check` добавляет 6
структурных, всего 28; для разворота объекта из 26 полигонов — 247;
для resize — 26):

1. оракул разбирает исходный и новый файл ровно до EOF;
2. counts (текстуры/эффекты/секторы/объекты/полигоны/**вершины**) и
   флаговые слова объектов не изменились;
3. свой читатель (`walk`, независимый от `gm.sbw`) доходит до EOF и
   совпадает с оракулом по counts;
4. длина изменилась ровно на `2·Σ(new_n_idx − old_n_idx)`; ненулевая
   дельта допустима только с `--allow-resize`;
5. заголовок целевого объекта (`u32` + 96 байт трансформа) идентичен;
6. **все байты вне целевого объекта** идентичны (сравнение по спанам
   обоих файлов, поэтому покрывает и сдвинутый поток);
7. **все остальные объекты** (голова + геометрия) идентичны;
8. внутри целевого объекта байты вне целевых полигонов идентичны
   (префикс, промежутки, суффикс);
9. запись каждого целевого полигона с замаскированными правимыми полями
   побайтово идентична (голова, индексы, хвост);
10. оба читателя видят ровно ожидаемое значение каждого правленого поля;
11. все прочие документированные поля целевых полигонов не изменились
    (сравниваются `centre`, `corner_a/b`, `uv_fp`, `scroll_*`, `anim*`,
    `handle`, `f74/f76`, `reserved`, `flags`, `n_idx` — 31 поле);
12. при том же размере **каждый** отличающийся байт лежит внутри спана
    правленого поля; при resize единственное изменение — сдвиг потока;
13. `Sbw.to_bytes()` оракула побайтово равен исходному и новому файлу;
14. для `--expect-reindex` — обратный порядок индексов, неизменная
    `normal`, смена знака Newell и (для плоских) первого звена веера.

Проверка не «пустая»: self-test подменяет чужое поле, значение целевого
поля, другой полигон, хвост объекта, чужой объект и заголовок (`origin`) —
каждая подмена ловится.

### 6.1 Независимый оракул (`gm.sbw` без кода инструмента), `level0`

| правка | размер | отличающиеся байты | что видно в `gm.sbw` |
|---|---:|---|---|
| `texture 1→2` (obj 0, poly 0) | 254439 → 254439 | **1**: `[26345]` | только `texture` первого полигона |
| `normal (0,0,-1)→(0.42,-0.5,0.75)` (obj 43, poly 7) | 254439 → 254439 | **11**: `79831..79842` | только `normal` (нормализована до `(0.422351,-0.502798,0.754197)`) |
| `--reindex` (obj 187, 26 полигонов) | 254439 → 254439 | **120** | индексы развёрнуты, `normal` та же, `dot(geo,data_normal)` −1 → +1 |
| `indices 4→5` (obj 0, poly 0, `--allow-resize`) | 254439 → **254441** | сдвиг потока | `n_idx=5`, прочие объекты/поля те же |

Во всех случаях: counts совпадают, `data_end == len(data)` у обоих

### 7.1 `--self-test` (без файлов игры), 118/118

Синтетический `.sbw` строит сам тест: 2 текстуры, 1 эффект, 2 сектора,

## 8. Ограничения

* **Полигоны не создаются и не удаляются.** `n_polys` объекта неизменен;
  нет команды «вставить/удалить полигон». Инструмент отказывает по
  индексу вне `0..n_polys-1` текстом и кодом 2.
* **Вершины не создаются и не удаляются.** Меняются только индексы внутри
  существующего `0..n_verts-1`; для правки координат — `sbwmesh.py`.
* **`n_idx` только с `--allow-resize`.** Другая длина списка меняет размер
  файла и сдвигает поток; это безопасно (нет таблицы смещений) и
  доказывается по содержанию (§4), но абсолютные смещения последующих
  объектов в новом файле другие. Верхняя граница `n_idx` — 255 (u8); в
  поставке максимум 26, поведение движка на 27..255 не проверялось.
* **`normal` нормализуется и не может быть нулевой.** 24 нулевые нормали
  в поставке — вырожденные полигоны; воспроизвести их через `--set`
  нельзя. Полярность (`normal` против обхода) не проверяется: в поставке
  встречаются оба знака (14 полигонов «same» по вееру), поэтому редактор
  не «исправляет» ориентацию молча.
* **`u_axis`/`v_axis` не нормализуются** — так записана поставка
  (22 % осей ненормированы); нормализация изменила бы масштаб текстуры.
* **Кэш кадра не пересчитывается.** `centre`, `corner_a/b`, `uv_u/v`,
  `uv_fp`, `u_scale/v_scale`, `scroll_*`, `anim*` остаются прежними, если
  их не править. `corner_a/b` движок всё равно пересчитывает при загрузке
  (`0x43529f`), `centre` и `uv_fp` — авторские.
* **`--reindex` меняет не только знак.** Веер триангуляции привязан к
  первому индексу, поэтому у `n_idx > 3` меняются диагонали: у плоских
  полигонов это та же площадь с обратной ориентацией, у неплоских —
  другие треугольники (в `level0` объект 187 это дало 2 пикселя рендера и
  −18 треугольников у `collide_goldens`). Новый обход не «канонизируется»
  и не проверяется на выпуклость.
* **`flags` пишется буквально.** Сброс `0x8000` заставит движок
  пересчитать UV при загрузке (`0x43e02d`); инструмент этого не
  эмулирует и не предупреждает — это осознанная правка поля.
* **Лайтмапы не пересчитываются.** `lightmap` — индекс записи sibling
  `.sbc`; правка поля не трогает сам `.sbc`, не пересчитывает базу
  лайтмапов (`0x428064`) и запечённый свет. Для проверки диапазона нужен
  `.sbc` (`--sbc` или файл рядом с уровнем); без него `lightmap=` 
  отвергается.
* **Сцена/скрипты не пересчитываются.** `.sbt` (двери/переключатели/
  лифты), сущности, лайтмапы и порталы остаются прежними; правка
  полигона не двигает триггеры.
* **Нет рантайм-кэшей.** Инструмент пишет только `.sbw`; AABB секторов,
  сферы, порталы и прочие кэши оригинального движка в файл не входят.
* **Точность.** `normal`/`u_axis`/`v_axis` — `f32`: запрос
  `normal=0.42,-0.5,0.75` сохраняется как
  `(0.4223506, -0.5027983, 0.7541975)`; `--list`/`--check` показывают
  именно сохранённые `f32`-значения.
* **`--check` без `--against`** проверяет только структуру (EOF, counts,
  round-trip, индексы в диапазоне); побайтовое сравнение включается
  `--against LEVEL` (или автоматически, если рядом с `--game` есть файл с
  тем же именем).
* **`--list` sharing — точное равенство `f64`.** Позиции считаются как
  `origin + basis · local`; вершины в разных объектах делят позицию только
  при побитовом совпадении (в поставке 52 134 такие позиции по корпусу).
* **Правка одного файла.** Инструмент не синхронизирует зеркало
  `~/.cache/gunmetal-re/game` и не пишет в установку игры (`--game`).

## 9. Сводка команд

```sh
# что внутри уровня: полигоны, поля, две нормали, sharing
python3 tools/editor/sbwpoly.py --list level0 --limit 8
python3 tools/editor/sbwpoly.py --list level0 --object 0 --limit 0
python3 tools/editor/sbwpoly.py --list level0 --object 0 --limit 0 --json

# поля одного полигона (размер не меняется)
python3 tools/editor/sbwpoly.py --set level0 --object 0 --index 0 \
    --field texture=2 --out /tmp/opencode/poly/tex/level0.sbw
python3 tools/editor/sbwpoly.py --set level0 --object 43 --index 7 \
    --field normal=0.42,-0.5,0.75 --out /tmp/opencode/poly/norm/level0.sbw
python3 tools/editor/sbwpoly.py --check /tmp/opencode/poly/norm/level0.sbw \
    --against level0 --object 43 --index 7 --field normal=0.42,-0.5,0.75

# разворот обхода (сохранённая normal не меняется)
python3 tools/editor/sbwpoly.py --reindex level0 --object 187 \
    --out /tmp/opencode/poly/rei/level0.sbw
python3 tools/editor/sbwpoly.py --check /tmp/opencode/poly/rei/level0.sbw \
    --against level0 --object 187 --expect-reindex

# другой n_idx (поток сдвигается) — только с --allow-resize
python3 tools/editor/sbwpoly.py --set level0 --object 0 --index 0 \
    --field indices=0,2,4,6,2 --allow-resize \
    --out /tmp/opencode/poly/resize/level0.sbw
python3 tools/editor/sbwpoly.py --check /tmp/opencode/poly/resize/level0.sbw \
    --against level0 --object 0 --index 0 --field indices=0,2,4,6,2 \
    --allow-resize

# весь корпус, измерения, самотест
python3 tools/editor/sbwpoly.py --roundtrip
python3 tools/editor/sbwpoly.py --audit
python3 tools/editor/sbwpoly.py --self-test

# движок на правке (полная установка, слинкованная по файлам)
build/sandbox/engine/gunmetal -g /tmp/opencode/poly/norm -l level0 --info
build/sandbox/engine/gunmetal -g /tmp/opencode/poly/norm -l level0 \
    --render /tmp/opencode/poly/norm-640.png --width 640 --height 400

# независимый оракул коллизий (классификация по обходу)
python3 tools/re/collide_goldens.py level0 --game /tmp/opencode/poly/rei
```

Коды возврата: `0` — успех; `1` — проверка не прошла (`--check`,
`--roundtrip`, `--self-test`, `--audit`); `2` — неверный ввод или отказ
(сообщение в stderr); `3` — внутренняя ошибка. Трассировка наружу не
выходит.
