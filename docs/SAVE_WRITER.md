# C++-писатель сейвов Gunmetal

* **Статус:** запись контейнера, заголовка, цепочки блоков и блока игрока (9)
  реализована; `saved0.sbt`/`saved1.sbt` проходят round-trip байт-в-байт.
* **Ветка:** `feat/cpp-save-writer`, база `master` `4141bbe`, дата 2026-10-20.
* **Игра:** только чтение (`/mnt/d/games/Gunmetal 3dfx/SAVEGAME`).
* **Файлы:** `engine/src/res/save.h`, `engine/src/res/save.cpp`,
  `engine/tests/test_save_writer.cpp`, регистрация теста в
  `engine/tests/CMakeLists.txt`.
* **Эталон:** `tools/re/save_rebuild.py`, `tools/re/save_fields.py`,
  `docs/SAVE.md`, `docs/SAVE_FIELDS.md`, `docs/SAVE_CPP.md`.

Читатель не менял своего поведения: новый код расширяет `Save`/`SaveBlock`
полями raw-байтов и добавляет `Save::to_bytes()` и `rebuild_save()`.
Существующий API `parse_save()`/`find_save_level()` и все поля `SaveHeader`/
`SaveBlock`/`SavePlayer` сохранены.

## 1. Контейнер

```
0x000  char name[0x50]     title в байтах 0..11, дальше нули
0x050  u32  reserved
0x054  char level[0x50]    имя уровня, NUL-terminated ("LEVEL0")
0x0a4  u32  F[22]          поля F0..F21
0x0fc  4 x char[16]        "K-9", "", "coargus", "none"
0x13c  [u8 id][payload]... [0xff]
```

Писатель собирает ровно `kSaveHeaderSize` (`0x13c`) байт заголовка, затем
блоки в порядке `Save::blocks` и завершающий `0xff`. Выравнивания,
контрольной суммы и хвоста нет.

## 2. API

```cpp
#include "res/save.h"

std::string error;
auto save = gm::parse_save(bytes, error);       // как раньше
if (!save) { /* error */ }

// 1. Просто сериализовать текущую модель.
auto out = save->to_bytes(error);
if (!out) { /* error: поле не представимо / нет raw / битые границы */ }

// 2. Правка типизированных полей игрока и пересборка с проверкой.
save->player->ammo[0] = 2500;
save->player->armor   = 9000;
save->player->position[0] += 10.0;

auto patched = gm::rebuild_save(*save, /*verify=*/true, error);
if (!patched) { /* error: поле не пережило round-trip */ }
// *save теперь описывает новые байты: block.offset/raw и player.slot_offsets
// пересчитаны из результата.
```

`to_bytes()` — структурная сериализация. `rebuild_save(save, verify, error)`:

1. вызывает `save.to_bytes()`;
2. парсит результат заново;
3. при `verify=true` требует, чтобы повторная сериализация дала те же байты
   и чтобы типизированные поля заголовка/игрока (включая биты `double`)
   совпали с исходной моделью;
4. заменяет `save` разобранным результатом (смещения и raw-байты становятся
   согласованы с новым файлом).

Ошибка возвращается через `error`, успех — `std::optional<std::vector<uint8_t>>`
с полным файлом.

## 3. Стратегия raw/typed

**Raw (побайтовое хранение).** `parse_save()` теперь кладёт payload каждого
блока (всё после байта id) в `SaveBlock::raw`; инвариант
`raw.size() == size - 1`. Писатель копирует `raw` для всех блоков, кроме 9,
поэтому нетронутые блоки возвращаются ровно теми же байтами, даже если их
тело (двери, скрипт, ITEM, SECTOR_STUFF, ...) остаётся непрозрачным.

**Typed (поля игрока).** Блок 9 пересобирается из `SavePlayer`:

* `present[8]` — флаги слотов;
* `slot_raw[8]` — исходная структура `0x3510` каждого присутствующего слота;
* `attachment_raw[8]` — склеенные 16-байтовые записи вложений (по одной на
  каждый ненулевой `u32` в `struct+0x317c`); сами вложения не интерпретируются;
* `pair_header_raw[2]`, `pair_struct_raw[2]` — две хвостовые пары
  `{0x50 header, 0x3510 struct}`;
* типизированные поля первого присутствующего слота: `position`, `angles`,
  `history_index`, `exists`, `status_present`, `object_id`, `armor_max`,
  `armor`, `shield_max`, `shields[4]`, `weapon_slot`, `weapon_mask`, `ammo[12]`.

При записи структура слота копируется из `slot_raw` и в неё патчатся только
типизированные поля по фиксированным смещениям (`0x0000`, `0x0018`, `0x3178`,
`0x3204`, `0x3210`, `0x3214`, `0x3244`, `0x3248`, `0x324c`, `0x3250`,
`0x3294`, `0x3298`, `0x329c`). Размер `0x3510` и все неизвестные байты
сохраняются. Поддерживаются сейвы с 1 и 8 присутствующими слотами; поля
патчатся в первом присутствующем, остальные переносятся raw.

Заголовок сериализуется из типизированных полей: `title` (не более 12
байт) в `+0x00`, `version` в `+0x0c`, `reserved` в `+0x50`, `level_name`
(не более `0x50`) в `+0x54`, 22 поля в `+0xa4`, четыре слота по 16 байт в
`+0xfc`. Свободные байты заполняются нулями — в обоих поставочных сейвах
они и так нулевые.

Проверки при записи повторяют читатель: title — печатный ASCII и не пуст,
level не пуст, габариты брони/щитов и `weapon_slot` в допустимых границах,
позиция/углы конечны. Дополнительно отвергаются пустой `raw`, дубликаты id,
id `0xff`, блок 9 без `player`-состояния, `player` без блока 9 и результат
больше 64 МиБ.

## 4. Byte-exact

`saved0.sbt` и `saved1.sbt` (по 243368 байт, 15 блоков, 1 присутствующий
слот игрока) проходят `parse_save -> to_bytes` без единого отличия:

| файл | размер | FNV-1a 64 | SHA-256 |
|---|---|---|---|
| `saved0.sbt` | 243368 | `0xb994929515f53af5` | `e39c0c35…b623ff` |
| `saved1.sbt` | 243368 | `0x0d038197e152cd65` | `93f4edd3…34bd13` |

Тест `gm_save_writer_tests` проверяет размер, FNV-1a 64, побайтовое равенство,
`raw.size() == size - 1` для каждого блока и сумму `0x13c + Σsize + 1`.
Отдельно проверяется, что `rebuild_save(..., verify=true)` возвращает те же
байты и обновляет `Save::size`/смещения.

## 5. Правки полей

Правка меняет ровно байты выбранного поля, а повторный `parse_save` видит
новое значение. Это закреплено тестом на `saved0.sbt`:

| поле | смещение в файле | сколько байт может измениться |
|---|---|---|
| `position[0]` | `slot_offsets[0] + 0x0000` | 8 (`f64`) |
| `armor` | `slot_offsets[0] + 0x3248` | 4 (`i32`) |
| `ammo[0]` | `slot_offsets[0] + 0x329c` | 4 (`u32`) |
| `ammo[5]` (8 слотов) | `slot_offsets[0] + 0x329c + 20` | 4 (`u32`) |

Тест сравнивает все байты вне ожидаемого диапазона и проверяет, что размер
файла не изменился. Для 8 присутствующих слотов дополнительно проверяется,
что raw-структура и вложения нетронутого слота 5 остаются прежними.

## 6. Границы

* Блоки пишутся **в порядке `Save::blocks`**, без канонической сортировки.
  `parse_save` сохраняет порядок файла, поэтому round-trip точен; если
  собрать `Save` вручную в другом порядке, файл будет другим (но валидным,
  если порядок устраивает игру).
* Заголовок не хранится raw: байты между полями нормализуются в ноль.
  Для поставочных сейвов это no-op; сейв с мусором в padding будет
  канонизирован.
* Блок 9 типизирован только для первого присутствующего слота. Остальные
  присутствующие слоты и обе хвостовые пары переносятся raw; их поля
  (кроме `pair_headers`, которые можно менять как строку) не редактируются.
* Вложения (`attachment_raw`) и id вложений в `struct+0x317c` не
  редактируются; число записей должно совпадать с числом ненулевых id.
* Остальные блоки — raw. Типизированные писатели дверей/переключателей/
  things/SCRIPT не входят в эту задачу.
* `to_bytes()` не гарантирует, что результат распарсится: для этого есть
  `rebuild_save()` (он всегда перепарсивает, а `verify=true` ещё и сверяет
  модель).
* Движок по-прежнему только читает сейвы: `main.cpp` и игровой цикл не
  подключают писатель.

## 8. Проверка

```sh
export PATH=$HOME/tools/cmake-4.4.4-linux-x86_64/bin:$HOME/tools/bin:$PATH
cmake -S . -B build/sandbox -G Ninja -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_CXX_COMPILER=$HOME/tools/bin/zigcxx \
      -DCMAKE_C_COMPILER=$HOME/tools/bin/zigcc -DGM_BUILD_TESTS=ON \
      -DGM_WITH_SDL3=ON -DSDL3_DIR=$HOME/tools/sdl3/lib/cmake/SDL3
cmake --build build/sandbox --target gm_save_writer_tests -j 32
ctest --test-dir build/sandbox -R save --output-on-failure
python3 regress.py
```

`ctest -R save` гоняет старый `save` и новый `save_writer`; `regress.py`
остаётся без изменений и покрывает Python-эталон (`save / rebuild is
byte-exact`, `--set`, `diff`).
