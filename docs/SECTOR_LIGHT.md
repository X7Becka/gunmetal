# Скриптовый свет сектора: `sector+0x16` (M4.2.5)

Статус: измерение готово. Инструмент — `tools/re/sector_light.py`
(только чтение: `gm/sbt.py`, `gm/sbtvm.py`, `gm/sbtvm_exec.py`, `gm/sbw.py`).
Вопрос: второе слагаемое света движка — байт `light` записи сектора мира,
команда `SET_SECTOR_BRIGHTNESS` и родня — используется ли он в поставочных
уровнях и что это значит для `gm/render.py`.

## 1. Короткий ответ

**Используется, но только как событийный эффект — не как освещение уровня.**

| величина | значение |
|---|---|
| уровней с командами света сектора | **36/36** |
| всего команд | **903** (`SET_SECTOR_BRIGHTNESS` 9, `SET_SOURCESECTOR_BRIGHTNESS` 562, `SET_HANDLESECTOR_BRIGHTNESS` 332) |
| при загрузке уровня (главный скрипт, `offset 0`) исполнено | **0** (36/36 прогонов дошли до `END`) |
| значения (знаковый байт): отрицательные / 0 / положительные | **199 (22%) / 362 (40%) / 342 (38%)** |
| `sector+0x16` в файле `.sbw` | **нет поля**; загрузчик пишет 0 (`0x42ae05`) |
| запись `SECTOR_STUFF` (тип 8) в поставочных `.sbt` | **нет ни в одном из 36** |
| состояние на загрузке у всех секторов всех уровней | **0** |

То есть статический кадр `gm/render.py` (`brightness + ambient`) корректен:
на момент загрузки оба «скрытых» слагаемых — `object+0x74` (0 во всех
28 192 объектах, см. `docs/LIGHTMAP_AUDIT.md` §4) и `sector+0x16` (0 у всех
секторов, этот документ) — равны нулю. Скриптовый свет меняет кадр только
после события (взрыв, выключение/включение освещения). Это закрывает
последний открытый пункт `docs/LIGHTMAP_AUDIT.md` §5 — «`sector+0x16` из
SBT-скриптов».

## 2. Что доказано кодом

### 2.1 Где живёт поле

`sector+0x16` — поле **записи сектора мира** `0x5670d8`, шаг `0x18`
(счётчик `0x5670dc`), а не `SECTOR_STUFF` `0x800b60`. Это разные массивы:
в `SECTOR_STUFF` смещение `+0x16` попадает в старшую половину `move[2]`
(три `f64` в `+0x00..+0x17`), а свет — только в записи `0x5670d8`
(`docs/VM_EXEC.md` §3.2, `docs/WORLD_FIELDS.md` §2.1).

### 2.2 Читатель: сумма и `movsx`

```
43ca32  movsx ecx, BYTE PTR [eax+0x70]   ; poly.brightness  (+0x70, u8)
43ca3c  movsx eax, BYTE PTR [edx+0x74]   ; object.brightness_bias (+0x74, i8)
43ca48  movsx eax, BYTE PTR [edx+0x16]   ; sector.light      (+0x16, u8 -> signed)
43ca40  add  ecx,eax                     ; +0x70 + 0x74
43ca4c  add  ecx,eax                     ; + sector+0x16  -> [ebp-0x818]
...
43cca7  cmp  DWORD PTR [ebp-0x818],0x7f  ; clamp(..., 0x7f, -0x80)
43ccc8  cmp  DWORD PTR [ebp-0x8a4],0xffffff80
```

Байт читается **знаково** (`movsx`), поэтому `0xb8` — это `-72`, а `0x80` —
`-128`; сумма клампится в `-128..127`. Второй читатель того же поля —
`0x43d8e3` (трасса/выборка света, `docs/WORLD_MATERIALS.md` §3.5).

### 2.3 Загрузчик: поле обнуляется

`0x42ad9c` читает `u32 n_objects` в `+0x00`, `0x42adbd` — `u16 kind` в `+0x14`,
`0x42adde` — `u8 sub` в `+0x17`, после чего:

```
42adf3  mov WORD PTR [edx+0x8],0x0      ; резерв
42adfc  mov WORD PTR [eax+0xa],0x0      ; n_sprites
42ae05  mov BYTE PTR [ecx+0x16],0x0     ; light: в файле поля нет, значение = 0
```

В файле `.sbw` записи сектора — `u32 n_objects, u16 kind, u8 sub`
(ровно 7 байт, `gm/sbw.py: Sector(kind, sub, objects)`), байта света нет.

### 2.4 Писатели: три команды

| опкод | команда | обработчик | запись | цель |
|---:|---|---|---|---|
| 9 | `SET_SECTOR_BRIGHTNESS` | `0x4578d6` | `0x4578f8` `mov BYTE PTR [eax+0x16],cl` | индекс сектора из операнда, геттер `0x42d8a5`: `0 <= i < 0x5670dc` |
| 28 | `SET_SOURCESECTOR_BRIGHTNESS` | `0x458063` | `0x45807c` | сектор **источника** (`edi`), статически неизвестен |
| 41 | `SET_HANDLESECTOR_BRIGHTNESS` | `0x4583a6` | `0x4583f1` | все секторы таблицы `SECTOR_HANDLE` с тегом из операнда (`0x5b1df8` теги, `0x617fb8` секторы, счётчик `0x5e3de0`) |

Значение во всех трёх — **младший байт** `L`-операнда: `mov cl,BYTE PTR
[ecx+edx]`, где `edx = [0x4b6784]` (таблица размеров операндов). Старшие байты
игнорируются: операнд `-72` (`0xffffffb8`) и `184` (`0x000000b8`) дают в
`sector+0x16` один и тот же байт `0xb8` → `-72`. Других писателей поля нет:
`docs/WORLD_FIELDS.md` §2.1 перечисляет те же три адреса плюс обнуление
загрузчика.

### 3.2 К каким секторам и что это за эффекты

* **`SET_SOURCESECTOR_BRIGHTNESS` (28) — вспышка взрыва.** Есть на всех 36
  уровнях (14..30 команд). Типовая пара: `32`/`48`/`64`/`127` → `0` после
  `SOURCE_CLEAR`. Пример level0 (`+0x6c11`): `ADD_SPRITE_MOVING_AT_SOURCE`,
  `PLAY_FRAME_LOOP_SAMPLE_AT_SOURCE`, `CAUSE_BLAST_RADIUS_DAMAGE`,
  `SET_SOURCESECTOR_BRIGHTNESS 48`, `SOURCE_CLEAR`, `SLEEP 4`,
  `SET_SOURCESECTOR_BRIGHTNESS 0`.
* **`SET_HANDLESECTOR_BRIGHTNESS` (41) — выключение/включение освещения.**
  332 команды на 15 уровнях; теги разрешаются через `SECTOR_HANDLE` (тег — не
  номер сектора!). Пример level0: теги `5..11,42..48` → секторы
  `50,51,52,8,11,24,33..35,38..44`; значения `-72`/`-128` (свет выключен),
  а возврат в `0` — в отдельных обработчиках: теги `5..10` → `0` с `+0xca9c`,
  тег `11` проходит `-92,-88,…,−8` → `0` (`+0xcb5f`..`+0xcc07`), теги
  `42..48` → `0` (`+0xcc27`..`+0xcd29`) — то есть «плавное включение» сделано
  цепочкой команд с задержками, а не одним присваиванием.
  Масштаб: `level13` — 143 из 146 секторов (90.5% граней), `level4` —
  102 из 185 (39.2%), `level11` — 64 из 210 (35.0%), `level7` — 27 из 122,
  `level0` — 16 из 58.
* **`SET_SECTOR_BRIGHTNESS` (9) — точечное затемнение по номеру сектора.**
  Всего 9 команд на 2 уровнях: `level1` — сектор 82, `-24` ×4 и `0` ×4
  (мигание); `level13` — одна команда.
* **Свет полигонов** (`poly+0x70`, другое слагаемое): `SET_HANDLEPOLY_BRIGHTNESS`
  246 команд на 22 уровнях (только она; 16 и 33 не встречаются). Это
  отдельное семейство — пульсация/подсветка отдельных полигонов (значения от
  `-128` до `127`, чаще положительные, 44 нуля); лишь 22 из 246 стоят в том же
  обработчике, что команда света сектора. На `sector+0x16` они не влияют.

### 3.3 Контекст, порядок и «сброс»

| проверка | значение |
|---|---|
| команд в `init`-блоке (`offset 0`) / в обработчиках | **0 / 903** |
| строк таблицы сущностей: enabled (`flags & 0x1ff`) / disabled (`flags == 0`) | 831 / 72 |
| команд в блоке, где есть `ADD_*` | 300 |
| из них `ADD_*` стоит **до** команды света | **292 (97.3%)** |
| цель-последовательностей в одном обработчике | 441 |
| из них с ненулевым значением | 407 |
| заканчиваются нулём (эффект снят в том же обработчике) | 313 |
| заканчиваются ненулём (снимает другой обработчик или остаётся) | 94 |

72 команды лежат в блоках, скомпилированных как `DISABLED` (`flags == 0`):
`level4` — 42, `level8` — 20, `level11` — 8, `level5` — 2. Они сработают
только если какой-то скрипт включит строку (`ENABLE`, `docs/ENTITY_FIELDS.md`
§1), поэтому в «всегда доступные» эффекты их записывать нельзя.

Ответ на вопрос «до или после `ADD_*`»: **никогда не до**. Когда в том же
обработчике создаётся объект (мина, спрайт, дверь), команда света идёт после
`ADD_*` (292 из 300); в остальных 603 командах блок вообще не создаёт объектов
— это чистые переключатели света (в т.ч. 94 последовательности, которые
оставляют затемнение до отдельного обработчика «включить»).

## 4. Сверка с `.sbw` и с загрузкой

* Запись сектора в `.sbw` (`gm/sbw.py`) содержит только `kind`, `sub`,
  `objects`; поля света нет (инструмент печатает `sector_fields`).
* Записи `SECTOR_STUFF` (тип 8, `0x5800` байт) нет **ни в одном** из 36
  поставочных `.sbt` (там всегда `12, 20, [15, 16,] 17, 5, 4, 11, 255`), так
  что и через неё свет задать нечем.
* Прогон главного скрипта (`offset 0`) через `gm/sbtvm_exec`: **36/36**
  уровней доходят до `END` (38 путей — 2 форка, 768 шагов суммарно),
  исполненных команд света — **0**. Это исполнение, а не только статическая
  классификация блоков.

Следствие: `sector+0x16 == 0` для всех 256 слотов у всех 36 уровней при
загрузке — свойство загрузчика, а не «данные такие». Проверить его из файлов
нельзя (нечего читать), поэтому в отчёте инструмента это структурный факт с
адресом `0x42ae05`.

## 5. Что это значит для рендера

`gm/render.py` сейчас:

* `gm/render.py:733` — для граней с лайтмапом `base = face.brightness + ambient`;
* `gm/render.py:747` — для граней без лайтмапа `shade += _face_brightness(face)`.

Движок считает `clamp(poly+0x70 + obj+0x74 + sector+0x16 [+ texel], -128, 127)`,
поэтому «недостающие» слагаемые — `obj+0x74` (0 во всех 28 192 объектах) и
`sector+0x16` (0 при загрузке, §4). **Для кадра состояния «уровень только что
загружен» `brightness + ambient` — полная формула; менять `gm/render.py` не
нужно.**

Скриптовый свет — событийный: вспышка взрыва на секторе источника
(`+16..+127`, живёт единицы тиков) и выключение/включение освещения участков
(`-5..-128`, в `level13` — почти всего уровня). Чтобы увидеть такое состояние
в рендере, нужно не «добавить поле в парсер» (его нет в файлах), а
исполнить/смоделировать скрипт и применить команды 9/28/41 к записи сектора.
В C++-порте эти записи уже есть: `VmState::world_sectors[].light`
(`engine/src/res/vm_exec.h:501`, заполняется `vm_load_world`; там же в
комментарии зафиксировано, что `+0x16` равен нулю при загрузке — `0x42ae05`)
и таблица команд `docs/VM_CPP.md` §2. Растеризатор `engine/` это поле пока не
читает — для статического кадра это и не требуется; для сценарных сцен
понадобится резолв источника/хэндла во время исполнения.

```
python3 tools/re/sector_light.py --self-test        # 18 проверок, rc=0
python3 tools/re/sector_light.py                    # сводка по 36 уровням
python3 tools/re/sector_light.py --level level0     # все записи уровня
python3 tools/re/sector_light.py --json > light.json  # побайтно детерминирован
```

## 7. Что осталось

* **562 команды `28`** статически не разрешаются: цель — сектор источника,
  он известен только в рантайме (какой объект вызвал `GENERATE`). Нужен
  прогон исполнителя с реальным источником и записью `world_sectors[].light`.
* **94 последовательности** заканчиваются ненулевым значением: часть снимается
  отдельным обработчиком «включить свет» (видно в `level0`), часть — нет;
  чтобы отличить «осталось темно» от «снимет другой триггер», нужен
  событийный прогон, а не статика.
* **Знак и кламп**: `-128` при `poly.brightness == 0` даёт сумму `-128`
  (грань гаснет полностью); влияние на палитру/`lighttable` —
  `docs/LIGHTMAP_AUDIT.md` §5, отдельная задача.
