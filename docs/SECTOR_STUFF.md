# `SECTOR_STUFF`: какой слот адресует команда (27–31, 40–45)

Статус: **измерение готово** (M5.2/M6). Инструмент —
`tools/re/sector_stuff.py` (`--self-test`, `--summary`, `--level`, `--map`,
`--json`; работает без Ghidra, только `.sbt`/`.sbw` + статический разбор).

Вопрос: `SET_SOURCESECTOR_*` (опкоды 27–31) и `SET_HANDLESECTOR_*` (40–45)
пишут массив `SECTOR_STUFF` (`0x800b60`, 256 × `0x58`) и/или запись сектора
мира (`0x5670d8`, шаг `0x18`), но **индекс слота в операндах отсутствует**.
Ниже: как он вычисляется (доказано дизасмом), что пишется, кто читает и что
из этого проверено на 36 поставочных уровнях.

Смежное, не дублируется: `docs/RECORDS.md` §2 — карта `SECTOR_STUFF`;
`docs/WORLD_FIELDS.md` §2.1/§2.6 — поля секторов; `docs/SECTOR_LIGHT.md` —
свет `sector+0x16` (там доказано, что `SET_*SECTOR_BRIGHTNESS` пишут **не**
`SECTOR_STUFF`); `docs/VM_EXEC.md` §3 — диспетчер и статусы команд;
`docs/ENTITY_FIELDS.md` §8 — таблица спящих подскриптов.

Все адреса — VA `gundx.exe` 1.36 (`ImageBase 0x400000`).

## 0. Короткий ответ

| опкод | команда | обработчик | индекс слота | статус |
|---:|---|---|---|---|
| 27 | `SET_SOURCESECTOR_MOVEMENT` | `0x457fc6` | `edi` = аргумент 3 `0x457390` («сектор источника»), `0..255` | доказано кодом, значение — рантайм |
| 28 | `SET_SOURCESECTOR_BRIGHTNESS` | `0x458063` | тот же `edi` → `0x42d8a5(edi)` | доказано кодом, значение — рантайм |
| 29 | `SET_SOURCESECTOR_FLAGS` | `0x458111` | тот же `edi` | доказано кодом, значение — рантайм |
| 30 | `SET_SOURCESECTOR_TYPE` | `0x4580a9` | тот же `edi` → `0x42d9d5(edi, v)` | доказано кодом, значение — рантайм |
| 31 | `SET_SOURCESECTOR_DAMAGE` | `0x4580cf` | тот же `edi` | доказано кодом, значение — рантайм |
| 40 | `SET_HANDLESECTOR_MOVEMENT` | `0x45829b` | `sector = 0x617fb8[i]`, где `0x5b1df8[i] == E` | **доказано и разрешено статически** (из `.sbt`) |
| 41 | `SET_HANDLESECTOR_BRIGHTNESS` | `0x4583a6` | то же; на каждый совпавший сектор — `0x42d8a5` | доказано + статически |
| 42 | `SET_HANDLESECTOR_TYPE` | `0x458429` | то же; `0x42d9d5` на каждый сектор | доказано + статически |
| 43 | `SET_HANDLESECTOR_DAMAGE` | `0x458486` | то же | доказано + статически |
| 44 | `SET_HANDLESECTOR_FLAGS` | `0x4584e7` | то же | доказано + статически |
| 45 | `SET_HANDLESECTOR_SOUND` | `0x45833a` | то же; `0x46b740(sector, …)` | доказано + статически |

Формулы (обе — из кода, не из документации):

```
SECTOR_STUFF   байт слота = index*11*8 = index*0x58   база 0x800b60
              0x457fdd lea ecx,[edi+edi*4]   ; 5i
              0x457fe9 lea edi,[edi+ecx*2]   ; i + 10i = 11i
              0x457fec shl edi,0x3           ; *8  -> 0x58
              0x4582c6/0x4582c9/0x4582cc     ; то же для хэндлов

world sector   байт записи = index*0x18               база 0x5670d8
              0x42d8c0 imul ecx,ecx,0x18 (геттер 0x42d8a5)
              0x42d9f7 imul edx,edx,0x18 (сеттер 0x42d9d5)
```

**Главный вывод.** Для семейства 27–31 слот — это **сектор источника**, т.е.
сектор сущности/события, запустившего подскрипт (не «сектор полигона» и не
первый аргумент команды). Для семейства 40–45 слот — это **номер сектора из
строки `SECTOR_HANDLE`** с тегом `E`; таблица читается из `.sbt` (тип 17),
поэтому здесь индекс разрешается статически для 1017 из 1023 команд.

## 1. Откуда берётся индекс: «сектор источника» (27–31)

### 1.1 `edi` — третий аргумент командной ВМ

```
457396  sub  esp,0x74
4573ab  mov  edi,[ebp+0x10]        ; edi = arg3
4573ae  mov  eax,[ebp+0x28]        ; arg9 (хэндл источника)
```

`0x457390` — исполнитель скрипта, 9 аргументов: `arg1` = смещение кода
(PC), `arg2` = «сколько тиков уже прошло», `arg3` = **сектор источника**,
`arg4`/`arg5` = объект/полигон источника, `arg6..arg9` — остальной контекст
(см. `docs/ENTITY_FIELDS.md` §8). Все пять обработчиков 27–31 используют
именно `edi` и больше ничего про сектор не спрашивают.

### 1.2 Кто и как передаёт arg3

| путь | адрес | что происходит |
|---|---|---|
| тикер/спящие слоты | `0x457305` (`mov ecx,[esi+0x5e3df0]`), `0x45734b` (`mov edx,[esi+0x616258]`), `0x457353` `push edx` | при пробуждении подскрипта его сохранённый сектор идёт в arg3 |
| `SLEEP` сохраняет контекст | `0x457739` `jg 0x45c43b` → `0x45c46c..0x45c4b3` (в т.ч. `0x45c4a5` `mov [ecx*4+0x616258],edi`) | шесть аргументов и хэндл складываются в слот 0..255; `offset < 0` = слот свободен |
| `GENERATE` (2, 3, 4) | `0x4575a3`: `0x4575bb push edi` → `0x479960` → `0x45fa00` | дочерний подскрипт получает **сектор родителя** (наследование), а не сектор созданной вещи |
| `0x45fa00` → ВМ | `0x45fabe` `mov edx,[esp+0x30]` (= arg2 `0x45fa00`), `0x45fac2 push edx` → arg3 `0x457390` | передача по цепочке без изменений |
| главный скрипт уровня | инициализационные вызовы (`0x442643`, `0x442655`, `0x442683`, `0x442695`, `0x4426a7`, `0x4428c7`, `0x443253`, `0x443265`, `0x443299`, `0x4432ab`, `0x4432bc`, `0x4432ce`) кладут в `arg2` регистр `ebx` — «пустое» значение (он же служит нулём в проверках `cmp [0x5a46d4],ebx`) | `offset 0` стартует с **сектором 0** — **гипотеза** (константы `push 0` для сектора в коде нет; `0x45fac3 push 0x0` — это `arg2` = «сколько тиков прошло», а не сектор) |
| события секторов | `0x44503f`/`0x445095` (чтение `slot+0x3c`/`+0x38`) → `event_post` `0x4795b0` (запись: байт типа, `+1` dword id, `+5` **word = сектор**, `0x479686`); декодер `0x479a3a` (`movsx esi,WORD PTR [ebx+…+4]`) → `0x479960(id, sector, …)` | скрипт, запущенный событием, получает **сектор, который это событие разместил** |

Событийный путь замыкает цепочку «сектор → скрипт → слот»: `SET_SECTOR_EVENTS`
(опкод 13, `0x4579ab`) кладёт два id в `slot+0x38/+0x3c` (`0x4579d6`,
`0x4579e0`); когда игрок оказывается в этом секторе, `0x4450xx` читает
`[slot+0x38]`/`[slot+0x3c]` и постит событие, передавая сектор
(`0x4450cf push eax`, где `eax = [0x81c27c]` = текущий сектор игрока);
`0x4795b0` пишет его 16-битным полем записи события, а `0x479a3a` отдаёт
обратно как `arg2` `0x479960` → `arg3` `0x457390`.

### 1.3 `SOURCE_IS_PLAYER` и `SOURCE_SWAP` — это **не** про сектор

Частое заблуждение: «`SOURCE_IS_PLAYER` даёт текущий сектор источника».
Нет — это условие второй ВМ (`0x45d120`), и оно смотрит на **хэндл**:

```
45d15b  mov edx,[esp+0x94]      ; адрес слота arg9 командной ВМ (хэндл)
45d162  mov eax,[edx]
45d164  and eax,0xffff
45d169  jl  ...                 ; < 0 -> false
45d16f  cmp eax,8               ; 0..7 = слоты игроков
45d172  jge ...
45d178  mov eax,1               ; true
```

То же у `SOURCEPLAYER_IS` (`0x45d185`, `[source] & 0xffff == operand`) и
`SOURCE_SWAP` (`0x45d1b3`: меняет местами 16-битные половины дескриптора и
требует новое младшее поле `< 0xa38`). Сектор в этих проверках не участвует —
он отдельный аргумент командной ВМ. Условие `SOURCESECTOR_FLAGS` (id 51,
`0x45ecd1`) — единственное, что читает `SECTOR_STUFF` по сектору:
`0x45ecfc mov ecx,[eax*8+0x800bb0]` затем `(flags & operand) == operand`.

### 1.4 «Нет сектора»

Если `arg3` вне `0..255` (например, подскрипт запущен из события, у которого
сектор не задан, или из движка с `-1`), поведение по обработчикам разное —
см. §3.3. Своего «сектора сущности» команда не ищет: геттеров «сектор по
объекту» здесь нет, вся работа с геометрией (`0x4360f1` точка → сектор)
происходит раньше, при спавне, и её результат лежит в экземпляре вещи
`+0x3c8` (`docs/THING_FIELDS.md` §4) — но в `0x457390` он не передаётся.

## 2. Откуда берётся индекс: `SECTOR_HANDLE` (40–45)

```
458356  mov eax,[esp+0x10]            ; E-операнд
45835a  mov ecx,[edi*4+0x5b1df8]      ; tags[i]
458361  cmp eax,ecx
458363  jne 0x458391                  ; нет break: обход до конца таблицы
458365  mov edx,[ecx*4+0x617fb8]      ; sector = sectors[i]
```

* счётчик — `0x5e3de0`, теги — `0x5b1df8`, секторы — `0x617fb8`, лимит
  `0x100` (`0x463825`); цикл идёт по **всем** строкам, поэтому один тег,
  записанный дважды, меняет оба сектора;
* таблица **читается из `.sbt`**: загрузчик записи 17 — `0x463900`
  (`fread u32 n` → `0x5e3de0`, затем `n*4` тегов в `0x5b1df8`, затем `n*4`
  секторов в `0x617fb8`); в `docs/LEVEL_LOAD.md` §4 тип 17 разрешён в режиме
  уровня (в отличие от 1/2/3/8/9/10/13/19);
* из текста (`SECTOR_HANDLE <тег> <сектор>`) таблицу добавляет `0x463820`
  — этот путь относится к сейвам/текстовому источнику, а не к `.sbt`.

> **Поправка к `docs/RECORDS.md` §2.5 и `docs/VM_EXEC.md` §3.1.**
> Там написано, что `SECTOR_HANDLE` «не строится из уровня» и в поставочных
> уровнях пуста, поэтому `SET_HANDLESECTOR_*` — no-op. Это неверно: запись
> типа 17 есть в **33 из 36** `.sbt` (`dm3`, `level0b`, `temple` — без неё),
> всего 900 строк; `0x463900` их читает. Данные: `level13` — 144 строки,
> `level9` — 127, `level4` — 119; см. §4.

## 3. Что именно пишется

### 3.1 Поля (проверено по инструкциям)

| опкод | цель | поля | адрес записи |
|---:|---|---|---|
| 27 | `SECTOR_STUFF` | `+0x00/+0x08/+0x10` = `move[0..2]` (`f64` из `fild` трёх `L`); `+0x18/+0x20/+0x28` = `extra[0..2]` (8 сырых байт каждого `A`) | `0x457fef`, `0x457fff`, `0x45800f`, `0x458019`, `0x458023`, `0x458032`, `0x45803c`, `0x45804b`, `0x458055` |
| 28 | запись сектора мира | `+0x16` = `light` (`u8` = младший байт `L`; читатель расширяет знаково) | `0x45807c` |
| 29 | `SECTOR_STUFF` | `+0x50` = `flags` | `0x458134` |
| 30 | запись сектора мира | `+0x14` = `kind` (`u16` = `value*6`, `0x42d9f1 imul ecx,ecx,6`) | `0x42d9ff` |
| 31 | `SECTOR_STUFF` | `+0x40` = `v & 0xffff`, `+0x44` = `v >> 16` (арифм.) | `0x458100`, `0x458106` |
| 40 | `SECTOR_STUFF` | как 27 | `0x4582cf`, `0x4582d9`, `0x4582e3`, `0x4582ed`, `0x4582f7`, `0x458301`, `0x45830b`, `0x458315`, `0x45831f` |
| 41 | запись сектора мира | `+0x16` | `0x4583f1` (через `0x42d8a5`) |
| 42 | запись сектора мира | `+0x14` | `0x42d9ff` (через `0x42d9d5`) |
| 43 | `SECTOR_STUFF` | `+0x40`, `+0x44` | `0x4584c0`, `0x4584cc` |
| 44 | `SECTOR_STUFF` | `+0x50` | `0x458523` |
| 45 | `SECTOR_STUFF` | `+0x48`, `+0x4c`, `+0x30` (через `0x46b740`) | `0x46b760/0x46b76a/0x46b774/0x46b77a` |

`+0x18/+0x20/+0x28` (`extra`) пишутся, но читателей в билде нет
(`docs/RECORDS.md` §2.2) — инструмент подтверждает: все *абсолютные* ссылки
на `0x800b78..0x800b8c` в `gundx.exe` — записи (18 инструкций `mov [mem],reg`
в 8/27/40 плюс обнуление в `0x46b1b0` через регистр).

### 3.2 Значение — младший байт для света

`28`/`41` кладут в `+0x16` только младший байт `L`-операнда
(`0x458079 mov dl,[edx+ecx]`), поэтому `-72` (`0xffffffb8`) и `184`
(`0x000000b8`) неразличимы: в поле попадает `0xb8`, читатель `0x43ca48`
(`movsx`) видит `-72`. Для `30`/`42` значение — `u16` и умножается на 6.

### 3.3 Границы и отказы (асимметрия!)

| опкод | проверка | при выходе за диапазон |
|---:|---|---|
| 27 | `0x457fc6 test edi,edi` / `0x457fd4 cmp edi,0x100` | `0x45899a`: **молча** пропускает `0x24` (= размер операндов `LLLAAA`) |
| 28 | `0x42d8a5`: `0 <= i < [0x5670dc]` | `0x45808d`: печать `Script run error: unable to obtain sector %ld.` (`0x4b85cc`), записи нет |
| 29 | `0x458111` / `0x458119` | `0x45c36a`: молча пропускает 4 байта |
| 30 | `0x4580a9` / `0x4580b1`, затем `0x42d9d5` | `0x45c36a` либо `0x42d9d5 -> -1` (без сообщения) |
| 31 | `0x4580d5` / `0x4580e0` | `0x45c41b`: молча (операнд уже прочитан) |
| 40, 43, 44 | **нет** | запись по `0x800b60 + sector*0x58` «как есть» |
| 41, 42 | `0x42d8a5` / `0x42d9d5` на каждый сектор | 41 — сообщение (`0x4583f6`), 42 — `-1` без сообщения |
| 45 | `0x46b740`: `0 <= i < 0x100` | `0x46b791`: `Sector sound sector number (%ld) greater than max …` (`0x4ba864`) |

То есть **40/43/44 не проверяют сектор из таблицы вообще** (ни загрузчик
`0x463900`, ни обработчик): испорченный `SECTOR_HANDLE` с `sector > 255`
пишет за пределы `SECTOR_STUFF`. В поставочных данных этого нет — все
разрешённые секторы `< числа секторов .sbw` (`--self-test`, «0 вне мира»).
В C++ (`engine/src/res/vm_exec.cpp::write_sector_stuff`) такая проверка есть
и это **осознанное отличие**: комментарий фиксирует поведение оригинала.

### 3.4 Особенность `SET_HANDLESECTOR_SOUND` (45)

Вызов общий с `SET_SECTOR_SOUND` (12) — `0x46b740`, который раскладывает
аргументы так: `a2 -> slot+0x48` (`sound`), `a3 -> slot+0x4c`
(`sound_count`), `a4/a5 -> slot+0x30` (`sound_param`, две половины `f64`).
Опкод 12 передаёт `(sector, N, V, D.lo, D.hi)` (`0x4579f6..0x457a06`:
`[8]=N` → `a2`, `[4]=V` → `a3`), а опкод 45 — `(sector, E, N, V, D.lo)`
(`0x458372` `mov ecx,[ebx+esi]` = `E` → `a2`, `0x45836d/0x458375` `N` → `a3`,
`0x458369/0x458371` `V` → `a4`, `0x458365/0x458371` `D.lo` → `a5`). Значит
`SET_HANDLESECTOR_SOUND` пишет в `+0x48` **тег** `E`, в `+0x4c` — `N`, а в
`+0x30` — «двойное» из `(V, D.lo)`.

Это **доказано кодом**; трактовка «ошибка оригинала: задумано как op 12»
остаётся гипотезой (§8.2). Практическое следствие ограничено: `45` — не
основной путь звука (`SET_SECTOR_SOUND` в данных 2329 команд, `45` — 489).

## 4. Потребители: что читает слот

Все ссылки на `0x800b60..0x800bb8` в `gundx.exe` (65 инструкций; список можно
воспроизвести `grep -o '0x800b..'` по листингу):

| поле слота | читатель | что делает |
|---|---|---|
| `+0x00/+0x08/+0x10` `move` | `0x4713ab`, `0x4713cc`, `0x4713ed` (в `0x470c70`) | `pos += move*dt` для вещи |
| `+0x18..+0x28` `extra` | — | читателей нет |
| `+0x30` `sound_param` | `0x46c6cd` (в `0x46c5c0`) | `volume = f(расстояние) − count*sound_param` |
| `+0x38/+0x3c` `event_a/b` | `0x44503f`, `0x445095` | `event_post` при входе в сектор |
| `+0x40/+0x44` `damage_a/b` | `0x4450f6`, `0x4450fc` | `imul` на `dt` → два первых аргумента `0x453b50` |
| `+0x48/+0x4c` `sound/count` | `0x46c5f3`, `0x46c5fd`, `0x46c644` | ambient-сэмпл сектора и его громкость |
| `+0x50` `flags` | `0x45ecfc` (`SOURCESECTOR_FLAGS`), `0x46bcde`/`0x46c18c`/`0x46c41b` (сдвиг громкости), `0x4727cb` (бит `0x10`), `0x444166` (бит `1`) | геймплей |

### 4.1 `0x470c70` — движение вещей (слот `move`)

```
470c79  mov ecx,[ebp+0x8]            ; индекс вещи
470c80  shl ebx,0x5 / add ... / lea / shl 0x3   ; ebx = slot*0x148 (0x7ac080)
470c8c  test DWORD PTR [ebx+0x7ac3e4],0x20000  ; мёртвая вещь -> выход
471376  call 0x42efc3                ; сектор вещи по позиции (0x4360f1)
47137e  mov [ebx+0x7ac448],eax       ; -> поле «сектор»
47138c  cmp eax,0x100 / jge выход    ; 0..255
471397  mov ecx,[ebx+0x7ac3e4]
47139d  test ch,0x8                  ; флаг 0x800 = «сектор двигает»
4713ab  fld QWORD PTR [eax*8+0x800b60]   ; move[0]
4713a2  fild DWORD PTR [ebp+0xc]    ; dt — целое (второй аргумент 0x470c70)
4713b2  fmul st,st(1)                ; move * dt
4713b4  fadd QWORD PTR [ebx+0x7ac238]    ; += pos.x
4713cc/0x4713ed  то же для +0x08/+0x10
```

Порядок: сначала пересчитывается сектор вещи (`0x42efc3`), затем (если у
вещи флаг `0x800`) применяется `move` этого сектора. `dt` — целое из
`[ebp+0xc]` (`fild`), единицы — тик/мс тикера, здесь не уточняются.

### 4.2 `0x453b50` — урон (слот `damage_a/b`)

`0x453b50` — общая функция «нанести урон игроку» (щит/броня/сложность,
приёмник `0x81c240` и т.п.); `SECTOR_STUFF` она **не читает** (в её теле нет
ни одной ссылки на `0x800b..`). Значения приходят уже посчитанными:

```
4450f6  mov eax,[ecx+0x800ba0]    ; damage_a  (ecx = slot*0x58)
4450fc  mov ecx,[ecx+0x800ba4]    ; damage_b
445102  imul eax,edx              ; * dt
445105  imul ecx,edx
445113  push 0xffffffff / push ecx / push eax ...   ; -> 0x453b50
```

То есть слот задаёт «сколько урона в тик получает игрок, находящийся в этом
секторе»; `SET_SOURCESECTOR_DAMAGE` (31) и `SET_HANDLESECTOR_DAMAGE` (43) —
единственные писатели (в поставке 0 и 21 команда соответственно).

### 4.3 `0x46c5c0` — ambient-звук (слот `sound/count/param`)

```
46c5ea  lea ecx,[eax+eax*4] / lea eax,[eax+ecx*2] / shl eax,0x3   ; slot*0x58
46c5f3  mov ecx,[eax+0x800bac]     ; +0x4c sound_count
46c5f9  test ecx,ecx / jle ...     ; 0 -> сектор не звучит
46c5fd  mov edx,[eax+0x800ba8]     ; +0x48 sample
...
46c649 (фолбэк) цикл по секторам 0..min([0x5670dc],0x100):
46c64c  cmp [esi],0 / jle next                ; +0x4c <= 0 -> мимо
46c652  test BYTE PTR [esi+0x4],0x8           ; +0x50 бит 3 -> мимо
46c65c  mov eax,[esi-0x4] / test / jl         ; +0x48 < 0 -> мимо
46c6a4  call 0x43554d                        ; расстояние игрок-сектор
46c6cd  fmul QWORD PTR [esi-0x1c]             ; * +0x30 sound_param
46c6d0  fsubp st(1),st                        ; f(расстояние) - count*param
46c6dd  выбор максимума (самый громкий сектор)
```

### 4.4 Свет — это **не** `SECTOR_STUFF`

`SET_SOURCESECTOR_BRIGHTNESS` (28) и `SET_HANDLESECTOR_BRIGHTNESS` (41)
кладут байт в `world_sector+0x16` (`0x45807c` / `0x4583f1`), а не в
`0x800b60`. Читатель суммы — `0x43ca32..0x43ca4c`:

```
43ca32  movsx ecx,BYTE PTR [eax+0x70]   ; poly.brightness
43ca3c  movsx eax,BYTE PTR [edx+0x74]   ; object.brightness_bias
43ca48  movsx eax,BYTE PTR [edx+0x16]   ; sector.light  (эта команда)
43ca4c  add ecx,eax                     ; сумма, затем clamp -128..127
```

Это ровно то, что уже доказано в `docs/SECTOR_LIGHT.md` §2 — здесь
подтверждается независимо: три «световых» опкода (9, 28, 41) пишут **не**
`SECTOR_STUFF`, и `tools/re/sector_stuff.py` показывает разные наборы слотов
для «SECTOR_STUFF» и «world sector» (колонки SS / WS в `--summary`).
Вершины/яркость зависят от `SECTOR_STUFF` только косвенно — через `move`
(позиции вещей → их мировые трансформы), не через цвет.

`gundx.exe`/листинг, иначе `skip`):

1. арифметика слота (`i*11*8 == i*0x58`, `256*0x58 == 0x5800`);
2. имена/сигнатуры 27–31/40–45 против оракула `gm.sbtvm`;
3. диспетчер `0x45c500[op-1]` = обработчик (10/10);
4. байты формул: `0x457fdd/0x457fe9/0x457fec` (27) и
   `0x4582bc..0x4582cc` (40);
5. наличие/отсутствие проверок границ (27/29/31 есть, 40/43/44 нет);
6. `41` пишет `[eax+0x16]` через `0x42d8a5`; `45` берёт сектор из
   `[edi*4+0x617fb8]`;

## 7. Доказано / гипотеза / осталось

**Доказано кодом**: диспетчер и обработчики 27–31/40–45 (§0, §3.1);
формула слота `index*0x58` и записи `0x18` (§0); источник = `arg3 0x457390`
и все пути его передачи (§1.2); `SECTOR_HANDLE` читается из `.sbt`
(`0x463900`), лимит `0x100`, обход без `break` (§2); отсутствие проверок
границ у 40/43/44 (§3.3); поля `+0x16`/`+0x14` — запись сектора мира, а не
`SECTOR_STUFF` (§3.1, §4.4); потребители `move`/`damage`/`sound`/`events`/
`flags` (§4).

**Доказано данными** (36/36 уровней): числа §5; 33 уровня с непустой
таблицей `SECTOR_HANDLE` (900 строк); 6 команд с несуществующим тегом;
16 команд с однозначным сектором источника (`level16`); записей
`SECTOR_STUFF` (тип 8) в поставочных `.sbt` нет.

**Гипотезы и остатки:**

0. **Сектор 0 у главного скрипта** — гипотеза (§1.2): доказан только
   событийный путь. Если он не 0, меняется лишь множество возможных секторов
   у двух неоднозначных команд `level15` (оно и так неоднозначно), выводы §5
   не затрагиваются.
1. **Сектор источника у 552 команд** статически не выводится: их блоки
   запускаются движком (переключатели/вещи/предметы), а не `GENERATE` и не
   событием сектора. Нужен событийный прогон (или трасса `0x4795b0`) —
   статики недостаточно. Инструмент помечает такие команды
   `complete=false` и **не** выдумывает номер.
2. **Опкод 45** передаёт в `0x46b740` `(sector, E, N, V, D.lo)`, тогда как
   `12` — `(sector, N, V, D.lo, D.hi)`. Похоже на ошибку оригинала
   (задумано как у `12`), но это гипотеза о замысле; сама раскладка
   аргументов доказана (`0x458365..0x458380`).
3. **C++ `vm_exec.cpp` (op 12/45)**: `slot.sound = args[0]` (= `V`),
   `sound_count = args[1]` (= `N`). По asm наоборот: `+0x48` ← `N`,
   `+0x4c` ← `V`. Нужна сверка автором `vm_exec.cpp` (`docs/RECORDS.md` §2.3
   повторяет ту же перестановку, тогда как §2.2 описывает поля верно).
   В этом инструменте C++ не менялся (задача — только новые файлы).
4. **`SET_HANDLESECTOR_*` в C++** уже проверяет `0..255`, оригинал — нет
   (§3.3): отличие задокументировано в комментарии `vm_exec.cpp`.
5. **`docs/RECORDS.md` §2.5 / `docs/VM_EXEC.md` §3.1** утверждают, что
   `SECTOR_HANDLE` в поставке пуста — это опровергнуто (§2). Доки не
   правились (условие задачи: только новые файлы); поправку нужно внести
   основному агенту.
6. **`INDEX.md`** не обновлён (генерируется `tools/ctx.py index`).
