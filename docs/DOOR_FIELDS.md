# Поля дверей, переключателей и лифтов (M2.3.4)

Карта **runtime-записей** и того, что из них читает `engine/src/world/doors.*`.
Разбор — по `gundx.exe` (ImageBase `0x400000`, Ghidra 12.1.4) и по 36
поставочным `.sbt`/`.sbw` (только чтение). Инструмент —
`tools/re/door_fields.py`; модель C++ и её golden'ы — `docs/DOORS_CPP.md`,
формат `.sbt`/сейва — `docs/RECORDS.md` §4 и `docs/SAVE_FIELDS.md` §3/§4.

Статусы: **код** — адрес инструкции доказывает поле/потребителя; **данные** —
проверено на поставке; **гипотеза** — смысл правдоподобен, но кодом не
доказан.

### 1.1. Фаза, направление, группа, авто-закрытие

* Фаза живёт в **`0..0xffff`**, а не `0..65536`: `0x44f335..0x44f349`
  зажимает в `0..0xffff`, множитель `0x44f371` равен `1/65535`
  (`1.5259021896696422e-05`), а не `1/65536`. При `phase = 0xffff` доля ровно
  `1.0`. C++ держит счётчик до `65536` (это удобная граница `step`-арифметики),
  но геометрия берёт `min(phase, 0xffff)`. В поставе все 1779 дверей стартуют с
  `phase = 0`.
* `0x44f2e0` каждый тик: `+0x90 = +0x8c + state * step * dt`, clamp
  `0..0xffff` (`0x44f335..0x44f349`). Дальше считает **вектор движения**
  `(open-closed) * (phase_next-phase_prev)/65535` и вызывает
  `0x434f72(sector, object, dx, dy, dz)`, который пишет эти три `f64` в
  `obj+0x90/+0x98/+0xa0` — это тот же слот, что пишет
  `0x434e32` (`engine_setobjectmvector`): **вектор смещения объекта за кадр**.
  Потребители: `0x437d05` (луч освещения, компенсация сдвига),
  `0x434fed` (AABB сектора расширяется в сторону движения),
  `0x440867` (бит «в секторе есть движущийся объект»). В
  `docs/WORLD_FIELDS.md` §2.2 поле названо `extent`; это одна и та же память,
  но писатель у неё есть — двери и кабины лифтов.
* `0x44f3f0` фиксирует `+0x8c = +0x90`, крутит таймер `+0x9c`
  (`0x44f5f8..0x44f605`), при полном открытии (`phase > 0xfffe`) ставит
  `+0x9c = +0x98` (`0x44f54d/0x44f550`) и вызывает `0x44dfc0` — пересчёт
  трансформа створки (§1.2). События: `event_post(ids[3], sector, object, 0,
  origin, -1)` на открытии (`0x44f572`), `event_post(ids[4], …)` на закрытии.
  На каждом конце — звук остановки `v2/n2`.
* `0x44f690` по id переключателя перебирает **все** двери; id сравнивается
  с `ids[0..2]` (`+0x6c/+0x70/+0x74`), двери с `kind == 0` пропускаются
  (`(flags & 0xf) != 0`):
  * `ids[0]` — обычный toggle: если `state==+1` или `phase==0xffff` →
    `-1`, иначе `+1` (`0x44f6c0..0x44f6e5`);
  * `ids[1]` — только открыть, если `phase < 0xffff` (`0x44f6ee..0x44f701`);
  * `ids[2]` — только закрыть, если `phase > 0` (`0x44f706..0x44f710`).
  Одновременно `+0x9c = 0` (`0x44f725`) — таймер сбрасывается, и играется
  звук запуска `v0/n0` (`0x44f66b`). Это и есть «группа»: отдельного поля
  группы нет, группа = совпадение id.
* `(sector, object)` — адрес створки в `.sbw`; `0x434419` идёт по таблице
  `ds:0x5670d8` (stride `0x18`: `{count, pointer}`), индекс объекта —
  второй уровень. В поставке пары валидны **1779/1779**, все **1779**
  различны.
* `ids[3]`/`ids[4]` — **id событий**, а не «связь створок»: `0x44f3f0`
  постит их через `event_post` (с `source = -1`) в момент полного
  открытия/закрытия. В поставе `ids[3] != 0` у 200 дверей, `ids[4] != 0` у
  182. C++ хранит их как `Door.event_open`/`Door.event_close`; поле `linked`
  оставлено как прежний алиас `ids[3] != 0` (на него завязаны счётчики).
* `0x450590` — **реакция на препятствие**: вызывается из коллизии сущностей
  (`0x4392de`, `0x43abb7`) с `(sector, object)`; `0x450550` находит дверь:
  * `kind == 1` — ничего (обычная дверь);
  * `kind == 2` — `state = +1`, `+0x90 = +0x8c` (тик отбрасывается, дверь
    едет обратно);
  * `kind == 3` — `+0x90 = +0x8c` и `event_post(-22, sector, object, 0,
    точка створки, source)` — crush-событие (`0x44f..`, `0x4795b0`).
  То есть игрок в проёме не «толкает» створку, а отменяет её ход.

### 1.2. Геометрия створки (как двигается объект `.sbw`)

Единственный писатель origin/базиса объекта в мире — `0x434887`; его
вызывает только `0x44dfc0` (создание `0x44e4ad`, тик `0x44f3f0`, отладка
`0x4673d0`, `0x44f260`). Порядок (проверено по asm `0x44dfc0..0x44e23f` и
`0x434887`):

1. `frac = phase(+0x8c) / 65535`;
2. `center[k] = closed[k] + (open[k] - closed[k]) * frac`, где `closed/open` —
   **уже сложенные** с `size` углы (`+0x00 += +0x30` в загрузчике
   `0x44e368..0x44e3f6`);
3. ось вращения: если `axis[2] != 0` → ось `z`, иначе если `axis[0] != 0` →
   `x`, иначе если `axis[1] != 0` → `y`, иначе вращения нет. Единичный
   вектор оси: `-x`, `+y`, `-z` (три ветки `0x44dfc0`);
4. `angle = axis[i] * phase` (без деления — `axis[]` уже `/65535`);
5. `0x434887` строит базис как поворот на `-angle` вокруг этой оси
   (`FPU` `FSIN`/`FCOS` через `0x480314`/`0x480954`, матрица
   `[x²t+c, xy·t+z·s, xz·t-y·s; …]`, `t = 1-c`), складывает строки в
   `obj+0x18..0x60`;
6. `origin = center - basisᵀ * size` (asm: `obj+0x00 = center_x - (b0·sx +
   b3·sy + b6·sz)` и т.д.), `obj+0x00..0x18`;
7. при `phase == 0` дополнительно `0x434b71`: полигонам возвращаются
   «авторские» `+0x54/+0x58` (сдвиг `short << 7`).

Следствия:

* у 1422 из 1779 дверей все три `A` равны нулю → базис единичный, створка
  просто едет по `closed → open` (это и есть «скользящая» дверь);
* у 357 дверей есть угол: 147 выбирают `x`, 113 — `z`, 97 — `y`; при
  нескольких ненулевых `A` работает приоритет `z > x > y`, остальные
  компоненты игнорируются;
* углы в данных — `0`, `±π/2`, `±0.349`, `2π` (полный оборот) и т.п.;
* `origin` при `phase = 0` равен ровно исходному углу `D1..D3`, потому что
  `center = D1 + size` и вычитается `basisᵀ·size = size`. Это проверено на
  всех 1779 дверях корпуса (`doors_full`).

В C++: `door_transform(door)` / `door_transform_at(door, phase)` →
`DoorTransform{origin, basis, center, axis, angle}`; `apply_to_objects()`
отдаёт его в `ObjectDoorState::transform`. `door_motion_delta(door, prev,
next)` — тот самый вектор `obj+0x90`.

### 1.3. Звук двери: что, когда и с какими параметрами (доказано дизасмом)

Движок не микширует звук на месте: он кладёт **запрос** в очередь 3D-звука
`0x62ce18` (шаг `0x2c`, счётчик `0x62fa18`, максимум **256** записей — проверка
`DAT_0062fa18 < 0x100` в `0x46b8d0`), а микшер `0x46bed0` разбирает её позже.
Разбор записи (`0x46b8d0`/`0x46b840`/`0x46b9f0`/`0x46ba90`):

| off | поле | кто пишет | доказательство (адрес записи) |
|---|---|---|---|
| `+0x00` | f64 `atten` — затухание на единицу расстояния | 8-й/9-й аргумент `0x46b8d0`/`0x46b9f0`; `0x46b840` пишет константу `0.03` | `0x46b941`/`0x46b937`, `0x46ba6f`/`0x46ba75`, `0x46b8ad`/`0x46b8b7`; формула `volume − atten*dist` — `0x46c243..0x46c258` |
| `+0x08/+0x0c/+0x10` | i32 `x/y/z` | 5-й/6-й/7-й аргументы | `0x46b8f0`, `0x46b8f6`, `0x46b900` (`0x62ce20/24/28`) |
| `+0x14` | u32 `class` — ключ 3D-источника | `0x46b8d0`/`0x46b840`: **0**; `0x46b9f0`: 2-й аргумент; `0x46ba90`: единственный аргумент | `0x46b90c` (`XOR EDX,EDX`), `0x46b87c`, `0x46ba33`, `0x46baac` |
| `+0x18` | u32 `sample_id` — индекс `SOUND_SAMPLE_TABLE` | 1-й аргумент всех трёх | `0x46b912`, `0x46b882`, `0x46ba3d` (`0x62ce30`) |
| `+0x1c` | u32 `volume` — **базовая** громкость | 2-й аргумент `0x46b8d0`/`0x46b840`, 3-й аргумент `0x46b9f0` | `0x46b91d`, `0x46b88d`, `0x46ba47` (`0x62ce34`); чтение `0x46c246` |
| `+0x20` | u32 `rate` | 3-й/4-й аргумент | `0x46b927`, `0x46b897`, `0x46ba51` (`0x62ce38`) |

кладится последним):

| функция | аргументы | class | loop |
|---|---|---|---|
| `0x46b8d0` | `(sample, volume, rate, priority, x, y, z, atten)` | 0 | 0 |

Позиция `x/y/z` — всегда **целые**: координаты объекта/точки читаются как
`double` и режутся `0x40e0e0` (`__ftol`) в тройку `int`.

| **движение (петля)** | `0x44f5ee` (`0x44f3f0`) | `n1`/`v1` (1-й/3-й арг. `0x46b9f0`), class = `1000000 + индекс двери` (`0x44f5e5`: `LEA EAX,[EBX+0xf4240]`), rate `0x2b11`, priority `1000`, позиция = origin створки, `atten` = `+0x60` | **каждый тик**, пока `state != 0` (`0x44f598`) |
| **остановка** | `0x44f4b1` (закрылся) и `0x44f53e` (открылся) | `n2`/`v2` (1-й/2-й арг. `0x46b8d0`) | фаза дошла до 0 или `0xffff` |
| **стоп петли** | `0x44f5a6` → `0x46ba90` | class = `1000000 + индекс двери` | каждый тик, пока `state == 0` |

Все пять вызовов закрыты глобальным флагом `0x4aa384` (звук выключен → ничего
не играет) и требуют, чтобы `0x434419(sector, object)` вернул створку.

**Crush (`0x450590`) звука не производит**: в ветках kind 2 (`0x450696`) и
kind 3 (`0x4506cf`) нет ни одного вызова звуковой функции — только
`event_post(-22, …)` (`0x45065f`/`0x450787`) и сброс фазы. Слышно только то,
что играет сама дверь (петля движения/старт/стоп).

**Переключатель (`0x44f960`)** — единственный вызов `0x46b840` (две ветки:
`0x44f9f7` при `kind < 0x101` и `0x44fab7` при `kind >= 0x101`):

* условие: `sound (+0x1c) >= 0` (`0x44f9ca`) и `0x4aa384 != 0`;
* `sample` = `+0x1c`, `volume` = `+0x18` (2-й аргумент `0x46b840` → `+0x1c`
  очереди → формула `volume − atten*dist`), rate `0x2b11`, priority `1000`;
* позиция: при `kind < 0x101` — мировые `x/y/z` операндов (`0x44f9dc`);
  при `kind >= 0x101` — **центроид полигона** `0x43577c` (`0x44fa05`),
  тоже режется в `int`;
* `atten` = 0.03 (константа внутри `0x46b840`), class = 0, loop = 0;
* звук играется **после** `generate_event` и не зависит от того, нашлась ли
  дверь/лифт по `target`.

Данные поставки (36 уровней, только чтение):

| величина | значение |
|---|---|
| `n0 >= 0` / `n1 >= 0` / `n2 >= 0` | **523 / 864 / 626** из 1779 дверей |
| диапазон sample | `0..206` (все < 300 — размер `SOUND_SAMPLE_TABLE`) |
| диапазон volume | `0..64` |
| `switch.sound` (`+0x1c`) | `>= 0` у **1620** из 3964, `-1` у 2344 |
| `switch.aux` (`+0x18`) | `0..64`, 13 разных значений |

В C++: `SoundRequest`/`SoundSource` и очередь `WorldState::drain_sounds()`
(`docs/DOORS_CPP.md` §3.3) — переносимая копия этого описания: запрос рождается
в тех же переходах, что и `WorldEvent`, несёт `sample/volume/position/loop`,
и не дублируется (курсор, как у `post_door_events`).

## 2. Запись переключателя `SWITCH` / `0x5a4af0`, `0x20`

Все восемь dword'ов пишутся дословно в `0x44e5f0` (счётчик `0x5a945c`).
Отдельного `pressed`/cooldown/`source` в записи **нет**.

| смещ. | тип | смысл | кто читает/пишет (адреса) | статус |
|---|---|---|---|---|
| `+0x00` | i32 | `kind` | `0x44f960` (`<0x101` / `>=0x101`), `0x44fc30` (`0/1/0x101`), `0x44fad0` (`0x102`), `0x44fb30` (`0x102/0x103`), `0x44fbd0` (`0x104`) | код, данные |
| `+0x04` | i32 | `target` — id для `GENERATE` | `0x44f960` → `generate_event` `0x479960`; `0x44fbd0`; **перезапись** `0x44e680` (опкод `0x24`) | код, данные |
| `+0x08` | i32 | `radius` / максимальная дистанция | `0x44fc30` (октагон, kind 0/1); `0x44fc30` (длина луча, kind `0x101`); `0x44fb30` (евклид до полигона, `0x102/0x103`) | код, данные |
| `+0x0c` | 3 × i32 | **полиморфно**: `kind 0` — мировой `x/y/z`; `kind >= 0x101` — `(sector, object, polygon)` | `0x44fc30`, `0x44f960` (`0x43577c`), `0x44fb30`, `0x44fad0`, `0x44fbd0`, `0x44e680` | код, данные (§2.2) |
| `+0x18` | i32 | `aux` — **базовая громкость** звука переключателя | 2-й аргумент `0x46b840` в `0x44f960` → `+0x1c` 3D-очереди → `volume − atten*dist` (`0x46c246`) | код, данные |
| `+0x1c` | i32 | `sound` — индекс `SOUND_SAMPLE_TABLE`, `-1` = тишина | 1-й аргумент `0x46b840`/`0x46b8d0` в `0x44f960`; проверка `sound >= 0` — `0x44f9ca` | код, данные |

Семантика `kind` (по веткам потребителей):

| kind | смысл | доказательство |
|---|---|---|
| `0` | proximity игрока: октагон `0x4344df(player.pos − pos) < radius`; `pos` — **мировые** координаты | `0x44fc30`, ветка `piVar6[-1]==0` (§2.2) |
| `1` | proximity к створке двери, найденной по id (id = `ids[0..2]`) | `0x44fc30`, ветка `==1` |
| `0x101` | прицел: луч `0x43c51f` из камеры игрока, попадание должно дать ровно `(sector, object, polygon)` из операндов 4..6 и `distance <= radius` | `0x44fc30`, ветка `0x101` (§2.2) |
| `0x102` | proximity к полигону (евклид `0x43e541`), плюс точное совпадение тройки из внешнего события (`0x44fad0`) | `0x44fb30` (вызов из опкода 75), `0x44fad0` |
| `0x103` | то же proximity к полигону, без exact-ветки | `0x44fb30` |
| `0x104` | точное совпадение тройки `(sector, object, polygon)` с переданной точкой, затем событие с source | `0x44fbd0` |

Во всех `kind >= 0x101` операнды 4..6 — **не координаты**, а индексы
полигона: из 3433 таких переключателей поставки все 3433 указывают на
существующий полигон (проверено `tools/re/doors.py --frame`).

* `repeat`: в `0x44fc30` нет latch/cooldown — пока условие выполнено,
  событие type-2 пишется **каждый вызов** (кадр/тик). C++ `Switch.pressed`
  — состояние модели, в файле его нет; `Switch.inside` — последний ответ
  `poll_triggers`, чтобы вызывающий мог сделать фронт сам. Защёлку (если она
  нужна) держит **скрипт уровня**, а не переключатель.
* `source`: пишется в событие type-2 (`0x479810`: тип `2`, `u32 switch_index`
  по `+1`, `u16 source` по `+5`), затем `0x44f960` передаёт source в
  `generate_event` как `param_2 - 0x10000`. Это индекс игрока/источника,
  а не поле записи.
* `pressed` в C++ сбрасывается в конце следующего `tick`; на запись `0x20`
  не отображается.

### 2.1. Триггерная цепочка (кто открывает дверь)

```
игрок в радиусе (kind 0/1) ─┐
выстрел/прицел  (kind 0x101) ┼→ 0x479810 (type-2: switch_index, source)
точка из скрипта (0x104)  ──┘        │
                                     ▼
                    0x44f960(switch_index, source)
                    ├─ generate_event(target, pos…, source-0x10000)
                    └─ звук переключателя (+0x1c sample / +0x18 volume)
                                     │
                          скрипт уровня (SCRIPT / VM)
                                     │  GENERATE(id)
                                     ▼
                              0x44f690(id):
                     ├─ ids[0..2] совпали → state = ±1, timer = 0, звук v0/n0
                     └─ call-id лифта   → остановка/направление
```

* **`0x44fc30`** (раз в кадр на сущность, `param_1` — индекс игрока) идёт по
  массиву переключателей:
  * `kind == 0`: `dist_окт(player.pos, sw.pos) < radius(+0x08)`.
  * `kind == 1`: находит **первую** дверь, у которой `ids[0..2] == target`,
    берёт `origin` её объекта (`0x434419`) и сравнивает расстояние до него с
    радиусом.
  * `kind == 0x101`: только через прицел — `0x43c51f` (луч по миру) плюс
    сравнение `sector/object/poly` и `local_58 <= radius`; позиции
    недостаточно (§2.2). Луч строит `0x41e025` из углов записи игрока
    (`0x819058..0x81906c`): в `0x43c51f` идёт **второй** выход (`local_50`) —
    forward базиса (`gm::camera_basis`), начало — глаз (`0x81c1b8`).
    Дальность луч не клампит: `0x43c51f` стартует с double `1e38`
    (`0x47d2ced3_2a16a1b1`), а принимает попадание по радиусу switch
    (`+0x08`). C++ — `GameRuntime::aim_switch_from_basis/from_camera`
    (`max_distance` — внешняя граница, `docs/CAMERA.md` §3,
    `docs/DOORS_CPP.md` §2.3).
  * `kind == 0x102/0x103` в `0x44fc30` **не участвуют**: их тикает
    `0x44fb30`, который вызывается из опкода 75 (взрыв) — см. §2.2.
  * Лифты: `dist(entity, модель кабины) < +0x80` → `event_post(+0x7c, …)`.
* Метрика расстояния — **не евклидова**: `0x4344df` возвращает
  `max + (mid + min) / 4` по модулям компонент (октагон). Поэтому точка
  `(0.75r, 0.75r, 0.1r)` уже внутри радиуса, хотя евклидово расстояние
  `1.065r`.
* **`0x44f960`** (обработчик type-2): `target = sw+0x04`; для `kind < 0x101`
  `generate_event(target, 0,0,0, sw.pos, source)`; для `kind >= 0x101` —
  `0x43577c` (преобразование позиции) и `generate_event(target, pos, source)`.
  Плюс звук переключателя, если `sound >= 0`.
* **`0x44fbd0`** (`kind == 0x104`): точное совпадение трёх `int` позиции
  (не радиус), затем `0x479810(index, param_4)`.

C++: `interact(id)` / `interact(id, source)` — это `0x44f960`+`0x44f690`
(скрипт уже разрешён в `target`); `poll_triggers(pos, source)` — половина
`0x44fc30` для `kind 0/1`; `poll_aim(PolygonHit, source)` — прицельная
половина `0x44fc30` (`kind 0x101`, точная тройка + `t <= radius`);
`poll_blast(PolygonHit, source)` — `0x44fb30` (`kind 0x102/0x103`, точная
тройка + `d <= radius`, вызывающий считает евклид `0x43e541`);
`trigger_poly(PolygonHit, source)` — `0x44fad0` (`kind 0x102`, только точная
тройка, без дистанции);
`trigger_at(pos, source)` — `0x44fbd0`;
`block_contact(sector, object)` — `0x450590`. Событийная половина
(`event_post(ids[3]/ids[4])` при полном открытии/закрытии) модель только
логирует (`WorldEvent::target`), диспетчеризация — дело `game/events.*` +
VM.

### 2.2. Два смысла операндов 4..6 (закрывает «кадр 1.875»)

Раньше считалось, что операнды 4..6 — позиция, которая «численно совпадает с
`1.875·local`» для 85 % переключателей. Это ошибка чтения: совпадение
возникало потому, что для большинства переключателей там лежат **маленькие
индексы** полигона, и они случайно оказывались рядом с локальными
координатами вершин.

Доказательства по байтам:

* `0x44fc30`, ветка `kind == 0`: `FUN_004344df(player.pos −
  (double)op4..6) < (double)op3` — позиция игрока читается как `double`
  (`player+0x00/0x08/0x10`, страйд `0x3510`), операнды — как `int`. Никакого
  масштаба нет.
* `0x44fc30`, ветка `kind == 0x101`: `FUN_0043c51f` (луч из камеры) отдаёт
  три `int` (выходные `param_12/13/14`), и код требует
  `op4 == sector`, `op5 == object`, `op6 == polygon`, а `local_58` (длина
  луча) `<= op3`. Внутри `0x43c51f` эти индексы разыменовываются:
  `0x5670d8 + sector*0x18` → таблица объектов → `+0x6c + poly*0x80`.
* `0x44f960`, ветка `kind >= 0x101`: `0x43577c(op4, op5, op6)` превращает
  тройку в мировую точку полигона (проверяет существование и
  `+0x71 != 0`) и передаёт её в `generate_event`.
* `0x44fb30` (`kind 0x102/0x103`, вызывается из опкода 75 — blast): для
  каждой записи `0x428399(op4, op5) == 0` и
  `0x43e541(op4, op5, op6, x, y) <= op3`, где `x/y` — координаты источника
  взрыва, а `0x43e541` считает евклидово расстояние до вершин полигона.
* `0x44fad0` (`kind 0x102`) и `0x44fbd0` (`kind 0x104`) сравнивают тройку
  операндов 4..6 с тройкой, пришедшей извне **точно**.
* `0x44e680` — опкод `0x24` `SET_SOURCEPOLY_SWITCH_EVENT` (сигнатура `E`,
  таблица `0x4b53e8`, индекс 123): находит переключатель с
  `kind >= 0x101` и тройкой, равной полигону **источника** (аргументы
  `[EBP+0x14]/[EBP+0x18]`), и переписывает его `target` (`+0x04`) на
  операнд. То есть скрипт может «перевесить» событие на другой полигон.

Данные поставки (36 уровней, `tools/re/doors.py --frame`):

| kind | штук | проверка | результат |
|---:|---:|---|---|
| `0` | 531 | мировая позиция внутри бокса геометрии уровня | 531/531 |
| `>= 0x101` | 3433 | `(sector, object, polygon)` существует в `.sbw` | 3433/3433 |

Разбивка по видам: `0x101` — 1855, `0x102` — 1067, `0x103` — 131,
`0x104` — 380. Поэтому `gm/scene.py::SCALE = 1/1.875` удалён: он существовал
только ради ошибочного сравнения индексов с координатами.

### 3.1. Остановки

`stop_start + stop_index` индексирует три глобальные колонки:

| колонка | база | смысл |
|---|---|---|
| 0 | `0x5a9130` | floor / button id |
| 1 | `0x5a8e10` | height, clamp `0xffff` при добавлении `0x44ebd9` |
| 2 | `0x5a8af0` | sound / effect id |

`0x44f690` по call-id выбирает остановку, `0x4502a0` ведёт `stop_index`,
сравнивает `+0x5c` с `height[stop]`, задаёт `+0x68 = ±1`, затем по прибытии
`+0x68 = 0`, `event_post(sound)`, `+0x64 = +0x58`. Выбор остановки
(`0x44f6c0..0x44f7a0`): `call_ids[0]` — шаг `(index+1) mod count`,
`call_ids[1]` — `+1` с зажимом, `call_ids[2]` — `-1` с зажимом; затем
перебор всех остановок, и совпавший `floor_id` перекрывает результат
(остановка на текущей высоте только выбирается, хода не начинает). Если
`bVar2` остался false, лифт не двигается и звука вызова нет. В C++ —
`start_lift(index, lift, call_id)`; `lift_targets_` включает и `floor_id`
(дедуп), CTest `test_lift_call_aliases`.

### 3.2. Геометрия кабины

`0x450180` (тик): `+0x60 = speed * dt * direction + +0x5c`, клампится
высотой остановки; затем `0x434e32(handle, dx,dy,dz)` —
`engine_setobjectmvector`, тот же слот `model+0x90`, что у дверей: кабине
задаётся **вектор смещения**. `0x4502a0` после этого зовёт `0x44e6f0`:

1. `frac = height(+0x5c) / 65535`;
2. позиция кабины `pos + pos_delta * frac` (база `+0x3c`, приращение `+0x48`);
   `0x43823c` ставит модель в эту точку;
3. три угла `value[i] = basis[i] + basis[3+i] * frac`, но в `0x41e025`
   передаются в порядке `(value[1], value[0], value[2])`;
4. `0x41e025(a,b,c)` строит **базис** модели (`FSIN`/`FCOS` от трёх углов):
   ```
   row0 = ( c3·c1 − s3·s2·s1, −s3·c1 − c3·s2·s1, −c2·s1 )
   row1 = ( s3·c2,              c3·c2,              −s2    )
   row2 = ( s3·s2·c1 + c3·s1,   c3·s2·c1 − s3·s1,    c2·c1 )
   ```
   (`s1 = sin a`, …, строки кладутся в `obj+0x18/+0x30/+0x48`).

То есть «basis кабины» — это 6 `f64` (три угла + три приращения), а не
матрица; в поставе все 45 лифтов имеют нулевые базовые углы, у части
ненулевые приращения (напр. `0.715585` рад в `level11`).

В C++: `Lift::basis[6]`, `Lift::pos_delta[3]`, `lift_fraction()`,
`lift_transform()` → `LiftTransform{origin, basis, angles}`.

### 3.3. `ADD_LIFT`: 37 dword'ов → runtime-поля

`0x45c9a0` передаёт `head[i]` как операнд `i+1` в `0x44e800`. Важно:
операнды 9..16 — **`double`** (по 2 dword'а: шесть значений базиса), поэтому
целочисленные поля сдвинуты на 8 относительно «одно поле = один dword».
Это и есть причина, по которой прежняя карта (`head[16] = speed`) была
неверной: `head[16]` — младшая половина четвёртого `f64` (в `dm3` там
`1413754135`).

## 6. Доказано / гипотеза / осталось

**Доказано (код + данные):**

1. Базы/шаги/счётчики из §0; лифты — `0x836de0`, шаг `0xA8`, счётчик
   `0x5a9454`, максимум 30; остановки — три колонки, шаг `0x5a9458`.
2. Все смещения и потребители из §1–§3; привязка `(sector,object)`
   1779/1779; группы по `ids[0..2]`; авто-закрытие `+0x98 → +0x9c`;
   лифтовые `stops/speed/height/direction/stop_index/call_ids`.
3. `ADD_LIFT`: 37 dword'ов, `n × 0xc` остановок; `head[20]=speed`,
   `head[22]=height`, `head[1]=SOB`, операнды 9..16 — `double`.
4. Переключатель: `kind/target/radius/pos`; `source` — поле события type-2,
   а не записи; `pressed`/cooldown в файле отсутствуют.
5. **Геометрия створки**: `0x44dfc0` → `0x434887` переписывает origin и
   базис объекта `.sbw` (`center = lerp(closed, open, phase/65535)`,
   поворот на `-angle` вокруг оси из `A1..A3`, `origin = center - basisᵀ·size`);
   единственный писатель origin/базиса в мире. `0x434f72`/`0x434e32` пишут
   вектор движения в `obj+0x90` — это не `extent`, а смещение за кадр.
6. **Триггеры**: `0x44fc30` (kind 0/1 — октагональное расстояние,
   `0x101` — прицел) → `0x479810` (type-2) → `0x44f960` → `generate_event` →
   скрипт → `0x44f690`. `0x44fbd0` — точное совпадение точки для `0x104`.
7. **Столкновение в проёме**: `0x450590` отменяет ход двери (`+0x90 = +0x8c`)
   для kind 2/3; kind 2 уходит в открывание, kind 3 ещё и постит `-22`
   (crush).
8. **Звук**: три пары `v/n` у двери (`+0xa0/+0xac` запуск, `+0xa4/+0xb0`
   цикл движения с ключом `i+1000000`, `+0xa8/+0xb4` остановка) и у лифта
   (`+0x84/+0x90` вызов, `+0x88/+0x94` движение с ключом `i+2000000`,
   `+0x8c/+0x98` прибытие); `n` — индекс `SOUND_SAMPLE_TABLE` (300 записей).
9. **Звук двери и переключателя — по дизасму (§1.3)**: `v` — базовая громкость
   (`+0x1c` 3D-очереди, `volume − atten*dist`), `n` — индекс сэмпла
   (`+0x18`); `+0x60` — затухание на единицу расстояния (`0.03`), а не
   «просто константа»; позиция двери — origin створки (режется в `int`),
   позиция переключателя — его `x/y/z` (kind 0) или центроид полигона
   (`0x43577c`, kind ≥ 0x101); петля движения имеет class
   `1000000 + индекс двери` и останавливается через `0x46ba90`; crush
   (`0x450590`) звука не производит вовсе.
10. **Writer** записей 1/2/18: `parse_*_block`/`encode_*_block` покрывают
    каждый байт; round-trip байт-в-байт на реальных блоках сейва (25 дверей,
    24 переключателя) и на 45 лифтах/151 остановке корпуса.

**Гипотеза:**

1. `kind` дверей 1/2/3 — тип открывания; код различает только реакцию на
   препятствие (2/3) и «используемость» (0 = инертен); геометрию все три
   считают одинаково.
2. `basis` лифта — углы, а не матрица: подтверждено вызовами `0x41e025`,
   но семантика трёх углов (yaw/pitch/roll в каком порядке) не названа.
3. Роли `v0..v2`/`n0..n2` (запуск/движение/остановка) названы **по местам
   вызова**, а не по подписям в данных: сами сэмплы (что именно играется —
   «скрип», «стоп» и т. п.) без `SOUND.SOU`-имён не названы.

**Осталось:**

1. `0x101` (прицел/выстрел): нужен луч `0x43c51f` и таблица `sector/object/
   poly`, поэтому модель честно не считает его позиционным триггером.
2. Диспетчеризация событий двери (`ids[3]/ids[4]`) и `-22` — работа
   `game/events.*` + VM; модель их только логирует.
3. Звук: сам микшер (`0x46bed0` → `0x40be20`/`0x40bec0` → `0x4cabd8`) вне
   этого модуля; доказан только формат запроса и места его рождения.
   Переход `n` → файл сэмпла (`SOUND_SAMPLE_TABLE`) тоже вне модуля.
4. `+0xa4` лифта и `0xa4` у дверей без читателей — оставлены как `unknown`.
5. Звук **лифта** разобран и попадает в очередь `WorldState`:
   `0x44f690`/`0x4502a0` → `0x46b840` (`n_a/v_a` вызов, `n_c/v_c` прибытие),
   `0x4502a0` → `0x46b960` (петля `n_b/v_b`, class `2000000 + индекс`) и
   `0x46ba90` (стоп петли); позиция — origin кабины (`lift_transform`).
   CTest `test_lift_sound_queue` (в т.ч. сейв с уже едущей кабиной).
6. Позиция звука переключателя с `kind >= 0x101` — центроид полигона
   (`0x43577c`: среднее мировых вершин). `WorldState::build` считает его из
   `.sbw` (`Switch::world_position`) и отдаёт запрос с `position_known =
   true`; `false` остаётся только если тройка/полигон не резолвится или
   геометрии нет (CTest `test_polygon_switch_centroid`).
