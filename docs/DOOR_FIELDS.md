# Поля дверей, переключателей и лифтов (M2.3.4)

Карта **runtime-записей** и того, что из них читает `engine/src/world/doors.*`.
Разбор — по `gundx.exe` (ImageBase `0x400000`, Ghidra 12.1.4) и по 36
поставочным `.sbt`/`.sbw` (только чтение). Инструмент —
`tools/re/door_fields.py`; модель C++ и её golden'ы — `docs/DOORS_CPP.md`,
формат `.sbt`/сейва — `docs/RECORDS.md` §4 и `docs/SAVE_FIELDS.md` §3/§4.

Статусы: **код** — адрес инструкции доказывает поле/потребителя; **данные** —
проверено на поставке; **гипотеза** — смысл правдоподобен, но кодом не
доказан.

## 0. Что подтверждено в Ghidra

| таблица | база | шаг | счётчик | максимум | писатель | потребитель |
|---|---|---|---|---|---|---|
| двери | `0x8381a0` | `0xB8` | `0x5a9450` | 100 | `ADD_DOOR` `0x459b5b` → `0x44e250` | tick `0x44f2e0`/`0x44f3f0`, `0x44f690`, `0x44fc30` |
| переключатели | `0x5a4af0` | `0x20` | `0x5a945c` | 512 | `ADD_SWITCH` `0x45b6ff` → `0x44e5f0` | событие type-2 `0x479810` → `0x44f960`; proximity `0x44fc30` |
| лифты | `0x836de0` | `0xA8` | `0x5a9454` | 30 | `ADD_LIFT` `0x45c9a0` → `0x44e800` | tick `0x450180`, state `0x4502a0`, call `0x44f690` |
| остановки лифтов | 3 колонки `0x5a9130` / `0x5a8e10` / `0x5a8af0` | 3 × `u32` | `0x5a9458` | 200 | `0x44eb80` | `0x4502a0`, `0x44f690`, `0x44eed0` |

Счётчики/границы подтверждены кодом: `0x44e250` (`99 < 0x5a9450`),
`0x44e5f0` (`0x1ff < 0x5a945c`), `0x44e800` (`0x1d < 0x5a9454`),
`0x44eb80` (`199 < 0x5a9458`). Чтение/запись типа 18 — `0x44eed0`
(`n`, `n*0xA8`, `k`, три колонки), создание — `0x44e800` + `0x44eb80`.

`ADD_LIFT` — не запись 18: `0x45c9a0` берёт 37 dword'ов (`0x94` байта) и
передаёт их как `param_1..param_37` в `0x44e800`, затем читает `u32 n` по
`+0x94` и `n` остановок по `0xc` (`floor/height/sound`), добавляя их
`0x44eb80`. Поэтому индексы `head[]` ниже — это **порядок операндов
`ADD_LIFT`**, а не смещения 168-байтной записи.

### 1.1. Фаза, направление, группа, авто-закрытие

* `0x44f2e0` каждый тик: `+0x90 = +0x8c + state * step * dt`, clamp
  `0..0xffff` (`0x44f335..0x44f349`), затем двигает створку через
  `0x434f72` на долю `(open-closed) * (phase_next-phase_prev)/65536`.
* `0x44f3f0` фиксирует `+0x8c = +0x90` (`0x44f461/0x44f466`) и крутит
  таймер `+0x9c` (`0x44f5f8..0x44f605`). По истечении — `state = -1`
  (закрывание). При полном открытии (`phase >= 0xfffe`) —
  `+0x9c = +0x98` (`0x44f54d/0x44f550`).
* `0x44f690` по id переключателя перебирает **все** двери; id сравнивается
  с `ids[0..2]` (`+0x6c/+0x70/+0x74`):
  * `ids[0]` — обычный toggle: если `state==+1` или `phase==0xffff` →
    `-1`, иначе `+1` (`0x44f6c0..0x44f6e5`);
  * `ids[1]` — только открыть, если `phase < 0xffff` (`0x44f6ee..0x44f701`);
  * `ids[2]` — только закрыть, если `phase > 0` (`0x44f706..0x44f710`).
  Одновременно `+0x9c = 0` (`0x44f725`) — таймер сбрасывается.
  Это и есть «группа»: отдельного поля группы нет, группа = совпадение id.
* `(sector, object)` — адрес створки в `.sbw`; `0x434419` идёт по таблице
  `ds:0x5670d8` (stride `0x18`: `{count, pointer}`), индекс объекта —
  второй уровень. В поставке пары валидны **1779/1779**, все **1779**
  различны.
* `linked` в C++ = `ids[3] != 0`, но `+0x78` в билде **никто не читает**
  (единственный xref — запись `0x44e2bd`). Это данные редактора/будущего
  поведения, а не работающая механика.

## 2. Запись переключателя `SWITCH` / `0x5a4af0`, `0x20`

Все восемь dword'ов пишутся дословно в `0x44e5f0` (счётчик `0x5a945c`).
Отдельного `pressed`/cooldown/`source` в записи **нет**.

| смещ. | тип | смысл | кто читает/пишет (адреса) | статус |
|---|---|---|---|---|
| `+0x00` | i32 | `kind` | `0x44f960` (`<0x101` / `>=0x101`), `0x44fc30` (`0/1/0x101`), `0x44fbd0` (`0x104`) | код, данные |
| `+0x04` | i32 | `target` — id для `GENERATE` | `0x44f960` → `generate_event` `0x479960`; `0x44fbd0` | код, данные |
| `+0x08` | i32 | `radius` | distance compare `0x44fc30`; `0x44fb9e` для `0x102..0x104` | код, данные |
| `+0x0c` | 3 × i32 | `pos.x/y/z` (мировой кадр движка) | source-контекст `0x44f960`; distance `0x44fc30` | код, данные |
| `+0x18` | i32 | `aux` | 2-й аргумент `0x46b840` в `0x44f960` | **гипотеза**: громкость |
| `+0x1c` | i32 | `sound`, `-1` = тишина | sample для `0x46b840`/`0x46b8d0` в `0x44f960` | код, данные |

Семантика `kind` (по веткам потребителей):

| kind | смысл | доказательство |
|---|---|---|
| `0` | proximity игрока: расстояние до `pos` `< radius` | `0x44fc30`, ветка `piVar6[-1]==0` |
| `1` | proximity к створке двери, найденной по id (id = `ids[0..2]`) | `0x44fc30`, ветка `==1` |
| `0x101` | transformed-триггер: экранные/мировые координаты после `0x43c51f`, сравнение с `radius` | `0x44fc30`, ветка `0x101` |
| `0x102`, `0x103` | source-варианты `GENERATE` (позиция передаётся в событие) | `0x44f960`, ветка `>=0x101` |
| `0x104` | точное совпадение `pos` с переданной точкой, затем событие с source | `0x44fbd0` |

* `repeat`: в `0x44fc30` нет latch/cooldown — пока условие выполнено,
  событие type-2 пишется **каждый вызов** (кадр/тик). C++ `Switch.pressed`
  — состояние модели, в файле его нет.
* `source`: пишется в событие type-2 (`0x479810`: тип `2`, `u32 switch_index`
  по `+1`, `u16 source` по `+5`), затем `0x44f960` передаёт source в
  `generate_event` как `param_2 - 0x10000`. Это индекс игрока/источника,
  а не поле записи.
* `pressed` в C++ сбрасывается в конце следующего `tick`; на запись `0x20`
  не отображается.

## 3. Запись лифта `LIFT` (тип 18) / `0x836de0`, `0xA8`

Тип 18 в поставке не встречается (0 файлов), поэтому колонка «данные» здесь
пустая; поля доказаны кодом `0x44e800` (создание), `0x450180` (тик),
`0x4502a0` (state machine), `0x44f690` (вызов/выбор остановки).

| `+0xa4` | i32 | не названо | читателей/писателей нет | неизвестно |

### 3.1. Остановки

`stop_start + stop_index` индексирует три глобальные колонки:

| колонка | база | смысл |
|---|---|---|
| 0 | `0x5a9130` | floor / button id |
| 1 | `0x5a8e10` | height, clamp `0xffff` при добавлении `0x44ebd9` |
| 2 | `0x5a8af0` | sound / effect id |

`0x44f690` по call-id выбирает остановку, `0x4502a0` ведёт `stop_index`,
сравнивает `+0x5c` с `height[stop]`, задаёт `+0x68 = ±1`, затем по прибытии
`+0x68 = 0`, `event_post(sound)`, `+0x64 = +0x58`.

### 3.2. `ADD_LIFT`: 37 dword'ов → runtime-поля

`0x45c9a0` передаёт `head[i]` как `param_{i+1}`; запись в `0x44e800`:

| head | поле записи | смысл | адрес записи | C++ |
|---|---|---|---|---|
| `head[0]` | `+0x34` | kind | `0x44e855` | `Lift.kind` ✅ |
| `head[1]` | `+0x38` | **SOB-индекс**, не id | `0x44e85f` | `Lift.id` ❌ (смысл другой) |
| `head[2..4]` | `+0x3c..+0x44` | x/y/z | `0x44e869..` | `Lift.x/y/z` ✅ |
| `head[16]` | `+0x54` | **speed** | `0x44e907` | не парсится ❌ |
| `head[17]` | `+0x58` | dwell | `0x44e911` | не парсится ❌ |
| `head[18]` | `+0x5c` | **height** | `0x44e91b` | сейчас берётся `head[7]` ❌ |
| `head[21]` | `+0x6c` | stop_index | `0x44e9b2` | ✅ |
| `head[22..24]` | `+0x70..+0x78` | call ids | `0x44e98b..` | ✅ |

Важно: `head[7]` — это `+0x50` (приращение базиса), **не высота**. Из-за
этого скриптовые лифты в C++ имеют неверную высоту и `speed = 0`
(следовательно, не двигаются).

## 6. Доказано / гипотеза / осталось

**Доказано (код + данные):**

1. Базы/шаги/счётчики из §0; лифты — `0x836de0`, шаг `0xA8`, счётчик
   `0x5a9454`, максимум 30; остановки — три колонки, шаг `0x5a9458`.
2. Все смещения и потребители из §1–§3; привязка `(sector,object)`
   1779/1779; группы по `ids[0..2]`; авто-закрытие `+0x98 → +0x9c`;
   лифтовые `stops/speed/height/direction/stop_index/call_ids`.
3. `ADD_LIFT`: 37 dword'ов, `n × 0xc` остановок; `head[16]=speed`,
   `head[18]=height`, `head[1]=SOB`.
4. Переключатель: `kind/target/radius/pos`; `source` — поле события type-2,
   а не записи; `pressed`/cooldown в файле отсутствуют.

**Гипотеза:**

1. `kind` дверей 1/2/3 — тип открывания; код только хранит и ветвит
   `kind == 2/3` в `0x450590` (crush/синхронизация), но не различает
   геометрию.
2. `+0xa0..+0xb4` двери и `+0x84/+0x88/+0x94/+0x98` лифта — звуковые
   параметры (адреса вызовов есть, роль не доказана).
3. `linked` (`ids[3]`) — вторая створка/редакторская связь; читателей нет.
4. `basis` лифта (`+0x00..+0x30`, `+0x48`) — ориентация/смещение кабины;
   раскладка ясна, математика — нет.

**Осталось:**

1. Реализовать в C++ `+0x98/+0x9c` (dwell/timer) и `ADD_LIFT head[16]/[18]`;
   сейчас `hold_ticks` — opt-in, а скриптовые лифты статичны.
2. Разделить `kind` 1/2/3 и `0x102/0x103` (повтор/источник/кулдаун).
3. Дочитать `basis` лифта и звуковые поля; writer/round-trip записи 18.
4. Движение геометрии створки в мировом кадре (`+0x48` delta и кадр
   `D`-операндов) — по-прежнему вне модели.

## 7. Воспроизведение

```sh
# карты полей (по умолчанию), JSON, проверка данных, самотест
python3 tools/re/door_fields.py --fields
python3 tools/re/door_fields.py --fields --json
python3 tools/re/door_fields.py --verify
python3 tools/re/door_fields.py --verify --level dm1 --level level0
python3 tools/re/door_fields.py --self-test

# независимые инструменты
python3 tools/re/doors.py --level dm1
python3 tools/re/records.py --fields

# Ghidra (сервер: tools/ghidra/start.sh)
python3 tools/ghidra/mcp.py decompile 0x44e250 0x44e5f0 0x44e800 0x450180
python3 tools/ghidra/mcp.py disasm 0x44f2e0 --count 120
python3 tools/ghidra/mcp.py disasm 0x44f690 --count 200
```

`--self-test` проверяет синтетические записи на всех смещениях (дверь
`0xB8`, переключатель `0x20`, лифт `0xA8`, тип 18, `ADD_LIFT head`),
обрезанные payload'ы и живые агрегаты; при расхождении возвращает `1`.
`--verify` возвращает `1` при несовпадении `1779/3964/45/151`,
`1779/1779`, `1534/200` или per-level `dm1`/`level0`.
