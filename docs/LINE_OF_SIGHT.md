# Gunmetal — линия видимости до цели (`M6.2.5`, срез 2)

Что здесь: модуль `engine/src/game/line_of_sight.{h,cpp}` — трассировка
«есть ли геометрия уровня между глазом и сферической целью». Это новый слой
поверх `CollisionWorld` (`docs/COLLIDE.md`), а не порт оригинального кода:
hitscan-скан цели `0x477f90`/`0x4779f0` проверяет конус и дистанцию
(`docs/WEAPONS_CPP.md` §6) и мир на преграду не трассирует. Единственная
прежняя проверка видимости в C++ — приватный `Ai::line_of_sight` (луч
точка-точка с зазором `los_skin`, `docs/AI_CPP.md`); здесь она формализована
как публичный запрос с учётом размера цели.

Статус: API, реализация, синтетические и реальные (`level0`, `dm1`) тесты
готовы, CTest `line_of_sight` (метка `quick`) зелёный. Модуль **не подключён**
к `fire()`/`resolve_hitscan_impact`/AI/рантайму (см. §5).

---

## 0. Коротко

| что | значение |
|---|---|
| запрос | один **центральный** луч `eye -> target.center` |
| преграда | пересечение строго ближе `distance - radius` |
| `distance` | евклидово `|center - eye|`, заполняется и для «закрыто» |
| размер цели | только как отсечка луча; собственные треугольники цели не трассируются |
| точность | `double`, порядок обхода как у `CollisionWorld::raycast` |
| фильтр | `CollideFilter` вызывающего (полы/стены/потолки, секторы, `backfaces`) |
| ошибки | отказ (`visible=false` + текст), а не «видно» |
| аллокации | одиночный запрос — нет; батч — один `std::vector` на результат |
| не подключено | к оружию, AI, рантайму |

## 1. Модель

### 1.1. Правило преграды

```
delta    = target.center - eye
distance = |delta|
limit    = distance - target.radius
hit      = world.raycast(eye, delta, limit, filter)
blocked  = hit && hit->t < limit          // строго ближе
visible  = !blocked
```

* Луч нормируется внутри `raycast`, поэтому `t` — расстояние в мировых
  единицах, как в `docs/COLLIDE.md` §4.1.
* Сравнение **строгое**: поверхность ровно на границе сферы цели преградой не
  считается. Это проверено синтетикой: стена на `t = 20` при `distance = 30`,
  `radius = 10` (`limit = 20`) даёт `visible = 1`.
* Если `limit <= 0` (цель в глазу или её радиус дотягивается до глаза),
  поверхностей между точками быть не может — `visible = true` без трассировки.
* `radius` — радиус ограничивающей сферы цели, не точная геометрия. Края и
  касательные лучи **не** трассируются (одна центральная трассировка), поэтому
  частично выглядывающая из-за угла цель может считаться видимой. Это
  осознанное приближение (§4).
* «Преграда» — только геометрия уровня. Другие цели в батче не перекрывают
  друг друга: `line_of_sight_all` поэлементно равен одиночным вызовам (§3).

### 1.2. Почему цель не блокирует сама себя

Луч ограничен `limit = distance - radius`. Любая геометрия, принадлежащая
цели, лежит внутри её ограничивающей сферы, то есть на расстоянии
`>= distance - radius` от глаза. `raycast` не возвращает `t > limit`, а
`t == limit` отбрасывается строгим сравнением. Поэтому собственные
треугольники цели физически не могут попасть в ответ, **без** отдельного
списка исключений и без сравнения индексов.

Проверено синтетикой: куб 2×2×2 с центром `(5,0,5)` (ближняя грань `x = 4`),
глаз `(0,0,5)`, `distance = 5`, `radius = 2`, `limit = 3`:

| запрос | результат |
|---|---|
| `raycast` без ограничения | `t = 4` (куб действительно в мире) |
| `line_of_sight`, `radius = 2` | `visible = 1`, преграды нет |
| барьер на `x = 2` (внутри `limit = 3`) | `visible = 0`, `blocker_t = 2` |
| `line_of_sight`, `radius = 0` | `visible = 0`, `blocker_t = 4`, треугольник куба |

Тот же эффект на реальных данных: цель в одном юните перед стеной
(`level0`, центр `(79,−208,58)`, стена `x = 80`): несвязанный `raycast` даёт
`t = 56`, а LOS с `radius = 20` — `visible = 1`, потому что след остановлен на
`55 − 20 = 35`. Стена **за** целью не считается преградой.

### 1.3. Ошибки — отказ, а не «видно»

Отказ (`visible = false`, `triangle = nullptr`, текст в `error`) для:

* `eye` или `target.center` — `NaN`/`inf`;
* `radius < 0`, `NaN` или `inf`;
* `world.triangle_count() == 0` — в мире нет статической геометрии.

Обоснование: пустой мир означает «уровень не собрался/не загружен», а не
«между точками пусто». Молчаливое «видно» на таком мире маскировало бы ошибку
загрузки и разрешало бы попадания сквозь отсутствующую геометрию. Отказ
безопаснее: вызывающий видит текст и решает, что делать. Динамический набор
(`set_dynamic`) сам по себе мира не заменяет — проверка идёт по
`triangle_count()`, как записано в задании.

`line_of_sight_all` не прерывается на плохой цели: она остаётся в результате
невидимой (`distance = 0`), первая ошибка копируется в общий `error`, остальные
цели считаются как обычно.

## 2. API

```cpp
#include "game/line_of_sight.h"

gm::LosTarget target{7, {24, 228, 58}, 10.0};   // id, center, radius
std::string error;
const gm::LosResult r = gm::line_of_sight(world, eye, target, {}, &error);
if (!error.empty()) { /* отказ: не finite / radius < 0 / пустой мир */ }

std::vector<gm::LosTarget> targets = /* ... */;
const std::vector<gm::LosResult> all =
    gm::line_of_sight_all(world, eye, targets, {}, &error); // all[i] <-> targets[i]
```

| тип | поля |
|---|---|
| `LosTarget` | `id` (непрозрачный, эхо в результате), `center`, `radius` (`>= 0`) |
| `LosResult` | `visible`, `distance`, `triangle` (`const Triangle*`), `triangle_index`, `blocker`, `id`, `dynamic`, `blocker_distance` |
| константы | `kLosWorldBlocker = 0`, `kLosNoBlocker = 0xffffffff` |

`triangle_index` — в `triangles()` для статической преграды и в
`dynamic_triangles()` при `dynamic = true` (та же конвенция, что у
`RayHit::triangle_index`, `docs/DOOR_COLLISION.md`). `triangle` жив, пока жив
`CollisionWorld`. `blocker_distance` — `t` преграды; при `visible` он `0`.
`blocker` сейчас всегда `kLosWorldBlocker` или `kLosNoBlocker`: id целей
зарезервированы под будущий проход «цель-цель» и этот модуль их не выставляет.

Фильтр — обычный `CollideFilter`, поэтому «только полы», список секторов и
односторонний `backfaces = false` работают без отдельного кода LOS.

## 3. Что доказано числами

Все числа воспроизводятся `engine/tests/gm_line_of_sight_tests`
(CTest `line_of_sight`, ~0.3 с). Реальные пары найдены сканированием сетки
64 юнита на высоте глаза спавна; в тесте они закреплены.

### 3.1. Синтетика

| проверка | ожидание | факт |
|---|---|---|
| стена `x = 20`, глаз `(0,0,5)`, цель `(30,0,5)`, `r = 1` | закрыто | `distance = 30`, `blocker_t = 20`, `tri = 2` |
| цель `(10,0,5)`, `r = 1` | видно | `distance = 10`, треугольника нет |
| стена ровно на `limit`: цель `(30,0,5)`, `r = 10` | видно (строгое `<`) | `limit = 20`, видно |
| цель в глазу, `r = 1` | видно | `distance = 0` |
| цель `(0,0,25)`, `r = 30` (радиус дотягивается до глаза) | видно | `distance = 20` |
| фильтр «только полы» на закрытую цель | видно | по умолчанию `visible = 0`, с фильтром `1` |
| `backfaces = false` для стены, освещённой с тыла | видно | `visible = 1` |
| куб цели, `r = 2`, `limit = 3` | видно | `raycast` даёт `t = 4`, LOS — `1` |
| барьер `x = 2` внутри предела | закрыто | `blocker_t = 2` |
| куб цели, `r = 0` | закрыто кубом, не стеной | `blocker_t = 4`, `tri` из 0..11 |

### 3.2. `level0` (3162 треугольника, 58 секторов)

Глаз спавна `(24,−208,58)` (`docs/COLLIDE.md` §6.2).

| цель | `radius` | `distance` | `blocker_t` | треугольник | видно |
|---|---:|---:|---:|---:|---|
| `(−8,104,58)` — открытое место | 10 | 313.636732543 | — | — | да |
| `(180,−208,58)` — за `+X` стеной | 10 | 156 | 56 | 3091 | нет |
| `(−148,−208,58)` — за `−X` стеной | 10 | 172 | 72 | 2355 | нет |
| `(24,228,58)` — за `+Y` стеной | 10 | 436 | 336 | 747 | нет |
| `(24,−388,58)` — за `−Y` стеной | 10 | 180 | 80 | 17 | нет |
| `(79,−208,58)` — в юните перед `+X` стеной | 20 | 55 | — | — | да |

* `distance` открытой пары равно `sqrt(32² + 312²) = 313.636733` (сверка с
  евклидовым расстоянием в тесте — `1e-9`).
* `t` стен совпадают с прямыми лучами из `docs/COLLIDE.md` §6.2:
  `+X = 56`, `−X = 72`, `+Y = 336`, `−Y = 80`.
* Батч из 10 целей (6 открытых + 4 за стенами): `visible = 6`,
  `blocked = 4`; каждое поле совпадает с одиночным вызовом.
* `floors`-only фильтр снимает `+Y` стену: `visible = 0` -> `1`.
* Повторные вызовы дают побитово те же `visible/distance/triangle/
  triangle_index/blocker_distance`.

| `(−660,176,74)` — за `−X` стеной | 10 | 500 | 400 | 10955 | нет |

### 3.4. Отказы и детерминизм

| запрос | текст (начало) |
|---|---|
| `eye = NaN` / `inf` | `line_of_sight: eye is not finite` |
| `center = NaN` / `inf` | `line_of_sight: target center is not finite` |
| `radius = −1` / `NaN` / `inf` | `line_of_sight: target radius is negative or not finite` |
| пустой `CollisionWorld` | `line_of_sight: collision world has no static triangles` |

Батч с одной плохой целью: `error` содержит сообщение о радиусе, хорошие цели
по-прежнему совпадают с одиночными вызовами.

## 4. Гипотеза и ограничения

Гипотеза (не доказано кодом оригинала):

* **Одна центральная трассировка вместо конуса.** Оригинальный скан цели
  (`0x477f90`/`0x4779f0`) проверяет конус, дистанцию и глубину, но функции
  «мир между стрелком и целью» в разобранном коде нет. Поэтому LOS сделана
  отдельным запросом, а не повторением оригинала; конус остаётся в
  `weapons.h` (`hitscan_in_cone`), LOS его не дублирует.
* **Радиус как отсечка.** Что считать «телом» цели, в оригинале не найдено;
  здесь это ограничивающая сфера, а правило `distance - radius` — инженерное
  решение. Оно не моделирует частично видимую цель (край/касательная), зато
  детерминировано и не требует перебора.
* **Оригинальный учёт материалов.** Прозрачных материалов в модели нет;
  не проверялось, пропускал ли оригинал стекло/решётки.

Ограничения модуля:

1. **Нет конуса и разброса.** Стрельба с `spread` может уйти в сторону от
   центрального луча, а LOS всё равно ответит по центру. Связка «конус +
   LOS по лучу попадания» — задача вызывающего.
2. **Нет прозрачных материалов.** Любой треугольник, прошедший фильтр,
   считается непрозрачным. Стекло, сетка, решётка блокируют.
3. **Нет своего broad-phase.** Работает `CollisionWorld::raycast` (AABB
   секторов + AABB треугольников, `docs/COLLIDE.md` §5); это не BSP/PVS, на
   больших уровнях цена линейна по числу секторов на запрос. Для одиночных
   проверок этого достаточно, для «всех целей каждый тик» может понадобиться
   кэш/секторный список.
4. **Нет цели-цель.** Другие `LosTarget` не перекрывают линию; `blocker`
   зарезервирован, но всегда `kLosWorldBlocker`/`kLosNoBlocker`. Это
   следствие требования «батч = одиночные вызовы» и отсутствия тел целей в
   `CollisionWorld`.
5. **Не подключено к рантайму.** `resolve_hitscan_impact`, `fire()`, AI и
   `GameRuntime` модуль не вызывают; это следующий срез `M6.2.5`.
6. **Только статический мир как база.** Динамический набор (`set_dynamic`)
   учитывается через `raycast` (преграда может быть дверью, `dynamic = true`),
   но мир без статических треугольников отвергается даже при непустом
   динамическом наборе (см. §1.3).
7. **Нет точки преграды и её владельца.** Отдаются `t` и треугольник; точки
   `origin + direction * t` в результате нет — вызывающий при необходимости
   считает её сам (одно умножение).

## 5. Тесты и воспроизведение

```sh
export PATH=$HOME/tools/cmake-4.4.4-linux-x86_64/bin:$HOME/tools/bin:$PATH
cmake --build build/sandbox --target gm_line_of_sight_tests -j 4
ctest --test-dir build/sandbox -R line_of_sight --output-on-failure
./build/sandbox/engine/tests/gm_line_of_sight_tests     # числа в выводе
```

Тест печатает каждую проверку: позиции, `distance`, `blocker_t`, индекс
треугольника, счётчики `visible/blocked`, тексты отказов. Без установленной
игры реальные части печатают `skipped` и не падают; синтетика и отказы
проверяются всегда.

`python3 regress.py --mirror --json` к модулю отношения не имеет (проверяет
`gm.py`), но запускался: файлы Python-оракула не менялись.
