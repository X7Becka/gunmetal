# Регенерация щитов/брони в тике (`game/regen.*`, `M6.1.3`, срез 4)

Снимок 2026-10-23. В `M6.1.3` было записано: «Регенерации в игровом тике
нет; `DEFINE_REGEN` в ВМ только регистрирует таблицу». Этот срез добавляет
регенерацию **в тик** на чистых данных: `game/regen.h/.cpp` (модель),
опциональный `SimPlayer::set_regen()` и тест `engine/tests/test_regen.cpp`
(CTest `regen`, метка `quick`).

Канон по опкоду и маркеру — `docs/PICKUP.md` §7 и `docs/OBJECTIVES.md`
§4.3; по отсутствию регенерации в оригинале — `docs/DAMAGE.md` §6. Здесь
только сводка, API и числа теста.

## 1. Что доказано (код + данные)

Опкод **174** `DEFINE_REGENERATION_MARKER`, сигнатура `ODD`
(`gm/sbtvm.py`, `engine/src/res/vm_exec.cpp`), обработчик
`0x45c375..0x45c39f`:

| операнд | запись | адрес записи | смысл в 1.36 |
|---|---|---|---|
| `O` dword | `ds:0x80d878` | `0x45c37d` | индекс SOB маркера (жив) |
| `D` double | `ds:0x80f9e0` | `0x45c38a` | **читателей нет** |
| `D` double | `ds:0x80f830` | `0x45c399` | **читателей нет** |

* Загрузка уровня обнуляет оба double (`0x45713f`, `0x457153`); кроме
  записи опкодом и этого обнуления обращений к ним нет — проверено по
  листингу (`docs/PICKUP.md` §7, `docs/DAMAGE.md` §6).
* Живая часть — только SOB: `0x468840` берёт `[0x80d878]` и создаёт маркер
  вместо исчезнувшего предмета в DM. К шкалам игрока отношения не имеет.
* Корпус: ровно **36/36** `.sbt`, по одному опкоду на файл, значения всегда
  `(19, 3000.0, 50.0)` (проверка ниже, §7). В C++ то же самое для `dm1` и
  `level0` проверяет `test_marker_data()`.

**Вывод:** в поставке 1.36 регенерации щитов/брони нет — два double мёртвые.
Поэтому `game/regen.*` — **модель**, а не порт: она параметризуется
правилом вызывающего, а не читает `.sbt` автоматически.

## 2. Что гипотеза

Ни одно из чисел ниже не доказано кодом оригинала; это явные допущения
модели (помечены и в `game/regen.h`):

1. **Смысл двух double.** Гипотеза A: `a` — задержка, `b` — скорость.
   Если читать `3000.0` как тики (≈33 с) и `50.0` как сотые за тик
   (0.50 гейджа/тик = 45.5 гейджа/с), полные щиты 8000 набираются за
   160 тиков после задержки. Гипотеза B: `a` — миллисекунды (3 с), `b` —
   радиус/высота маркера из редактора (её же упоминает `docs/PICKUP.md` §7).
   Модель **не** фиксирует ни одну из них: числа задаёт вызывающий.
2. **Что регенерирует.** В опкоде нет ни флага щитов/брони, ни топлива.
   `RegenRule::shields`/`armor` — выбор вызывающего; по умолчанию оба.
3. **Порядок и бюджет.** Один общий бюджет `rate_per_tick` на тик: сначала
   четыре квадранта щита в фиксированном порядке front, right, back, left,
   затем броня. Пул, заполненный до `*_max`, пропускается; остаток бюджета
   сбрасывается, а не копится. Дробная часть бюджета копится в
   `RegenState::carry`.
4. **Задержка.** «Задержка после урона» = `delay_ticks` полных тиков;
   первый восстанавливающий тик — `delay_ticks + 1` после тика урона. Новый
   урон сбрасывает и задержку, и накопленную дробь.
5. **Источник флага урона.** `damaged_this_tick` считает сам `SimPlayer` по
   уменьшению `armor`/`shields` за тик (до регенерации).

## 3. API

```cpp
struct RegenRule {
    int    delay_ticks   = 0;    // полных тиков после урона
    double rate_per_tick = 0.0;  // сотые гейджа за тик (может быть дробным)
    bool   shields       = true; // четыре квадранта до shield_max
    bool   armor         = true; // броня до armor_max, после щитов
};

struct RegenState {
    int    since_damage = 0; // 0 на тике урона
    double carry        = 0.0; // дробный остаток, 0 <= carry < 1
};

const char* regen_rule_error(const RegenRule& rule); // nullptr = правило годно
bool apply_regen(Vitals&, RegenState&, const RegenRule&, bool damaged_this_tick);
void reset_regen(RegenState&);
```

`apply_regen()` — чистая функция: при негодном правиле возвращает `false`
**без изменений** `Vitals` и `RegenState`. Границы: `0 <= delay_ticks <=
1000000`, `0 <= rate_per_tick <= 1000000`, конечно; правило без обоих пулов
отвергается (это не «выключено», а ошибка — выключено = правило не задано).

`SimPlayer` (по умолчанию регенерации **нет**):

```cpp
bool set_regen(const RegenRule&, std::string* error = nullptr);
void clear_regen();
bool has_regen() const;
const RegenRule*  regen_rule()  const;
const RegenState& regen_state() const;
```

Правило — конфигурация: переживает `init()`/`respawn()`. Часы (`RegenState`)
сбрасываются в `init()`, `set_vitals()`, `respawn()`, `set_regen()` и
`clear_regen()`.

Порядок тика (срез 3 + срез 4): шаг контроллера → `set_player_eyes` →
`install_vitals` → оружие/спавн → `runtime.tick(1)` → `apply_blasts` →
чтение шкал назад → учёт `damage_taken()` и смерти (`armor <= 0`) →
**`apply_regen()`**. Регенерация идёт после учёта урона, поэтому
`damage_taken()` не может уменьшиться; мёртвый игрок не регенерирует.
Изменённые шкалы помечаются dirty и ставятся на рантайм в начале
следующего тика, чтобы следующий взрыв видел уже восстановленные значения.

## 4. Числа теста (реальные `dm1` + `level0` ROCKET)

`ctest --test-dir build/sandbox -R regen -V` / прямой запуск
`./build/sandbox/engine/tests/gm_regen_tests`.

Чистая арифметика:

| случай | результат |
|---|---|
| `delay=3`, `rate=2.0`, фронт 7000 | 3 тика без роста, затем +2/тик: 7000 → 7020 за 10 тиков |
| `rate=0.5` за 10 тиков | 7990 → 7995, `carry` 0 (дробь копится) |
| границы (`rate=100`, броня 9999, фронт 7999) | 10000 и 8000 за один тик, `carry=0`, перелива нет |
| `shield_max=0` | щиты не трогаются, броня 9999 → 10000 |
| негативы | `delay=-1`, `delay>10^6`, `rate=-1`, `NaN`, `inf`, `rate>10^6`, «нет пулов» → `false` + текст, состояние не изменено |

Сценарий `SimPlayer` (сильнейшая цель — `POPMACH` id 138, `max_hp=100000`,
ноги `(642.00, 621.00, 28.00)`, yaw 0): 220 тиков, огонь `0..29` и
`80..149`, правило `delay=10`, `rate=2.0`, только щиты.

| событие | тик | сумма щитов |
|---|---|---|
| первый урон | 0 | 22240 |
| первая регенерация (+2) | 11 | 22240 → 22242 |
| второй урон (новая задержка) | 130 | 2718 |
| вторая регенерация (+2) | 141 | 2718 → 2720 |

Рост ровно +2 на каждом тике после `урон + delay + 1`, до второго урона;
`damage_taken()` между уронами не меняется (по одному значению на тик).

Паритет со срезом 3 (по умолчанию правило не задано; слабейшая цель —
`OILDRUM` id 139, как в `test_sim_damage.cpp`): 30 тиков огня дают
`shots=1 spawned=1 blasts=2 damage_taken=5060`, щиты `6735/6735/6735/6735`,
броня `10000` — **те же числа**, что печатает `test_sim_damage` в строке
«first shot after 30 ticks». Затем 120 холостых тиков не меняют ни шкалы,
ни `damage_taken` (регенерации нет), а повтор на свежем рантайме даёт те же
числа.

Границы в `SimPlayer`: `set_vitals(броня 9990/10000, щиты 7999/8000×4)` +
`rate=100` → за 10 тиков ровно `10000` и `8000×4`, `damage_taken()=0`.

Негативы `set_regen`: `delay=-1`, `rate=-0.5`, `rate=NaN`, «нет пулов» →
`false` с текстом, правило не установлено; отклонённая замена не стирает
прежнее правило; `clear_regen()` возвращает `has_regen()=false`.

## 5. Ограничения

* **Нет регенерации топлива/батарей.** В `Vitals` таких шкал нет, и в
  опкоде 174 их тоже нет: только SOB + два double. Добавлять нечего.
* **Нет автоматического чтения `.sbt`.** `DEFINE_REGENERATION_MARKER` не
  превращается в правило: два double мертвы, и их отображение — гипотеза
  (§2). `Weapons`/`VmState` не тронуты.
* **Нет связи с HUD.** Индикаторы щитов/брони (`render/hud*`) рисуют шкалы
  `Vitals`; отдельного «эффекта регенерации» (вспышка, звук) нет и в
  оригинале не найдено.
* **Нет per-quadrant скорости.** Один общий бюджет заполняет квадранты
  последовательно; равномерного «все четыре сразу» нет. Это выбор модели.
* **Нет регенерации мёртвого игрока** и нет воскрешения: смерть остаётся
  `armor <= 0`, дальше только `respawn()`.
* **Оружие в тесте**: кулдаун ROCKET убывает только пока удерживается
  курок (тик оружия вызывается лишь при `segment.fire`), поэтому второй
  залп в тесте длиннее 50 тиков. Это свойство среза 1–3, не регенерации.
