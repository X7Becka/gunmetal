# 3D-позиционный звук (M7.3): очередь, слушатель, формулы

Статус: **математика прослежена до конца** (источник → очередь → слушатель →
гейн → панорама → запрос → L/R). Инструмент:
`tools/re/audio_3d.py` (`--fields`, `--check`, `--calc`, `--self-test`), без
Ghidra, игру только читает. Всё снято с `gundx.exe` v1.36
(sha256 `929ffa72…acd17`), VA с базой `0x400000`.

Дополняет `docs/SOUND_FIELDS.md` (записи сэмплов и голоса),
`docs/AUDIO_MIXER.md` (наш микшер), `docs/CAMERA.md` (оси и угол камеры).
Уточнения к `SOUND_FIELDS` — §10.

## 0. Коротко

| что | как в оригинале | где |
|---|---|---|
| позиция источника | **int** `x, y, z` в мировых единицах (не double) | очередь `+0x08/+0x0c/+0x10` |
| слушатель | **тело игрока**: позиция `+0x00`, базис `+0x18/+0x30/+0x48` | `player+0x3178` → `0x4523df` |
| ориентация | рыскание/тангаж/крен **шасси** (`+0x28/+0x18/+0x20`), без view-pitch и тряски | `0x444b81..0x444c9f` |
| расстояние | **не** евклидово: `max + 0.25·(mid+min)` | `0x4344df`, `[0x4a2248]=0.25` |
| затухание | линейное: `gain = vol − atten·dist`, `atten` из данных | `0x46bda4..0x46bdfd` |
| потолок | `gain = min(gain, vol)`; `gain < 2` → запроса нет | `0x46bdcf`, `0x40be58` |
| панорама | `pan = (dot(d, right)/dist + 1)·128`, 0…255 | `0x437909`, `0x46be21` |
| клиппинг 3D | L/R зажимаются в `1…32` (5 бит), 3D-путь не клиппит | `0x40a4f4..0x40a550` |
| приоритет | `priority + vol/2`, 8 голосов, вытеснение по минимуму | `0x40bea6`, `0x40c080` |
| Doppler | **нет**; поле `rate` меняет только длину SOU0 | `0x40a4d9..0x40a5c3` |
| max distance | нет константы: тишина там, где `gain < 2` | — |
| occlusion/reverb | нет | — |

## 1. Цепочка вызовов (один кадр)

```
опкод/скрипт/уровень
   │  21/37/38  → 0x46b840 / 0x46b960   (7–8 аргументов)
   │  187       → 0x46b210 → колонки 0x800340/…
   ▼
очередь 0x62ce18 (stride 0x2c, ≤256, счётчик 0x62fa18)
   ▲                                  │
   │ 0x46b570 (заполнение из SOUND_SOURCES и «эмиттеров» игрока)
   │                                  ▼
   │                        0x46baf0 (раз в вид/кадр):
   │                          distance 0x4344df
   │                          gain     0x46bda4
   │                          pan      0x437909 + 0x46be21
   │                                  │
   │                                  ▼
   │                  запросы 0x4cabd8 (stride 0x20, ≤0x200)
   │                       0x40be20 (one-shot) / 0x40bec0 (loop)
   │                                  │
   │                                  ▼
   │                  планировщик 0x40c080 (8 голосов, приоритет)
   │                                  │
   │                                  ▼
   └── очистка 0x46bae0      старт голоса 0x40a4b0 / 0x40a690
                                     │  L/R = ((255∓pan)·v + 0x3d)/0x7a
                                     ▼
                              голоса 0x84e068 (0x50), микшер 0x409330
```

Точки вызова в кадре: `0x44b5f0` — заполнение (`0x46b570`), затем
`0x447610` → `0x46baf0` (разбор всей очереди для текущего вида) → `0x44793e`
— очистка (`0x46bae0`); `0x44b60a` — планировщик `0x40c080([0x5a4a74])`.
`0x46baf0` вызывается из `0x447936` один раз на вызов `0x447610`; других
вызовов у него нет (grep по листингу).

Очередь живёт **один кадр**: всё, что положили, разбирается и стирается.
Скриптовый one-shot (`loop = 0`) звучит ровно один раз, «эмиттер» уровня
(`loop = 1`) заводится заново каждый кадр из таблицы.

## 2. Источники: что передаёт каждый опкод

| опкод | сигнатура | обработчик | что уходит |
|---|---|---|---|
| 20 `PLAY_SAMPLE` | `NVLLL` | `0x457d3e` → `0x40be20` | 2D: sample, volume, pan, rate, priority |
| 21 `PLAY_SAMPLE_AT_LOCATION` | `NVLLLLL` | `0x457d7f` → `0x46b840` | 3D: sample, volume, rate, priority, `x, y, z` |
| 23 `SPEAK_SAMPLE` | `NVLL` | `0x457f2e` → `0x40bd80` | 2D: sample, volume, pan, rate; позиции нет |
| 37 `PLAY_SAMPLE_AT_SOURCE` | `NVLL` | `0x457dbb` → `0x46b840` | 3D: sample, volume, rate, priority + позиция сущности |
| 38 `PLAY_FRAME_LOOP_SAMPLE_AT_SOURCE` | `LENVL` | `0x457df4` → `0x46b500` → `0x46b960` | loop, rate `0x2b11` = 11025, class из `(hi<<16)|lo` |
| 187 `ADD_SOUND_SOURCE` | `LLLNVD` | `0x459c6e` → `0x46b210` | колонки `x,y,z, sample, volume, atten(f64)` |

### 2.1. `PLAY_SAMPLE_AT_LOCATION` (21)

`0x457d7f`: читает 7 dword'ов операндов и вызывает
`0x46b840(a0, a1, a2, a3, a4, a5, a6)`. В `0x46b840`:

* `a0 → +0x18` sample, `a1 → +0x1c` volume, `a2 → +0x20` rate,
  `a3 → +0x24` priority, `a4/a5/a6 → +0x08/+0x0c/+0x10` x/y/z;
* `+0x00` (atten) = `0x3f9eb851eb851eb8` = **0.03** (`0x46b8ad..0x46b8c1`);
* `+0x14` class = **0**, `+0x28` loop = **0**.

Итого направление: `(sample, volume, rate, priority, x, y, z)`, затухание
жёстко 0.03 на единицу.

### 2.2. `PLAY_SAMPLE_AT_SOURCE` (37)

`0x457dbb`: те же 4 операнда (`NVLL`), а `x,y,z` берутся из кадра ВМ:
`[ebp+0x1c]`, `[ebp+0x20]`, `[ebp+0x24]` (`0x457dc8..0x457de7`). Это
**параметры** точки входа подскрипта `0x457390` (она же читает их в
`0x4573e0..0x4573f6`); `GENERATE` кладёт туда три dword'а из кадра
вызывающего (`0x45fae5..0x45fb01`). По смыслу это позиция сущности, чей
подскрипт исполняется: доказано, что это её параметры, но какой именно
слот рантайм-экземпляра их питает — не трассировано до конца.

### 2.3. `PLAY_FRAME_LOOP_SAMPLE_AT_SOURCE` (38)

`LENVL`: `(event_hi, event_lo, sample, volume, priority)`. `0x457df4`
склеивает `event_hi<<16 | event_lo`, регистрирует class через
`0x46b500(id, 2)` (таблица на 100 слотов `0x62caf8`/`0x62cc88`, class =
`0xa7d8c0 + idx`; второй аргумент — счётчик «keep»: `0x46b584..0x46b59d`
уменьшает его раз в кадр и по нулю гасит class через `0x46ba90`) и зовёт
`0x46b960(sample, class, volume, 0x2b11, priority, x, y, z)`. `rate` всегда
11025, `atten` 0.03, `loop = 1`.

### 2.4. `SPEAK_SAMPLE` (23)

`0x457f2e` → `0x40bd80(sample, volume, pan, rate)`: **не 3D** (позиции в
запросе нет). Запись идёт в 16-слотовую таблицу `0x4cf0a8`
(`0x40bdc0..0x40bde3`, указатель-счётчик `0x4cf6c0`), откуда `0x40c320`
забирает её в голос 7 (`0x40c1d5`: `push 7`). В корпусе `pan` всегда
0/127/128/255 — то есть это обычные 2D-реплики.

### 2.5. `ADD_SOUND_SOURCE` (187)

`0x459c6e` передаёт 7 dword'ов в `0x46b210`, тот раскладывает их по
параллельным массивам (до 128 источников, счётчик `0x800740`):

| операнд | массив | смысл | статус |
|---|---|---|---|
| a0 | `0x800340` | `x` | доказано (`0x46b5e0`) |
| a1 | `0x800540` | `y` | доказано (`0x46b5eb`) |
| a2 | `0x800140` | `z` | доказано (`0x46b5f4`) |
| a3 | `0x7fff40` | **sample** | доказано (`0x46b602` → очередь `+0x18`) |
| a4 | `0x7ffd40` | **volume** | доказано (`0x46b60c` → очередь `+0x1c`) |
| a5/a6 (f64) | `0x800760` | **atten на единицу** | доказано (`0x46b5e4` → очередь `+0x00`) |

Колонка f64 — это **не** pitch: она попадает в `+0x00` записи очереди и
умножается на расстояние в `0x46bda4`. Никакого питча/Doppler в тракте нет.

Каждый кадр `0x46b570` переносит источники в очередь: class `0x3d0900+i`
(4 000 000 + i), rate 16000, priority 1000, loop 1. Там же — «эмиттеры»
игрока (`player+0x346c`, 8 слотов, поля `+0x00` sample, `+0x20` volume,
`+0x40` rate, `+0x60` priority, `+0x80` atten f32), class `0x989680+i`
(10 000 000 + i), позиция — позиция игрока `+0x00/+0x08/+0x10`
(`0x46b652..0x46b6f9`). Роль этих восьми полей (двигатель/гусеницы) не
трассирована — см. §11.

## 3. Очередь `0x62ce18` (stride `0x2c`, ≤256)

| off | тип | поле | доказательство |
|---|---|---|---|
| `+0x00` | f64 | `atten` — затухание на единицу | W `0x46b8ad`/`0x46b8b7` (0.03), `0x46b5e4`; R `0x46bda4` |
| `+0x08` | i32 | `x` | W `0x46b860`, `0x46b5e8`; R `0x46bd63` |
| `+0x0c` | i32 | `y` | W `0x46b86a`, `0x46b5f2`; R `0x46bd4f` |
| `+0x10` | i32 | `z` | W `0x46b874`, `0x46b5f6`; R `0x46bd52` |
| `+0x14` | u32 | `class` | W `0x46b87c` (0), `0x46b5f9` (4e6+i), `0x46b6bf` (1e7+i); R `0x46bd36` |
| `+0x18` | u32 | `sample` (индекс записи `0x83d960`) | W `0x46b882`, `0x46b609`; R → arg1 `0x46be69`, `0x4ca720` |
| `+0x1c` | u32 | `volume` 0…255 | W `0x46b88d`, `0x46b613`; R `0x46bd31`, `0x46bda7` |
| `+0x20` | u32 | `rate` | W `0x46b893`, `0x46b618`; R `0x46be53` |
| `+0x24` | u32 | `priority` | W `0x46b89d`, `0x46b61f`; R `0x46be56` |
| `+0x28` | u32 | `loop` (1 — петля) | W `0x46b8a7`, `0x46b626`; R `0x46bd36` |

Писатели (все — cdecl, аргументы слева направо):

| функция | аргументы | atten | loop | class |
|---|---|---|---|---|
| `0x46b840` | sample, volume, rate, priority, x, y, z | 0.03 | 0 | 0 |
| `0x46b8d0` | sample, volume, rate, priority, x, y, z, atten | явный | 0 | 0 |
| `0x46b960` | sample, class, volume, rate, priority, x, y, z | 0.03 | 1 | явный |
| `0x46b9f0` | sample, class, volume, rate, priority, x, y, z, atten | явный | 1 | явный |
| `0x46ba90` | class | — | 1 | «стоп» (volume 0) |

`0x46b8d0`/`0x46b960`/`0x46ba90` используют и двери/переключатели/лифты
(`0x44f142..0x450435`), т.е. это общая шина 3D-событий, а не только скрипт.

## 4. Слушатель

Слушатель — **объект тела игрока**, на которого сейчас идёт вид:

* `player+0x3178` (`body_object`) заполняется при смене модели `0x4523df`
  (`[esi+0x81c1b8] = eax`, `eax = 0x43b639(0x47c990(sob))`), это указатель,
  а не индекс; `0x4277cd` в этой сборке — тождественная заглушка;
* `0x46bca2` берёт `[player + 0x3178]` для игрока `[ebp+8]`, `0x46bcac`
  проверяет на 0 и передаёт его как `ecx` дальше;
* в `0x437909` этот указатель читается как структура:

| off | тип | поле |
|---|---|---|
| `+0x00/+0x08/+0x10` | f64 | позиция тела (x, y, z) |
| `+0x18/+0x20/+0x28` | f64 | `e1` — вправо (ось панорамы) |
| `+0x30/+0x38/+0x40` | f64 | `e2` — вперёд (взгляд) |
| `+0x48/+0x50/+0x58` | f64 | `e3` — вверх |

Базис пересобирается каждый кадр в камере первого лица:
`0x444c4d` читает указатель, `0x444c62` проверяет на 0, `0x444c8e..0x444c9f`
вызывает `0x41e025(obj+0x18, obj+0x30, obj+0x48, a, b, c)` — ровно те же
столбцы, что описаны в `docs/CAMERA.md` §3.

Углы для **слушателя** — углы шасси, а не камеры:

| аргумент | адрес (игрок 0) | поле игрока | в камере |
|---|---|---|---|
| `a` (крен) | `0x819060` | `+0x20` (крен + view-roll) | так же |
| `b` (тангаж) | `0x819058` | `+0x18` (тангаж) | `+0x18 + [0x81bea0]` (view-pitch) |
| `c` (рыскание) | `0x819068` | `+0x28` | так же |

То есть **мышь вверх/вниз панораму не меняет** (`player+0x2E60` в базис
слушателя не входит, тряска тоже). Позиция — центр шасси, не глаз
(`+0x2F50` не добавляется).

## 5. Формулы

### 5.1. Вектор и расстояние (`0x4344df`)

```
d   = (src.x − lis.x, src.y − lis.y, src.z − lis.z)      // double
a   = sort_desc(|dx|, |dy|, |dz|)
dist = a0 + 0.25·(a1 + a2)                              // [0x4a2248] = 0.25
```

Это **не** евклидова длина, а дешёвая оценка (`0x43452d..0x4345a1`: три
`fabs` (сравнение с 0.0 + `fchs`), затем два сравнения с обменом, затем
`s0 + (s1+s2)·0.25`, где `s0` — максимум). Проверки:
`d=(3,4,0) → 4.75` (а не 5), `d=(100,100,100) → 150.0` (а не 173.2),
`d=(0,0,−7) → 7.0`. Оценка всегда ≤ евклидовой длины, максимум
недооценки −13.4 % (равные компоненты); на панораму это влияет (см. 5.3).

Порог: `dist < 1.0 → 1.0` (`0x46bd84`, `fcomp [0x4a2628]`).

### 5.2. Гейн (`0x46bda4..0x46bdfd`)

```
n     = число бит 0x2 и 0x4 в flags сектора игрока  (0..2)   // 0x46bce5/0x46bcec
scale = 2^n
gain  = trunc(volume − atten·scale·dist_clamped)            // 0x40e0e0, RC=trunc
gain  = gain >> (2·n)                                       // sar edi,cl, cl=2n
gain  = min(gain, volume)
```

* `volume` — поле `+0x1c` (0…255), оно же потолок;
* `atten` — поле `+0x00` (0.03 у скрипта, у источников 0.002…0.3, один
  выброс 8.0 в `level2`);
* `n` — «заглушка» сектора: биты `0x2`/`0x4` флагов сектора игрока
  (`0x800bb0 + idx·0x58`, `idx = player+0x323c`); каждый бит даёт
  `atten×2` и деление гейна на 4;
* `gain < 2` → запрос не создаётся (`0x40be58`: `gain·32>>6 ≤ 0` → выход).

Отсюда практическая слышимость: `dist < (volume − 2)/atten` (при `n = 0`).
Константы `atten` зашиты только у скриптовых (0.03) и у источников (f64 из
данных); «максимальной дистанции» как константы нет.

### 5.3. Панорама (`0x437909`, `0x46be21`)

`0x437909(out, src_pos, listener)` считает три скалярных произведения
`d·e1`, `d·e2`, `d·e3` (строки `0x43793d..0x4379a5`). Потребитель берёт
только **первое** (`d·e1`, то есть проекцию на «вправо»):

```
if dist <= 1.0:   pan = 128                               // 0x46be1a
else:             pan = trunc((dot/dist_clamped + 1.0)·128.0)
                  pan = clamp(pan, 0, 255)                // 0x46be3a..0x46be47
```

Константы: `[0x4a2638] = -1.0` (сдвиг), `[0x4a2640] = 128.0` (масштаб),
деление — на `dist_clamped`, не на «сырое» расстояние. `pan = 0` — строго
слева, `128` — центр, `255` — строго справа.

Вертикаль в панораме не участвует только пока `roll = 0`: при крене `e1`
имеет z-компоненту и высота начинает влиять. Тангаж на панораму не влияет
никогда (он крутит `e2/e3`, но не `e1` при `roll = 0`).

Из-за приближённого `dist` панорама — не точный косинус: на диагонали
`dot/dist` может превысить 1 и «прилипнуть» к 255.

### 5.4. Запрос (`0x40be20` one-shot, `0x40bec0` loop)

```
v = (gain·32) >> 6            // = gain/2, зажимается 1..32; 0 → выхода нет
req.volume   (+0x0c) = v
req.pan      (+0x10) = pan
req.rate     (+0x14) = rate
req.priority (+0x18) = priority + v
req.flags    (+0x1c) = 0x80 (loop) | 0
req.class    (+0x04) = 0 (one-shot) | class (loop)
```

То есть 255-шкала гейна превращается в 5-битную делением на 2 (с
насыщением на 32), а приоритет получает тай-брейк по громкости.
`0x40bec0` дополнительно кладёт `class` — по нему `0x40bf80(class)` умеет
гасить петлю, а планировщик — перезапускать уже играющий звук.

### 5.5. Финальные L/R (`0x40a4b0`, `0x40a690`)

```
L = clamp(((255 − pan)·v + 0x3d) / 0x7a, 1, 32)     // /122, magic 0x4325c53f
R = clamp((pan·v + 0x3d) / 0x7a, 1, 32)
```

`+0x3d` — округление, `0x7a` = 122 = 2·61. При `v = 32` и `pan = 128`
получается 32/32; при `pan = 0` — 32/1; при `pan = 255` — 1/32. Оба канала
всегда ≥ 1, поэтому «панорама в край» не глушит канал полностью, а 3D-путь
сам по себе клиппинга не даёт (насыщение — только в сумме голосов,
`0x8610d0`).

### 5.6. Константы (байты из `.rdata`/`.text`)

| адрес | значение | байты | где читается |
|---|---|---|---|
| `0x4a2628` | `1.0` (мин. дистанция) | `00 00 00 00 00 00 f0 3f` | `0x46bd84` |
| `0x4a2638` | `-1.0` (сдвиг панорамы) | `00 00 00 00 00 00 f0 bf` | `0x46be29` |
| `0x4a2640` | `128.0` (масштаб панорамы) | `00 00 00 00 00 00 60 40` | `0x46be2f` |
| `0x4a2248` | `0.25` (оценка длины) | `00 00 00 00 00 00 d0 3f` | `0x434595` |
| `0x4a68bc` | `32` (pan → 5 бит) | `20 00 00 00` | `0x40be4e` |
| `0x4a6810` | `32000` (выход) | `00 7d 00 00` | `0x40a55e` |
| imm `0x46b8b3`+`0x46b8bd` | `0.03` (atten скрипта) | `b8 1e 85 eb` + `51 b8 9e 3f` = `0x3f9eb851eb851eb8` | `0x46b8ad`/`0x46b8b7` |

## 6. Голоса, приоритеты, клиппинг

* 8 эффект-голосов (`0x84e068`, stride `0x50`) + музыкальный слот 8 —
  см. `docs/SOUND_FIELDS.md` §0/§3. 3D-путь занимает те же 8.
* Планировщик `0x40c080(now)`:
  * гасит флаги `queued`, собирает до 8 запросов с `class == 0` в список
    `0x4cf088`, выбирая максимум `+0x18` (`0x40c0a6..0x40c0c2`);
  * запросы с `class != 0` ищут уже играющий голос того же class
    (`0x4cf658`) и перезапускают его через `0x40c3c0(req, voice)`
    (`0x40c10d..0x40c132`);
  * свободный голос — тот, у которого `voice_until (+0x4cf678) < now`;
    иначе вытесняется голос с **минимальным** `voice_priority`
    (`0x4cf698`), если приоритет запроса не меньше (`0x40c1e8..0x40c233`);
  * голос 7 — отдельный «поток»: перед обычной выдачей он забирает
    следующую запись из таблицы `0x4cf0a8` (`0x40c179..0x40c198` →
    `0x40c320`), туда пишет `SPEAK_SAMPLE` (см. 2.4);
  * `voice_until` — оценка конца (`0x40d0c0` = `(a·b)>>16`), т.е. это
    time-based lifetime, а не «сколько угодно».
* `priority` берётся из данных: у скрипта — 4-й операнд (`AT_LOCATION`
  0…60000, `AT_SOURCE` 0…100000; чаще 1000, 5000, 10000), у источников —
  1000, у эмиттеров игрока — из `+0x60`.
  В запросе к нему прибавляется `gain/2`, так что более громкий из двух
  равных по приоритету выигрывает.
* Клиппинг: `gain` зажат сверху `volume`; L/R — в `1…32`. Клиппинг
  возможен только при суммировании голосов в `int16` (`0x8610d0`).

## 7. Чего в тракте нет

* **Doppler** — нет: в записи очереди нет скорости, `rate` идёт только в
  длину SOU0 (`0x40a4d9..0x40a573`), SOU1/2 вообще не ресемплируются.
* **Окклюзия/препятствия** — нет: `0x4344df` не смотрит на геометрию.
* **Максимальная дистанция** — нет константы; тишина наступает по
  `gain < 2`.
* **Отдельный 3D-микшер** — нет: 3D сводится к двум числам (gain, pan) и
  дальше идёт обычным 2D-путём.
* **Затухание по частоте (low-pass)** — нет, только громкость.
* **Радиус источника** — поля нет: слышимость целиком задаётся парой
  `volume`/`atten` (эквивалентный радиус `≈ volume/atten`, а с учётом
  порога `gain ≥ 2` — `(volume−2)/atten`).

## 8. Ручные вычисления

Все числа воспроизводятся `tools/re/audio_3d.py --calc …` (вывод приведён

### 8.1. `level0:0` — справа, в слышимой зоне

```sh
python3 tools/re/audio_3d.py --calc --call level0:0 --listener 0,3200,48,0
```

```

  pos=(48, 3208, -136)  volume=64  atten=0.03  rate=22050  priority=100  muffle=0
listener: pos=(0, 3200, 48)  roll=0.000 pitch=0.000 yaw=0.000 deg=(0, 0, 0)
  right e1 = (1.000000000, -0.000000000, -0.000000000)
d = source - listener = (48.000, 8.000, -184.000)
dist = max + 0.25*(mid+min) = 184.000 + 0.25*(48.000 + 8.000) = 198.000000
dist_clamped = 198.000000   audible range (volume/atten) = 2133.3
gain = trunc(64 - 0.03*198.000000) = 58  (clamped to <= volume) -> 58
dot = d.right = 48.000000
pan = clamp(trunc((48.000000/198.000000 + 1)*128), 0, 255) = 159
request: volume=29 (gain/2 clipped 1..32), pan=159, rate=22050, priority=129
L/R (5-bit, 0x40a4b0): L = ((255-159)*29+61)/122 = 23, R = (159*29+61)/122 = 32
```

Вручную: `dist = 184 + 0.25·56 = 198`; `gain = 64 − 0.03·198 = 58` (это и
есть потолок, `min(58,64)=58`); `v = 58·32>>6 = 29`;
`pan = (48/198 + 1)·128 = 159.03 → 159`;
`L = (96·29+61)/122 = 23.3 → 23`, `R = (159·29+61)/122 = 38.3 → 32`.

## 10. Доказано / гипотеза / осталось

### Доказано (код)

* цепочка и все точки вызова: `0x457d7f`/`0x457dbb`/`0x457df4`/`0x459c6e`
  → `0x46b840`/`0x46b960`/`0x46b210` → `0x62ce18` → `0x46baf0` →
  `0x40be20`/`0x40bec0` → `0x40c080` → `0x40a4b0`/`0x40a690`;
* поля очереди и запроса (таблицы §3, §5.4), включая `atten` в `+0x00`;
* расстояние = `max + 0.25·(mid+min)` (`0x4344df`), порог `dist ≥ 1.0`;
* гейн `trunc(volume − atten·2^n·dist) >> 2n`, потолок `volume`, порог
  запроса `gain ≥ 2`, `n` из бит `0x2/0x4` флагов сектора;
* панорама `(d·e1/dist + 1)·128` c клампом `0…255` и центр при `dist ≤ 1`;
* слушатель = объект тела (`player+0x3178`), позиция `+0x00`, базис
  `+0x18/+0x30/+0x48`, углы — шасси (`+0x20/+0x18/+0x28`), без view-pitch;
* L/R `((255∓pan)·v + 0x3d)/0x7a`, `v = gain/2` в `1…32`;
* 8 эффект-голосов, приоритет `+0x18 = priority + v`, вытеснение по
  минимальному приоритету, class-перезапуск, `0x40bf80` — стоп по class;
* отсутствие Doppler/окклюзии/макс. дистанции.

### Гипотеза

* `n` (биты `0x2/0x4` сектора) — «заглушка» воды/повреждения; смысл битов
  не доказан, но формула (`×2` к atten, `>>2` к гейну) — код.
* `[0x5a4a74]` — «звуковое время» планировщика (единицы не проверены);
  `voice_until` — оценка конца по длине сэмпла (`0x40d0c0` = `(a·b)>>16`).
* 8 «эмиттеров игрока» (`player+0x346c`, class `1e7+i`) — двигатель/шасси;
  поля и формула чтения доказаны, назначение — нет.
* `SPEAK_SAMPLE` использует слот 7 как отдельный поток (по `0x40c1b2`), но
  приоритет/микширование этого слота не разобраны.

### Осталось

* какой именно сущностью задаётся канал `class != 0` в планировщике (в
  каком порядке перезапускаются петли при совпадении class) — проверено
  только «перезапуск по совпадению»;
* точная единица `[0x5a4a74]` и поведение `voice_until` для SOU1/2;
* стерео в 3D-пути: два 3D-вызова ссылаются на стерео-SOU1
  (`level0`: sample 122 = `VRCHAMBR`, `level20`: sample 125 = `VRCHAMHQ`,
  оба 32 кГц stereo); `right_offset` записи (`+0x14`) в голос не копируется
  (`docs/SOUND_FIELDS.md` §3), поэтому как именно звучит стерео-клип,
  запущенный как 3D-событие, не проверено;
* панорама в split-screen: слушатель берётся по `[ebp+8]` (индекс вида),
  но как выбирается вид в кооперативе — не проверялось.

## 11. Что нужно нашему микшеру (`engine/src/audio/mixer`)

Сейчас `Mixer` (`docs/AUDIO_MIXER.md` §4) считает 3D «по-своему»:
евклидово расстояние, `1/(1+d)` и панораму по горизонтали. Чтобы повторить
оригинал, нужны четыре правки (все — в `PlayParams`/`Listener` и `mix`,
структура голоса не меняется):

1. **`Listener`** — добавить полный базис или, как минимум, `right`:
   `Listener{ Vec3 position; float yaw, pitch, roll; }`, `right` считать как
   `e1` из `0x41e025` (`docs/CAMERA.md` §3). Текущий `forward/right` от
   одного `yaw` — частный случай при `pitch = roll = 0`.
2. **Расстояние** — формула `max + 0.25·(mid+min)` вместо `sqrt`: это
   влияет и на затухание, и на панораму (наш `p3d` на диагонали даст
   другое число). Порог `d < 1 → 1`.
3. **Гейн** — линейный `vol − atten·d` (аттенюация из данных), а не
   `1/(1+d)`: нужен параметр `atten` (по умолчанию 0.03 для скриптовых
   звуков) и потолок `volume`; тишина при `gain < 2` (в 255-шкале).
4. **Панорама** — `(dot(d,right)/d + 1)·128` в 0…255, затем в L/R тем же
   законом `((255∓pan)·v+61)/122` с `v = gain/2` в `1…32` (либо перевести
   в наши Q15-гейны, сохранив отношение). Сейчас у нас линейный закон
   `gl = g·(1−p)`, `gr = g·(1+p)` — это другая кривая.

Дополнительно: `PlayParams::velocity` можно удалить или оставить
неиспользуемым — Doppler в оригинале нет; `kMaxDistance`/`kRolloff` —
наши собственные константы, в оригинале их нет; пул 8+1 против наших 32 —
поведение данных не меняет, но приоритеты (`priority + v`, вытеснение по
минимуму) стоит перенести, если понадобится паритет по «какой звук
замолчал».
