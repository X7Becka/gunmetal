# Экранные эффекты: фейд-«дымка» (HAZE), вспышка урона, палитра (M4.2.8)

Что здесь: как `gundx.exe` v1.36 рисует полноэкранную заливку (фейд/вспышку),
откуда берётся её альфа, как устроена «вспышка урона» (это свет модели
игрока, а не тонировка кадра) и как кадр связан с 6-битной палитрой.

Статус: **цепочка фейда доказана кодом и данными**; для вспышки урона
доказан код (`damage_player` → свет модели), а в скриптах найдены только её
ручные варианты (смерть, маскировка), но не путь «получил урон». Палитра
доказана кодом загрузчика, установщика и формулы яркости. Гипотезы помечены
явно.

Инструмент: `tools/re/screen_fx.py` (stdlib, игру только читает).
Канон по заливке — `docs/SKY.md` §1.3; здесь разобран **источник** `ctx+0xe8`,
кривая и данные, поэтому при расхождении верить этому файлу.

```
python3 tools/re/screen_fx.py --self-test        # 85 проверок, якоря байтов
python3 tools/re/screen_fx.py --map              # карта полей/функций
python3 tools/re/screen_fx.py --scripts          # опись SET_CAMERA_HAZE в *.sbt
python3 tools/re/screen_fx.py --frames           # кадры оракула: полосы/гистограмма
python3 tools/re/screen_fx.py --json             # всё одним объектом
python3 tools/re/screen_fx.py --trace --level 1.3 --decay 0.002
```

## 0. Коротко

| эффект | механизм | адреса | данные |
|---|---|---|---|
| фейд/вспышка экрана | белый полноэкранный квад, `alpha = ftol(255·haze)` | `0x45b3bf` → `0x80f9a8` → `0x44672c`/`0x446764` → `0x83d288` → `0x418c7f` | 247 `SET_CAMERA_HAZE` в 36 `.sbt` |
| затухание фейда | `haze -= dt·0.91·arg2`, ниже 0 не опускается | `0x4572b9`..`0x457300`, `dt` ≤ 45 мс (`0x44d518`) | `arg2 = 0.005` → 220 мс на 1.0 |
| вспышка урона | свет **своей** модели: флаг `0x20` + `p+0x3238` → `inst+0x70` | `0x453b50`, `0x4538d0`, `0x4283ca`, `0x428421`, `0x41ab8f` | `+91·pct/100` мс (`0x453f76`) |
| палитра | 6-бит RGB, `>>2` при загрузке, `<<2` при выводе | `0x47f0ae`, `0x407220` | GAMEPAL / WATERPAL |
| яркость палитры | `out = 63 − (63−b)·(1−level/16)` | `0x4847b0` → `0x40c7d0` | уровень `0..3` (`0x5a4950`) |

«Фейд» и «вспышка урона» — **разные** вещи: первая заливает экран белым,
вторая меняет уровень освещения меша игрока (0..127, `docs/LOOK16.md`).

## 1. Фейд: `SET_CAMERA_HAZE`

### 1.1. Команда

| что | адрес/факт |
|---|---|
| id команды | `80` (`0x50`), `SET_CAMERA_HAZE`, сигнатура `DD` (`docs/VM_EXEC.md`, `gm/sbtvm.py:136`) |
| обработчик | `0x45b3bf` |
| первый операнд (f64) | уровень → `[0x80f9a8]` (`0x45b3bf`..`0x45b3c2`) |
| второй операнд (f64) | скорость затухания → `[0x5e3dd8] = arg·0.91` (`0x45b3cc`..`0x45b400`) |

Разбор ветки (`0x45b3c8`..`0x45b409`):

```
fld  qword [stream+8]        ; второй операнд d
fcom qword [0x4a2570]        ; 0.0
fnstsw ax ; test ah,0x41 ; je 0x45b3fa
    ; d > 0:  rate = d * [0x4a2578] = d * 0.91      (0x45b3fa..0x45b400)
    ; иначе:  rate = 0  (два dword-нуля в 0x5e3dd8/0x5e3ddc, 0x45b3d9..0x45b3e8)
```

`0x4a2578` — ровно `0.91` (f64, проверяется `--self-test`); `0x4a2570` — `0.0`.
При `rate = 0` уровень **никогда** не убывает (см. 1.3), то есть заливка
остаётся до следующей команды.

### 1.2. Тик: `0x457230`

Функция `0x457230(dt_ms)` уменьшает несколько таймеров (`docs/SHAKE.md` §5.4)
и в конце — фейд:

| шаг | адрес |
|---|---|
| `if [0x80f9a8] > 0.0` (сравнение с `0x4a2570`) | `0x4572b9`..`0x4572ca` |
| `fild dt` · `fmul qword [0x5e3dd8]` | `0x4572cc`..`0x4572d0` |
| `fsubr qword [0x80f9a8]` (то есть `haze − dt·rate`) | `0x4572d6` |
| `fst qword [0x80f9a8]` (без pop) | `0x4572dc` |
| если результат `< 0` — оба dword (`0x80f9a8`, `0x80f9ac`) в 0 | `0x4572e2`..`0x457300` |

Вызывается из главного цикла `0x44d993` (и из меню `0x44b7d7`). `dt` — реальный
интервал кадра в мс: `0x44d4c0`..`0x44d539`, с потолком `0x2d = 45` мс
(`0x44d518`, `0x44d51d`); при фиксированной частоте `dt = 91/[0x5a4720]`
(`0x44d4f0`).

Инициализация/сброс: `0x45712b`/`0x457135` обнуляют `0x80f9a8`/`0x80f9ac`
в функции `0x456f50` (камера по умолчанию); её вызывает цепочка рестарта
`0x454cf0` → `0x454d13` (`0x454b0b`, `0x454dcf`).

### 1.3. Мост в кадр: `0x446590` → `0x446764`

`0x446590` заполняет запись камеры/сцены `0x83d1a0`; кадр (`keys_state`,
`0x447610`) передаёт её в Glide-проход: `0x4469b7` push `0x83d1a0` →
`0x41928e`, проход кладёт её в `[ebp-0x14]` (`0x419449`) и отдаёт в
`0x4188b2` (`0x41a2cc`).

Поля, которые читает заливка:

| поле | VA | пишется | смысл |
|---|---|---|---|
| `ctx+0xa8` | `0x83d248` | `0x4465cc` | x (u16) |
| `ctx+0xaa` | `0x83d24a` | `0x4465d7` | y (u16) |
| `ctx+0xac` | `0x83d24c` | `0x446625` | ширина (u16, `&~7`) |
| `ctx+0xae` | `0x83d24e` | `0x4465a8` | высота (u16, `&~3`) |
| `ctx+0xe8` | `0x83d288` | `0x446764` | f32, альфа-доля 0..1 |

`0x44672c` кладёт в x87 `[0x80f9a8]`; дальше идут `fld` ещё четырёх
`double` и `fxch`/`fstp`-серия (`0x446744`..`0x44677a`). Стек сходится так,
что в `0x83d288` попадает именно значение из `0x44672c`:

```
0x44672c fld  [0x80f9a8]      ; ST0 = haze
0x446744 fxch st(5) ; 0x446746 fstp [0x83d230]   ; +0x90 zoom  = [esp+0x74]
0x44674c fxch st(6) ; 0x44674e fstp [0x83d234]   ; +0x94 = 4H·zoom/(3W)
0x446754 fxch st(4) ; 0x446756 fstp [0x83d280]   ; +0xe0 = [0x80d7e0] = 0.9
0x44675c fxch st(1) ; 0x44675e fstp [0x83d284]   ; +0xe4 = [0x80d8a8] = 0.4
0x446764            fstp [0x83d288]              ; +0xe8 = [0x80f9a8]
```

Порядок совпадает с независимой картой `docs/CAMERA.md` §7 (`+0xe0 = 0.9`,
`+0xe4 = 0.4`, `+0xe8 = [0x80f9a8]`), то есть это не совпадение.

### 1.4. Полноэкранный квад (`0x4188b2`)

| шаг | адрес |
|---|---|
| Glide-состояние (вызовы через таблицу `0x4d74xx`) | `0x4188b8`..`0x41890a` |
| если список 2D-примитивов исчерпан — ветка заливки | `0x41891b` → `0x418c7c` |
| `fld dword [ctx+0xe8]` | `0x418c7f` |
| `fmul dword [0x4a20d4]` (`255.0f`) | `0x418c85` |
| `ftol` (`0x40e0e0`) | `0x418c8b`..`0x418c90` |
| `alpha <= 0` → не рисовать | `0x418c93`..`0x418c97` |
| `alpha > 255` → 255 | `0x418c9d`..`0x418ca6` |
| `grConstantColorValue(0xffffff)` | `0x418cb3`..`0x418cb8` |
| альфа во все 4 вершины (`0x4d36xx`) | `0x418d42`..`0x418dc1` |
| координаты вершин из `ctx+0xa8`..`+0xae` | `0x418dc7`..`0x418eb9` |
| `guDrawPolygonVertexListWithClip(4)` | `0x418ec6` |

Вызов защищён флагом `[0x530968] != 0` (`0x41a2bf`..`0x41a2cc`); роль самого
флага в этом файле не разобрана (гипотеза: «2D/HUD-проход включён»).
После квада состояние сбрасывается (`0x418ecc`, `0x418ed2`). Имена точек входа
таблицы `0x4d74xx` сверены только для `0x4d7468` (`grConstantColorValue`) и
`0x4d74bc` (`guDrawPolygonVertexListWithClip`) — см. `docs/SKY.md` §1.3.

Итог: в обычном кадре `[0x80f9a8] = 0`, `alpha = 0`, ветка `0x418c93` уходит
в `0x418ecc` — заливка не рисуется. Это же подтверждают кадры оракула (§4).

### 1.5. Кривая и длительности

```
alpha(t) = clamp( ftol(255 · haze(t)), 0, 255 )
haze(t)  = max(0, level − t_ms · 0.91 · arg2)
```

Затухание линейное по времени кадра, не экспоненциальное; шаг — `dt` кадра
(≤ 45 мс), поэтому по построению на 15 FPS кривая ступенчатая, а суммарное
время то же.

| `SET_CAMERA_HAZE` | раз | затухание до 0 | полностью белый (alpha 255) |
|---|---:|---:|---:|
| `1.0, 0.005` | 125 | 219.8 мс | — |
| `0.35, 0.005` | 72 | 76.9 мс | — |
| `1.3, 0.002` | 28 | 714.3 мс | 164.8 мс |
| `0.7, 0.005` | 15 | 153.8 мс | — |
| `2.0, 0.005` | 2 | 439.6 мс | 219.8 мс |
| `0.7, 0.003` | 2 | 256.4 мс | — |
| `0.8, 0.005` | 1 | 175.8 мс | — |
| `3.0, 0.003` | 1 | 1098.9 мс | 732.6 мс |
| `0.7, 0.02` | 1 | 38.5 мс | — |

Уровень > 1.0 — это «пересвет»: альфа упирается в 255 и держится, пока
`haze > 1.0`. Числа воспроизводятся `--scripts` и `--trace`.

### 1.6. Что включает фейд в поставочных данных

Опись (`--scripts`, 36 `.sbt`, 247 команд) по объемлющим условиям:

| условие | значение | раз |
|---|---|---:|
| `IF SOURCE_FROM_GROUND(96.0)` | `1.0, 0.005` | 37 |
| `IF SOURCE_UNDERWATER` | `1.0, 0.005` | 36 |
| `IF SOURCE_IS_LOCAL_PLAYER_ONE/TWO` (после `SOURCE_SWAP`) | `0.35, 0.005` | 36 + 36 |
| `IF FIRE_SOURCEPLAYER_BULLET(...)` и/или `RANDOM(0.4)` | `1.3, 0.002` | 28 |
| без условия (верхний уровень скрипта) | `1.0` ×52, `0.7` ×12, `2.0` ×2 | 66 |

То есть белая заливка используется как: всплеск при входе в воду и жёстком
приземлении (1.0), вспышка респауна (0.35, 77 мс), вспышка выстрела (1.3,
пересвет 165 мс), и как разовые скриптовые вспышки уровней (0.7…3.0).

### 1.7. Чего фейд не касается

* `NEW_LEVEL` (op 61, `0x457af3`) и `NEXT_LEVEL` (op 62, `0x457b11`) не пишут
  ни `0x80f9a8`, ни палитру — только имя/счётчик уровня (`0x5a47c8`,
  `0x80f9cc`). Переход уровня сам по себе экран не заливает.
* Смерть игрока: в DM-скриптах после «destroyed» идёт не `SET_CAMERA_HAZE`,
  а рампа `SOURCEPLAYER_HAZE_BRIGHTNESS` 127→0 (§2.6) — гаснет модель, не
  экран.
* Катсцены/фильмы: `[0x80f9a8]` встречается в образе только в
  `0x44672c`, `0x45712b`/`0x4572xx`, `0x45b3c2` и `0x49ccxx` — ни одного
  обращения из путей `.sof`/`.sbv`. Кадры `.sof` — индексы общей палитры
  (`docs/FILM.md` §4), отдельного фейда у них нет.
* Перезагрузка/старт игры: `0x456f50` обнуляет `0x80f9a8` (`0x45712b`) —
  после рестарта заливки нет, пока скрипт снова не позовёт команду.

## 2. Вспышка урона и «щита»

### 2.1. Поля игрока

База записи — `0x819040`, шаг `0x3510` (`docs/PLAYER_FIELDS.md` §1).

| поле | VA игрока 0 | смысл | кто пишет |
|---|---|---|---|
| `+0x3200` | `0x81c240` | флаги; бит `0x20` = haze/вспышка, `0x10` = неуязвимость, `0x40/0x80` = заражение | `0x45a2c5`, `0x453f9e`, `0x45a6d9`, `0x45ad4b` |
| `+0x3220` | `0x81c260` | таймер неуязвимости, мс | `0x45ad37` (`+= arg`) |
| `+0x3224` | `0x81c264` | таймер вспышки, мс | `0x45a2b0`, `0x453f8a` |
| `+0x3234` | `0x81c274` | свет модели «по умолчанию» (снимок `inst+0x70` при спавне) | `0x452409` (читает `0x4284bb`) |
| `+0x3238` | `0x81c278` | свет модели во время вспышки | `0x45a47b`, сброс `0x40` — `0x452762` |

Тик — `0x443c0b`..`0x443c3d`: если стоит бит `0x20`, `p+0x3224 -= dt`; когда
таймер ≤ 0, бит снимается (`0x443c34`) и вызывается `0x4538d0` (`0x443c41`).
Бит `0x10` тикает так же в `0x443bd9`..`0x443c01` (без вызова).

### 2.2. `damage_player` (`0x453b50`)

* неуязвимость: `if flags & 0x10 → return` (`0x453b94`);
* «маска»: `param_6 == -1` → `p+0x3224 += (param_7 · 0x5b) / 100`
  (`0x453f62`..`0x453f8a`; `0x5b = 91` набирается тремя `lea`, деление на 100 —
  через магическое `0x51eb851f` в `0x453f6f`);
* если таймер стал > 0 — `flags |= 0x20` (`0x453f9e`) и `call 0x4538d0`;
* `param_6 == -2` → `flags |= 0xc0` (заражение, `0x453fa2`).

### 2.3. Применение: `0x4538d0`

```
0x453aef: edx = flags & 0x20
0x453afa: 0x4283ca(obj, edx)          ; obj+0x70 |= 0x10  (0x428401)
0x453b0c: light = p+0x3238
0x453b1a: 0x428421(obj, light)        ; [obj->0x6c]+0x70 = light (0x42845a)
```

Если бита `0x20` нет, берётся `p+0x3234` (`0x453b29`). `0x4283ca` при снятии
флага делает `obj+0x70 &= ~0x10` (`0x428412`).

### 2.4. Что с этим делает кадр

`inst+0x70` — это **свет 0..127** (та же шкала, что `LOOK16`, `docs/LOOK16.md`):

* `0x41ab8f`: `movsx` байта → `fild` → `fmul [0x9e82b0]` → `/ [0x4a2170]`
  → `0x9e8d24`;
* `0x41be9f`: `light = inst+0x70 + obj+0x74 + tex+0x16 + 0x80` → `0x9e8cf4`;
* `0x41a9fe`: если стоит `obj+0x70 & 0x10` и `light <= 0`, объект **не
  рисуется** (`0x41a9f2`..`0x41aa06`) — так работает «исчезновение» при
  нулевой яркости.

Значит «вспышка урона» — это краткое повышение освещённости собственного
меша (и, при 0, его пропажа), а не красная плёнка на кадре.

### 2.5. `SOURCEPLAYER_HAZE` / `_BRIGHTNESS` (op 120/121)

| команда | id | обработчик | эффект |
|---|---:|---|---|
| `SOURCEPLAYER_HAZE` | 120 (`0x78`) | `0x45a281` | `p+0x3224 += arg` (`0x45a2a6`..`0x45a2b0`); если > 0 — `flags |= 0x20` (`0x45a2c5`) |
| `SOURCEPLAYER_HAZE_BRIGHTNESS` | 121 (`0x79`) | `0x45a455` | `p+0x3238 = arg` (`0x45a47b`) |
| `SOURCEPLAYER_INVINCIBLE` | 122 (`0x7a`) | `0x45ad04` | `p+0x3220 += arg`, `flags |= 0x10` (`0x45ad4b`) |

### 2.6. Поставочные данные

`--scripts`: `SOURCEPLAYER_HAZE` ×108, `SOURCEPLAYER_HAZE_BRIGHTNESS` ×684.

* **Смерть** (`dm1` `0x3a3e`..`0x3a93`): `HAZE(273)` + `BRIGHTNESS` 127, 112,
  96, 80, 64, 48, 32, 16, 0 с `SLEEP 22` между шагами (22 мс — `SLEEP` тикает
  в мс, `0x457315`; вся рампа ≈198 мс), сразу после —
  `ADD_SOURCESCREEN_TEXT 'YOUR R.P.V. HAS BEEN DESTROYED'`.
* **Маскировка** (`dm1` `0xb3b9`): `HAZE(3640)` + `BRIGHTNESS(16)` +
  `SLEEP(3640)` — модель почти чёрная на 3.6 с.
* В обычном уроне скрипт не участвует: таймер ставит только `damage_player`
  (§2.2); `SOURCEPLAYER_HAZE` в поставочных `.sbt` — это смерть, маскировка и
  разовые эффекты уровней.

### 2.7. Неуязвимость

`SOURCEPLAYER_INVINCIBLE` (`0x45ad04`) пишет только таймер и бит `0x10`.
Бит проверяется только в двух местах: `0x443bd9` (тик) и `0x453b94`
(ранний выход из `damage_player`); в кадровом пути его нет. То есть
неуязвимость **не** даёт визуального эффекта (ни мерцания, ни тонировки).

### 2.8. Красный `0xff0000` — не вспышка урона

В той же функции, что рисует заливку, есть второй цвет:
`grConstantColorValue(0x00ff0000)` (`0x4189da`). Он выбирается по полю
`item+0x14` — режим 3 (красный), иначе 2 (белый, `0x418988`); режим ставит
построитель 2D-списка: `item+0x14 = 3`, если `obj+0x75 != 0` (`0x4170e0`),
а `obj+0x75` — это `(sprite_id − 0xbc614e) & 0x7f` (`0x425d38`..`0x425d52`),
т.е. признак специального спрайта, а не урона.

Вывод: полноэкранного **красного** урона в этом билде не найдено. Гипотеза:
«покраснение» в игре — это и есть свет модели (§2.4) плюс красные спрайты
попаданий; отдельной палитровой/полноэкранной вспышки урона нет.

## 3. Палитра

### 3.1. В памяти палитра 6-битная

* Загрузчик `0x47efe0` читает 1024 Б BMP-палитры и пишет по 3 байта на
  запись: `R = pal[2] >> 2`, `G = pal[1] >> 2`, `B = pal[0] >> 2`
  (`0x47f0ae`..`0x47f0cd`; `shr dl,2` — `0x47f0b4`/`0x47f0bd`/`0x47f0c6`,
  порядок байт — `0x47f0c2`).
* Декод текстуры в 16 бит: индекс палитры клампится `0x3f` (`0x418769`) и
  сдвигается `<<2` (`0x41878b`, `0x41879a`) — снова 6 бит, `docs/LOOK16.md`.
* Поэтому `docs/PALETTE.md` прав про **файл** (`GAMEPAL` = 8-битные 203/127/55),
  но в памяти те же слоты лежат как `50/31/13` (203>>2 и т.д.).

### 3.2. `GAMEPAL` и `WATERPAL`

| что | адрес |
|---|---|
| `GAMEPAL` | `0x83d320` (768 Б), грузится `0x44af88` (`"frontend"`, `"gamepal"` → `0x4abbf8`) |
| `WATERPAL` | `0x83d640` (768 Б), грузится `0x44afa3` (`"waterpal"` → `0x4abbac`) |
| текущая палитра | `[0x83d2c4]`, старт `0x44afb3` = `0x83d320` |
| ошибка GAMEPAL | строка `0x4abbb8` |
| ошибка WATERPAL | строка `0x4abb5c` |

Переключение на воду: если у игрока стоит бит `0x8` флагов и состояние
`!= 7`, палитра меняется на `0x83d640` — в цикле по игрокам `0x447962`..
`0x447990` и в мировом проходе `0x449f4d`..`0x449f6e` / `0x449fa3`..`0x449fbf`.
Каждое переключение поднимает локальный флаг (запись `1` в `[esp+0x10]`),
и в конце кадра `0x449eba`/`0x449ec0` палитра переустанавливается.

Если `WATERPAL.BMP` нет, таблица генерируется из `GAMEPAL`:
`R>>2`, `G/2 + 0x10`, `B/2 + 0x0a` (`0x41edd3`, арифметика `0x41ee00`,
`0x41ee20`, `0x41ee41`) — сине-зелёный сдвиг.

### 3.3. Единственная глобальная модуляция — «яркость» `0..3`

| шаг | адрес |
|---|---|
| уровень `[0x5a4950]` (i32) | пишет `keyconfig_loader` `0x484f52`; в меню `--`/`++` — `0x48bf20` / `0x48c7b5` (кламп 0..3), сброс `0x48d7a3` |
| применение | `0x4847b0`: `fild [0x5a4950]`, `×0.25`, `×0.25` (`0x4a2918`), затем `0x40c7d0([0x83d2c4], p)` |
| формула (ветка `[0x4c05c8] == 8`) | `out = ftol(63 − (63 − b)·(1 − p))`, `p = level/16` (`0x40c80e`..`0x40c831`, константы `0x4a1878` = 1.0, `0x4a1880` = 63.0) |
| результат | 765 Б (слоты 1..255) в `0x4cf6c8`, затем `0x407220` |

То есть яркость не умножает, а **подмешивает белый** (в 6-битном пространстве,
точка белого — 63): `b + p·(63 − b)`. Уровни 0..3 дают 0 %, 6.25 %, 12.5 %,
18.75 %. Уровень 0 — таблица не меняется (функция не вызывается, `0x48bf20`).

Установка в DirectDraw: `0x407220` собирает 1024-байтный массив
`PALETTEENTRY` (`<<2` — `0x407268`) и вызывает `SetEntries` с флагами `0x44`
(`0x4072b0`..`0x4072b3`) — только когда `[0x4c05c8] == 8` или включён флаг
`0x2` (`0x407239`..`0x407249`).

В кадре это единственная палитровая модуляция: `0x449ec0` вызывается на
конце кадра, если палитра менялась (флаг из `0x447990`/`0x449f6e`), и
переставляет её с текущей яркостью. Сам `0x40c7d0` вызывается только из
`0x4847b0` (`0x4847ce`), то есть других «модуляторов» яркости нет.

Отдельно от кадра палитру ставят и напрямую (не через `0x4847b0`): например
`0x40cef6` собирает рампу в `0x4cf96c` и вызывает `0x407220`, а фронтенд
`0x490c10` (`0x490da2`) обнуляет 0x300 байт перед установкой — это экраны
фронтенда/загрузки (`0x44b287`), не игровой кадр.

### 3.4. Чего в кадре нет

* Нет «палитровой анимации» урона/фейда: `0x83d320`/`0x83d2c4` не читаются
  в ветках `damage_player`/фейда, а `0x40c7d0` вызывается только из
  `0x4847b0` (меню/яркость/вода).
* `LOOK16` — это не палитровая анимация, а таблица «свет 0..127 → индекс
  палитры» (доказано в `docs/LOOK16.md`); она применяется при расчёте
  освещения вершин/текселей, а не к готовому кадру.

## 4. Кадры оракула (`--frames`)

`out/oracle/win2.png`, `win3.png` — снимки рабочего стола 1920×1080 с окном
игры (`docs/ORACLE.md`). Метрика: средняя яркость luma, 8 горизонтальных
полос, 16-бинная гистограмма, доля пикселей ≥ 240 и «красный сдвиг»
`(R − (G+B)/2)`.

| кадр | mean | std | ≥240 | полосы (сверху вниз) | R/G/B | red_bias | вердикт |
|---|---:|---:|---:|---|---|---:|---|
| `win2` | 36.5 | 34.0 | 0.292 % | 24.6 24.1 40.7 43.1 40.2 36.4 47.4 35.3 | 38.0/36.3/35.5 | +2.13 | фейда нет |
| `win3` | 39.2 | 34.4 | 0.268 % | 36.6 41.3 47.9 31.6 21.1 33.6 56.1 45.6 | 40.5/39.1/38.2 | +1.86 | фейда нет |

Оценка: заливка с `alpha = 255` подняла бы `mean` к ~200+ и `white_frac` к
десяткам процентов; здесь этого нет — согласуется с `haze = 0` в обычном кадре.
Красного сдвига тоже нет (в пределах шума текстур). Порог вердикта в
инструменте намеренно грубый: `mean ≥ 200` или `white_frac ≥ 0.60` —
«white-wash».

## 5. Инструмент `tools/re/screen_fx.py`

* `--self-test` — 47 байтовых якорей (инструкции и константы в exe),
  синтетические кривые (`alpha`, затухание, длительности, `rate = 0`,
  потолок `dt`), формула палитры (`63`-пивот), автогенерация `WATERPAL`,
  опись скриптов и кадры оракула. Выход 1 при любом провале.
* `--map` — карта «VA → поле/функция → роль» (47 якорей проверяются тут же).
* `--scripts` — опись `SET_CAMERA_HAZE`/`SOURCEPLAYER_*` по всем `.sbt`
  с условиями и расчётными длительностями.
* `--frames` — метрики кадров (см. §4).
* `--json` — всё выше одним объектом (включая `unproven`).
* `--trace --level L --decay D --dt MS` — покадровая кривая уровня и альфы.

Инструмент ничего не пишет; пути берутся из `GUNMETAL_EXE` (`exelib`),
`GUNMETAL_GAME`, `GUNMETAL_ORACLE`; для worktree, где нет `out/`, каталог
оракула ищется в основном чекауте.

## 6. Гипотезы и что осталось

1. **Гипотеза:** `[0x530968]` — флаг включения 2D/HUD-прохода; по нему
   `0x41a2bf` проверяется, а `0x41a2cc` вызывает `0x4188b2`, и только там
   рисуется заливка. Имя флага не установлено.
2. **Гипотеза:** «покраснение» при уроне в игре — это свет модели (§2.4) +
   красные спрайты (`obj+0x75`, режим 3). Полноэкранной красной заливки в
   коде нет; если она есть в другом билде, это другой путь.
3. Не разобрано, кто и зачем ставит `obj+0x75` (какие `sprite_id` > `0xbc614e`
   дают красный режим) — нужен разбор `ADD_SPRITE`-идентификаторов.
4. Не проверено, что `0x5a4950` — именно пункт «brightness» меню (доказано
   только, что это одно из 31 поля `keyconfig_loader`, меняемое клавишами
   в диапазоне 0..3 и применяемое к палитре).
5. Точное округление x87→`ftol` проверено для альфы и палитры; для остальных
   потребителей `0x83d288` (только `ctx+0xe8`) вопроса нет.
6. Роль `0x49cc90` (тот же `0x80f9a8` в меню/эффекте) не разобрана: там
   значение масштабируется `×1/3×20` и уходит в `0x49dba0`; это не кадровый
   путь.

## Реализация (2026-10-23)

* **C++**: `VmState::haze` / `haze_rate`, обработчик op 80
  (`VmExecutor::h_camera_haze`: `rate = арг2·0.91`) и тик `vm_tick_haze`
  (`dt ≤ 45 мс`, кламп 0). CTest `vm` проверяет синтетику (пять кадров
  `1 → 0`, `arg2 ≤ 0` без затухания, отрицательный `dt` игнорируется) и
  реальный `level0` (op 80 исполняется в главном блоке).
* **Python**: `gm/render.fade_rgb(alpha)` + `render(fade=…)`, CLI
  `oracle_render.py --fade 0..1` (self-test 20/20: 0 — кадр без изменений,
  255 — белый, 128 — середина, монотонность).
* **Асимметрия намеренная**: Python-ВМ op 80 не моделирует — её состояние не
  входит в сцену, а сравнение трасс (`docs/VM_TRACE.md`) смотрит операнды,
  не поля состояния. Фейд к кадру применяет вызывающая сторона.
* **C++-рендер**: `render/postfx.*` (`haze_alpha` = `ftol(255·haze)`,
  `fade_white` — тот же целочисленный over-блендинг, что в Python),
  `RenderOptions::haze` и CLI `gunmetal --haze 0..1`. Проверка на `level0`
  160×120: `--haze 1` даёт все байты 255, `--haze 0.5` — минимум 127 и
  среднее 169.02 = `(84.16·128 + 255·127)/255`, `--haze 0` — исторический
  кадр без изменений. CTest `postfx`.
* Не сделано: вызов `vm_tick_haze` из игрового цикла (фейд сейчас задаётся
  параметром кадра, а не состоянием) и порядок «фейд до/после 2D-HUD» —
  в оригинале квад рисуется в 2D-проходе.
