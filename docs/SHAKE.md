# Gunmetal — тряска камеры, view-pitch и отдача

Что здесь: как `gundx.exe` v1.36 добавляет к камере первого лица «тряску»
(shake), смещение прицела (view pitch) и отдачу (recoil); какие глобалы и
команды скриптов за это отвечают, какие формулы и константы, что из этого
реально используется в игре.

Дополняет `docs/CAMERA.md` (§6 и §11): там доказан базис `0x41e025` и что
камера прибавляет `[0x81bea0]` к тангажу. Здесь разобраны источник этого
поля, затухание, отдельная система `SET_CAMERA_*_SHAKE` и «отдача» как
физический импульс.

Всё снято с `gundx.exe` v1.36 (`D:\games\Gunmetal 3dfx`), листинг —
`/tmp/opencode/gundx.asm` (objdump, Intel-синтаксис), адреса — VA с базой
`0x400000`. Инструмент: `tools/re/shake.py` (stdlib, игру только читает).

Статус: **формулы и адреса доказаны кодом**; не найдено ни одного
использования shake-команд в поставочных `.sbt` (§7), поэтому «как оно
выглядит в игре» проверяемо только скриптом.

## 0. Коротко

| что | значение | где доказано |
|---|---|---|
| база записи игрока | `0x819040`, шаг `0x3510` | §1 |
| тангаж камеры | `player[0x18] + player[0x2E60] + shake_pitch` | §2 |
| крен камеры | `player[0x20] + shake_roll` | §2 |
| рыскание камеры | `player[0x28] + shake_yaw` | §2 |
| `player[0x2E60]` | свободный view-pitch (мышь/джойстик), зажим ±90° | §3 |
| импульс тангажа | `player[0x2F38]`, одноразовый, гасится в `player[0x2E60]` | §3 |
| затухание view-pitch | `-dt·0.016·k/zoom`; таймеры в этом билде не пишутся → 0 | §3 |
| `player[0x2F40]` | накопленное рыскание, применяется с лимитом `player[0x2D98]·dt` | §4 |
| тряска | три глобальных канала `SET_CAMERA_{PITCH,ROLL,YAW}_SHAKE` | §5 |
| формула тряски | треугольник с периодом `4·period` и пиком `amplitude` | §5 |
| отдача | `SOURCEPLAYER_RECOIL(D)` → горизонтальный импульс скорости `-D·forward` | §6 |
| поля отдачи в оружии | **нет** (684 записи, 21 dword, ни одного recoil) | §7 |
| тик | `dt` в мс, ограничен 45 мс; shake-параметры в мс | §8 |

Однострочно (для углов, без shake):

```
pitch_cam = player[0x18] + player[0x2E60]          # ±30° + ±90°
roll_cam  = player[0x20]                            # ±20°
yaw_cam   = player[0x28]
```

## 1. Карта записи игрока

Запись игрока — массив на 8 игроков с шагом `0x3510`:

* `0x44d918`..`0x44d938` — обход `esi = 0x81c250 + i·0x3510`, `i < 8`;
* `0x452740`..`0x452755` — тот же шаг `0x3510` в инициализаторе
  (`lea`/`shl` даёт `13584·i`);
* `0x459f4f`, `0x45a124` — обработчики скриптов отбрасывают source `>= 8`.

База игрока 0 — `0x819040`; все «глобалы» ниже — это поля записи игрока 0:

| смещение | абсолютный VA | смысл | доказательство |
|---|---|---|---|
| `+0x00` | `0x819040` | x | `0x448d3e` |
| `+0x18` | `0x819058` | тангаж тела/прицела, ±`π/6` | `0x444af8`..`0x444b87` |
| `+0x20` | `0x819060` | крен, ±20° | `0x444aaa`..`0x444ba5` |
| `+0x28` | `0x819068` | рыскание | `0x448dd1` |
| `+0x2D50` | `0x81bd90` | внешняя скорость x (отдача/удар) | `0x459f94`, `0x444478` |
| `+0x2D58` | `0x81bd98` | внешняя скорость y | `0x459fba` |
| `+0x2D60` | `0x81bda0` | скорость тангажа | `0x44493e`, `0x444964` |
| `+0x2D98` | `0x81bdd8` | лимит скорости рыскания (только чтение) | `0x44456a` |
| `+0x2DA0` | `0x81bde0` | скорость рыскания | `0x4439f7`, `0x444618` |
| `+0x2DC0` | `0x81c000` | цель скриптового наклона | `0x45a8c2` |
| `+0x2DC8` | `0x81c008` | скорость скриптового наклона | `0x45a8d6` |
| `+0x2DE8` | `0x81be28` | добавка к крену | `0x444b99` |
| `+0x2E60` | `0x81bea0` | **view pitch** | §3 |
| `+0x2E68` | `0x81bea8` | минимум `-π/2` | `0x4527b3` |
| `+0x2E70` | `0x81beb0` | максимум `+π/2` | `0x4527c3` |
| `+0x2F38` | `0x81bf78` | одноразовый импульс тангажа | `0x443a16` |
| `+0x2F40` | `0x81bf80` | накопленное рыскание | `0x4439c2` |
| `+0x2F48` | `0x81bf88` | множитель затухания, 0.5 | `0x44d6ca` |
| `+0x2F50` | `0x81bf90` | высота глаза | `0x448d2b` |
| `+0x2FE0` | `0x81c020` | делитель затухания (zoom) | `0x44d730` |
| `+0x3210` | `0x81c250` | состояние игрока | `0x44382d` |
| `+0x3358` | `0x81c398` | флаг «сбросить view pitch» — не пишется | `0x443a5e` |
| `+0x3360/64` | `0x81c3a0/a4` | таймеры затухания — не пишутся | `0x443a36` |

Инициализатор/сброс записи — `0x452730` (его вызывает спавн `0x452670`
в `0x452698`): он обнуляет `+0x2E60`, `+0x2F38`, `+0x2F40`, `+0x2F48` и
ставит `+0x2E68 = -π/2`, `+0x2E70 = +π/2` (`0x4527a2`..`0x4527d0`).

## 2. Куда камера прибавляет углы

`0x446590` собирает кадр первого лица. Три угла лежат в стековых
аргументах функции (два `f64` на каждый) и уходят в `0x41e025`:

* `0x4468e3`..`0x446900` — шесть dword'ов складываются в три `f64`;
* `0x446910` — вызов `0x41e025`.

Разбор push-последовательности даёт (см. также `docs/CAMERA.md` §4):

| аргумент `0x41e025` | стек `0x446590` | значение |
|---|---|---|
| `a` (крен) | `[esp+0x58]` | `player[0x20]` |
| `b` (тангаж) | `[esp+0x50]` | `player[0x18] + player[0x2E60]` |
| `c` (рыскание) | `[esp+0x60]` | `player[0x28]` |

Именно в эти слоты дописывают shake-каналы (§5), поэтому порядок
«pitch, roll, yaw» проверяется ещё и по именам команд.

Вызовы камеры первого лица, где видно `fadd [player+0x2E60]`:
`0x447e43`, `0x447f25`, `0x448b99`, `0x448cee`, `0x4493dd`, `0x449532`,
`0x44fde9`; cutscene-путь — `0x4471a8`, `0x4472ac`.

Тот же суммарный тангаж используется не только для картинки: `0x478013`
и `0x47876b` строят по нему направление (basis через `0x41e025` /
`0x41e360`), когда игрок целится/стреляет. То есть `player[0x2E60]` —
это **угол взгляда**, а не косметическая «отдача».

## 3. `player[0x2E60]` — view pitch

### 3.1. Формула кадра

Функция `0x443690(player_index, dt_ms)` вызывается из главного цикла
(`0x44d921`) для каждого живого игрока. Ветка `0x443a03`..`0x443ac8`:

```
pending  = player[0x2F38]
if pending != 0:
    player[0x2E60] += pending          ; 0x443a16..0x443a22
    player[0x2F38]  = 0                ; 0x443a28
else:
    player[0x2E60] -= (player[0x3360] - player[0x3364]) * 0.016
                                       ; 0x443a36..0x443a58
if player[0x3358] != 0:                ; 0x443a5e
    player[0x2E60] = 0
player[0x2E60] = clamp(player[0x2E60], -π/2, +π/2)
                                       ; 0x443a72..0x443ac2
```

Вторая копия той же логики — `0x443f6d`..`0x44406b` (ветка, которая
исполняется после обхода игроков и коллизий). Отличия:

```
k = 1.0                                если player[0x2F48] < 0.5
k = 0.25 + 1.5 * player[0x2F48]        иначе          ; 0x443f80..0x443f94
player[0x2E60] -= (t1 - t2) * 0.016 * k / player[0x2FE0]
                                                       ; 0x443fcf..0x443ff9
```

Константы (все `f64`):

| VA | значение | роль |
|---|---|---|
| `0x4a2308` | `0.016` | скорость затухания, рад на единицу таймера |
| `0x4a2310` | `0.5` | порог `k(scale)` |
| `0x4a2318` | `-1.5` | наклон `k` |
| `0x4a2320` | `0.25` | свободный член `k` |
| `0x4a22d8` | `1.0` | `k` при `scale < 0.5` |
| `0x4a22e0` | `0.0` | сравнения |

Зажим задан не константами, а полями игрока: `0x4527b3` кладёт
`0xBFF921FB54442D18 = -π/2`, `0x4527c3` — `0x3FF921FB54442D18 = +π/2`.

### 3.2. Откуда берётся импульс

Очередь ввода (`0x44d640`..`0x44d860`) переносит накопленные дельты в
поля игрока:

```
player[0x2F38] += [0x5a4a88]           ; 0x44d6d6..0x44d6ed
player[0x2F40] += [0x5a4a98]           ; 0x44d6f9..0x44d713
```

`0x5a4a88`/`0x5a4a98` — массивы на двух локальных игроков (слоты 0/1,
разнос 8 байт). Их пишет обработчик аналоговых осей
`0x44c8f2`..`0x44c9c2`:

```
delta = axis_now - axis_prev                  ; 0x4bfcd4/d8/dc, 16-битные
sen   = [0x4aac38 + 8*axis]                   ; чувствительность
val   = delta * sen * (±1/1024)               ; 0x4a2430 / 0x4a2438
```

То есть 1 отсчёт оси = `1/1024` рад. При `[0x5a4938] == 1` дельта идёт
в первый слот очереди (`0x5a4a88`/`0x5a4a98`), иначе — во второй
(`0x5a4a90`/`0x5a4aa0`); очередь затем раскладывает их по двум локальным
игрокам (`0x44d652`/`0x44d767`).

### 3.3. Затухание — мёртвая ветка в этом билде

Обе копии вычитают `(player[0x3360] - player[0x3364]) * 0.016`.
Но **ни одна инструкция в `gundx.exe` не пишет** `0x81c3a0`,
`0x81c3a4`, `0x81c398`, `0x81c3b4`, `0x81c3b8`:

* все вхождения этих VA — только чтение (`0x443a36`, `0x443fcf`,
  `0x443a5e`, `0x444001`, `0x44478b`);
* в инициализаторе `0x452730` они не обнуляются отдельно — массив игроков
  целиком лежит в BSS (VA за концом файла, `va2off()` для `0x819040`
  возвращает `None`), поэтому стартует с 0;
* косвенных писателей через указатель тоже нет: смещения `0x3360`,
  `0x3364`, `0x3358`, `0x3374`, `0x3378` не встречаются в листинге
  ни разу (ни как `[reg+0x3360]`, ни как `add reg,0x3360`).

Следствие: **в обычной игре view-pitch не затухает** — это и есть
механизм «мышь двигает прицел, прицел остаётся». Значение `0.016` рад/мс
(≈16 рад/с) для плавного возврата в центр неправдоподобно велико, что
согласуется с тем, что ветка осталась от другой схемы ввода/сетевой
интерполяции.

> Гипотеза (не доказана): таймеры заполняются сетевым/демо-снимком,
> который копируется в запись игрока целиком. В `0x467120`..`0x467260`
> есть поштучное восстановление полей из снимка `0x61ec00` (включая
> view-pitch `0x61ec64`), но `0x3360` там нет.

### 3.4. Кто ещё пишет view pitch

1. **Скриптовый наклон** `SOURCEPLAYER_FALL_PITCH_DOWN(D,D)`
   (id `0x91`, обработчик `0x45a896`): пишет цель и скорость в
   `player[0x2DC0]`/`+0x2DC8`. В кадре `0x444bab`..`0x444c47` из них
   считается добавка и при необходимости пишется прямо в `player[0x2E60]`
   (зажим `±π/2`), а `player[0x18]` обнуляется; флаг `0x2000` в
   `player[0x3200]` не даёт повторно применять наклон.
2. **Снимок состояния** `0x46714e`: `f32 [0x61ec64] → player[0x2E60]`.
3. **Сброс**: `player[0x3358] != 0` (`0x443a5e`), конец скриптового
   наклона (`0x444c32`).

Прямой записи из кода стрельбы нет (§7.2).

## 4. `player[0x2F40]` — накопленное рыскание

Симметричный канал, но с ограничением скорости. В `0x4439af`..`0x443a03`:

```
if player[0x2F40] != 0:
    player[0x28]   += player[0x2F40]     ; 0x4439c8
    player[0x2F40]  = 0
    player[0x2DA0]  = 0
else:
    player[0x28] += dt * player[0x2DA0]  ; 0x4439f7
```

Более полная ветка — `0x44452c`..`0x44462e`: при `player[0x2F40] != 0`
шаг ограничивается `player[0x2D98] * dt` (лимит скорости поворота,
`0x44456a`..`0x444581`), остаток остаётся в `player[0x2F40]`; иначе
рыскание интегрируется из `player[0x2DA0]`.

> Точный знак/ветвление лимита (`0x44457e`) не разобран до конца:
> `player[0x2D98]` в этом билде тоже **никем не пишется** (только
> чтение в `0x443940`, `0x443963`, `0x44456a`, `0x4442c4`), поэтому
> фактический лимит может быть нулевым, а шаг — полным. В модели
> `shake.py` лимит включается только при `yaw_rate_max > 0`.

В режиме «демо/скриптового поворота» (`[0x5a46f0] != 0`) рыскание
подменяется значением `[0x64bbc8]` (`0x443990`..`0x4439ad`,
`0x44450a`..`0x444527`).

## 5. Собственно тряска: `SET_CAMERA_*_SHAKE`

Это отдельная от view-pitch система: три **глобальных** канала
(не на игрока), которые добавляются к углам уже внутри `0x446590`.

### 5.1. Команды

| команда | id | обработчик | сигнатура | амплитуда | период | длительность |
|---|---|---|---|---|---|---|
| `SET_CAMERA_PITCH_SHAKE` | `0x4d` | `0x45b411` | `APP` | `0x80f828` | `0x80f9a0` | `0x80d8bc` |
| `SET_CAMERA_ROLL_SHAKE` | `0x4e` | `0x45b462` | `APP` | `0x80f820` | `0x80d8b0` | `0x80d8c4` |
| `SET_CAMERA_YAW_SHAKE` | `0x4f` | `0x45b4b3` | `APP` | `0x80f838` | `0x80f9c8` | `0x80d7e8` |

`A` = `f64` (амплитуда, радианы), `P` = `int32` (период и длительность,
миллисекунды). Обработчик сразу делит амплитуду на период
(`0x45b451`), а неположительный период заменяет на 1 (`0x45b441`).

### 5.2. Формула

В кадре (`0x4467ef`..`0x4468b1`), для каждого канала:

```
if duration <= 0:  добавка = 0
p = period                                  ; >= 1
r = duration mod (4*p)                      ; idiv, 0x446806
s = (r < 2*p) ? (r - p) : (3*p - r)         ; 0x446808..0x44681d
angle += (amplitude / p) * s                ; 0x44681f..0x44682d
```

Это треугольная волна с периодом `4p` по `duration`, пиком `amplitude`
и нулями при `r = p` и `r = 3p`. Поскольку `duration` убывает на `dt`,
волна проходится в обратную сторону.

Проверка (P = 100 мс, A = 0.4 рад):

| `duration` | `r` | `s` | добавка |
|---:|---:|---:|---:|
| 400 | 0 | -100 | **-0.400** |
| 300 | 300 | 0 | 0 |
| 200 | 200 | +100 | **+0.400** |
| 100 | 100 | 0 | 0 |
| 1 | 1 | -99 | -0.396 |

Та же таблица воспроизводится `shake.py --trace`.

### 5.3. Куда добавляется

| канал | стековый слот | угол |
|---|---|---|
| pitch | `[esp+0x50]` | `b` (тангаж) |
| roll | `[esp+0x58]` | `a` (крен) |
| yaw | `[esp+0x60]` | `c` (рыскание) |

Важно: shake добавляется **после** клампов игрока. Тангаж тела ограничен
±30°, view-pitch ±90°, но их сумма со shake может выйти за 120°; крен
shake тоже не проходит через кламп ±20° (тот применяется только к
`player[0x20]` в `0x444aaa`).

### 5.4. Тик

Таймеры уменьшает `0x457230(dt_ms)` — вызов из главного цикла `0x44d993`:

```
0x457271..0x4572b3:  [0x80d8bc] -= dt;  [0x80d8c4] -= dt;  [0x80d7e8] -= dt
                     (ниже нуля не опускаются)
```

`dt` — реальный интервал кадра в мс (`0x44d4c0`..`0x44d539`), с потолком
`0x2d = 45` мс (`0x44d518`).

## 6. Отдача: `SOURCEPLAYER_RECOIL(D)`

id `0x76`, обработчик `0x459f4d`. Это **не** добавка к камере, а
горизонтальный импульс скорости игрока:

```
p = player[source]
p[0x2D50] -= sin(p[0x28]) * |cos(p[0x2E60])| * D    ; 0x459f88..0x459f9a
p[0x2D58] -= cos(p[0x28]) * |cos(p[0x2E60])| * D    ; 0x459fb4..0x459fc7
```

Разбор x87-стека: `fsin(yaw)`, `fcos(view_pitch)`, `fabs`, `fmulp`,
`fmul D`, `fsubr [0x2D50]` — то есть ровно минус проекция «вперёд» на
горизонталь. Вертикальная составляющая (`-sin(pitch)`) не применяется:
отдача толкает только по плоскости X/Y.

Скорость `p+0x2D50/58` затем интегрируется в позицию с трением
(`0x444478`..`0x4444d5`) и корректируется при столкновении
(`0x45104e`..`0x4510f9`).

Использует только view-pitch `p[0x2E60]`, а не тангаж тела
`p[0x18]` — ещё одно подтверждение, что «отдача» в `CAMERA.md` и
«view pitch» — разные вещи.

## 7. Оружие, патроны, оборудование

### 7.1. Полей отдачи в таблицах нет

Проверено по всем 36 поставочным `.sbt`: **684 записи** `DEFINE_WEAPONS`,
19 уникальных имён, у всех одинаковая сигнатура — 17 операндов
(21 dword после развёртки `f64`). Карта полей (`tools/re/sbt_fields.py`,
`docs/FORMATS.md` 12.3):

| файл → память | поле |
|---|---|
| d0 → `+0x24` | fire mode |
| d1 → `+0x2c` | fire period |
| d2 → `+0x3c` | ammo type index |
| d3 → `+0x40` | ammo per shot |
| d4/d5 → `+0x30/+0x34` | projectile id / alt |
| d6 → `+0x38` | state value |
| d7 → `+0x4c` | id |
| d8 → `+0x44` | price |
| d9 → `+0x48` | weight |
| d10 → `+0x28` | flags |
| d11 → `+0x294` | class index |
| d12/13 → `+0x00` | charge rate (`f64`) |
| d14..d17 → `+0x08..0x14` | spread cone tan 1/2 |

Ни одного поля «recoil/kick/shake». Запись 0x2a8 (`0x445c49`,
`0x445caf`), массив `0x80fa00`.

### 7.2. Код стрельбы не трогает камеру

Функция выстрела заканчивается на `0x445f91`; она:

* ставит кулдаун `player[0x3318] = weapon[+0x2c]` (`0x445f02`..`0x445f08`);
* ставит `GENERATE`-событие через `event_post` `0x4795b0` с
  `weapon[+0x30]`/`[+0x34]` (`0x445eee`, `0x445f61`); объект создаёт
  подскрипт сущности, см. `docs/EVENTS.md`;
* выставляет состояние `player[0x331c] = weapon[+0x38]` (`0x445f75`);
* играет звук `0x454900` (`0x445f82`).

Записи в `0x80f828/0x80f820/0x80f838` (shake) или в `0x81bea0`
(view pitch) здесь нет; вообще единственные писатели shake-глобалов —
три VM-обработчика `0x45b411/0x45b462/0x45b4b3`.

Патроны (`0x818960`, запись `0x38`) и оборудование (`0x814c60`, запись
`0x40`; `0x814c8c` — точка входа загрузчика в подблок `+0x2c`,
`0x450e87`) в путях тряски/отдачи не встречаются вообще: ни одного
обращения из `0x443690`, `0x446590`, `0x457230`, `0x459f4d`.

### 7.3. Скрипты команд не используют

`grep` по всем 36 `.sbt`: `SET_CAMERA_PITCH_SHAKE`,
`SET_CAMERA_ROLL_SHAKE`, `SET_CAMERA_YAW_SHAKE`, `SOURCEPLAYER_RECOIL`,
`SOURCEPLAYER_FALL_PITCH_DOWN` — **0 совпадений**. То есть в кампании и
DM эти механизмы не задействованы; они доступны авторам уровней, но
поставочные данные их не вызывают.

## 8. Тики и частота

* `0x443690(index, dt)` — обновление игрока; `dt` — мс.
* `0x457230(dt)` — таймеры shake; тот же `dt`.
* `dt` считается в `0x44d4c0`..`0x44d539`:
  * при `[0x83d634] != 0` — `dt = [0x5a4a74] - [0x5a46e8]`;
  * иначе — `dt = 0x5b / [0x5a4720]` (фиксированный шаг, `91/делитель`);
  * `dt` ограничен `0x2d` (45 мс).
* `0x4436a2`: в режимах `[0x83cb7c] == 2` и `== 5` обновление игрока
  (и вся ветка view-pitch) не выполняется.
* Параметры `SET_CAMERA_*_SHAKE` — в **миллисекундах** (обработчик не
  переводит их в кадры, таймер вычитает `dt` мс).

## 9. Смерть/респавн: состояние 7

Единственная найденная «анимация камеры», кроме shake и скриптового
наклона (§3.4), — обработчик состояния 7 (`0x4452d8[5] = 0x443846`). Он на каждом миллисекундном
тике `dt` раз делает:

```
pitch = 0.95 * pitch + 0.01308996938995747   ; +0.75°
roll  = 0.95 * roll  + 0.019634954084936207  ; +1.125°
```

(`0x44385b`..`0x44388c`, константы `0x4a22e8 = -0.95`,
`0x4a22f0 = 0.75°`, `0x4a22f8 = 1.125°`; знак минус в `fmul`
компенсируется `fsubr`.)

Пределы: тангаж → `0.01309/0.05 = 15°` (вниз, т.к. `pitch > 0` — вниз),
крен → `22.5°`, но крен затем клампится ±20° (`0x444aaa`). Точный триггер
состояния 7 (смерть или конец уровня) по коду не прослежен: записей
`player[0x3210] = 7` в билде нет — состояние приходит извне.

## 10. Опровергнутые гипотезы

| гипотеза | почему неверна |
|---|---|
| `[0x81bea0]` — отдача от выстрела | поле пишется из аналогового ввода (мышь/джойстик, `0x44c8f2` → `0x5a4a88` → `0x81bf78` → `0x81bea0`), сохраняется в снимке (`0x46714e`) и используется как угол взгляда для наведения (`0x478013`); прямой связи с выстрелом нет |
| view-pitch затухает к нулю за ~секунду | таймеры `0x3360/0x3364` в билде не пишутся ни одной инструкцией → вычитаемое всегда 0 |
| отдача — это добавка к тангажу камеры | `SOURCEPLAYER_RECOIL` меняет `p+0x2D50/0x2D58` (скорость), а не углы; вертикальная составляющая не применяется |
| тряска — это `[0x81bea0]` | тряска живёт в трёх глобальных каналах `0x80f820/28/38` и добавляется в `0x446590` уже после сборки углов; `0x81bea0` — состояние игрока |
| амплитуда shake — это «сила в кадр» | обработчик делит амплитуду на период; добавка за кадр = `A·s/P`, где `s` — треугольник в единицах периода |
| период shake — полный период волны | полный период `4·period`; аргумент `P` — четверть периода (нули при `r = P`, `3P`) |
| тряску задаёт оружие (fire period/weight) | ни одно поле `DEFINE_WEAPONS` не читается в путях shake; fire period идёт только в кулдаун `player[0x3318]` |
| `SET_CAMERA_*_SHAKE` используется в кампании | 0 совпадений по 36 `.sbt` |
| shake-таймер в кадрах | таймер вычитает `dt` в мс; параметры в мс (`0x457271`) |
| shake не может превысить лимиты игрока | shake добавляется после клампов; крен shake не клампится ±20° |

## 11. Что осталось

1. **Кто пишет `0x81c3a0/a4/398/b4/b8`.** В статическом образе — никто.
   Либо мёртвый код, либо запись идёт через массовое копирование
   состояния (сеть/демо), которого я не нашёл. Пока в модели эти поля
   параметры с нулём по умолчанию.
2. **`player[0x2D98]` (лимит скорости рыскания).** Только читается; откуда
   берётся значение (шасси? таблица игрока?) — не найдено. Ветка лимита
   `0x44457e` разобрана не до конца (знак шага).
3. **Реальные значения амплитуд/периодов/длительностей shake.** Ни один
   поставочный `.sbt` команды не вызывает; эталонных кадров с тряской нет.
4. **Источник `0x5a4a88/0x5a4a98` для второго слота.** Маппинг
   `[0x5a4938] == 1` → слот 0, иначе слот 1 подтверждён кодом, но
   семантика `[0x5a4938]` (число локальных игроков? режим?) — нет.
5. **Скриптовый наклон `SOURCEPLAYER_FALL_PITCH_DOWN`.** Цель/скорость
   (`0x81c000/08`) и запись в `0x81bea0` найдены, но полная логика
   `0x444bab`..`0x444c47` (флаг `0x2000`, взаимодействие с `player[0x18]`)
   не проверена на данных.
6. **Триггер состояния 7.** Формула «сползания» камеры есть, но что
   именно переводит игрока в 7 — не прослежено.
7. **Влияние урона/взрыва.** Прямой связи «урон → shake/view-pitch» в
   коде нет; возможно, эффект задаётся скриптами уровней (которых в
   поставке нет) или достигается через `SOURCEPLAYER_RECOIL`.

## 13. Воспроизведение

```sh
# математика и защита от NaN
python3 tools/re/shake.py --selftest

# калибровка (адреса, константы, формулы) в JSON
python3 tools/re/shake.py --json

# треугольная волна SET_CAMERA_PITCH_SHAKE
python3 tools/re/shake.py --trace --amp 0.05 --period 200 --duration 800

# отдача SOURCEPLAYER_RECOIL(200) при yaw=30°, view pitch=10°
python3 tools/re/shake.py --recoil 200 --yaw 30 --view-pitch 10

# листинг и точечные проверки
python3 tools/re/disrange.py 0x443a00 0x443ad0
python3 tools/re/disrange.py 0x4467e0 0x4468c0
python3 tools/re/disrange.py 0x459f40 0x459fd0
python3 tools/re/cmdtable.py COMMANDS | grep CAMERA_.*SHAKE
```

`shake.py` не открывает exe: все константы зашиты вместе с VA, поэтому
`--selftest` работает без установки игры. Сверка с бинарником — глазами
по `disrange.py` (адреса в §12).
