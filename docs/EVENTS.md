# Event queue and `GENERATE` events

**Статус:** механика очереди событий доказана по декомпиляции Ghidra 12.1.4
(2026-10-20). Старое имя `0x4795b0 = projectile_spawner` **опровергнуто**:
функция только кладёт событие в очередь. Спавн объекта происходит позже, в
подскрипте сущности через `GENERATE`.

## 1. `event_post` — `0x4795b0`

Сигнатура в декомпиляторе усечена (`int, u16, int, int`), потому что остальные
аргументы лежат в стеке. Реальные вызовы (например `0x445eee`, `0x445f61`)
передают id события, u16, два i16, три `double` и `u32`. Координаты
прогоняются через `__ftol` (`0x40e0e0`, `FISTP` с truncate) и пишутся как
**i32**, а не f32.

Функция пишет запись одного из двух форматов:

### Тип 1, размер `0x1b`

| offset | тип | поле |
|---|---|---|
| `+0x00` | u8 | тип = 1 |
| `+0x01` | u32 | `event_id` |
| `+0x05` | u16 | `param` |
| `+0x07` | i16 | `arg_a` |
| `+0x09` | i16 | `arg_b` |
| `+0x0b` | i32 | `x` |
| `+0x0f` | i32 | `y` |
| `+0x13` | i32 | `z` |
| `+0x17` | u32 | `extra` |

### Тип 3, размер `0x17`

| offset | тип | поле |
|---|---|---|
| `+0x00` | u8 | тип = 3 |
| `+0x01` | u32 | `event_id` |
| `+0x05` | u16 | `param` |
| `+0x07` | i32 | `x` |
| `+0x0b` | i32 | `y` |
| `+0x0f` | i32 | `z` |
| `+0x13` | u32 | `extra` |

Тип выбирается по `arg_a == 0 && arg_b == 0`: тогда пишется тип 3, иначе тип 1.

### Тип 2 — `Trigger Switch`, 7 байт

| offset | тип | поле |
|---|---|---|
| `+0x00` | u8 | тип = 2 |
| `+0x01` | u32 | `switch_index` (индекс таблицы `0x5a4af0`) |
| `+0x05` | i16 | `source` |

Писатель — `0x479810`; обработчик `0x44f960` вызывает `generate_event` и
3D-звук (для `kind >= 0x101` позиция — центроид сектора).

### Типы 4…12 — текст/чат

| offset | тип | поле |
|---|---|---|
| `+0x00` | u8 | `channel + 5` (4 = системный канал `-1`, 5…12 = игроки 0…7) |
| `+0x01` | u8 | `font` (0…0x1e) |
| `+0x02` | char[] | текст, NUL-терминированный |
| `+len+3` | — | один **незаписанный** байт-пропуск |

Писатель `0x4798b0` пишет `2 + len + 1` байт, но счётчик увеличивает на
`len + 4`; диспетчер шагает так же. Реестр сообщений — `0x619860`
(10 записей, дедуп по text/kind/font, дедлайн `time + 0x111`).

Очередь:

- в режимах `DAT_0083d620 == 2/3` — staging `0x62fbc8`, счётчик `0x62fbc0`;
  копия идёт в `0x79cf80` и `0x7a44c0` (сетевой снимок);
- иначе — буфер `0x79cf80`, счётчик `0x79cf6c`;
- счётчик — **в байтах**, буфер ровно `0x7530`; пороги писателей разные:
  `0x750e` (типы 1/3), `0x7526` (тип 2), `0x74de` (типы 4…12);
- порядок FIFO; счётчик перечитывается на каждой итерации, поэтому
  самопостинг из подскрипта обрабатывается в том же проходе;
- неизвестный тип (0, 13+) → `printf("Internal Error: Bad event value...")`,
  затем `count = 0` — вся очередь теряется.

`event_post` **не создаёт объект, не ищет модель и не задаёт скорость**. Это
только очередь.

Мост THING → очередь: `gm::post_thing_event(queue, thing, kind)` берёт id из
`Thing::create_event`/`damaged`/`destroy`/`expire`/`timeout`/`collide`
(+0x1f0/+0x1f4/+0x1f8/+0x1ec/+0x1c0/+0x1c4), координаты — из абсолютной
`Thing::position`, `extra = id − 0xfff8` (как `0x4703a0`/`0x470290`).
Source-relative вещь без мировой точки даёт координаты 0: оригинал берёт
трансформацию через `FUN_004277cd`, а C++ статическое представление её не
хранит.

## 2. `event_dispatch` — `0x4799b0`

В начале кадра (при `DAT_0083d620 == 2/3`) записи копируются из staging-буфера
`0x62fbc8` в `0x79cf80`, затем идёт цикл по записям. Переключатель — **байт
типа**, а не event id:

| тип | обработчик | статус |
|---|---|---|
| 1, 3 | `generate_event` (`0x479960`) | код |
| 2 | `FUN_0044f960` | **C++** `EventDispatcher` (§2.2) |
| 4…12 | `FUN_00463ab0(record + 2, ...)` | **C++** `TextRegistry` (§2.1) |
| иное | `Internal Error: Bad event value in do_events()` | код |

Для типа 1 в `generate_event` передаются id, u16, два i16, x/y/z, extra; для
типа 3 — без i16.

### 2.1. Реестр сообщений — `0x619860`

Записи типов 4…12 не порождают событие, а попадают в **реестр сообщений**
(10 слотов). Разбор `FUN_00463ab0` (post), `FUN_00463e00` (expire),
`FUN_00463bc0`/`FUN_00463ef0` (draw) и `FUN_00463a90` (clear):

| что | где | смысл |
|---|---|---|
| текст | `0x619860 + i·0x32` | `strncpy(dst, src, 0x32)` + принудительный NUL в конце слота → **не более 0x31 = 49 символов** |
| kind/канал | `0x619838 + 4i` | `-1` = системный канал, `0…7` = игроки |
| font | `0x619a58 + 4i` | индекс шрифта (из байта `+1` записи) |
| deadline | `0x619810 + 4i` | `DAT_005a46e4 + 0x111` (номер кадра + 0x111) |
| updated | `0x619a80 + 4i` | глобальный счётчик `0x619ab0` на момент записи |
| число | `0x619aac` | 0…10 |
| счётчик | `0x619ab0` | растёт на **каждое** принятое сообщение |

Правила:

* **дедуп**: ищется слот с тем же текстом (`strcmp`), kind и font; найденный
  слот обновляется (deadline = новый, updated = текущий счётчик), второй слот
  не занимается;
* **переполнение**: при 10 занятых слотах новое сообщение **отбрасывается**,
  счётчик при этом не растёт;
* **срок жизни**: запись умирает, когда `deadline < now` (`FUN_00463e00`);
  освободившийся слот заполняется **последним** сообщением (обмен, а не
  сдвиг), поэтому порядок слотов меняется;
* **канал**: `event_dispatch` передаёт `kind = тип − 5`, т.е. тип 4 → −1
  (системный), 5 → 0 … 12 → 7;
* **отбор при отрисовке**: слоты с `kind == -1` (системный) или
  `kind == запрошенный канал`, отсортированные по `updated` **по возрастанию**
  (старое обновление первым); сортировка — вставкой, обход слотов с конца.

Ограничения оригинала: реестр **один на игру** (не на игрока) — каналы
различаются полем kind; ёмкость — 10 сообщений, текст — 49 символов.

### 2.2. Побочные эффекты записи типа 2 (Trigger Switch)

`event_dispatch` для типа 2 вызывает `FUN_0044f960(index, source)`. Функция
работает с **runtime-таблицей переключателей** `0x5a4af0` (шаг `0x20` на
переключатель):

| смещение | поле |
|---|---|
| `+0x00` | вид (`kind`) |
| `+0x04` | id события (`0` = переключатель не активен → ничего не делать) |
| `+0x08` | пишется `FUN_0044e5f0`, смысл не назван (`reserved`) |
| `+0x0c` | x |
| `+0x10` | y |
| `+0x14` | z |
| `+0x18` | id 3D-звука |
| `+0x1c` | индекс звука (для `FUN_0046b840`) |

* `kind < 0x101` → `generate_event(id, 0, 0, 0, x, y, z, source − 0x10000)` —
  обычное событие с координатами переключателя;
* `kind >= 0x101` → позиция берётся **центроидом сектора**
  (`FUN_0043577c`), а `generate_event` вызывается с другим набором
  аргументов (id, x, y, z, source);
* в обоих случаях, если звук включён (`DAT_004aa384 != 0`) и индекс звука
  положителен, проигрывается 3D-звук `FUN_0046b840(index, sound_id, 0x2b11,
  1000, x, y, z)`; `0x2b11` = 11025.

Итог: переключатель = «поставить `GENERATE`-событие + звук в точке».
В C++ таблица реализована как `gm::EventDispatcher` (массив
`SwitchEffect[0x200]`, `set_switch`/`switch_at`) и `dispatch()`:
типы 1/3 уходят в `generated`, тип 2 ищет запись, выбирает координаты
переключателя или центроид сектора (`kind >= 0x101`) и добавляет
`SoundCommand` при `sound_index > 0`; типы 4…12 уходят в `TextRegistry`.
Файл таблицы (`FUN_0044f000`/`FUN_0044f0a0`): little-endian `u32 count`
(0…0x200) + `count` записей по 0x20 байт в порядке полей выше. C++
`EventDispatcher::serialize()`/`deserialize()` повторяют этот формат;
`install_switches()` переносит `ADD_SWITCH` (`Switch::id` → индекс,
`target` → event id, `kind`/`pos` → поля) в ту же таблицу.
`EventRuntime` связывает `EventQueue` + `EventDispatcher` + `TextRegistry`:
`install_switches`, `pump(now)` (drain → dispatch) и доступ к частям; тест
`test_event_runtime`. Центроид
(`SwitchEffect::centroid`) — runtime-поле и в 0x20-байтовый файл не входит;
после `serialize→deserialize` запись использует сохранённые `x/y/z`.
`parse_network_blob`/`parse_event_queue` отвергают type-2 с индексом
`>= 0x200` целиком (как испорченную очередь). Осталось
подключить чтение/запись файла `0x5a4af0` к игровому циклу.

### 2.3. Сетевой блоб событий

Очередь событий уезжает в сеть **как есть**. Сторона сервера
(`FUN_00465400`, сборка пакета состояния):

```
u32  длина блоба (DAT_007ab9f0)
...  байты очереди (снимок 0x7a44c0)
```

Снимок `0x7a44c0` наполняется в `event_dispatch`: в сетевых режимах
(`DAT_0083d620 == 2/3`) staging-буфер `0x62fbc8` копируется и в буфер
диспетчеризации `0x79cf80`, и в снимок `0x7a44c0`, а счётчик
`DAT_007ab9f0` получает длину.

Сторона клиента (`FUN_00466ae0`): читает `u32` длины и копирует столько же
байт **в буфер диспетчеризации** `0x79cf80` (`DAT_0079cf6c = длина`) — то
есть записи сразу разбираются тем же кодеком, что и локальная очередь.

Кадрирование пакета (общий код, не только события):

| поле | смещение | значение |
|---|---|---|
| магия | `+0x00` | `u32 0x12345678` |
| номер пакета | `+0x04` | `u32` (счётчик `DAT_00619abc`) |
| управляющий байт | `+0x08` | `0` = пакет целиком, `1` = последний чанк, `2`/`3` = продолжение |
| данные | `+0x09` | до `0x37b` = 891 байт |

Сборка состояния начинается с байта-типа: `2` = состояние игры, `5` = список
игроков, `0x66` = отдельный канал. В конце пакета — маркер `0x12345678`
(«Packet end code wrong» при несовпадении).

C++: `gm::EventQueue::parse_network_blob()` разбирает блоб «`u32` + записи»;
обрыв блоба в C++ — ошибка, в оригинале — копирование за границей буфера.

Приём клиента: `EventQueue::accept_network_blob()` проверяет блоб
(включая `length <= 0x7530`) и заменяет очередь его записями; при ошибке
прежняя очередь сохраняется. CTest `events` проверяет и разбор, и приём.

## 3. `generate_event` — `0x479960`

Это **обёртка `GENERATE`**, а не спавнер:

1. если `DAT_0083d620 != 1`, вызывает `door_toggle_by_id(event_id)` (`0x44f690`);
2. затем вызывает `generate_runner(event_id, ...)` (`0x45fa00`).

То есть событие с id сущности одновременно пытается переключить дверь с этим
id и запустить подскрипт сущности. Для оружия это означает: выстрел ставит
`GENERATE`-событие для id из `weapon[+0x30]` (и `+0x34`), а не создаёт снаряд
напрямую.

## 4. `generate_runner` — `0x45fa00`

Функция ищет id в таблице сущностей (`0x5e4680`, счётчик `0x5b1df0`), проверяет
флаги `0x5b0df0` и вызывает VM-исполнитель `0x457390` по смещению подскрипта.
Строки: `event %ld (%s)`, `end event %ld`, `SYSTEM_LEVEL_STARTUP`,
`Warning: [%s] event not defined`. Это запуск скомпилированного подскрипта, а не
фабрика объектов.

## 4.1. Встроенные event id

Имена лежат в `.rdata` `0x4acde8` (26 записей × `0x30`), счётчик
`0x5e3dec`; формула `0x45fb90`: `-index` для системных, `-30000-index` для
скриптовых. `0` (`SYSTEM_LEVEL_STARTUP`) `event_post` отбрасывает.

| id | имя | что делает |
|---:|---|---|
| 0 | `SYSTEM_LEVEL_STARTUP` | напрямую, не через очередь |
| -1 | `SYSTEM_LEVEL_STARTUP_RESUME` | напрямую |
| -2 | `INTERNAL_LEVEL_STARTUP_RESUME` | напрямую |
| -3 | `INTERNAL_LEVEL_RESUME` | напрямую |
| -4 | `INTERNAL_LEVEL_STARTUP` | напрямую |
| -5 | `INTERNAL_LEVEL_LOADING` | напрямую |
| -6 | `SYSTEM_LEVEL_LOADING` | напрямую |
| -7 | `SYSTEM_PLAYER_KILLED` | очередь |
| -8 | `SYSTEM_LEVEL_FINISHED` | очередь; `NEW_LEVEL`/`NEXT_LEVEL` |
| -9 | `SYSTEM_FILM_FINISHED` | очередь |
| -10 | `SYSTEM_PLAYER_HIT_GROUND` | очередь; тряска камеры + звук |
| -11 | `SYSTEM_PLAYER_HIT_WATER` | очередь; всплеск (бит `0x8`, порог ×0.5) |
| -12…-15 | `SYSTEM_PLAYER_*_SHIELD_GONE` | очередь |
| -16 | `SYSTEM_TIMER_EXPIRED` | очередь |
| -17 | `SYSTEM_PLAYER_LIFE_HALF_GONE` | очередь |
| -18 | `SYSTEM_PLAYER_ABOVE_HALF_LIFE` | очередь |
| -19 | `SYSTEM_PLAYER_CREATED` | очередь |
| -20 | `SYSTEM_LEVEL_LOADING_COMPLETE` | очередь; музыка уровня |
| -21 | `SYSTEM_PLAYER_STUCK` | очередь; loop двигателя |
| -22 | `SYSTEM_DOOR_CRUSH` | очередь; `HEAL -10`, `REPAIR -20`, crush-loop |
| -23 | `SYSTEM_THING_HIT_GROUND` | очередь; звук удара |
| -24 | `SYSTEM_THING_ENTER_WATER` | очередь |
| -25 | `EVENT_SYSTEM_THING_EXIT_WATER` | очередь |

`-22` — **не** «обновление препятствия двери»: это crush-урон, когда игрок
упирается в движущуюся створку (`0x45065f`/`0x450787` из пути коллизии
`0x4392de`). Объём двери обновляют `0x44f2e0`/`0x44dfc0` → `0x434887`
независимо от события. `-11` — вода, `-10` — земля, `-21` — застревание;
старые трактовки `-11/-21` как «удар/эффект» опровергнуты.

## 5. Что это значит для оружия

В `0x445ec0…0x445f61` функция огня делает два `event_post`:

- `arg0 = weapon[+0x30]` (первое событие);
- `arg0 = weapon[+0x34]` (второе, если `0x81c35c == 0`).

Аргументы содержат id игрока (или источника) и мировые координаты. Поэтому
поле `Weapon::projectile_id` в C++ — это **id GENERATE-события/сущности**, а не
прямой указатель на снаряд. Настоящий спавн, скорость и урон надо искать в
подскрипте сущности, который исполняет `0x457390`; в записи `DEFINE_WEAPONS`
их нет.

Старые формулировки «выстрел спавнит объект `0x4795b0`» и «`0x4795b0` — спавнер»
надо читать как «выстрел ставит `GENERATE`-событие; `0x4795b0` — `event_post`».
Для двери `0x4795b0(..., -22, box)` — это `SYSTEM_DOOR_CRUSH`: событие
crush-урона, а не обновление препятствия.

## 6. Открытые вопросы

1. `-3/-6/-9/-25` не имеют записей-обработчиков в поставке (теряются или
   warning); `-16` есть только в `level23`. Нужны проверки на других сборках.
2. ~~Разобрать типы 4…12 и `FUN_00463ab0`~~ — **сделано** (§2.1): реестр
   `0x619860` разобран (дедуп, срок жизни, обмен при истечении, порядок
   отрисовки), C++ — `gm::TextRegistry`.
3. `CREATE/THING` найден (`0x45e19d` → `0x46ea40` → `0x46d8b0`), hitscan
   BULLET/LASER — `0x478520`/`0x478be0`; осталось связать impact-урон
   снарядов и `level10.sbt`.
4. Оружейные id не совпадают с дверными/switch id на 36 уровнях, поэтому
   `door_toggle_by_id` для выстрела — no-op (проверено по данным).
5. ~~Побочные эффекты записи типа 2 (`FUN_0044f960`) и сетевой блоб событий
   (`u32 len + bytes`)~~ — **разобраны** (§2.2, §2.3): переключатель ставит
   `GENERATE`-событие и 3D-звук (`0x2b11`), блоб событий — `u32` длины плюс
   записи (C++ `parse_network_blob`). Осталось: runtime-таблица
   переключателей `0x5a4af0` в C++ и приём сетевого пакета целиком.

## 8. C++

`engine/src/game/events.h` / `events.cpp` — `gm::EventQueue` с форматами
type 1/2/3/4…12, little-endian, i32-координатами, отдельными порогами
`0x750e/0x7526/0x74de`, буфером `0x7530` и `drain()`/`parse()`.
`drain()` очищает очередь всегда, как оригинал. Тест `events` проверяет
смещения, switch, текст (включая байт-пропуск), i32-усечение, переполнение,
обрезанную и неизвестную запись. Это только кодек очереди; `GENERATE`,
реестр сообщений и подскрипты подключаются отдельно.

Реестр сообщений — `gm::TextRegistry` (`engine/src/game/events.{h,cpp}`):
десять слотов, дедуп по (текст, kind, font), обновление срока жизни при
повторе, отбрасывание при переполнении, обмен «последний → освободившийся»
при истечении (`deadline < now`), отбор по каналу (`-1` или запрошенный) с
сортировкой по `updated` по возрастанию. Текст обрезается до 0x31 символа.
`gm::post_event(registry, event, now)` переносит записи типов 4…12 из очереди
в реестр со сроком жизни `now + 0x111` — как в `event_dispatch`. Тест
`events` (CTest `events`) фиксирует все эти правила.

Сетевой блоб — `gm::EventQueue::parse_network_blob()`: `u32` длины плюс
записи (§2.3). Обрыв блоба — ошибка (в оригинале — копирование за границей
буфера).
