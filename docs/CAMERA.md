# Gunmetal — камера первого лица: оси, матрица, проекция

Что здесь: математика камеры первого лица Gunmetal — как из трёх углов
игрока получаются мировые оси, как строится матрица «мир → камера», откуда
берётся точка глаза и какие масштабы проекции использует растеризатор.
Всё снято с `gundx.exe` v1.36 (`D:\games\Gunmetal 3dfx`), листинг —
`/tmp/opencode/gundx.asm` (objdump), адреса — виртуальные адреса образа с
базой `0x400000`. Инструмент: `tools/re/camera.py` (stdlib, игру только
читает).

Статус: **ориентация и точка камеры доказаны** на всех 36 уровнях
(143 кампанийные + 248 DM-точек); открытые вопросы — в §11.
Дополняет `docs/PLAYER.md` (§4–§7), где разобран спавн и высота глаза;
здесь — только камера и проекция.

## 0. Коротко

| что | значение | где доказано |
|---|---|---|
| мировые оси `.sbw` | X — вправо, Y — вперёд, Z — вверх | §2 |
| углы камеры | `a = player+0x20` (крен), `b = player+0x18 + [0x81bea0]` (тангаж + view-pitch), `c = player+0x28` (рыскание) | §3 |
| базис | `R = Rz(-yaw) · Rx(-pitch) · Ry(roll)`, столбцы `e1,e2,e3` | §3 |
| взгляд | `forward = e2` | §4 |
| `yaw = 0` | взгляд вдоль **+Y**; `yaw > 0` поворачивает к **+X** | §2, §4 |
| `pitch > 0` | взгляд **вниз** | §3 |
| eye | `(x, y, z + player[0x2F50])` | §5 |
| высота глаза | LIGHT 10.0, MEDIUM/STEALTH 11.0, HEAVY 12.0, 57 CHEVY 14.0, иначе 16.0 | §5 |
| лимит тангажа | ±30° (`π/6`), `0x81be18` | §6 |
| лимит крена | ±20°, `0x81be20` | §6 |
| проекция | `+0x90 = zoom`, `+0x94 = zoom·4H/(3W)`; при 320×200 это `1` и `5/6` | §7 |

Однострочно (крен 0):

```
forward = ( sin(yaw)·cos(pitch),  cos(yaw)·cos(pitch), -sin(pitch) )
right   = ( cos(yaw),            -sin(yaw),             0            )
up      = ( sin(yaw)·sin(pitch),  cos(yaw)·sin(pitch),   cos(pitch)  )
eye     = ( spawn_x, spawn_y, spawn_z + eye_height )
```

## 1. Обозначения

* `roll`, `pitch`, `yaw` — радианы, поля игрока `+0x20`, `+0x18`, `+0x28`.
* `e1`, `e2`, `e3` — столбцы матрицы поворота: вправо, вперёд, вверх.
* В формулах `sA = sin(a)`, `cA = cos(a)` и т.д.
* `0x41e025` — функция построения базиса (см. §3), `0x446590` — сборка
  кадра камеры первого лица (§4).
* Все адреса — VA; смещения полей игрока приведены от начала записи игрока
  в сейве (`SAVEGAME/saved0.sbt`, разбор — `docs/PLAYER.md` §3).

## 2. Мировые оси и знак yaw

При `roll = pitch = yaw = 0` формула §3 даёт ровно мировые оси:

```
e1 = (1, 0, 0)   e2 = (0, 1, 0)   e3 = (0, 0, 1)
```

Поэтому **X — вправо, Y — вперёд, Z — вверх**; при нулевом yaw камера смотрит
вдоль `+Y`. Это не соглашение «на глаз», а следствие того, что:

1. `0x41e025` при нулях возвращает единичную матрицу (проверяется
   `camera.py --selftest`);
2. рендер берёт `e1` как экранную X, `e2` — как глубину, а `±e3` — как
   экранную Y (§4), то есть `e2` — действительно направление взгляда;
3. `yaw` в данных спавна совпадает с поворотом камеры: `0x448dd1` грузит
   `player+0x28` и передаёт его третьим углом в `0x446590`.

При `yaw = +90°`:

```
e2 = (1, 0, 0)  → взгляд вдоль +X
```

Сверху (ось Z на нас) это поворот **по часовой стрелке** от `+Y` к `+X`.
В данных спавна встречаются только «человеческие» углы: `0, ±45°, ±80°,
±90°, ±110°, ±120°, ±135°, ±140°, 180°` (сырые радианы, без нормализации;
`4.7124` = 270°).

Обратное направление (`yaw + 180°`) даёт `e2 ≈ -Y`, что и используется в
cutscene-пути (§9): `yaw - (-π) = yaw + π`.

## 3. Формулы `0x41e025`

Функция вызывается как

```
0x41e025(out1, out2, out3, a, b, c)
```

и раскладывает результат в три вектора по 3 `f64`; внутри — шесть вызовов
`fsin`/`fcos` (`0x480314`/`0x480954`) и арифметика. Эквивалентная запись:

```
R = Rz(-c) · Rx(-b) · Ry(a)
```

Столбцы `R` — это `e1` (ось X камеры, вправо), `e2` (ось Y, взгляд),
`e3` (ось Z, вверх). В развёрнутом виде:

```
e1 = ( cC·cA - sC·sB·sA,  -sC·cA - cC·sB·sA,  -cB·sA )
e2 = ( sC·cB,              cC·cB,             -sB    )
e3 = ( cC·sA + sC·sB·cA,  -sC·sA + cC·sB·cA,   cB·cA )
```

где `A = a` (крен), `B = b` (тангаж), `C = c` (рыскание).

Проверка в `camera.py`:

* формулы сравниваются с явным матричным произведением
  `Rz(-yaw)·Rx(-pitch)·Ry(roll)` на 2000 случайных наборов углов;
* максимальное расхождение — `0.0` (побитовое совпадение с двойной
  точностью на этих операциях), максимальное скалярное произведение
  разных осей — `2.1e-16`;
* `det R = +1` с точностью `1e-12`, `|e1| = |e2| = |e3| = 1`.

При `roll = 0` (все спавны в данных такие) формулы упрощаются до:

```
e1 = ( cos(yaw),           -sin(yaw),           0          )
e2 = ( sin(yaw)·cos(pitch), cos(yaw)·cos(pitch), -sin(pitch) )
e3 = ( sin(yaw)·sin(pitch), cos(yaw)·sin(pitch),  cos(pitch) )
```

Отсюда сразу видны знаки: `pitch > 0` даёт `e2.z < 0` — взгляд вниз;
`yaw = +90°` даёт `e2 = +X`.

## 4. Сборка кадра: `0x446590`

`0x446590` — функция, которая заполняет структуру камеры `0x83d1a0`
(позиция `+0x00/+0x08/+0x10`, оси `+0x30/+0x48/+0x60`, масштабы
`+0x90/+0x94`, вьюпорт `+0xac/+0xae`). В районе `0x4468e3` она готовит
шесть `f64` и вызывает `0x41e025` (`0x446910`):

| аргумент `0x41e025` | источник | смысл |
|---|---|---|
| `a` | `player+0x20` | крен |
| `b` | `player+0x18 + [0x81bea0]` | тангаж + view-pitch (мышь/джойстик) |
| `c` | `player+0x28` | рыскание |

Выходы: `out1 = +0x30` (`e1`), `out2 = +0x48` (`e2`), `out3 = +0x60`
(`e3`). Сразу после вызова (`0x446915`..`0x446942`) движок делает `fchs`
над `out3`, то есть в `+0x60` лежит **`-e3`**. Это не ошибка знака:
экранная Y в растеризаторе растёт вниз, поэтому «вниз по экрану» — это
`-e3` (а `e3` — вверх в мире).

Дальше:

* `0x4469bc` вызывает `0x41928e` — установку вида/вьюпорта;
* `0x41928e` и `0x4409b8` используют `+0x30` как ось X, `+0x60` как ось Y
  (вниз), `+0x48` как глубину. В `0x440c1d`..`0x440c8f` видны множители:
  `+0x30` (e1) умножается на `+0x90`, `+0x60` (-e3) — на `+0x94`,
  `+0x48` (e2) — на `64 / (+0xa0)`;
* следовательно **направление взгляда — `+e2`**, а не `e1` и не `-e2`.

`camera.py` печатает матрицу в обычном «y-up» виде:

```
[ e1.x  e1.y  e1.z  -dot(e1, eye) ]
[ e3.x  e3.y  e3.z  -dot(e3, eye) ]
[ e2.x  e2.y  e2.z  -dot(e2, eye) ]
[ 0     0     0      1            ]
```

Если нужна точная копия экранных осей движка, вторую строку (`e3`, y-up)
надо заменить на `-e3` (экранная Y вниз). Матрица ортонормальна, `det = +1`;
это проверяется для каждой точки.

## 5. Точка камеры и высота глаза

В первом лице камера ставится в позицию игрока, а к `z` добавляется поле
`player+0x2F50`. В коде это видно в `0x448d2b`..`0x448d3a` (и в
cutscene-пути `0x4471ba`..`0x4471c6`):

```
fld  QWORD PTR [player+0x2F50]     ; 0x81bf90 при player = 0x819040
fadd QWORD PTR [player+0x10]       ; z игрока (0x819050)
```

То есть

```
eye = ( player[0x00], player[0x08], player[0x10] + player[0x2F50] )
```

`x` и `y` не меняются. В этой инструкции позиция берётся из игрока
напрямую; возможное сглаживание самого `player+0x10` в движении не
проверялось (§11), а эффекты вроде отдачи добавляются к углам (§6).

`player+0x2F50` заполняется из таблицы `DEFINE_PLAYER_TYPES`; значения
(подтверждены сейвом `saved0.sbt`: `10.0` для LIGHT):

| шасси | высота глаза |
|---|---:|
| LIGHT CHASSIS | 10.0 |
| MEDIUM CHASSIS | 11.0 |
| STEALTH CHASSIS | 11.0 |
| HEAVY CHASSIS | 12.0 |
| 57 CHEVY | 14.0 |
| без шасси (fallback) | 16.0 |

В скрипте `.sbt` `z` — опорная точка («ноги»/центр шасси), не глаз.
Поэтому для `level0` (`spawn = 24,-208,48`) камера стоит в
`(24, -208, 58)`, а не в `48`.

## 6. Тангаж, крен, view-pitch и тряска

**Тангаж** `player+0x18` ограничен ±30°:

* константа `[0x81be18]` инициализируется в `0x45290e`/`0x452918` как
  `0x3fe0c152382d7365` = `π/6` = 30.0°;
* кламп — `0x444af8`..`0x444b48`: сравнение с `+[0x81be18]`, затем с
  `-[0x81be18]`, запись обратно в `[0x81bde8]`;
* результат копируется в `player+0x18` в `0x444b81`..`0x444b87`.

**Крен** `player+0x20` ограничен ±20°:

* константа `[0x81be20]` = `0x3fd657184ae74487` = 20.0° (`0x452922`);
* целевой крен `[0x81be10]` вычисляет `0x451160` (путь/геометрия шасси):
  `0x4077f` даёт углы, результат пишется в `[0x81be10]`; `0x443690`
  пружиной ведёт фактический `[0x81bdf0]` к цели;
* кламп — `0x444aaa`..`0x444af6` для `[0x81bdf0]`; итоговый крен
  `player+0x20 = [0x81bdf0] + [0x81be28]` записывается в
  `0x444b99`..`0x444ba5` (ветка без «snap back», `0x444a55` — ветка
  возврата);
* это опровергает прежнее предположение, что 20° нигде не используется.
  Источник добавки `[0x81be28]` пока не установлен.

**View-pitch**: в камеру идёт не сам `player+0x18`, а

```
pitch_camera = player[0x18] + player[0x2E60] + shake_pitch
```

`player[0x2E60]` — это и есть `[0x81bea0]` (база игрока 0 — `0x819040`).
Это **не отдача**: поле питается аналоговым вводом (мышь/джойстик,
`0x44c8f2` → `0x5a4a88` → `0x44d6d6` → `player[0x2F38]`), переносится в
`player[0x2E60]` в `0x443a03`..`0x443ac8` и зажимается в ±90°. Затухание
`-(player[0x3360]-player[0x3364])·0.016·k/zoom` в этом билде мертво:
таймеры не пишутся, поэтому вычитаемое всегда 0.

Отдельно есть три глобальных канала тряски (скриптовые
`SET_CAMERA_{PITCH,ROLL,YAW}_SHAKE`): треугольная волна с пиком
`amplitude` и периодом `4·period`, добавляется после клампов игрока.
Формула отдачи `SOURCEPLAYER_RECOIL` — горизонтальный импульс скорости, а
не добавка к углу. Подробности и xref — `docs/SHAKE.md`.

В данных спавна `pitch` и `roll` **всегда нули** (143 кампанийные + 248 DM
точек), поэтому стартовая камера всегда без наклона и крена; ненулевыми они
становятся только в игре.

## 7. Проекция и «FOV»

Явного угла FOV в структуре камеры нет. Растеризатор получает два масштаба
(`0x4466a6`..`0x446780`, поля `f32` в структуре камеры):

| поле | формула | 320×200 | 640×480 |
|---|---|---:|---:|
| `+0x90` (`0x83d230`) | `zoom` | 1.0 | 1.0 |
| `+0x94` (`0x83d234`) | `zoom · 4H / (3W)` | 0.833333 | 1.0 |
| `+0xa0` (`0x83d240`) | `0.8 · W · [0x80d8a0] · k(level)` | 256·k | 512·k |

Здесь `W = [0x83d944]` (320), `H = [0x83d630]` (200) — внутреннее
разрешение; `zoom = [0x4aa390]` (в игре `1.0`, в cutscene умножается на
`0.25`);
`[0x80d8a0] = 1.0` (инициализация `0x4570ef`), а `k(level)` — множитель
из таблицы уровня `0x81bf98 + 0x190·index` (в этой работе не перечислен).
Рядом сохраняются `+0xe0 = 0.9` (`[0x80d7e0]`), `+0xe4 = 0.4`
(`[0x80d8a8]`) и `+0xe8 = [0x80f9a8] = 0.0`; их роль — near/far и
вспомогательные коэффициенты, здесь не доказывается.

Как это используется (`0x440c1d`..`0x440c8f`):

```
x_screen ∝ (+0x90) · (e1 · p)
y_screen ∝ (+0x94) · (e3 · p)
depth    ∝ (64 / (+0xa0)) · (e2 · p)
```

Отсюда видно, что `+0x90`/`+0x94` — горизонтальный и вертикальный
масштабы (фокусные), а не углы. При 320×200 `focal_y/focal_x = 5/6`, что
совпадает с `4H/(3W)` и с растяжением кадра 320×200 до 4:3; при 640×480
масштабы равны. Угол FOV, если он нужен, выводится из них:
`tan(hfov/2) = 1/focal_x`, `tan(vfov/2) = 1/focal_y` **при условии**, что
экранные координаты нормированы в ±1 (это предположение о конкретной
ступени растеризатора; в игре абсолютные пиксели получаются умножением
на половину вьюпорта).

Проверка в `camera.py`:

```sh
python3 tools/re/camera.py --width 640 --height 480      # focal 1 / 1
python3 tools/re/camera.py --width 320 --height 200      # focal 1 / 5/6
python3 tools/re/camera.py --zoom 0.25                   # cutscene
```

### 8.2 Геометрия старта

Проверка та же, что в `tools/re/spawn.py` §7 `docs/PLAYER.md`: AABB мира
`.sbw`, расстояние до ближайшего **вертикального** треугольника
(`|n_z| < 0.8`), луч вперёд/назад, луч вниз. Порог «в стене» — `< 1.0`.

| показатель | кампания (143) | DM (248) |
|---|---:|---:|
| внутри AABB `.sbw` | 75 | 38 |
| вне AABB `.sbw` | 68 | 210 |
| `in_wall` (< 1.0) | 5 | 0 |
| `floor_gap < 0` | 0 | 0 |
| луч вперёд ближе 1.0 | 3 | 0 |

Пять кампанийных точек ближе 1.0 к вертикальной плоскости **на высоте
глаза**: `level0[4]` (0.4), `level2[4]` (0.8), `level2[5]` (0.5),
`level2[6]` (0.3), `level4[0]` (0.4). Это те же тесные места, что и в
`docs/PLAYER.md` §7 (там порог считался от «ног», поэтому список чуть
другой: `level2` — кластер из 8 стартов в комнате с зазорами 0.2–0.7,
`level4` — старт в 0.6 от стены).

Три точки упираются лучом в поверхность ближе 1.0: `dm1[0]` — 0.2
(скат/потолок, `|n_z| ≥ 0.8`, формально не стена), `level2[5]` — 0.5,
`level4[0]` — 0.8. Это не ошибка камеры: старт стоит вплотную к
геометрии; признаков «внутри» (отрицательного `floor_gap`) нет.

**68/210 «вне AABB» — не ошибка.** Это интерьеры, собранные из
`.sob`-моделей, которые скрипт ставит через `ADD_THING*`; в `.sbw` их нет,
поэтому проверка по мировым треугольникам для таких уровней бессмысленна
(подробно — `docs/PLAYER.md` §7). `camera.py` всё равно печатает
`nearest_wall`/`forward_hit`, но трактовать их для этих уровней нельзя.

## 9. Cutscene и «третье лицо»

`0x4471f1` вызывает ту же `0x446590`, но с инвертированными углами
(`0x447169`..`0x4471c6`):

```
pitch' = -(player[0x18] + [0x81bea0])
roll'  = -player[0x20]
yaw'   =  player[0x28] - [0x4a23c0],  [0x4a23c0] = -π  →  yaw + π
eye    =  player[0x00], player[0x08], player[0x10] + player[0x2F50]
```

Это «камера смотрит на игрока с противоположной стороны»: взгляд
развёрнут на 180°, наклон и крен отражены. Дополнительно в cutscene
`zoom` умножается на `0.25` (`[0x4a2320]`, `0x447247`/`0x447254`), то есть
картинка приближается в 4 раза (см. §7).

Путь `0x448c16`/`0x448d76` — обычный кадр первого лица; `0x448e3c`
вызывает `0x44a020` — **другой** режим (базис `a = yaw, b = π/2, c = 0`,
ортопроекция/экранный слой), это не камера первого лица. Поэтому не надо
смешивать формулы `0x44a020` с `0x41e025` из §3.

## 10. Опровергнутые гипотезы

| гипотеза | почему неверна |
|---|---|
| при `yaw = 0` взгляд вдоль `-Y` | формула и `0x41e025` при нулях дают `e2 = +Y`; `e2` — глубина в `0x440c98` |
| `yaw` отсчитывается против часовой от `+X` | `yaw=+90°` даёт `e2=+X`, то есть от `+Y` по часовой (сверху) |
| `pitch > 0` — взгляд вверх | `e2.z = -sin(pitch)`: положительный тангаж смотрит вниз |
| `+0x18` — крен, `+0x20` — тангаж | `0x448dd1`/`0x4468e3` передают `+0x18` вторым (тангаж), `+0x20` первым (крен); сейв подтверждает порядок |
| смотреть надо вдоль `e1` или `-e2` | рендер использует `e2` как глубину (`+0x48`), `e1` — как X, `-e3` — как Y |
| `camera_z = spawn_z + 8` | высота глаза берётся из `player+0x2F50`: 10/11/12/14/16 в зависимости от шасси; сейв `level0` даёт 10 |
| лимит тангажа 20° | 30° (`π/6`, `[0x81be18]`); 20° — лимит **крена** (`[0x81be20]`) |
| 20° нигде не используется | используется: кламп `[0x81bdf0]` в `0x444aaa`..`0x444af6`, запись в `player+0x20` |
| `fchs` после `0x41e025` меняет знак всего базиса | меняется только `out3` (`+0x60`), то есть `e3 → -e3`; `e1`/`e2` не трогаются |
| FOV задан углом в конфиге | угла нет; есть масштабы `+0x90 = zoom` и `+0x94 = zoom·4H/(3W)` |
| `+0x90 = 4·W·zoom/0.9`, `+0x94 = 3·H·zoom/0.9` | не подтверждается трассировкой x87-стека: `+0x90 = zoom`, `+0x94 = zoom·4H/(3W)`; `0.9` сохраняется в `+0xe0` |
| `0x44a020` — камера первого лица | это отдельный ортопроекционный путь; первый глаз — `0x446590` |

## 11. Что осталось

1. **Крен в динамике.** Источник найден частично: `0x451160` вычисляет
   целевой крен/тангаж из пути/геометрии (`0x4077f`) и пишет `[0x81be10]` /
   `[0x81be08]`; `0x443690` пружиной ведёт к ним `[0x81bdf0]`/`[0x81bde8]`.
   Добавка `[0x81be28]` (пишется `0x466ae0`) ещё не отождествлена.
2. **View-pitch и тряска — разобраны** (`docs/SHAKE.md`): `[0x81bea0]` =
   `player[0x2E60]`, аналоговый ввод с зажимом ±90°; три shake-канала
   применяются после клампов. Не найдены скрипты, которые включают shake в
   поставочных `.sbt`, и реальные амплитуды/периоды (данных нет).
3. **Третье лицо и cutscene целиком.** Инверсия углов и `zoom·0.25`
   доказаны, но полный набор переходов (интерполяция позиции/углов,
   дистанция камеры, коллизии) — нет.
4. **Сглаживание/интерполяция камеры.** В точке спавна позиция берётся
   напрямую; есть ли лаг/сглаживание в движении (и как оно влияет на
   `eye`), не проверялось.
5. **Смысл `+0xa0` и констант `+0xe0/+0xe4/+0xe8`.** `+0xa0` явно
   масштабирует глубину (`64/(0.8·W·k)`), но точная роль множителя
   `k(level)` из таблицы `0x81bf98` (возможно, это и есть per-level FOV),
   near/far и клиппинг не доказаны.
6. **FOV в градусах.** Масштабы доказаны; преобразование в угол зависит от
   того, как конкретная ступень растеризатора переводит NDC в пиксели
   (нормировка ±1 или половина вьюпорта) — в игре не проверялось.

## 13. Воспроизведение

```sh
# математика
python3 tools/re/camera.py --selftest

# один уровень, слот 0 (кампания)
python3 tools/re/camera.py level0

# все 36 уровней, только слот 0
python3 tools/re/camera.py

# все точки кампании / все DM-точки
python3 tools/re/camera.py --all-spawns
python3 tools/re/camera.py --dm --all-spawns

# конкретный слот и подмена углов (градусы)
python3 tools/re/camera.py level1 --slot 3
python3 tools/re/camera.py level0 --pitch 15 --roll 5 --yaw 30

# JSON (в stdout) и без чтения .sbw
python3 tools/re/camera.py --no-geom --json > /tmp/opencode/camera.json

# проекция
python3 tools/re/camera.py --width 640 --height 480 --zoom 1
```

`--strict` возвращает ненулевой код, если какая-то точка попала в
эвристический `in_wall` (< 1.0); по умолчанию это только предупреждение,
потому что тесные старты — свойство данных, а не ошибка камеры.
