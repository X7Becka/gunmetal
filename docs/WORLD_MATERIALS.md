# Материалы, оверлеи и флаги мира: потребители полей (M2.3.2)

Что здесь: продолжение `docs/WORLD_FIELDS.md`. Там карта мира построена, но у
части полей не были прослежены **потребители**. Здесь они найдены (или
доказано, что их нет) — с адресами инструкций `gundx.exe` 1.36
(ImageBase `0x400000`), байтовым сканом образа и прогоном 36 поставочных
`.sbw`. Отдельно закрыт вопрос про «конверсию `f32`-заголовка объекта в
`f64`-трансформ»: **конверсии нет, заголовок в файле — это 12 `f64`**.

Инструмент: `tools/re/materials.py` (`--map`, `--verify`, `--self-test`; только
stdlib, парсер `gm/sbw.py`). Смежное: `docs/WORLD_FIELDS.md` (карта),
`docs/RENDER.md` (C++-рендер), `docs/DOORS_CPP.md` (трансформ створок).

## 0. Коротко

| вопрос | ответ | статус |
|---|---|---|
| таблица материалов `0x5670e0` | 30 записей × `0x40`, `index = style*6+kind`, рецепт `0x420c03` | доказано |
| `+0x04/+0x08/+0x0c/+0x14` (указатели на LUT) | **читателей нет** ни в C, ни в asm-сегментах; значения доказываются рецептом и аллокатором `0x41e3d8` | доказано (запись) / читателей нет |
| `+0x20/+0x24/+0x28` (RGB стиля) | та же картина: пишутся, не читаются | доказано (запись) |
| `+0x2c` (`0/64/64/100/127/−128`) | параметр прохода вида; **читателей нет**; диапазон значений доказан рецептом | доказано (запись), семантика — гипотеза |
| `+0x30` (тинт стиля) | 24-битный `R<<16\|G<<8\|B`, только для kind 0; читателей нет | доказано (запись) |
| `+0x00` режим | бит 0 = «второй проход»; читается в луче/трассах и валидаторе | доказано |
| `+0x10` light-LUT | единственное поле LUT, которое кто-то читает: `0x4409cb` (рендер, запись `[0]`) | доказано |
| overlay `poly+0x78` | оверлей-текстура/эффект: луч, две трассы, запекание лайтмапов, валидатор, писатель `.sow` | доказано |
| scroll `0x5c/0x60` | вес скольжения текстуры: `0x434c11` (вектор движения), `0x433e00` (интерполяция) | доказано |
| anim `0x5e/0x62/0x66` | интерполируются `0x433e00`; в данных ненулевые **у всех** 235 069 полигонов | доказано |
| флаги `obj+0x70` | `0x10`/`0x10000` — cull луча/трасс, `0x20000` — форс-рендер, `0x40000/0x80000` — «чужие» массивы, `0x100000` — не пересчитывать UV | доказано |
| `obj+0x80` владелец | указатель на экземпляр вещи (пул `0x71cd40`, шаг `0x148`), `0` = статика уровня | доказано |
| `obj+0x90` extent | **всегда 0** в поставке; читается как `f64`: расширяет AABB сектора (`0x434fed`) и ставит флаг «сектор с extent» (`0x440867`) | доказано |
| `f32` → `f64` конверсия | **не нужна**: в файле 12 `f64`; «1.875» — это `f32`-биты `1.0` | доказано |

Числа (36 уровней, 5104 сектора, 28 192 объекта, 235 069 полигонов):
материалы `0: 230 499, 1: 300, 2: 966, 3: 227, 4: 3 077` (вид `shade` = 5 не
встречается, стили > 0 не встречаются); overlay ≠ 0 у **156** полигонов
(все 156 без текстуры, 133 из них — эффекты, т.е. отрицательный индекс);
`0x72` ≠ 0 у 11 356, `0x74` ≠ 0 у 1 022, `0x76` ≠ 0 у 586; scroll ≠ 0 у 2 917.

## 1. Метод

1. Выборка потребителей поля таблицы — **полный** список xref на базу
   `0x5670e0` (`list_xrefs`) плюс независимый байтовый скан образа на
   little-endian `e0 70 56 00` (все 183 вхождения сгруппированы по функциям,
   см. §2.4). Второй скан нужен, чтобы не пропустить код, который Ghidra не
   разобрала (в exe есть asm-сегменты `tex`, `vidseg`, `imageseg`, `putseg`,
   `adx`…).
2. Проверка полей записи: дизассемблер `disasm` + декомпилятор
   (`decompile`) — декомпилятор только гипотеза, все ключевые утверждения
   ниже подтверждены инструкциями (адреса в тексте).
3. Семантика LUT-полей — по **аллокатору** `0x41e3d8` (там у таблиц есть
   имена-строки: `paltable`, `redtable`, `goldtable`, `bluetable`,
   `lighttable`, `redlighttable`, `trantable`, `varaddtable`, `addtable`,
   `shadetable`) и по **строителям** таблиц.
4. Данные: `tools/re/materials.py --verify` (36 `.sbw`, только чтение).

## 2. Таблица материалов (`0x5670e0`, 30 × `0x40`)

### 2.1 Рецепт `0x420c03`

```
0x42123f  MOV  dword ptr [0x005670e4], 0x1e        ; count = 30
0x421250  ...  malloc(0x1e << 6) -> [0x5670e0]     ; 0x780 байт
```

Далее двойной цикл `style = 0..4` × `kind = 0..5` (`local_8 = style*6`,
`local_c = style`), запись по адресу `table + (style*6+kind)*0x40`:

| поле | значение (по видам/стилям) | адрес записи |
|---|---|---|
| `+0x00` | `mode`: kind0 `0`, kind1 `1`, kind2..5 `2` | `0x4212f0`…`0x421362` |
| `+0x04` | палитра стиля: styles 0,1 → `paltable`; 2 → `redtable`; 3 → `goldtable`; 4 → `bluetable` | `switch` по стилю, таблица переходов `0x422242` → case-блоки `0x421728/0x421963/0x421b97/0x421dcc/0x422007` |
| `+0x08` | kind0 `0`, kind1 и kind2 → `trantable`, kind3 → `varaddtable`, kind4 → `addtable`, kind5 → `shadetable` | `0x42136f`…`0x4213eb` |
| `+0x0c` | `LEA 0xa01040 + style*0x600` (`IMUL ECX,ECX,0x180`, `LEA EDX,[ECX*4+0xa01040]`) — ramp стиля, `0x180` dword | `0x4213f2`…`0x42140e` |
| `+0x10` | `lighttable` (`0x567104`) — у **всех 30** записей | `0x42129b` |
| `+0x14` | `redlighttable` (`0x567108`) — у всех 30 | `0x4212b0` |
| `+0x18..+0x1f` | **не пишется** (malloc без memset ⇒ мусор) | — |
| `+0x20/0x24/0x28` | `f32` R/G/B стиля: `(1,1,1)`, `(0.5,1,1)`, `(1,0,0)`, `(1,0.5,0)`, `(0,0,1)` | `0x4214xx`…`0x4215xx` |
| `+0x2c` | `0, 0x40, 0x40, 100, 0x7f, 0xffffff80` по kind | `0x4214d8`…`0x421549` (ср. `0x421533` = `0x7f`, `0x421549` = `0xffffff80`) |
| `+0x30` | тинт стиля: `0x9c9c9c`, `0x50a0a0`, `0xa00000`, `0xa05000`, `0x0000a0` — **только** для kind 0 | case-блоки конструктора |
| `+0x34` | имя: style 0 — `none/reflective/translucent/varadd/add/shade`, стили 1..4 — `_ld_none_2 … _ld_shade_5` | `0x42155b`… (`strcpy`/`sprintf`) |

Тинт — 24-битный `R<<16 | G<<8 | B` (серый 156, бирюза 80/160/160, красный,
оранжевый, синий); в декомпиляторе `0xa00000` выглядит как `&DAT_00a00000`
только потому, что константа попала в диапазон адресов образа.

### 2.2 Поля: «смещение → тип → смысл → чем доказано → статус»

| смещ. | тип | смысл | доказательство (инструкции) | статус |
|---:|---|---|---|---|
| `+0x00` | `u32` | режим; бит 0 = второй (смешиваемый) проход | запись `0x4212f0`…`0x421362`; чтение `0x437fc3` (`AND EAX,1`), `0x439e7e`, `0x43d571`, `0x423edb` (`&2` и `&1`) | доказано |
| `+0x04` | `u32*` | палитра стиля (`paltable` 0x20100 Б; `red/gold/bluetable` по 0x2100 Б) | запись в case-блоках `0x421728/0x421963/0x421b97/0x421dcc/0x422007`; аллокатор `0x41e3d8` | доказано (запись), читателей нет |
| `+0x08` | `u32*` | blend-LUT вида, 256×256 Б (`trantable/varaddtable/addtable/shadetable`) | запись `0x42136f`…`0x4213eb`; аллокатор `0x41e3d8` | доказано (запись), читателей нет |
| `+0x0c` | `u32*` | ramp стиля `0xa01040+style*0x600` | `0x4213f2`…`0x42140e` | доказано (запись), читателей нет |
| `+0x10` | `u32*` | light-LUT 256×256 (+256 Б запас): `lit = LUT[level*256 + shade]` | запись `0x42129b`; **чтение `0x4409c5`/`0x4409cb`** (рендер `0x4409b8`), индексация `0x440xxx` (`+ level*0x100`) | доказано |
| `+0x14` | `u32*` | red-light-LUT (тот же формат) | запись `0x4212b0` | доказано (запись), читателей нет |
| `+0x18` | `u32[2]` | не инициализируется | malloc без memset в `0x421250` | unknown (мусор) |
| `+0x20/24/28` | `f32` | RGB-множители стиля | запись в case-блоках | доказано (запись), читателей нет |
| `+0x2c` | `i32` | параметр прохода вида (0/64/64/100/127/−128) | `0x4214d8`…`0x421549` | доказано (запись); семантика — гипотеза |
| `+0x30` | `u32` | тинт стиля `R<<16\|G<<8\|B` | case-блоки, только kind 0 | доказано (запись), читателей нет |
| `+0x34` | `char[12]` | имя материала | `0x42155b`…; чтение `0x42eaf5`, `0x42eb63`, запись в `.sow` `0x426df4` | доказано |

### 2.3 LUT-таблицы: кто их делает

`0x41e3d8` (вызывается один раз при инициализации) аллоцирует и запоминает
указатели (имена — строки рядом, в фигурных скобках — размер):

```
0x5670e8 paltable      {0x20100}  -> 0x567100 (выровнено на 0x100)
0x5670f4 redtable      {0x2100}   -> 0x56710c
0x5670f8 goldtable     {0x2100}   -> 0x567110
0x5670fc bluetable     {0x2100}   -> 0x567114
0x5670ec lighttable    {0x10100}  -> 0x567104
0x5670f0 redlighttable {0x10100}  -> 0x567108
0x567124 trantable     {0x10000}
0x567118 varaddtable   {0x10000}
0x56711c addtable      {0x10000}
0x567120 shadetable    {0x10000}
0x567128 / 0x56712c = 0x8c8000 / 0x908000  (два буфера по 0x40000 — 8-битные
                                             кадры/дизеры рендера)
```

Строители (вызываются из инициализации уровня/яркости):

| функция | что заполняет | индексация |
|---|---|---|
| `0x422256` | `paltable` (по глобальной яркости `DAT_0080d89c/…`, вызывается из `0x4232b7` при `DAT_00567100 == 0`) | 256×(источник, назначение) |
| `0x4201fe` | `lighttable` | `LUT[shade + level*0x100]` |
| `0x420542` | `redlighttable` | то же |
| `0x41f618` | `addtable` | `LUT[shade + level*0x100]` |
| `0x41f8d1`, `0x41fbe3`, `0x41ff6f` | `shadetable` / `varaddtable` / `trantable` | то же |

То есть `+0x10` — таблица «перекраски» 8-битного кадра: `new = LUT[row][old]`,
строка — уровень света/дальности (`0..63`), столбец — старый индекс. Именно
так её и использует рендер:

```
0x4409c5  MOV ECX,[EAX+0xb4]      ; ctx->materials
0x4409cb  MOV EDX,[ECX+0x10]      ; material[0]+0x10 == lighttable
; далее схематично (внутренний цикл растеризации, 0x440bxx):
;   row  = 0x3f - ftol(depth), clamp 4..63
;   buf[i] = lighttable[ buf[i] + row*0x100 ]
```

### 2.4 Кто реально читает запись таблицы

Полный список **всех** мест, где образ обращается к базе `0x5670e0`
(xref + байтовый скан, 183 вхождения, 8 кластеров):

| адрес/функция | что делает с записью |
|---|---|
| `0x420bd3` (free), `0x420c03` (рецепт) | запись/освобождение |
| `0x4223a6` (`0x4223c8`) | `ctx+0xb4 = table` (контекст рендера) |
| `0x423edb` (`&2`, `&1`) | валидатор уровня: предупреждения о материале/текстуре |
| `0x426ac3` (`0x426df4`) | писатель `.sow`: имя материала |
| `0x42eaf5` (`+0x34`) | имя → индекс (поиск `strcmp`) |
| `0x42eb63` (`+0x34`) | индекс → имя |
| `0x437d05` (`0x437fbc`) | луч по миру: `material & 1` |
| `0x4392de` (`0x439e77`) | трасса с порталами: `material & 1` |
| `0x43cd32` (`0x43d56a`) | трасса с порталами: `material & 1` |
| `0x4409b8` (`0x4409cb`) | **рендер**: `material[0]+0x10` (light-LUT) |

`0x4409b8` — это и есть кадровый проход движка: её вызывает `0x44a020`
(`0x44a1e0: CALL 0x4409b8`), а сама она обходит все секторы/объекты/полигоны
и пишет 8-битный кадр в `ctx+0x104` (шаг `ctx+0xd4`).

И только. Ни `+0x04`, ни `+0x08`, ни `+0x0c`, ни `+0x14`, ни `+0x2c`, ни
`+0x30` никем не читаются — ни в `.text`, ни в asm-сегментах (`tex`, `vidseg`,
`imageseg`, `putseg`, `mixasm*`, `adpcmseg`): байтовый скан не нашёл ни одного
обращения к `0x5670e0` вне перечисленных кластеров, а указатели LUT
(`0x567100/104/108/10c/110/114/118/11c/120/124`) читаются только
аллокатором/фри, строителями и конструктором.

**Вывод.** В `gundx.exe` 1.36 запись материала используется как:
`+0x00` — «проходимость/второй проход» для луча и трасс; `+0x34` — имя для
текстового экспорта; `+0x10` — light-LUT для рендера (причём всегда запись
стиля 0). Остальные поля — **данные рецепта без потребителя в этой сборке**
(вероятно, наследие программного рендера DOS-версии `gun.exe`; в DX-сборке
палитровые LUT строятся, но кадр рисуется через `D3DImm.dll`, см.
`DAT_004d74xx` — IAT Direct3D). Это не ошибка чтения: адреса записей
проверены по дизассемблеру.

Практическое следствие для C++: веса `material+0x2c/127` в
`engine/src/render/render.cpp` — это **догадка вьювера**, а не поведение
движка. Движок различает материалы только битом 0.

## 3. Оверлей / scroll / anim полигона

### 3.1 `+0x78` overlay (i16, кодировка как у `+0x00`: `>0` — текстура, `<0` — эффект)

| потребитель | что делает |
|---|---|
| `0x437d05` (луч, `0x437fxx`) | при `param_11 != 0` (флаг «учитывать оверлеи») полигон с `overlay != 0` тестируется, даже если `texture == 0` |
| `0x4392de` (`0x439e8x`) | то же при `param_13 & 1`: оверлейный полигон участвует в трассе |
| `0x43cd32` (`0x43d5xx`) | то же при `param_12 & 1` |
| `0x43e69d` (`0x43e6xx`) | запекание лайтмапа: полигон без текстуры **и** без оверлея пропускается; оверлейный — запекается |
| `0x423edb` (`0x4245xx`) | валидатор: `texture == 0 && overlay != 0` → «Warning: eliminating overlay at …», поля `0x78/0x7a` обнуляются; при наличии оверлея/текстуры ставит `poly+0x7c |= 4` |
| `0x426ac3` (`0x426df4`…) | писатель `.sow`: `overlay < 0` → имя эффекта, `> 0` → имя текстуры, `0` → `none` |

В данных: 156 полигонов с оверлеем, **все** без текстуры, 133 — эффекты.
Так что «второй проход рендера» из старой карты — неверно: оверлей
участвует в трассировке/лайтмапах/экспорте, отдельного прохода отрисовки
оверлея в `gundx.exe` не найдено (см. §8).

### 3.2 `+0x5c` / `+0x60` scroll (i16, вес скольжения текстуры)

`0x434c11` (вход — `0x434c80`), после `0x434463` (полигон по `(sector,object,poly)`):

```
fVar1 = 1/|u_axis|^2 ; fVar2 = 1/|v_axis|^2      ; нормировка на всякий случай
out = ((s16[0x60]*v_axis*fVar2 + s16[0x5c]*u_axis*fVar1) * (-speed)) / 256
```

То есть `0x5c/0x60` — **скорость скольжения текстуры вдоль её же осей**,
`1/256` на тик, знак — против направления (`-param_5`). Это подтверждает
`SET_POLY_SCROLL` и снимает вопрос «вес против чего».

### 3.3 `+0x5e` / `+0x62` / `+0x66` anim (u16, анимируемые s16-половины)

`0x433e00` (интерполяционный цикл — `0x4342f0`) — морфинг объекта по двум
кадрам анимации. Вход (`param_1`) — запись анимации: `+0x7c` — индекс клипа
(`< 0`, таблица с шагом `0x108` в `0x6fbd40`), `+0x78` — начальный тик,
`param_2` — текущий тик; режим клипа `0` — зажим на последнем кадре, `1` —
зацикливание. Далее:

* заголовок полигона (`texture/material/lightmap`, `+0x00/0x02/0x04`)
  копируется из кадра-источника;
* линейно интерполируются вершины (буфер `obj+0x64`), `centre`/`normal`/
  `u_axis`/`v_axis`, `uv_u/uv_v` (`0x50/0x52`), `uv_u_fp/uv_v_fp`
  (`0x54/0x58`), `brightness` (`0x70`) и **пять s16-полей**
  `0x5c, 0x5e, 0x60, 0x62, 0x66`;
* вызывается `0x434d78` (пересчёт производных кадра).

В поставке `0x5e/0x62/0x66` ненулевые у **всех** 235 069 полигонов — это
упакованные биты `f32` из экспортёра (см. `gm/sbw.py`), движок читает их
только как `s16` в этой интерполяции; `0x5c/0x60` ненулевые у 2 917.

### 3.4 `+0x54` / `+0x58` (`uv_u_fp/uv_v_fp`)

* `0x43e69d`: `uv = (int)(poly+0x54) >> 6`, затем деление на 32 — привязка
  выборки лайтмапа к сетке (`0x43e6xx`), запись обратно `+= 0x40`.
* `0x43c51f` / `0x43d8e3`: `(uv_fp + dot(axis, hit-centre)*64)/2`, затем
  `>> 10` и маска страницы лайтмапа — выборка яркости лайтмапа в точке удара.
* `0x434887`: при перемещении объекта (дверь/лифт) пересчитывает `0x54/0x58`,
  если у объекта **нет** флага `0x100000`.

### 3.5 `+0x70` brightness (u8) — и `obj+0x74`, `sector+0x16`

`0x43c51f` и `0x43d8e3` (трасса + выборка света) складывают три источника:

```
local_81c = (signed char)poly[0x70] + (signed char)obj[0x74] + (signed char)sector[0x16]
            + lightmap_byte(...)
clamp(-0x80, 0x7f)
```

Отсюда:

* `poly+0x70` — собственная яркость полигона (в данных — кратные 8, мода 8,
  есть 0 и 255; `0x433b53` принудительно ставит `0x7f`);
* `obj+0x74` — **знаковая поправка яркости объекта** (в поставке 0; старая
  карта называла поле «runtime aux» — это неверно, потребитель есть);
* `sector+0x16` — байт света сектора (`SET_SECTOR_BRIGHTNESS`).

## 4. Флаги объекта (`obj+0x70`, `+0x80`, `+0x90`)

### 4.1 `+0x70` — битовое поле

| бит | смысл | доказательство |
|---:|---|---|
| `0x10` | объект не участвует в луче/трассах | `0x437d05` (`0x437dxx`: `AND ...,0x10010`), `0x4392de`, `0x43cd32` |
| `0x10000` | то же (объединено в маску `0x10010`) | те же три места; в данных 1222 объекта только с этим битом |
| `0x20000` | форс-рендер «владельческого» объекта в мировом проходе | `0x4409b8` (`0x440xxx`: `if (param_3 != 0 \|\| obj->0x80 == 0) \|\| (obj->0x70 & 0x20000)`) |
| `0x40000` | массив полигонов **не принадлежит** объекту (не освобождать) | `0x422ab6` (`0x422axx`) |
| `0x80000` | массив вершин не принадлежит объекту | `0x422ab6` |
| `0x100000` | не пересчитывать `uv_*_fp` при трансформе | `0x434887` (`0x4348xx`: `if (param_12 && !(obj+0x70 & 0x100000))`) |

Наблюдённые значения в 36 уровнях: `0` — 26 664, `0x10000` — 1 222,
`0x20` — 143, `0x100000` — 83, `0x8` — 31, `0x10010` — 28, `0x10` — 16,
`0x10020` — 3, `0x10008` — 2. Биты `0x8/0x20` потребителей не нашли
(кандидаты — геймплей/скрипты), маска `0x10010` для луча доказана.

### 4.2 `+0x80` — владелец

`0` — статическая геометрия уровня; иначе — указатель на **экземпляр вещи**
(пул `0x71cd40`, шаг `0x148`; `+0x128` — «in use»):

* `0x435995` (`0x4359xx`) — при удалении объекта из сектора правит у владельца
  списки `+0xa8[32]` (сектор) и `+0xe8[32]` (индекс полигона), иначе
  «deleteobject is in use»;
* `0x429e3b` — лайтмапы остаются только у объектов с `owner == 0`, у
  владельческих `lightmap` обнуляется;
* `0x42f183` — портальная склейка только для `owner == 0`;
* `0x42d045`, `0x437c4e` — возвращают `owner` как результат трассы (во что
  попали).

Старая формулировка «указатель на модель `0x148`» неточна: это запись
**экземпляра**, а не модель-ассет.

### 4.3 `+0x90` — extent (3 × `f64`)

В поставке **всегда 0** (0 объектов из 28 192). Читается как `f64`:

* `0x434fed` (`0x4350xx`): `min = origin − bounds + min(0, extent)`,
  `max = origin + bounds + max(0, extent)` — то есть extent **расширяет**
  AABB сектора только в свою сторону (`fabs` в куллинге луча `0x437d05`,
  `FUN_004804b0`);
* `0x440867`: `memset(0x5733b8, 0, 0x400)` и по секторам:
  `if (extent.x != 0 || extent.y != 0 || extent.z != 0) flag[sector] = 1` —
  «сектор содержит объекты с extent» (флаг читается рендером/коллизией);
* `0x437d05`: `|extent|` прибавляется к радиусу сферы объекта при выборе
  сектора лучом.

Писателей в загрузчике нет (поле читается из файла как 24 «reserved» байта,
`0x425fxx`); в рантайме его, видимо, заполняют скрипты/двери — в поставке не
встречается.

## 5. Ссылки полигона `+0x72` / `+0x74` / `+0x76`

Порядок на диске — **`0x72, 0x74, 0x76`** (это видно по порядку чтения в
загрузчике `0x425f4c`: сначала `local_c+0x72`, затем `+0x74`, затем `+0x76`;
`sector` — `0x72−1`, `object` — `0x74`, `poly` — `0x76−1`). Поэтому
`gm/sbw.py` (`Poly.f74/f76/handle`) и `engine/src/res/sbw.h` хранят **дисковые
слоты**, а не одноимённые смещения: `f74` = `+0x72`, `f76` = `+0x74`,
`handle` = `+0x76`.

Потребители:

* `0x42f183` — резолв/склейка порталов: только объекты с `owner == 0` и только
  полигоны с `texture != 0`; при совпадении всех трёх полей вызывается
  `0x42f46a` (геометрическая склейка, затем `0x422ab6` + `0x43529f`), а
  ссылки переписываются в маркеры: `0x72 = 0x7ff9` (тот же сектор) или
  `0x7ff8` (другой сектор). У **нетекстурированных** полигонов, чья ссылка
  указывает на текущий сектор (`0x72−1 == sector`), тройка полей обнуляется.
* `0x42d045` — переносит вершины по маркерам `0x7ff8/0x7ff9` (портальный
  трансформ, `+0x54/+0x58` пересчитываются).
* `0x43869a` — при выборе сектора камерой ставит биты «портал впереди/сзади»
  по `poly+0x72 != 0` (биты 1/2 локального флага).
* `0x426ac3` — писатель `.sow`: `0` → `none`, `== sector+1` → «this sector»,
  иначе — номер сектора.

Данные (36 уровней): `0x72` ≠ 0 у 11 356 полигонов, `0x74` ≠ 0 у 1 022,
`0x76` ≠ 0 у 586; совпадает с `sector+1` ровно **1**. Полигонов с
`texture != 0` **и** всеми тремя ненулевыми полями — **1** (`level12.sbw`,
сектор 204/объект 7/полигон 1 при источнике 204/6/18). То есть в поставке
склейка порталов практически не работает: 99.9 % ссылок — остаток экспорта
(у них нет текстуры, и `0x42f183` их не трогает).

## 6. «Конверсия `f32` → `f64`»: конверсии нет

Старая карта предполагала, что 96-байтовый заголовок объекта — это 12 пар
`(u32 pad, f32)`, которые загрузчик копирует «как есть», а где-то потом
превращает в `f64`-трансформ. Проверка опровергает это:

1. **Загрузчик читает 96 байт в `origin/basis` без преобразования**
   (`0x42ae86`, `0x42aea7`, `0x42aec8`, `0x42aee9` — четыре `fread` по 24 Б
   прямо в `obj+0x00/+0x18/+0x30/+0x48`).
2. **Трансформ работает с `f64`** — `0x437af8`:
   `FLD double ptr [ECX+0x18]` / `FMUL` / `FADD double`; входные локальные
   вершины — `FLD float ptr [EAX]`, результат — `FSTP double`.
3. **В данных младший dword каждого 8-байтового слова = 0 у всех 338 304
   слов** (28 192 объекта × 12) — это ровно то, что даёт `f64`, полученный из
   `f32` (низшие 32 бита мантиссы нулевые). Читать их как `f32` из старшего
   dword — артефакт: `f32`-биты `1.0` (`0x3FF00000`) дают `1.875`, отсюда и
   «масштаб 1.875».
4. **Базис единичный**: норма каждой из 84 576 строк `basis` равна ровно
   `1.0` (в `f64`-чтении); в `f32`-чтении — ровно `1.875` (масштаб).
5. **Геометрия сходится с AABB сектора только в `f64`**: бокс сектора
   `origin ± bounds` (его строит `0x434fed` из `origin`) содержит все вершины
   сектора у **4716 из 5104** секторов; в `f32`-кадре — **0 из 5104**.
6. Косвенно: `level0` объект 0 в `f64` даёт `origin = (1432, 7568, 48)`;
   `z = 48` совпадает с `z` игрока в сейве `level0` (наблюдение из
   `docs/WORLD_FIELDS.md` §3), в `f32`-кадре `z = 3.125`.

**Итог.** Заголовок объекта в `.sbw` — 12 little-endian `f64`: `origin[3]` +
`basis[3][3]`, `world = origin + basis·local`, базис — единичный (поворот).
Никакой конверсии в загрузчике/трансформе нет; «1.875» — это `f32`-биты
`1.0`, а не масштаб файла. Множитель `1/1.875` в `gm/scene.py` (`SCALE`)
относится к **другой** вещи — единицам скриптов SBT (они в 1.875 раза
крупнее геометрии `.sbw`); это отдельный вопрос, к кодировке заголовка он не
относится.

Следствие (не правил, вне моей зоны): `gm/sbw.py::_points` и
`engine/**` читают старший dword как `f32` и получают кадр
`origin32 + 1.875·local`; паритет C++/Python от этого не страдает (оба
реализуют одну и ту же неверную модель), но с рантаймом она не совпадает.
`tools/re/world_fields.py` использует тот же `f32`-разбор (совместимость с
`gm/sbw.py`), а `tools/re/materials.py` проверяет заголовок независимо, как
`f64`.

## 8. Открытые вопросы

1. **`+0x2c` (и `+0x04/+0x08/+0x0c/+0x14/+0x30`) — мёртвые поля?** Читателей в
   `gundx.exe` нет (полный xref + байтовый скан). Не проверено: `gun.exe`
   (DOS/4GW-сборка, 3 МБ) — там должен быть программный рендер, который эти
   LUT использует; но это другой бинарь, вне задачи.
2. **Второй проход оверлея в рендере.** Полигон с `overlay != 0` участвует в
   трассах/лайтмапах, но прохода отрисовки оверлея в `gundx.exe` не найдено
   (рендер `0x4409b8` вообще не читает `texture/overlay/brightness` — он
   рисует грани через `lighttable`, а текстуры отдаёт D3D через IAT
   `0x4d74xx`). Утверждение старой карты «второй проход рендера `0x437fd5`»
   неверно: `0x437fd5` — это цикл полигонов внутри луча `0x437d05`.
3. **Биты `obj+0x70` `0x8` и `0x20`** (31 и 143 объекта) — потребителей не
   нашли; вероятно, геймплей/скрипты.
4. **Кто пишет `obj+0x90` (extent)** в рантайме: в загрузчике только чтение,
   в поставке нули, флаг `0x440867` не взводится. Кандидаты — скриптовые
   команды, но подтверждения нет.
5. **Единицы SBT vs `.sbw`** (множитель 1.875 в `gm/scene.py`): требует
   отдельного разбора, здесь только зафиксировано, что он не про заголовок.
