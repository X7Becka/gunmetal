# Предметы: подбор, маркеры регенерации, вирус и щиты (`M6.2.6`)

**Статус:** модель снята по коду игры (дизассемблер, только чтение) и сверена
с 36 поставочными `.sbt`; инструмент — `tools/re/pickup.py`
(`--self-test`, `--summary`, `--fields`, `--json`, `--items`, `--anchors`).
Все утверждения ниже либо помечены «код» (проверено `tools/re/disrange.py`,
адрес указан), либо «данные» (проверено по `.sbt`), либо «гипотеза».
Байтовых якорей — 53/53 (`python3 tools/re/pickup.py --anchors`), SHA exe:
`929ffa72…` (см. `docs/BASELINE.md`).

Смежные документы, которые здесь **не** пересказываются: `docs/RECORDS.md`
§3 (запись `ITEM`), `docs/SBT_RECORDS.md` §2.5 (`NAMED_ITEMS`),
`docs/ECONOMY.md` (деньги/щиты/вес), `docs/EQUIPMENT.md` (экипировка),
`docs/DM_RULES.md` §2 (режимы), `docs/VM_EXEC.md` (опкоды),
`docs/ENTITY_FIELDS.md` (вещи/things), `docs/PLAYER_FIELDS.md` (поля игрока).

## 0. Итог

* **Подбор — не «касание объекта», а радиус-скан.** Триггер предмета
  (`+0x44`) постит функция `0x469770`, её зовёт физика игрока `0x443690`
  каждый тик (`0x445165`) с флагами `3`; она перебирает 300 записей и берёт
  `state 0/-1` (бит 0) и `-4` (бит 1), сравнивая расстояние с **радиусом
  самого предмета** `+0x4c`. Второй вызывающий — код вещей `0x471e03`.
* **Награду выдаёт скрипт, а не движок.** `+0x44` — id события; под-скрипт
  сущности делает `ADD_SOURCEPLAYER_CASH/SALVAGE`, `HEAL_SOURCEPLAYER`,
  `ADD_SOURCEPLAYER_AMMO`, `SOURCEPLAYER_INFECT`, а затем обычно
  `REMOVE_SOURCE_ITEM` (op 39 → `0x469020`). 690 из 1138 предметов с
  ненулевым триггером разрешаются в существующую сущность, 448 имеют
  `trigger = 0` (и радиус 0) — это декор.
* **Состояния:** `-2` свободен, `-1` «фантом» (объекта нет, но срабатывает
  по радиусу), `0` живой, `-3`/`-4` взведённые мины (`-4` ещё и цепочка +
  взрыв), `>0` таймер появления (тики 91 Гц). **Создают объект только
  `0`/`-3`/`-4`** (`0x4687e8/0x4687ed/0x4687f2`). Состояния «-5» в бинарнике
  нет.
* **`-3` → `-4`** — автоматический переход в апдейтере: если в радиусе
  предмета **нет** игрока, состояние становится `-4` (`0x4695d4`).
* **Респавн:** при снятии предмета `+0x3c` (2-й операнд) задаёт поведение:
  `0` — слот свободен, `>0` — тики до появления, `<0` — только в DM
  (маркер + `|+0x3c|` тиков). Маркер (`PUMARKER`) создаёт `0x468840` моделью
  из `0x80d878` (sob 19 во всех 36 уровнях).
* **Вирус** (`DEFINE_VIRUS`): заражение ставит `0x81c240 |= 0xc0`
  (игрок) или `0x7ac3e0 |= 0x18` (вещь); у игрока 4 плиты щита
  `0x81c290..0x81c29c` дренируются на `dt · L0` за тик; вирус снимается,
  когда все 4 плиты дошли до нуля (`0x443e10`); заражение контактное.
* **Щиты** (`DEFINE_SHIELDS`): `[50, 0]` во всех 36 уровнях — цена 100 щитов
  и вес 100 щитов (`0x45c359`, `0x45c364`).

### 2.2. Создание записи `0x4686a0`

Аргументы (0-базные) → поля: `arg0 → +0x40` (sob), `arg1 → +0x38` (state),
`arg2 → +0x3c`, `arg3/4/5 → +0x18/+0x20/+0x28` (позиция, `fild`),
`arg6..11 → +0x00..+0x14` (базис, 3 double), `arg12 → +0x44`,
`arg13 → +0x48`, `arg14 → +0x4c`, `arg15 → +0x50 и +0x54`, `arg17 ≠ 0 → kind 1,
иначе 2` (`0x468715`/`0x468720`), `arg18 → +0x5c`, `arg16` передаётся в
`0x4684b0` (не используется). Соответствие операндов опкодов — §5.

Порядок:

1. `arg0 < 0` → ошибка «Unable to add Item, SOB not loaded.» (`0x4ba200`);
2. поиск первого слота со `state == -2` (`0x4686d2`); нет — «Maximum number of
   items exceeded» (`0x4ba1d4`, предел `0x12c` = 300);
3. запись полей;
4. `state` ∈ `{0, -3, -4}` → `0x46882b` → `0x4684b0` (создать объект);
5. иначе, если `[0x83d2c8] != 0` (не кампания, `0x4421c0`) и `state > 0` →
   `0x468840` (объект-маркер) и выход;
6. иначе — отказ: `+0x30 = 0`, возврат `-2` (`0x468819`, `0x468823`).
   Состояние при этом **не** меняется — слот остаётся занятым (см. `-1`).

`0x4684b0(slot, …)`: `SOB_TABLE[+0x40]` → `0x47c990` → `0x4277cd`; ошибки
«unable to get SOB handle» (`0x4ba1a4`) и «engine_addobject failed»
(`0x4ba130`); позиция копируется в объект, `0x41e025` строит матрицу,
`0x4360f1` сажает на землю, `0x43b639` создаёт объект; `+0x30` = объект.

## 3. Состояния

| state | имя | создаёт объект | что делает код |
|---:|---|---|---|
| `-2` | free | — | слот свободен (`0x4686d7`, `0x469050`, `0x469099`) |
| `-1` | phantom | **нет** | слот занят, объект не создан; радиус-скан его берёт (бит 0); op 39 освобождает слот (`0x469047..0x469052`); в сейв не попадает (`0x466340`) |
| `0` | live | да | обычный предмет; подбор по радиусу; снятие → свободен либо таймер |
| `-3` | armed | да | мина: триггер по контакту (`0x4692be`); при отсутствии игрока в радиусе → `-4` |
| `-4` | chain | да | мина «взведена»: контакт, взрыв (op 75), цепочка соседей |
| `>0` | timer | нет (в кампании) | `state -= dt` каждый тик (`0x4694dc`); по нулю — маркер заменяется предметом и постится `+0x48` (`0x46950c`, `0x46952b`) |

Переходы (все — код):

```
создание: 0,-3,-4 -> объект (+0x30);
          -1       -> объекта нет, слот занят (0x468819);
          >0       -> маркер 0x468840 только вне кампании, иначе отказ
апдейтер: state > 0        -> state -= dt; 0 -> state = 0, kind = 1 (если 0),
                              destroy, 0x4684b0, пост +0x48   (0x4694dc..0x469557)
          state <= -3      -> если игрока в радиусе нет: state = -4, пост +0x48
                              (0x46956d..0x4695da)
          state 0/-1/-2    -> таймер +0x50; 0 -> 0x469020 (снятие)
снятие (op 39, 0x469020):
          state == -1      -> -2 (свободен)                    (0x469050)
          state == -2      -> ничего                         (0x4690de)
          state == 0 или <= -3:
              destroy; +0x3c > 0  -> (в DM маркер) state = +0x3c   (0x4690a8..0x4690cc)
              +0x3c == 0          -> в DM свободен, иначе свободен (0x469099)
              +0x3c < 0           -> только DM: |+0x3c| + маркер, иначе свободен
```

В поставочных данных встречаются `0`, `-1`, `-3`, `-4`, `36`, `45`, `91`,
`5460`, а в `NAMED_ITEMS.f2` ещё `50`, `-5460`, `-10920`, `-17800`
(см. §6). Любое `state <= -4`, кроме `-4`, апдейтер нормализует в `-4` на
первом же тике, если рядом нет игрока (`0x4695d4`) — поэтому «-5460» у
именованных предметов ведёт себя как «взведён»; задержкой респавна это
**не** является (задержка — `f3 → +0x3c`, у всех записей `0`).

## 4. Кто постит `+0x44`

| путь | точка входа | подробности |
|---|---|---|
| радиус игрока | `0x469770` ← `0x445165` | физика игрока `0x443690` (вызов из `0x44d923`) каждый тик зовёт `0x469770(player, x, y, z, 3)`; перебор 300 записей, `state 0/-1` при `флаги & 1`, `-4` при `флаги & 2`; условие `distance < +0x4c` (`0x4344df` — длина, `0x4695b1`/`0x4697eb` — `fild` радиуса) |
| радиус вещи | `0x469770` ← `0x471e03` | вещь с битом `0x80` в `+4` или `0x800000` в `+8` (флаги `0x7ac3e4`/`0x7ac3e8`) тоже сканирует предметы вокруг себя, флаги `3` |
| взрыв | `0x4698b0` ← op 75 `0x4577f9` | только `state == -4` (`0x4698dd`); радиус = аргумент × 0.5 (`0x4a2608`); источник = handle + `+0x5c` |
| цепочка | `0x469670` | из апдейтера при `state == -4` (`0x4692af`, `0x46938b`) и при взведении (`0x469612`); все прочие `state == -4` в радиусе 40.0 (`0x4a2600`), кроме себя (`0x4696a2`) |
| снятие с обновления | `0x4690f0` | если трансформ предмета не пересчитался (`0x43c51f` — «targetpointinworld2listfromobject», `0x434c11` — дельта сектора/объекта, сравнение с 0.0 `0x4a25f0`), то `kind = 0` (`0x46929c`/`0x469378`) и для `state -3/-4` постится `+0x44` (`0x4692c7`, `0x4693a3`) |

Пост — всегда `event_post` `0x4795b0`:

```
event_post(id, 0, 0, 0, x, y, z, source)
x,y,z  — позиция предмета (f64, +0x18/+0x20/+0x28)
source — (0x10c + slot) << 16 + [+0x5c]
```

Связанные опкоды:

* **39 `REMOVE_SOURCE_ITEM`** (`0x457bc0`): handle из источника → слот
  (`(h>>16)&0xffff`, диапазон `0x10c..0x237`, `0x457bc8`) → `0x469020`.
* **64 `ITEMS_MOVE_CHECK`** (`0x457c26` → `0x469880`): для записей
  `kind == 0`, `state <= 0`, `state != -2` ставит `kind = 1` (`0x46989f`) —
  «вернуть предмет в обновление».
* **65 `SET_SOURCEITEM_TRIGGER_EVENT`** (`0x457bf1`): `+0x44 = операнд`
  (`0x46900e`); мины обнуляют свой триггер, чтобы цепочка не зациклилась.
* **75 `CAUSE_BLAST_RADIUS_DAMAGE`** (`0x45775b` → `0x4698b0`).

| 2 | `+0x3c` respawn | да | да |

`kind`: 52/53 → 1, 54/55 → 2 (`0x468715`/`0x468720`, `arg17`); AT_SOURCE
берёт позицию объекта-источника из кадра VM (`[ebp+0x1c..0x24]`), остальные —
из операндов. «FIXED» — только `kind = 2` (не двигается сектором).

### 5.2. `ADD_RANDOM_AMMO_ITEM_AT_SOURCE` (177)

Один операнд — **state** (`0x45be5c` → `0x450940`); sob, trigger и radius
берутся из записи `DEFINE_AMMO` (`+0x14`, `+0x18`, `+0x1c`, `0x450aeb`),
позиция — источника, `kind = 1`, `+0x5c = 0xffffffff` (литерал `0x450aa6`).
Все 440 вызовов лежат внутри `IF DEATHMATCH_GAME` (данные, `--summary`),
state: `5460` ×396, `91` ×36, `0` ×8.

### 5.3. Именованные предметы (185/186 → `0x468d40`)

`ADD_NAMED_ITEM` (`ILLLAAA`, индекс в операнде 0) и `ADD_NAMED_ITEM_EX`
(`LLLILLLAAA`, индекс в операнде 3) берут поля из `NAMED_ITEMS` (тип 5,
52 байта, `name[16] + f0..f8`):

```
f0,f1 -> min/max игроков (сравнение с [0x83d62c], 0x468d67/0x468d6f)
f2    -> +0x38 state       f3 -> +0x3c respawn
f4    -> +0x40 sob         f5 -> +0x44 trigger
f6    -> +0x48 appear      f7 -> +0x4c radius
f8    -> +0x50 и +0x54 timer
kind: 185 -> 1, 186 -> 2 (0x468d86 push 1 / 0x459ae8.. push 0)
```

Индекс `-1` → запись не создаётся (`0x468d52`, возврат `-1`); в корпусе таких
две инструкции (`level16.sbt`, `level24.sbt`). В `--summary` состояния
именованных предметов считаются по разрешённым записям.

`CAUSE_BLAST_RADIUS_DAMAGE 0,0,10000,0,400,0`, `GENERATE`. Салваж-поды
(`0x4326`, `0x4353`, `0x43d7`, …) — `state 0`, радиус 200, триггер
`-30083/-30085/-30086` → `ADD_SOURCEPLAYER_CASH` + `…_SALVAGE` +
`REMOVE_SOURCE_ITEM`. Невидимые лечилки (`0x6fee`, `0x700b`, …) —
`state -1`, радиус 1600/200, триггер → `HEAL_SOURCEPLAYER`.

## 7. Маркер регенерации (`DEFINE_REGENERATION_MARKER`, 174)

```
опкод 174, сигнатура ODD: dword -> 0x80d878 (sob), double -> 0x80f9e0,
double -> 0x80f830                       (0x45c375..0x45c39f)
в корпусе: [19, 3000.0, 50.0] во всех 36 уровнях (данные)
SOB_TABLE[19] = PUMARKER в level0/level15/dm1 (данные)
```

Потребитель — `0x468840(slot, …)`: берёт `[0x80d878]` как sob, создаёт объект
в позиции/базисе записи и кладёт в `+0x30`; ошибки «…get item's object3di»
(`0x4ba2b4`). Вызывается из создателя (`0x468807`) и из снятия
(`0x4690b8`) — то есть в DM вместо пропавшего предмета появляется маркер,
а `state = |+0x3c|` отсчитывается до нового появления (`0x4694dc..0x46950c`).

Два double (`0x80f9e0`, `0x80f830`) **не читает никто**: кроме записей
`0x45c38a`/`0x45c399` есть только обнуления при загрузке уровня
(`0x45713f`, `0x457153`). Их смысл — **не найдено** (гипотеза: радиус/высота
маркера из редактора, в этом билде не используется).

**Итого по опкоду 174:** sob-часть жива (в DM вместо пропавшего предмета
появляется маркер, §7 выше), а «регенерационные» double-поля мертвы —
именно их имеет в виду `docs/DAMAGE.md` §6 («регенерация в 1.36 не
работает»).

## 8. Вирус (`DEFINE_VIRUS`, 173)

```
опкод 173: 5 × dword + double  (0x45c3a4..0x45c3f9)
L0 -> 0x80d8b4  урон щиту за тик
T  -> 0x80d880  текстура заражения (0x453923: если флаг 0x80 — взять T)
N  -> 0x80d884  сэмпл петли
V  -> 0x80d890  громкость
P  -> 0x80d8b8  приоритет
D  -> 0x80f9c0  затухание (double)
```

В корпусе: `L0 = 16`, `V = 28`, `P = 10`, `D = 0.03` везде; `N = 12`
(34 уровня) и `22` (`dm2.sbt`, `level15.sbt`); `T` — 76…251, по уровню свой.

**Заражение.** Опкод 123 `SOURCEPLAYER_INFECT` (`0x45a6aa`): игрок —
`0x81c240 |= 0xc0` (`0x45a6d9`, затем `0x4538d0`); вещь —
`0x7ac3e0 |= 0x18` (`0x45a71a`, затем `0x46ca40`). Биты `0x80`/`0x40`
у игрока: `0x80` — «заражён» (подмена текстуры, `0x453919`), `0x40` —
вирус активен (снимается по концу).

**Дренаж щита.** `0x443c7a..0x443e03`: 4 плиты `0x81c290 + 4·i`
(у игрока 0; смещение `+0x3250`), каждая `plate -= dt · L0`
(`0x443c8f`: `imul edx,[0x80d8b4]`); по `<= 0` плита обнуляется и
обрабатывается побочный эффект (переключение текстур/вспышка через
`0x4452f0`). Для вещей — `0x471810` (те же 4 плиты в блоке вещи).

**Конец.** Когда все 4 плиты дошли до нуля (`0x443e09`: счётчик == 4),
снимается бит `0x40`: `and al,0xbf` (`0x443e16`); далее `0x4538d0`
возвращает обычную текстуру.

**Контагиозность.** `0x443e23..0x443eb5` — по игрокам: если расстояние
меньше `player+0x81bda8` + собственный радиус цели (`player+0x2d68`), то
`флаги |= 0xc0` и `0x4538d0`; `0x443ec3..0x443f56` — по вещам (шаг 0x528):
бит `0x1` в `[thing]`, не бит `0x40` в `[thing+4]`, расстояние меньше
`player+0x81bda8` + `[thing+0x60]` → `[thing] |= 0x18` и `0x46ca40`.
То есть вирус передаётся и игрокам, и вещам-«монстрам».

**Звук.** Петля 3D: `0x46bb2c..0x46bb8a` читает `0x80d884` (сэмпл),
`0x80d890` (громкость), `0x80d8b8` (приоритет) и `0x80f9c0` (затухание) и
зовёт `0x46b9f0(sample, class, volume, rate, priority, x, y, z, atten)`.

## 9. Щиты (`DEFINE_SHIELDS`, 176)

```
опкод 176, сигнатура LL: arg0 -> 0x818954, arg1 -> 0x818950 (0x45c353..0x45c36d)
в корпусе: [50, 0] во всех 36 уровнях (данные)
```

Потребители (подробно — `docs/ECONOMY.md` §4, §8):
`0x818954` — цена 100 щитов (`0x452fb1`, `0x45bc6d`, `0x479e08`),
`0x818950` — вес 100 щитов (`0x4524d6`, `0x4524fe..0x452526`).
Само значение щита игрока — те же 4 плиты `0x81c290..0x81c29c`

## 10. Расхождения с существующими документами

1. **`docs/RECORDS.md` §3 и `tools/re/records.py:ITEM_FIELDS`** называют
   `state -1` «active», а `0` — «(re)spawn», `-3/-4` — «pending removal».
   По коду: `-1` — **фантом без объекта** (§3), `0` — обычный живой предмет,
   `-3/-4` — **взведённые мины**, которых никто автоматически не удаляет;
   удаление делает только скрипт (op 39) или таймер `+0x50`.
   Константы `ITEM_ACTIVE = -1`, `ITEM_PENDING = (-3, -4)`,
   `ITEM_SPAWN = 0` в `records.py` — только имена, проверки `--check` при
   этом корректны (наборы состояний совпадают), но семантика в комментарии
   неверна.
2. **`+0x54`** в `records.py` назван `op6_hi`/«copy of +0x50» — по коду это
   `timer_reload`, из него восстанавливается `+0x50` при респавне
   (`0x4690d2` → `0x4690d8`), а не «второй операнд».
3. **`+0x5c`** в `records.py` — «sentinel, 0xffff written by all four
   handlers». На самом деле это слагаемое к handle при посте события
   (`0x4692d8`), значение = `eax & 0xffff` из контекста VM (`0x4573ae`),
   т.е. у op 52–55 обычно `0x0000ffff`, а op 177 пишет литерал `0xffffffff`
   (`0x450aa6`). Название «sentinel» описывает только наблюдаемое значение
   в сейвах.
4. **`-5`**: в прошлых заметках (`docs/RECORDS.md`,
   `docs/EQUIPMENT.md` §7) упоминалось состояние `-5`. В бинарнике его нет:
   создатель принимает ровно `0`, `-3`, `-4` (`0x4687e8`, `0x4687ed`,
   `0x4687f2`), константы `0xfffffffb` в коде нет.
5. **`docs/SBT_RECORDS.md` §2.5** — подтверждено полностью (`f2 → +0x38`
   и т.д.); добавление: `f3` (задержка) во всех 1160 записях корпуса равен
   `0`, поэтому именованные предметы в DM **не** респавнятся, а их
   отрицательные `f2` — не задержки, а «взведённые» состояния (§3).

## 11. Гипотезы и что осталось

* **Смысл ветки «снятие с обновления»** (`0x4690f0` → `kind = 0` +
  пост `+0x44` для `-3/-4`): по инструкциям это происходит, когда позиция
  предмета не пересчиталась ни через `0x43c51f` (targetpointinworld2…),
  ни через `0x434c11` (дельта сектора/объекта), т.е. предмет «потерял»
  движущуюся опору. Игровое намерение (взорвать мину, потерявшую
  платформу?) — **гипотеза**.
* **Почему у именованных предметов `f2 = -5460/-10920/-17800`**, если
  задержка лежит в `f3` (и там `0`): похоже на наследие редактора
  (значение «рес­павн, с» с минусом). Влияние на игру: любое `<= -3`
  нормализуется в `-4` за один тик, поэтому фактически это «взведён».
* **`+0x58`** (байт → `object+0x74`): источник — стек апдейтера
  (`0x469239`, `[esp+0x20] - 0x50`), смысл не установлен (**гипотеза**:
  видимость/альфа при «снятии»).
* **`0x80f9e0`/`0x80f830`** (double из `DEFINE_REGENERATION_MARKER`) —
  читателей нет (§7).
* **Флаги `0x469770`**: бит 0/1 доказаны вызовами (`3` у игрока и вещей),
  но зачем вещам бит 1 (`-4`) — не проверено; возможные значения 0/1/2
  в поставочных данных не встречаются.
* **Первый спавн DM-ящиков**: `state 5460` (60 с) у всех 396 вызовов
  op 177; в DM создатель сразу ставит маркер и отсчитывает `5460` тиков,
  т.е. ящик появляется через 60 с после старта уровня. Это буквально то,
  что делает код; намерение (задержка первого спавна vs. таймер респавна,
  случайно применённый и к первому) — **гипотеза**.
* **`+0x50` timer**: код снимает предмет по истечении (через `0x469020`),
  но зачем одним предметам `109/259/664/728/910/5460` тиков, а другим `0` —
  не документировано; в корпусе это, видимо, «время жизни» дропа.
* **`ITEM_SLOTS` и сейв**: `saved0.sbt` содержит 300 слотов, 2 занятых
  (`state -1`, sob 41 и sob 36) — это `ADD_NAMED_ITEM` (SMSW803, `f2 = -1`)
  и `ADD_ITEM_FIXED` (`state -1`); проверено
  `python3 tools/re/records.py "…/saved0.sbt" --type 19`.
